## 对上述文档的独立复核与批判（推翻多处结论）

- 新建文档：`AGENT服务/Multi-Agent必要性-独立复核与批判.md`；并在原文档顶部加了修订指引（原文档 §0 总表、§2 拆分结论、§5 优先级已失效；§1.2 反判据 R1–R4 与 §3 通用不变式仍有效）。
- **批判结论**：原七条判据中 4 条不成立/归错层、1 条方向说反、2 条夸大。
  - C2 对抗校验**因果倒置**：审核的价值在"引入生成方没有的外部证据"（CRITIC ICLR2024 消融：移除工具验证后提升消失；Huang et al. ICLR2024：无外部反馈时自我纠正反而更差），不在"换个 Agent"。
  - C6 概念混淆：CP-SAT 求解器是服务不是 Agent（按此定义带计算器即 Multi-Agent）。
  - C7 归错层：多角色审批链是工作流引擎/权限系统职责，不是 Agent 职责。
  - C4 因果错误：长程任务需要的是外部化状态（LangGraph checkpoint/Temporal/状态机），不必然需要 Multi-Agent。
  - C5 方向说反：同进程下"隔离"只是 prompt 层工具可见性，非安全边界；且多 Agent 因 Agent 间通信通道而**扩大**攻击面。
- **重要概念区分**：sub-agent（单 Agent 框架内的上下文隔离技巧）≠ multi-agent 系统。原文档多处混用。
- **收敛后结论**：真正需要 Multi-Agent 的只有"广度优先的只读取证"一类（影响面清点、限定分支后的 RCA 取证）；其余 8 个模块退化为"单 Agent + 工具/服务 + 工作流引擎"。排产属 Agent+求解服务混合架构，求解器不算 Agent。
- **前置前提**：MES 场景真正瓶颈常是**数据就绪度**（过点记录是否绑定设备参数/工艺版本快照、批次绑定完整性），不是 Agent 架构；动架构前先补数据 + 建离线评测集（否则无法证明"拆了更好"，易落入 Tran & Kiela 指出的算力混淆陷阱）。
- 引用分级纪律（后续文档沿用）：【A】同行评议论文 /【B】厂商可溯源报告 /【C】二手聚合需核对 /【推】推断 /【设】未验证假设。

## 通用文章：哪些场景真正需要 Multi-Agent 系统（可独立发布）

- 新建文档：`AGENT服务/哪些场景真正需要Multi-Agent系统.md`（脱离 MES 语境的通用稿，篇幅中等，含小结，可直接成篇发布）。
- 结构：概念澄清（sub-agent ≠ multi-agent；工具/服务 ≠ Agent）→ 判断标准 → 五类场景 → 成本与边界 → 落地路径 → 小结。
- 严格定义：Multi-Agent = 两个及以上自主决策的 LLM 实体，各持不同上下文/工具/职责，通过显式协议交换信息。
- 三条硬判据（与复核文档一致）：① 工具或知识域冲突且**分层路由解决不了**（先试路由，别直接拆）；② 存在**真独立**子任务且延迟是真瓶颈（检验法：拿掉一个子任务输出，另一个会变吗）；③ **信息或能力不对称**（审核方须有生成方拿不到的外部证据——CRITIC 消融依据）。
- 五类真受益场景及核心机制：① 复杂需求多角色交付（验证方拿执行证据，不得修改验收闸门）；② 广度优先并行调研（真独立 + 就地压缩，只读）；③ 长链路数据交叉验证（独立数据源/方法重算；**确定性环节仍需留在代码里**）；④ 质量与效率分层流水线（小模型跑量+强模型把关，利用写难验易，独立采样聚合常优于辩论）；⑤ 对抗式评审与博弈推演（反对方须拿到不同输入，否则信念固化成回音室）。
- 立场：不吹捧。成本项含 token 一个数量级、协调复杂度组合数增长、每步概率乘法、trace 与契约治理、攻击面扩大；并提示"模型进步会吞掉编排类用例"，需预留回退。

## 落地篇：Multi-Agent 真实业务场景详解

- 新建文档：`AGENT服务/Multi-Agent真实业务场景详解.md`（上篇的落地深化，六段式模板：业务背景 → 角色与诉求 → 现状痛点 → 引入后流程 → 关键数据流转 → 可衡量价值 → 边界）。
- 五个真实业务案例（跨行业，脱离 MES 语境）：
  1. **SaaS 特性交付**（规格/实现/验证 Agent）：成立机制=验证方拿执行证据且不得改验收闸门；边界=lint/类型检查/单测/CI 留在确定性链。
  2. **PE 尽职调查**（规划 + N 路并行检索 + 交叉核对 + 汇总）：成立机制=子问题正交 + 就地压缩 + 只读；关键 artifact=可回溯的引用锚点。
  3. **集团月度经营对账**（双路独立重算）：**核心提醒=取数/清洗/比对/断言必须用代码**，Agent 只做口径歧义消解与异常归因；关键 artifact=口径定义文件（本月裁决固化供下月复用）。
  4. **跨境电商内容本地化**（规则分层 + 小模型跑量 + 强模型终审）：成立机制=按风险分层投入算力 + 写难验易；合规判定须引规则库条目，不能靠模型记忆。
  5. **银行对公授信评审**（提案 vs 红队 vs 裁判）：成立机制=红队持有提案方不可见的外部数据源；反面警示=同材料"唱反调"会成回音室（信念固化）。
- 四条共性结论：① 全部命中"信息不对称"或"真并行"，无一靠"多角色"本身取胜；② 确定性环节全部留在代码；③ 写操作与最终决策在人；④ 价值落在周期缩短与覆盖率提升，而非替代人。
- **写作纪律（后续沿用）**：场景文章中的业务价值数字一律标注为"目标示例，需按实际基线校准"，禁止当行业基准引用；无基线则无法区分"多烧算力"与"架构更优"。

- 五个车间场景（六段式：业务背景/角色诉求/现状痛点/引入后流程/关键数据流转/可衡量价值/边界）：
  1. **SMT 换线编排**：**编排主体归工作流引擎**（非 Agent）；唯一真正的多 Agent 环节=四个准备项（工艺版本/点检计量/物料齐套/工装钢网）**并行只读检查**（真独立）；首件判定与过点放行归规则引擎，Agent 只推人侧动作卡，不调放行 API。
  2. **批次质量异常的根因分析 + 影响面清点**（车间最值得上多 Agent 的场景）：**先 narrowing 再并行**（2-4 条假设，非六路全开）；红队须持不同数据源/方法；影响面五级清点（在制/线边/成品库/在途/已交付）真独立并行；**处置决策回到单线程**；谱系图遍历是确定性图服务不包 Agent。
  3. **月度产能与工时多源核对**（MES 报工/设备采集/考勤/工单产出×标准工时）：多路径独立重算；关键 artifact=口径定义文件（固化复用）+ 数据完整率报告（取数阶段即产出，含采集断点）。
  4. **SOP 更新与合规审核**：**生成环节顺序执行不并行**（强一致性文档，并行分章有害）；审核 Agent 必须查工艺规格/质量门禁/设备能力等**外部规则库**，不得凭模型记忆；审核发现须引具体规格值来源。
  5. **航空件超差 MRB 评审**：提案 vs 红队（持客户规范/适航/历史服役数据/返修成功率）vs 裁判；反驳须挂**条款锚点**；红队设证据门槛防噪音。
- 五条共性：① 全命中"真并行"或"信息不对称"；② 确定性环节留代码/规则引擎，过点 200ms 红线未碰；③ 写与最终决策在人；④ 价值落在周期缩短与漏检率，非替代岗位；⑤ 特意标出两处"不该并行"（换线编排归工作流、SOP 顺序生成）。

## 关键澄清：工具注册边界 ≠ 任务分解边界（用户追问后修正）

- 用户追问：影响面清点为何按五级（在制/线边/成品库/在途/已交付）横向并行，而非按过点/返修/工单等模块纵向并行。
- **修正此前表述**：原写"上下文边界 = 工具边界 = Agent 边界"有误导，已改为"上下文边界 = **工具注册**边界"，并明确**任务分解边界按'要回答的问题的结构'划分**，二者正交。已同步修改 `MES-Multi-Agent架构适用性分析.md` §3 通用不变式 与 `车间MES的Multi-Agent真实业务场景详解.md` 开头硬约束。
- 选横向不选纵向的五条理由：① 横向五级互斥且完备可直接相加，纵向既不互斥（同件在多模块有记录，需去重）也不完备；② **纵向会系统性漏掉"在途"与"已交付"**（二者不是 MES 模块，数据在 ERP/物流/客服），而漏报客户是航空合规红线；③ **纵向拆本质是用 Agent 做查询路由**——"批次→候选对象"是确定性关联查询，应归图服务（对应流程 5a），不该包 Agent；④ 状态是跨模块推导的（在制需综合过点+工单+返修），横向拆让子 Agent 在干净上下文完成判定，汇总 Agent 只做相加；⑤ 五级各自对应不同处置动作与责任人，输出可直接路由为动作卡，模块维度输出无业务语义需二次转换。
- 纵向拆仍合理的场景（已写入文档）：系统健康度盘点（问题本身按模块提出）、按系统所有权分工问责。
- 场景二流程表已细分为 5a（确定性关联查询产出候选对象清单）与 5b（五级并行清点）。
