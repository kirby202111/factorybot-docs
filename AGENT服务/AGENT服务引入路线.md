# MES Agent 服务引入路线（按能力引入，不分层）

> 面向场景：面试中被问"你这套 MES 能不能上 Agent / 智能体""如果给系统用户引入 AI Agent，你怎么做"时，输出**能力矩阵 + 与领域耦合点 + 引入顺序**。
> **与 RAG 的关系**：Agent 是 [RAG服务引入路线.md](../RAG服务/RAG服务引入路线.md) 路线 E（Agentic RAG 收口）的展开。RAG 解决"问得到"，Agent 解决"做得完"——多步规划、主动触发、可控写回。
> **核心纪律**：MES 对误写零容忍（错发一张返工单可能批量报废）。所以本路线的主轴不是"选什么模型"，也不是"Agent 自主到第几级"，而是 **三项能力各自对齐 MES 的写红线与过点事务边界**。
> **详细设计**：[FactoryAgent 总体设计与实现方案](FactoryAgent/FactoryAgent-总体设计与实现方案.md)、[诊断能力](FactoryAgent/FactoryAgent-诊断能力.md)、[草稿编写能力](FactoryAgent/FactoryAgent-草稿编写能力.md)、[流程编排能力](FactoryAgent/FactoryAgent-流程编排能力.md)。

---

## 0. 先界定：Agent 相对 RAG 的增量在哪

| 能力 | RAG | Agent | 对 MES 的含义 |
|------|-----|-------|--------------|
| 检索 + 回答 | ✅ | ✅ | 两者共有 |
| 多步规划 / 工具调用 | ❌ | ✅ | 能跨 14 个限界上下文串推理 |
| 主动触发（非问答） | ❌ | ✅ | 能巡检、预警、推动作卡片 |
| 写回系统 | ❌（只读） | ⚠️ 受限 | **最大风险点，必须按能力声明写权限** |

一句话：**RAG 把"工程师手动查 5 个界面"变成一次问答；Agent 把"查完 → 诊断 → 草拟处置 → 推动作"变成一条自动链，但写动作的闸门始终在人手里**。

---

## 1. 一个 Agent，三项能力

不做能力分级（不高阶 / 低阶之分），也不做"三个独立 Agent"。`agent-service` 是一个服务，对外暴露三项能力：

| 能力 | 做什么 | 写权限 | 起步价值 | 风险 |
|------|--------|--------|---------|------|
| **诊断** `diagnosis` | 多步只读推理，跨上下文串追溯 → 5M1E 根因假设排序 + 证据链 | 无（只读 toolset） | **高** | 低 |
| **草稿编写** `drafting` | 生成写意图草稿（返工单 / 8D / SOP / 处置卡 / 隔离集卡），**不落库** | 无（只持有读 client） | **高** | 中 |
| **流程编排** `orchestration` | 跨上下文长流程推进（换线 / 故障复产 / 客诉 / 工艺变更），关键步人在回路 | 受限写 + confirmation gate | 高 | 中高 |

三者共用一套运行时、一张工具注册表、一套策略闸门、一条 trace。能力之间的差别是**图的形态 + 工具切片 + 写权限声明**，不是等级：

- 诊断 = 开放式 ReAct 子图；
- 草稿 = 固定链 + 策略分派；
- 编排 = supervisor 代码图，在非确定决策点 `invoke` 前两项能力。

**主动触发是调用形态，不是第四项能力**：订阅领域事件（`equipment.fault`、`process.route.activated`、`defect_rate.spike`）后路由到对应能力——巡检推诊断、升版推草稿、故障推编排。复用已有事件流（[领域总览.md](../领域模型/领域总览.md) §4.3），不造新管道。

## 2. 三项能力详解（对齐领域模型）

### 2.1 诊断能力（最契合护城河，建议主推）

把 RAG 路线 A 的"追溯型检索"升级成**多步推理**：Agent 主动调用一系列只读工具，自己决定下一步查什么。

- **两种入口同一张图**：工程师提问（自然语言 + 业务对象）／结构化异常（mismatch / fault / complaint）——编排的非确定节点用后者，不需要另写一个"根因 Agent"。
- **典型链路**：查该单件过点记录（过点执行）→ 拿工艺版本查当时工艺（工艺管理，§5.1 版本一致性）→ 查同批次锡膏批次（物料）+ 贴片机当时参数（设备数据接入）→ 查同批次不良率 → 5M1E 假设排序。
- **工具注册对齐限界上下文**：每个上下文暴露一组只读工具，**上下文边界天然就是工具边界**（[领域总览.md](../领域模型/领域总览.md) §2 的 14 个上下文），不需要另造一套工具分类。
- **为什么低风险**：全程只读，永不进过点主事务（§5.3），只是把"工程师跨 5 个界面手动串"自动化。
- **为什么是护城河**：建立在 `source_work_order_id`、工艺版本、`asset_id` 这些跨上下文引用之上——别人没有这套领域模型，Agent 没有可调的工具。

### 2.2 草稿编写能力（把"写"控制在草稿态）

Agent 生成**写意图草稿**，但不落库，由人在正式界面确认后下达。这是 MES 写红线的安全落地形态。

- **典型场景**：
  - **返工单草拟**：诊断出某批次要返工 → 生成返工工单草稿（再入点、返工工艺路线引用 `source_work_order_id`），工程师在返工上下文正式界面审核后下达。
  - **8D 报告草拟**：拉追溯链 + 历史同类 8D → 草稿，质量工程师改完发布。
  - **SOP 草拟**：工艺变更后（订阅 `ProcessRouteActivated`，§4.3）基于新版本 + 旧 SOP 草拟新 SOP。
  - **处置卡 / 隔离集卡**：给编排图的非确定节点提供统一的产物形态。
- **关键约束**：输出是 **intent + draft**，落库走返工 / 工单 / 质量 / 工艺上下文的**正常应用服务**，绝不旁路写。草稿能力**不持有任何写 client**，启动断言扫描方法名禁止写动词。

### 2.3 流程编排能力（跨上下文流程，人在回路）

跨多个上下文编排一个**完整流程**，关键步骤人在回路审批。典型是**换线**：

- 换线涉及：首件触发（首件处理）→ 工艺版本切换确认（工艺管理）→ 点检 / 计量校验（点检保养 / 计量检定）→ 物料齐套核对（物料 / WIP）→ 首件放行门禁（过点执行）。
- 编排把这些步骤做成显式图，**每步给操作工一个动作卡**：需要写 / 放行的步骤走正常 MES 流程由人确认，Agent 只做"下一步该干啥 + 卡片推送 + 异常提醒"。
- **只有非确定的那段调能力**：钢网 / 程序 mismatch 后判根因（诊断）+ 出处置卡（草稿）；故障隔离范围（诊断 + 草稿）；8D / SOP 生成（草稿）。**换线全程 PASS 时 LLM 调用为 0**。
- **风险点**：极易越界进过点主事务。硬约束——只编排**人侧动作**，不直接调过点引擎的放行 / 拦截 API；过点 P99 ≤200ms（§4.1）的判定仍走规则引擎。

## 3. 按用户映射（对齐 RAG 路线 §0 四类用户）

| 用户 | 会用到的能力 | 为什么 |
|------|------------|--------|
| 操作工 / 线长 | 流程编排（换线 / 故障复产的动作卡）+ 主动巡检推送 | 现场要"下一步动作卡"，不要长答案 |
| 工艺 / 质量工程师 | **诊断 + 草稿（8D / 返工单 / SOP）** | 最高价值，复用追溯护城河 |
| 设备工程师 | 诊断（设备故障）+ 草稿（维修单 / 隔离集卡） | 复用 RAG 路线 B 的设备手册与维修历史 |
| 管理层 | 无（走 RAG 路线的 Text2SQL 只读查询） | 只读数据查询，不需要 Agent 行动 |

> 以前按"自主度 L0–L4"分配用户，现在按"这个用户真正需要哪种功能"分配——管理层不需要 Agent，就不该给他一个"最低级 Agent"。

## 4. 硬约束（Agent 比 RAG 多出来的几条）

RAG 路线 §4 的六条约束（版本一致性、只读边界、权限隔离、实时性、部署形态、可观测兜底）Agent **全部继承**，并新增三条：

| 新增约束 | 说明 | 与本 MES 的耦合点 |
|---------|------|-----------------|
| **写动作 confirmation gate** | Agent 可生成写意图，但落库必须人确认；绝不旁路应用服务写 | 写工具标记 `requires_confirmation` + `writes_via`；写路径过聚合根不变式 + 事务发件箱（§5.4） |
| **能力级写权限声明** | 诊断 / 草稿 `writes_allowed=False`，编排 `True`；启动断言校验 | `CapabilitySpec` + `ToolPolicyGate`，无写权限能力拿不到写工具 |
| **工具注册对齐限界上下文** | Agent 能调的工具 = 14 个上下文暴露的 toolset，边界即工具边界 | 每上下文一个只读 toolset + 受限写 toolset 白名单 |
| **不进过点主事务（继承加强）** | 过点辅助只能拦后异步推；编排不得调放行 / 拦截 API | §5.3 过点主事务零分布式事务；§4.1 过点 P99 ≤200ms，判定仍走规则引擎 |

继承自 RAG 的六条中要点名三条：

- **版本一致性**：诊断拉工艺必须带版本锚点（§5.1），否则会基于已失效工艺给根因。
- **只读边界**：诊断 / 草稿全程只读；编排的"写"是草稿 + 人确认，不是 Agent 直写。
- **可观测兜底**：每步推理带工具调用链 + 置信度，低置信度转人工 / 转规则引擎，与 MES 防错理念一致——宁可拦下让人判。

## 5. 推荐引入顺序（按能力启用，不按等级爬坡）

**诊断 → 草稿编写 → 流程编排（先纯代码骨架）→ 编排接入能力节点 → 主动触发叠加。**

1. **第一步：诊断能力**。建立在 RAG 路线 A/B 成型后，把追溯检索升级成多步推理。纯只读，最坏情况是"没诊断出来"。
2. **第二步：草稿编写能力**。把诊断结论变成返工单 / 8D / SOP 草稿。仍不落库，写风险为零。
3. **第三步：流程编排 —— 先纯代码骨架**。挑一条产线做换线编排，全程 PASS 路径不调 LLM，先把 barrier / gate / 动作卡做扎实，验证编排能进生产主线而不越界。
4. **第四步：编排接入能力节点**。mismatch 分支调诊断 + 草稿；故障场景调诊断 + 隔离集卡；客诉场景串诊断 → 8D。
5. **第五步：主动触发叠加**。订阅已有领域事件做异常巡检与升版草拟，证明 Agent 能"主动"而不只是问答。

> 这个顺序只说明"哪块先做"，不说明"哪块更高级"。**每一项能力内部仍然用三问决定哪一步给 LLM、哪一步给代码**——详见 [能力边界与选型决策卡](FactoryAgent/FactoryAgent-能力边界与选型决策卡.md)。

## 6. 面试防守 Q&A

**Q：Agent 和你已经规划的 RAG 是什么关系？是不是重复了？**
A：不重复。RAG 解决"问得到"，Agent 解决"做得完"。RAG 路线 E（Agentic RAG）就是 Agent 的收口形态。Agent 比 RAG 多三件事：多步规划（跨 14 个上下文串推理）、主动触发（订阅领域事件巡检预警）、可控写回（草稿 + 人确认）。落地顺序是 RAG 的 A/B 先成型，再把追溯检索升级成诊断能力，把诊断结论升级成草稿能力，写动作始终人在回路。

**Q：为什么不按自主度分级（诊断 / 草稿 / 编排三级）来做？**
A：因为真实需求横跨它们，分级后只能靠单向依赖硬接。客诉 8D 一次要走编排（隔离 gate）+ 诊断（5M1E 排序）+ 草稿（8D 正文）；换线 mismatch 要走编排骨架 + 诊断根因 + 草稿处置卡。现在是一个 runtime 承载三种图形态，共用会话表、工具注册表、策略闸门和一条 trace，能力可以互相 invoke。风险梯度不靠"层号"，靠能力级写权限声明 + 工具级写声明 + 运行时 token 三层共管。

**Q：Agent 最大的风险是什么？**
A：不是模型幻觉，是**写动作越界**。MES 对误写零容忍。所以写风险由三层共同控制：能力声明（诊断 / 草稿 `writes_allowed=False`，拿不到写工具）、工具声明（写工具必须 `requires_confirmation` + `writes_via`）、运行时（写调用必须带绑定 `action:target` 的 confirmation token）。落库走各上下文正常应用服务，绝不旁路写。自治写（Agent 自己决定并落库）现阶段不做，要等置信度标定与评测集积累够。

**Q：Agent 会不会拖慢过点？**
A：不会进过点主事务。过点 P99 ≤200ms（§4.1）是硬约束，Agent 的过点辅助只能在**拦截之后**异步推卡片，主判定仍走规则引擎。编排只编排人侧动作，绝不直接调过点引擎的放行 / 拦截 API——这条边界即过点主事务零分布式事务（§5.3）。

**Q：为什么把工具注册对齐到限界上下文？**
A：因为上下文边界天然就是工具边界。已有 14 个限界上下文（[领域总览.md](../领域模型/领域总览.md) §2），每个上下文暴露一组只读 toolset + 受限写 toolset 白名单，Agent 在这上面规划。这比另造一套工具分类更稳——边界、权限、版本过滤都跟着上下文走，权限在工具调用前就隔离了，不是答完再裁剪。

**Q：Agent 能不能直接改工艺 / 发返工单？**
A：不能直写。草稿能力能**草拟**返工单、8D、SOP，但输出是 intent + draft，落库走返工 / 工单 / 质量 / 工艺上下文的正常应用服务，过聚合根不变式校验 + 事务发件箱（§5.4）。任何写操作只能人在正式界面确认后下达，LLM 最多给草稿。

**Q：为什么不让 Agent 一上来就做换线编排？**
A：风险集中在"越界进过点主事务"。诊断与草稿是只读 + 草稿，踩坑成本可控。先把诊断和草稿做扎实、把置信度标定和证据回溯跑通，再挑一条产线试点编排——按"价值 / 风险 / 依赖"排，不是按热度。

## 7. 红线（口径纪律）

- ❌ "我们 MES 已经上了 Agent"——这是设计阶段规划，不是已落地。
- ❌ "Agent 自动发返工单 / 改工艺"——写动作必须人确认，Agent 最多草拟。
- ❌ "Agent 进了过点主事务"——绝不允许，过点 200ms 是硬约束。
- ❌ "Agent 直接查 / 改 MES 原始表"——走上下文只读 toolset / 正常应用服务，不碰原始表。
- ❌ "L1 诊断 Agent / L2 草稿 Agent / L3 编排 Agent"——已废弃的分层说法，现在是**一个 Agent 的三项能力**（诊断 / 草稿编写 / 流程编排）。

**正确讲法**：
- ✅ "我把 Agent 设计成一个服务、三项能力：诊断做多步只读取证，草稿把结论变成可下达的处置，编排把这些处置塞进跨上下文长流程并在关键步停下来等人。写权限按能力声明，写工具必须过 confirmation gate，落库不旁路应用服务。"
- ✅ "Agent 建立在 RAG 追溯护城河之上，把'问得到'升级成'做得完'，但写的闸门始终在人手里——这是 MES 场景下 Agent 和通用 Agent 的本质区别。"

被问"上线了吗"时，老实说："这是设计阶段的引入规划，重点是能力矩阵与领域耦合点的判断，落地需要先等 RAG 追溯能力成型，再做诊断与草稿验证可用性，编排是试点形态。"——**诚实 + 体现架构判断力，比硬吹"已上线 AI Agent"得分高。**

## 8. 一句话定位（收尾用）

"给 MES 引入 Agent，关键不是选多强的模型，而是**把 Agent 的行动边界对齐到 MES 的领域边界**——工具注册对齐 14 个限界上下文、写权限按能力声明、写动作过 confirmation gate 不旁路应用服务、编排不进过点主事务。我不做能力分级，只做一个 Agent 的三项功能：诊断把证据变成假设，草稿把假设变成可下达的处置，编排把处置塞进长流程并停下来等人——让 Agent 在 RAG 护城河上把'问得到'升级成'做得完'，而写的闸门始终在人手里。"
