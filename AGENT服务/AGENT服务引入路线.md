# MES Agent 服务引入路线

> 面向场景：面试中被问"你这套 MES 能不能上 Agent / 智能体"或"如果给系统用户引入 AI Agent，你怎么做"时，分层输出"自主度光谱 + 与领域耦合点 + 落地顺序"。
> **与 RAG 的关系**：Agent 是 [RAG服务引入路线.md](../RAG服务/RAG服务引入路线.md) 路线 E（Agentic RAG 收口）的展开。RAG 解决"问得到"，Agent 解决"做得完"——多步规划、主动触发、可控写回。本文沿用 [项目亮点与指标卡片.md](../面试指南/项目亮点与指标卡片.md) §0 的口径纪律：说"规划方向 / 设计取舍"，不说"我们已上线 Agent"。
> **核心纪律**：MES 对误写零容忍（错发一张返工单可能批量报废）。所以本路线的主轴不是"选什么模型"，而是 **自主度光谱**——Agent 能做到哪一级"行动"，每一级如何对齐 MES 的写红线与过点事务边界。

---

## 0. 先界定：Agent 相对 RAG 的增量在哪

通用 RAG 与 Agent 的差异点，映射到本 MES：

| 能力 | RAG | Agent | 对 MES 的含义 |
|------|-----|-------|--------------|
| 检索 + 回答 | ✅ | ✅ | 两者共有 |
| 多步规划 / 工具调用 | ❌ | ✅ | 能跨 14 个限界上下文串推理 |
| 主动触发（非问答） | ❌ | ✅ | 能巡检、预警、推动作卡片 |
| 写回系统 | ❌（只读） | ⚠️ 可分级 | **最大风险点，必须按自主度分级** |

一句话：**RAG 把"工程师手动查 5 个界面"变成一次问答；Agent 把"查完->诊断->草拟处置->推动作"变成一条自动链，但写动作的闸门始终在人手里**。

---

## 1. 自主度光谱：五个方向

这是给系统用户引入 Agent 的主轴。自主度越高，价值越大，MES 红线越紧。

| 等级 | 方向 | 做什么 | 写权限 | 起步价值 | 风险 |
|------|------|--------|--------|---------|------|
| **L0** | 收口型问答 Agent（=RAG 路线 E） | 统一入口路由到 RAG A/B/C/D 工具 | 无 | 中 | 低 |
| **L1** | 诊断型 Agent（多步只读推理） | 跨上下文串追溯 -> 给根因 / 建议 | 无（只读 API） | **高** | 低 |
| **L2** | 草稿型 Agent（生成写意图，人确认落库） | 自动草拟返工单 / 8D / SOP | 生成草稿，**不落库** | **高** | 中 |
| **L3** | 编排型 Agent（跨上下文流程，人在回路） | 换线 / 首件 / 异常处置编排 | 受限写 + confirmation gate | 高 | 中高 |
| **L4** | 自治型 Agent（sandbox 内自动写） | 无人介入执行 | 全自动写 | — | **目前不建议** |

**建议起步落在 L1 + L2**：复用 RAG 路线 A/B 已建好的检索能力，把"问答"升级成"多步诊断 + 草稿"，写动作仍 100% 由人在正式界面确认——既不碰红线，又能讲清"Agent 比 RAG 进了一步"。

## 2. 各方向详解（对齐领域模型）

### 2.1 L0 收口型问答 Agent

一个 Agent 入口，按问题路由到 RAG 路线 A/B/C/D 的工具（检索文档 / 查追溯链 / 跑 SQL / 调 MES 只读 API）。

- **定位**：RAG 路线 E 的原样展开，是 Agent 的最低形态——有"路由 + 工具选择"，但没有跨上下文多步推理、没有写意图。
- **何时做**：等 L1–L3 能力成型后再收口，否则 Agent 没工具可调，退化为套壳问答。

### 2.2 L1 诊断型 Agent（最契合护城河，建议主推）

把 RAG 路线 A 的"追溯型检索"升级成**多步推理**：Agent 主动调用一系列只读工具，自己决定下一步查什么。

- **场景**：工艺 / 质量工程师说"这批焊接不良根因" -> Agent 不再一次性检索，而是：
  1. 查该单件过点记录（过点执行上下文）
  2. 拿到 `routeVersion` -> 查当时工艺版本（工艺管理上下文，§5.1 版本一致性）
  3. 查同批次锡膏批次（物料上下文）+ 贴片机当时参数（设备数据接入上下文）
  4. 查同批次其他单件不良率 -> 给出 **5M1E 假设排序**
- **工具注册对齐限界上下文**：每个上下文暴露一组**只读工具**，Agent 在工具集上规划。这正复用 [领域总览.md](../领域模型/领域总览.md) §2 的 14 个上下文边界——**上下文边界天然就是工具边界**，不需要另造一套工具分类。
- **为什么低风险**：全程只读，永不进过点主事务（§5.3），只是把"工程师跨 5 个界面手动串"自动化。
- **为什么是护城河**：和 RAG 路线 A 同源——建立在 `source_work_order_id`、`routeVersion`、`asset_id` 这些跨上下文引用之上，别人没有这套领域模型，Agent 没有可调的工具。

### 2.3 L2 草稿型 Agent（把"写"控制在草稿态）

Agent 生成**写意图草稿**，但不落库，由人在正式界面确认后下达。这是 MES 写红线的安全落地形态。

- **典型场景**：
  - **返工单草拟**：L1 诊断出某批次要返工 -> Agent 生成返工工单草稿（再入点、返工工艺路线引用 `source_work_order_id`），工程师在返工上下文正式界面审核后下达。
  - **8D 报告草拟**：Agent 拉追溯链 + 历史同类 8D -> 草拟报告，质量工程师改完发布。
  - **SOP 草拟**：工艺变更后（订阅 `ProcessRouteActivated`，§4.3）Agent 基于新工艺版本草拟新 SOP。
- **关键约束**：Agent 输出的是 **intent + draft**，落库走返工上下文 / 工单管理上下文的**正常应用服务**，绝不旁路写。这条讲清楚，就体现你懂 MES 写路径的严肃性——写不是"调个 API"，是要过聚合根不变式校验、过事务发件箱的。

### 2.4 L3 编排型 Agent（跨上下文流程，人在回路）

跨多个上下文编排一个**完整流程**，关键步骤人在回路审批。典型是**换线 Agent**：

- 换线涉及：首件触发（首件处理上下文）-> 工艺版本切换确认（工艺管理）-> 点检 / 计量校验（点检保养 / 计量检定）-> 物料齐套核对（物料 / WIP）-> 首件放行门禁（过点执行）。
- Agent 编排这些步骤，**每步给操作工一个动作卡**：需要写 / 放行的步骤走正常 MES 流程由人确认，Agent 只做"下一步该干啥 + 卡片推送 + 异常提醒"。
- **风险点**：极易越界进过点主事务。硬约束——Agent 只编排**人侧动作**，不直接调过点引擎的放行 / 拦截 API；过点 P99 ≤200ms（§4.1）的判定仍走规则引擎。

### 2.5 主动式 Agent（横切能力，可叠加在 L1–L3）

这是 Agent 相对 RAG 最易被忽略的增量：**不等人问，主动发现**。

- **异常巡检 Agent**：订阅领域事件（在制品齐套率下降、设备点检临期、同批次不良率突增）-> 主动推送预警 + 建议动作给线长 / 工程师。
- **复用已有事件流**：[领域总览.md](../领域模型/领域总览.md) §4.3 已定义 `ProcessRouteActivated`、设备状态变更事件——Agent 直接订阅这些事件做触发，不造新管道。
- **贴合本系统**：直接命中 CLAUDE.md 关注的"实时性 + 防错"——把"事后查"变成"事前推"。

### 2.6 L4 自治写 Agent（远期形态，现不做）

受限 sandbox 内全自动写（如自动调整点检计划、自动派维修工单）。MES 场景下误写代价是批量不良 / 停线，**在 L1–L3 没有充分可观测数据前不做**。可作为远期形态提一句，体现判断力而非技术堆砌。

## 3. 按用户映射（对齐 RAG 路线 §0 四类用户）

| 用户 | 推荐方向 | 为什么 |
|------|---------|--------|
| 操作工 / 线长 | L3 换线编排 + 主动巡检推送 | 现场要"下一步动作卡"，不要长答案 |
| 工艺 / 质量工程师 | **L1 诊断 + L2 草稿（8D / 返工单）** | 最高价值，复用追溯护城河 |
| 设备工程师 | L1 设备诊断 + L2 维修单草拟 | 复用 RAG 路线 B 的设备手册与维修历史 |
| 管理层 | L0 收口（路由到 RAG C 的 Text2SQL） | 只读数据查询，不需要 Agent 行动 |

## 4. 硬约束（Agent 比 RAG 多出来的几条）

RAG 路线 §4 的六条约束（版本一致性、只读边界、权限隔离、实时性、部署形态、可观测兜底）Agent **全部继承**，并**新增三条 Agent 特有的**：

| 新增约束 | 说明 | 与本 MES 的耦合点 |
|---------|------|-----------------|
| **写动作 confirmation gate** | Agent 可生成写意图，但落库必须人确认；绝不旁路应用服务写 | L2 草稿态、L3 审批步；写工具标记 `requires_confirmation`；写路径过聚合根不变式 + 事务发件箱（§5.4） |
| **工具注册对齐限界上下文** | Agent 能调的工具 = 14 个上下文暴露的 toolset，边界即工具边界 | 每个上下文一个只读 toolset + 受限写 toolset 白名单 |
| **不进过点主事务（继承加强）** | Agent 的过点辅助只能拦后异步推；编排 Agent 不得调放行 / 拦截 API | §5.3 过点主事务零分布式事务；§4.1 过点 P99 ≤200ms，判定仍走规则引擎 |

继承自 RAG 的六条同样要点名，尤其：

- **版本一致性**：L1 诊断拉工艺时必须带 `routeVersion` 过滤（§5.1），否则会基于已失效工艺给根因。
- **只读边界**：L1/L0 全程只读；L2/L3 的"写"是草稿 + 人确认，不是 Agent 直写。
- **可观测兜底**：Agent 每一步推理带工具调用链 + 置信度，低置信度转人工 / 转规则引擎，与 MES 防错理念一致——宁可拦下让人判。

## 5. 推荐落地顺序

**L1 诊断 + L2 草稿 起步 -> 主动巡检叠加 -> L3 编排试点 -> L0 收口。**

1. **第一步（L1 + L2）**：建立在 RAG 路线 A/B 成型后，把追溯检索升级成多步诊断 + 返工单 / 8D 草稿。低风险，复用领域事件与过点记录。
2. **第二步（主动巡检）**：订阅已有领域事件做异常预警，证明 Agent 能"主动"而不只是问答。
3. **试点（L3 换线编排）**：挑一条产线做换线 Agent，confirmation gate 做扎实，验证 Agent 能进生产主线而不越界。
4. **收口（L0）**：统一 Agent 入口，路由到 RAG 工具 + L1–L3 能力（即 RAG 路线 E 的最终形态）。

## 6. 面试防守 Q&A

**Q：Agent 和你已经规划的 RAG 是什么关系？是不是重复了？**
A：不重复。RAG 解决"问得到"，Agent 解决"做得完"。RAG 路线 E（Agentic RAG）就是 Agent 的收口形态。Agent 比 RAG 多三件事：多步规划（跨 14 个上下文串推理）、主动触发（订阅领域事件巡检预警）、可控写回（草稿 + 人确认）。我的落地顺序是 RAG 的 A/B 先成型，再把追溯检索升级成 L1 诊断 Agent + L2 草稿 Agent，写动作始终人在回路——不是另起炉灶，是在 RAG 护城河上往前走一步。

**Q：Agent 最大的风险是什么？**
A：不是模型幻觉，是**写动作越界**。MES 对误写零容忍——错发一张返工单可能批量报废。所以我把 Agent 按自主度分五级，起步只做 L1（只读诊断）和 L2（草稿不落库），写动作必须过 confirmation gate，落库走返工上下文 / 工单管理上下文的正常应用服务，绝不旁路写。L4 自治写现在不做，要等 L1–L3 积累够可观测数据。

**Q：Agent 会不会拖慢过点？**
A：不会进过点主事务。过点 P99 ≤200ms（§4.1）是硬约束，Agent 的过点辅助只能**拦截之后**异步推卡片，主判定仍走规则引擎。L3 编排 Agent 只编排人侧动作，绝不直接调过点引擎的放行 / 拦截 API——这条和 RAG 路线 D 的边界完全一致（§5.3 过点主事务零分布式事务）。

**Q：为什么把工具注册对齐到限界上下文？**
A：因为上下文边界天然就是工具边界。我已有 14 个限界上下文（[领域总览.md](../领域模型/领域总览.md) §2），每个上下文暴露一组只读 toolset + 受限写 toolset 白名单，Agent 在这上面规划。这比另造一套工具分类更稳——边界、权限、版本过滤都跟着上下文走，权限在工具调用前就隔离了，不是答完再裁剪。

**Q：Agent 能不能直接改工艺 / 发返工单？**
A：不能直写。L2 草稿型 Agent 能**草拟**返工单和 SOP，但输出的是 intent + draft，落库走返工上下文 / 工单管理上下文的正常应用服务，过聚合根不变式校验 + 事务发件箱（§5.4）。任何写操作只能人在正式界面确认后下达，LLM 最多给草稿——这条和 RAG 路线的只读边界一脉相承，只是 Agent 把"草稿"做得更完整。

**Q：为什么不让 Agent 一上来就做换线编排（L3）？**
A：L3 跨上下文编排，风险集中在"越界进过点主事务"。L1/L2 是只读 + 草稿，踩坑成本可控。先把诊断和草稿做扎实、把 confirmation gate 和可观测跑通，再挑一条产线试点 L3——这是按"价值 / 风险 / 依赖"排的，不是按热度。L0 收口更要等 L1–L3 都成型，否则 Agent 没工具可调，退化为套壳。

**Q：主动式 Agent 和 RAG 路线 D（防错即时辅助）什么区别？**
A：RAG 路线 D 是**过点拦截事件触发**的即时辅助，命中即推短卡片，靠预计算 + 缓存；主动式 Agent 是**订阅领域事件做巡检预警**，不绑定过点时刻——比如同批次不良率突增、点检临期，主动推给线长。两者都复用已有的领域事件流（§4.3），不造新管道，区别在触发时机和受众。

## 7. 红线（口径纪律）

- ❌ "我们 MES 已经上了 Agent"——这是设计阶段规划，不是已落地。
- ❌ "Agent 自动发返工单 / 改工艺"——写动作必须人确认，Agent 最多草拟。
- ❌ "Agent 进了过点主事务"——绝不允许，过点 200ms 是硬约束。
- ❌ "Agent 直接查 / 改 MES 原始表"——L1 走上下文只读 toolset，L2 草稿走正常应用服务，不碰原始表。

**正确讲法**：
- ✅ "我规划了五级自主度的 Agent 引入路线，起步做只读诊断 + 草稿型，写动作过 confirmation gate，核心约束是工具对齐限界上下文、不进过点主事务、写不旁路应用服务。"
- ✅ "Agent 建立在 RAG 追溯护城河之上，把'问得到'升级成'做得完'，但写的闸门始终在人手里——这是 MES 场景下 Agent 和通用 Agent 的本质区别。"

被问"上线了吗"时，老实说："这是设计阶段的引入规划，重点是自主度光谱与领域耦合点的判断，落地需要先等 RAG 追溯能力成型，再做 L1 诊断 + L2 草稿验证可用性。"——**诚实 + 体现架构判断力，比硬吹"已上线 AI Agent"得分高**。

## 8. 一句话定位（收尾用）

"给 MES 引入 Agent，关键不是选多强的模型，而是**把 Agent 的行动边界对齐到 MES 的领域边界**——工具注册对齐 14 个限界上下文、写动作过 confirmation gate 不旁路应用服务、编排不进过点主事务。我规划了五级自主度路线，起步做只读诊断 + 草稿型，让 Agent 在 RAG 护城河上把'问得到'升级成'做得完'，而写的闸门始终在人手里。"
