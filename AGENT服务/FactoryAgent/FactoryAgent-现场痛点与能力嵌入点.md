# FactoryAgent —— 现场痛点与能力嵌入点

> 本文逐一讲清"Agent 到底省了什么、防了什么"——**只讲传统代码做不了或做起来极复杂、而 Agent 能大幅降复杂度的那一段**。用于面试 / 评审中体现"懂什么时候该上 Agent、什么时候不该上"。
> **口径纪律**：本文描述的是**操作步骤与设计能力**，不编造业务效果数字（良率提升、停线下降百分比等）。凡涉及耗时，均为"人工作业经验量级"的定性描述，非线上实绩；收益以"消除某类非确定处置靠人脑拍 / 生成类输出靠人手写 / 跨上下文证据靠人串"等能力口径表述。
> **配套**：[能力边界与选型决策卡](FactoryAgent-能力边界与选型决策卡.md)、[诊断能力](FactoryAgent-诊断能力.md)、[草稿编写能力](FactoryAgent-草稿编写能力.md)、[流程编排能力](FactoryAgent-流程编排能力.md)。

---

## 0. 先划界：哪些痛点归代码，哪些才归能力

编排是"代码骨架（确定性）+ 能力（非确定）"两层。**只有非确定那层才是 Agent 的真痛点**。先把账算清楚，避免把工作流引擎的功劳记到 LLM 头上：

| 痛点（现象） | 归属 | 谁解决 | 本文是否深挖 |
|------|------|------|------|
| 换线慢、跨界面串行 | 编排骨架 | 工作流引擎 + 并行 + barrier | 否（代码） |
| 漏步骤、带病生产 | 硬防错 | 状态机 + 应用服务不变式 + barrier 硬校验 | 否（代码） |
| 写动作越界 / 无审计 | 权限模型 | 写工具白名单 + 走正常应用服务 + gate 落库 | 否（代码） |
| Agent 误触放行 | 架构层隔离 | 放行能力从工具集裁掉 + 启动断言 | 否（代码） |
| 版本串错（当前版本套历史） | ACL | 版本锚点从领域模型强制过滤 | 否（代码） |
| 长流程卡住无人推进 | 编排骨架 | 动作卡主动推 + 超时升级 + session 状态可视 | 否（代码） |
| **核对异常的根因分支与处置路由** | 非确定处置 | **诊断能力推理根因 + 草稿能力出处置卡** | **是（痛点 A）** |
| **故障影响批次隔离范围判定** | 非确定判定 | **诊断能力跨上下文取证 + 草稿能力出隔离集卡** | **是（痛点 B）** |
| **客诉根因的多源证据关联与假设排序** | 非确定诊断 | **诊断能力 5M1E 假设排序 + 自适应取证** | **是（痛点 C）** |
| **生成类输出（SOP / 8D）** | 开放生成 | **草稿能力草拟 + 人确认发布** | **是（痛点 D）** |

**判断标准**（贯穿全文）：一步输入是否开放、是否需要推理 / 生成、分支是否难以穷举。三者皆否 → 代码做；三者有一 → 交给能力。下文 A–D 逐一展开"痛点存在时人怎么干、代码为什么难、能力怎么降复杂度、边界在哪"。

## 痛点 A：核对异常的根因分支与处置路由

### A.1 痛点存在时的操作步骤（人工）

换线场景，硬防错层拦下一个结构化校验失败（这是代码的活，正常）：

```
check    = TOOLING_STENCIL_MATCH
status   = FAILED
code     = TOOLING_STENCIL_MISMATCH
expected = ST-B      (来自工艺路线 RR-B v4)
actual   = ST-A      (钢网库扫码读到)
route_id = RR-B, version = v4, asset_id = ASSET-01
```

放行被 barrier 挡住（图走不到放行节点），换线停在那。接下来现场怎么处置——**这才是痛点**：

1. 线长看到"expected ST-B / actual ST-A"，第一反应是"产线拿错钢网了"，电话叫库管重发 ST-B。
2. 库管到钢网库一查：ST-B 其实在架上没借出，ST-A 是上一个工单 A 的钢网，**还挂在产线上没归还**——根因不是"拿错"，是"上工单收线没把 ST-A 还库 + 这工单该领 ST-B 没领"。
3. 但线长不确定，又打电话问工艺工程师："工艺路线 v4 里 ST-B 对不对？会不会是 v4 录错？"工程师查工艺台账，确认 v4 录的就是 ST-B。
4. 工程师再问："那是不是钢网库台账错？ST-A 其实就是 ST-B 的旧编号改过名？"——又一层可能性，需查钢网主数据变更历史。
5. 三种根因（产线拿错 / 上工单未还库 + 本工单未领 / 台账编号变更未同步）**对应三种处置**：重发 ST-B 并让产线归还 ST-A / 让产线去领 ST-B / 修台账并放行用 ST-A。**升级对象也不同**：线长 / 库管 / 工艺工程师 + 主数据管理员。
6. 线长在 3 个电话、2 个系统界面间来回串，20 分钟才搞清是"上工单未还库"这条，期间产线停。
7. 处置动作（归还 ST-A、领用 ST-B、重发）散落在电话和口头里，**无审计**——事后问"这次 mismatch 怎么处置的"，只有线长口头回忆。

同样的结构化失败，程序版本不一致（`expected=PB-B-v4 / actual=PB-B-v3`）也有类似的多根因分支：贴片机本地程序库没更新 / 工艺路线 v4 录的程序号错 / 设备程序下发链路丢包 / 操作工手动调了旧版本。

### A.2 为什么传统代码难

看上去 mismatch 的处置可以写成规则表，但**根因分支是组合爆炸且持续演化**的：

- **根因空间不闭合**：钢网 mismatch 的根因不止"拿错"一种，还有"上工单未还库""台账改名""借出未登记""工艺录错""扫码枪读码制式不同"……每加一种现场情况，规则表就多一行，**永远落后于现场**。
- **判定需要跨上下文证据汇聚**：要区分"产线拿错"vs"台账改名"，必须同时查钢网库借还记录 + 钢网主数据变更历史 + 工艺路线 v4 录入审计 + 上工单收线记录——**没有单一上下文能独立判定**。代码做 = 写一个跨 4 上下文的联合查询 + 一棵决策树，而每条分支的判定阈值（"如果借出记录里有 ST-A 且无归还 → 未还库"）是启发式的，新情况一来就漏。
- **处置动作与升级对象是开放映射**：每种根因该推给谁、建议什么动作，不是 1:1 映射，还受当前班次 / 责任人在线状态影响。代码穷举 = 一张永远在补的对照表。

### A.3 能力如何降复杂度

编排图在 mismatch 分支调用两项能力：

- **诊断能力（结构化异常入参）**：不套决策树，按需调只读 toolset——先查钢网库借还记录（发现 ST-A 借出未还）、再查上工单收线记录（发现工单 A 收线未触发归还）、再查工艺路线 v4 审计（确认 ST-B 录入无误）——**取证路径由中间结果驱动**，不是固定 JOIN。固定 JOIN 取不到"上工单收线未触发归还"这种跨流程的因果。
- **诊断产出**：根因假设 + 置信度 + 仍需人确认的疑点（"需库管确认 ST-A 实物是否仍在产线"）。
- **草稿能力（`DISPOSITION_CARD`）**：把根因结论格式化成处置卡，含 `root_cause_hypothesis` + `evidence`（trace_id 列表）+ `suggested_actions`（归还 ST-A / 领用 ST-B / 重发）+ `route_to`（库管 + 线长）。**"判定该找谁、建议怎么处置"是 LLM 不可被代码穷举的部分。**

复杂度从"维护一棵永远落后的跨上下文决策树"降到"维护一组只读 toolset + 一个推理 prompt"。新根因出现时，只要取证能查到证据，能力就能给出假设；**决策树不用改**。

### A.4 边界与对应实现

- **硬防错仍是代码**：mismatch 的**检出与拦截**是 barrier / 应用服务不变式做的（[流程编排能力 §6.3](FactoryAgent-流程编排能力.md) `barrier_node`），能力不碰。能力只在**检出之后**的处置段介入。
- **写动作仍走应用服务**：处置卡人确认后，归还 / 领用 / 重发走钢网上下文正常应用服务（过聚合根不变式 + 事务发件箱），Agent 不直写。
- **gate 留痕**：处置卡 `interrupt` 等人确认，`agent_step_record` 记谁确认、基于哪张卡、根因假设是什么，全可审计。

**能力口径**：把"结构化校验失败 → 人脑判断根因 + 电话串 3 个系统 + 口头处置"升级为"诊断能力自适应取证 + 根因假设 + 草稿能力出处置卡 + 人确认留痕"。消除的是"非确定根因分支靠人脑拍 + 处置无审计"，不是"检出 mismatch"（那层是代码）。

## 痛点 B：故障影响批次隔离范围判定

### B.1 痛点存在时的操作步骤（人工）

贴片机 ASSET-01 故障停机，维修工到场。换线之外的痛点是：**ASSET-01 从什么时候开始参数漂移、漂移期间生产了哪些批次、这些批次要不要隔离**——这步现场几乎没人做好：

1. 维修工判断故障模式：是硬停（电机烧了，故障前参数正常），还是软漂移（温控阀长期偏，参数早就偏了只是今天才报警）？**软漂移的起始时间未知**。
2. 线长凭记忆说"应该是今早 10 点报警前才坏的"，于是隔离范围划成 `[10:00, 修复]` 之间 ASSET-01 生产的批次——**但漂移可能从昨晚夜班就开始了**，夜班那几批次没被隔离。
3. 工程师被叫来判定"漂移参数对哪些产品敏感"：ASSET-01 漂移的是贴装压力，敏感的是细间距 0201 产品，普通 0603 产品不受影响——**但工程师不一定记得每个产品的敏感参数**，要么全隔离（过隔离，返工量大），要么凭印象隔离（漏隔离）。
4. 隔离决策拖到维修完成后才做，期间受影响批次已流转到下道工序甚至入库。
5. 事后客诉才发现夜班某批次也受影响，但已发货，需召回。

### B.2 为什么传统代码难

- **故障模式分类不闭合**：硬停 / 软漂移 / 间歇性故障 / 软件版本回退导致的参数变化……故障模式空间开放，"漂移起始时间"无法用固定规则推出，需对设备遥测时序做形态判断。
- **隔离范围 = 故障模式 × 漂移窗口 × 产品敏感度**，三者乘积是动态的：同一设备故障，对产品 X（细间距）要隔离、对产品 Y（粗间距）不用；同一产品，硬停不用隔离漂移前批次、软漂移要往前回溯。**代码做 = 把这个三维判定写成规则引擎，规则随产品族和设备类型爆炸**。
- **产品敏感度知识散落**：某产品对贴装压力敏感、某产品对炉温敏感——这些知识在工艺 FMEA / 工艺路线 / 历史不良记录里散落，**没有结构化的"产品 × 参数敏感度"矩阵可供代码查询**（即便有，也维护不全）。

### B.3 能力如何降复杂度

编排图在故障场景并行跑"维修单拼装（代码）‖ 故障影响排查（能力）"：

- **诊断能力推理故障模式**：拉设备遥测时序（振动 / 温度 / 压力曲线），推理硬停 vs 软漂移 vs 间歇，对软漂移**估漂移起始窗口**——这是时序形态判断，规则引擎做不了，需基于历史遥测形态做类比推理。
- **跨上下文自适应取证**：按故障模式驱动取证——硬停只查报警时刻前后批次；软漂移往前回溯，查漂移窗口内 ASSET-01 生产的所有批次，跨过点上下文 + WIP 上下文 + 工艺上下文。**取证深度由故障模式决定**，不是固定时间窗。
- **产品敏感度关联**：拉工艺 FMEA + 历史同类故障的不良记录，**推理"漂移参数 × 受影响产品"的敏感度**，对受影响产品标隔离、对不受影响产品标放行——避免一刀切全隔离。
- **草稿能力（`ISOLATION_CARD`）**：生成隔离集卡（隔离批次清单 + 每批次隔离理由 + 证据 trace_id），过 confirmation gate 人确认后，走返工 / 返修上下文正常应用服务下达隔离。

复杂度从"维护故障模式 × 产品敏感度的规则引擎"降到"设备遥测取证 + FMEA 关联推理"。新故障模式 / 新产品出现时，只要遥测和 FMEA 可查，能力就能给出隔离假设；**规则引擎不用改**。

### B.4 边界与对应实现

- **隔离下达仍是代码**：隔离集卡人确认后走返工 / 返修上下文应用服务（过聚合根不变式 + 发件箱），Agent 不直写。
- **复校 / 复产 gate 仍是代码**：计量复校 gate、复产首件 gate 是编排骨架的显式节点（[流程编排能力 §3.2](FactoryAgent-流程编排能力.md)），能力不碰这两道红线。
- **兜底**：能力节点连续失败标 `SUSPENDED` 推线长升级，不自动隔离、不自动复产。

**能力口径**：把"故障影响批次靠人脑估时间窗 + 凭印象判敏感度 → 漏隔离或过隔离"升级为"诊断能力推理故障模式 + 自适应取证 + 敏感度关联 + 草稿能力出隔离集卡 + 人确认"。消除的是"非确定隔离范围靠人脑拍"，不是"隔离下达"（那层是代码）。

## 痛点 C：客诉根因追溯的多源证据关联与假设排序

### C.1 痛点存在时的操作步骤（人工）

客户反馈批次 P 焊接不良。质量工程师逆向追溯：

1. 过点系统查批次 P 生产记录——拿到过点时间、设备、当时工艺路线版本。**版本是最隐蔽的坑**：工艺界面默认显示当前生效版本 v5，工程师用 v5 的参数去分析批次 P（其实批次 P 过点时用的是 v3，中间已升级两次），**根因分析建立在错误工艺基础上**。
2. 物料系统查锡膏批次 B-77、供应商批次。
3. 设备系统查贴片机 ASSET-01 在批次 P 过点时段的参数——按时间范围查，工程师记错几分钟，参数对不上。
4. 质量系统查同批次其他单件不良率，手工 Excel 统计，口径不一致。
5. 工程师基于以上信息给根因假设：是锡膏问题？炉温问题？贴装坐标偏？设备参数漂移？**5M1E 六类假设靠人脑排序**，但步骤 1 版本串错 + 步骤 3 时间记错，假设建立在错误证据上。
6. 给出错误根因 → 错误处置（如误调工艺 v5，而问题其实在 v3 的某参数；v5 没问题却被改坏）。
7. 8D 报告手工起草，追溯链手工拼接，慢且易错。

### C.2 为什么传统代码难

- **版本钉死是 ACL 能做的**（版本锚点强制过滤，这是代码的活，在编排骨架里）。**但"证据齐了之后排根因假设"代码做不了**：5M1E 六类假设每类要查不同上下文，查到的证据如何加权、哪个假设置信度最高，是开放推理——同样一批证据，在不同产品族、不同历史不良背景下，根因排序不同。
- **取证是自适应的**：查到锡膏批次 B-77 后，要根据"B-77 是否在别处也出过焊接不良"决定要不要深挖供应商批次——**取证路径依赖中间结果**，固定 JOIN 取不到这种因果链。
- **跨上下文证据的语义关联**：过点 TestResult=FAIL + 设备参数轻微漂移 + 锡膏批次在别处也有不良——三条证据单独看都不致命，**合起来才指向锡膏根因**。代码的 JOIN 是字段相等，不是语义相关。

### C.3 能力如何降复杂度

编排图在客诉场景**先调诊断能力，再调草稿能力**：

- **版本钉死（代码层）+ 证据汇聚（能力层）**：版本锚点从过点记录强取 v3，诊断用 v3 查工艺参数（不会用当前 v5 套历史）——这层是 ACL 代码做的。能力在此之上汇聚跨上下文证据：过点 TestResult、设备遥测、锡膏批次、同批次不良率，按 5M1E 分类归位。
- **5M1E 假设排序 + 置信度**：诊断能力对六类假设排序（"锡膏批次 B-77 在别处也有不良 → 料因置信度高；设备参数漂移幅度小 → 机因置信度中"），给出排序假设 + 证据链 + 置信度。**这是规则引擎做不了的加权推理。**
- **自适应取证**：按假设排序驱动后续取证——料因置信度高就深挖供应商批次在库品、机因置信度高就回溯设备漂移窗口。**取证路径由假设驱动**，不是固定查询。
- **隔离并行**：供应商批次追溯的同时，并行判定同批次在库品隔离范围（同痛点 B 的动态判定，复用诊断 + 草稿能力），不靠人记得就做。
- **8D 草拟（痛点 D）**：草稿能力拉追溯链 + 历史同类 8D，草拟 8D 报告。

复杂度从"维护跨 5 上下文的固定追溯 JOIN + 人工排序假设"降到"版本钉死（代码）+ 诊断自适应取证 + 5M1E 假设排序"。新故障模式 / 新产品出现时，5M1E 框架不变，能力根据证据动态排序。

### C.4 边界与对应实现

- **版本钉死是代码**：版本锚点强制过滤是 ACL 做的（与诊断能力共用），能力不碰版本校验本身，只消费钉死后的版本。
- **隔离 / 8D 发布仍是代码**：隔离集卡人确认走应用服务；8D 报告人确认发布走质量上下文。
- **诊断结论仍需人确认**：给假设 + 置信度，不自动下处置结论，避免幻觉导致误处置。

**能力口径**：把"跨 5 界面手工串 + 版本串错 + 5M1E 假设靠人脑排 → 错误根因 → 错误处置"升级为"版本钉死（代码）+ 诊断自适应取证 + 5M1E 假设排序 + 草稿出 8D"。消除的是"非确定根因排序靠人脑拍 + 跨源语义关联靠人串"，不是"查记录"（那层是代码 + 只读 toolset）。

## 痛点 D：生成类输出（SOP / 8D）

### D.1 痛点存在时的操作步骤（人工）

两类现场高频的"写"活，本质都是**开放生成**，代码写不出：

1. **新工艺 SOP 草拟**：工艺路线 RR-B 从 v4 升 v5，引入新焊接参数。工艺工程师要基于 v5 的参数 diff，**手写新 SOP**（操作步骤、关键控制点、与 v4 的差异提示、安全注意事项）。从零写慢，且容易漏 v4→v5 的差异点。
2. **8D 报告草拟**：客诉 8D 报告要拉追溯链、根因分析、纠正措施、预防措施、历史同类 8D 对照——**全靠工程师手工填**，慢且格式不统一。

> 返工工艺建议不在生成类：其产物是"路线指针 + 再入工位"，属选型（三问皆否），主路径归代码；仅"库未命中的新不良模式"边角才让能力做候选推荐，且参数绝不经 LLM（见 [选型决策卡 §2](FactoryAgent-能力边界与选型决策卡.md)）。

### D.2 为什么传统代码难

- **这两类是自然语言生成，代码写不出**。模板拼接能做骨架，但"v4→v5 差异点提示""历史同类 8D 对照"需要**理解工艺语义 + 关联历史案例**，模板填空填不出有意义的差异提示。
- **输入开放**：v5 工艺参数 diff 千变万化，不良模式千变万化，无法穷举模板。

### D.3 能力如何降复杂度

草稿能力按 `draft_kind` 分派 builder：

- **`SOP` builder**：基于工艺路线 v5 参数 diff + v4 旧 SOP + 工艺 FMEA，**草拟新 SOP**（含差异点提示），gate 人确认发布——工程师从"从零写"变成"审改草稿"。
- **`EIGHT_D` builder**：拉追溯链（痛点 C 已汇聚）+ 历史同类 8D 案例库，**草拟 8D 报告**（根因 / 纠正 / 预防 / 案例对照），gate 人确认发布。

复杂度从"工程师从零手写"降到"能力草拟 + 人审改"。**这是 Agent 价值最干净的一类——代码完全做不了自然语言生成。**

### D.4 边界与对应实现

- **发布仍是代码**：SOP / 8D 人确认后，走各自上下文正常应用服务发布（过聚合根不变式 + 发件箱），Agent 不直写。
- **生成不碰红线**：这两类都是文档生成，不触碰过点放行、不触碰隔离下达，生成能力严格限制在"草拟"。
- **人审改兜底幻觉**：生成内容必须人确认，不自动发布——LLM 幻觉的成本留在审改环节，不出厂。

**能力口径**：把"开放生成靠工程师从零手写"升级为"能力草拟 + 人审改"。这是 Agent 不可替代的一类。

## 1. 代码层兜的那一半（不深挖，列出归属）

为完整性列出，**这些不是 Agent 的功劳，是编排骨架 + 应用服务不变式 + ACL 做的**：

| 痛点 | 代码解法 | 实现位置 |
|------|------|------|
| 换线慢、跨界面串行 | 工作流引擎 + 无依赖步骤并行 + barrier | [流程编排能力 §3.1](FactoryAgent-流程编排能力.md) |
| 漏步骤、带病生产 | barrier 硬校验双 PASS + 应用服务不变式 | [流程编排能力 §6.3](FactoryAgent-流程编排能力.md) `barrier_node` |
| 写动作越界 / 无审计 | 写工具白名单 + gate 走正常应用服务 + 决策落库 | [总体设计 §5.3](FactoryAgent-总体设计与实现方案.md) `ToolPolicyGate` |
| Agent 误触放行 | 放行能力从工具集裁掉 + 启动断言禁 `pass_judge` / `force_release` | [流程编排能力 §4.4](FactoryAgent-流程编排能力.md) |
| 版本串错 | 版本锚点从领域模型强制过滤（ACL） | [诊断能力 §3](FactoryAgent-诊断能力.md) |
| 长流程卡住无人推 | 动作卡主动推 + 超时升级 + session 状态可视 | [流程编排能力 §5](FactoryAgent-流程编排能力.md) |

**为什么要把这层划清楚**：面试时如果把"防错 / 并行 / 审计"都算 Agent 卖点，一问"这工作流引擎能不能做"就露馅。把这层明确划给代码，能力只讲 A–C + D 四类非确定 / 生成痛点，**恰恰是"懂什么时候不用 AI"的判断力**。

## 2. 总结：Agent 解决的真痛点

| 痛点类别 | 人脑痛点 | 代码为什么难 | 能力如何降复杂度 | 设计支撑 |
|---------|---------|------------|-----------------|---------|
| **核对异常处置**（A） | mismatch 后人脑判根因 + 电话串 3 系统 + 口头处置 | 根因分支组合爆炸 + 跨上下文证据汇聚 + 处置映射开放 | 诊断自适应取证 + 根因假设；草稿出处置卡 + 路由 | 编排 mismatch 分支 |
| **故障隔离范围**（B） | 人脑估漂移时间窗 + 凭印象判产品敏感度 | 故障模式 × 漂移窗口 × 敏感度三维动态 + 敏感度知识散落 | 诊断推理故障模式 + 敏感度关联；草稿出隔离集卡 | [流程编排能力 §3.2](FactoryAgent-流程编排能力.md) |
| **客诉根因追溯**（C） | 跨 5 界面手工串 + 5M1E 假设靠人脑排 | 跨源语义关联 + 自适应取证 + 假设加权排序 | 版本钉死（代码）+ 诊断自适应取证 + 5M1E 排序 + 草稿出 8D | [流程编排能力 §3.3](FactoryAgent-流程编排能力.md) |
| **生成类输出**（D） | SOP / 8D 靠工程师从零手写 | 自然语言生成，代码写不出 | 草稿能力草拟 + 人审改 | `SOP` / `EIGHT_D` builder |

**一句话**：Agent 解决的真痛点是 **"非确定异常处置靠人脑拍 + 跨上下文证据靠人串 + 生成类输出靠人手写"**——这三类传统代码做不了或做起来极复杂（根因分支组合爆炸、跨源语义关联、自然语言生成），能力用"自适应取证 + 推理假设 + 草拟 + 人确认"大幅降复杂度。**它不碰两层确定性活**：不替代规则引擎做过点判定（200ms 硬约束），不替代 barrier 做硬防错。Agent 只把"查完 → 诊断 → 草拟处置 → 推动作 → 人确认落库"这条人肉链里**非确定的那段**升级成带闸门的自动链，而写的闸门始终在人手里。

## 3. 面试防守 Q&A

**Q：这些痛点是不是为了讲技术造的？**
A：不是。换线 mismatch 后人脑判根因、故障期间漏隔离、客诉追溯版本串错、SOP/8D 手写——都是 MES 现场真实高频痛点。但我只挑传统代码做不了的那 4 类（根因分支 / 隔离范围动态判定 / 跨源根因排序 / 生成类）；其余的慢、漏、越界写、误触放行、版本串错、卡住无人推，我明确划给工作流引擎 + 状态机 + ACL——那些代码能做且更可靠，不算 Agent 卖点。痛点是真的，解法是设计阶段的规划，我不编业务效果数字，只讲能力。

**Q：换线防错如果代码就能做，为什么还要上 Agent？**
A：判断标准是三问。换线里步骤顺序、齐套率判定、钢网号比对、程序版本校验全是确定规则，代码做、能力不掺和。能力只在四处赚回成本：① mismatch 后推理根因 + 出处置卡（诊断 + 草稿）；② 故障隔离范围动态判定（诊断 + 草稿）；③ 客诉 5M1E 假设排序（诊断）；④ SOP/8D 草拟（草稿）。如果某场景全程确定，那就不该上 Agent，上个工作流引擎就够了。

**Q：痛点 A 的 mismatch 处置，规则引擎真的做不了吗？**
A：能写，但维护成本高且永远落后。根因不止"拿错"，还有"上工单未还库""台账改名""借出未登记""工艺录错""扫码枪读码制式不同"……每出现一种现场情况就要补分支 + 补跨上下文联合查询，而判定阈值是启发式的，新情况一来就漏。Agent 的优势不是"比决策树聪明"，而是**取证路径由中间结果驱动**——查到"ST-A 借出未还"后自适应去查上工单收线记录，而不是套固定 JOIN。新根因出现时只要取证能查到证据就能给假设，决策树不用改。

**Q：为什么"通用 Agent 误触放行"不算 Agent 痛点？**
A：因为它不是"Agent 解决的痛点"，是"引入 Agent 后必须用代码堵的风险"。通用 Agent 接 MES 写 API 是很多"AI 赋能 MES"方案的默认做法，风险在幻觉 + 无权限隔离。本方案的解法是**架构层把放行能力从工具集裁掉**（任何能力下都不注册 `pass_judge` / `force_release` / `release_*`，启动断言校验）——这是代码 / 架构层的活，不归在 Agent 真痛点里。讲清楚这条，体现的是懂 MES 写红线的严肃性。

**Q：这些场景上线了吗？**
A：没有，是设计阶段的方案。落地要先等 RAG 追溯能力成型，诊断与草稿先验证可用性，编排是试点形态。我讲的是"如果这么设计能解决什么"，不是"已经跑出多少收益"——诚实 + 体现架构判断力，比硬吹"已上线 AI Agent"得分高。

---

## 4. 一句话定位

"Agent 的价值只在三处：把'非确定异常处置靠人脑拍'变成'诊断能力自适应取证 + 假设排序'，把'跨上下文证据靠人串'变成'一条 trace 串起来的证据链'，把'生成类文档靠人手写'变成'草稿能力草拟 + 人审改'。其余的防错、并行、审计、版本钉死全是代码的功劳——把这层划清楚，才谈得上懂什么时候不用 AI。"
