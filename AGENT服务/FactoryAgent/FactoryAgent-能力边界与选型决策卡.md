# FactoryAgent —— 能力边界与选型决策卡

> 一页速查：**什么时候用哪项能力、什么时候什么能力都不用**。用于方案评审 / 面试现场快速回答"这里为什么上 LLM""这里为什么不上"。
> **口径纪律**：不编业务效果数字（良率 / 停线百分比等），只讲选型判断与代码事实。
> **配套**：[总体设计](FactoryAgent-总体设计与实现方案.md)、[诊断能力](FactoryAgent-诊断能力.md)、[草稿编写能力](FactoryAgent-草稿编写能力.md)、[流程编排能力](FactoryAgent-流程编排能力.md)、[现场痛点与能力嵌入点](FactoryAgent-现场痛点与能力嵌入点.md)。

## 1. 判定三问（与"能力"无关的第一性标准）

一个 MES 步骤要不要交给模型，先过三问：

| # | 问题 | "是"的含义 |
|---|------|-----------|
| ① | **输入是否开放？** | 非结构化、需语义理解，不是 `expected == actual` 的结构化判定 |
| ② | **是否需要推理 / 生成？** | 非固定规则，要假设 / 排序 / 生成 |
| ③ | **分支是否难以穷举？** | 决策树永远落后于现场，新情况一来就漏 |

**判定规则：三问皆否 → 代码节点；三问有一 → 交给能力。**

三问过后再问第二层：**该用哪项能力？**

| 命中 | 该用哪项能力 | 理由 |
|------|-------------|------|
| ②③ 命中，需要"假设 / 排序 / 归因"，且取证路径不固定 | **诊断能力** | 开放式 ReAct 循环，取证由中间结果驱动 |
| ①②③ 命中，需要"结构化叙事 / 长文本 / 卡片内容" | **草稿编写能力** | 固定链 + 结构化输出，开放生成是代码做不了的 |
| 需要跨上下文按序推进、并行、硬防错、写落库 | **流程编排能力**（代码图） | 确定性段用代码，非确定段再调上两项 |
| 三问皆否 | **不用能力**（代码 / 规则引擎 / 工作流引擎） | LLM 在这里是负资产，靠近过点红线还是风险 |

> 可验证标志：换线全程 PASS 时 `agent_llm_invocation_total{scenario="changeover"} = 0`，而 `agent_step_total{node_type="CODE"}` 正常增长——"该用才用"是能被指标验证的，不是口号。

## 2. 该用能力的四类（代码做不了或极复杂）

| 能力使用点 | 用哪项能力 | 真痛点 | 三问命中 | 传统代码为什么难 |
|---|---|---|---|---|
| **A 核对异常根因与处置路由** | 诊断 + 草稿（`DISPOSITION_CARD`） | 换线 mismatch 后人脑判根因 + 电话串 3 系统 + 口头处置无审计 | ②③ | 根因分支组合爆炸 + 跨 4 上下文证据汇聚 + 启发式阈值 |
| **B 故障隔离范围** | 诊断（遥测 + FMEA）+ 草稿（`ISOLATION_CARD`） | 人脑估漂移时间窗 + 凭印象判产品敏感度 → 漏隔离 / 过隔离 | ②③ | 故障模式 × 漂移窗口 × 敏感度三维动态，规则引擎爆炸 |
| **C 客诉根因追溯** | 诊断（5M1E 排序） | 跨 5 界面手工串 + 版本串错 + 假设靠人脑排 | ②③ | 跨源语义关联（JOIN 只能做字段相等）+ 假设加权排序 |
| **D1 生成类** | 草稿（`EIGHT_D` / `SOP`） | 8D / SOP 靠工程师从零手写 | ①②③ | 结构化叙事生成，代码写不出 |

**A / B / C 的共同收益**：取证路径由中间结果驱动（不是固定 JOIN），新根因 / 新故障 / 新产品出现时只要取证能查到证据就给假设，**决策树不用改**。D1 是价值最干净的一类——代码完全做不了。

> **D2 返工工艺选型不属于生成类**：其输出契约是 `{rework_route, reentry_point}` 两个**指针**（路线 ID + 回起工位），不是工艺内容；返工路线的温度 / 时间 / 工序都在版本化路线库里由 ACL 守（版本锚点强制 + `ACTIVE` 校验），LLM 碰不到参数。过三问：① 输入半结构化、目标空间（工艺库）结构化 → 否；② 匹配 route + 选 reentry 工位，非生成 → 否；③ `(不良模式 → 返工路线)` 是库内有界映射 → 否。**三问皆否 → 代码节点**（`不良模式 → query_route(版本锚点强制 + ACTIVE 校验) → (rework_route_ref, reentry_point)`）。仅"库未命中的新不良模式"边角才上能力做候选推荐，输出仍是结构化选型 + `need_human_review`，参数绝不经 LLM。

## 3. 不该用能力的地方（代码兜底，硬逻辑更快更好）

| 活 | 代码解法 | 为什么不用能力 |
|---|---|---|
| 步骤编排 / 并行 / 汇合 | `StateGraph` 显式边 | 确定性，LLM 非确定性是负资产 |
| 结构化比对（齐套率 / 钢网号 / 程序版本） | `query_compare` 代码节点 | `expected == actual` |
| 漏步骤 / 带病生产防错 | `barrier` 双 PASS 硬校验 | 状态机比 LLM 可靠 |
| 写动作越界 | 写工具白名单 + confirmation token | 权限模型，不是能力 |
| 误触放行 | 放行能力从工具集架构层裁掉 + 启动断言 | 风险兜底靠代码不靠 LLM |
| 版本串错 | ACL 强制版本锚点过滤 | 确定性校验 |
| 过点放行 / 拦截（P99 ≤200ms） | 规则引擎 | 能力绝不进过点主事务 |
| 返工工艺选型（D2） | `query_route(不良模式)` → 指针 | 输出是指针不是工艺内容，三问皆否 |
| 放行卡拼装 | 代码结构化拼装 `draft_release_card` | 碰过点红线，不让 LLM 生成 |
| 缺料挂起催料 | 直接 `SUSPENDED` + 推卡 | 缺料是确定的 |

> 这层划清楚很重要：面试时若把"防错 / 并行 / 审计"都算 Agent 卖点，一问"工作流引擎能不能做"就露馅。明确划给代码，能力只讲 A–C + D1 四类非确定痛点，恰恰是"懂什么时候不用 AI"的判断力。

## 4. 三条红线（写动作的闸门始终在人手里）

1. **不进过点主事务**——放行类工具（`pass_judge` / `force_release` / `release_*` / `block_pass`）不注册到任何能力，启动断言校验。
2. **写不旁路应用服务**——写工具必须声明 `requires_confirmation` + `writes_via`，人确认后走各上下文正常应用服务（过聚合根不变式 + 事务发件箱），不直写原始表。
3. **能力只草拟不发布**——生成 intent + draft（动作卡），低置信度标 `need_human_review`，不自动路由 / 不自动发布。

三条红线分别由三个机制兜底：能力声明（`writes_allowed`）、工具声明（`requires_confirmation` + `writes_via`）、运行时 token（绑定 `action:target` + 过期）。**都是启动或调用时失败的硬约束，不是评审时的口头承诺。**

## 5. 场景节点验证

对着 `factorybot/app/orchestration/scenarios/specs.py` 的三个场景，逐节点过三问，确认能力使用点都踩在"三问有一"上。

### 5.1 验证方法

- 对每个**能力节点**（`run_agent(...)`）逐一过三问，记录命中数与理由。
- 对"看似该用能力却用了代码"的节点，确认三问是否皆否（代码合理）。
- 对占位桩 / 悬空能力，标 ⚠️ gap。

### 5.2 场景① `CHANGEOVER`

| 节点 | 性质 | 三问验证 |
|---|---|---|
| plan / first_article / process_switch | 代码 | 确定性查询 |
| tooling_check / kitting_check | 代码 | `expected == actual` 结构化比对 |
| barrier | 代码 | 确定性分流 |
| draft_release / gate_* | 代码 | 结构化拼装 + gate |
| **root_cause** | **诊断能力** | ①半（结构化 mismatch，但根因需跨 4 上下文语义区分）②**是**（根因假设 + 置信度）③**是**（根因空间开放）→ **2 是，成立 ✓** |
| **disposition_card** | **草稿能力** | ②**是**（自然语言处置建议 + 路由）③**是**（升级对象开放）→ **成立 ✓** |

**两个"懂不用"的点**：`kitting FAIL → suspend` 不调能力（缺料确定）；`draft_release_card` 由代码结构化拼装（不让 LLM 生成放行卡）。

### 5.3 场景② `FAULT_RESPONSE`

| 节点 | 性质 | 三问验证 |
|---|---|---|
| plan | 代码 | 确定性 |
| draft_repair_order | 代码 | 结构化拼装（`asset_id` / `fault_time` / `status`）→ 三问皆否 ✓ |
| **fault_impact** | **诊断能力** | ①半（遥测时序需形态判断）②**是**（故障模式 + 漂移窗口 + 敏感度）③**是**（三维动态）→ **2 是 ✓** |
| **isolation_card** | **草稿能力** | ②③ 命中（隔离理由 + 敏感度说明需生成）✓ |
| gate_repair / gate_isolation | 代码 gate | gate 是代码 |
| gate_recalibration / gate_restart_first_article | 代码 gate | **复校 / 复产首件两道红线，能力不碰** ✓ |

### 5.4 场景③ `COMPLAINT_8D`

| 节点 | 性质 | 三问验证 |
|---|---|---|
| plan | 代码 | 确定性 |
| **traceability** | **诊断能力** | ①半（批次号结构化，跨 5 上下文证据需语义关联）②**是**（5M1E 加权排序）③**是**（同证据不同背景排序不同）→ **2 是 ✓** |
| supplier_trace | 代码 | 自适应取证后的并行确定性查询 ✓ |
| **isolation_scope** | **代码（占位桩）** | ⚠️ 见 §5.5 |
| **draft_8d** | **草稿能力** | ①**是**（追溯链 + 历史 8D 开放文本）②**是**（自然语言生成）③**是**（代码写不出）→ **3 是，最干净 ✓** |
| gate_isolation_8d / gate_8d_publish | 代码 gate | gate 是代码 |

### 5.5 验证发现：1 个 gap + 1 个悬空能力

**⚠️ Gap：`isolation_scope` 是空占位桩。** `query_compare.py` 恒返 `{"batches": [], "reason": "determined_by_code"}`，而 [痛点方案](FactoryAgent-现场痛点与能力嵌入点.md) 明确写客诉场景的隔离范围判定"同痛点 B 的动态判定"。两条出路需拍板：① 若客诉隔离可确定（已知不良批次 → 按供应商批次号查在库品集合），实现成真正的确定性查询代码节点；② 若确需动态判定（关联敏感度 / 历史不良），改为 `invoke("diagnosis")` 复用隔离范围能力。**不能留空桩**——隔离集恒为空等于该分支是哑的。

**⚠️ 悬空能力 + 分类错配：`draft_rework_craft` 不该是生成类。** 其输出契约是 `{rework_route, reentry_point}` 两个指针，安全参数（温度 / 时间 / 工序）在版本化路线库里由 ACL 守，LLM 碰不到；且草稿能力的 `ReworkOrderDraftBuilder` 已在草拟返工单，编排层这份是重叠悬空物。收口路径：主路径代码化（`query_route` → 指针），仅"库未命中的新不良模式"边角调能力做候选推荐（`low confidence + need_human_review`），或直接删除。

### 5.6 验证总结

| 场景 | 能力使用点 | 三问结论 | 纪律执行 |
|---|---|---|---|
| CHANGEOVER | 诊断（root_cause）+ 草稿（disposition_card） | ②③ 成立 | ✓ 缺料不调能力、放行卡走代码 |
| FAULT_RESPONSE | 诊断（fault_impact）+ 草稿（isolation_card） | ②③ 成立 | ✓ 复校 / 复产首件红线留代码 |
| COMPLAINT_8D | 诊断（traceability）+ 草稿（draft_8d） | ②③ / ①②③ 成立 | ⚠️ `isolation_scope` 空桩、`draft_rework_craft` 分类错配 |

**结论**：三个场景的能力使用点全部踩在"三问有一"上，没有任何一个确定性步骤被错配给 LLM。待收口的是功能性 gap（空桩）与分类错配（选型非生成），**不是选型错误**。

## 6. 面试防守 Q&A

**Q：换线防错如果代码就能做，为什么还要上 Agent？是不是为了用 AI 而用 AI？**
A：判断标准是三问。换线里步骤顺序、齐套率判定、钢网号比对、程序版本校验、barrier 未双 PASS 不放行，全是确定规则，代码做、能力不掺和——所以我把它划成代码节点 + barrier，换线全程 PASS 时 LLM 调用为 0。能力只在 mismatch 后推理根因（诊断）、故障隔离范围（诊断 + 草稿）、客诉 5M1E 排序（诊断）、8D / SOP 生成（草稿）这四处赚回成本。

**Q：这些场景上线了吗？**
A：没有。这是设计阶段的方案，落地要先等 RAG 追溯能力成型，诊断与草稿先跑通，编排再试点。本文的"验证"是对着当前代码的静态选型审查，确认能力使用点没站错位置，不编业务效果数字。

**Q：为什么不再按"诊断 / 草稿 / 编排"分等级？**
A：因为真实需求横跨它们，分级后只能靠单向依赖硬接。现在能力是"图形态 + 工具切片"：诊断是开放式 ReAct 子图、草稿是固定链、编排是 supervisor 代码图，共用一套 runtime / 注册表 / 闸门 / trace。风险梯度改用两个更本质的维度控制：能力的 `writes_allowed` 声明 + 工具的 `requires_confirmation` / `writes_via` 声明，两者都由启动断言兜底。

**Q：`isolation_scope` 为什么是空桩？**
A：待收口的功能性 gap，不是选型错误。设计说客诉隔离范围同痛点 B 的动态判定（该调诊断能力），当前实现是空代码桩、隔离集恒为空。若可确定就实现成确定性查询代码；若需动态判定就复用诊断能力。不管哪条，不能留空桩给人"已覆盖隔离"的错觉。

**Q：返工工艺草拟原本算生成类，为什么又归代码层？**
A：按三问纠偏，不是来回改。核代码：`draft_rework_craft` 输出 `{rework_route, reentry_point}` 两个指针，不是工艺内容；返工路线的参数在版本化路线库里由 ACL 守，agent 碰不到。过三问：输入半结构化、匹配 route 非生成、`(不良模式 → 返工路线)` 是库内有界映射——三问皆否，就是代码节点。真要上能力，只在"库未命中的新不良模式"边角做候选推荐，输出仍是结构化选型 + `need_human_review`。这正是"懂什么时候不用 AI"：把选型硬塞给生成类，一问"输出是不是自然语言"就露馅。

## 7. 一句话定位

"选型不看它在哪项能力里，只看三问：输入是否开放 / 是否需推理生成 / 分支是否难穷举。三问皆否就用代码强校验、规则引擎、工作流引擎——更快、更可靠、更可审计，靠近过点红线时 LLM 反而是风险；三问有一才交给能力，并按'要假设排序就走诊断、要自然语言产物就走草稿、要跨上下文推进就走编排'落到具体能力上。写动作过 confirmation gate、走应用服务、不进过点主事务。**懂得什么时候不用 AI，比硬塞 Agent 值钱得多。**"
