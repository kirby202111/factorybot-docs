# L3 编排型 Agent —— 痛点操作步骤与解决方案对照

> 本文针对 [L3编排型Agent-实现方案.md](L3编排型Agent-实现方案.md) §1.4 列出的典型场景所解决的痛点，逐一展开 **"痛点存在时（无 Agent）的详细人工操作步骤"** 与 **"L3 引入后的解决方案"**，用于在面试 / 评审中讲清"这套 multi-agent 到底省了什么、防了什么"。
> **口径纪律**：本文描述的是**操作步骤与设计能力**，不编造业务效果数字（良率提升、停线下降百分比等）。凡涉及耗时，均为"人工作业经验量级"的定性描述，非线上实绩；L3 的收益以"消除某类等待 / 消除某类漏步骤 / 写动作可审计"等能力口径表述，符合 [项目亮点与指标卡片.md](../../面试指南/项目亮点与指标卡片.md) §0 的纪律。
> **配套**：实现方案见 [L3编排型Agent-实现方案.md](L3编排型Agent-实现方案.md)，LangGraph 架构见 [L3编排型Agent-LangGraph架构与流程图.md](L3编排型Agent-LangGraph架构与流程图.md)。
> **场景口径修正**：换线（痛点 1、2）只覆盖"工艺版本切换 / 物料齐套 / 钢网夹具核对 / 设备程序下发 / 首件验证放行"。**不含日常设备点检与计量检定**——前者属班次点检上下文、后者属计量周期校验上下文，与换线无依赖，不应混入换线链路。设备故障场景（痛点 6）的"维修后计量复校"是精度恢复动作，与换线无关。

## 痛点 1：换线 / 异常处置慢，停线时间长

### 1.1 痛点存在时的详细操作步骤（人工）

假设 SMT+整机组装产线从工单 A（产品 X）切换到工单 B（产品 Y），线长主导：

1. **接收换线指令**：线长在调度系统看到工单 B 已下达，手动记下目标工艺路线 ID 和版本。
2. **登入工单系统**：打开工单管理界面，查工单 B 状态、确认排产数量、交付期。
3. **切到工艺系统**：打开工艺管理界面，查工单 B 对应工艺路线 RR-B 的当前生效版本 v4——v4 里挂着 SMT 贴装程序号 PB-B-v4、钢网编号 ST-B、回流炉温曲线 TC-B-v4、组装 SOP 版本。**人脑记下 v4 和这一串编号**（或写在纸上）。
4. **切到物料系统**：打开物料管理界面，按工单 B 的 BOM v4 核对物料齐套——SMT reel / 飞达、锡膏批次、辅料、组装件，缺料则电话催仓库备料。
5. **切到钢网夹具管理**：从钢网库取出 ST-B 钢网、过炉夹具、组装工装，**手工逐项核对编号**与工艺要求一致（拿错钢网是现场经典事故）。
6. **切到设备程序下发**：在 SMT 贴片机调用程序 PB-B-v4、回流焊加载炉温曲线 TC-B-v4、组装工位加载 SOP——**凭步骤 3 人脑记的编号手输**，易输错版本。
7. **切到首件系统**：打开首件处理界面，手动创建首件工单，关联工单 B 与工艺路线 RR-B v4，提交。
8. **等首件工单审批**：电话 / 微信找工艺工程师确认首件工单，工程师登入系统审批。
9. **回到工单 / 过点系统**：确认工艺版本已激活、物料齐套、钢网夹具核对、程序下发完成，**人脑汇总判断**可以放行首件。
10. **切到过点系统**：打开过点执行界面，手动下达首件放行，首件过点。
11. **首件验证**：首件过点后送检，等质检结果，不合格则回到第 3 步重调工艺。

**痛点点**：

- 步骤 4 / 5 / 6 三件事**本无依赖**（都只依赖工艺版本 v4），却在线长手里被串行执行——在工艺 / 物料 / 钢网夹具 / 设备程序 4 个界面间来回切，每步等上一步完成才动，白白多花两三倍时间。
- 步骤 3 与步骤 6 的"人脑记 v4 + 手输程序号 / 钢网号"是版本串错的隐患（见痛点 5）——拿错钢网、调错程序版本都是现场高频事故。
- 步骤 9 的"人脑汇总判断"是漏步骤的隐患（见痛点 2）。
- 整个换线期间产线停工，串行时长直接等于停线产能损失。

### 1.2 L3 解决方案

L3 把步骤 2–10 编排成 supervisor + sub-agent 的自动链，关键改造：

- **①②串行保留**：首件触发 → 工艺版本切换确认，仍是串行（有依赖：首件工单要绑工艺路线版本）。
- **③④并行**：步骤 4（物料齐套核对）与步骤 5 / 6（钢网夹具核对 + 设备程序下发确认）由 MaterialKittingAgent 和 ToolingSetupAgent **并发执行**，supervisor 在放行门禁前 barrier 一次，等两者都 PASS。省掉的是"人串界面"的串行等待，不是省判定时间。
- **gate 替代人脑判断**：每个需要确认的步骤（首件触发、工艺激活、放行）是 supervisor 图里的显式 gate 节点，`interrupt` 暂停 → 推动作卡给责任人 → 人确认 → `resume` 续跑。线长不再"人脑汇总判断"，图自己卡在 barrier 直到双 PASS。
- **版本不靠人记、编号不靠人输**：工艺版本由 ProcessSwitchAgent 的 ACL 强制带 `routeVersion` 查询（继承 L1 §4.3）；钢网编号、程序号、炉温曲线号都由工艺路线 v4 驱动下发，不靠线长手输——从根上消除"拿错钢网、调错程序版本"。

**对应实现**：[实现方案 §5.1](L3编排型Agent-实现方案.md) 并行分支 + barrier；[架构图 §3](L3编排型Agent-LangGraph架构与流程图.md) supervisor 编排流程图。

**能力口径（非数字）**：消除"物料齐套 ‖ 钢网夹具 / 程序核对"的串行等待；消除线长跨 4 个界面切换 + 手输编号的认知负荷；停线时长从"全串行 + 人串界面 + 手输编号"降为"无依赖步骤并行 + gate 等人确认"。

## 痛点 2：漏步骤导致带病生产（防错失效）

### 2.1 痛点存在时的详细操作步骤（人工）

接痛点 1 的换线场景，线长在压力下常见的"漏步骤"路径：

1. 工单 B 紧急，线长接到调度催促"尽快换线"。
2. 步骤 5 钢网夹具核对：线长图快，**没去钢网库核对 ST-B**——"上一工单的钢网差不多还能用"，或扫了一眼编号没细对。
3. 步骤 6 设备程序下发：**凭记忆调程序**，错调成 PB-B-v3（v4 之前的旧版本），或回流炉温曲线没切换、仍用上一个产品的曲线。
4. 步骤 4 物料齐套：齐套率显示 92%，缺某辅料，线长判断"辅料不影响首件"，**齐套未达 100% 仍推进**。
5. 步骤 9 人脑汇总判断：线长记得"程序调了、物料差不多齐了、钢网应该对了"，**主观判定可以放行**。
6. 步骤 10 下达首件放行，首件过点。
7. 首件过点后批量生产：错钢网导致印刷偏移、或错程序版本导致贴装坐标偏、或炉温曲线错导致焊接冷焊 → **批量不良**。
8. 不良在后道工序（AOI / 质检）才被发现，此时已生产若干批次，**返工或报废**。

**痛点点**：

- 步骤 2–4 的"图快跳步 / 凭记忆"是人性，MES 现场高频发生——换线时拿错钢网、调错程序版本是经典事故。
- 步骤 5 的"人脑汇总判断"是防错的最后一道闸门，但**全靠人自觉**，无系统强制。
- 步骤 2 / 3 的问题在步骤 7 才暴露，**无前置校验**——系统不会主动拦"钢网编号与工艺要求不符 / 程序版本不是当前生效版本就不让放行首件"。
- 后果是"带病生产"到后道才暴露，返工 / 报废成本远高于"换线时多等 10 分钟"。

### 2.2 L3 解决方案

L3 把"防错"从"人自觉"升级为"图结构强制"：

- **步骤是显式图的边**：supervisor 的 `StateGraph` 里，`barrier_node` → `release` 这条边**只有一条**，barrier 内部硬校验 `gate_kitting == PASS and gate_tooling == PASS`（齐套 + 钢网夹具核对 / 程序下发确认）。漏任何一个 gate，图根本走不到 `release` 节点——**不是"提醒人别漏"，是"漏了就走不下去"**。
- **gate 必须人确认**：钢网夹具核对 gate、程序版本下发 gate、齐套 gate 各自 `interrupt` 等人确认。线长不能"扫一眼编号"糊弄，因为 gate 等的是**确认 token + 责任人**，确认即留痕。
- **编号由工艺版本驱动，不靠人输**：ToolingSetupAgent 拿工艺路线 v4 里的钢网号 / 程序号 / 炉温曲线号驱动核对与下发，**线长手输编号这一步被消除**——拿错钢网、调错版本从源头杜绝。
- **齐套率不达标直接挂起**：MaterialKittingAgent 返回齐套率 < 100% 时，gate 标 `REJECT`，supervisor `SUSPENDED` 推异常卡，**不允许"差不多齐了就推进"**。
- **程序版本不一致阻塞**：ToolingSetupAgent 发现设备当前程序版本与工艺路线 v4 不一致，sub-agent 返回 `FAILED`，supervisor 挂起推线长升级，**不会自动跳过**。

**对应实现**：[实现方案 §5.1](L3编排型Agent-实现方案.md) `_barrier_node` 未双 PASS 直接 `SUSPENDED`；[§8.3](L3编排型Agent-实现方案.md) 故障隔离兜底。

**能力口径**：消除"漏步骤放行"这一类防错失效——barrier 把"齐套 PASS 且 钢网 / 程序核对 PASS"从人脑判断变成图结构硬约束；消除"图快跳步 / 凭记忆调错版本"——gate 必须人确认留痕，且编号由工艺版本驱动不靠人输。

## 痛点 3：写动作越界 / 无审计

### 3.1 痛点存在时的详细操作步骤（人工）

现场常见的"为了快而越界写"路径，以发返工单为例：

1. 质量工程师发现某批次要返工，登入返工上下文正式界面。
2. 正式界面要求填返工工单（关联 `source_work_order_id`、返工工艺路线、返工用料），填完提交，走应用服务 → 聚合根不变式校验 → 事务发件箱落库。**这是正规路径**。
3. 但返工工单审批流程要走两级（工程师提 + 主管批），耗时。工程师"为了快"：
   - **越界路径 A**：直接调返工上下文的内部 REST（绕过正式界面的校验），用 Postman / 内部工具直发返工工单。聚合根不变式可能被绕过（直接写表或调了不该公开的接口）。
   - **越界路径 B**：让产线操作工在过点系统"手动标记返工"，但实际没走返工工单流程，返工数据散落。
4. 事后追溯"这张返工单谁批的"：
   - 正规路径：`changeover_step_record` / 审批表有记录。
   - 越界路径 A：只有一条 REST 调用日志，**不知是谁、为何批**，应用服务层的不变式校验日志缺失。
   - 越界路径 B：返工数据在过点系统手填，与返工上下文不一致，**追溯链断裂**。
5. 审计 / 客诉时查不到完整链路，责任无法界定。

**痛点点**：

- 步骤 3 的"为了快越界写"是 MES 现场高频痛点——正规流程慢，人就找捷径。
- 越界写的核心问题是**绕过应用服务的不变式校验和事务发件箱**：直接写表可能破坏聚合根不变式（如返工工单未关联 `source_work_order_id`），不走发件箱则返工事件不发，下游缓存 / 追溯链不更新。
- 步骤 4–5 的"无审计"是越界写的必然结果——没有 gate 决策记录，事后查不到谁批的、基于什么批的。

### 3.2 L3 解决方案

L3 把"写"控制成"意图卡 + 人确认 + 走正常应用服务"：

- **Agent 只生成意图卡**：写工具强制 `requires_confirmation=True`，Agent 调 `draft_rework_order` 工具只生成 ActionCard（含 `draft_payload` + `writes_via` + `evidence`），**不落库**。
- **gate 必须人确认**：ActionCard 推给责任人，`interrupt` 暂停，人确认后 issue confirmation token（绑定 `action:target` + 过期），`Command(resume=token)` 续跑。
- **写落库走正常应用服务**：token 交给 `writes_via` 指向的应用服务 REST（如返工上下文的 `POST /api/rework-orders`），**过聚合根不变式校验 + 事务发件箱**——与正规路径完全一致，只是触发源从"人点按钮"变成"Agent 草拟 + 人确认"。
- **gate 决策全留痕**：`changeover_step_record` 记录谁确认、何时、基于哪张卡、token 是什么，**全可审计**。
- **越界路径被架构层堵死**：Agent 进程不持有 MES 原始表的写权限，只持 REST 调用权限；REST 调用必须带 confirmation token，token 绑定具体 `action:target`——"为了快"无法绕过 gate，因为 gate 是图结构里的必经节点。

**对应实现**：[实现方案 §4.3](L3编排型Agent-实现方案.md) `WriteToolGate`；[§5.3-5.4](L3编排型Agent-实现方案.md) 写路径与 ACL；[§5.2](L3编排型Agent-实现方案.md) gate 决策落库。

**能力口径**：消除"为快越界写"——写动作过 gate 人确认，无法绕过；消除"无审计"——gate 决策全留痕；保证写路径不旁路应用服务——过聚合根不变式 + 事务发件箱，与正规写路径一致。

## 痛点 4：放行 / 拦截被 Agent 误触（过点红线）

### 4.1 痛点存在时的详细操作步骤（通用 Agent 场景）

假设引入了一个"通用 AI Agent"赋能现场，未做权限隔离：

1. 线长问 Agent："工单 B 首件可以放行了吗？"
2. 通用 Agent 调度过点系统的放行 API（`POST /api/pass/release`），**直接触发过点放行**。
3. 但此时钢网 / 程序核对未完成（步骤 5 / 6 漏了核对，或程序仍是旧版本），或物料齐套率仅 92%。
4. Agent 基于不完整信息或模型幻觉，判定"可以放行"，放行 API 被调用。
5. 过点主事务执行放行，首件过点，**规则引擎未拦截**（因为 Agent 调的是放行 API，绕过了"首件未验证不放行"的业务规则检查，或规则检查被 Agent 的上下文误导）。
6. 首件过点后批量生产，因钢网 / 程序版本错导致批量不良。
7. 事后查：Agent 调了放行 API，日志显示"AI 触发放行"，**但无人为审批记录**，责任无法界定。

**痛点点**：

- 步骤 2 的"Agent 直接调放行 API"是通用 Agent 在 MES 的最大风险——**模型幻觉 + 无权限隔离 = 灾难**。
- 步骤 4 的"基于不完整信息判定"是模型固有问题，不可根除，只能靠**架构层不让它有放行能力**。
- 步骤 5 的"规则引擎未拦截"暴露了 Agent 进过点主事务的危害——过点 P99 ≤200ms 的判定本应只走规则引擎，Agent 进来会拖慢判定、引入不确定性。
- 后果是批量不良 + 责任无法界定，这是 MES 写红线的最严重后果。

### 4.2 L3 解决方案

L3 把放行能力从架构层切掉，不靠 prompt 约束：

- **放行能力只挂在 PassReleaseAgent**：且 PassReleaseAgent 只有 `draft_pass_release_card` 工具（生成放行意图卡），**没有任何调放行 / 拦截 API 的工具**。工具名前缀禁含 `pass_judge` / `force_release`，启动断言校验。
- **supervisor 不持工具**：supervisor 想放行也调不到工具——能力从架构层切掉，不是 prompt 说"你别放行"。
- **其他 sub-agent 看不到放行工具**：工具按 `agent_role` 裁剪，FirstArticleAgent / InspectionAgent 等根本注册不到放行类工具。
- **实际放行仍走过点主事务**：人确认放行意图卡后，走过点执行上下文的正常应用服务（过点主事务 + 规则引擎判定，P99 ≤200ms）。Agent 只生成意图，判定仍是规则引擎——**Agent 不进过点主事务**。
- **barrier 前置防错**：supervisor 在 PassReleaseAgent 之前 barrier 等钢网 / 程序核对 + 齐套都 PASS，**避免在钢网 / 程序核对未完成、物料未齐时推放行卡**——即使模型幻觉想放行，barrier 不通过，放行卡根本不生成。

**对应实现**：[实现方案 §4.1](L3编排型Agent-实现方案.md) 工具映射；[§5.5](L3编排型Agent-实现方案.md) 过点 sub-agent 特殊约束；[§7.5](L3编排型Agent-实现方案.md) 启动断言。

**能力口径**：消除"Agent 误触放行"——放行能力从架构层隔离，模型幻觉无法触发放行 API；保证过点主事务不被 Agent 侵入——过点 P99 ≤200ms 判定仍走规则引擎；保证放行可审计——意图卡 + 人确认留痕。

## 痛点 5：跨系统信息孤岛，人肉串联慢且错

### 5.1 痛点存在时的详细操作步骤（人工）

以"诊断某单件焊接不良根因"为例，工程师人肉串联：

1. 工程师登入过点系统，查单件 SN-001 的过点记录，看到过点时间、过点站、TestResult。**人脑记下过点时间**。
2. 切到工艺系统，查该过点时间对应的工艺路线版本——但工艺界面默认显示**当前生效版本** v5，工程师**没意识到** SN-001 过点时用的是 v3（版本已更新过两次），**用 v5 的工艺参数去分析 v3 的过点问题**，得出错误结论。
3. 切到物料系统，查同批次锡膏批次号 B-77，**人脑记下 B-77**。
4. 切到设备数据系统，查贴片机 ASSET-01 在 SN-001 过点时段的参数，但设备数据按时间范围查，工程师**记错时间**（差了几分钟），查到的参数不是当时的。
5. 切到质量系统，查同批次其他单件的不良率，手工统计（Excel 或系统报表），**统计口径不一致**（有的按批次、有的按工单）。
6. 工程师基于以上信息给根因假设，但步骤 2 的版本串错导致**根因分析建立在错误工艺基础上**，步骤 4 的时间记错导致**设备参数对不上**。
7. 给出错误根因 → 错误处置（如误调工艺 v5，而问题其实在 v3 的某参数）。

**痛点点**：

- 步骤 1–5 的"跨 5 界面手动串"慢且易错，工程师认知负荷大。
- 步骤 2 的"版本串错"是最隐蔽的错误——工艺界面默认显示当前版本，工程师容易用当前版本套历史过点，**根因分析建立在错误基础上**。
- 步骤 4 的"时间记错"导致设备参数对不上，分析失真。
- 步骤 5 的"统计口径不一致"导致同批次不良率不准。
- 后果是错误根因 → 错误处置，可能引入新问题。

### 5.2 L3 解决方案

L3 把"人肉串联"升级为"sub-agent 自动串接 + 版本一致性从领域模型兜"：

- **sub-agent 自动串接**：FirstArticleAgent / ProcessSwitchAgent / InspectionAgent / MaterialKittingAgent 各自调本上下文只读 toolset，supervisor 编排串接，工程师不再跨界面切换。
- **版本不靠人记**：ProcessSwitchAgent 的 ACL 强制 `route_version` 入参，从过点记录拿到的 `routeVersion` 就是当时生产用的版本（v3），**不会用当前 v5 套历史**。ACL 层二次校验返回状态为 `ACTIVE`（针对该版本的当时状态），避免基于失效工艺给处置。
- **设备参数按过点时间精确查**：设备数据 toolset 入参带 `time_range`，由过点记录的精确时间驱动，不靠人脑记时间。
- **统计口径统一**：同批次不良率由过点上下文的 `query_defect_rate` 工具统一口径，按批次查，不靠手工 Excel 统计。
- **复用 L1 诊断能力**：L3 在场景②⑤把 L1 诊断作为子步骤嵌入，L1 的 5M1E 假设排序 + 证据链 + 置信度兜底直接复用。

**对应实现**：[实现方案 §4.1](L3编排型Agent-实现方案.md) 工具对齐上下文边界；[§5.4](L3编排型Agent-实现方案.md) ACL 强制 `route_version` 校验（继承 L1 §4.3）。

**能力口径**：消除"跨 5 界面手动串"——sub-agent 自动串接；消除"版本串错"——`routeVersion` 从领域模型兜底，强制版本过滤；消除"时间记错 / 口径不一致"——工具入参由过点记录精确驱动，统计口径统一。

## 痛点 6：故障期间批次隔离盲、复产盲目

### 6.1 痛点存在时的详细操作步骤（人工）

以"贴片机 ASSET-01 故障停线"为例：

1. 设备停机报警，线长登入设备系统，看到 ASSET-01 报警码，电话叫维修工。
2. 维修工到场，登入维修系统，**手工开维修工单**，描述故障，开始维修。
3. 维修期间，**没人主动判断"ASSET-01 近期生产的批次要不要隔离"**——线长忙着催维修，工程师在别处。
4. 维修完成，维修工在维修系统登记完成，**没人通知计量员复校**（或电话通知了但没跟踪）。
5. 线长看 ASSET-01 修好了，**直接安排复产**，首件过点放行——但计量复校未做、复产首件未验证。
6. 复产后发现某工装因故障影响了精度（未复校发现），**复产后首批次不良**。
7. 事后排查：故障期间 ASSET-01 生产的某批次其实已受影响，但因步骤 3 未隔离，**该批次已流转到下道工序甚至入库**，需追溯召回。

**痛点点**：

- 步骤 3 的"没人主动判断隔离范围"——故障期间批次隔离盲，靠人记得就做、忘了就漏。
- 步骤 4 的"计量复校没人跟踪"——维修完成与复校脱节，复校靠电话通知易丢。
- 步骤 5 的"直接复产"——复产首件无人把关，未复校就放行。
- 步骤 7 的"受影响批次已流转"——隔离决策滞后，召回成本高。
- 整个流程"停线—维修—复校—复产"无编排，各步骤靠人衔接，易脱节。

### 6.2 L3 解决方案

L3 把"故障响应"编成"维修 ‖ 隔离排查并行 + 复产 gate 把关"的链：

- **维修单草拟 ‖ 故障影响批次排查并行**：维修工单 sub-agent 草拟维修单（gate 人确认下达）的同时，**另一个 sub-agent 并行排查 ASSET-01 近期生产的批次**是否需隔离——不等人记得，编排层主动派发。
- **隔离决策过 gate**：排查结果生成"批次隔离意图卡"，过 confirmation gate 人确认后，走返工/返修上下文的正常应用服务下达隔离（过聚合根不变式 + 发件箱），**不靠人记得就做**。
- **复校作为 gate**：维修完成后，计量复校是 supervisor 图里的显式 gate 节点，`interrupt` 等计量员确认复校结果，**不确认不进复产**。
- **复产首件 gate 把关**：复校 PASS + 点检 PASS barrier 后，才推复产首件放行卡，人确认后过点——**杜绝"修好直接复产"**。
- **故障隔离兜底**：维修期间若 sub-agent 连续失败，标 `SUSPENDED` 推线长升级，不自动复产。

**对应实现**：[实现方案 §1.4 场景③](L3编排型Agent-实现方案.md)；[§5.1](L3编排型Agent-实现方案.md) 并行 + barrier + gate。

**能力口径**：消除"故障期间隔离盲"——隔离排查与维修并行，主动派发不靠人记；消除"复校脱节"——复校是显式 gate；消除"复产盲目"——复校 + 点检 barrier 后才推复产放行卡。

## 痛点 7：工艺变更落地不全

### 7.1 痛点存在时的详细操作步骤（人工）

以"工艺路线 RR-B 从 v4 升级到 v5"为例：

1. 工艺工程师在工艺系统激活 RR-B v5，系统发 `ProcessRouteActivated` 事件。
2. **没人主动草拟新 SOP**：工艺变更后，SOP 文档仍指向 v4，操作工按旧 SOP 操作。
3. **没人核对操作工新工艺资质**：v5 引入新焊接参数，需操作工重新培训取证，但**培训系统与工艺变更无联动**，未培训操作工仍上线。
4. **没人触发新工艺首件验证**：v5 上线后，**直接按 v5 过点生产**，未做首件验证。
5. 某操作工按旧 SOP（v4 的参数）操作 v5 工艺，参数不匹配 → 批量不良。
6. 或：v5 工艺本身有缺陷（未通过首件验证暴露），直接批量生产 → 批量不良。
7. 事后查：工艺激活了，但 SOP / 培训 / 首件验证三件事都脱节，**变更落地不全**。

**痛点点**：

- 步骤 2–4 的"三件事脱节"——工艺变更后 SOP、培训、首件验证无编排，各做各的或都不做。
- 步骤 3 的"未培训操作工上线"是典型防错失效——工艺变更与人员资质无联动。
- 步骤 4 的"未首件验证直接生产"跳过了首件门禁。
- 后果是"版本切了防错没跟上"，批量不良。

### 7.2 L3 解决方案

L3 订阅 `ProcessRouteActivated` 事件触发编排，把"变更落地"串成带 gate 的链：

- **事件触发**：主动式 Agent 订阅 `ProcessRouteActivated`（复用已有领域事件流，不造新管道），事件触发 L3 编排。
- **新 SOP 草拟 ‖ 操作工资质核对并行**：SOP sub-agent 基于新工艺版本草拟新 SOP（gate 人确认发布），同时**资质 sub-agent 并行核对该工艺所需操作工资质**——不培训无资质的操作工不能上线。
- **barrier 等双就绪**：新 SOP 发布 PASS 且 操作工资质核对 PASS 后，barrier 才允许进首件验证。
- **新工艺首件验证 gate**：首件处理 sub-agent 触发新工艺首件，过点放行卡 gate 人确认，**未验证不放行批量生产**。
- **三处写各自 gate**：工艺激活确认、SOP 发布、首件验证放行，三个写动作各自过 confirmation gate，全留痕。

**对应实现**：[实现方案 §1.4 场景④](L3编排型Agent-实现方案.md)；事件触发复用领域事件流（[AGENT服务引入路线.md](../AGENT服务引入路线.md) §2.5）。

**能力口径**：消除"SOP/培训/首件脱节"——三件事编排成带 barrier 的链，缺一不可推进；消除"未培训操作工上线"——资质核对是显式 gate；消除"未首件验证直接生产"——首件验证 gate 把关。

## 痛点 8：客诉追溯慢，隔离决策滞后

### 8.1 痛点存在时的详细操作步骤（人工）

以"客户反馈某产品批次 P 焊接不良"为例：

1. 客户投诉到达，质量工程师登入过点系统，**手工逆向追溯**批次 P 的生产记录——按序列号一个个查过点记录，找到生产时间、工单、设备。
2. 切到 WIP 系统，查批次 P 的在制品位置——**部分已流转到下道工序、部分已入库、部分已发货**。
3. 切到物料系统，查批次 P 用的锡膏批次、供应商批次——**手工关联**，易漏。
4. **没人主动判断"同供应商批次的在库品要不要隔离/召回"**——工程师忙着追溯，隔离决策滞后。
5. 切到 8D 报告系统，**手工起草 8D 报告**——拉追溯链、历史同类 8D、根因分析，全靠手工填。
6. 隔离决策晚了一天做出，**同批次在库品已部分发货**，需召回。
7. 8D 报告手工起草慢，且追溯链手工拼接易错。

**痛点点**：

- 步骤 1–3 的"手工逆向追溯"慢且易漏，跨系统串联认知负荷大。
- 步骤 4 的"隔离决策滞后"——同批次在库品在追溯期间继续流转 / 发货，扩大召回范围。
- 步骤 5 的"手工起草 8D"慢，追溯链手工拼接易错。
- 后果是隔离决策慢导致召回范围扩大，8D 报告慢导致闭环晚。

### 8.2 L3 解决方案

L3 把"客诉处置"编成"自动追溯 + 隔离并行 + 8D 草拟"的链：

- **自动逆向追溯**：过点 / WIP sub-agent 自动逆向追溯批次 P 的生产记录、在制品位置、物料批次，**不靠手工一个个查**。
- **供应商批次追溯 ‖ 同批次在库品隔离判定并行**：物料 sub-agent 追溯供应商批次的同时，**另一个 sub-agent 并行判定同批次在库品的隔离范围**——不等人记得，编排层主动派发。
- **隔离决策过 gate**：隔离范围生成"隔离/召回意图卡"，过 confirmation gate 人确认后，走正常应用服务下达隔离——**隔离决策从"晚一天"变成"追溯同时并行判定"**。
- **8D 报告草拟复用 L2**：8D sub-agent 拉追溯链 + 历史同类 8D，草拟 8D 报告（gate 人确认发布），**不靠手工填**。
- **追溯复用 L1**：根因诊断嵌入 L1 的 5M1E 假设排序 + 证据链 + 置信度兜底。

**对应实现**：[实现方案 §1.4 场景⑤](L3编排型Agent-实现方案.md)；复用 L1 诊断作为子步骤（[L1诊断型Agent-实现方案.md](../L1诊断型Agent/L1诊断型Agent-实现方案.md)）。

**能力口径**：消除"手工逆向追溯慢"——sub-agent 自动串接；消除"隔离决策滞后"——隔离判定与追溯并行，决策从"晚一天"变成"同时并行"；消除"手工起草 8D 慢"——8D sub-agent 草拟 + gate 人确认。

## 痛点 9：长流程卡在某步无人推进

### 9.1 痛点存在时的详细操作步骤（人工）

以"换线卡在等工艺工程师确认工艺版本激活"为例：

1. 换线进行到步骤 2（工艺版本切换确认），线长在工艺系统提交激活申请。
2. 工艺工程师在另一产线忙，**没看到激活申请**（系统无主动推送，或推送了但工程师没刷界面）。
3. 换线**停在那等**，线长不知道下一步该谁动，**以为工程师在处理**。
4. 30 分钟过去，线长电话催工程师，工程师才发现申请，登入确认。
5. 但产线已停 30 分钟，产能损失。
6. 类似情况发生在返工审批、计量复校确认、首件放行审批——**每个 gate 都可能卡住**。
7. 线长无全局视图，不知道整个换线流程进行到哪一步、卡在谁那。

**痛点点**：

- 步骤 2 的"工程师没看到申请"——系统无主动推送，或推送了但责任人不刷界面。
- 步骤 3 的"停在那等"——长流程各 gate 靠人衔接，卡住无人催。
- 步骤 4 的"电话催"——被动催办，延迟大。
- 步骤 7 的"无全局视图"——线长不知道流程进行到哪、卡在谁那，无法主动推进。

### 9.2 L3 解决方案

L3 把"被动等"升级为"主动推 + 超时升级"：

- **主动推动作卡**：每个 gate `interrupt` 时，supervisor 经 WebSocket + Kafka **主动推动作卡给当前步骤的责任人**——不靠责任人刷界面，卡片推到他面前。
- **超时自动升级**：gate 等待有 deadline，超时自动 `SUSPENDED` 推线长升级——**不无限阻塞**，超时即升级到线长介入。
- **全局状态可视**：`changeover_session` 表记录 `current_step` 和各 gate 状态，线长 UI 可看全局进度——**知道进行到哪、卡在谁那**。
- **证据可回溯**：动作卡含 `evidence`（trace_id 列表），责任人点开可看 sub-agent 的推理与工具调用，**基于证据确认**，不是盲批。
- **故障隔离不阻塞**：sub-agent 连续失败 2 次标 `SUSPENDED` 推异常卡，不自动重试到死，**最坏情况退回人工编排**，不会越界写、不会错误放行。

**对应实现**：[实现方案 §5.3](L3编排型Agent-实现方案.md) 动作卡推送；[§8.3](L3编排型Agent-实现方案.md) gate deadline 兜底；[§5.2](L3编排型Agent-实现方案.md) `changeover_step_record` 状态可视。

**能力口径**：消除"卡住无人推进"——动作卡主动推责任人 + 超时升级线长；消除"无全局视图"——session 状态可视，知道进行到哪、卡在谁那；消除"盲批"——动作卡带 evidence，基于证据确认。

## 总结：L3 解决的核心痛点归纳

| 痛点类别 | 人工痛点 | L3 解法 | 设计支撑 |
|---------|---------|--------|---------|
| **慢** | 跨界面串行 + 人串界面 | 无依赖步骤真并行 + sub-agent 自动串接 | §5.1 并行 + barrier |
| **漏** | 人脑汇总判断、图快跳步 | 显式图 + barrier 硬校验双 PASS | §5.1 `_barrier_node` |
| **越界写** | 为快绕应用服务直写 | 写工具 gate + 走正常应用服务 | §4.3 `WriteToolGate` + §5.4 |
| **误触放行** | Agent 直接调放行 API | 放行能力架构层隔离 + 仅意图卡 | §5.5 + §7.5 启动断言 |
| **串错版本** | 当前版本套历史过点 | `routeVersion` 从领域模型兜底 | §5.4 ACL 强制版本校验 |
| **隔离盲** | 故障期间没人判断隔离 | 维修 ‖ 隔离排查并行 | §1.4 场景③ |
| **变更不全** | SOP/培训/首件脱节 | barrier 等三件事就绪 | §1.4 场景④ |
| **追溯慢** | 手工逆向 + 隔离滞后 | 自动追溯 + 隔离并行 | §1.4 场景⑤ |
| **卡住无人推** | 被动等 + 无全局视图 | 主动推卡 + 超时升级 + 状态可视 | §5.3 + §8.3 |

**一句话**：L3 解决的核心痛点是 **"跨上下文长流程靠人串——慢、漏、越界、不可审计"**：慢靠真并行、漏靠显式图 + barrier 防错、越界靠写工具白名单 + 放行能力隔离、不可审计靠 gate 决策落库。它不替代规则引擎做过点判定（那是 200ms 硬约束），只把"查完→诊断→草拟处置→推动作→人确认落库"这条人肉链升级成带闸门的自动链，而写的闸门始终在人手里。

## 面试防守 Q&A

**Q：这些痛点是不是为了讲技术造的？**
A：不是。换线慢、换线拿错钢网 / 调错程序版本、为快越界写、故障期间隔离盲、工艺变更落地不全——这些都是 MES 现场真实高频痛点，任何一个在车间待过的人都见过。我讲 L3 的切入点就是"这些痛靠人串流程解决不了，靠单 agent 也只能解决'查'这一段，必须 multi-agent 把'查→诊→草拟→推→人确认落库'串成带闸门的链"。痛点是真的，解法是设计阶段的规划——我不编业务效果数字（如"良率提升 30%"），只讲能力：消除某类等待、消除某类漏步骤、写动作可审计。

**Q：L3 真能消除漏步骤吗？人确认时还是会糊弄啊。**
A：barrier 把"齐套 PASS 且 钢网 / 程序核对 PASS"从人脑判断变成图结构硬约束——漏了图走不到放行节点，这是架构层兜底，不是提醒。gate 必须人确认留痕（谁/何时/基于哪张卡），确认即担责，糊弄的成本留在审计记录里——这比"扫一眼编号 / 凭记忆调程序"无留痕强得多。当然，人确认时仍可能主观放行，但那是人的决策责任，Agent 不会替人放行，也不会让人无记录地放行。

**Q：痛点 4 的"通用 Agent 误触放行"是不是稻草人？真有人这么干？**
A：不是稻草人。通用 Agent 接 MES 写 API 是当下很多"AI 赋能 MES"方案的默认做法，风险就在这——模型幻觉 + 无权限隔离 = 灾难。我之所以在 L3 设计里把"放行能力架构层隔离"作为硬约束（supervisor 不持工具、放行能力只挂 PassReleaseAgent 且仅意图卡、启动断言禁 `pass_judge`/`force_release`），正是为了避免这种通用 Agent 的越界。这条讲清楚，体现的是懂 MES 写红线的严肃性——不是选什么模型的问题，是行动边界对齐领域边界的问题。

**Q：这些场景你都上线了吗？**
A：没有。这是设计阶段的引入规划（[AGENT服务引入路线.md](../AGENT服务引入路线.md) §7 红线），重点是自主度光谱与领域耦合点的判断。落地需要先等 RAG 追溯能力成型，再做 L1 诊断 + L2 草稿验证可用性，L3 是在 L1/L2 护城河上往前走一步的试点形态。我讲痛点和解法，讲的是"如果这么设计能解决什么"，不是"已经跑出多少收益"——诚实 + 体现架构判断力，比硬吹"已上线 AI Agent"得分高。
