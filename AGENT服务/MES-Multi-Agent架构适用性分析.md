## 1. 判断框架：什么时候单 Agent 撑不住

先给判据，再看模块。**满足 2 条及以上判据，才值得上 Multi-Agent。**

### 1.1 该拆的七条判据

| 判据 | 含义 | 单 Agent 的失效模式 | MES 典型信号 |
|------|------|-------------------|-------------|
| **C1 知识域异构** | 任务需要横跨多个语义差异极大的知识域 / 数据源 | 工具集膨胀到 30+，工具选择准确率断崖下降；system prompt 塞不下多套领域术语，出现术语串台 | 任务涉及 ≥3 个限界上下文 |
| **C2 对抗校验** | 结论必须经得起反驳（质量、合规、安全） | 单 Agent 一旦形成假设，后续检索只找支持性证据（确认偏误），自我复核基本失效——自我 critique 与生成同源，推翻率低 | 错判代价 = 批量报废 / 停线 / 客户投诉 |
| **C3 并行扇出** | 存在多个相互独立的子问题需分别取证后聚合 | 串行执行 N 次检索，延迟线性叠加；且前序结果挤占 context，后序取证质量下降 | 5M1E、横向展开、影响面分派 |
| **C4 长程 / 大上下文** | 任务跨小时到数周，或产物是长文档 | 单会话 context 膨胀直至溢出，早期关键信息被稀释；一次失败全链重跑 | 换线、8D、ECN 落地 |
| **C5 权限与安全等级隔离** | 子任务间所需权限不同（只读 vs 受限写） | 单 Agent 挂载了写工具，任何一步被 prompt 注入都可直接落库——**攻击面 = 全工具集** | L2 草稿 + L3 审批混在同一会话 |
| **C6 异构求解器** | 子问题需要 LLM 之外的求解器（约束优化、时序分析、图算法） | LLM 硬算排产 / 硬算 FFT，结果不可用；或反过来把确定性算法包成 LLM 推理，成本与精度双输 | 排产、设备信号诊断、追溯图遍历 |
| **C7 多角色人在回路** | 不同步骤由不同岗位审批，且审批之间有先后/并行关系 | 单 Agent 会话只能对接一个审批人，无法表达"工艺签完质量签、质量签完计划签"的责任链 | 换线、ECN、8D、返工 |

### 1.2 不该拆的四条反判据

| 反判据 | 说明 | 正确做法 |
|--------|------|---------|
| **R1 硬实时** | 有毫秒级 SLA 的链路 | 规则引擎 / 确定性代码。Agent 只能在**判定之后**异步推卡片 |
| **R2 确定性事务写** | 写路径要过聚合根不变式 + 事务发件箱 | 应用服务；Agent 最多产 draft（L2） |
| **R3 单域问答** | 一个知识域内检索 + 回答 | 单 Agent + RAG（你已有的路线 A/B） |
| **R4 流程固定无分支** | 步骤、条件、责任人都确定 | BPMN / 状态机 / 定时任务，编排是过度设计 |

> **一句话决策卡**：先做单 Agent + 工具集；只有当它出现"工具选不对 / 结论没人反驳 / 延迟线性叠加 / context 溢出 / 权限没法隔离 / 该算的算不动 / 审批链挂不上"这七种症状之一时，才按对应判据拆。

### 1.3 Multi-Agent 的四种协作拓扑（MES 适用）

| 拓扑 | 结构 | 适用 | MES 例子 |
|------|------|------|---------|
| **Supervisor + Fan-out/Fan-in** | 编排者分派 → 子 Agent 并行 → 汇聚裁决 | C1 + C3 | A1 根因分析、A7 影响面 |
| **Pipeline + Critic** | 生成 → 独立审核 → 修订循环 | C2 | A10 SOP、A5 返修判定 |
| **State-machine Orchestrator + 无状态子 Agent** | 编排者只持状态机，每步新建短命子 Agent | C4 + C7 | A3 换线、A8 8D |
| **Blackboard（黑板）** | 多 Agent 读写共享证据板，异步贡献 | C4 + 长程异步 | A2 ECN、A8 8D 措施跟踪 |

**MES 的关键取舍**：子 Agent 之间传递**结构化证据包（artifact）**，不传递对话历史。理由是可审计——质量场景要能回答"这条结论的依据是哪条过点记录 / 哪个批次号"，对话历史无法作为审计证据。

## 2. 建议采用 Multi-Agent 的模块详解

---

### A1 质量根因分析（5M1E 诊断）—— 最典型的 Multi-Agent 场景

**业务场景**：某批次焊接/涂胶不良率突增，工艺或质量工程师需要定位根因并给出处置建议。现状是人工跨 5~6 个界面串联取证，耗时数小时到数天。

**为什么单 Agent 不够**

| 判据 | 具体失效 |
|------|---------|
| C1 | 需要同时操作物料批次、设备参数时序、工艺版本、过点记录、检验/测试数据五类语义完全不同的数据源，术语与过滤规则各不相同（如工艺必须带 `routeVersion` 过滤，否则会基于已失效工艺给根因） |
| C2 | 单 Agent 先入为主：一旦怀疑"锡膏过期"，后续检索只强化该假设。**这是 RCA 最致命的失效模式**，而 MES 的错判代价是批量报废 |
| C3 | 六条线串行取证 = 六倍延迟；且"人/机/料/法/环/测"取证之间无依赖，天然可并行 |
| C4 | 取证结果（时序曲线、检验分布、批次清单）体积大，全塞进一个 context 会淹没关键异常点 |

**Agent 拆分**

| 角色 | 职责 | 绑定的上下文工具集 | 并行 | 自主度 |
|------|------|-----------------|------|--------|
| Planner（假设编排） | 解析不良现象，生成 5M1E 假设清单，分派取证任务，控制终止条件 | 只读：过点记录摘要 | — | L1 |
| 取证 Agent ×6 | 每条线独立取证，输出**结构化证据包**（含证据强度、反证据） | 料→物料上下文；机→设备数据接入/点检保养/计量检定；法→工艺管理；人→人员资质+过点 operator；环→环境采集（若有）；测→测试数据接入 | ✅ 并行 | L1 |
| Critic（红队） | 专责**寻找反例推翻**各假设，只输出反证据 | 同上的只读集 | ✅ 并行 | L1 |
| Judge（裁决） | 综合正反证据排序，输出置信度 + 证据链；低置信度转人工 | — | — | L1 |
| Reporter | 生成 D4 段落 / 处置建议 | — | — | L2 草稿 |

**拓扑**：Supervisor + Fan-out（取证 + 红队）→ Fan-in（裁决）。

**红线**：全程只读，绝不进过点主事务；若需出返工/隔离草稿，交由独立的 L2 草稿 Agent，落库走返工上下文的正常应用服务。

**何时可退回单 Agent**：仅限"单一症状 + 明确单一可疑因子"的窄场景（如"某台设备报警后当批不良"），此时单 Agent + 3 个工具足够。

### A2 工程变更（ECN/ECO）影响评估与落地

**业务场景**：设计或工艺变更下发，需评估影响面并处置在制/库存/已交付产品。航空制造场景下还涉及客户批准与适航合规（波音/C919 类项目的变更通报要求）。

**为什么单 Agent 不够**

- **C1**：影响面横跨 BOM（物料）、工艺路线版本（工艺管理）、在制品（在制品执行）、库存/在途、已交付与客户现场，五个域查询语义各异。
- **C4 + C7**：处置落地周期常以天计，且需工艺、质量、计划、销售/客户多方依次或并行签核——**这是典型的多角色责任链，单会话无法表达**。
- **C2**：处置策略（用完 / 立即切换 / 隔离待判 / 返工）一旦选错，代价是停线或批量返工，需要独立审核。

**Agent 拆分**

| 角色 | 职责 |
|------|------|
| 变更解析 Agent | 识别变更类型（物料替换 / 参数变更 / 工序增删 / 工装变更）与生效策略 |
| 影响面 Agent | 调 where-used 图服务 + 在制品投影 + 库存 + 已交付，产出受影响清单（**图遍历本身是确定性服务，不是 LLM**） |
| 在制处置 Agent | 对每个受影响批次给策略，受工艺可行性 + 质量风险 + 交期三约束 |
| 库存/在途处置 Agent | 隔离 / 退料 / 替代料可用性与认证状态 |
| 文件同步 Agent | 草拟 SOP、检验标准、工艺路线更新（复用 A10） |
| 合规 Agent | 判定是否需客户通知 / PPAP / 适航文件更新（C2 独立审核位） |
| 汇总 Agent | 出影响评估报告，按角色路由审批 |

**拓扑**：Blackboard（异步长程，各方逐步贡献）+ 路由审批。

### A3 换线（Changeover）编排

**业务场景**：产线切换产品/工艺版本，涉及首件触发、工艺版本核对、点检/计量状态、工装准备、物料齐套、人员资质、首件放行门禁。

**为什么单 Agent 不够**

- **C4 长程状态隔离（核心理由）**：换线是小时级流程，中间大量等待人工操作。单 Agent 长会话会把"已完成步骤的中间产物"和"当前步骤的上下文"混在一起，且一次中断需全链重放。
  → **正确结构：编排 Agent 只持有状态机，每一步新建无状态子 Agent**。这是 Multi-Agent 在长程任务上最本质的收益——**把长程状态与短程执行解耦**。
- **C7**：各步骤责任人不同（操作工、工艺工程师、质量工程师、设备工程师）。
- **C1**：跨首件处理、工艺管理、点检保养、计量检定、物料、在制品执行六个上下文。
- **C3**：点检准备与物料齐套可并行。

**红线（对齐你的硬约束）**：编排 Agent 只编排**人侧动作**，推动作卡片，**绝不直接调过点引擎的放行/拦截 API**；过点 P99 ≤ 200ms 的判定仍走规则引擎。

### A4 设备故障诊断与维修决策闭环

**为什么单 Agent 不够 —— 核心是 C6 异构求解器**

- 故障波形/频谱分析、时序异常检测是**算法活**，LLM 硬算必然不可用；而手册检索、历史工单类比、维修策略权衡是**语义活**，纯算法做不了。
- 这两类能力放在一个 Agent 里，要么被 LLM 包办（算不准），要么被算法包办（读不懂手册）。**必须拆，且子 Agent 的实现技术栈都不同**——这是 Multi-Agent 而非 Multi-Prompt 的硬理由。

| 角色 | 技术栈 |
|------|--------|
| 信号诊断 Agent | 时序/频谱算法 + LLM 解读 |
| 知识检索 Agent | GraphRAG（设备手册、FMEA、历史维修工单） |
| 备件/资源 Agent | 库存与采购周期查询 |
| 排程影响 Agent | 停机时长 → 调 A6 排产 Agent |
| 维修策略 Agent | 修/换/外协的成本-停机时间权衡 |
| 工单草拟 Agent | L2 草稿，落库走维修上下文应用服务 |

---

### A5 返工 / 返修决策与工单草拟

- **C1**：可返修性判定（质量上下文）→ 再入点计算（工艺管理，需 `routeVersion`）→ 返工用料（物料）→ 排程影响（排产）→ 成本交期。
- **C2 多目标裁决**：成本 vs 交期 vs 质量风险三者冲突，需要"各自取证 + 统一裁决"的结构；且不返修/报废的建议必须经独立审核（报废决策影响交付）。
- **L2 红线**：输出 intent + draft，**由人在返工/返修上下文正式界面确认后下达**，过聚合根不变式 + 事务发件箱，绝不旁路写。

### A6 排产与动态重排（APS）—— 最典型的 C6 场景

**为什么必须 Multi-Agent（这是本文最强的一条）**

排产是**约束优化问题**，不是语言问题。用 LLM 直接排产是方向性错误；但纯求解器又缺少"理解计划员真实意图、解释结果、协商修订"的能力。因此必须混合编排：

| 角色 | 职责 | 是否 LLM |
|------|------|---------|
| 约束澄清 Agent | 与计划员对话澄清目标优先级（交期优先 / 换线最少 / 设备利用率 / 插单策略） | ✅ |
| 数据准备 Agent | 汇总工单、齐套状态、设备/工装可用性、人员班次、工艺产能，产出求解输入 | 部分 |
| **求解器 Agent（可多策略并行）** | CP-SAT / 遗传算法 / 启发式规则，产出候选方案 | ❌ **非 LLM** |
| 结果解释 Agent | 解释"为什么这么排"、瓶颈在哪、关键约束是哪条 | ✅ |
| 冲突消解 Agent | 计划员说"这条不行" → 回写约束 → 触发重解 | ✅ |
| 快照回写 Agent | 确认后落槽，走排产上下文应用服务（确认即 `schedule.confirmed`） | 受限写 |

**关键点**：多个求解策略 Agent 并行跑、结果对比选型，本身就是 C3 并行扇出；人机多轮协商是 C7。**这一条判据足以让排产必须上 Multi-Agent。**

---

### A7 影响面追溯与隔离 / 召回处置（诚实分层）

**必须先说清楚：追溯查询本身不需要 Multi-Agent，甚至不需要 Agent。**

- 单件/批次谱系（where-used / where-from）是**图遍历 + GraphRAG**，确定性服务即可，用 Agent 包一层是纯开销。
- **需要 Multi-Agent 的是"查完之后怎么办"**：

| 角色 | 职责 |
|------|------|
| 影响分级 Agent | 在制 / 库存 / 在途 / 已交付 / 客户现场，分级定隔离范围 |
| 处置策略 Agent | 隔离、复检、返工、报废的组合策略（可复用 A5） |
| 合规与客户 Agent | 航空场景：适航要求、FRACAS、客户通报时限与口径 |
| 沟通草稿 Agent | 内部通报 / 客户通报草稿（必须人审核后发出） |

**这个分层本身就是架构判断力的体现**：把"确定性查询"和"不确定性决策"切开，只对后者用 Agent。

---

### A8 8D / CAPA 质量闭环

- **C4 超长程**：8D 周期数周，跨多次会议与多部门。
- **C7**：D1–D8 各步骤责任部门不同（质量主导，工艺/设备/生产/采购配合）。
- **C3 横向展开**：D7 预防需 fan-out 搜索"同类产品 / 同类工艺 / 同类设备 / 同类供应商"的相似历史问题——这是天然的并行扇出。
- **可复用**：D4 直接调用 A1 根因 Agent；D3 遏制直接调用 A7 隔离 Agent。**复用子 Agent 是 Multi-Agent 相比单 Agent 的另一项收益——能力可组合。**
- **拓扑**：State-machine Orchestrator + Blackboard（措施跟踪跨周）。

---

### A9 主动巡检与告警收敛

- **C1 指标异构**：齐套率、SPC 不良率、设备点检/计量临期、过点堆积、测试数据漂移、工艺参数漂移——各自数据源、判定逻辑、阈值、责任人完全不同。塞进一个 Agent 等于维护一个巨型 prompt。
- **单一职责**：告警风暴必须有一个**独立的收敛层**（去重、定级、关联到同一根因、路由），这是与"检测"完全不同的关注点，天然该独立成 Agent。
- **工程收益**：各监视 Agent 独立部署、独立扩缩容、独立调阈值，互不干扰。

| 层 | 角色 |
|----|------|
| 检测层 | 6+ 个独立监视 Agent，订阅已有领域事件（复用 §4.3 的事件流，不造新管道） |
| 收敛层 | 告警收敛 Agent：去重 / 定级 / 根因关联 |
| 路由层 | 按类型推给线长 / 工艺 / 质量 / 设备 |
| 处置层 | 复用 A1 诊断 Agent 给建议（L1），需要动作则转 L2 草稿 |

---

### A10 SOP / 工艺文件生成与合规审核

- **C2 生成/审核对抗（核心）**：LLM 自我审核推翻率极低，必须由**独立审核 Agent** 校对新 SOP 与工艺路线参数规格、质量门禁规则是否矛盾。MES 场景下 SOP 写错 = 现场按错误参数作业。
- **C4 长文档分章**：按工序分章节并行撰写再合并，避免长文档生成时的质量衰减。
- **审核位具体化**：一致性审核（参数/规格矛盾）、可操作性审核（术语、步骤粒度、工位信息）、版本 diff（新旧差异，用于培训与变更说明）。

---

### A11 缺料 / 齐套风险协同（次级，可并入 A6）

- 齐套监控 → 替代料判定（AVL / 认证状态；航空场景替代料常需工程批准）→ 供应商交期协同（跨企业边界）→ 排产影响（复用 A6）。
- **建议**：不作为独立 Multi-Agent 系统，作为 A6 的输入子 Agent + 独立监控 Agent 即可，避免过度拆分。

## 3. 通用不变式：MES Multi-Agent 的硬约束

这些是你已有 Agent 路线 §4 约束在 Multi-Agent 形态下的延伸：

| 不变式 | 说明 |
|--------|------|
| **工具注册对齐限界上下文** | 每个子 Agent 只挂载所用上下文的 toolset，**上下文边界 = 工具注册边界**，避免工具集膨胀与术语串台。**注意这不等于任务分解边界**——任务分解要按"要回答的问题的结构"划分，一个子 Agent 可跨多个上下文取工具（详见 [车间MES场景详解](./车间MES的Multi-Agent真实业务场景详解.md) 场景二） |
| **权限在 Agent 级物理隔离（C5）** | 只读 Agent 不挂载任何写工具；写意图只在标记 `requires_confirmation` 的 L2/L3 Agent 中暴露。攻击面从"全工具集"缩小到"单个子 Agent" |
| **不进过点主事务** | 任何 Agent 不得调过点引擎放行/拦截 API；编排只推人侧动作卡 |
| **写不旁路应用服务** | 草稿落库走正常应用服务，过聚合根不变式 + 事务发件箱 |
| **子 Agent 间传 artifact 不传对话** | 证据包必须结构化、可引用（批次号、过点记录 ID、`routeVersion`），满足质量审计要求 |
| **版本一致性** | 诊断 Agent 拉工艺必须带 `routeVersion` 过滤（领域总览 §5.1），否则基于失效工艺给根因 |
| **低置信度转人工 / 转规则引擎** | 与 MES 防错理念一致——宁可拦下让人判 |
| **全链路 trace** | 每个子 Agent 的工具调用链、置信度、耗时可观测，否则 Multi-Agent 无法调试 |

## 4. 诚实的代价：Multi-Agent 不是免费的

| 代价 | 说明 | 缓解 |
|------|------|------|
| Token 成本 N 倍 | 6 个取证 Agent 各带一份上下文 | 子 Agent 只传 artifact；用轻量模型跑取证，强模型只跑裁决 |
| 延迟 | 并行可压扇出延迟，但编排层串行步骤仍在 | 只对该并行的并行；编排层异步 |
| 调试困难 | 错误在 Agent 间传播放大 | 全链路 trace + 单 Agent 可独立回放 |
| 一致性 | 各子 Agent 结论可能冲突 | 显式 Judge/Critic 位，不靠隐式共识 |
| 过度设计风险 | 本可单 Agent 解决的被拆开 | 严守 §1.2 反判据 R1–R4 |

## 5. 落地优先级建议

1. **第一批（价值最高、风险最低）**：A1 根因分析 —— 复用追溯护城河，全程只读，是唯一"无写风险却有高价值"的 Multi-Agent 场景。
2. **第二批**：A9 主动巡检（复用已有领域事件）+ A10 SOP 生成审核（生成-审核对抗最易验证）。
3. **第三批**：A4 设备诊断、A5 返工决策 —— 引入 L2 草稿，先跑通 confirmation gate。
4. **第四批（试点）**：A3 换线编排（L3，跨上下文，挑一条产线试点）、A6 排产（先做求解器 + 解释 Agent 的最小闭环）。
5. **远期**：A2 ECN、A8 8D —— 长程多部门，依赖前面积累的可观测数据与组织配合。

## 6. 评审防守 Q&A

**Q：Multi-Agent 和你已有的 L1/L2/L3 自主度分级是什么关系？**
A：正交的两级判断。L1/L2/L3 决定"Agent 能写到哪一级"，Multi-Agent 决定"要不要把一个任务拆给多个 Agent"。一个 L1 只读诊断系统完全可以是 Multi-Agent 的（如 A1 根因分析：多个取证 Agent + 红队 Agent + 裁决 Agent，全部只读）；反过来一个单 Agent 也可以是 L2 草稿型。先定自主度红线，再定拆分粒度。

**Q：为什么质量根因分析一定要拆，不能一个 Agent 挂全部工具？**
A：三个失效：一是工具集到 30+ 后选择准确率断崖下降；二是确认偏误——单 Agent 形成假设后只找支持性证据，自我 critique 与生成同源，基本推翻不了自己，而 MES 错判代价是批量报废；三是六条取证线的原始证据（时序曲线、检验分布、批次清单）全进一个 context 会淹没关键异常点。所以需要"并行取证 + 独立红队 + 统一裁决"的结构。

**Q：排产为什么必须有非 LLM 的求解器 Agent？**
A：排产是约束优化，不是语言任务。LLM 直接排产结果不可用（硬约束都未必满足）。结构是：LLM Agent 负责澄清目标优先级与解释结果，CP-SAT/遗传算法 Agent 负责实际求解，再由一个 Agent 做冲突消解与计划员协商。多个求解策略并行对比选型，也是并行扇出的收益。

**Q：追溯查询是不是也要做成 Multi-Agent？**
A：**不。** 谱系 where-used/where-from 是图遍历，确定性服务 + GraphRAG 就够了，包一层 Agent 是纯开销。需要 Multi-Agent 的是查完之后的"处置决策"——影响分级、隔离策略、合规与客户通报、沟通草稿，这些才涉及不确定性权衡和多角色审批。把确定性查询和不确定性决策切开，只对后者用 Agent，这个分层本身就是判断力。

**Q：Multi-Agent 会不会更容易越权写库？**
A：恰恰相反，正确拆分会**缩小**攻击面。单 Agent 挂全部工具时，任何一步被注入就能碰写工具；拆开后只有标记 `requires_confirmation` 的 L2/L3 Agent 暴露写工具，且写仍走正常应用服务过聚合根不变式。权限在 Agent 级物理隔离，比在单 Agent 里靠 prompt 约束可靠得多。

**Q：会不会过度设计？你怎么判断该拆不该拆？**
A：有反判据卡着。R1 硬实时（过点 200ms）不上 Agent；R2 确定性事务写走应用服务；R3 单域问答单 Agent + RAG 就够；R4 流程固定无分支用状态机/BPMN。只有出现七种症状之一（工具选不对 / 结论没人反驳 / 延迟线性叠加 / context 溢出 / 权限没法隔离 / 该算的算不动 / 审批链挂不上）才拆。先单 Agent + 工具，症状驱动拆分，不是一开始就用 Multi-Agent 炫技。

---

## 7. 一句话定位

"判断 MES 该不该上 Multi-Agent，看的不是功能重不重要，而是**单 Agent 会不会被撑爆**——工具集撑爆（C1）、结论没人反驳（C2）、延迟线性叠加（C3）、context 溢出（C4）、权限没法隔离（C5）、该算的算不动（C6）、审批链挂不上（C7）。满足两条才拆，且拆分边界对齐 14 个限界上下文，写动作仍全部过 confirmation gate。**根因分析和排产是必拆的，过点判定和工单写入是永不许碰的。**"
