# MES 场景 Multi-Agent 架构适用性分析

> **口径说明**：本文的判据体系与模块结论已按 [Multi-Agent必要性-独立复核与批判.md](./Multi-Agent必要性-独立复核与批判.md)（下称《复核》）的实证复核结果重写——判据从七条收敛为三条硬判据（C1' / C3' / C8），模块裁定与《复核》§3 一致。**Multi-Agent 的结论以《复核》为唯一权威源，本文是它在 MES 语境下的展开，不与之冲突。**

> **本文要回答的问题**：不是"MES 哪些功能适合上 Agent"（那是 [AGENT服务引入路线.md](./AGENT服务引入路线.md) 的能力矩阵（诊断 / 草稿编写 / 流程编排）），而是**"哪些功能用单 Agent + 工具集撑不住，必须拆成多 Agent 协作"**。
>
> 二者是正交的两级判断：
> - **第一级（要不要 Agent）**：由自主度光谱决定 —— 判据是"是否需要多步规划 / 主动触发 / 写意图"。
> - **第二级（要不要 Multi）**：由本文 §1.1 的三条硬判据决定 —— 判据是"是否存在**工具/知识域冲突且路由不经济**、**真独立且延迟敏感的子任务**、**信息或能力的不对称**"。
>
> **长程状态、多角色审批链、异构求解器、"想要一个独立审核角色"都不构成拆分理由**——它们分别由外部化状态、工作流引擎、工具化服务、外部证据工具来解决（《复核》P0-1 / P0-2 / P0-3 / P0-4）。
>
> 很多团队的误区是跳到第二级直接上 Multi-Agent，把本可以一个 Agent + 20 个工具解决的问题拆成 6 个 Agent，换来**约一个数量级**的 token 成本和调试地狱。**本文同时给出"该拆"和"不该拆"两侧清单。**
>
> **口径纪律**：沿用 [AGENT服务引入路线.md](./AGENT服务引入路线.md) §7 —— 这是**设计阶段的架构判断**，不是已上线能力的说明。领域上下文引用以 [领域总览.md](../领域模型/领域总览.md) §2 的 14 个限界上下文为准。文中引用的外部研究沿用《复核》的分级标注（【A】同行评议 /【B】厂商技术报告 /【C】二手聚合 /【推】推断 /【设】假设）。

## 1. 判断框架：什么时候单 Agent 撑不住

先看判据。**修订后只剩三条硬判据，"三条至少满足一条"且"成本闸门通过"才拆**（《复核》§2.7）。只满足"感觉该拆"或"角色名字不同"→ 不拆。

### 1.1 该拆的三条硬判据

| # | 判据 | 检验问题 | 单 Agent 的失效模式 | MES 典型信号 |
|---|------|---------|-------------------|-------------|
| **C1' 工具/知识域冲突且路由不经济** | 任务横跨语义差异极大的多个知识域 / 数据源，且**分层路由也救不回来** | 工具数 >20 且语义跨多个域，先用轻量路由选出 5–10 个相关工具再交给执行方，仍然选不准？（要有量化证据） | 工具选择准确率随数量下降（20 个以上明显下滑【C，二手聚合，仅作量级参考】），失败主要不是"选错工具"而是"选对工具、填错参数"；system prompt 塞不下多套领域术语，出现术语串台 | 任务涉及 ≥3 个限界上下文，且各域术语与过滤规则互不相容 |
| **C3' 存在真独立子任务且延迟敏感** | 多个子任务**结果互不影响、无共享假设**，且延迟真的是瓶颈 | 拿掉一个子任务的输出，另一个的结果会变吗？会变 → 不是真独立。这任务本来就要人等几十分钟吗？要 → 省下的并行时间没有价值 | 串行执行 N 次检索，延迟线性叠加；前序原始结果挤占 context，后序取证质量下降 | **五级影响面清点**（在制工单 / 库存 / 在途 / 已交付 / 客户现场）——真独立；narrowing 之后**已分叉且真正独立**的 RCA 假设取证 |
| **C8 存在信息 / 能力不对称** | 某个角色能拿到另一方**可证实地拿不到**的外部证据或工具（最重要，也最常被忽略） | 审核方 / 反对方调用的数据源或方法，生成方能不能调到？调不到 → 拆；调得到同一份东西 → 不拆 | 单 Agent 自验自收：对自己产出的复核基本无效——**无外部反馈时自我纠正反而降低准确率**【A，Huang et al. ICLR 2024】；CRITIC 消融显示移除工具验证、只留自我评估后大部分提升消失【A】 | SOP 审核方查**工艺路线参数规格 / 质量门禁规则库**；红队查**客户规范条款库、适航要求、服役数据** |

**三条的共性**：收益来自**不同的上下文、不同的工具、不同的证据**，不是来自"多几个角色"。如果两个 Agent 看到的是同一份东西，它们其实是一个 Agent，只是花了两倍的钱。

### 1.2 原七条判据的去向（为什么只剩三条）

原版的 C2/C4/C5/C6/C7 不是"弱化"，而是**归错了层**——它们各自指向一个更便宜、更正确的解法（依据《复核》§1.1 与 §1.4 判据修订对照表）：

| 原判据 | 复核裁定 | 它真正指向的解法 |
|--------|---------|----------------|
| C2 对抗校验（"自我审核推翻率极低，必须由独立审核 Agent"） | ❌ 因果倒置（P0-1） | **被 C8 取代**：审核的价值来自引入生成方不具备的**外部信息 / 工具**，与"是不是另一个 Agent"无关。没有新信息 → 不拆，改为单 Agent + 外部工具验证 |
| C4 长程 / 大上下文 | ❌ 因果错误（P0-4） | 归入**外部化状态**：状态持久化（`AgentState` + `SessionService`，Redis-backed）+ 上下文压缩 + 每步重建上下文，单 Agent 完全能达到同样效果；Multi-Agent 只是可选实现之一，不是必要条件 |
| C5 权限与安全等级隔离 | ❌ 方向说反（P0-5） | 归入**工具执行层安全**：真正的边界在工具网关（服务端鉴权、参数校验、白名单、幂等键）与 Permission 闸门，不在"把工具挂给哪个 Agent"。同一进程内的"Agent 级物理隔离"只是 prompt 层的工具可见性；Agent 间通信通道要记为**新增攻击面（成本项）** |
| C6 异构求解器 | ❌ 概念混淆（P0-2） | 归入**求解服务**：CP-SAT / 遗传算法 / 时序算法是确定性服务，不是 LLM 驱动的决策实体。C6 证明的是"需要工具化与编排"，不是"需要多个 LLM Agent" |
| C7 多角色审批链 | ❌ 归错层（P0-3） | 归入**工作流引擎**：多审批人 + 先后/并行责任链是 BPMN / 审批流 / 状态机的原生职责。用 Multi-Agent 承载审批链，会得到比 BPMN 更难调试、更难审计、更难改的劣化实现 |
| C1 知识域异构 | ⚠️ 方向对、表述夸大（P1-1） | 降级为 **C1'**：先做工具分层路由 + 参数程序化校验；只有路由不经济时才按域拆 |
| C3 并行扇出 | ⚠️ 过度简化（P1-2） | 收紧为 **C3'**：真独立才并行；并行只压延迟、不降成本（总 token 反而上升） |

### 1.3 不该拆的四条反判据

| 反判据 | 说明 | 正确做法 |
|--------|------|---------|
| **R1 硬实时** | 有毫秒级 SLA 的链路 | 规则引擎 / 确定性代码。Agent 只能在**判定之后**异步推卡片 |
| **R2 确定性事务写** | 写路径要过聚合根不变式 + 事务发件箱 | 应用服务；Agent 最多产 draft（草稿能力） |
| **R3 单域问答** | 一个知识域内检索 + 回答 | 单 Agent + RAG（你已有的文档检索 / 制造追溯两项能力） |
| **R4 流程固定无分支** | 步骤、条件、责任人都确定 | BPMN / 状态机 / 定时任务，编排是过度设计 |

> **一句话决策卡**：先做单 Agent + 工具集，并把更便宜的十项手段做完（工具分层路由、参数程序化校验、即时检索、压缩与结构化笔记、外部化状态、sub-agent 上下文隔离、外部证据驱动的生成-验证、独立采样聚合、prompt caching、小模型分流——见《复核》§4.2）；**只有出现 C1' / C3' / C8 之一、且成本闸门通过时才拆**。是**症状驱动**拆分，不是"角色驱动"拆分。

### 1.4 四种协作拓扑（限定适用面后保留）

| 拓扑 | 结构 | 限定后的适用面 | MES 例子 |
|------|------|--------------|---------|
| **Supervisor + Fan-out/Fan-in** | 编排者分派 → 子 Agent 并行 → 汇聚裁决 | **只在 C3' 成立**：子任务真独立 + 全程只读 + 各路就地压缩。要计入 P2-4"转述损失"（子结论经编排者转述存在信息衰减） | 五级影响面清点；narrowing 限定 2–4 条假设后的 RCA 并行取证 |
| **顺序流转 + Critic**（生成-验证；纯拓扑形态名，不指任何框架 API） | 顺序流转 → 独立审核 → 修订循环 | **只在 C8 成立**：审核方必须带生成方拿不到的外部证据（规格库、规则库、实测数据）。否则退化为"换个 prompt 重读草稿"，无效甚至更差【A】 | SOP 顺序生成 + 带工艺规格 / 质量门禁规则的审核 |
| **状态机 Orchestrator + 无状态子 Agent** | 编排者只持状态机，每步新建短命子 Agent | **主体是工作流引擎，不是 Multi-Agent**：步骤 / 等待 / 升级 / 审批归工作流 + 外部化状态；每步挂一个**独立的单 Agent 建议器**或只读取证器。"任务长"本身不构成拆分理由（P0-4） | 换线编排（工作流引擎 + 每步单 Agent 建议器）、8D 闭环 |
| **Blackboard（黑板）** | 多 Agent 读写共享证据板，异步贡献 | **适用面最窄**：共享写板同时踩两个坑——Agent 间通信通道是新增攻击面（P0-5），共享状态属强耦合（各自局部合理、合起来全局不自洽）；且**框架 2.0 不提供共享消息上下文原语**，要"黑板"就得自建中转（成本项，见下文底座口径）。MES 里应退化为**只读证据集存储 + 单线程汇总**，而不是让多 Agent 各写各的 | 跨周的 8D 措施跟踪（证据只读、写入单线程） |

**拓扑的承载方式（底座口径）**：以 [架构设计v2/00-架构决策记录ADR.md](../架构设计v2/00-架构决策记录ADR.md) 的 ADR-01 裁定表 / ADR-02 四道闸，与 [基于AgentScope2.0的架构设计.md](../基于AgentScope2.0的架构设计.md) §2.2 编排表、§6.1（诚实边界版）、§8 附录速查表为准——单 Agent 的推理循环用统一 `Agent` 类（`reply` / `reply_stream`，内置 ReAct）；**顺序流转**在应用层用 `await` 串联（上游产物以 Content Block 显式传入下游输入），**Fan-out/Fan-in** 用 `asyncio.gather` 并发多个**各自独立**的 `Agent.reply()`、结论在应用层显式合并，编排代码在本仓库落在 `flows/` 目录；长程状态与会话恢复用 `AgentState` + `SessionService`（Redis-backed；2.0.5 起 `SessionManager` 已改名，旧名不可导入）；写动作闸门与人在回路确认由 Permission 系统 + 事件系统（`RequireUserConfirmEvent`）承载。

⚠️ **框架不提供下列原语，需自建**（旧口径曾把它们写成"框架支持"，现已按源码核对撤回）：`MsgHub` / `sequential_pipeline` / `fanout_pipeline` 是 **1.x API**，2.0.0 起 `agentscope/pipeline`、`agentscope/msghub` 模块已删除；`Handoffs` / `Routing` **从未提供**——分诊是**单 Agent 的 ReAct + `Toolkit` 工具选择**，跨能力委托是**显式服务调用**（上下文只传 `evidence_set_id` / `session_id` / `traceparent`，不传消息历史）；"多 Agent 共享消息上下文"在 2.0 **无原语**，硬做要自建消息中转。`GoalPipeline` / `TeamPipeline` 虽仍存在但官方标注 **experimental**，且 `TeamPipeline` 明确"成员间不互相说话"——**观察，不进生产，不能作为"框架支持协同"的论据**。

**这对本文结论的影响**：模式①并不依赖"共享上下文"原语——它要求的恰恰是**各分支只读同一份 `evidence_set_id`、彼此不看对方中间结论**（扇出互看会放大错误：无中心校验 17.2× vs 中心化 4.4×【A/B，arXiv:2512.08296】），所以"两类模式"的裁定不变；变的是**实现成本归应用层**（自建并发与汇合裁决），以及 Blackboard 一类"共享写板"拓扑从"框架支持"降级为"框架不提供 + 证据反对"。这些是**编排形态**，与"要不要 Multi-Agent"是两件事——应用层顺序 `await` 里可以全是确定性节点加一个 Agent 节点。

**MES 的关键取舍**：子 Agent 之间传递**结构化证据包（artifact）**，不传递对话历史。理由是可审计——质量场景要能回答"这条结论的依据是哪条过点记录 / 哪个批次号"，对话历史无法作为审计证据。**同时计入代价**：复用子 Agent 的前提是稳定的输入输出契约，artifact schema 的治理本身是持续成本（《复核》P2-6）。

## 2. MES 模块裁定：与《复核》§3 保持一致

《复核》按"两个及以上自主 LLM 决策实体"的严格定义逐一复核了 11 个模块，结论是：**按严格定义确定受益的只有两类模式，RCA 是第①类的有条件子集，其余 8 个 MES 模块退化为"单 Agent + 工具 / 服务 + 工作流"**。本节只做 MES 落点映射，论证过程以《复核》为准，计数表述不得另立。

### 2.1 确定受益的两类模式

| 类 | 命中判据 | MES 落点 | 限定条件 |
|----|---------|---------|---------|
| **① 广度优先的只读取证** | C3'（真独立）+ 上下文隔离 | **影响面清点**：在制工单 / 库存 / 在途 / 已交付 / 客户现场五个系统并行清点，各路就地压缩成结构化清单 | 全程只读；**清点完成后处置决策必须回到单线程**——隔离范围、返工策略、客户通报口径只能由**一个**决策 Agent（或人）在汇总证据上做，绝不让五个 Agent 各写各的 |
| **② 带外部证据的生成-验证** | C8 | SOP / 工艺文件的**一致性校验**：审核 Agent 去查工艺路线参数规格、质量门禁规则、设备能力参数，比对草稿是否矛盾 | 审核方不得"重读一遍"（P0-1）；不得修改证据源与发布闸门；**SOP 本身顺序生成，不分章并行**（P1-3） |

**RCA（质量根因分析）不独立成第三类**：它是①的**有条件子集**——先 narrowing 限定 2–4 条假设、并行度按假设分叉动态决定、红队必须持有不同数据源或不同方法、**前置数据就绪度评估**（P2-1：过点记录是否绑定设备参数与工艺版本快照、批次绑定是否完整、检验数据能否回溯到单件）。数据不全时，单 Agent 和多 Agent 都做不出根因。

### 2.2 逐模块裁定（《复核》所称"退化的 8 个" = A2–A6、A8–A10）

下表列全 11 个模块的裁定，便于逐条对照，**但"退化"只指其中 8 个（A2–A6、A8–A10）**：A7 属模式①、A1 是①的有条件子集，两者不计入 8；A11 随 A9 的确定性检测层与 A6 一并退化，不单独计数；A10 被否的是"分章并行"，其**带外部证据的审核**属模式②。

| 模块 | 正确架构（《复核》裁定） |
|------|----------------------|
| A1 质量根因分析 | **有条件**受益：单 Agent 先 narrowing → 限定分支的只读取证子 Agent → 红队（不同数据源 / 方法）→ 单线程裁决；不是"六路固定并行" |
| A2 ECN 影响评估 | 影响面计算是**确定性关系型关联查询服务**；处置策略分派是规则 + 人工审批；只有"评估报告生成"是单个 Agent |
| A3 换线编排 | **工作流引擎**（步骤、等待、审批、升级）+ 每步一个**独立单 Agent 建议器**；审批链不由 Agent 承载 |
| A4 设备诊断 | **一个诊断 Agent 挂多个工具**：信号算法是服务、手册检索是 RAG 工具、备件查询是 API |
| A5 返修决策 | 可返修性判定是**规则引擎**（缺陷码 → 再入点映射）；多目标权衡（成本 / 交期 / 质量风险）由人决策 |
| A6 排产与动态重排 | **Agent + 求解服务 + 工作流**的混合架构：LLM 负责澄清目标优先级、解释结果、与计划员协商修订；CP-SAT / 遗传算法 / 启发式规则作为**确定性求解服务**被调用（**求解器不是 Agent**）；多策略并行对比属 orchestrator-executor 二级；确认落槽走排产上下文应用服务 |
| A7 影响面追溯与隔离 | **谱系查询本身不需要 Agent**；查完之后五级**只读并行清点**是①的正当落点；处置决策单线程 |
| A8 8D / CAPA | 本质是跨部门**工作流**（周期数周）+ 若干独立单 Agent 建议器；D4 可复用 RCA 的取证 sub-agent，但整体不是多 Agent 系统 |
| A9 主动巡检 | 检测层用 **SPC / 阈值 / 定时任务**（确定性、可复现）；Agent 只在告警触发后做诊断与建议 |
| A10 SOP 生成与合规审核 | 单 Agent **顺序**生成 + **带外部证据的独立审核** + 迭代修订；禁分章并行 |
| A11 缺料 / 齐套风险 | 齐套监控是确定性阈值；作为 A6 的输入，不作独立 Multi-Agent 系统 |

**一句话**：原文档"根因分析和排产必拆"的结论已作废——**根因分析是"有条件受益"，排产是"Agent + 求解服务 + 工作流的混合架构"，两者都不是"必拆多 Agent"**。

## 3. 通用不变式：MES Multi-Agent 的硬约束

这些是你已有 Agent 路线 §4 约束在 Multi-Agent 形态下的延伸：

| 不变式 | 说明 |
|--------|------|
| **工具注册对齐限界上下文** | 每个子 Agent 只挂载所用上下文的 toolset，**上下文边界 = 工具注册边界**，避免工具集膨胀与术语串台。**注意这不等于任务分解边界**——任务分解要按"要回答的问题的结构"划分，一个子 Agent 可跨多个上下文取工具（详见 [车间MES场景详解](./车间MES的Multi-Agent真实业务场景详解.md) 场景二） |
| **安全边界建在工具执行层** | 只读能力不挂载任何写工具；写工具必须经 Permission 闸门 + 人在回路确认，服务端还要做鉴权、参数校验、白名单、幂等键。**同一进程内的"Agent 级物理隔离"只是 prompt 层的工具可见性，不是安全边界**；Agent 间通信通道要按**新增攻击面**计入成本（P0-5） |
| **写操作保持单线程** | 有子任务需要写 → 不允许多个 Agent 各写各的。取证/清点可以多路并行，但处置决策与写动作只有一个执行者（Agent 建议 + 人确认），额外 Agent 只贡献判断不贡献动作 |
| **不进过点主事务** | 任何 Agent 不得调过点引擎放行/拦截 API；编排只推人侧动作卡 |
| **写不旁路应用服务** | 草稿落库走正常应用服务，过聚合根不变式 + 事务发件箱 |
| **子 Agent 间传 artifact 不传对话** | 证据包必须结构化、可引用（批次号、过点记录 ID、`routeVersion`），满足质量审计要求；代价是 artifact schema 的契约治理成本（P2-6） |
| **版本一致性** | 诊断 Agent 拉工艺必须带 `routeVersion` 过滤（领域总览 §5.1），否则基于失效工艺给根因 |
| **低置信度转人工 / 转规则引擎** | 与 MES 防错理念一致——宁可拦下让人判。**但置信度不能由 Agent 自评**（P2-5：LLM 自评置信度本身不可靠），须由标定与外部校验得出 |
| **全链路 trace** | 每个子 Agent 的工具调用链、证据锚点、耗时可观测，否则 Multi-Agent 无法调试；每个 Agent 要写清角色、工具白名单、停止条件与**步数和工具调用预算上限**（MAST：失败最集中在这几项缺失）。承载方式：OTel + Tempo/Jaeger，单 Agent 失败用 `reply_stream` 事件回放——**`AgentScope Studio` 已归档，不作为方案** |

## 4. 诚实的代价：Multi-Agent 不是免费的

| 代价 | 量级与说明 | 缓解 |
|------|-----------|------|
| **Token 成本约为单 Agent 的一个数量级** | 每个 Agent 都要带自己的系统提示和共享上下文（【B】量级；社区生产数据【C】仅作量级参考）。原文档写的"N 倍"严重低估 | 子 Agent 只传 artifact；小模型跑取证 / 摘要 / 路由，强模型只做裁决与生成；prompt caching |
| **端到端可靠性的复合衰减（根本代价）** | 每增加一个 handoff 就多一次概率乘法：单步 95% 可靠 → 10 步 59.9%、20 步 35.8%【推，算术演示，非实验数据】 | 给 Agent 步数与工具调用次数设预算上限；每步做独立校验；失败即停并升级人工 |
| **协调复杂度按组合数增长** | 4 个 Agent = 6 个交互点，10 个 = 45 个【C，组合数】 | 拓扑尽量浅；单一汇聚点；契约固定 |
| **并行只压延迟、不降成本** | 总 token 不减少反而上升，实际收益还受 API 并发与速率限制约束【推】 | 先问"延迟是不是真瓶颈"；MES 诊断类场景人往往等得起几分钟 |
| **错误传播与转述损失** | 一个 Agent 判断错误，下游基于它连做 10 个决策才发现【C】；子结论经编排者转述会衰减【推，P2-4】 | 独立校验方必须能拿外部证据；证据锚点全程可回放 |
| **安全面扩大** | Agent 间通信通道（共享黑板、消息传递）是新的注入载体：低权限 Agent 读到的投毒内容可经 handoff 传给高权限 Agent【B/C】 | 通信内容按不可信输入处理；写入单线程；工具白名单 + 服务端鉴权 |
| **一致性 vs 回音室** | 各子 Agent 结论可能冲突；而同质 Agent 辩论又会形成 echo chamber，放大共享偏见而非纠正【A，P2-7】 | 显式裁决位，不靠隐式共识；反对方必须拿不同数据源或不同方法，否则不上辩论结构 |
| **算力混淆** | 相同 thinking-token 预算下，单 Agent 在多跳推理上与五种多 Agent 架构（sequential / debate / ensemble / parallel roles / subtask-parallel）持平甚至更优【A，转引，建议核对原文】 | **没有离线评测集就不许声称"拆了更好"**（评测栈自建：框架 2.0 已删除 `agentscope.evaluate` 且未回归，judge 用独立包 `py-openjudge`） |
| **过度设计风险** | 本可单 Agent 解决的被拆开 | 严守 §1.3 反判据 R1–R4 与 §5 的评审顺序（《复核》§5.2 决策清单五组：前置 / 三条硬判据 / 反向检查 / 成本 / 运维） |

**成本闸门**：给每个候选拆分算一次"每成功任务成本"。若单次成本上升超过一个数量级、而质量收益**无法用离线评测集量化证明**，就不该拆。

## 5. 评审防守 Q&A

**Q：Multi-Agent 和你已有的三项能力自主度分级是什么关系？**
A：正交的两级判断。三项能力决定"Agent 能写到哪一级"，Multi-Agent 决定"要不要把一个任务拆给多个自主 LLM 实体"。一个只读诊断系统可以是 Multi-Agent 的（多个只读取证子 Agent + 单线程裁决），反过来一个单 Agent 也可以是草稿型的。**先定自主度红线，再定拆分粒度；并且记住 sub-agent ≠ multi-agent**——把脏活丢给子 Agent、拿回一段压缩摘要，是单 Agent 框架内的上下文隔离技巧，不构成"多智能体系统"，也不该记在多 Agent 的功劳簿上。

**Q：质量根因分析是不是"必拆"？**
A：**不是，它是"有条件受益"**（《复核》§3.1）。真实 RCA 是序贯、假设驱动的：5M1E 六条线并不独立——发现设备参数漂移会改变对物料批次的取证策略，盲目六路 fan-out 会在注定废弃的分支上浪费取证，无效结果还会挤占后续上下文；而且取证延迟主要在数据查询（时序库 / 关系库）而非 LLM 推理【推】。正确形态：单 Agent 先 narrowing 出 **2–4 条**假设 → 只对**已分叉且真正独立**的假设并行取证（并行度动态决定，不是固定六路）→ 单线程裁决；红队必须给它**不同的数据源或不同的方法**（统计检验 vs 语义检索历史案例），否则"独立"是假的【A，P2-7】。动工前先做**数据就绪度评估**——数据不全时什么架构都不行。

**Q：排产为什么需要"求解器 Agent"？**
A：**不需要，求解器不是 Agent**（P0-2）。排产是约束优化问题不是语言问题，LLM 直接排产结果不可用（硬约束都未必满足）；但按"调用了非 LLM 模块就算多 Agent"来定义，所有带工具的 Agent 都是多智能体，这个定义就失去意义了。正确描述是 **Agent + 求解服务 + 工作流的混合架构**：LLM Agent 负责澄清目标优先级、解释"为什么这么排"、与计划员协商修订；CP-SAT / 遗传算法 / 启发式规则作为**确定性求解服务**被调用；多策略并行对比属 orchestrator-executor 二级；确认落槽走排产上下文应用服务。

**Q：追溯查询是不是也要做成 Multi-Agent？**
A：**不。** 单件 / 批次谱系（where-used / where-from）是**确定性关系型固定关联查询**（追溯读模型 + 参数化查询计划）——制造追溯不使用图检索，不引入 Neo4j、Cypher 或图投影；包一层 Agent 是纯开销。需要 Agent 的是查完之后怎么办：**五级影响面清点才是"广度优先只读取证"的正当落点**（真独立、只读、就地压缩），而处置决策必须回到单线程。把确定性查询和不确定性决策切开，只对后者用 Agent，这个分层本身就是判断力。

**Q：Multi-Agent 会不会更容易越权写库？拆开后权限是不是就"物理隔离"了？**
A：方向要说反过来看（P0-5）：**同一进程内的"Agent 级物理隔离"只是 prompt 层的工具可见性，不是安全边界**；真正的边界在**工具执行层**——Permission 闸门 + 人在回路确认 + 服务端鉴权 + 参数校验 + 白名单 + 幂等键。若工具层不鉴权，把工具挂给哪个 Agent 都一样。而且多 Agent 会**扩大**攻击面：Agent 间通信通道是新的注入载体，低权限 Agent 读到的投毒内容可经 handoff 传给高权限 Agent——这要记为成本项而非收益项。**结论：写操作保持单线程，安全靠工具层，不靠拆分。**

**Q：会不会过度设计？你怎么判断该拆不该拆？**
A：按《复核》§5.2 决策清单的顺序过（**本文不叫它"四道闸门"**——[ADR-02](../架构设计v2/00-架构决策记录ADR.md) 的"四道闸"是另一套编号：模式 / 可拆性 / 中心校验 / 成本，两套并存但别混用）。顺序：①**前置闸门**：数据就绪度评估做了吗？离线评测集建了吗？十项更便宜的上下文工程手段试过了吗？（多数场景到此就解决了）②**三条硬判据**至少中一条：C1' 分层路由仍选不准 / C3' 真独立且延迟是真瓶颈 / C8 有可证实的信息不对称。③**反向检查**，任一为是就不拆：子任务共享需要全局一致的状态 / 命名 / 格式；有任何子任务需要写；审批链、等待人、长程状态该归工作流引擎；检测判定是确定性阈值或 SPC。④**成本闸门**：成本上升幅度能否被评测集上的质量提升量化抵消？每个子 Agent 的输出有基于外部证据的独立校验吗？失败隔离与重试设计了吗？⑤**运维闸门**：角色 / 工具白名单 / 停止条件 / 预算上限写清了吗，有全链路 trace 吗，有回退条件吗（`AGGREGATE_MODE` / `REPORT_MODE` 三档可一键退回单 Agent）。另有 R1–R4 兜着：硬实时不上 Agent、确定性事务写走应用服务、单域问答单 Agent + RAG 就够、流程固定用状态机 / BPMN。

## 6. 一句话定位

"判断 MES 该不该上 Multi-Agent，看的不是功能重不重要、角色多不多，而是三条硬判据：**工具/知识域冲突且分层路由不经济（C1'）、存在真独立且延迟敏感的子任务（C3'）、存在可证实的信息/能力不对称（C8）**——三条至少中一条、且成本闸门通过才拆。长程任务交给外部化状态，审批链交给工作流引擎，求解器是服务不是 Agent，检测判定是 SPC 不是 Agent，'换个 prompt 重读同一份材料'的审核 Agent 不叫独立验证。按这个口径，车间里确定受益的只有两类模式：**广度优先的只读取证**（五级影响面清点）和**带外部证据的生成-验证**（SOP 查规则库），质量根因分析只是前者的**有条件子集**，其余 8 个 MES 模块退化为"单 Agent + 工具 / 服务 + 工作流"。**过点判定和工单写入是永不许碰的**：写操作保持单线程、不进过点主事务（P99 ≤ 200ms）、不旁路应用服务。"
