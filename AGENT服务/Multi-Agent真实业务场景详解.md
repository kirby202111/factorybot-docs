# Multi-Agent 真实业务场景详解（跨行业通用版）

> **另有一份车间 MES 专用版**：[车间MES的Multi-Agent真实业务场景详解.md](./车间MES的Multi-Agent真实业务场景详解.md)，五个场景全部落在车间 MES（SMT 换线编排、批次质量异常的根因分析与影响面清点、月度产能工时多源核对、SOP 更新与合规审核、航空件超差 MRB 评审），并遵循过点 200ms 红线、`routeVersion`、写走应用服务等车间约束。**如果你的场景是制造/车间 MES，请直接看那一版**，本版的跨行业案例（SaaS 交付、PE 尽调、集团对账、跨境电商本地化、银行授信）仅供参照。

> **本文是 [哪些场景真正需要 Multi-Agent 系统](./哪些场景真正需要Multi-Agent系统.md) 的落地篇。** 上篇讲的是判据与类型，本篇把每一类放进一个可指认的真实业务里，按统一结构展开：
>
> **业务背景 → 用户角色与核心诉求 → 现状与痛点 → 引入后的完整流程 → 关键数据流转 → 可衡量的业务价值 → 边界（哪些环节仍不该用 Agent）**
>
> **关于文中的所有数字**：各场景的"业务价值"表格给的是**目标示例值**，用于说明应该衡量什么、量级大概在哪，**不是行业基准数据**。真实目标必须用你自己的基线校准。这一条请务必注意——把示例值当基准引用，是这类文章最常见的误导。

## 场景一：企业级软件的特性交付 —— 多角色协作

### 业务背景

一家 SaaS 公司，产品团队每月要交付 20–30 个中等复杂度特性。一个特性从一句话需求到上线，要跨需求澄清、设计、编码、测试、验收五个环节。团队已经在使用 AI 编码助手，但基本是"一个会话从头做到尾"的用法。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 产品经理 | 需求被准确理解，别做完了才发现理解偏了 | 需求返工次数 |
| 开发工程师 | 少写样板代码，少被模糊需求卡住 | 单个特性交付工时 |
| 测试 / QA | 有清晰、可测的验收标准 | 缺陷逃逸率 |
| 技术负责人 | 质量可控、过程可审计 | 一次通过率、线上回滚率 |

### 现状与痛点

1. **长会话上下文退化**。一个特性做到后期，Agent 开始违反它在前十几轮自己定下的约束——比如"不要动支付模块"，做到三十轮后就忘了。这不是它故意的，是那条约束被后续大量代码和工具输出稀释了。
2. **自验自收**。同一个 Agent 写完代码自己写测试、自己跑、自己判通过。它会本能地让测试迁就实现，严重时直接改测试让它通过——"独立验证"名存实亡。
3. **验收标准事后才定**。往往等实现完了才讨论"怎样算做完"，此时返工成本最高。
4. **失败重跑代价大**。单会话里一次失败，往往要整链重放。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 关键约束 |
|------|------|--------|---------|
| 0. 规格 | 规格 Agent | 把一句话需求展开成规格：功能点、边界条件、验收标准 | 输出物人工确认 |
| 1. 对齐 | 实现 Agent + 验证 Agent | **先就"完成标准"达成一致**，再动手 | 标准先于实现，避免事后扯皮 |
| 2. 实现 | 实现 Agent | 在干净上下文里按规格编码，产出变更说明 | 不参与验收判定 |
| 3. 取证 | 执行环境（**代码，不是 Agent**） | 跑测试、起服务、真实浏览器操作，产出执行证据 | 证据是客观产物 |
| 4. 验证 | 验证 Agent | **只读证据**提缺陷清单 | **不得修改测试用例与验收闸门** |
| 5. 返修与裁决 | 实现 Agent / 人 | 缺陷回修；争议由规格 Agent 或人裁决 | 复跑取证后闭环 |

**这套结构成立的真正原因**：验证方拿到的是生成方**没有的东西**——执行证据（测试输出、渲染截图、运行日志）。审核的对象是证据，不是草稿。这也是上篇判据三的要求。

### 关键数据流转

```
需求文本
  → [规格 Agent] → 规格文档（功能点 + 边界条件 + 验收标准 + 完成标准）
  → [实现 Agent] → 代码变更 + 变更说明
  → [执行环境 - 确定性] → 证据包（测试报告 / 截图 / 日志）
  → [验证 Agent] → 缺陷清单（每条挂证据位置）
  → [返修] → 补丁 → 复跑取证 → 通过 / 升级人工
```

两个要点：**状态通过制品文件传递，不靠对话历史**（可审计、可回放）；**验证 Agent 的输入是证据包，不是代码草稿**。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 需求返工次数 | 从需求确认到验收之间的规格变更次数 | 显著下降 |
| 缺陷逃逸率 | 上线后 7 天内发现的缺陷数 / 交付特性数 | 下降 |
| 单特性交付工时 | 工时系统统计 | 下降 |
| AI 产出的一次通过率 | 未经返修直接通过验证的比例 | 提升 |

建议先测两周基线，再定目标值。**没有基线就无法证明架构改进有效。**

### 边界

lint、类型检查、单测断言、CI 门禁——全部留在确定性工具链里。**不要把这些确定性检查也换成 Agent**，那只会得到更慢、更贵、还不可复现的结果。发布审批归人和工作流。

## 场景二：PE 投资尽职调查 —— 并行探索多条线索

### 业务背景

一家 PE 机构做项目尽调，需要在 2–4 周内完成财务、法务、商业、技术四条线的核查，产出投决材料。信息源高度分散：公开工商与司法数据、行业研报、专家访谈纪要、标的方提供的资料包、机构内部的历史项目库。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 投资经理 | 快速形成判断，不漏掉关键风险 | 尽调周期、漏检风险 |
| 财务分析师 | 财务真实性、关联交易识别 | 核查覆盖率 |
| 法务 | 股权沿革、诉讼与合规瑕疵 | 瑕疵发现率 |
| 投委会 | 结论有据可查，敢据此决策 | 结论可溯源性 |

### 现状与痛点

1. **串行检索太慢，且上下文很快被原文填满**。研报 PDF、工商档案动辄几百页，单 Agent 读完再读下一份，有效上下文迅速退化。
2. **过早收敛**。先看到一个风险点，后面就一路深挖这一个方向，其他方向根本没覆盖——这正是单 Agent 检索最容易踩的坑。
3. **引用不可溯**。研报里说"该公司市场占有率约 15%"，没有出处，投委会不敢用。
4. **四条线口径不一**，汇总时结论互相矛盾，人工协调成本高。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 |
|------|------|--------|
| 0. 分解 | 规划 Agent | 把尽调问题拆成 N 个**正交**子问题：财务真实性、关联交易、股权沿革、诉讼与处罚、市场空间、竞争格局、技术壁垒、团队背景 |
| 1. 并行取证 | 检索 Agent ×N | 各自深挖一个子问题，在干净上下文里读大量原文，**只回传结构化摘要 + 引用锚点** |
| 2. 交叉核对 | 核对 Agent | 检查各路结论是否冲突；抽检引用是否真实存在 |
| 3. 汇总 | 汇总 Agent | 形成风险清单与结论，每条挂证据链与置信度；低置信度明确标注"需人工复核" |
| 4. 人工复核 | 投资经理 / 投委会 | 复核标注项，形成投决意见 |

**这套结构成立的真正原因**：子问题**真独立**（财务真实性核查的结果不会影响股权沿革怎么查），且每个子任务要吞入大量低信噪比原文、需要就地压缩。这正是上篇判据一（上下文隔离）与判据二（真并行）同时命中。

### 关键数据流转

```
尽调问题清单
  → [规划 Agent] → 正交子问题列表（含每个子问题的检索范围与来源类型）
  → [检索 Agent ×N 并行] → 每路摘要 + 引用锚点（文档 ID + 页码/段落定位）
  → [交叉核对 Agent] → 冲突清单 + 引用真实性校验结果
  → [汇总 Agent] → 尽调报告（每条结论挂证据链与置信度）
  → 人工复核 → 投决材料
```

关键 artifact 是**引用锚点**：必须能回溯到原文的文档与位置，否则复核无法进行，投委会也不会采信。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 尽调周期 | 从启动到投决材料的自然日 | 明显缩短 |
| 信息源覆盖数 | 单项目实际检索并引用的来源数 | 成倍提升 |
| 关键结论可溯源率 | 挂了可回溯引用的关键结论占比 | 接近 100% |
| 投决材料准备工时 | 分析师投入工时 | 下降 |
| 漏检率 | 投后 12 个月内发现的、尽调未识别的重大风险 | 下降（需长期跟踪） |

### 边界

出资决策在人。估值测算、财务比率计算用代码。监管与合规判定用确定性规则。**这一整条线是只读的**——不产生写冲突，这是它能安全并行的基础。

## 场景三：集团月度经营对账 —— 长链路数据处理与交叉验证

### 业务背景

某零售集团每月关账后，财务与数据团队要核对多个系统的经营数据：ERP 的收入、OMS 的订单、WMS 的出库、支付网关的流水、各渠道平台的结算单。跨系统时间差、退换货跨期、口径不一致，导致每月对账要耗掉团队大量工时。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 财务分析师 | 找到每一笔差异的原因，别让我逐条看 | 对账周期、归因准确率 |
| 数据工程师 | 口径稳定，别每月重吵一遍 | 口径变更次数 |
| 业务线负责人 | 我的数据准不准 | 差异金额 / 营收占比 |
| 审计 | 过程可追溯 | 可审计性 |

### 现状与痛点

1. **链路长、错误复利**。取数 → 清洗 → 对齐口径 → 比对 → 找差异 → 归因 → 出报告，七步以上。单步 90% 可靠，五步之后整体成功率只剩六成。
2. **自验自收**。同一段脚本取的数、又用它自己核对，口径错了根本发现不了。
3. **差异归因全靠人**。几百条差异逐条看，占了对账工时的大头。
4. **口径歧义无人裁决**。收入按发货还是按签收算？每月重复讨论一次。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 定口径 | 人 + 口径 Agent | 确定本期口径规则，固化为可执行的口径定义文件 | 半自动 |
| 1. 取数与清洗 | **代码 + 单测** | 抽取、标准化、入事实表 | **确定性** |
| 2. 独立重算 | 校验 Agent | 用**不同路径**重算关键指标（用明细重算汇总、用支付流水反推收入） | 验证核心 |
| 3. 差异检出 | **程序化比对** | 产出差异清单（金额、科目、样本） | **确定性** |
| 4. 归因 | 归因 Agent | 对每条差异分类：跨期 / 口径 / 漏传 / 重复 / 真异常，并附证据 | Agent 判断 |
| 5. 裁决与报告 | 人 + 报告 Agent | 裁决口径争议，出具对账报告 | 人机 |

**这套结构成立的真正原因**：校验方用**独立的计算路径**得到生成方拿不到的第二份结果。两条路径一致才算验证通过——这才是真验证（判据三）。同一条路径算两遍不叫验证。

### 关键数据流转

```
各系统原始数据
  → [取数清洗 - 代码] → 标准化事实表
  → [双路计算] → 指标 A（主路径）+ 指标 B（独立路径：不同数据源或不同方法）
  → [程序化比对] → 差异清单（差异金额 / 影响科目 / 差异样本）
  → [归因 Agent] → 分类后的差异清单（每条附证据与建议处置）
  → [人裁决口径争议] → 对账报告 + 口径定义文件（供下月复用）
```

关键 artifact 是**口径定义文件**：本月裁决的结果要固化下来，下月直接复用，避免同一场争论每月重开。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 月度对账人力投入 | 人天 | 大幅下降 |
| 对账周期 | 关账到出报告的自然日 | 从数天压到 1–2 天 |
| 差异归因准确率 | 归因结论经复核正确的比例 | 提升 |
| 因未发现差异导致的后期调账 | 次数与金额 | 下降 |
| 口径争议重复发生次数 | 同一歧义反复讨论的次数 | 趋近于零（已固化） |

### 边界（这个场景尤其重要）

**取数、清洗、比对、断言——全部用代码 + 单元测试 + 断言完成。** 这条链路绝大部分是确定性的，把它整体 Agent 化是典型的过度设计。Agent 只介入两个真正需要判断的地方：**口径歧义消解**和**异常归因**。

## 场景四：跨境电商商品内容本地化 —— 质量与效率的分层流水线

### 业务背景

某跨境电商需把数十万 SKU 的商品信息（标题、卖点、规格参数、合规声明）本地化到多个国家站点，要同时满足当地语言习惯、平台规则、以及当地法规要求（如欧盟的合规声明、能效标签、化学品标识）。特点是：**量大、单条价值低、但错一处合规声明可能招致下架或罚款**。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 本地化运营 | 快，别卡在上架前 | 处理吞吐、上市时效 |
| 品类经理 | 卖点表达准确，不影响转化 | 转化率 |
| 合规专员 | 高风险品类零出错 | 合规错误率 |
| 平台运营 | 别违反平台规则 | 下架 / 处罚次数 |

### 现状与痛点

1. **全量用强模型，成本扛不住**。数十万 SKU × 多语种，账单是线性叠加的。
2. **全量用小模型，质量不过关**。规格参数与合规声明错误率高，只能人工全检——省下的钱又花回去了。
3. **风险与投入不匹配**。电器、化妆品、儿童用品和一件普通 T 恤，走完全相同的流程，高风险品类没有得到更多审查资源。
4. **返工闭环慢**。合规问题往往在上架审核阶段才被发现，重新走一遍全流程。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 风险分层 | **规则引擎** | 按品类 / 市场 / 法规敏感度给 SKU 打风险标签 | **确定性** |
| 1. 批量生成 | 小模型 ×N | 批量产出初稿（结构化字段：标题 / 卖点 / 规格 / 合规声明） | 低成本跑量 |
| 2. 程序化校验 | **确定性校验** | 必填字段完整性、单位换算、禁用词、平台字数限制 | **确定性** |
| 3. 分级终审 | 强模型 + 合规规则库工具 | 高风险 SKU 逐条审；低风险抽检 | 分层投入 |
| 4. 事实核查 | 确定性比对 + Agent 消歧 | 规格参数与源数据比对，歧义由 Agent 消解 | 混合 |
| 5. 人工兜底 | 合规专员 | 终审不通过进人工队列 | 人 |

**这套结构成立的真正原因**：不是"多个 Agent 一起想办法"，而是**按难度分层投入算力**——用便宜模型处理量大容错高的部分，把昂贵模型集中在高风险样本上；同时利用"写难验易"的不对称（生成本地化文案难，核查字段与规则是否合规容易）。

### 关键数据流转

```
源 SKU 数据（规格库）
  → [规则分层] → 风险标签（高 / 中 / 低）
  → [小模型批量生成] → 初稿（结构化字段）
  → [程序化校验] → 校验失败清单（退回重生成或自动修正）
  → [分级终审：强模型 + 合规规则库工具] → 终审结论 + 修改建议 + 规则依据
  → [事实核查：源数据比对] → 参数一致性结果
  → [人工队列 - 仅高风险未通过项] → 上架
```

关键 artifact 是**规则依据**：终审判定必须引用具体的合规规则条目，而不是模型"觉得不合适"。合规事实来自规则库这个**外部证据源**，不能依赖模型记忆。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 单 SKU 本地化成本 | 总成本 / SKU 数 | 大幅下降 |
| 处理吞吐 | 单位时间完成 SKU 数 | 数倍提升 |
| 高风险品类合规错误率 | 抽检错误率 | 不高于人工全检水平 |
| 上市时效 | 从商品建档到上架 | 缩短 |
| 因合规问题导致的下架次数 | 平台侧统计 | 趋近于零 |

### 边界

合规判定必须有规则库依据。禁用词、字数限制、单位换算这类**确定性检查必须用代码**。模型只做语言生成、歧义消解和基于规则的判断。另外要承认：这类收益主要来自**分层模型 + 更多算力**，不是"多 Agent"这个形式——同样的收益有时用"单 Agent 多次采样 + 规则筛选"也能拿到，先试简单版本。

## 场景五：银行对公授信评审 —— 对抗式评审

### 业务背景

银行对公授信审批：客户经理提交授信方案与材料，风控、合规、审批官多方评审。材料动辄几百页（财报、银行流水、合同、担保结构）。核心难点不是"读不完"，而是**评审意见容易趋同**——大家都跟着客户经理写的叙事走。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 客户经理 | 批得快，别反复补材料 | 审批时效 |
| 风控经理 | 识别真实风险，尤其隐性的 | 风险线索发现率 |
| 合规 | 程序合规、要件齐全 | 合规瑕疵率 |
| 审批官 | 决策有据，敢签字 | 决策可追溯性 |

### 现状与痛点

1. **材料核查靠人读**。几百页材料，风控实际能细看的比例有限。
2. **评审意见趋同**。评审会上容易形成"材料说什么就是什么"的共识，缺少系统性的反面论证。
3. **反驳缺乏证据支撑**。凭经验说"我觉得这家有问题"，既不能写进纪要，也说服不了审批官。
4. **隐性风险发现晚**。关联交易、表外负债、实际控制人风险常在贷后才暴露。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 关键约束 |
|------|------|--------|---------|
| 0. 材料解析 | 解析 Agent | 把材料结构化：财报关键科目、流水特征、合同条款、担保结构 | 输出结构化材料包 |
| 1. 提案 | 提案 Agent | 基于结构化材料形成"支持授信"的完整论证与还款能力测算 | 只看到材料包 |
| 2. 独立取证 | 红队 Agent | 用**外部数据源**（工商/司法/舆情/行业数据/历史违约库）独立取证，专门找反证 | **数据源与提案方不同** |
| 3. 对抗 | 红队 vs 提案方 | 红队输出反驳清单，每条挂外部证据锚点；提案方可在**证据层面**应辩 | 不是嘴仗，是证据对抗 |
| 4. 裁判 | 裁判 Agent | 汇总正反证据，输出风险分级与争议点清单 | 中立 |
| 5. 人工审批 | 审批官 | 基于风险分级与争议清单决策 | 决策权在人 |

**这套结构成立的真正原因**：红队 Agent 拥有提案方**看不到的外部数据**。这是判据三最纯粹的形态。

**反面警示**：如果红队只是换个 prompt 说"请你唱反调"，用的还是同一份材料——那得到的不是反驳，是换个说法的重复。更糟的是同质 Agent 之间会形成回音室：多数派观点被反复强化，即使它是错的。**红队必须拿到不同的输入**，这个场景才成立。

### 关键数据流转

```
授信材料
  → [解析 Agent] → 结构化材料包
  ├─ 提案路径 → 支持论证 + 还款能力测算
  └─ 红队路径（外部数据源，提案方不可见） → 反驳清单 + 外部证据锚点
  → [证据层面的对抗与应辩]
  → [裁判 Agent] → 风险分级 + 争议点清单 + 完整证据链
  → 人工审批
```

关键 artifact 是**反驳清单的证据锚点**：每一条反驳必须能指到具体的外部数据记录，否则审批官无法采信，也写不进评审纪要。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 单笔授信评审工时 | 从受理到审批完成 | 下降 |
| 风险线索发现率 | 评审阶段识别出的风险点数量 | 提升（尤其隐性关联、表外负债） |
| 评审意见趋同度 | 评审意见中独立反面意见的占比 | 下降（出现有证据的反面意见） |
| 材料补正次数 | 审批过程中要求补充材料的轮次 | 下降 |
| 贷后 12 个月违约率 | 最终验证指标 | 下降（需长期跟踪，注意归因困难） |

### 边界

审批决策权在人，Agent 只提供证据与分级。监管指标计算、授信额度测算用确定性规则。红队要设**证据门槛**——没有证据的反驳不进入清单，否则噪音会淹没真信号，反而拖慢审批。

## 小结：五个场景的横向对比

| 场景 | 命中的判据 | 成立的关键机制 | 不该 Agent 化的部分 |
|------|-----------|--------------|-------------------|
| 软件特性交付 | 判据三（信息不对称） | 验证方拿执行证据，且不改验收闸门 | lint / 类型检查 / 单测断言 / CI 门禁 |
| 投资尽职调查 | 判据一 + 二（上下文隔离、真并行） | 子问题正交，就地压缩，只读 | 估值测算、财务比率、合规判定 |
| 经营对账 | 判据三（信息不对称） | 独立路径重算，双路比对 | 取数、清洗、比对、断言 |
| 内容本地化 | 分层与算力分配 | 按风险分层投入模型档位，规则驱动分层 | 禁用词、字数、单位换算、合规规则库 |
| 授信评审 | 判据三（信息不对称） | 红队有提案方看不到的外部数据 | 额度测算、监管指标、最终审批 |

**四个共性**：

1. **全部命中的都是"信息不对称"或"真并行"**，没有一个是靠"多几个角色"本身取胜的。红队若与提案方看同一份材料，就不成立；对账若用同一条路径算两遍，就不叫验证。
2. **确定性环节全部留在了代码里**。五个场景里，真正交给 LLM 的都是"需要判断"的窄环节：口径歧义、异常归因、语言生成、证据层面的对抗。
3. **写操作与最终决策全部在人手里**。尽调不出资、对账不调账、授信不审批、上架前高风险项过人工。
4. **价值都落在"周期缩短"和"覆盖率提升"上**，而不是"替代了某个人"。这是当前能力水平下最现实的收益形态。

**最后重复一遍开头的提醒**：文中的所有数字都是**目标示例**，用来说明该衡量什么。真实目标请用你自己两周的基线数据校准——**没有基线，就无法证明任何架构改进是有效的**，也无法把"多烧了算力"和"架构真的更优"区分开。
