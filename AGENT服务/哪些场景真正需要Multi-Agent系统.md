# 哪些场景真正需要 Multi-Agent 系统

> 一句话回答：**比大多数人以为的少得多。**
>
> 现在"Multi-Agent"这个词被用得很宽——一个 Agent 挂了十几个工具、调用了两次子流程，也被叫做多智能体。但工具不是 Agent，子流程不是 Agent，求解器也不是 Agent。混淆这些概念，会让团队在本可以用更简单方案解决的地方，付出一个数量级的成本和一整套调试地狱。
>
> 本文先给判断标准，再说明**真正受益的两类模式**（附两个具体案例作为这两类的实例，另有一个有条件子集），最后把成本和边界摆清楚。本文的判据与模式划分在独立复核后重建，证据分级用【A】同行评议 /【B】厂商技术报告 /【C】二手聚合 /【推】推断 /【设】假设。
>
> **范围限定**：本文只讨论 Agent 作为**协助者**的场景——只读取证、独立校验、评审与推演，产出证据、结论与建议，不落地生产动作。凡需要 Agent 作为执行者嵌入生产/业务流程、直接产出或改写生产数据的用法，均不在讨论范围内（Agent 不进生产流程）。

---

## 一、先把概念分清楚

在讨论"要不要多 Agent"之前，有两个常被混为一谈的东西必须切开：

**子 Agent（sub-agent）≠ 多 Agent 系统。**

把一个脏活丢给子 Agent、让它在一块干净的上下文里深挖，最后只回传一两千 token 的摘要——这是**上下文隔离技巧**，是单 Agent 框架内部的工程手法。它的目的是不让低信噪比的原始数据污染主干推理。很多团队宣称的"多智能体架构"，实际上只是用到了这一招，主干决策者始终只有一个。这不是坏事，但它不该被记在多 Agent 的功劳簿上，更不该成为上多 Agent 的理由。

**工具/服务 ≠ Agent。**

CP-SAT 求解器、图数据库、时序异常检测算法、规则引擎——它们是被调用的能力，不是自主决策实体。一个 Agent 调了求解器，和一个 Agent 调了计算器，在架构上没有本质区别。如果按"调用了非 LLM 模块就算多 Agent"来定义，那所有带工具的 Agent 都是多智能体，这个定义就失去意义了。

本文采用较严格的定义：**Multi-Agent 系统 = 存在两个及以上自主决策的 LLM 实体，各自持有不同的上下文、工具与职责，通过显式协议交换信息并共同完成一个目标。**

按这个定义往下看。

## 二、判断标准：什么时候单 Agent 够，什么时候值得引入

### 2.1 单 Agent 的天花板在哪

单 Agent 不是不能用，而是规模上去后会撞到四堵墙：

**第一堵：上下文不是"装不下"，而是"装多了会变笨"。**

这一点常被误解。很多人以为问题出在窗口容量，于是等更大窗口的模型。但实测结论是：随着输入变长，模型的表现会**持续下降**，而且远在触及窗口上限之前就开始了。Chroma 在 2025 年测了 18 个前沿模型，无一例外都呈现这个趋势；一个拥有 200K 窗口的模型，在 5 万 token 左右就可能明显退化【B】。更反直觉的是：**哪怕只放入一个同主题的干扰项，准确率都会下降**；信息放在开头和结尾时利用得最好，放在中间最差（即所谓的 lost in the middle）【A/B】。

实际表现就是：会话后期，Agent 开始引用含糊（说"那个文件"而不是精确路径）、重复读取已经读过的东西、违反自己在前十几轮定下的约束——不是它故意的，是那条约束被后续内容稀释了。

**第二堵：工具越多，越选不准。**

工具集较小的时候选择准确率很高；数量上到 20 个以上，准确率会出现明显下滑，且失败主要不是"选错工具"，而是"选对工具、填错参数"【C，二手聚合榜单，未核对原始来源，仅作量级参考】。

**第三堵：串行执行，延迟与错误一起累积。**

工具调用是链式的。假设单次调用准确率 90%，三步之后整体成功率约 73%，五步约 59%，十步只剩 35%【C，算术演示】。这是算术，不是危言耸听。

**第四堵：没人反驳它。**

单 Agent 对自己产出的复核基本无效。研究结论相当一致：在没有外部反馈的情况下让模型审查并修正自己的回答，准确率**反而可能下降**——它把正确答案改错的次数，多于把错误改对的次数【A，Huang et al. ICLR 2024；TACL 综述 arXiv:2406.01297】。真正有效的审查，必须引入生成时不存在的新信息。

### 2.2 值得引入 Multi-Agent 的三条硬判据

单 Agent 撞墙之后，也**不意味着**就该拆。拆之前要过这三关，至少满足一条：

**判据 C1'：工具或知识域冲突，且路由解决不了。**

当工具集超过 20 个、且语义上分属多个差异极大的领域时，选择准确率会下降【C，二手聚合，仅作量级参考】。但**先别急着拆**——更便宜的方案是工具分层路由：先用一个轻量模型或检索器选出 5–10 个相关工具，再交给执行模型。只有当工具集的语义跨度大到连路由都做不好时，才考虑按域拆分成多个 Agent。

**判据 C3'：存在真正独立的子任务，且延迟是真实瓶颈。**

"独立"是要检验的：**拿掉一个子任务的输出，另一个的结果会变吗？** 会变，就不是真独立，并行只会在注定要废弃的分支上浪费算力。

同时要问：延迟真的是瓶颈吗？如果任务本来就要人等几十分钟，省下的那点并行时间没有价值，而成本是实打实上升的。

**判据 C8：存在信息或能力的不对称——这一条最重要，也最常被忽略。**

拆分能带来收益的真正原因，是某个角色能看到或做到另一个角色看不到、做不到的事。**审核方必须有生成方拿不到的外部证据**，而不是换个身份把同一份材料重读一遍。

CRITIC 研究给了个很干净的对照：让模型用外部工具（搜索引擎、Python 解释器）验证自己的答案，效果显著提升；把工具验证这一步拿掉、只保留自我评估，**大部分提升就消失了**【A，ICLR 2024】。这说明审查的价值不在"让模型再想一遍"，而在引入了新信息。

所以：**如果两个 Agent 看到的是同一份东西，那它们其实是一个 Agent，只是花了两倍的钱。**

### 2.3 反向检查：这些情况不该拆

| 情况 | 为什么不该拆 |
|------|------------|
| 子任务共享需要全局一致的状态（命名、格式、口径、风格） | 各自做局部合理的选择，合起来全局不自洽。这是"两个 Agent 一个做深色主题、一个做浅色主题"的经典翻车 |
| 有子任务需要**写** | 并发写会产生冲突状态。写操作应保持单线程，额外 Agent 只贡献判断，不直接写 |
| 流程是确定性的（阈值判定、固定 ETL、规则校验） | 用代码。确定性的事交给概率系统，只会得到更贵、更慢、还不可复现的结果 |
| 需要人工审批、等待、长周期挂起 | 这是工作流引擎与审批流的活。用 Agent 承载审批链，会得到比 BPMN 更难调试、更难审计的实现。本项目据此把 4 个编排场景的 gate 等待全部落到 **MES 已有工单/待办实体**，agent 侧不挂起、不计时、不续跑，确认后回调 `/advance` 重查当下事实另起一段（见 [ADR-05](../架构设计v2/00-架构决策记录ADR.md)） |
| 单域问答、简单检索 | 单 Agent + RAG 足够 |
| 硬实时链路（毫秒级 SLA） | 规则引擎或确定性代码，Agent 只能在判定之后异步介入 |

### 2.4 成本闸门

满足判据还不够，最后过一道经济账：

- **成本**：多 Agent 系统的 token 消耗大致是单 Agent 的**一个数量级**【B，Anthropic 公开报告的量级；社区生产数据【C】仅作量级参考】。每个 Agent 都要带上自己的系统提示和共享上下文。
- **协调复杂度**：交互点按组合数增长，4 个 Agent 有 6 个交互点，10 个就有 45 个【C，组合数】。
- **可靠性**：每增加一个交接环节，就多一次概率乘法——单步 95% 可靠，10 步链剩 59.9%、20 步剩 35.8%【推，算术演示，非实验数据；真实系统步骤间非独立，实际可能更好也可能更差】。
- **可观测性**：出问题时要能回放单个 Agent 的链路，否则无法定位。
- **安全面**：每增加一个 Agent 就多一扇门，而 Agent 之间的通信通道本身会成为新的注入载体——一个低权限 Agent 读到的投毒内容，可以经由交接传给高权限 Agent【B/C，未核对原始技术报告】。

**闸门问题**：多 Agent 方案的单次成本上升，能否被**离线评测集上可量化的质量提升**抵消？如果答不上来，就先别拆。

## 三、真正受益的两类模式（下面两个案例是这两类的实例）

**先说结论：能独立站住的受益模式只有两类**——

- **模式①：广度优先的只读取证**（命中 C3'）——多个真独立的子任务并行取证，各路在干净上下文里吞入大量低信噪比原始数据、就地压缩，只回传结构化结论；全程只读。
- **模式②：带外部证据的生成-验证**（命中 C8）——验证/反对方掌握生成方拿不到的外部证据（执行结果、规则库、实测数据、独立数据源、独立计算路径）。

再加一个**有条件受益**：**限定分支后的 RCA 取证**——它是模式①的子集，不是第三类（须先 narrowing 限定假设数、并行度按分叉动态决定、前置数据就绪度评估）。

下面两个案例分属这两类，**不是两类之外的独立受益场景**；每个案例仍按：痛点 → 为什么多 Agent 能解决 → 角色划分与协作方式 → 诚实的提醒 展开。两类的共同前提是 **Agent 只在只读侧协助，不进生产流程**。

---

### 案例一（模式①：广度优先的只读取证）：并行探索多条方案的调研与决策

**痛点**

调研类任务是广度优先的：要在大量来源里找信息，还要避免过早收敛。单 Agent 串行检索有两个毛病——慢，且上下文很快被低信噪比的原文填满；更要命的是它一旦形成初步结论，就会停止探索其他方向。

**为什么多 Agent 能解决**

这是各家权威来源口径最一致的一个受益区。多个检索 Agent 分头深挖不同方向，各自在干净上下文里处理大量原文，**只回传压缩后的摘要**；主干上下文因此保持精炼，而覆盖面成倍扩大。并行还直接压缩了墙钟时间。

前提是**只读**：这类任务不产生写冲突，是所有来源公认的安全区。

**角色划分**

| 角色 | 职责 |
|------|------|
| 规划 Agent | 把问题分解成 N 个**正交**子问题（按方向、来源类型、时间段、地域切分） |
| 检索 Agent ×N | 各自深挖一个子问题，就地压缩成一两千 token 的结构化摘要 |
| 交叉核对 Agent | 检查各路结论是否互相矛盾，引用是否真实可溯源 |
| 汇总 Agent | 在汇总证据上形成结论，标注置信度与分歧点 |

**协作方式**：扇出 → 扇入。规划 Agent 负责保证子问题正交（不重叠、不遗漏），交叉核对 Agent 负责处理各路结论打架的情况。

**典型案例**：竞品与技术选型调研、文献综述、市场进入研究、投资尽职调查（财务、法务、技术、市场四条线分头推进）、政策与合规影响排查。

**诚实提醒**

这类收益**只对广度优先、可并行的任务成立**。同样的架构搬到需要紧密共享上下文的任务上（比如协同改一份代码、合写一份强一致性的文档），效果会变差甚至变糟。此外，有研究在控制算力预算的条件下对比单 Agent 与五种多 Agent 架构（sequential / debate / ensemble / parallel roles / subtask-parallel），发现单 Agent 在多跳推理任务上**持平甚至更优**【A，Tran & Kiela，转引自二手教材章节，建议核对原文】——部分"多 Agent 更好"的结论，可能只是多消耗了算力。

**模式①的有条件子集：限定分支后的根因取证（RCA）**

质量根因分析的取证阶段常被当作"最典型的必拆场景"，**复核后要打折**：真实 RCA 是序贯、假设驱动的，各条线索（如 5M1E 六条线）**并不独立**——发现设备参数漂移会改变对物料批次的取证策略，盲目全开并行会在注定废弃的分支上浪费取证，无效结果还会挤占后续上下文；取证延迟也主要在数据查询而非 LLM 推理【推】。因此它只在满足三个条件时成立：**① 先 narrowing，把假设限定在 2–4 条；② 并行度按假设分叉动态决定，不是固定 N 路；③ 前置数据就绪度评估**（原始记录是否绑定参数与版本快照、批次绑定是否完整——数据不全时任何架构都做不出根因）。**它是模式①的子集，不是第三类受益场景。**

### 案例二（模式② 的对抗形态，成立前提只有 C8）：对抗式评审与多方博弈推演

**痛点**

高风险产出（安全方案、投资决策、合规判断、合同条款）需要有角色专门唱反调。单 Agent 不会真心反对自己——它生成的方案，它自己审，天然倾向于自洽而非证伪。

**为什么多 Agent 能解决**

角色化对抗能**强制展开反面论证**：反对方的目标函数被显式设为"找出这个方案不成立的地方"，因此会去搜索提案方不会主动去看的证据。

在博弈与谈判推演里，多角色更是天然需求：买方有底价、卖方有成本、监管有底线，各方的**信息与目标本就不对称**，用不同 Agent 承载不同立场，才能模拟出真实的博弈过程。

**角色划分**

| 场景 | 角色 |
|------|------|
| 方案评审 | 提案方 / 红队（反对方）/ 裁判（汇总并定级风险） |
| 博弈推演 | 各方 Agent 各持私有信息与目标函数 / 环境 Agent 提供规则与反馈 / 观察者 Agent 汇总均衡结果 |

**典型案例**：安全架构红队评审、投资委员会多空辩论、合同条款的双方立场推演、定价策略博弈、危机公关预案压力测试。

**诚实提醒**

这一类的实证结果**最混杂**，要特别小心：

- 有研究在控制算力预算后发现，多 Agent 辩论并不稳定优于单 Agent【A，转引自二手教材章节，建议核对原文】。
- 同质 Agent 之间会形成"回音室"：多数派观点被不断强化，即使它是错的——这在学术上被称为**信念固化**（belief entrenchment）【A，TACL】。
- 因此，**反对方必须拿到不同的输入**：不同的数据源、不同的分析框架、不同的历史案例库。仅仅在同一个 prompt 后面加一句"请你唱反调"，得到的多半是换个说法的重复，而不是真正的反驳。**判定规则**：数据源与方法都相同 → 判为回音室与信念固化，**不拆**；改用单 Agent + 外部数据源工具做规则化反证检索，成本更低、结果更可复核。
- 博弈推演同理：只有当各方的**私有信息与目标函数确实不同**（买方底价 / 卖方成本 / 监管底线）时，分 Agent 承载立场才有意义；否则它只是把同一个模型跑了几遍。

## 四、成本与适用边界

### 4.1 必须计入的成本

| 成本项 | 量级 |
|--------|------|
| Token 消耗 | 约为单 Agent 的**一个数量级**【B】 |
| 协调复杂度 | 交互点按组合数增长（4 个 Agent 6 个交互点，10 个 45 个）【C】 |
| 端到端可靠性 | 每步 95% 可靠，10 步链剩 59.9%，20 步剩 35.8%【推，算术演示】 |
| 调试成本 | 需要全链路 trace 与单 Agent 独立回放能力，否则无法定位 |
| 契约治理 | Agent 之间传递结构化产物需要稳定的 schema，这是持续的维护成本【推】 |
| 安全面 | Agent 间通信通道成为新的注入载体【B/C】 |

### 4.2 明确的适用边界

不该用 Multi-Agent 的情况，前面 2.3 已经列了六条，这里补充一条**时间维度**上的：

**模型能力在快速进步，会持续吞掉编排类用例。** 今天需要精心设计多 Agent 才能完成的任务，下一代模型可能单 Agent 就足够。所以架构上要预留回退路径，并定期用评测集复测——**别把架构锁死在今天的模型能力上**。

## 五、落地路径建议

1. **从单 Agent + 工具起步。** 所有新功能默认单 Agent，工具集按业务域组织。
2. **先做上下文工程。** 工具分层路由、参数程序化校验、即时检索（上下文只存引用、用时再取）、定期压缩、结构化笔记外置、外部化状态。这些手段做完，大多数"必须拆"的场景会自然消失。
3. **建离线评测集。** 这一步无法跳过：没有它，就无法证明"拆了更好"，很容易把"多烧了算力"误判成"架构更优"。
4. **只对只读的并行环节引入子 Agent。** 深挖脏活用子 Agent 做上下文隔离，严格限定只读。
5. **角色化多 Agent 也只做协助。** 角色限于取证、独立校验与评审，全程只读，产出证据、结论与建议；生产动作仍由既有系统与人在正式流程里完成。每个 Agent 写清角色、工具白名单、停止条件、预算上限；每个子 Agent 的输出都要有基于外部证据的独立校验。

## 小结

判断要不要 Multi-Agent，看的不是"任务重不重要""听起来先不先进"，而是三条硬判据：**C1' 工具或知识域冲突且分层路由解决不了、C3' 存在真正独立的子任务且延迟是真瓶颈、C8 存在信息或能力的不对称。**

其中 C8 最容易被忽略，也最决定成败：**如果多个 Agent 看到的是同一份信息，它们其实还是一个 Agent，只是贵了好几倍。** 多 Agent 的收益来源从来不是"多几个角色"，而是**不同的上下文、不同的工具、不同的证据**。

真正受益的**只有两类模式**：**① 广度优先的只读取证**（命中 C3'，如并行调研、影响面清点）、**② 带外部证据的生成-验证**（命中 C8，如对抗式评审与博弈推演）。本文的两个案例是这两类的实例，**不存在两类之外的独立受益场景**；**限定分支后的 RCA 取证**是模式①的**有条件子集**（先 narrowing、并行度按分叉动态决定、前置数据就绪度评估），也不独立成一类。共同点只有两条——**要么能真并行、要么能引入新信息**；都不占的，单 Agent 就够了。

**前提始终是：Agent 只做协助**——产出证据、结论与建议，不进入生产流程、不落地生产动作。

而成本这边要清醒：一个数量级的 token、组合数增长的协调复杂度、每步相乘的错误率、以及被扩大的攻击面。在动架构之前，先把上下文工程做扎实、把离线评测集建起来——**能证明"拆了更好"再拆**。
