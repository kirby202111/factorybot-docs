# 车间 MES 中的 Multi-Agent 真实业务场景详解

> **业务设定**：面向 SMT/PCBA + 整机装配的两段式车间，航空制造背景（结构件、蒙皮类零件的超差与追溯要求）。系统按三个核心服务划分——制造资源服务（物料、工艺管理、质量）、设备管理服务（台账、数据接入、点检保养、计量检定、维修）、生产执行服务（工单管理、在制品执行、首件处理、返修、返工、排产）。
>
> **统一的业务背景模板**：每个场景按 **业务背景 → 用户角色与核心诉求 → 现状与痛点 → 引入后的完整流程 → 关键数据流转 → 可衡量的业务价值 → 边界** 展开。
>
> **两点前置声明**：
>
> 1. **不是所有 MES 模块都需要 Multi-Agent。** 按 [独立复核](./Multi-Agent必要性-独立复核与批判.md) 的结论，车间里真正站得住的多 Agent 用法集中在：**广度优先的只读取证**、**带外部证据的独立审核**、**证据层面的对抗评审** 三类。换线编排的主体应是工作流引擎，设备诊断的主体应是单 Agent + 工具，本会在对应场景里明确标出。
> 2. **文中的所有数字都是目标示例值**，用于说明该衡量什么、量级大概在哪，**不是行业基准**。真实目标请用你自己两周的基线校准。
>
> **贯穿所有场景的硬约束**（来自你的领域设计）：
> - 过点引擎 P99 ≤ 200ms，判定走规则引擎，**任何 Agent 不得进入过点主事务**、不得调放行/拦截 API。
> - 涉及工艺时必须带 `routeVersion` 过滤，否则会基于已失效工艺给出结论。
> - 任何写操作只能产出 draft，落库走对应上下文的正常应用服务，过聚合根不变式与事务发件箱，**人在正式界面确认**。
> - Agent 可调工具 = 各限界上下文暴露的 toolset，**上下文边界即工具注册边界**。但**任务分解边界按"要回答的问题的结构"划分**，与工具注册边界正交——一个子 Agent 可同时挂载多个上下文的只读 toolset（详见场景二）。

## 场景一：SMT 换线（Changeover）编排 —— 多角色协作

### 业务背景

SMT 线每天换线 3–8 次，单次换线 20–45 分钟。一次换线要跨六个限界上下文：工艺管理（版本与参数核对）、物料（齐套与替代料）、点检保养（设备点检状态）、计量检定（钢网张力、仪器有效期）、设备工装台账（钢网/Fixture 准备）、首件处理（首件触发与放行门禁）。

换线时间里真正用于操作的不到一半，其余耗在**等待与协调**上：等点检结果、等物料、等工艺确认，以及发现漏项后的补救。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 产线线长 | 换线快，别卡在等待上；别漏项 | 换线时长、等待占比 |
| 操作工 | 明确知道下一步干什么 | 动作清晰度 |
| 工艺工程师 | 工艺版本与参数正确 | 版本错用次数 |
| 设备工程师 | 设备状态可用、点检未超期 | 因设备未就绪导致的换线中断 |
| 质量工程师 | 首件必须合格 | 首件一次通过率 |
| 物料员 | 料备齐、替代料合规 | 缺料导致的等待 |

### 现状与痛点

1. **依赖人工记忆 checklist**，漏项频发——钢网未清洗、Feeder 未校准、计量器具临期，都是到了首件才暴露。
2. **串行等待**：设备点检完了才发现工装没到位，物料齐套确认完才发现工艺版本没切换。**本可并行的准备项被串行执行**。
3. **信息分散在多个界面**，线长要在 MES、设备系统、物料系统之间来回切。
4. **异常无人升级**：料没到，谁去催？卡住就是干等。
5. **换线长流程状态无人维护**：跨小时、中间大量等待，一次中断就丢失上下文。

### 引入后的完整流程

**先明确架构分工——这是本场景最容易被做错的地方：**

| 层 | 归属 | 说明 |
|----|------|------|
| 流程编排（步骤、等待、升级、审批） | **工作流引擎**（状态机） | 不是 Agent。审批与等待是工作流引擎的原生职责 |
| 每个节点的检查与建议 | 独立单 Agent（无状态） | 每次新建，只处理当前节点 |
| **并行准备项检查** | **多 Agent（并行，只读）** | 本场景唯一真正需要多 Agent 的环节 |
| 首件判定与过点放行 | **规则引擎** | Agent 不介入 |

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 触发 | 工作流引擎 | 订阅换线工单事件，启动换线状态机 | 确定性 |
| 1. 并行只读检查 | **4 个 Agent 并行** | 工艺版本核对 / 点检与计量状态 / 物料齐套与替代料 / 工装钢网准备，各绑对应上下文 toolset | **并行 + 只读** |
| 2. 汇总阻塞项 | 汇总 Agent（单） | 合并四路结果，输出阻塞项清单与责任角色 | 单 Agent |
| 3. 动作卡路由 | 工作流引擎 | 按角色推送动作卡（线长/物料员/设备工程师各收到自己那部分） | 确定性 |
| 4. 人工执行与回填 | 人 | 执行动作，状态回填状态机 | 人 |
| 5. 首件触发与判定 | 规则引擎 + 质量工程师 | 首件检验与放行门禁 | **确定性 + 人** |
| 6. 异常升级 | 工作流引擎 | 超时未完成的阻塞项按规则升级 | 确定性 |

**为什么这里需要多 Agent**：四个准备项**真独立**（拿掉"点检状态"，不影响"物料齐套"怎么查），且各自要查不同上下文、吞入不同原始数据。并行把原本串行的等待压成一次，这是真金白银的换线时间。

### 关键数据流转

```
换线工单下达事件
  → [工作流状态机] → 换线实例（步骤清单 + 责任人）
  → [4 路并行只读检查]
      ├ 工艺 Agent  → 工艺版本 + 参数核对结果（带 routeVersion）
      ├ 设备 Agent  → 点检/计量/工装状态清单
      ├ 物料 Agent  → 齐套状态 + 替代料合规性
      └ 工装 Agent  → 钢网/Fixture 准备状态
  → [汇总 Agent] → 阻塞项清单（阻塞项 + 责任角色 + 影响）
  → [动作卡路由] → 各角色动作卡 → 人执行 → 状态回填
  → [首件触发] → 首件检验（规则判定 + 质量工程师确认）→ 放行
```

关键 artifact 是**阻塞项清单**：每条必须带责任角色，否则动作卡无法路由，换线仍会卡在"不知道谁去办"。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 平均换线时长 | 从工单下达到首件放行 | 下降 |
| 换线中的等待占比 | 等待时间 / 总换线时间 | 显著下降（并行化的直接收益） |
| 漏项导致的返工次数 | 首件才发现准备项遗漏的次数 | 趋近于零 |
| 首件一次通过率 | 首件一次检验合格比例 | 提升 |
| 工艺版本错用次数 | 用了错误 routeVersion 投产的次数 | 趋近于零 |

### 边界

**编排主体是工作流引擎，不是 Agent。** 把"等待人工、超时升级、按角色审批"这些交给 Agent 协同来实现，会得到比 BPMN 更难调试、更难审计的系统。首件判定与过点放行走规则引擎，Agent 只推人侧动作卡，**绝不调放行/拦截 API**。

## 场景二：批次质量异常的根因分析与影响面清点 —— 并行探索

> 这是车间里**最值得上多 Agent** 的场景，也是最容易做错的场景。

### 业务背景

某 SMT 工单的焊接不良率从 0.3% 突增到 4.2%（AOI 检出）。质量工程师需要在几小时内回答两个问题：**根因是什么**、**影响范围有多大**。

取证要跨六个域：过点记录（哪个工序、哪个班次）、工艺版本（当时生效的 `routeVersion` 与参数规格）、物料批次（锡膏、PCB、元件批次与替代料）、设备参数（回流焊温度曲线、贴片机吸嘴与压力）、测试数据（SPI/AOI/ICT 分布）、环境与人员（温湿度、班次与资质）。

清点要跨五个系统：在制工单、线边库存、成品库、在途、已交付/客户现场。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 质量工程师 | 快速定位根因，别误判 | 根因定位时长、误判次数 |
| 工艺工程师 | 是不是工艺/参数被改了 | 根因命中率 |
| 设备工程师 | 设备有无异常 | 设备类根因发现率 |
| 生产计划 | 要不要停线、要不要重排 | 停线时长 |
| 物料/仓储 | 哪些批次要隔离 | 隔离范围准确性 |
| 客服/交付 | 已交付的是否要通知客户 | 客户影响漏报 |

### 现状与痛点

1. **人工跨 5–6 个界面串联取证**，耗时数小时到数天。
2. **单 Agent 串行取证慢**，且时序曲线、检验分布这类大体积原始数据会把上下文塞满，后面查的东西质量下降。
3. **确认偏误**：先怀疑锡膏，后面就一路查锡膏，其他方向根本没看——这是单 Agent 做 RCA 最致命的失效模式。
4. **工艺版本搞错**：用了当前版本而非生产时的 `routeVersion`，得出完全错误的根因。
5. **影响面清点易漏**：五个系统人工清点，尤其"在途"和"已交付"最容易漏，而航空场景下漏报客户是严重事件。

### 引入后的完整流程

**注意顺序：先 narrowing，再并行。** 直接六路全开是错的——真实 RCA 是假设驱动的，盲目并行会在注定废弃的分支上浪费取证。

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 现象刻画 | **确定性统计 + 单 Agent** | 确定不良的时空分布：哪个工单/班次/设备/时间段/缺陷类型/集中工序 | 确定性为主 |
| 1. 假设生成 | 单 Agent | 基于画像**收敛**出少量候选假设（通常 2–4 条，不是六条全开） | 单 Agent |
| 2. 并行取证 | **多 Agent 并行** | 每条假设一个取证 Agent，各绑对应上下文 toolset，**只回传结构化证据包**（含支持证据与反证据） | **并行 + 只读** |
| 3. 红队 | 红队 Agent | 专责找反例推翻假设 | **必须持有不同数据源或不同方法** |
| 4. 裁决 | Judge（单 Agent） | 综合正反证据排序，输出置信度 + 证据链；低置信度转人工 | 单 Agent |
| 5a. 候选对象集 | **确定性关联查询**（非 Agent） | 批次 → 关联的单件 / 工单 / 上料记录，产出**候选对象清单** | **确定性** |
| 5b. 五级并行清点 | **多 Agent 并行 ×5** | 在制 / 线边 / 成品库 / 在途 / 已交付，各自判定状态并输出清单与依据 | **并行 + 只读** |
| 6. 处置决策 | **单线程**：人或单个决策 Agent | 隔离范围、是否停线、是否返工、是否通知客户 | 单线程 |

**两个关键设计**：
- **红队必须拿到不同的东西**。如果红队与取证 Agent 用同样的工具看同样的证据，它的"独立"是假的，只是换个说法重复。真正的独立来自不同数据源（如用统计检验 vs 用语义检索历史案例）或不同方法。
- **清点完全程只读，处置必须回到单线程**。五个 Agent 绝不能各自写各自的处置结论。

#### 为什么按"五级"横向拆，而不是按模块纵向拆

影响面清点要回答的问题是：**受影响的件现在在哪、处于什么状态**。备选的两种拆法：

- **横向（采用）**：在制 / 线边 / 成品库 / 在途 / 已交付——按**物料的物理位置与生命周期阶段**拆。
- **纵向（不采用）**：过点模块 / 返修模块 / 工单模块 / 返工模块——按**系统模块**拆。

选横向不选纵向，有五条理由：

**1. 横向互斥且完备，纵向既不互斥也不完备。**

一个单件在某一时刻**只能**处于五级中的一级，且**必然**处于其中一级——这是可以直接相加的答案。而同一个物理对象会同时在多个模块里留下记录（过点记录、返修任务、工单归属都有它），纵向拆会重复计数，必须在汇总时去重。

**2. 纵向拆会系统性漏掉"在途"和"已交付"——这是航空场景的合规红线。**

"在途"（已发货未签收）和"已交付/客户现场"**根本不是 MES 的模块**，它们的数据在 ERP、物流、客服/售后系统里。按模块拆，这两级无处安放，会被直接漏掉。而在航空场景下，漏报客户是严重事件——**这两级恰恰是最不能漏的**。

**3. 纵向拆本质上是在用 Agent 做查询路由——而这活不该由 Agent 做。**

"批次 → 关联的单件/工单/上料记录"这一步，是**确定性的关联查询**。它按模块去查，只是查询路径恰好经过这些模块而已。这正应了本文边界里那条：**谱系追溯的图遍历是确定性图服务，不要包一层 Agent**。所以纵向拆错的不是"拆"，而是**用 Agent 拆了一个本该用确定性查询解决的问题**——它对应的是上表的 5a（确定性），不是 5b（Agent 并行）。

**4. 状态是跨模块推导出来的，不是某个模块直接存着的。**

一个件算不算"在制"，要综合过点记录（最后过点到哪道工序）+ 工单状态（是否完工）+ 是否有未闭环的返修任务。纵向拆会把这个推导推给汇总 Agent，让它在汇总层做带业务规则的判定（离线返修中的件算不算在制？），汇总层的上下文因此变复杂、判断变脆弱。

横向拆则让每个子 Agent 在自己干净的上下文里完成状态判定，只输出"数量 + 清单 + 判定依据"，**汇总 Agent 只做相加和分级**——关注点分离更干净。

**5. 输出结构要能直接驱动处置动作。**

清点的目的不是计数，而是触发不同的动作，而五级各自对应完全不同的动作与责任人：

| 级 | 处置动作 | 责任人 |
|----|---------|--------|
| 在制 | 停产 / 隔离 / 返工 | 线长、质量 |
| 线边 | 隔离退料 | 物料员 |
| 成品库 | 冻结发货 | 仓储 |
| 在途 | 拦截 / 召回 | 物流、客服 |
| 已交付 | 客户通知（合规） | 质量、客服 |

横向拆的输出可以直接映射成动作卡路由给对应责任人；纵向拆输出的是"过点模块 37 条记录"这种**没有业务语义**的中间量——还得先回答"这 37 条对应哪些件、这些件现在在哪"，多一层转换就多一处出错。

#### 什么时候纵向拆反而合理

保持诚实，纵向拆在另两类问题里是对的：

- **系统健康度盘点**：各模块的记录数、未闭环任务数、数据完整率——问题本身就是按模块提出的，纵向拆更简单。
- **按系统所有权分工**：各模块数据由对应团队负责，纵向拆便于定位与问责。

但它们都不是"影响面清点"。**拆分维度要对齐"要回答的问题的结构"，不是"系统的结构"。**

#### 由此澄清一处表述：工具边界 ≠ 任务分解边界

前面说"上下文边界即工具边界"，这指的是**工具注册**——按限界上下文注册可以避免工具集膨胀和术语串台。但**任务分解要按问题结构划分**，两者是正交的两个维度：

- 工具注册：按限界上下文划分。
- 任务分解：按要回答的问题的结构划分。
- **一个横向子 Agent 可以同时挂载多个上下文的只读 toolset**（例如"在制"这一级要同时查在制品执行上下文的过点记录和工单管理上下文的工单状态），只要这些工具服务于同一个子问题。

把这两件事混为一谈，正是会误以为"应该按模块纵向拆"的根源。

### 关键数据流转

```
不良率告警
  → [现象刻画 - 确定性统计] → 异常画像（工单/班次/设备/时段/缺陷类型/集中工序）
  → [假设生成 - 单 Agent] → 候选假设清单（2-4 条，每条注明需查哪个上下文）
  → [并行取证 ×N - 只读]
      └ 每条 → 证据包 { 支持证据, 反证据, 证据强度, 数据来源锚点 }
  → [红队 - 不同数据源/方法] → 反驳清单
  → [裁决 - Judge] → 根因排序 + 完整证据链 + 置信度
  → [影响面并行清点 ×5 - 只读] → 影响清单（在制/线边/成品库/在途/已交付，含批次与数量）
  → [单线程处置决策] → 隔离/返工/停线/客户通知 → **人工确认后落库**
```

关键 artifact 有两个：
- **证据包**：每条证据必须挂数据来源锚点（过点记录 ID、批次号、`routeVersion`），否则质量审计无法追溯。
- **影响清单**：五级分类必须齐全，航空场景下"已交付/客户现场"这一级是合规红线。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 根因定位时长 | 从告警到给出根因排序 | 从数小时/数天压缩到小时级 |
| 根因一次命中率 | 首次给出的根因经后续验证正确的比例 | 提升 |
| 影响面清点遗漏 | 事后发现漏掉的影响批次/数量 | 趋近于零 |
| 误判导致的处置成本 | 错误的隔离/返工/报废决策造成的浪费 | 下降 |
| 停线时长 | 从异常发现到恢复生产 | 下降 |
| 客户影响漏报次数 | 已交付批次未及时通知客户 | 趋近于零（合规红线） |

### 边界

- **过点判定与防错校验不上 Agent**（200ms 硬约束）。
- **谱系追溯的图遍历本身是确定性图服务**（where-used / where-from），不要包一层 Agent——那是纯开销。需要 Agent 的是查完之后的处置决策。
- **返工单/隔离单只能产出 draft**，落库走返工上下文的应用服务，过聚合根不变式与事务发件箱，人在正式界面确认。
- 数据不全时（如设备参数未采集、批次绑定缺失）这套架构也做不出根因——**先评估数据就绪度**。

## 场景三：月度产能与工时多源核对 —— 长链路数据处理与交叉验证

### 业务背景

车间月度核算要核对四套数据：**MES 报工工时**、**设备采集的有效运行时长**、**考勤系统的出勤工时**、**工单产出数量 × 标准工时**。四源口径天然不一致——设备开机 ≠ 运行 ≠ 有效加工；报工可能滞后或补录；标准工时本身有版本问题。

核对结果直接进成本核算与车间绩效，错了会影响成本归集和工时分摊。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 生产统计员 | 别让我逐条翻差异 | 核对工时、差异条数 |
| 车间主任 | 产能与绩效数据准 | 数据可信度 |
| 成本会计 | 成本核算有据 | 成本核算返工次数 |
| 工艺工程师 | 标准工时的版本与口径正确 | 标准工时争议次数 |
| 设备工程师 | 设备数据完整，别因采集断点背锅 | 数据完整率 |

### 现状与痛点

1. **链路长、错误复利**：取数 → 对齐 → 比对 → 找差异 → 归因 → 裁决 → 出报告，七步以上。单步 90% 可靠，五步后整体成功率只剩六成。
2. **自验自收**：用同一套逻辑取数又核对，口径错了发现不了。
3. **差异归因全靠人**：几百条差异逐条看，占了对账工时的大头。
4. **口径歧义每月重吵**：换线时间算不算有效工时？等料停机算谁的？每月重复讨论。
5. **设备采集有断点**，导致根本无法核对，却常在最后才发现。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 定口径 | 人 + 口径 Agent 辅助 | 确定本期口径规则，固化成**可执行的口径定义文件** | 半自动 |
| 1. 取数与清洗 | **代码 + 单测** | 四源抽取、标准化、入事实表；同时输出**数据完整率报告**（含采集断点清单） | **确定性** |
| 2. 独立重算 | 校验 Agent | 用**不同路径**重算关键指标：用工单过点记录反推工时 vs 用设备采集有效时长 vs 用考勤工时 | 验证核心 |
| 3. 差异检出 | **程序化比对** | 产出差异清单（工时差、产量差、影响工单） | **确定性** |
| 4. 归因 | 归因 Agent | 对每条差异分类：采集断点 / 跨月补报 / 换线未计入 / 标准工时版本错 / 真异常，并附证据 | Agent 判断 |
| 5. 裁决与固化 | 人 | 裁决口径争议，结果回写口径定义文件 | 人 |

**这套结构成立的真正原因**：校验方用**独立的计算路径**得到生成方拿不到的第二份结果。同一条路径算两遍不叫验证。

### 关键数据流转

```
四源原始数据（MES 报工 / 设备采集 / 考勤 / 工单产出）
  → [取数清洗 - 代码 + 单测] → 标准化事实表 + 数据完整率报告（含采集断点清单）
  → [多路径计算]
      ├ 路径 A：过点记录反推工时
      ├ 路径 B：设备采集有效时长
      └ 路径 C：考勤工时 × 产能系数
  → [程序化比对 - 确定性] → 差异清单（工时差 / 影响工单 / 差异样本）
  → [归因 Agent] → 分类后的差异清单（每条附证据与建议处置）
  → [人裁决口径争议] → 对账报告 + **口径定义文件（下月复用）**
```

关键 artifact 是**口径定义文件**：本月裁决的结果固化下来，下月直接复用，避免同一场争论每月重开。这一环容易被漏掉，但实际价值很高。

第二个关键 artifact 是**数据完整率报告**——必须在取数阶段就产出，否则到归因阶段才发现设备数据有断点，整轮核对白做。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| 月度核对人力投入 | 人天 | 大幅下降 |
| 核对周期 | 月末到出报告的自然日 | 从数天压到 1–2 天 |
| 差异归因准确率 | 归因结论经复核正确的比例 | 提升 |
| 成本核算返工次数 | 因工时数据错误导致的重新核算 | 下降 |
| 口径争议重复发生次数 | 同一歧义反复讨论的次数 | 趋近于零（已固化） |

### 边界

**取数、清洗、比对、断言全部用代码 + 单测。** 这条链路绝大部分是确定性的，把它整体 Agent 化是典型过度设计。Agent 只介入两个真正需要判断的窄环节：**口径歧义消解**与**异常归因**。标准工时计算、产能系数换算一律确定性实现。

## 场景四：作业指导书（SOP）批量更新与合规审核 —— 质量与效率的分层

### 业务背景

工艺版本生效（`ProcessRouteActivated`）后，受影响的工位 SOP 需要同步更新。车间几百个工位，SOP 必须与三件事一致：**工艺路线的参数规格**、**质量上下文的门禁与检验要求**、**设备的实际能力参数**。航空场景下还要符合客户规范与适航文件要求。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| 工艺工程师 | SOP 参数准确、可执行 | 参数一致性错误数 |
| 质量工程师 | 符合质量门禁与检验要求 | 质量规则冲突数 |
| 线长 / 操作工 | 看得懂、能照做，知道改了什么 | 变更点清晰度 |
| 培训 | 变更点说明齐全 | 培训遗漏 |

### 现状与痛点

1. **全量人工改**：慢，且容易漏掉受影响的工位。
2. **全量用强模型生成**：成本线性叠加；更糟的是参数与规则靠模型记忆生成，容易写出与工艺规格不符的数值。
3. **生成后与规格/规则矛盾**：SOP 写的参数与工艺路线里的规格值不一致——这在车间是直接导致批量不良的错误。
4. **变更点不清晰**：操作工不知道这次具体改了什么，容易沿用旧做法。
5. **一个隐藏陷阱**：如果按工位并行生成，各工位 SOP 会出现术语与参数口径不一致——**SOP 是强一致性文档，并行分章是有害的**。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 性质 |
|------|------|--------|------|
| 0. 影响识别 | **确定性** | 对比新旧工艺版本，确定受影响工位清单 | 确定性 |
| 1. 顺序生成 | 单 Agent | **按工位顺序生成**，全程共享已确定的参数表与术语表 | 单 Agent（**不并行**） |
| 2. 独立审核 | 审核 Agent | 带**外部证据**审核：查工艺路线参数规格、质量门禁规则、设备能力参数，逐项比对 | **多 Agent 的核心价值点** |
| 3. 程序化校验 | **确定性** | 必填字段、单位、数值范围、与规格值的逐项比对 | 确定性 |
| 4. 变更 diff | 单 Agent | 输出新旧 SOP 差异，用于培训与变更说明 | 单 Agent |
| 5. 人工确认发布 | 工艺 + 质量工程师 | 确认后发布 | 人 |

**为什么这里需要多 Agent**：审核方能拿到生成方**生成时不具备的外部数据**——工艺规格库、质量门禁规则、设备能力参数。这是判据三的纯粹形态。CRITIC 那类研究的结论很明确：审查的价值在于引入新信息，而不在于"再想一遍"。**让第二个 Agent 重读草稿是无效的。**

**为什么生成环节不并行**：SOP 前后工序的参数与术语必须一致，并行分章必然导致局部合理、全局不自洽。

### 关键数据流转

```
ProcessRouteActivated 事件
  → [影响识别 - 确定性] → 受影响工位清单
  → [顺序生成 - 单 Agent] → SOP 初稿（按工位，共享参数表与术语表）
  → [独立审核 - 审核 Agent + 外部规则库]
      ├ 查工艺路线参数规格 → 参数矛盾清单
      ├ 查质量门禁规则 → 检验要求缺失/冲突清单
      └ 查设备能力参数 → 超限项清单
  → [程序化校验 - 确定性] → 字段/单位/范围校验结果
  → [修订循环] → 修订后 SOP
  → [变更 diff] → 新旧差异清单（供培训与变更说明）
  → 人工确认 → 发布
```

关键 artifact 是**审核发现清单**：每条必须引用具体的规则条目或规格值来源（"SOP 写的 245℃ 与工艺规格 235±5℃ 冲突，见工艺路线 XXX 版本第 X 工序"），而不是"我觉得这里不合适"。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| SOP 更新周期 | 工艺生效到 SOP 全部发布 | 从数天压到当天 |
| 参数一致性错误数 | SOP 与工艺规格不符的项数 | 趋近于零 |
| 质量规则冲突数 | SOP 与质量门禁不符的项数 | 趋近于零 |
| 变更点遗漏 | 未向操作工说明的变更 | 趋近于零 |
| SOP 相关的人为失误 | 因 SOP 错误导致的现场操作失误 | 下降 |

### 边界

参数与规格的逐项比对、单位换算、数值范围检查**全部用确定性校验**。审核 Agent 必须查规则库，**不能凭模型记忆判断合规性**。发布闸门在人（工艺 + 质量双签）。

## 场景五：航空件超差处置的 MRB 评审 —— 对抗式评审

### 业务背景

飞机结构件/蒙皮加工出现超差（尺寸超差、表面缺陷、孔位偏差），需由 MRB（材料评审委员会）判定处置方式：**原样让步接收 / 返修后使用 / 报废**。

航空制造的特殊性在于：让步接收不是企业内部决定就完事——涉及**适航要求与客户规范**（波音、C919 等项目的客户批准），且决策影响飞行安全与交付节点。

### 用户角色与核心诉求

| 角色 | 核心诉求 | 关注的指标 |
|------|---------|-----------|
| MRB 工程师 / 质量经理 | 判定合规、风险可控 | 判定合规率、后期问题率 |
| 工艺工程师 | 能否返修、返修方案是否引入新风险 | 返修一次成功率 |
| 生产计划 | 交付压力，别动不动报废 | 交付达成率 |
| 客户代表 / 适航 | 让步接收需有充分依据并获批准 | 客户批准一次通过率 |

### 现状与痛点

1. **材料多、核查慢**：检验报告、三坐标测量数据、工艺规程、历史同类超差的处置记录、客户规范条款，人工读完要很久。
2. **评审意见趋同**：交付压力下，评审会容易整体倾向让步接收——大家都跟着"这个可以接受"的叙事走，缺少系统性的反面论证。
3. **反驳缺乏依据**：凭经验说"这个不能让步"，说不出具体条款，既说服不了审批方，也写不进评审纪要。
4. **历史同类案例检索不到**：知识散落在个人经验里，同样的超差上次怎么处理的没人记得。
5. **返修方案的风险未评估**：返修本身可能引入新缺陷（如补焊导致热影响区），但常被忽略。
6. **客户批准材料准备慢**：条款引用不准确，被打回重做。

### 引入后的完整流程

| 阶段 | 负责 | 做什么 | 关键约束 |
|------|------|--------|---------|
| 0. 超差解析 | 解析 Agent | 结构化：超差项、实测值、公差带、部位、对应工艺规程条款 | 输出结构化超差包 |
| 1. 提案 | 提案 Agent | 基于历史同类 + 工艺可行性，形成处置建议与依据（含返修方案） | 只看到超差包与历史库 |
| 2. 独立取证 | **红队 Agent** | 用**不同的数据源**取证：客户规范条款库、适航要求、历史同类的后续服役/后工序数据、返修历史成功率 | **数据源与提案方不同** |
| 3. 证据对抗 | 红队 vs 提案方 | 红队输出反驳清单，每条挂条款/数据锚点；提案方可在**证据层面**应辩 | 不是嘴仗，是证据对抗 |
| 4. 裁判与分级 | 裁判 Agent | 汇总正反证据，输出风险分级与争议点清单 | 中立 |
| 5. MRB 人工决策 | MRB / 客户代表 | 决策；需客户批准的走批准流程 | 决策权在人 |

**这套结构成立的真正原因**：红队拥有提案方**看不到的外部数据**——客户规范条款库、适航要求、历史同类的后续表现数据。

**反面警示**：如果红队只是换个 prompt 说"请你唱反调"、用的还是同一份超差包，得到的不是反驳，是换个说法的重复。同质 Agent 之间还会形成回音室，多数派观点被反复强化，即使它是错的——在交付压力下，这种回音室恰恰会集体倒向让步接收，风险最大。

### 关键数据流转

```
超差检验记录
  → [解析 Agent] → 结构化超差包（超差项 / 实测值 / 公差 / 部位 / 工艺规程条款）
  ├─ 提案路径 → 处置建议 + 依据 + 返修方案（基于历史同类库 + 工艺可行性）
  └─ 红队路径（外部数据源，提案方不可见）
        ├ 客户规范条款库 → 条款级限制
        ├ 适航要求 → 合规红线
        ├ 历史同类后续数据 → 同类超差的服役/后工序表现
        └ 返修历史成功率 → 返修方案的风险量化
  → [证据层面对抗与应辩]
  → [裁判 Agent] → 风险分级 + 争议清单 + 完整证据链（含条款锚点）
  → MRB 人工决策 → 客户批准（如需）
```

关键 artifact 是**条款锚点**：每一条反驳必须能指到具体的规范条款编号或历史案例编号，否则既写不进评审纪要，也过不了客户批准。

### 可衡量的业务价值（目标示例，需按基线校准）

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| MRB 评审周期 | 从超差发现到判定完成 | 缩短 |
| 材料准备工时 | 评审前的资料准备投入 | 下降 |
| 让步接收的后期问题率 | 让步接收件在后工序/服役中出问题的比例 | 下降（**最重要的指标**） |
| 报废误判率 | 本可返修/使用却判报废的比例 | 下降 |
| 客户批准一次通过率 | 提交客户批准一次通过的比例 | 提升 |
| 评审纪要可追溯性 | 判定结论挂条款/数据锚点的比例 | 接近 100% |

### 边界

最终判定权在人（含客户批准）。公差计算、尺寸链分析用确定性代码。适航与客户条款的引用必须可溯源到条款编号。**红队要设证据门槛**——没有条款或数据支撑的反驳不进入清单，否则噪音会淹没真信号，反而拖慢评审。

## 小结：五个场景的横向对比

| 场景 | 命中判据 | 成立的关键机制 | 不该 Agent 化的部分 |
|------|---------|--------------|-------------------|
| SMT 换线编排 | 真并行 + 上下文隔离 | 四个准备项真独立、并行只读检查 | **编排主体归工作流引擎**；首件判定与过点放行走规则引擎 |
| 批次质量异常 RCA | 真并行（取证与清点） | 先 narrowing 再并行；红队持不同数据源 | 过点判定；谱系图遍历用确定性图服务；处置落库走应用服务 |
| 月度产能工时核对 | 信息不对称（独立重算） | 多路径独立计算后比对 | 取数、清洗、比对、断言全部用代码 |
| SOP 更新与审核 | 信息不对称（外部规则库） | 审核方查工艺规格/质量规则，**生成环节顺序执行不并行** | 规格逐项比对、单位换算、范围校验 |
| MRB 超差评审 | 信息不对称（外部数据源） | 红队持客户规范/适航/历史服役数据 | 公差与尺寸链计算；最终判定与客户批准 |

**五条共性**：

1. **全部命中的是"真并行"或"信息不对称"，没有一个是靠"多几个角色"取胜的。** 红队若与提案方看同一份材料就不成立；核对若用同一条路径算两遍就不叫验证；RCA 若不先 narrowing 就六路全开，只是在浪费取证。

2. **确定性环节全部留在了代码和规则引擎里。** 五个场景里真正交给 LLM 的都是窄环节：假设生成、证据归因、语言生成、证据层面的对抗。过点 P99 ≤ 200ms 这条红线，五个场景都没碰。

3. **写操作与最终决策全部在人手里。** 换线放行、返工单落库、SOP 发布、MRB 判定——Agent 最多产出 draft 与建议。

4. **价值都落在"周期缩短"和"覆盖率/漏检率"上**，而不是"替代了某个岗位"。换线省的是等待时间，RCA 省的是取证时间与漏检，核对省的是人力与周期，SOP 省的是更新周期与一致性错误，MRB 省的是材料准备与后期问题。

5. **两个场景里"不该并行"的地方被特意标了出来**：换线的编排主体归工作流（不是多 Agent），SOP 的生成环节顺序执行（不能分章并行）。这两处是最容易照搬通用做法而做错的地方。

**最后重复一遍**：文中的所有数字都是**目标示例**，用于说明该衡量什么。真实目标请用你自己两周的基线校准——**没有基线，就无法把"多烧了算力"和"架构真的更优"区分开。** 而在这五个场景动工之前，建议先做一次数据就绪度盘点：过点记录是否绑定了设备参数与 `routeVersion`、批次绑定是否完整、设备采集是否有断点——数据不全时，任何架构都做不出正确的根因与影响面。
