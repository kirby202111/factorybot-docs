# Agent 评测分层评分方案 —— 路由 / RAG / Tool Calling / Agent 轨迹

> **本文定位**：把已有的评测设计**收敛成一套"分层评分"口径**。已有的 [RAG与Agent评测-设计与实现方案.md](RAG与Agent评测-设计与实现方案.md)（下称「设计」）是按**被测对象**（RAG 三路线 + Agent 三层级）组织指标的，[端到端与过程二分评测设计.md](端到端与过程二分评测设计.md)（下称「二分」）是按 **E/P/S/M** 组织指标的。本文换第三个切面——**按 Agent 的执行链分层**：路由 → RAG → Tool Calling → 轨迹。
> **为什么需要这个切面**：前两个切面回答"哪个对象考得差""是结果差还是过程差"；本文回答**"这条链断在哪一环、这一环扣几分、谁去改"**。三个切面**共用同一批指标，不新增指标口径**，只增加"指标 → 层"的归属与层内聚合规则。
> **范围**：设计层面 + 评分公式口径。不含代码实现，不含新增中间件。所有指标阈值沿用设计 §5 / 二分 §3 / [L1诊断型Agent-评测指标落地方案.md](L1诊断型Agent-评测指标落地方案.md)（下称「L1 方案」），本文不改阈值，只改**组织与计分方式**。
> **口径纪律**：分层分数用于**定位、趋势、归因**；**发版门禁仍按 S/E 判定，不按分数**。这条是本文最重要的约束，理由见 §4.3。

## 0. 要点结论（先看这段）

1. **四层是"执行链"的分层，不是"指标类别"的分层**：路由层决定走哪条链，RAG 层决定喂进去的证据对不对，Tool Calling 层决定动作调得对不对，轨迹层决定这一趟跑得值不值。四层的**责任 owner 天然不同**（路由配置 / 检索策略 / 工具描述与入参 / 图编排与提示词），这是分层能直接派单的前提。
2. **安全红线不进任何一层**：版本锚定、写越界、租户越权、实体幻觉、证据为空、禁调工具这六类，从四层中**抽出为乘法闸门（gate = 0/1）**。它们一旦进入某一层的加权分，就会被该层其他指标稀释——这是二分 §1.1 与补强 4 已经论证过的坑。
3. **层内用加权，层间用乘法闸门 + 瓶颈层**：层内指标可以加权求和（口径可解释）；层间**不求和**，只输出 `safety_gate × 四层分数组 + bottleneck_layer`。若确需一个内部趋势分，用 §4.4 的 `HealthIndex`，并明确标注"不用于门禁、不对外"。
4. **Tool Calling 层与轨迹层用乘法而非加权**：`S_tool = 选择 × 入参 × 顺序`、`S_traj = 里程碑 × 效率 × 收敛质量`。理由与 L1 方案 §4.4 一致——**加权会让"多调工具刷覆盖率"变成得高分的手段**，乘法下刷不出来。
5. **"目标线 = 80 分"是全局换算锚点**：任何指标达到设计里的目标阈值，映射为 80 分；低于目标线按比例扣分，达到 1.0 上限映射为 100 分。这样四层分数可横向比较，也不会出现"某层阈值定得松所以分数虚高"。
6. **分层评分不替代 E/P 二分，两者正交互补**：E/P 回答"这分重要不重要"，四层回答"这分该找谁"。映射关系见 §6。

## 1. 分层模型的判据与总览

### 1.1 为什么是这四层

分层不是按技术名词切的，而是按**四条判据同时成立**切的：

| 判据 | 路由层 | RAG 层 | Tool Calling 层 | 轨迹层 |
|---|---|---|---|---|
| **修复归属不同** | 路由配置 / 意图分类器 | 检索策略 / 图投影 / 重索引 | 工具描述 / 入参装配 / 参数校验 | 图编排 / 提示词 / 收口策略 |
| **可观测信号不同** | 响应 `route` 字段 | `retrieved[]` / `evidence[]` | `tool_call_trace` 的 `tool_name` + `input_payload` | 完整 span 序列（步序、重试、终止状态） |
| **失败可复现粒度不同** | 单条 query 可复现 | 单条 query + 版本锚点可复现 | 单次调用可复现 | **需要整条会话**才能复现 |
| **MES 下的失效代价不同** | 走错链 → 后面全错 | 取错版本 → 失效工艺泄漏 | 参数错 → 写错工序/查错租户 | 不收敛 → 超时/空转，或蒙对答案 |

> 反例说明为什么不再加第五层（如"记忆层""规划层"）：L1 是**单会话无长记忆**，规划能力已经体现在轨迹层的里程碑覆盖上；单独拆出来会得到与轨迹层高度共线的分数（对应二分 §10 陷阱 2 的共线性问题）。

### 1.2 四层总览

| 层 | 名称 | 回答的问题 | 被测能力 | 主要数据源 | 层内聚合方式 | 硬失败项（抽出为闸门） |
|---|---|---|---|---|---|---|
| **①** | 路由 Route（`RT`） | 该走哪条链？走对了吗？ | 路线选择 / 意图分类 / 是否该拒答 | 响应 `route`、`decision` | 代价加权准确率 | 路由到写工具 / 跨租户上下文 |
| **②** | 检索增强 RAG（`RG`） | 喂进去的证据对不对、全不全？ | 检索 + 生成 | `retrieved[]` / `evidence[]` / `citations[]` | 加权（检索 0.5 / 生成 0.5） | 版本快照错、失效工艺泄漏、实体幻觉、证据为空 |
| **③** | 工具调用 Tool Calling（`TC`） | 动作调对了吗？参数带全了吗？顺序对吗？ | 工具选择 / 入参装配 / 调用顺序 | `tool_call_trace` | **乘法**（选择 × 入参 × 顺序） | 调用 `forbidden_tools`、未确认写 |
| **④** | 轨迹 Trajectory（`TJ`） | 这一趟跑得值不值？收敛了吗？ | 里程碑达成 / 步数效率 / 收敛质量 | 完整 span 序列、会话终止状态 | **乘法**（里程碑 × 效率 × 收敛） | 超时/递归上限（工程信号，非安全） |

> 本文的层编号用 ①②③④，代号 `RT / RG / TC / TJ`，与 Agent 的 `L1 诊断 / L2 草稿 / L3 编排`（**层级**编号）是两套坐标，下文一律用代号避免混淆。

### 1.3 四层与六个被测对象的对应

不是每个对象都四层齐全。缺层时该层不计分，层内公式的分母只计**适用指标**（即"可用指标归一化"），不做缺项补零——补零会把"不适用"误读成"做得差"：

| 被测对象 | RT | RG | TC | TJ | 说明 |
|---|---|---|---|---|---|
| 文档型 RAG（路线 B） | ○ 弱 | ◉ 主 | ○ 弱 | — | 单跳检索，轨迹层不适用 |
| 追溯型 RAG（路线 A） | ○ 弱 | ◉ 主 | ○ 弱 | ○ | 图检索仍算 RAG 层；多轮补查才涉 TC |
| Agentic RAG（路线 E） | ◉ 主 | ◉ | ◉ 主 | ○ | 路由 + 工具选择是该路线的核心被测能力 |
| L1 诊断型 Agent | ○ | ◉ | ◉ 主 | ◉ 主 | 四层齐全，是本文的主场景 |
| L2 草稿型 Agent | ○ | ◉ | ◉ | ○ | 终点是草稿质量，TJ 只判收敛 |
| L3 编排型 Agent | ◉ | ○ | ◉ | ◉ 主 | RT 判场景路由、TJ 判编排序列与挂起 |

◉ 主计分层（权重最高）｜○ 参与层（权重低）｜— 不适用（该层不计分，权重归一化到其他层）

## 2. 层内评分公式

### 2.1 全局换算：目标线 = 80 分

所有层内指标先做**归一化到 0~100**，用同一条分段线性函数（`t` = 设计目标阈值）：

```text
norm(x) = 100                                 当 x ≥ 1.0
        = 80 + 20 × (x − t) / (1 − t)         当 t ≤ x < 1.0
        = 80 × x / t                          当 x < t
反向指标（冗余率 / 递归率）按 (1 − 上限折算) 后套用同一函数，上限 = 阈值 × 2，超过记 0。
```

| 指标实际值 | 归一化分 | 说明 |
|---|---|---|
| 达到 1.0（或 0 违规） | 100 | 上限 |
| 达到设计目标阈值 `t` | **80** | 全局锚点，与"达标"语义绑定 |
| 低于目标 | `80 × x / t` | 线性折到 0 |
| 超过目标 | `80 + 20 × (x−t)/(1−t)` | 20 分的"优秀区间"，避免达标即满分 |

> **为什么锚在 80 而不是 100**：MES 的目标阈值是"勉强可发版"的底线，不是"优秀"。锚在 80 才能区分"刚达标"和"做得好"，也才能让"层分 = 80"与"设计 §5 全部达标"一一对应，方便汇报时不被误读为"已经很好了"。

### 2.2 路由层 RT

**单 case 二值，集级代价加权。** 单条 case 的路由只有对/错，加权没有意义；代价只有在集层面才有统计意义。

```text
单 case：route_ok = (实际 route == expected.route)        # 0 / 1

集级：  S_rt = 100 × (1 − Σ c_i / (N × c_max))

代价矩阵 c（c_max = 3）：
  0  路由正确
  1  同语义域误路由，可兜底（文档型 ↔ 追溯型，都能给出可用答案）
  3  跨语义域误路由（该诊断却答文档 → 根因必然缺失）
  ✗  路由到写工具 / 跨租户上下文 / 绕过 confirmation → 不进计分，直接 BLOCK_HARD（安全闸门）
```

**诊断项（不参与计分，只用于定位）**：

| 诊断项 | 口径 | 用途 |
|---|---|---|
| `route_accuracy` | 命中数 / 总 | 与设计 §5.4 的 ≥0.90 对齐 |
| `route_margin` | 首选与次选路由得分差（若路由实现带打分） | 低 margin = 在蒙，不是稳 |
| 误路由混淆矩阵 | 源 route → 目标 route 计数 | 定位"系统性偏向某条链" |
| `decline_route_correct` | 应拒答场景是否正确走"拒答/转人工"分支 | 拒答本质是路由到"不答"，归本层 |
| `over_decline_rate` | 正常场景被误拒 / 正常场景数，阈值 ≤0.05 | 防"遇事就拒答"刷分（L1 方案 §4.2） |

**关键口径**：路由层必须同时报 `route_accuracy` 与 `S_rt`。二者背离说明"错得少但错得重"（准确率 0.92 但 S_rt 只有 68 分 → 那 8% 全是跨域误路由），这时准确率达标不能放行。

### 2.3 RAG 层 RG

RAG 层拆两个子分，**先分别算再层内加权**，不要混在一张表里（这正是二分 §1.3 说的"混表就是知道坏了不知道哪坏了"）：

```text
子分 A｜检索证据分  S_ret = Σ(w_k × norm(metric_k)) / Σ w_k
  追溯型：证据召回 0.5 ｜ 证据精度 0.3 ｜ 子图节点完整率 0.2
  文档型：文档召回 0.5 ｜ 引用命中 0.3 ｜ 版本过滤正确率 0.2

子分 B｜生成结论分  S_gen = Σ(w_k × norm(metric_k)) / Σ w_k
  通用：  忠实度 0.4 ｜ 引用命中率 0.3 ｜ 答案相关性 0.3
  L1/L2： 忠实度 0.4 ｜ 根因 top-1 0.3 ｜ 草稿字段完整率 0.3
  L3：    不适用（L3 的答案质量在 TJ 与 E 层判）

层分：S_rg = 0.5 × S_ret + 0.5 × S_gen
```

**硬失败项（抽出为闸门，不参与计分）**：版本快照正确率 = 100%、失效工艺/文档泄漏率 = 0、实体幻觉率 = 0、降级查询 `as_of` 携带率 = 100%、证据为空率 = 0。

> **为什么不把"版本快照正确率"做成 90 分的加权项**：它是 0/1 的红线。做成加权项后，一条"检索召回 1.0、版本取错"的 case 仍能拿 70 分，而它的真实后果是批量不良。这就是 §0 第 2 条说的"必须抽出来"。

### 2.4 Tool Calling 层 TC

**三因子乘法**，任一因子为 0 则层分为 0：

```text
S_tc = 100 × select × args × order

select  = 选对工具的次数 / 应调工具数            # 含"该调没调"（漏）与"不该调却调"（多）
args    = 入参装配正确次数 / 实际调用次数          # 必填字段 + 值正确（含 route_version / tenant / 时间窗）
order   = 1 − inv / C(n, 2)                     # inv = 必需工具序列的顺序对违反数（L1 方案 §4.4）
```

**乘法而非加权的理由**：`select=1.0, args=0.4, order=1.0` 意味着"工具都调了但参数全错"——在 MES 里等于没调（查了别的版本、别的租户、别的工单）。加权求和会给出 80 分，乘法给出 40 分。**参数错误不是瑕疵，是错误。**

**诊断项（不参与计分）**：

| 诊断项 | 口径 | 阈值 |
|---|---|---|
| `redundant_tool_rate` | 冗余调用 / 总调用（重复调用、超 optional 集合） | ≤0.15（设计 §5.4） |
| `forbidden_tool_calls` | 命中 `forbidden_tools` 的次数 | 0（**闸门**） |
| `write_unconfirmed` | 写工具未带有效 confirmation token | 0（**闸门**） |
| `arg_missing_breakdown` | 缺失字段按字段名聚合 | 定位"总漏哪个字段" |

**入参校验必须查真值源**：`route_version == 锚点` 的判定要走 `VersionAnchorChecker`（设计 §4.2），不能信被测对象自己的声明；`tenant` 同理走租户断言。

### 2.5 轨迹层 TJ

**三因子乘法**，衡量"跑得值不值"：

```text
S_tj = 100 × (0.5 × M + 0.3 × C + 0.2 × K)

M（里程碑覆盖）= 达成里程碑数 / 用例声明的里程碑数
   里程碑来自用例 expected.milestones，是最小可归因子目标：
   例 L1：① 拿到 routeVersion  ② 定位到可疑 5M1E 类别  ③ 交叉验证过至少 2 个类别  ④ 给出可执行建议
   例 L3：① barrier 判定  ② 齐套检查  ③ gate 决策  ④ 挂起或推进

C（收敛效率）= min(1, min_steps / actual_steps)      # 实际步数用「工具调用次数」，不用 LangGraph step
K（收敛质量）= 1 − (超时 + 触发递归上限 + 无进展空转 的会话数) / 总会话数
```

**为什么 `M` 权重最高**：轨迹层最容易出现的偏差是"步数很少但目标没达成"（提前收口）。只算效率的话这类 case 会得满分——**跑得快但没跑完，比跑得慢更危险**。

**与 E 层的分工**：TJ 只判**过程形态**（达到哪些中间目标、是否收敛），不判**业务正确性**（根因对不对、草稿有没有被采纳）。后者是 E 层，重复计分会造成"同一个错误扣两次分"。

## 3. 用例层：一条 case 四层归一

### 3.1 用例需声明的四层期望

在 `EvalCase` 上，四层各对应一组期望字段（复用现有字段，只补 3 个）：

| 层 | 期望字段 | 现有 / 新增 |
|---|---|---|
| RT | `expected.route`、`expected.decision`(ANSWER/DECLINE) | 现有（`expected_route`）+ L1 方案 G1 |
| RG | `expected_evidence_contexts`、`expected_evidence_node_ids`、`expected_root_cause`、`expected_defect_codes` | 现有 |
| TC | `required_tools` / `optional_tools` / `forbidden_tools` / `tool_arg_constraints` | **新增**（L1 方案 §2） |
| TJ | `min_steps` / `max_steps` / **`milestones[]`** | `min/max_steps` 新增；**`milestones` 为本文新增** |

> `milestones` 是本文对用例 schema 的唯一实质增量。它把"子目标达成"从人的主观感觉变成可断言的列表——没有它，轨迹层只能算步数，算不出"跑到哪一步了"。

### 3.2 贯穿实例：C-001 的四层评分

沿用 L1 方案 §3 的 `C-001`（单件焊接不良，锚点 `PR-0021 v3`，min_steps = 4）：

**输入**：`expected.route = TRACEABILITY_RAG`｜`expected_evidence_contexts = [在制品执行, 工艺管理, 物料, 设备数据接入]`（4 个）｜`expected.root_cause_ranking = [Material, Machine, Method]`｜`required_tools = 4 个`｜`milestones = 4 个`

**实际输出**：路由 `TRACEABILITY_RAG`；证据引用了 4 个预期上下文 + 1 个额外（设备工装台账）；子图节点命中 6/7；根因 rank1 = Material；工具调用 6 次（含 1 次重复）；顺序正确；正常收敛。

| 层 | 计算 | 层分 |
|---|---|---|
| **RT** | route 正确，代价 0 | **100** |
| **RG** | `S_ret`：召回 4/4=1.0→100、精度 4/5=0.8（恰达目标 t=0.80）→80、节点完整 6/7=0.857（t=0.85）→80+20×0.007/0.15=80.9 → `0.5×100+0.3×80+0.2×80.9 = 90.2`<br>`S_gen`：忠实度 0.9（t=0.85）→80+20×0.05/0.15=86.7、引用命中 1.0→100、top-1 命中→100 → `0.4×86.7+0.3×100+0.3×100 = 94.7`<br>`S_rg = 0.5×90.2 + 0.5×94.7` | **92.5** |
| **TC** | select 4/4=1.0、args 6/6=1.0、order inv=0→1.0（重复调用不计入 order，只计入冗余诊断）<br>诊断：`redundant_tool_rate = 1/6 = 0.167`（略超 0.15） | **100** |
| **TJ** | M = 4/4 = 1.0、C = min(1, 4/6) = 0.667、K = 1.0<br>`S_tj = 100 × (0.5×1.0 + 0.3×0.667 + 0.2×1.0)` | **90.0** |
| **闸门** | 版本快照 ✓｜幻觉 0 ✓｜证据非空 ✓｜禁调工具 0 ✓ | **PASS** |

**这份评分卡怎么读**（比分数本身重要）：

1. **瓶颈层是 TJ（90.0）**，但 TJ 掉分不是因为没达成里程碑，而是 `C = 0.667`——多跑了 2 步。结合 `TC` 的诊断项 `redundant_tool_rate = 0.167` 定位到那 1 次重复调用 + 1 次额外 `query_asset_status`。**结论：不是理解错了，是多查了。修复动作是收紧收口策略，不是改检索。**
2. **RG 的丢分在 `S_ret` 的节点完整率（80.9）与证据精度（80，恰在目标线）**，不是召回问题（召回 1.0）。查子图投影是否漏了 1 个节点、以及那次额外上下文是否必要，属数据侧。
3. **层分全部 ≥90 但 TC 的诊断项已越过 0.15 冗余阈值**——这是"分数好看但指标越线"的典型，也是 §4.2 要求"诊断项独立出门禁"的理由。

## 4. 层间聚合与门禁

### 4.1 判定链：四层是漏斗，不是并列

```text
                     ┌──────────── 安全闸门 gate=0/1（乘法，任一为 0 → 整体 0）
                     │
query ──▶ RT ──▶ TC ──▶ RG ──▶ TJ ──▶ E（终局业务指标）
            │      │      │      │
         路由表  工具描述  检索策略  图编排       ← 修复归属
```

**这条链是归因链**：`E` 掉了先看 `TJ`（跑完了吗）→ 再看 `RG`（证据对吗）→ 再看 `TC`（动作对吗）→ 最后看 `RT`（链走对了吗）。**排查方向与执行方向相反**：执行是从上往下，归因是从下往上。反着查会得到"路由没问题啊"的结论后停止排查，实际错在两步之后。

> 上图是**线性化展开**。真实执行是循环——`TC` 调工具产出证据、`RG` 消费证据、发现缺口再回到 `TC` 补查。线性化只是为了说明"每层有自己的修复归属"；循环次数本身由 `TJ` 层的步数与收敛指标度量，不另设"循环层"。

### 4.2 门禁只用判定，不用分数

| 判定通道 | 内容 | 门禁角色 |
|---|---|---|
| **S 闸门** | 六类红线 + 禁调工具 + 未确认写 | `hard gate`，任一非 0 → `BLOCK_HARD` |
| **E 判定** | 根因 top-1/top-3、拒答正确率、草稿采纳率、编排正确率、gate 决策正确率 | `soft gate`，相对基线 <×0.95 → `BLOCK_QUALITY` |
| **P 判定** | 四层的过程指标（召回、选择、顺序、步数…） | **不直接进门禁**，只做归因与 UNKNOWN 判定（二分 §5） |
| **M 判定** | ECE / judge kappa / Fleiss kappa / run 间 σ | **先于门禁执行**，超标则本轮 E 结论标记"不可信" |

**为什么层分不进门禁**：层分是一段时间内多个指标的加权合成，天然有"以好补坏"的能力。门禁要的是"任一红线越界即拦"，两者语义不同。**用层分做门禁 = 把 P1 事故降级成周会讨论**（二分 §10 陷阱 4 的同型错误）。

### 4.3 层分与门禁的关系（一张图说清）

```text
分层评分  ──▶ 回答"扣在哪、找谁、趋势如何"     → 周报 / 复盘 / 派单
E/S 判定  ──▶ 回答"这版能不能发"               → CI gate
M 判定    ──▶ 回答"这次分数能不能信"           → 前置校验
三者共用同一批指标，不重复计算，只是聚合方式不同。
```

### 4.4 HealthIndex（仅内部趋势，不对外）

若需要一个跨层可比的单值趋势线，用：

```text
HealthIndex = 100 × gate × (w_rt × S_rt + w_rg × S_rg + w_tc × S_tc + w_tj × S_tj) / 100

层权重按被测对象取 §4.5 的权重矩阵（不设全局默认值——一个"平均权重"会让
纯 RAG 与 L3 编排的分数看起来可比，实际不可比）。
```

**三条使用约束**：

1. `gate` 是乘法项，不能挪进加权项——这是与补强 4 一致的做法（VETO 分离）。
2. `HealthIndex` **只能做同对象、同 `environment_fingerprint` 的纵向对比**，不能跨对象横比（L1 和文档型 RAG 的层权重不同，分数不可比）。
3. **不得用于发版决策、不得对外汇报"我们的 Agent 有 96 分"**——对外口径只说业务指标（换线时长、异常闭环时长、草稿采纳率）。

### 4.5 层权重矩阵（按对象）

`HealthIndex` 的权重按"该对象的主要失效模式"设定，不是拍脑袋：

| 对象 | w_rt | w_rg | w_tc | w_tj | 设定理由 |
|---|---|---|---|---|---|
| 文档型 RAG | 0.05 | **0.85** | 0.10 | 0 | 单跳检索，失败几乎全在 RAG 层 |
| 追溯型 RAG | 0.05 | **0.80** | 0.15 | 0 | 多轮补查才有 TC 的戏份 |
| Agentic RAG | **0.35** | 0.30 | **0.35** | 0 | 被测能力就是"路由 + 工具选择" |
| L1 诊断 | 0.15 | 0.30 | **0.30** | 0.25 | 行为评测，路径错则答案对也是蒙的 |
| L2 草稿 | 0.10 | **0.45** | 0.25 | 0.20 | 终点是草稿质量 |
| L3 编排 | **0.30** | 0.10 | 0.25 | **0.35** | 场景路由 + 编排序列是核心 |

## 5. 评分卡输出结构

```text
LayeredScorecard
  run_id / object_type / environment_fingerprint
  gate           : PASS | FAIL(reasons[])              # 六类红线 + 禁调工具 + 未确认写
  layers:
    RT: score / route_accuracy / margin / confusion_matrix / over_decline_rate
    RG: score / ret_breakdown{recall, precision, node_complete} / gen_breakdown{faithfulness, citation, top1}
    TC: score / select / args / order / redundant_rate / forbidden_calls
    TJ: score / milestones_hit / efficiency / convergence_quality / recursion_hits
  e_metrics      : 根因 top-1/top-3 / 拒答正确率 / 草稿采纳率 / 编排正确率
  m_metrics      : ECE / judge_kappa / fleiss_kappa / run_sigma
  bottleneck     : argmin(layer.score) + 归因链下一跳建议
  health_index   : x.x（内部趋势，不对外）
  gate_decision  : BLOCK_HARD | BLOCK_UNKNOWN | BLOCK_QUALITY | WARN | PASS
```

**数据模型增量**（在二分 §8 的改动清单上追加）：

| 表 | 新增字段 | 说明 |
|---|---|---|
| `eval_case` | `milestones`（JSON） | 轨迹层里程碑声明 |
| `metric_snapshot` | `layer`（RT/RG/TC/TJ） | 支持按层聚合与趋势 |
| `eval_run` | `layer_scores`（JSON）、`bottleneck_layer` | 评分卡快照 |
| `attribution_link` | `layer` | 归因链按层挂接 |
| 配置层 | `layer_weights`（按 object_type）、`route_cost_matrix_version` | 权重与代价矩阵版本化，改权重即改版本 |

> `route_cost_matrix_version` 必须版本化：代价矩阵改了，历史 S_rt 与新一轮不可比，不能直接拟趋势线。

## 6. 与现有三个切面的映射（防口径分叉）

| 切面 | 回答的问题 | 组织维度 | 本文关系 |
|---|---|---|---|
| 设计 §5 | 六个对象各自考哪些指标、阈值多少 | 被测对象 | 指标与阈值的**事实源**，本文不重定义 |
| 二分 §3 | 每个指标是 E / P / S / M | 判定性质 | 正交互补：E/P 说重要性，四层说归属 |
| **本文** | 每层扣几分、找谁改、趋势如何 | **执行链** | 增加"指标 → 层"归属与层内聚合 |

**E/P 与四层的映射（不冲突，只是两个坐标）**：

| | RT | RG | TC | TJ |
|---|---|---|---|---|
| **E（端到端）** | 收口正确率 | 根因 top-1/top-3、忠实度、草稿采纳率 | — | 编排正确率、gate 决策正确率、挂起合理性 |
| **P（过程）** | 路由准确率、工具选择合理性 | 证据召回/精度、节点完整率、文档召回率 | 工具序列、入参正确率、冗余率 | 里程碑覆盖、步数冗余、递归上限 |
| **S（安全）** | 路由到写工具/越权 | 版本快照、失效泄漏、幻觉、证据为空 | 禁调工具、未确认写 | — |
| **M（元）** | — | — | — | ECE / kappa / run σ（横切，不属任何层） |

**冲突处理规则**：同一指标在同一对象下若出现"E 层归属"与"某层归属"不一致，**以二分 §2.3 的 `module_overrides` 为准，层归属随之继承**。例：`证据召回`在 F1 模块下是 P（归 RG 层），在 F5 模块下是 E（仍归 RG 层）——层不变，性质变。

## 7. 六个陷阱

| # | 陷阱 | 后果 | 规避 |
|---|---|---|---|
| 1 | **把安全红线放进层内加权** | 一条"检索满分、版本取错"拿 70 分，实际是批量不良风险 | 六类红线抽出为 `gate` 乘法项（§2.2-§2.4 各节的"硬失败项"） |
| 2 | **TC 层用加权求和** | Agent 学会多调工具刷覆盖率、跳过参数校验也能得分 | 三因子乘法（§2.4） |
| 3 | **TJ 层只算步数效率** | "提前收口"的 case 得满分——跑得快但没跑完 | `M` 权重最高（0.5），效率只占 0.3（§2.5） |
| 4 | **跨对象横比层分** | L1 的 88 分与文档型 RAG 的 88 分含义完全不同 | 层权重按对象配（§4.5）；只做同对象纵向对比 |
| 5 | **用层分/HealthIndex 做发版门禁** | 以好补坏，红线被平均稀释 | 门禁走 S/E 判定（§4.2-§4.3） |
| 6 | **步数用 LangGraph step 数** | 与 `recursion_limit=20` 语义不一致，指标系统性翻倍（L1 方案 §8 错误 3） | 统一用**工具调用次数** |

## 9. 一句话定位

> "分层评分把 Agent 的执行链切成四段——**路由**决定走哪条链、**RAG** 决定证据对不对、**Tool Calling** 决定动作调得对不对、**轨迹**决定这一趟跑得值不值；层内按目标线锚定 80 分加权，层间用安全闸门相乘、用瓶颈层归因，**分数只用于定位与趋势、门禁仍按 S/E 判定**——它不新增一个指标口径，只是让'这条链断在哪一环、该找谁改'从开会讨论变成看评分卡。"
