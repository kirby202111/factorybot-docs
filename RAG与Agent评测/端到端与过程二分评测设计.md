## 1. 概念模型：四类标签与三条判据

### 1.1 为什么文章的两分法不够，要扩成四类

文章 §2.1.2 只分端到端 / 过程两类。MES 场景有两类指标**塞进任何一边都是错的**：

| 类 | 全称 | 含义 | 判定方式 | 门禁角色 |
|---|---|---|---|---|
| **`E`** | 端到端 End-to-End | 站在用户视角，"事有没有办成" | 阈值 + 相对基线 | soft gate（质量） |
| **`P`** | 过程 Process | 站在实现视角，"中间哪一步出问题" | 阈值 + 噪声带 | **不直接进门禁**，只做归因 |
| **`S`** | 安全 Safety | 红线，恒 0 | 逻辑与 | hard gate（零容忍） |
| **`M`** | 元指标 Meta | **量具自身健康度**，不是 Agent 能力 | 阈值 | **先于门禁执行**（见 §5.2 ③） |

**`S` 为什么不参与二分**：恒 0 + 一票否决。从 0 变非 0 **不需要归因，需要立即阻断**。给它做趋势归因，等于把 P1 事故降级成周会讨论。

**`M` 为什么不参与二分**：ECE、judge kappa、Fleiss kappa 度量的是"**量具准不准**"，不是"Agent 行不行"。这个区分在 §5.2 第三步排除里是决定性的——**量具坏了会导致 E 指标假性下降**，此时修 Agent 是南辕北辙。

### 1.2 三条判据（不按"是否最终输出"分）

| 判据 | 归 `E` | 归 `P` |
|---|---|---|
| **① 用户可评价性** | 车间用户拿到输出，**不看过程**就能判"能不能用" | 用户看不到，或看到了也不评价 |
| **② 失败可归因性** | 失败只知道"这条错了"，**不知道改哪里** | 失败**直接对应一个修复动作** |
| **③ 与业务价值单调性** | 与业务结果单调相关 | 可能"P 全绿但 E 红" |

### 1.3 两个反直觉但正确的划分

| 划分 | 理由 |
|---|---|
| **`文档召回率` = P，`忠实度` = E** | 召回全对但答案脑补因果——正是文章 §2.1.2 说的"**每个模块都达标但用户就是不满意**" |
| **`证据召回` = P，`根因 top-1` = E** | 设计 §5.3 把两者放同一张表，但修复动作完全不同（改检索 vs 改推理）。**这张混表就是"知道坏了不知道哪坏了"的成因本身** |

### 1.4 三个必须单独标注的例外

| 指标 | 处理 | 原因 |
|---|---|---|
| 全部安全红线（设计 §5.8 七项） | 归 `S` | 见 §1.1 |
| ECE / judge kappa / Fleiss kappa / run 间标准差 | 归 `M` | 见 §1.1 |
| **草稿采纳率** | `E` + **`human_influenced = true`** | 受工程师信任度、工作负荷、confirmation 疲劳影响，**不是纯 AI 指标**，归因链必须加业务侧分支（§4.2 F2） |

## 2. 资产结构：两类评测集

### 2.1 端到端评测集（按功能模块建）

文章 §2.1.2："**端到端评测集是站在用户视角建立的。也就是说当 Agent 功能逐渐增加之后，需要按照端到端的功能模块建立不同的端到端评测集**。"

**一条用例必标 `functional_module`**——否则无法按模块聚合出 E 集。这是数据模型层面的必要改动（§8）。

### 2.2 过程评测集（两级：被测对象 → 限界上下文）

文章 §2.1.3："**过程评测集还可以继续往下拆……拆解带来的一个额外收益是责任清晰。当过程评测集和组织分工对齐后，某一层的分数下降，就能直接找到对应的负责人，而不需要先开一轮会来确定'这是谁的问题'**。"

```text
P 一级：被测对象（6 类，设计 §2.1）      → owner: RAG / Agent 负责人
P 二级：限界上下文（14 个，领域总览 §2）  → owner: 该上下文的 MES 服务 owner
```

> 落地提示：可观测侧已有 `agent.tool.bounded_context` span 属性，按它聚合即可得"每个限界上下文的工具调用成功率 / 证据命中率"，**P 二级数据源无需另建**。

**拆解边界警告（文章 §2.1.3）**："**分层拆解是演进的结果，不是设计的起点……让拆解被真实问题驱动，而不是被完备性焦虑驱动**"。P 二级只在证据充分的上下文上开，样本不足的先不拆。

**读法**：**每一行 = 一个端到端评测集**（跨对象聚合，有独立交付率）；**每一列 = 一个过程评测集**（不跨，用于归因派单）。

## 4. 归因映射 `AttributionMap`

### 4.1 结构定义

```text
AttributionLink
  module            : FunctionalModule    # 功能模块（E 集）
  e_metric          : str                 # 端到端主指标
  chain             : list[Ref]           # 有序归因链，长度 ≤3
  min_sample        : int                 # 该 E 指标最小样本量，默认 30
  noise_band        : float               # 关联 Ref 的噪声带，默认 0.03
  owner_hint        : str                 # 兜底 owner

Ref（归因链节点）
  metric            : str
  class             : E | P | M           # ★ 下一级不一定非要是 P
  object_type       : EvalObjectType      # P 一级
  bounded_context   : str | None          # P 二级
  owner             : str
  fail_action       : str                 # 命中后的修复动作
```

> **关键设计**：归因链的下一级**不一定是 P，可以是更细粒度的 E**（例如 F3 的"编排正确率"由"gate 决策正确率"解释，两者都是 E）。这对应文章 §2.1.3"过程评测集还可以继续往下拆"——**拆解是相对的，链的语义是"更靠近过程的一层"**。

### 4.2 六条归因链

**F1 · E `root_cause_top1`**（首个启用）

| 序 | Ref | 类 | owner | 命中后的修复动作 |
|---|---|---|---|---|
| 1 | 证据召回 | P | RAG 负责人 | 查检索策略 / 图投影滞后 |
| 2 | 工具序列合理性 | P | Agent 负责人 | 查提示词 / 工具描述 |
| 3 | 证据充分度 | P | Agent 负责人 | 查证据门槛与收口策略 |
| 补 | 限界上下文级证据命中率（物料 / 工艺管理 / 质量 / 设备台账） | P 二级 | 各上下文服务 owner | 查该上下文只读接口或数据质量 |

**F1 · E `decline_correct_rate`**：① 证据充分度（P）→ ② ECE（**M**，若超标先修量具）→ ③ 无解释 → UNKNOWN

**F2 · E `draft_adoption_rate`**（human_influenced，**必须先问业务侧**）

| 序 | Ref | 类 | 说明 |
|---|---|---|---|
| 0 | **业务侧检查**（换线类型变化 / 工程师轮岗 / confirmation 疲劳 / 班次变化） | — | **不产生指标，直接进 Case 挖掘标注**。因为它是 human_influenced 指标 |
| 1 | 草稿字段完整率 | P | 提示词 / 模板 |
| 2 | 证据完整率 | S | 若抬头，走安全流程而非归因 |

**F3 · E `orchestration_correctness`**：① gate 决策正确率（**E 细粒度**）→ ② LLM 调用占比（P；上升 = 代码节点退化 / 异常分支增多 = **工程问题**）→ ③ 限界上下文级 barrier 通过率（P 二级）

**F4 · E `faithfulness`**：① 引用命中率（E 细粒度）→ ② 文档召回率（P）→ ③ 无解释 → UNKNOWN（常见真实原因：文档切片策略变化、版本过滤失效）

**F5 · E `evidence_recall`**：① 子图节点完整率（P）→ ② 限界上下文级命中率（P 二级）

**F6**：暂不建。

## 5. 未知异常判据

### 5.1 定义

> **`UNKNOWN_ANOMALY`** = 端到端指标**显著退化** ∧ 已**排除全部已知原因** ∧ 归因链上所有 Ref 的**波动均在噪声带内**（无法用任何已观测的过程变化解释这次退化）。

文章 §2.1.2 原表述："**若过程评测集指标未发生波动，但端到端交付率降低，则说明发生了未知异常，需要我们进一步挖掘和归因从而迭代评测集**。"

### 5.2 前置：四步排除（主体工作量，文章未覆盖）

**顺序不可变。每一步命中即终止，不算未知异常。**

| 步 | 排除项 | 判据 | 数据源 | 命中后去向 |
|---|---|---|---|---|
| **① 环境** | `environment_fingerprint` 变化 | 任一分量不同 | 主数据版本（route/bom/rule）、**数据源 schema 版本**、模型版本、提示词版本、用例版本 | 受控变更 → 走正常回归（设计 §6.5） |
| **② 安全** | `S` 类指标抬头 | 任一非 0 | SafetyChecker | BLOCK_HARD，立即阻断 |
| **③ 量具** | `M` 类指标异常 | ECE >0.1 ｜ kappa <0.8 ｜ Fleiss kappa <0.7 ｜ run 间标准差 >0.03 | CalibrationService / JudgeHumanAligner | **修量具**，走反向分派（补强 9） |
| **④ 分布** | 输入分布漂移 | PSI >0.2 | DriftDetector（设计 §9.2） | 漂移补样，走 E4 流程 |

**③ 最容易被漏**：judge 模型升级或 rubric 改动后未重新人工对齐，会让 E 指标**假性下降**。此时判未知异常去挖 Agent，方向完全反了。对应补强 9 引的文章 §4.3："**定期检查'是不是评测判错了'，是评测体系自我校准的必要动作**"。

**① 在 MES 下命中率会异常高**：过程绿、端到端红，在 MES 里最常见的真实原因是**主数据 / 环境静默变化**——工艺升版未同步、设备台账更新、人员资质过期、BOM 版本投影滞后。设计 §4.4 的脱敏（SN 前 4 后 2、批次打码）会进一步放大差异。**因此 `environment_fingerprint` 必须包含"数据源 schema 版本"，而不只是模型/提示词版本**（见 §7 实例）。

### 5.3 三要素判定（排除全过之后）

```
UNKNOWN = ①显著性(E侧) ∧ ②样本量 ≥ 30 ∧ ③所有 Ref |Δ| ≤ 噪声带(P侧未波动)
```

| 要素 | 定义 | 初版值 |
|---|---|---|
| ① 显著性 | 突破绝对阈值（跌破目标线）**或**相对基线回归 < baseline × 0.95 | 沿用设计 §6.5 |
| ② 样本量门槛 | 该 E 指标本次 run 的有效 case 数 | **≥30**；不足输出 `INSUFFICIENT_EVIDENCE`，只记录不判定 |
| ③ 噪声带 | Ref 指标 delta 上界 | 固定 **±0.03**（样本充足后切换统计带，§5.4） |

**两个易错点**：

- **② 是防误报第一道闸门**。50 case 时 top-1 的一次变动可能只是 2 条 case（4pt），远达不到显著性。**没有它，冷启动会疯狂误报**。
- **③ 的措辞是"未波动"不是"达标"**。P 指标**稳定地差**（证据召回长期 0.70 低于目标 0.85）且 E 下降，**同样属于未知异常**——E 的下降无法用 P 的*变化*解释。真正不算的只是"P 变差了"。

### 5.4 噪声带标定方法

| 阶段 | 条件 | 噪声带取值 |
|---|---|---|
| 一 | 同指纹 run 数 < 10 | 固定 **0.03** |
| 二 | 同指纹 run 数 ≥ 10 | `2 × std(近 10 轮 delta)`，**夹逼到 [0.02, 0.08]** |

- **下限 0.02**：防止带过窄导致频繁误报
- **上限 0.08**：防止带过宽导致判据永不触发
- **只有 `environment_fingerprint` 相同的 run 才进同一统计序列**（指纹不同不可比，补强 11 结论）
- **指标类型差异**：二值率类（top-1 / 召回）用绝对值；计数类（步数冗余 / LLM 占比）用相对变化 **10%**

### 5.5 判定输出字段

```text
UnknownAnomalyFinding
  finding_id / run_id
  module / e_metric
  current_value / baseline_value / delta / sample_size
  significance        : PASSED
  exclusions          : [{name, judgment_value, threshold, passed}]   # 四步排除留痕
  process_snapshot    : [{metric, class, current, delta, noise_band, in_band, owner}]
  environment_fingerprint : {current, baseline}
  status              : OPEN → ATTRIBUTED → CONVERTED / CLOSED_NO_CONCLUSION
  attribution_conclusion / converted_to / owner / due_at
```

`exclusions` 必须留痕——**它证明"这次真的不是已知原因"**，是后续复盘的凭据。

### 5.6 门禁集成

`gate_decision` 枚举扩展：`PASS / WARN / BLOCK_QUALITY / ` **`BLOCK_UNKNOWN`** ` / BLOCK_HARD`

**优先级**：`BLOCK_HARD` > `BLOCK_UNKNOWN` > `BLOCK_QUALITY` > `WARN` > `PASS`

强制动作：不得放行变更 → 建 Case 挖掘任务 → 指定 owner → **限期 3 个工作日**给归因结论。

### 5.7 闭环与进化指标

归因结论**必须落到两处之一**，不允许"查了但没结论"就关闭：

1. **新增或修订 P / Ref 指标** —— 把"未知"变成"已知"（评测体系迭代 Loop，文章 §1.2）
2. **修订 E 口径或用例** —— 认定是量具问题，走反向分派

| 健康度指标 | 定义 | 诊断 |
|---|---|---|
| **未知异常闭环率** | 限期给出结论的 / 总 | 低 = 挖掘能力不足，判据形同虚设 |
| **未知异常 → 新指标转化率** | 转化为新增/修订 Ref 的 / 总 | **体系进化的核心指标** |

> 第二个指标对应文章 §1.2 第一条 Loop：未知异常的价值**不在于被判定，而在于被转化为评测集扩充**。只判定不转化 = 每次重新踩同一个坑。

## 6. 完整运行流程（一次 eval run 的七个阶段）

```text
① 装载   按 functional_module 分组加载用例（每条用例必带 module 标签）
            ↓
② 执行   逐 case 调只读入口（设计 §6.3 适配器）
            ↓
③ 判定   断言层（S，确定性硬判定）
          指标层（E / P，量化打分）
          Judge 层（生成质量相关 E 维度）
            ↓
④ 汇总   按 module 聚合 E  →  各功能模块交付率
          按 object_type → bounded_context 聚合 P
          S 走逻辑与（safety_pass = all(...)）
          M 单独成组
            ↓
⑤ 比对   与「同 environment_fingerprint 的基线 run」算 delta
          指纹不同 → 不可比，拒判并告警
            ↓
⑥ 排除   四步排除（§5.2）→ 三要素判定（§5.3）→ UNKNOWN 判定
            ↓
⑦ 门禁   CIGate 输出 gate_decision（含 BLOCK_UNKNOWN）
          落库 metric_snapshot / unknown_anomaly → 派单 owner 或转 Case 挖掘
```

## 7. 完整实例：根因 top-1 从 0.68 掉到 0.59

**场景**：F1 异常根因诊断，本轮有效 case 62 条，`root_cause_top1 = 0.59`，基线 run `0.68`，delta `-0.09`。

**步骤 1 · 三要素（前两项）**

| 要素 | 判定 | 结论 |
|---|---|---|
| ① 显著性 | 0.59 < 0.68 × 0.95 = 0.646 ✓，且跌破目标线 0.60 ✓ | 通过 |
| ② 样本量 | 62 ≥ 30 ✓ | 通过 |

**步骤 2 · 四步排除**

| 步 | 实测 | 阈值 | 结果 |
|---|---|---|---|
| ① 环境指纹 | route=r12→r12，bom=b5→b5，model=v3→v3，prompt=p7→p7，case_version=c9→c9 | 任一不同 | **未命中** |
| ② 安全 | 七项全 0 | 任一非 0 | **未命中** |
| ③ 量具 | ECE 0.07 ｜ judge kappa 0.83 ｜ Fleiss kappa 0.76 ｜ run 间 σ 0.02 | <0.1 / ≥0.8 / ≥0.7 / <0.03 | **未命中** |
| ④ 分布 | 输入分布 PSI 0.11 | >0.2 | **未命中** |

**步骤 3 · P 侧快照**

| Ref | 类 | 当前 | 基线 | Δ | 噪声带 | 带内 | owner |
|---|---|---|---|---|---|---|---|
| 证据召回 | P | 0.85 | 0.86 | -0.01 | 0.03 | ✓ | RAG 负责人 |
| 工具序列合理性 | P | 0.87 | 0.88 | -0.01 | 0.03 | ✓ | Agent 负责人 |
| 证据充分度 | P | 0.80 | 0.81 | -0.01 | 0.03 | ✓ | Agent 负责人 |
| 物料上下文证据命中率 | P 二级 | 0.89 | 0.90 | -0.01 | 0.03 | ✓ | 物料上下文 owner |

**步骤 4 · 判定**

所有 Ref 均在带内 → **`UNKNOWN_ANOMALY`** → `gate_decision = BLOCK_UNKNOWN` → 建 Case 挖掘任务，owner = F1 模块负责人，due = 3 个工作日。

**步骤 5 · 归因（人工 + Trace）**

随机采样 20 条失败 case → 12 条集中在"焊接参数异常"子类 → 逐条看 Trace → 发现这批 case 都调了设备台账上下文，而**设备台账两周前新增了"焊机型号"字段**，Agent 取到了新字段，但提示词里没有对应解读规则，导致参数比对时把新型号当成异常值。

**步骤 6 · 收敛**

1. **根因**：设备台账 schema 变更未同步
2. **暴露的体系缺陷**：`environment_fingerprint` 只记了 route/bom/rule/模型/提示词版本，**没有记"数据源 schema 版本"**，所以第 ① 步没拦住 —— **这是指纹定义的漏洞，不是 Agent 的问题**
3. **转化**：
   - 新增 P 指标 `device_profile_schema_match`（设备档案 schema 匹配率），接入 F1 归因链第 4 位
   - `environment_fingerprint` 扩展，纳入各上下文的 schema 版本
4. **状态**：`CONVERTED`，计入"未知异常 → 新指标转化率"

> 这个实例同时演示了判定、归因、转化，**以及体系对自身的修正**——一次未知异常不仅修了 Agent，还补上了环境指纹的漏洞。这正是文章 §1.2 评测体系迭代 Loop 的价值。

## 10. 五个陷阱与验收标准

| # | 陷阱 | 后果 | 规避 |
|---|---|---|---|
| **1** | **为消除未知异常而乱加 P 指标** | 未知异常的价值就在于告诉你"有你没观测到的东西"，急着归到现有 P 上是**自欺欺人** | 先人工归因再决定建不建指标。文章 §2.1.3："让拆解被真实问题驱动，而不是被完备性焦虑驱动" |
| **2** | **Ref 之间高度共线** | 归因无意义（证据召回与子图节点完整率几乎同涨同跌） | 每链 ≤3 个 Ref，建链时查共线性，共线的只留一个 |
| **3** | **P 二级拆太细** | 单维度样本稀疏，噪声带失效 | 只在证据充分的上下文开 P 二级 |
| **4** | **把 S 放进 E/P 二分** | 把 P1 事故降级成周会讨论 | S 独立于二分，恒 0 一票否决 |
| **5** | **判据没接进 CI** | 文章 §2.2："**没有接入流程的门禁，本质上只是一个建议**" | 必须落到 `CIGate` |

**验收标准**

| 层级 | 标准 |
|---|---|
| **诊断能力已标注** | 全部指标有 E/P/S/M 标签；报告分四组；团队看到报告能说出"这次是端到端掉了还是过程掉了" |
| **草稿能力已可归因** | ≥2 个模块建成独立 E 集；AttributionMap 覆盖；**E 下降时能直接派单到 owner，不需要先开一轮会** |
| **编排能力已闭环** | UNKNOWN 进 CI 并实际触发过；有归因结论；**至少 1 次成功转化为新增/修订的 Ref 指标** |

> 编排能力最后一条是关键：**从未触发**说明判据没生效（门槛过高或带过宽）；**触发未转化**说明体系没有进化能力。两者都是"看起来做完了实际没做"，对应文章 §六警告的第三种割裂形态。
