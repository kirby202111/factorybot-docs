## 2. 三个前置阻塞项（B0，3~5 天）

**不解决这三项，评测建起来也拦不住任何东西。**建议在你的 46 项待办里把这三项提到所有 P1 之前。

### B1 — CI 门禁（最高优先级）

- **对应**：#20 + 根总览 #4
- **动作**：
  1. 加 `ruff` + `mypy` 配置到两个 `pyproject.toml`（顺便统一 Python 版本到 `>=3.12`、统一构建后端，解掉根总览 #6）

### B2 — 观测补链（评测的下钻与租户隔离依赖它）

- **对应**：#9 + #33 + #39 + #7 + #40
- **动作**（按文件）：
  1. `obs/tracing.py:32-64`：`tool_span` / `llm_span` 统一 merge `obs_ctx.base_attributes()`——否则 Jaeger 里按租户/会话过滤不到（#9）
  2. `obs/observability.py` + `obs/port.py`：补 `recursion_limit_hit` / `schema_error` / `cost` 三个代理方法（#33/#39）。**这是 P0 崩溃项**：real 模式诊断递归超限时会因 `AttributeError` 覆盖原始 `GraphRecursionError` 直接崩
  3. `obs/llm_call_logger.py`：`LlmCallRecord` 补 `trace_id` + `tenant_id` + `tool_call_trace` 关联字段。**理由**：设计 §12.2 写"eval_result_detail 可引用 trace_id 下钻过程"，但 `LlmCallRecord` 现在既无 `trace_id` 也无 `tenant_id`——**下钻和租户隔离在数据模型层就断了**。这是设计文档没意识到的隐含依赖
  4. `obs/metrics.py`：`SESSION_LATENCY` 补 `.observe()`（#7）；`llm_called()` 内按 token + 模型定价调 `cost()`（#40）

### B3 — MockChatModel 路由改造（评测置信度的前提）

- **对应**：#28
- **动作**：`mock_chat_model.py` 改为按 state 中 `capability` 字段路由，不解析 system prompt 文本

## 3. 最小闭环落地方案（4 周）

按美团文章"**全景图是终局不是起点，先让数据飞轮转起来**"，砍掉一切非必要项。**阶段一完全不碰 judge。**

### 第 1 周 — 领域模型 + 首批金标准

| 动作 | 说明 |
|---|---|
| 建 `mes_eval/domain/eval_case.py` | **裁剪**：`object_type` 先只支持 `TRACEABILITY_RAG` + `AGENT_L1` 两种，不要一上来建 8 个适配器。对应美团文章"不要过早拆得太细" |
| 建评测表族 | `eval_case` / `eval_run` / `eval_result_detail`。**先建这三张**，`judge_result`/`calibration_curve`/`drift_report`/`shadow_diff` 延后 |
| 首批 50 case | 见下方 §4.1 关于 fixture 的重要提醒 |

### 第 2 周 — 两个确定性检查器（MES 最有价值的部分）

| 动作 | 说明 |
|---|---|
| `VersionAnchorChecker`（§4.2） | 断言实际输出引用的 `route_version` == 锚点版本。**纯确定性，不需要数据集，不需要 LLM** |
| `SafetyChecker`（§13.2） | 失效工艺泄漏 / 写越界 / 租户越权 / 实体幻觉 / 证据为空，五条硬断言 |

**为什么这两个放最前面**：它们是确定性的、零依赖、且直接就是 MES 红线。这两个跑通，你的 CI 就已经能拦住"批量不良级"的变更了——投入产出比远高于 judge。

**明确不做**：`JudgeService`（需人工标注对齐，成本高）、`CalibrationService`（需要足够 case 才有统计意义）、`ShadowRunner`（需要线上流量）。

### 第 3 周 — pytest 集成 + CI hard gate

```python
# tests/eval/test_l1_diagnosis.py（骨架）
@pytest.mark.parametrize("case", load_cases(EvalObjectType.AGENT_L1), ids=lambda c: c.case_id)
async def test_l1(runner, case):
    result = await runner.run_one(case, MODEL_VERSION, PROMPT_VERSION)
    assert result.safety_ok, f"安全违规: {result.safety_violations}"    # 硬
    assert result.version_ok, f"版本违规: {result.version_violations}"   # 硬
    assert result.accuracy, "根因未命中"                                  # 软
```

- 硬断言在前、质量断言在后（设计 §13.4 已定，正确）
- 在 `CIGate` 中：`model` / `prompt` / `检索策略` / `工具` 任一变更触发回归；安全用例 hard block、质量用例先 warn
- **提示**：`factorybot/app/infrastructure/cost/eval_gate.py` 已存在（`EvalGate`），但它依赖评测数据源——这正是"决策 1"里 ModelRouter 悬空的原因（见 §5.1）。本阶段跑通后，EvalGate 才有数据源

### 第 4 周 — 转人工闭环（打通 HANDOFF）

设计文档 §4.3 把 HANDOFF 定为价值最高、目标占比 ≥50% 的样本源，**但代码里它不存在**。最小实现：

```text
低置信度 / 证据不足 → 落 handoff_record（含 trace_id + tenant + 版本锚点）
   → 工程师在界面处置（采纳 / 驳回 / 修正根因）
   → 回写 human_label（is_correct / corrected_root_cause）
   → 候选用例入池 → 评审 → 进 eval_case（source=HANDOFF）
```

- 先做 API + 表 + 最简页面，**不要等完整前端**
- 每条 `handoff_record` 必须带 `trace_id`——否则无法下钻，退化成"只知道错了不知道为什么错"
- 与美团文章"**随机采样是不可省略的**"呼应：即使没有转人工，也要每班随机抽 10~20 条会话人工复核。MES 场景建议由工艺/质量工程师轮值，纳入 sprint 排期（设计 §11.4 已指出激励问题）

## 4. 三个"别人没有"的优势，要用起来

### 4.1 ⚠️ 提醒：`data/rest/*.json` 是双刃剑

你有 22 个现成的 REST fixture（`work_orders.json`、`pass_records.json`、`process_routes.json`、`test_results.json`、`kit_status.json` …），是很好的**评测数据底座**。但有一个陷阱：

**它们是 mock，与生产分布系统性不一致**——正好命中美团文章警告的"环境保真度"问题。

**建议**：
1. 给每个 fixture 加 `_provenance` 标注（`MOCK` / `SHADOW` / `PROD-SNAPSHOT`）+ 版本锚点字段
2. 首批 50 case 明确标记 `source=SYNTHETIC`，**不要冒充真实分布**
3. 在文档和汇报中明确写："当前评测基于 mock fixture，覆盖的是**逻辑正确性**而非**分布真实性**"——这与你设计文档 §1.4 的口径纪律一脉相承，也避免面试时被追问"你这数据是真的吗"答不上来

### 4.2 `agent.tool.bounded_context` 是一等资产

`obs/tracing.py:38` 的 `tool_span` 已经带了 `agent.tool.bounded_context` 属性。**这个通用 Agent 框架里没有的东西，你已经有现成实现载体了。**

**建议直接用**：从这个属性聚合出"每个限界上下文的调用成功率 / 证据命中率"——这就是你过程评测集的数据源，**不用另建采集**。美团文章说"过程评测集与组织分工对齐 → 分数下降直接找得到责任人"，你已经具备技术前提。

具体做法：把它提升为 Prometheus 一级 label，配一条告警规则："某上下文调用成功率下降 >5pt **且** 端到端准确率下降 → 定位到该限界上下文 owner"。

### 4.3 版本锚定是你对美团方法论的超越，要讲出去

美团文章讲"二元化 Rubric"和"行为评测"，但**没有版本概念**——因为通用 Agent 场景没有工艺版本生命周期。你的 `VersionAnchor` + `VersionAnchorChecker` 把"取了当前生效版而非过点当时锁定版本"变成可断言的硬规则，**这是 MES 场景独有的、通用方法论覆盖不到的增值点**。

建议面试/汇报时把它作为"我们不是照搬通用评测，而是针对 MES 版本语义做了定制"的核心论据。

## 5. 三个待拍板决策的建议

### 5.1 决策 1：cost 子系统去留 → 建议选 **B（暂存 + 标注未上线）**

理由：
- `ModelRouter.route()` 明确依赖"EvalGate 评测数据源就绪"，而评测数据源要第 2~3 周才有。**A（现在接入主流程）不具备前置条件**
- C（删除）损失太大：ResultCompactor 已接入且有效
- **B 的叙事反而更有力**："成本优化分两阶段，第一阶段 ResultCompactor 已上线；第二阶段模型路由依赖评测数据的置信度/成本分布，评测体系建成后推进"——这把两个亮点用**因果链**串起来，比硬吹"已全量上线"可信得多，也符合你设计文档 §1.4 的口径纪律

### 5.2 决策：barrier 抽象方向（#35）→ 建议"通用汇合 + 场景化分流子节点"

理由：各场景独立 barrier 会导致节点膨胀；而纯通用汇合又丢了换线场景的 PASS/FAIL 分流语义。拆成"通用汇合（不做业务判断）+ 场景化分流子节点（各场景自己实现）"，既保持抽象一致（顺带解掉 #31 的裸函数问题），又不丢语义。

### 5.3 决策 2：跨项目共享内核 → 建议**现在就抽**，不要等

理由：你要建 `mes-eval`，它要同时给 factorybot 和 FactoryRAG 用。如果 obs / tenant / version 契约两边是镜像的（根总览 #1 已指出 `domain/version.py` 注释自承"镜像 RAG 侧"），**`mes-eval` 会立刻成为第三个事实源**。建议在 mes-eval 落地前先抽 `factorybot-shared`（至少 version_contract / tenant / obs base），否则评测契约注定不可比。

## 7. 风险提示

1. **口径一致性会反向翻车**：设计文档 §1.4 和面试指南反复强调"这是设计规划，不是已建成全自动评测"。一旦代码落地，要**同步更新** [面试指南/RAG与Agent评测-面试闪光点.md](../面试指南/RAG与Agent评测-面试闪光点.md) 的口径，否则会出现"文档说没上线、代码其实有"的反向不一致——这比"硬吹已上线"更伤。
2. **不要让评测进过点主事务**：设计 §1.4 已定为硬边界。落地时 pytest 集成要跑离线环境，CI 里禁止连生产库。
3. **路由残留问题**：根总览 #2 指出 40 个 .md 仍含 `route_version` 残留。评测落地后，`eval_case` 的 `route_version` 字段是**合理保留**的（版本锚点是设计核心），清理时不要误删——建议先把评测相关的标为"合理保留"再动手，避免把事实源清掉。
4. **标注工作量要提前排期**：设计 §11.4 已指出"标注是额外工作量，需纳入 KPI / 排期，否则闭环跑不起来"。这是评测体系最常见的死因，建议第 4 周前就与工艺/质量工程师谈定轮值。
