# 评测指标落地实现方案与中间件选型

> 本文回答"这些指标到底怎么算出来、用什么组件、数据从哪来到哪去"。**不提供业务代码实现**，只给选型、契约、表结构、配置片段与执行步骤。
> **基线依据**：`factorybot/pyproject.toml`（agent-service）、`FactoryRAG/pyproject.toml` + `docker-compose.yml`（rag-service）、`factorybot/app/infrastructure/obs/metrics.py`（现有埋点）。
> **配套文档**：[端到端与过程二分评测设计.md](端到端与过程二分评测设计.md)（指标定义与判据）、[RAG与Agent评测-设计与实现方案.md](RAG与Agent评测-设计与实现方案.md)（评测体系）。

---

## 0. 要点结论

1. **不需要引入新中间件**——现有 7 个组件（MySQL / Neo4j / Chroma / Redis / Kafka / OTel / prometheus-client）足以支撑全部指标。真正缺的是**把已有组件用起来**和补 4 个部署单元。
2. **最大的落地障碍不是技术，是两个契约缺口**：① RAG 只读 API 目前不返回检索明细（`retrieved` / `node_id` / `route_version`），检索类指标无从计算；② 草稿采纳率依赖 MES Java 侧回写，是唯一跨系统指标。
3. **现有 12 个 Prometheus 指标全是运维视角，没有一个是质量视角**。质量指标必须新增埋点或走离线解析，不能指望监控数据。
4. **`TOOL_CALL_TOTAL` 的 label 是 `[tool, status]`，没有 `bounded_context`、没有 `tenant`**——"按限界上下文聚合 P 指标"目前做不到，这是过程评测集落地的第一个阻塞点。
5. **分两批**：第一批（零新组件）能落地约 70% 指标；第二批补 4 个部署单元后可落地全部。

## 1. 中间件选型总表

### 1.1 已有（直接用，不新增）

| 用途 | 组件 | 现状证据 | 在评测中的角色 |
|---|---|---|---|
| 评测用例/结果存储 | **MySQL 8.0** | compose `mysql:8.0`；`sqlalchemy[asyncio]` + `asyncmy` + `alembic` | `mes_eval` schema，全部评测表族 |
| 图数据 / 证据存在性校验 | **Neo4j 5.20** | `neo4j[async]>=5.20`；compose `neo4j:5.20` | 子图节点完整率、**实体幻觉率（存在性校验）** |
| 向量检索 | **ChromaDB** | `chromadb>=0.5`，嵌入式 + Parquet 挂卷 | 文档型 RAG 检索评测（只读） |
| 缓存 / 幂等 | **Redis 7** | `redis>=5.0`；compose `redis:7-alpine` | 影子采样去重、评测幂等锁 |
| 事件 / 样本回流 | **Kafka 3.7** | `aiokafka>=0.10`；compose `bitnami/kafka:3.7` | 会话事件、候选用例、影子流量 |
| 链路追踪 | **OpenTelemetry** | `opentelemetry-sdk` + `-instrumentation-fastapi/httpx` | 工具序列、步数、Trace 归因 |
| 实时指标 | **prometheus-client** | `metrics.py` 已定义 12 个指标 | 运维监控层（E0）、成本漂移 |
| LLM 编排 | **LangGraph + langchain-core** | 两服务均有 | 被测对象；judge 侧也可用 |
| 评测框架 | **pytest + pytest-asyncio** | dev 组已有 | 评测执行引擎（设计 §6.4） |

### 1.2 需要补（4 个部署单元 + 1 个流程）

| # | 缺口 | 选型 | 为什么选它 | 代价 |
|---|---|---|---|---|
| **G1** | **CI 执行环境** | **GitHub Actions（或 GitLab CI）** | 设计与代码同仓，零运维；PR 触发跑 `MUST_PASS` 集即可 | 低。**这是 B1 前置阻塞，没它门禁只是一个建议** |
| **G2** | **Trace 后端** | **OTel Collector + Grafana Tempo**（Jaeger 亦可） | compose 里已配 `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317`，**但根本没有 otel-collector 这个 service** —— 属"配了没部署" | 中。补 2 个 compose service |
| **G3** | **指标后端与看板** | **Prometheus + Grafana** | `prometheus-client` 已在埋点，只差拉取端；Grafana 同时可挂 MySQL 数据源看评测趋势 | 中。补 2 个 compose service |
| **G4** | **调度（每日批 PSI / 巡检）** | **先 APScheduler 内嵌 → 量上来换 Argo Workflows** | 只有一个每日批任务，**不要一上来就 Airflow**（运维成本远超收益） | 低→中 |
| **G5** | **人工标注入口** | **v1：MySQL + 极简内部页面；v2：Label Studio** | 标注量初期每班 10~20 条，不值得上平台；等日标注 >100 条再迁 | 低。**但必须做，否则 HANDOFF 闭环为零** |

### 1.3 明确不引入

| 技术 | 为什么不引入 |
|---|---|
| Ragas / DeepEval 作为**主力** | 设计 §13.1 已规划为**可选适配层**。它们会额外调 LLM 做忠实度评判，成本高、且不受版本锚定约束。仅在 F4 模块抽样使用 |
| Airflow / DolphinScheduler | 一个每日批任务，运维成本远超收益 |
| 独立 judge 微服务 | v1 直接在评测进程里调 LLM SDK 即可，judge 不是在线服务，不需要独立部署 |
| Milvus / Qdrant 替换 Chroma | 评测只读，不替换生产向量库。**但见 §7 陷阱 1（Chroma 嵌入式与并行评测冲突）** |
| 向量化 Trace 存储（如 LangFuse） | 已有 OTel + Kafka，自建成本低于引入新系统的数据迁移成本 |

                              ▼

                              │

| topic | 生产者 | 消费者 | 载荷 |
|---|---|---|---|
| `agent.session.v1` | agent/rag-service | Case 挖掘 | session_id, trace_id, tenant, level, confidence, 摘要（脱敏后） |

## 3. 逐指标实现方案

**列含义**：`数据源` = 从哪取；`采集` = 谁负责取；`计算` = 哪个组件算；`存储` = 落哪；`时机` = 何时判定。

### 3.1 检索质量类（`P`）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **证据召回** | 响应 `evidence[].context` vs `expected_evidence_contexts` | 离线解析只读 API 响应 | `MetricsCalculator.retrieval` | `metric_snapshot` | E1 |
| **证据精度** | 同上（命中数 / 实际查的上下文数） | 同上 | 同上 | 同上 | E1 |
| **子图节点完整率** | 响应 `evidence[].node_id` vs `expected_evidence_node_ids` | 离线解析 | 同上 | 同上 | E1 |
| **文档召回率** | 响应 `retrieved[].doc_id` vs `expected_doc_ids` | 离线解析 —— **需 RAG API 返回检索明细（见 C1）** | 同上 | 同上 | E1 |
| **引用命中率** | `citations[]` vs `retrieved[]` 片段 | 离线解析 | 同上 | 同上 | E1 |

**实现要点**：
- **C1 是前置契约**：若 `/rag/{route}/query` 响应不含 `retrieved[]`（doc_id / node_id / route_version），检索类 5 个指标全部无法计算。解法：给只读 API 加 `?include_trace=true` 或内部 debug 字段，**只评测侧可见，不影响生产响应体**。
- 证据召回的"上下文"口径必须复用 14 个限界上下文的**枚举值**，不能是自由文本 —— 否则跨 run 不可比。

### 3.2 生成质量类（`E`）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **根因 top-1 / top-3** | `hypotheses[].category` vs `expected_root_cause` | 离线解析 | `MetricsCalculator.generation` | `metric_snapshot` | E1 + 巡检 |
| **5M1E 分类正确率** | 同上 | 同上 | 同上 | 同上 | E1 |
| **忠实度 faithfulness** | claims vs 检索文档 | 离线，**Ragas 适配层** | `RagasAdapter`（可选，设计 §13.1） | `judge_result` | E1，**仅 F4 抽样** |
| **答案相关性** | 问题 vs 答案 | 离线，Ragas 适配层 | 同上 | 同上 | 同上 |
| **拒答正确率** | `should_decline` vs 实际是否拒答+转人工 | 离线解析 | `generation` | `metric_snapshot` | E1 |

**实现要点**：
- 忠实度/相关性**要额外调 LLM**，成本高且不受版本锚定约束 → **只在 F4 模块跑，且抽样 ≤50 条/轮**；其余模块用确定性指标（引用命中率）替代。
- 根因 top-1 的"命中"判定要支持**类别层级**（如预期 `Material` 属 5M1E "料"，答案给"物料批次错误"应判命中），不能做字符串等值。这是 judge 与硬断言的分界：类别映射用硬断言，排序合理性用 judge。

### 3.3 Agent 行为类（`P`，部分细粒度 `E`）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **工具序列合理性** | OTel span 序列 | **在线采集（Tempo）→ 离线回放** | `MetricsCalculator.agent` | `metric_snapshot` | E1 |
| **证据充分度** | 实际 evidence 数 / 场景期望数 | 离线解析 | 同上 | 同上 | E1 |
| **步数冗余** | span 数 / 最少必要步数 | 离线回放 | 同上 | 同上 | E1 |
| **路由准确率** | 响应 `route` vs `expected_route` | 离线解析 | 同上 | 同上 | E1 |
| **工具选择合理性** | span `tool` 名 | 离线回放 | 同上 | 同上 | E1 |
| **多余工具调用率** | span 序列去重后 | 离线回放 | 同上 | 同上 | E1 |
| **收口正确率** | 响应终止状态 | 离线解析 | 同上 | 同上 | E1 |
| **LLM 调用占比** | `agent_llm_invocation_total` / 节点总数 | **在线已有 Prometheus** | PromQL + 离线复核 | Prometheus + `metric_snapshot` | E1 + 在线 |
| **递归上限命中率** | `agent_recursion_limit_hit_total` | **在线已有** | PromQL | Prometheus | 在线告警 |
| **gate 决策正确率** | gate 输出 vs `expected` | 离线解析 | `agent` | `metric_snapshot` | E1 |
| **编排正确率** | 编排步骤序列 vs `expected_route` | 离线解析 | `agent` | 同上 | E1 |
| **挂起合理性** | 编排挂起状态 vs 应挂起场景 | 离线解析 | `agent` | 同上 | E1 |

**实现要点**：
- **工具序列/步数依赖 Trace 可查询** → 依赖 G2（OTel Collector + Tempo）。**G2 不落地，这 4 个指标只能靠被测服务自己在响应里回带 `steps[]`，精度会下降**。
- `LLM 调用占比` 与 `递归上限命中率` 是**唯二能白嫖现有埋点**的指标，直接接 Prometheus。
- ⚠️ `SESSION_LATENCY` 在 `metrics.py:13` 已定义，但 `MetricsCollector` 中**没有任何 observe 调用** → 成本漂移里的"平均耗时 P95"目前恒空，必须补埋点。

### 3.4 安全红线类（`S`，硬失败）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **失效工艺泄漏率** | `evidence[].process_status` / `route_version` | 离线断言 | `SafetyChecker` + `VersionAnchorChecker` | `eval_result_detail.safety_violations` | E1 硬阻断 |
| **实体幻觉率** | `node_id` / `SN` / `batch` 是否存在 | 离线 —— **查 Neo4j 做存在性校验** | `SafetyChecker`（Cypher 存在性查询） | 同上 | E1 硬阻断 |
| **写越界率** | 是否产生写副作用 | 离线：**执行前后 DB/接口快照对比** | `SafetyChecker` | 同上 | E1 硬阻断 |
| **租户越权率** | 响应中是否含非本租户数据 | 离线断言 | 同上 | 同上 | E1 硬阻断 |
| **PII 泄漏率** | 输出文本扫描 | 离线：**复用现有 `obs/redactor.py` 规则** | `SafetyChecker` | 同上 | E1 硬阻断 |
| **证据为空率** | `hypotheses[].evidence` 是否空 | 离线断言 | 同上 | 同上 | E1 硬阻断 |
| **过点主事务侵入率** | — | **架构保证，非运行时检测** | 设计约束（§1.4） | 检查清单 | 人工评审 |

**实现要点（本节是性价比最高的一块）**：
- **7 项全部是确定性判定，零 LLM 调用、零成本**。这是第一批就该做的——不需要 judge、不需要 Ragas、不需要 Trace 后端。
- **实体幻觉 ≠ 要 LLM 判**：`MATCH (n {id: $node_id}) RETURN count(n)` 即可确定性判定。这是 MES 场景相比通用 Agent 的巨大优势。
- **PII 复用品侧已有的 `Redactor`**，不要另写规则——否则两套脱敏口径会漂移。
- "过点主事务侵入率"是**架构属性**，评测测不出来，只能靠 §15 检查清单人工评审，不要试图做自动化。

### 3.5 标定与漂移类（`M`）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **ECE** | `(confidence, is_correct)` 对 | 离线：E1 结果 + 人工标签 | `CalibrationService`（Platt scaling） | `calibration_curve` | E1 后 |
| **judge–人工 kappa** | judge 判定 vs 人工标注 | 离线，抽样 ≥50 条 | Cohen's kappa（`scikit-learn`） | `judge_result.aligned_with_human` | judge 上线前 + 季度 |
| **Fleiss kappa** | 多标注者结果 | 离线 | `statsmodels` 或自实现 | `human_label` | 用例入库前 |
| **输入分布 PSI** | 每日会话的问题分布 / 5M1E 分布 | **每日批** | `DriftDetector` | `drift_report` | 每日 |
| **成本漂移** | `agent_token_total` / `agent_cost_usd_total` | **在线已有 Prometheus** | PromQL | Prometheus | 实时 |

**实现要点**：
- ⚠️ `agent_cost_usd_total` 目前**恒 0**（cost 未接入，`metrics.py:88` 有 `if usd > 0` 守卫）→ 成本漂移当前无数据，需先修 cost 采集。
- PSI 每日批只需一个 APScheduler 任务，**不要为它上 Airflow**。
- kappa 计算建议直接用 `scikit-learn` 的 `cohen_kappa_score` / `statsmodels` 的 `fleiss_kappa`，不自实现。

### 3.6 业务与采纳类（`E`，含 human_influenced）

| 指标 | 数据源 | 采集方式 | 计算组件 | 存储 | 时机 |
|---|---|---|---|---|---|
| **草稿采纳率** | **工程师是否点"下达"** | ⚠️ **需 MES Java 侧回写** | 离线聚合 | `human_label` | 周/月 |
| **草稿字段完整率** | 草稿必填字段 | 离线解析 | `MetricsCalculator` | `metric_snapshot` | E1 |
| **草稿合规率** | 输出为 intent+draft、未落库 | 离线断言 | `SafetyChecker` | 同上 | E1 硬阻断 |
| **confirmation 不可绕过率** | `requires_confirmation` 恒 True | 离线断言 | 同上 | 同上 | E1 硬阻断 |

**实现要点 —— 这是全表最大的落地障碍**：

草稿采纳率是唯一**跨系统**指标（Agent 在 Python 侧，下达动作在 MES Java 侧）。三条可选路径：

| 路径 | 做法 | 代价 | 推荐 |
|---|---|---|---|
| A | 草稿生成时落 `draft_id`；MES 侧下达时**回调 agent-service** | 需改 Java 侧 | 长期正解 |
| B | MES 侧把下达事件写 **Kafka**，评测侧消费 | 需 Java 侧发事件；Kafka 已有 | **推荐**（解耦，且复用现有组件） |
| C | 定期从 MES 库**读返工单表**，用 `source_draft_id` 关联 | 需只读库权限 + 字段 | 兜底 |

**无论选哪条，`draft_id` 必须在草稿生成时落库并传给 MES**，否则事后无法关联。这个字段要尽早定，属于跨系统契约。

### 3.7 元指标与巡检

| 项 | 实现 |
|---|---|
| **巡检集** | 从 `eval_case` 的 `MUST_PASS` 集抽 20~30 条，APScheduler 每班触发，走**线上只读实例**（限流），结果落 `metric_snapshot` 并按产线/班次切片 |
| **AB** | 先不做自动化，用产线级分流 + 人工对比业务指标（换线时长、异常闭环时长） |
| **随机采样** | 每班从 Kafka `agent.session.v1` 随机抽 10~20 条推 `eval.candidate.v1`，工艺/质量工程师轮值复核 |

## 4. 必须补的埋点（按优先级，这是落地清单）

| # | 缺口 | 位置 | 影响哪些指标 | 优先级 |
|---|---|---|---|---|
| **C1** | **RAG/Agent 只读 API 返回检索明细**（doc_id / node_id / route_version / steps） | RAG/Agent 只读入口 | 检索类 5 项 + 工具序列/步数 | **P0** |
| **C2** | `TOOL_CALL_TOTAL` 加 label `bounded_context`、`tenant` | `obs/metrics.py:16` | 全部 P 二级（按上下文分组） | **P0** |

## 7. 六个落地陷阱

| # | 陷阱 | 后果 | 规避 |
|---|---|---|---|
| **1** | **ChromaDB 是嵌入式（Parquet 挂卷），多进程争用** | `pytest-xdist` 并行跑评测时 Chroma 数据损坏或报错 | 评测环境用**独立 Chroma 实例**或**禁用并行**；生产多副本时也需评估迁移 |
| **2** | **评测用测试库数据，与生产分布不一致** | 离线全绿、上线全红 → 团队不再信任评测（文章 §2「环境保真度」） | `eval_case` 必带 `environment_fingerprint`，含 route/bom/rule 版本 + **数据源 schema 版本** |
| **3** | **数据/rest/ 的 22 个 fixture 被当成真实分布** | 评测集系统性偏离 | fixture 显式标 `_provenance=MOCK`，首批用例标 `source=SYNTHETIC` |
| **4** | **judge 与 Ragas 全量跑** | token 成本失控，且不受版本锚定约束 | 只在 F4 抽样；其余用确定性指标 |
| **5** | **为一个每日批任务上 Airflow** | 运维成本远超收益 | APScheduler 内嵌起步 |
| **6** | **`MockChatModel` 按 prompt 子串路由** | 现有 74 个测试是假绿的，评测分数下降时分不清是模型退化还是 mock 走错分支 | 这是 B3 前置阻塞，必须第一批修 |

## 8. 一句话总结

**这套指标不需要新中间件——需要的是：补一个 CI、补一个 Collector + Tempo、补一个 Prometheus + Grafana，再补齐 8 处埋点。第一批（安全 + 版本锚定 + 根因准确率）零新组件即可落地，且全部是确定性判定。真正的难点在两个契约缺口：RAG 只读 API 返回检索明细（C1），和草稿采纳率的跨系统回写（C6）。**
