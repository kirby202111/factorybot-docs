# RAG 服务引入路线

> 面向场景：面试中被问"你这套 MES 能不能上 AI / RAG"或"如果给系统用户引入智能问答，你怎么做"时，分层输出"路线选型 + 与领域耦合点 + 落地顺序"。
> **核心纪律**：RAG 在本项目中是**设计阶段的引入规划**，不是线上已落地能力。讲法上遵循 [项目亮点与指标卡片.md](项目亮点与指标卡片.md) §0 的口径纪律--说"规划方向 / 设计取舍"，不说"我们已经做了 RAG"。MES 领域对错误答案零容忍（错给一条已失效工艺会直接导致批量不良），所以本路线强调**只读边界 + 版本一致性 + 可观测兜底**，而非堆模型。

---

## 0. 先定场景，再定技术

RAG 方向的选择，不从"用什么向量库 / 哪个模型"起手，而从**"谁问、问什么、答什么"**起手。本 MES 的用户里，工程师类场景的答案来源各不相同，一个方向吃不下全部：

| 用户 | 典型问题 | 答案来源 | 对应路线 |
|------|---------|---------|---------|
| 工艺 / 质量工程师 | "这批不良的根因？5M1E 怎么串？" | 追溯链 + 工艺版本 + 缺陷库 + 历史 8D | 路线 A |
| 设备工程师 | "这台设备报 E027 怎么修？" | 设备手册 + 维修历史 + 设备状态 | 路线 B |
| 操作工 / 线长 | "SPI 报警怎么处置？首件检验流程？" | SOP / 作业指导书 / 检验标准 | 路线 B |
| 所有角色 | 自然语言统一入口，按问题路由到 A/B | A + B 工具 + 多步组合 | 路线 E |

一句话：**前三类是"文档 + 事件 + 追溯"，E 是统一收口**，必须分线做，不能一个入口硬塞。

---

## 1. 三条路线总览

| 路线 | 名称 | 与本 MES 的契合度 | 落地难度 | 起步价值 |
|------|------|-----------------|---------|---------|
| A | 追溯型 RAG（GraphRAG + 领域事件流） | ★★★★★（护城河） | 高 | 高 |
| B | 文档型 RAG（SOP / 手册 / 标准） | ★★★★ | 低 | 高（建议起步） |
| E | Agentic RAG（统一入口） | ★★★（收口形态） | 高 | 依赖 A/B 成型 |

---

## 2. 各路线详解

### 2.1 路线 A：追溯型 RAG（最契合，差异化最强）

把 MES 已有的**全链路追溯**（物料批次 / 单件序列号 / 设备 / 人员 / 工艺版本 / 过点记录 / TestResult）做成可被 LLM 检索 + 推理的图谱。

- **输入**："某单件出现焊接不良" -> 自动按 **5M1E** 串起：该单件过哪几站、用了哪批锡膏、贴片机当时参数、谁操作的、当时工艺版本是哪版、同批次其他单件的不良率。
- **技术形态**：**GraphRAG + 领域事件流**，不是单纯向量检索。直接放大本 MES [领域总览.md](../领域模型/领域总览.md) §5 的"追溯性"核心价值。
- **为什么是护城河**：建立在已有的过点记录、工艺版本绑定（§5.1）和领域事件之上，别的系统抄不走--因为别人没有这 14 个上下文沉淀的追溯链。
- **难点**：实体关系建模重，需把聚合根之间的引用（如 `source_work_order_id`、`routeVersion`、`asset_id`）显式建成图边。

### 2.2 路线 B：文档型 RAG（最易落地，建议起步）

对**半结构化 / 非结构化知识**做向量化：SOP、作业指导书、IPC 标准、设备维修手册、检验标准、历史 8D 报告、培训资料。

- **典型问答**：工程师 / 操作工问"SPI 报警怎么处置""首件检验流程" -> 检索文档给答案 + 引用。
- **难点不在技术，在版本治理**：本 MES 的工艺路线有**版本生命周期**（§5.1），RAG 检索必须带 `routeVersion` / 生效状态过滤，否则会答出**已失效工艺**--这是和通用 RAG 最大的区别，也是面试最该展开的点。
- **与领域耦合点**：需订阅 `ProcessRouteActivated` 等事件（§4.3）触发重索引，保证检索到的工艺与生产执行侧缓存一致。

### 2.3 路线 E：Agentic RAG（统一入口，长期形态）

一个 Agent 入口，按问题路由到 A / B 的工具（查追溯链 / 检索文档），能多步推理。

- **定位**：最终形态，**不建议起步就做**。它依赖 A / B 的能力都成型，否则 Agent 没工具可调，会退化成套壳问答。

---

## 3. 推荐落地顺序

**先 B 后 A，E 收口。**

1. **第一步（B 文档型 RAG）**：2–4 周可出 demo，选"设备维修手册 + SOP + 检验标准"这一刀切进去，先把**版本治理**和**权限隔离**做扎实。验证"RAG 在车间到底有没有人用"。
2. **第二步（A 追溯型 RAG）**：建立在领域事件和过点记录之上，做不良根因自动串联--这是护城河。
3. **收口（E）**：A / B 能力成型后再做统一 Agent 入口。

---

## 4. 硬约束（一开口就要讲，体现架构判断力）

> 这几条是面试中**区分"懂 RAG"和"懂 MES 上 RAG"的关键**。通用 RAG 不会强调这些，但本 MES 必须强调。

| 约束 | 说明 | 与本 MES 的耦合点 |
|------|------|-----------------|
| **版本一致性** | 工艺 / BOM / 质量规则都有版本和生效状态，检索必须带版本过滤 | 订阅 `ProcessRouteActivated` 等事件触发重索引（§4.3）；过点记录 `routeVersion`（§5.1） |
| **只读边界** | RAG 永远只读 MES；任何"写"（发起返工、改工艺）只能由人在正式界面操作，LLM 最多给草稿 | 过点主事务零分布式事务（§5.3），RAG 不得进写路径 |
| **权限隔离** | 不同车间 / 产线 / 角色能看到的数据范围不同，检索层要带租户 / 权限上下文 | 多上下文边界即天然的权限切分面 |
| **部署形态** | 车间网络常与办公网隔离，需提前定是本地化模型 / 向量库还是云端 API | 影响选型与成本，常被忽略 |
| **可观测与兜底** | 所有答案带来源引用 + 置信度，低置信度直接转人工 / 转规则引擎，不硬答 | 与 MES 防错理念一致：宁可拦下让人判，不可错放 |

## 5. 面试防守 Q&A

**Q：你这套 MES 上 RAG，最大的风险是什么？**
A：不是检索准确率，是**版本一致性**。我的工艺路线有版本生命周期，过点记录绑定 `routeVersion` 保证历史可回溯（§5.1）。如果 RAG 检索到一条已失效的工艺给操作工，会直接导致批量不良。所以 RAG 必须订阅 `ProcessRouteActivated` 这类事件触发重索引，检索时带生效状态过滤--这是和通用 RAG 最大的区别。

**Q：RAG 会不会拖慢过点？**
A：不会进过点主事务。过点 P99 ≤200ms（§4.1）是硬约束，RAG 只在过点之外做检索问答，不进过点主事务。过点主事务内零分布式事务（§5.3），RAG 同样不得进写路径。

**Q：为什么不让 LLM 直接查 MES 数据库回答业务问题？**
A：业务问题分两类。文档类（SOP / 手册）走路线 B 向量检索；追溯类（不良根因、5M1E 串联）走路线 A 的 GraphRAG。两者都只读、都带版本过滤与租户隔离。任何写操作（发起返工、改工艺）只能人在正式界面做，LLM 最多给草稿。

**Q：为什么推荐先做文档型，而不是直接上 Agentic RAG？**
A：Agentic RAG 依赖底层工具都成型。文档型（B）2–4 周能出 demo，先验证"车间到底有没有人用"；追溯型（A）建立在已有领域事件和过点记录上，是护城河但建模重。先 B 后 A，最后 E 收口--这是按"价值 / 难度 / 依赖"排的，不是按热度。

**Q：追溯型 RAG 和通用 RAG 有什么本质区别？**
A：通用 RAG 是向量检索文档；追溯型 RAG 是 **GraphRAG + 领域事件流**，把物料批次 / 单件 / 设备 / 人员 / 工艺版本 / 过点记录之间的引用显式建成图边。输入"某单件焊接不良"，它能按 5M1E 自动串起这条单件的全链路。这套图谱建立在我已有的 14 个上下文和 `routeVersion`、`source_work_order_id`、`asset_id` 这些跨上下文引用上--别人没有这套领域模型，抄不走。

**Q：不同车间能看的数据不一样怎么管？**
A：检索层带租户 / 权限上下文，不是一个全局向量库。本 MES 的限界上下文边界本身就是天然的权限切分面，可以按上下文 + 产线做向量库的分片与过滤，权限在检索前过滤，不是答完再裁剪。

## 6. 红线（口径纪律）

- ❌ "我们 MES 已经上了 RAG"--这是设计阶段规划，不是已落地。
- ❌ "RAG 让良率提升 X%"--除非真实车间有对照数据。
- ❌ "LLM 直接改工艺 / 发返工单"--RAG 永远只读，写操作必须人在正式界面做。
- ❌ "RAG 进了过点主事务"--绝不允许，过点 200ms 是硬约束。

**正确讲法**：
- ✅ "我规划了三条 RAG 引入路线，按"先文档型、后追溯型、最后 Agentic 收口"的顺序推进，核心约束是版本一致性、只读边界、与过点主事务解耦。"
- ✅ "追溯型 RAG 建立在我已有的 14 个限界上下文和领域事件流之上，这是和通用 RAG 的本质区别。"

被问"上线了吗"时，老实说："这是设计阶段的引入规划，重点是路线选型与领域耦合点的判断，落地需要先做文档型验证可用性。"--**诚实 + 体现架构判断力，比硬吹"已上线 AI"得分高**。

---

## 7. 一句话定位（收尾用）

"给 MES 引入 RAG，关键不是选哪个模型，而是**把 RAG 的检索边界对齐到 MES 的领域边界**--版本要和工艺生命周期一致、只读不得进过点主事务。我规划了三条路线，先文档型起步验证可用性，再做建立在追溯链上的追溯型 RAG 作为护城河，最后用 Agentic RAG 收口成统一问答入口。"
