# RAG 服务引入方案

> 面向场景：说明“这套 MES 如何引入智能问答与制造知识助手”。
>
> 核心定位：只建设**一个 RAG 服务**，同时具备文档检索、制造追溯和 Agentic 检索编排能力。三者是同一服务内部协同的能力，不是三套产品，也不要求用户选择问答类型。
>
> 口径纪律：RAG 在本项目中是设计阶段的引入规划，不是线上已落地能力。MES 对错误答案高度敏感，因此方案重点是版本一致性、只读边界、权限隔离、证据引用和可观测兜底，而不是堆叠模型或框架。

---

## 0. 从统一问题入口出发

工程师不会关心后台使用了哪种检索技术，只会提出完整问题：

| 用户 | 典型问题 | 需要的证据 |
|------|---------|-----------|
| 工艺 / 质量工程师 | “这批不良的根因？5M1E 怎么串？按哪份 SOP 处理？” | 追溯记录、当时工艺版本、检验标准、历史 8D |
| 设备工程师 | “这台设备报 E027 怎么修？” | 设备手册、适用型号与版本、维修记录、设备状态 |
| 操作工 / 线长 | “SPI 报警怎么处置？首件检验流程？” | 当前有效 SOP、作业指导书、检验标准 |
| 所有角色 | “先查这个单件，再告诉我当时的要求和后续建议” | 多步追溯、版本解析、对应版本文档与证据组合 |

因此，合理设计不是一个入口硬塞一种检索，也不是拆成三种 RAG 让用户选择，而是：

**一个 `rag-service` 接收问题，由内部规划器判断需要哪些证据，调用文档与追溯工具，必要时通过 Agentic 追加检索，最后返回统一答案与引用。**

---

## 1. 一个 RAG 的三项内部能力

| 能力 | 作用 | 关键设计 |
|------|------|---------|
| 文档检索 | 找到 SOP、手册、标准、培训资料和历史 8D | 向量召回 + 元数据过滤 + 重排 + 精确引用 |
| 制造追溯 | 还原单件、批次、工单的过点、物料、设备、人员、测试和工艺版本 | MySQL 关系型读模型 + MES 只读接口，不使用图检索 |
| Agentic | 根据证据缺口选择工具、补充查询、解析版本并组合多源证据 | 有限状态机、只读工具白名单、步数与成本预算 |

三项能力共享同一套：

- `RagQuery` / `RagAnswer` 查询与答案契约；
- `Evidence` / `Citation` 证据与引用契约；
- `VersionAnchor` 版本锚点；
- `TenantContext` 权限上下文；
- 审计、Tracing、Metrics 和安全策略。

### 一个组合示例

问题：“批次 LOT-01 为什么焊接不良，应该怎么处理？”

1. 追溯工具按批次找到相关单件、过点和测试记录；
2. 按固定关联查询补充物料批次、设备、人员与当时工艺版本；
3. 文档工具使用解析出的历史版本检索 SOP、检验标准和相关 8D；
4. Agentic 判断证据是否足够，必要时补查缺失记录；
5. 统一答案分开呈现制造事实、文档处置建议、候选原因和待确认事项。

这是一笔 RAG 请求中的多步检索，不是多个 RAG 产品之间互相调用。

---

## 2. 为什么追溯不使用图检索

MES 的追溯关系已经有明确业务含义和关联字段，例如：

- `serial_no` 定位单件过点；
- `work_order_id` 关联工单；
- `operation_record_id` 关联测试结果、物料使用和设备上下文；
- `material_lot_id` 定位批次使用记录；
- `route_ref_id + route_version` 确定当时工艺版本。

基于这些字段建立 MySQL 读模型和索引，再用预先评审的固定查询计划逐段取证，就能支撑目标场景。

不采用图检索的原因：

1. **减少基础设施**：不需要额外维护图数据库、图 Schema、驱动和备份体系。
2. **减少同步复杂度**：制造事件更新关系型读模型即可，不再维护一套图投影。
3. **限制查询边界**：固定计划天然限制展开深度、时间窗口和记录数，避免无界多跳。
4. **贴近现有数据语义**：权限、版本和生效时间可以直接落入 SQL 条件。
5. **便于核对来源**：每条结果仍是明确的 MES 业务记录，而不是需要先解释的图结构。

代价是不能自由探索任意关系。对此应通过评测识别真正需要的查询计划，再显式增加，而不是把任意 SQL 或无界关联能力暴露给模型。

## 3. Agentic 的正确定位

Agentic 不是单独建设的一套 RAG，也不是所有请求必须经过的入口层。它只负责“什么时候再查一次、查什么、什么时候停止”。

### 简单问题

“当前首件检验流程是什么？”一次文档检索已经足够，直接检索并生成引用答案，不增加多步规划成本。

### 复杂问题

“这个批次当时用哪版工艺，同批不良集中在哪站，对应处置要求是什么？”需要追溯、版本解析、追加关联和文档检索，Agentic 在预算内完成多步组合。

### 硬约束

- 只开放 `document_search`、`trace_lookup`、`record_expand`、`version_resolve` 等只读工具；
- 默认最多 6 个编排步骤，并限制工具次数、记录数、时长和 token；
- 没有新增证据就停止；
- 权限或版本冲突时停止，不换路径绕过；
- 证据不足时澄清或拒答，不让模型补写制造事实。

---

## 4. 推荐落地顺序

落地顺序是同一服务的能力增量，不是三条独立路线。

### 第一阶段：统一底座与文档检索

- 建立统一查询、答案、证据、版本和权限契约；
- 打通文档解析、切块、向量索引、重排与引用；
- 提供基础 `/rag/query`；
- 验证版本过滤、租户隔离和文档答案忠实度。

### 第二阶段：加入非图追溯

- 建立面向查询的 MySQL 追溯读模型；
- 消费必要制造事件并记录幂等、位点和 freshness；
- 实现序列号、批次、工单三种种子查询与固定关联计划；
- 接入 MES 只读接口补数；
- 验证 5M1E 证据召回、错误关联率和历史版本对齐。

### 第三阶段：加入 Agentic 编排

- 引入有限状态机和工具预算；
- 支持“追溯解析版本后再查文档”等追加检索；
- 建立停止条件、证据充分性判断和审计页面；
- 用端到端评测确认多步检索确实提升答案质量，而不是只增加成本。

### 第四阶段：生产治理

- 完成压测、故障降级、备份重建和安全评测；
- 建立检索质量、证据完整率、延迟、步数和 token 成本看板；
- 将越权、写操作、失效版本和无证据制造事实设为 CI 阻断项。

---

## 5. 硬约束

| 约束 | 说明 | 落地方式 |
|------|------|---------|
| 版本一致性 | 工艺、BOM、质量规则有版本与生效状态，历史问题不能套用当前版本 | 从目标过点/工单解析 `VersionAnchor`，文档与追溯证据共同校验 |
| 只读边界 | RAG 不改工艺、不发返工、不进入 MES 写路径 | 只读 ACL、只读账号、工具白名单和启动检查 |
| 权限隔离 | 不同车间、产线和角色的数据范围不同 | 文档元数据、SQL 与 MES 请求都在检索前带权限上下文 |
| 证据约束 | 制造事实必须来自记录，处置建议必须来自适用文档或明确推理 | 统一 `Evidence`，生成后校验 citation，缺证据显式返回 |
| 查询有界 | 追溯与 Agentic 不能无限展开 | 固定查询计划、时间窗、记录数、步数和总时长预算 |
| 可观测与兜底 | 需要知道查了哪些数据、为何停止、答案来自哪里 | OTel、工具审计、证据页面、freshness 和降级矩阵 |
| 部署适配 | 车间可能网络隔离 | Embedding、Reranker 和向量库支持本地化，模型 provider 可替换 |

## 6. 面试防守 Q&A

**Q：为什么不是分别做文档 RAG、追溯 RAG 和 Agentic RAG？**

A：用户问题天然是组合的。例如批次不良既要制造记录，也要当时版本的 SOP，还可能需要追加查询。拆成三套会产生重复入口、权限、版本、证据和审计契约。我更倾向于一个 RAG 服务：文档与追溯是检索工具，Agentic 是按需编排，最终返回统一答案和引用。

**Q：不用图检索，怎么做 5M1E 追溯？**

A：以序列号、批次或工单为种子，先查过点等主记录，再通过 `operation_record_id`、`material_lot_id`、`asset_id`、`route_version` 等关联字段，按固定查询计划批量读取测试、物料、设备和工艺记录，最后按 5M1E 归类证据。关联深度、时间窗和数量都受限，缺失关系显式标注，不由模型猜测。

**Q：Agentic 会不会让系统不可控？**

A：只把 Agentic 用在有收益的追加检索上。简单请求直接检索；复杂请求也只能调用只读白名单工具，并受步数、工具次数、时间、记录数和 token 预算约束。无新增证据、权限冲突或版本冲突都会停止。

**Q：RAG 最大的风险是什么？**

A：不是模型不够大，而是版本和证据错误。历史工单绑定 v3，当前 ACTIVE 可能已经是 v4；如果退回查最新，就会给出不适用的 SOP。因此历史问题先从制造记录解析当时版本，再同时约束追溯证据和文档检索。无法解析时宁可澄清或拒答。

**Q：为什么不让 LLM 直接查 MES 数据库？**

A：模型不能获得任意 SQL、表名或数据库凭据。所有追溯都经过只读 Port 和固定查询计划，权限、时间窗、记录数与版本由服务端强制执行。文档检索和制造记录最终都转换为证据，生成器不能绕过检索层。

**Q：RAG 会不会拖慢过点？**

A：不会。RAG 不过问过点主事务，只消费必要事件、维护自己的读模型，或调用只读接口。RAG 故障最坏是问答不可用或证据不完整，不会阻塞生产写入。

**Q：不同车间的数据怎么隔离？**

A：租户和数据范围来自认证上下文，不由模型传入。文档元数据过滤、每一条 SQL 和 MES 只读请求都使用同一权限上下文，缓存 key 也包含权限与版本摘要，避免跨范围复用。

## 7. 口径红线

不要表述为：

- “我们已经上线 RAG”——当前是设计阶段规划；
- “RAG 已让良率提升 X%”——没有真实对照数据不能宣称；
- “LLM 可以改工艺或发返工单”——RAG 永远只读；
- “Agent 可以任意查询数据库”——只允许固定、只读、有界的工具；
- “系统能自动确认所有根因”——只能给证据、候选解释和人工确认建议；
- “追溯必须依赖图数据库”——本方案明确使用关系型读模型与只读接口。

推荐表述：

- “我规划的是一个统一 RAG，文档检索、非图制造追溯和 Agentic 是内部协同能力。”
- “追溯通过关系型读模型、固定关联查询和 MES 只读接口完成，不采用图检索。”
- “核心不是让模型多步调用，而是让每次调用都受权限、版本、证据和预算约束。”
- “先验证统一证据底座和文档检索，再增量加入追溯与多步编排，最终仍是一个服务、一套契约。”

---

## 8. 一句话定位

“给 MES 引入 RAG，不是并列建设几种 RAG，而是做一个统一的知识与证据服务：文档检索负责找到适用要求，关系型追溯负责还原制造事实，Agentic 在严格预算内补充和组合证据；全链路共享版本、权限、引用和只读约束。”
