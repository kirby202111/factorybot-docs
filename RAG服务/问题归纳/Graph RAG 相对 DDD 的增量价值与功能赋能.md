# Graph RAG 相对 DDD 模型的增量价值与功能赋能

> 本文归纳两个问题：① 引入 Graph RAG 后，相对传统 DDD 模型带来哪些好处；② 为 MES 系统新增了哪些功能、大幅改善了哪些原有功能。
> 口径同设计文档：Graph RAG 在本项目是**设计阶段的引入规划**，非线上已落地能力。

---

## 一、先厘清关系：Graph RAG 不是 DDD 的替代品

Graph RAG 与 DDD 不是二选一，而是**投影叠加**关系：

- 图的**节点** = 14 个限界上下文的聚合根实例；
- 图的**边** = 聚合间的跨上下文引用（`routeVersion` / `source_work_order_id` / `asset_id` / `batch_no`）；
- 图本身 = 领域事件的**只读投影**（CQRS 读模型），事实源仍是各上下文的聚合根。

所以真正的问题是：**在已有 DDD 模型之上，把它投影成属性图，多出来了什么能力？** Graph RAG 是 DDD 模型的"检索增强投影"，不是另起炉灶——没有 14 个上下文和跨上下文引用，图无米下炊。

---

## 二、相对传统 DDD 模型的增量价值

### 2.1 跨上下文串联：从"运行时联 5 个接口"到"一次 Cypher 一跳"

| | 传统 DDD 落地 | Graph RAG 之后 |
|---|---|---|
| 追溯方式 | 14 上下文各有服务/库/REST，跨 5 个界面手动串或应用层调 5 个 REST join | 跨上下文引用在事件投影时已建成边，一次 Cypher 一跳/两跳取齐 5M1E |
| 5M1E | 工程师脑子里的检查清单 | 确定性的图扩展路径，不需要 LLM 猜路径 |

核心边：`FOR_UNIT` / `CONSUMED_BATCH` / `SNAPSHOT_OF_ROUTE` / `PRODUCED_TESTRESULT` / `JUDGED_BY`。

### 2.2 把"隐式引用"提升为一等公民

DDD 里 `routeVersion`、`source_work_order_id` 等是聚合内字段，引用关系是**隐式**的——单库内是 FK，跨服务边界后不再可遍历。traceability 在传统 DDD 里是写路径的**副产品**（为过点防错而记录），不是可查询资产。

Graph RAG 把它们物化成显式边，traceability 从副产品升级为**可检索的核心资产**——这正是项目护城河：别人没有这套领域模型和跨上下文引用，抄不走。

### 2.3 LLM 检索接口：喂结构化子图，而不是让 LLM 自己找路

| | 让 LLM 直接查库/调 REST | Graph RAG |
|---|---|---|
| 找路径 | LLM 猜，跨服务 join | 确定性 Cypher，LLM 不找路径 |
| 权限 | 答完再裁剪，易漏 | `tenant_scope` 在 `WHERE` 前置过滤 |
| 版本 | 可能取到当前生效版（已失效） | `SNAPSHOT_OF_ROUTE` 锁当时版本 |
| 证据 | LLM 自由发挥 | 强制引用 `node_id`，无证据判失败重试 |

MES 对错误答案零容忍（错给一条失效工艺 -> 批量不良），"LLM 只综合、不找路径"不是性能取舍，是**安全取舍**。

### 2.4 版本快照的"可检索性"——与通用 RAG 最大的区别

DDD 写侧已保证版本一致（INV-09：过点记录绑 `routeVersion`）。但**检索时取当时版本**在跨服务场景下很难——要知道记录绑的是哪个版本，再去工艺服务查那个版本详情，还容易取成"当前生效版"。

图用**版本即节点 + `SNAPSHOT_OF_ROUTE` 快照边**，把"历史单件按当时工艺回放"变成带版本锚点过滤的一跳查询；工艺变更只新增版本节点、历史边不动。通用 RAG 检索文档不分版本会答出失效工艺，图从结构上杜绝这件事。

### 2.5 CQRS 读模型分离，零侵入过点主事务

图是领域事件的只读投影，与过点执行上下文已有的 `ProcessRouteCache` / `EquipmentAvailabilityCache` 同构：

- 过点 P99 ≤200ms 硬约束不受图索引影响——投影是异步消费事件，秒级最终一致可接受；
- 新增"追溯检索"能力完全不动写路径，符合 DDD 读写分离演化方向；
- 图库崩了返回 503 不阻塞生产，且节点/边全不可变 + `event_id` 幂等，**可从 Kafka 位点完整重建**，无需 MES 配合——传统 DDD 服务的库（非事件溯源）做不到这点。

### 2.6 证据链可回溯 + 置信度兜底，把 MES 防错理念带进 AI 检索

每个节点带 `source_event_id`，答案的每个假设都能回溯到原始领域事件；`confidence < 0.6` 或投影滞后超阈值 -> `needs_human_review`，不展示给操作工。

这把 MES"宁可拦下让人判"的防错理念落进了 LLM 输出层——传统 DDD 服务不存在这个维度，因为它不直接面向"给人一个带置信度的根因假设"。

### 2.7 诚实的边界

- **依赖 DDD 模型本身**：Graph RAG 放大 DDD 模型里已有的引用关系，不凭空造能力。
- **有构建/维护成本**：投影器、双层幂等、位点管理、启动断言（`ReadOnlyProjectionGate` / `assert_no_raw_data_topic`）都是实打实工程量。
- **最终一致，非实时**：秒级滞后，靠 `projection_lag_ms` 降权 + ACL 降级补齐兜底。
- **设计阶段，未落地**：讲"规划方向/设计取舍"，不讲"已经做了 GraphRAG"。

## 三、为 MES 新增的功能（传统 MES 基本没有的）

| # | 新增能力 | 图路径 | 原状 -> 新状 | MVP 覆盖 |
|---|---------|--------|------------|---------|
| 1 | **自然语言 5M1E 根因诊断** | `WipUnit{sn}` -> 五维扩展 -> LLM 假设排序 | 工程师跨 5 界面手动串、靠经验 -> 一问即出带证据链的 5M1E 假设 | ✅ Man/Material/Method/Measurement |
| 2 | **批次/供应商反向追溯（召回场景）** | `InventoryBatch` ←`CONSUMED_BATCH`← `WipUnit`；`SUPPLIED_BY` | 召回时让数据组临时写报表、慢且易漏 -> "B-77 这批锡膏进了哪些单件、现在在哪"一跳反向查询 | ✅ Material，🔴 `CONSUMED_BATCH` 边契约待对齐，MVP 先 ACL 降级补齐 |
| 3 | **跨单件共性因子挖掘 / 批次异常影响面** | `BatchQualityAnomaly` ->`AFFECTS`-> `WipUnit`；多不良回溯共同上游 | 数据分析师写 SQL 找共性 -> 图结构天然支持"这 5 个不良的共同因子"自动比对 | `BatchQualityAnomaly` 已投影；🔴 共性挖掘用 GDS 图算法属延伸，超出当前 MVP 设计 |
| 4 | **工艺变更影响面预判** | `RouteVersion` ←`BINDS_ROUTE`/`SNAPSHOT_OF_ROUTE`← `WorkOrder`/`WipUnit` | 变更评审靠人评估影响面 -> 激活新版本前反查哪些在制单件绑了旧版本，影响面一目了然 | ✅ Method |
| 5 | **L1 多步递进诊断 Agent** | 图作快路径给全貌，Agent 在某一维深挖追问 | 无 -> 复杂跨上下文递进诊断 | 对接在实现阶段五，强依赖图先建起来 |
| 6 | **诊断 + 处置一体化（与文档型 RAG 协同）** | `TraceAnswer.suggested_action` -> 路线 B `search_docs(query, version_anchor)` | 诊断结果与处置 SOP 分属两套系统 -> 给根因假设同时给带版本过滤的处置 SOP | 设计上协同，依赖路线 B 先行验证 |

## 四、大幅改善的现有功能

| 现有功能 | 原状 | Graph RAG 之后 | 关键图能力 |
|---|---|---|---|
| **质量追溯**（MES 核心价值） | "能查到"但要人工跨界面串 | 一次取齐 5M1E + AI 可解释 + 证据 `source_event_id` 可回溯 | 跨上下文边 + 结构化子图 |
| **不良品返修/报废决策** | 返修上下文 `ReworkTask` 的去向靠人判 | 5M1E 证据 + 置信度建议，低置信度转人工 | 5M1E 扩展 + `needs_human_review` |
| **供应商质量评估** | 数据组做报表、滞后、批次聚合级 | 按 `Supplier`->`InventoryBatch`->`WipUnit`->`QualityVerdict` 聚合不良率，可下钻到单件 | 反向多跳遍历 |
| **设备–质量联动**（Machine 维度） | 设备台账/维修/点检/计量与质量是两个孤岛 | 不良证据直接挂"该设备当时维修/点检/计量状态" | `USED_EQUIPMENT` + `REPAIRS`/`INSPECTS`/`CERTIFIES` |
| **审计与合规** | 人工抽审追溯记录 | 每个 AI 答案的假设都能回溯到领域事件，可解释、可复核 | `source_event_id` 证据链 |

## 五、需要诚实标注的边界

- **Machine / Environment 两维**：MVP 不覆盖，依赖设备工装台账 / 维修 / 点检保养 / 计量检定 / 设备数据接入上下文投影（§11 扩展）。表三、四中 Machine 相关改善要等这部分投影做完。
- **GDS 图算法层（共性挖掘、影响传播、关键节点）**：图结构天然支持，但当前设计未承诺，🔴 是否纳入路线待定。
- **不改变过点防错与实时性**：图是只读投影、不进过点主事务，过点判定/防错拦截这些**实时功能本身不变**，改善的是**事后诊断/追溯/分析**这一层。
- **强依赖 DDD 模型本身**：所有能力前提是 14 个上下文和跨上下文引用已建好。Graph RAG 是放大器，不是凭空造能力。

---

## 六、一句话定位

> Graph RAG 没有改变 DDD 模型的事实源地位（聚合根仍是事实源），它做的是把 DDD 模型里隐式、分散、跨服务的引用关系，投影成一个 LLM 可一次检索取齐、带版本快照、带证据链、零侵入主事务的只读属性图——**新增的是"根因诊断 / 反向召回 / 变更影响面 / 递进 Agent"等 MES 原本没有的能力，大幅改善的是"质量追溯 / 不良处置 / 供应商评估 / 设备质量联动 / 审计"等原本靠人跨界面串的核心功能**。
