# 传统 RAG vs Graph RAG 使用场景区别

> **⚠️ 适用边界**
> 本文是最初的问题梳理笔记：§一~§三 的通用对比（两种检索各自适配什么查询形态）仍成立，§三 里的"MES 典型"只是通用教科书示例，不是本仓库的选型结论。
> 原文"MES 生产数据必须用 Graph RAG"的结论**已撤回**——本仓库的制造追溯**不使用图检索**，走 MySQL 关系型读模型 + 参数化固定关联查询 + 版本锚点三段（`version_kind` / `version` / `version_ref_id`），不引入 Neo4j / Cypher / 图投影 / 快照边。
> 权威依据：[架构设计v2 · ADR-03](../../架构设计v2/00-架构决策记录ADR.md)、[rag-service-技术选型和实现方案.md](../rag-service-技术选型和实现方案.md)、[rag-service-整体结构设计.md](../rag-service-整体结构设计.md)。

## 一、核心机制差异（决定场景适配）

| 维度 | 传统 RAG | Graph RAG |
|------|---------|-----------|
| 检索依据 | 向量相似度（语义接近） | 知识图谱（实体+关系拓扑） |
| 检索单元 | 独立文本块（chunk） | 实体节点 + 关系边 |
| 跨文档能力 | 弱（块之间无关联） | 强（图遍历天然跨文档） |
| 推理深度 | 浅（top-k 拼接） | 深（多跳路径遍历） |
| 适合的查询粒度 | 局部、点状 | 全局、链状、网状 |

## 二、传统 RAG 适用场景

**查询特征：局部、事实性、答案集中在少数段落**

1. **单点知识查询**："X 的定义是什么""某不良代码 0x12 含义"
2. **独立文档检索**：SOP 作业指导书、设备操作手册、规格书查询
3. **答案局部化**：所需信息就在 1~2 个 chunk 里，不需要跨文档综合
4. **数据扁平、量大**：文档间无强关联，如 FAQ 库

> MES 典型：查某工单的 SOP、查某型号贴片机的参数说明、查某测试项的标准值。

## 三、Graph RAG 适用场景

**查询特征：全局、关系性、需要跨文档聚合或路径推理**

1. **全局总结性查询**："本月质量问题的主要主题有哪些""整个产线异常概览"（传统 RAG 只能返回相似段落，做不了主题归纳）
2. **多跳关系追溯**：物料 -> 供应商 -> 其他批次 -> 产线（链式追溯，向量检索无法跨越关系）
3. **影响范围 / 根因分析**：A 工序异常 -> 影响哪些工单 -> 影响哪些客户（图遍历天然胜任）
4. **实体密集关联**：物料、批次、工单、设备、人员、供应商之间网状关联
5. **答案分散在多文档**：需要把散落的信息按关系拼起来

> MES 典型：质量追溯（某物料来源全链路）、不良根因分析（跨工序关联）、供应商影响面排查、批次召回范围圈定。**本节只作通用教科书示例保留**：本仓库的制造追溯虽在形态上属于关系查询，但其深度固定、模式已知、关联字段已由 MES 业务契约给定，按 [ADR-03](../../架构设计v2/00-架构决策记录ADR.md) 用 MySQL 关系型读模型 + 参数化固定关联查询 + 版本锚点三段完成，**不套用 Graph RAG**。
