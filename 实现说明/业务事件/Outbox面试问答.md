## 一、动机与可靠性语义

### Q1. 为什么用 Transactional Outbox，而非"业务事务提交后直接发 Kafka"？

**A**：

- 直接发有崩溃窗口：DB commit 成功 -> 进程在 `send Kafka` 前宕机 -> 事件永久丢失（依据：§1）。
- Outbox 把"业务状态变更"和"outbox_event 插入"放**同一本地事务**原子提交，后台 Publisher 异步投递；任意时刻崩溃，未发布事件仍留表继续投递，崩溃零丢失（依据：§1）。
- 代价：每事件多一次 DB 写 + 亚秒级异步延迟，故**只用于低频业务契约事件**（依据：§1 对比表、§9.1）。

### Q2. Outbox 的可靠性语义为什么是"至少一次 + 消费端幂等"，而非 exactly-once？重复事件在哪些环节产生？

**A**：

- 跨"MySQL 事务 + Kafka 发送"两个系统无法低成本实现 exactly-once；Kafka 事务 Producer 也只解决 Kafka 内部多分区原子写，解决不了"MySQL事务+Kafka发送"的原子性（依据：§7.5）。
- 至少一次：Outbox 保证不丢（未发布留表重投），但**可能重复**--发送成功但标 SENT 前宕机，恢复后重发同一 `event_id`（依据：§7.8 重复窗口）。
- 故所有消费者必须 `event_id + consumer_group` 幂等，等效一次处理（依据：§7.8、§8.3）。

### Q3. 哪些事件走 Outbox、哪些不走？为什么说这是"架构级限流"？

**A**：

- 低频业务契约事件走 Outbox（过点/工单/维修/物料/质量/工艺版本/资产生命周期）；**高频设备原始采集不走 Outbox**，走"边缘缓冲 + Kafka 直连"（依据：适用边界、§9.1）。
- 采集若走 Outbox，`outbox_event` 会被秒级状态流写爆，§9.1 四类压力全部恶化。
- 这条边界让 Outbox 始终面对低频事件，限流参数才好定--**最根本的限流是架构级排除**（依据：§9.1）。项目级话术见 [总卡 §2.5/§4](../../面试指南/项目亮点与指标卡片.md)。

## 二、表结构与状态机

### Q4. outbox_event 的四个索引各自支撑什么？领取主索引的列顺序有何考量？

**A**：

- `uk_outbox_event_id`：生产侧去重，同一事件不重复入表（依据：§3.1）。
- `idx_outbox_publishable (status, next_retry_at, created_at)`：Publisher 领取主索引，按"状态 + 下次可投递时间 + 创建时间"扫描待发布事件（依据：§3.1）。
- `idx_outbox_topic_status (topic, status, created_at)`：按 topic 公平领取 + 按 topic 积压监控（依据：§3.1、§9.2）。
- `idx_outbox_aggregate`：按聚合根排查事件序列（依据：§3.1）。
- 列顺序：`status` 前缀先过滤待发布态、`next_retry_at` 过滤未到投递时间的重试事件、`created_at` 定序；高写表索引宜少不宜多，只留这 4 个避免写放大（依据：§3.4）。

### Q5. PUBLISHING 锁超时如何恢复？为什么这一步会导致重复发送？5 分钟阈值怎么定？

**A**：

- 恢复任务把 `locked_at` 超阈值的 `PUBLISHING` 重置为 `RETRYABLE`、清锁，立即可重投（依据：§6.3 恢复 SQL）。
- 重复来源：Kafka 已发送成功但来不及标 SENT 就宕机 -> 恢复后重发同一 `event_id`，消费端幂等吸收（依据：§6.3 注意、§7.8）。
- 5 分钟 🔴：太短 -> 正常慢发送被误判超时、重复发送增多；太长 -> 真宕机的记录卡住久、恢复延迟。按 `delivery.timeout.ms`(120s) 量级留余量定（依据：§6.3、§7.4）。

### Q6. event_id 和 outbox 主键 id 是什么关系？为什么 event_id 要建唯一索引？

**A**：

- `id`：outbox 主键，可与 `event_id` 相同或独立生成；`event_id`：全局事件唯一 ID，消费端幂等去重核心字段（依据：§3.2）。
- `uk_outbox_event_id` 唯一索引：生产侧防同一事件重复入表（命令重试/并发提交），从源头去重（依据：§3.1、§3.4）。

### Q7. consumed_event 主键为什么是 (event_id, consumer_group)？幂等保留期怎么定？

**A**：

- 不同消费组各自独立处理同一事件（如维修服务与投影服务都消费资产生命周期事件），幂等键须含 `consumer_group`，否则一组处理过会挡住另一组（依据：§3.3、§8.3）。
- 保留期 🔴：须 ≥ 最长重投窗口（PUBLISHING 超时恢复 + 重试导致的重复投递窗口）+ 安全余量，建议 ≥ Kafka retention 或 ≥ 7 天（依据：§12）。

## 三、生产侧实现

### Q8. 聚合根为什么不直接依赖 KafkaTemplate / OutboxRepository？由谁编排 outbox 写入？

**A**：

- 聚合根只表达业务事实、守不变式，依赖消息基础设施会污染领域层、违反 SRP（依据：§5.2）。
- 由**应用服务**编排：聚合根 `handle` 返回领域事件 -> 应用服务保存聚合 + 同事务写 outbox（依据：§5.1、§5.2）。
- 业务域只依赖 outbox 抽象（`OutboxEventFactory`），不直接依赖 Kafka 细节（依据：§14）。

### Q9. afterCommit 唤醒为什么不能替代轮询兜底？

**A**：

- `afterCommit` 只发唤醒信号降低延迟，不保证 Publisher 一定执行（进程刚唤醒就宕机 / 信号丢失）（依据：§5.4）。
- 可靠性靠定时轮询兜底扫 `PENDING`；即使 `afterCommit` 未执行，定时任务仍扫到（依据：§5.4）。
- 极低延迟用内存队列传 outbox id，但发布前仍须从 DB 读取并校验状态--**内存信号不可作为可靠性来源**（依据：§5.4）。

### Q10. 多实例 Publisher 如何避免重复处理？领取与发送的事务边界怎么划？

**A**：

- `FOR UPDATE SKIP LOCKED`：多实例并发领取时跳过已被其它实例锁定的行，各领各的不冲突（依据：§6.2、§6.3）。
- 领取与置 `PUBLISHING` 在**同一短事务**完成；**Kafka 发送不在该事务内**--避免 DB 长事务持行锁等 Kafka（依据：§6.2、§10）。
- 发送结果再单独 UPDATE 标记 `SENT` / `RETRYABLE` / `DEAD_LETTER`（依据：§6.3）。

## 四、与 Kafka 交互

### Q11. partition_key 怎么选？为什么禁止用随机 UUID 作 Kafka key？

**A**：

- 原则：同一聚合根事件必须有序 -> 用聚合根 ID 作 key，落同一分区保序（依据：§7.2）。
- 单据用单据 ID、资产/设备用其 ID、批次用批次 ID（依据：§7.2 表）。
- 禁随机 UUID：同聚合根事件散落多分区，顺序无法保证（依据：§7.2）。

### Q12. 为什么通常不需要 Kafka 事务 Producer？它解决不了什么？

**A**：

- 业务状态与 outbox 一致性由 MySQL 本地事务保证；Kafka 发布失败由 outbox 重试保证；重复由消费端幂等吸收（依据：§7.5）。
- Kafka 事务 Producer 解决"Kafka 内部多 topic/partition 原子写"，**解决不了"MySQL 事务 + Kafka 发送"的原子性**（依据：§7.5）。
- 故优先：`普通 Producer + 幂等 Producer + Transactional Outbox`（依据：§7.5）。

### Q13. 幂等 Producer 与 Outbox 层幂等是什么关系？为什么 max.in.flight<=5？

**A**：

- 幂等 Producer（`enable.idempotence=true`）降低 Producer **内部重试**导致的重复写入，并保分区内顺序（依据：§7.4）。
- 但消除不了 Outbox **故障恢复**导致的重复（发送成功标 SENT 前宕机重发），故仍需 Outbox 层 + 消费端 `event_id` 幂等（依据：§7.8）。
- `max.in.flight.requests.per.connection<=5`：Kafka 开启幂等时的建议上限，保证分区内重试不乱序（依据：§7.4、§7.2）。

### Q14. 限流会不会破坏分区内顺序？为什么？

**A**：

- 不会。令牌桶 / in-flight / 公平调度只改变"何时发、发多快、发哪个 topic"，**不改变分区内提交顺序**（依据：§9.5）。
- 领取按 `created_at`，发送按 `producer.send()` 调用顺序，幂等 Producer 保证分区内重试不乱序（依据：§7.2、§9.5）。
- 限流是**速率维度**，顺序是**分区维度**，两者正交可叠加（依据：§9.5）。

## 五、消费侧实现

### Q15. 消费处理顺序为何必须是"开事务->插幂等->业务->commit->ack"？各步崩溃的语义？幂等记录为何须与业务同事务？

**A**：

- 顺序：`poll -> 开本地事务 -> 插 consumed_event -> 业务处理 -> commit -> ack`（依据：§8.2）。
- commit 前失败：不 ack，Kafka 重投（依据：§8.2）。
- commit 成功 ack 前崩溃：Kafka 重投，靠幂等表主键冲突跳过（依据：§8.2、§8.3）。
- 幂等记录与业务同事务：否则出现"插了幂等但业务没成功"或反向的不一致（依据：§8.3）。

### Q16. 哪些错误直接进 DLT 不重试？DLT 之后如何处理？

**A**：

- **不可恢复错误**直接 DLT 不重试：序列化失败、topic 不存在、payload schema 非法等（依据：§6.5、§8.4 `addNotRetryableExceptions`）。
- 可恢复错误按指数退避重试，超 `max_retry_count` 进 DLT（依据：§6.5）。
- DLT 必须有告警、保留原始 payload/headers/异常摘要，人工处理或补偿，**不静默丢弃**（依据：§8.4）。
- 生产侧 `DEAD_LETTER` 经人工修复后可重置 `PENDING` 重放（依据：§13）。

## 六、限流与背压

### Q17. 生产端限流有必要吗？会不会影响用户体验？

**A**：

- **有必要，但作用在异步路径**（事务提交后异步发 Kafka），不阻塞用户同步操作（依据：§9.2、§10）。
- 正常态令牌充足 `acquire` 立即返回，不增加延迟；突发积压时限流用**可控延迟换不雪崩**（依据：§9.1、§9.2）。
- 五层里 ①领取节流 ②全局令牌桶 ④在途上限 是必须底座；③按 topic 公平 ⑤自适应背压 可后置（依据：§9.2）。
- 配额 🔴 压测后定，原则：**令牌桶速率 ≥ 常态事件产生速率峰值**，常态零等待，体验等同无限流。

### Q18. 生产端限流与消费端限流怎么区分？

**A**：

- 判据：卡"往 Kafka 发"是生产端（§9.2），卡"从 Kafka 收并处理"是消费端（§9.3）。
- **生产端五层**（作用在 Outbox Publisher -> Producer）：领取节流 / 全局令牌桶 / 按 topic 公平 / 在途上限 / 自适应背压（依据：§9.2）。
- **消费端五层**（作用在 poll + 业务处理）：`max.poll.records` / 消费端令牌桶 / Bulkhead / pause 背压 / 下游熔断（依据：§9.3）。

### Q19. 自适应背压的乘性缩减 / 加性恢复（MD/AI）是什么？为什么这么设计？

**A**：

- 监控发送延迟 p99 与失败率：恶化时**乘性缩减** `batch-size` / 增大 `fixed-delay`（MD，快速降载），恢复后**加性恢复**（AI，平稳回升）（依据：§9.2⑤）。
- 为何乘性减、加性增：病态集群要快速卸载避免打得更糟（MD），恢复时缓慢试探避免二次压垮（AI）--AIMD 经典拥塞控制思路。
- 触发 🔴：失败率 >5% 或 p99 >2s（依据：§9.6）。

### Q20. 消费端为什么用 pause/resume 背压，而不是靠 rebalance 兜底？

**A**：

- poll-ack 间隔逼近 `max.poll.interval.ms` 会触发 rebalance，消费者被踢出、分区重分配，代价大且恢复慢（依据：§8.1、§9.3④）。
- `consumer.pause(partitions)` 主动暂停拉取，处理完积压再 `resume()`，用**显式背压替代 rebalance**，分区不重分配（依据：§9.3④）。
- 配合 Bulkhead 有界线程池，避免慢路径耗尽 listener 线程（依据：§9.3③）。

## 七、重放与补偿

### Q21. Outbox 重放有哪几种场景？为什么单纯重放不会重跑业务？

**A**：

- 三场景：①生产侧死信重放（`DEAD_LETTER` 修复后重置 `PENDING` 重投）②消费端重建投影（新消费者 `earliest` 从头消费）③强制重处理 reprocess（依据：§13）。
- 单纯重放不重跑业务：`consumed_event` 已有该 `event_id` 记录，幂等会**跳过**已处理事件，避免重复副作用（依据：§13②）。
- 即"幂等是'不重复执行'的保证"。

### Q22. 要让消费方对已处理事件重跑业务，为什么不能复用原 consumer_group？

**A**：

- 复用原组，`consumed_event` 已有全部 `event_id`，幂等会全部跳过，重放等于没重跑（依据：§13③）。
- 两种做法 🔴：①**新 consumer_group** 从头消费，`consumed_event` 用新组名，等同首次处理（简单，推荐）②reprocess 模式引入"重处理标记 + 扩展幂等键"绕过旧记录（复杂，仅不能换组时用）（依据：§13③）。
- 关键认知：要"重复执行"必须**主动绕过幂等**（依据：§13）。

## 八、运维与治理

### Q23. outbox_event 大表如何治理？SENT 行为何要及时清理？

**A**：

- `outbox_event` 是高写表，每事件一 INSERT + 至少一 UPDATE，索引越多写放大越严重（依据：§3.4）。
- 治理二选一 🔴：①按月 `RANGE PARTITION`(`created_at`)，清理用 `DROP PARTITION` 替代 `DELETE` ②单表 + 定期归档 `SENT`/`DEAD_LETTER` 到归档表/对象存储（依据：§3.4）。
- MES 低频量级通常单表 + 归档即可，分区在确认单表超千万行再引入（依据：§3.4）。
- `SENT` 及时清理：否则 `idx_outbox_publishable` 扫描越过大量历史行，拖慢统计与备份（依据：§3.4、§12）。

### Q24. 哪些指标必须监控？DEAD_LETTER>0 持续 5 分钟意味着什么？

**A**：

- 必备指标：`outbox_pending_count` / `publishing_count` / `dead_letter_count` / `publish_latency_seconds` / `success_failure_total` / `retry_total` + 限流专属指标（依据：§11、§9.7）。
- `DEAD_LETTER>0` 持续 5 分钟（高）：有事件重试耗尽进死信，需人工介入或补偿，否则该事件链路断裂（依据：§11 告警）。
- 最老 PENDING 超 1 分钟（中/高）：发布延迟超 SLA；PENDING 持续增长（高）：发布/消费追不上，可能限流过严或下游慢（依据：§11）。
