# 消息全生命周期设计 — 状态、触发、限流与死信

> **定位**：把一条业务事件从"事务内落库"到"消费成功"的完整生命周期切成若干**故障域**，逐段说明该段由什么机制兜底、残留什么状态、故障时如何恢复。本文回答的是"为什么这样切"，机制参数与 DDL 以《[Outbox 设计方案](Outbox设计方案.md)》为准。
>
> **与既有文档的关系**：`Outbox设计方案.md` 是机制权威（表结构、SQL、Kafka 配置）；[点检异常 - 事件全流程](点检异常-事件全流程.md) 是单场景实例；**本文是横切的解释层**——讲清状态机为什么这么设计、触发路径为什么是两条、限流点为什么落在这些位置、死信为什么需要两套。
>
> **口径纪律**：数值均为设计容量目标 + 假设，非线上实绩（见 `Outbox设计方案.md` §0）。需按真实集群与业务 SLA 拍板的以 🔴 标注。

## 0. 全景：一条事件的五段旅程

```text
①  业务事务          ②  领取              ③  Kafka 客户端        ④  broker      ⑤  消费处理
┌────────────┐   ┌──────────────┐   ┌────────────────┐   ┌────────┐   ┌──────────────┐
│ 业务表 +    │   │ 扫 outbox    │   │ 令牌桶 → send() │   │ ISR    │   │ 幂等 + 业务   │
│ outbox 行   │──▶│ SKIP LOCKED  │──▶│ → 内存缓冲      │──▶│ 落盘   │──▶│ 变更 → ack   │
└────────────┘   └──────────────┘   └────────────────┘   └────────┘   └──────────────┘
     │                  │                    │                 │               │
   原子性            重复领取风险         内存溢出风险      broker 不可用    毒消息阻塞分区
   崩溃即丢            卡在 PUBLISHING      在途无限堆积      acks 不足丢数据   处理失败无退路
```

| 段 | 核心问题 | 兜底机制 | 失败后的"残留物" |
|---|---|---|---|
| ① 事务内 | 业务状态与待发事件是否同时成立 | 本地事务原子提交 | 全部回滚，无残留 |
| ② 领取 | 多实例抢同一条 / 领了不发 | 状态机 + `SKIP LOCKED` + 锁超时恢复 | `PUBLISHING` 行 |
| ③ 客户端 | 发送过快打爆 broker / 发送过慢堆内存 | 令牌桶 + 在途上限 + 自适应背压 | 内存中的在途请求 |
| ④ broker | 只写 leader 后 leader 失效 | `acks=all` + `min.insync.replicas=2` | 无（要么落盘要么失败） |
| ⑤ 消费 | 处理失败但 offset 已提交 / 毒消息卡分区 | 手动 ack + 幂等表 + DLT | `consumed_event` 行 / DLT 消息 |

**设计的核心思想**：每一段都必须有一个**持久化的事实载体**来记录"我做到哪了"。① 是 outbox 行本身，② 是 `status` 字段，③④ 交给 Kafka 的 ack 语义，⑤ 是 offset + 幂等表 + DLT。缺任何一段的载体，该段就没有恢复能力。

## 1. Outbox 状态设计

### 1.1 六个状态的职责

| 状态 | 可被 Publisher 领取 | 终态 | 语义 | 谁推进 |
|---|---:|---:|---|---|
| `PENDING` | 是 | 否 | 事件已落库，等待首次投递 | 应用服务写入 |
| `PUBLISHING` | 否 | 否 | 已被某实例领取，正在发送 | Publish   er 领取时置入 |
| `SENT` | 否 | 是 | 已成功写入 Kafka（ISR 确认） | Publisher 发送成功后 |
| `RETRYABLE` | 是（需到 `next_retry_at`） | 否 | 上次发送失败，等待退避后重试 | Publisher 失败时 |
| `DEAD_LETTER` | 否 | 是 | 重试耗尽或不可恢复，等待人工处置 | Publisher 判定失败终态 |
| `DISCARDED` | 否 | 是 | 人工确认不再发布 | 运维操作 |

### 1.2 状态迁移

```text
                    ┌──────────────────────────────────────┐
                    │                                      │
                    ▼                                      │
   [应用服务] ──▶ PENDING ──领取──▶ PUBLISHING ──send ok──▶ SENT（终态）
                    ▲                 │
                    │                 ├──可重试失败────────▶ RETRYABLE
                    │                 │                        │
                    │                 │     next_retry_at 到达 ─┘（重新领取）
                    │                 │
                    │                 ├──重试耗尽 / 不可恢复──▶ DEAD_LETTER（终态）
                    │                 │
                    │                 └──锁超时（实例崩溃）──▶ RETRYABLE
                    │
                    └──── 人工修复后重放 ──── DEAD_LETTER

                    DEAD_LETTER ──人工放弃──▶ DISCARDED（终态）
```

### 1.3 每个迁移的触发条件与伴随字段变更

| 迁移 | 触发条件 | 字段变更 | 失败后果（若不这样做） |
|---|---|---|---|
| `PENDING → PUBLISHING` | 被领取，`next_retry_at <= now` | `locked_by`、`locked_at` | 多实例重复发送 |
| `PUBLISHING → SENT` | Kafka 返回成功（`acks=all`） | `published_at`、清锁定字段与错误字段 | 事件被反复重发 |
| `PUBLISHING → RETRYABLE` | 可重试异常（网络、超时、`NotEnoughReplicas`） | `retry_count++`、`next_retry_at` = 指数退避 + 抖动、记录 `last_error_*` | 立即重试形成重试风暴 |
| `PUBLISHING → DEAD_LETTER` | 重试耗尽 / 不可恢复错误（序列化失败、topic 不存在、schema 非法） | `dead_lettered_at`、`last_error_*` | 无限重试，永远失败 |
| `PUBLISHING → RETRYABLE`（恢复） | `locked_at` 超时（默认 5 分钟） | 清锁定、`next_retry_at = now`、错误码 `PUBLISHING_LOCK_TIMEOUT` | 事件永久卡死，无人处理 |
| `RETRYABLE → PUBLISHING` | `next_retry_at` 到达后被重新领取 | 同首次领取 | 退避失效 |
| `DEAD_LETTER → PENDING` | 人工修复数据 / schema / 下游后重放 | 清 `retry_count`、`next_retry_at` | 死信只能靠人肉补发 |
| `DEAD_LETTER → DISCARDED` | 人工确认业务上不再需要 | 记录操作人与原因 | 死信表无限增长 |

### 1.4 状态机必须守住的不变量

1. **只有 `PUBLISHING` 能迁到 `SENT`**。更新语句带 `WHERE id = ? AND status = 'PUBLISHING'`，防止一个已被锁超时恢复的实例把状态错误地写成 `SENT`。
2. **`SENT` 是不可回退的终态**。一旦发出，任何后续动作都不得把它改回可领取状态；重复问题交给消费侧幂等，不靠生产者反悔。
3. **`PUBLISHING` 必须可超时恢复**。这是整个状态机里唯一的"活性"保证——没有它，任何一次发送中崩溃都会让事件永久滞留。
4. **`event_id` 唯一**。`uk_outbox_event_id` 在写入侧就去重，防止同一事件因重试被写两行。
5. **`DEAD_LETTER` 不得被 Publisher 自动领取**。进入死信意味着"重试不再是正确的修复手段"，必须人工判定。

### 1.5 为什么必须有 `PUBLISHING` 这个中间态

这是最容易被质疑"是不是多余"的一个状态。

若去掉它、用 `PENDING → SENT` 直接迁移，会有两个无法解决的缺陷：

- **无法区分"待发"和"正在发"**。多实例并发扫描时，A 已领取但尚未发完，B 仍会把它当成待发再领一次——重复率随实例数与扫描频率线性上升。
- **无法做锁超时恢复**。没有"领取时刻"这个事实，崩溃后无法判断"这条到底是没人领，还是领了没发"。

代价是多一次状态更新与一个恢复任务，换来的是**多实例安全 + 崩溃可恢复**，这是不可省的。

### 1.6 为什么不再多设几个状态

状态机的复杂度要花在能改变行为的地方：

- **不设 `SENDING_FAILED`**：它与 `RETRYABLE` 行为完全一致（都会被重新领取），差别只在失败原因——那是 `last_error_code` 的职责，不是状态。
- **不设 `PUBLISH_TIMEOUT`**：等价于 `PUBLISHING` 锁超时，属于恢复路径而非独立状态。
- **不把 `RETRYABLE` 拆成"可重试"与"待重试"**：`next_retry_at` 已经表达了时序，拆状态只会增加迁移分支。
- **不设 `PARTIALLY_SENT`**：不存在"半条事件"，`acks=all` 下每条事件要么获得 ISR 确认要么失败。

判据：**新状态的唯一理由是"可被领取的集合发生了变化"**。凡是只改变元信息、不改变行为差异的，都用字段表达。

## 2. 触发路径：轮询与唤醒的分工

### 2.1 两条路径，职责不同

| 路径 | 触发方式 | 作用 | 是否可靠性来源 |
|---|---|---|---|
| 定时轮询 | 空闲时等待信号，最长 `fixedDelay` 超时后必然执行一轮 | **唯一可靠的发布路径**：任何情况下事件终会被发出 | **是** |
| `afterCommit` 唤醒 | 事务提交后 `tryWakeup()` 打一个内存信号 | 消除轮询间隔（最坏 1s）的时延 | **否** |

**消息不是"事务提交后立刻由事务线程发出的"。** 事务线程只写一行 outbox、触发一次内存信号，随即返回；真正的发送由 Publisher 完成。

### 2.2 "可靠性来源"的判据

一个机制能成为可靠性来源，需要同时满足四条：

| 属性 | 轮询 DB | `afterCommit` 唤醒 |
|---|---|---|
| **持久**：进程崩溃后仍存在 | 是（`outbox_event` 行在磁盘） | 否（JVM 内存状态） |
| **可重试**：失败后能再执行 | 是（下一轮会再次扫到） | 否（只在提交瞬间发生一次） |
| **状态完整**：持有待发全集 | 是（`status` 字段即待办清单） | 否（只是信号，不含事件集合） |
| **与业务状态同源** | 是（同库、同事务提交） | 否（事务外回调） |

四条全中才算。唤醒只满足"触发"，不满足"记录"。

> 类比：**outbox 表是账本，`afterCommit` 是电话铃声**。电话没打通就去翻账本；把铃声当还款凭证，则会漏账。

### 2.3 为什么两条都不能省

- **只靠唤醒**：进程在提交后、Publisher 醒来前崩溃 → 内存信号消失 → 事件永久丢失，且生产者侧毫无察觉。
- **只靠轮询**：每次业务操作到事件发出之间空等最多 `fixedDelay`，高频业务与交互体验都无法接受。

### 2.4 实现形态

```java
// 单线程循环：有活连续跑，没活才睡；睡的时候可被 afterCommit 立即叫醒
public void run() {
    while (!stopped) {
        int n = publisher.publishBatch();                 // 领取 + 发送，SKIP LOCKED
        if (n == 0) {
            signal.await(1, TimeUnit.SECONDS);            // 空闲才退避，兼作兜底心跳
        }
    }
}
```

三个要点：

1. **`publishBatch()` 返回 0 时才睡**。积压时不退避、连续排空；空转时不空烧 CPU。
2. **用 `fixedDelay` 而非 `fixedRate`**。上一轮发完再计时，避免上一轮未结束时叠加下一轮造成并发堆积。
3. **唤醒信号不携带事件内容**。只允许叫醒，不允许把事件对象塞进内存队列直接发送——否则 outbox 行被人工处置（改 `DISCARDED`）或已被其它实例领取时，会发出本不该发的事件。

### 2.5 三条硬约束

1. **单一发送出口**：唤醒路径不得自己调 `kafkaTemplate.send()`，只能叫醒 Publisher。否则会出现两条独立发送逻辑，顺序、状态更新、限流各自为政。
2. **发送前重读并校验 `status`**：信号发出到真正发送之间，状态可能已被改变。
3. **删掉唤醒代码，正确性不变**：只是延迟从几十毫秒变成最多 1 秒。这是"优化"与"可靠性来源"的分界线——**拿掉它，正确性不变**。

### 2.6 多实例下的行为

- 唤醒信号是**本实例局部**的，A 实例的唤醒不会叫醒 B；其它实例靠各自心跳与 `SKIP LOCKED` 保持进度。
- 因此多实例时事件吞吐 ≈ 实例数 × 单实例排空速率，但**不会重复领取**（`FOR UPDATE SKIP LOCKED`）。

## 3. 限流的分段位置

### 3.1 三段式

```text
业务命令
  │
  ├─ [事务内] 写 outbox_event（PENDING） 
  │
  ▼  ────── 限流段 A：DB → 应用内存 ──────
  ① 领取节流（batch-size + fixedDelay）      保护：MySQL 主库
  ② 按 topic 公平领取                         保护：低量高紧急 topic 的延迟
  │
  ▼  ────── 限流段 B：内存 → Kafka 客户端 ──────
  ③ 全局令牌桶 acquire()                      保护：broker 与 Producer 缓冲
  ④ 在途上限 Semaphore acquire()              保护：JVM 堆
  │
  ▼
  producer.send() → RecordAccumulator（客户端内存缓冲）→ Sender 线程 → Broker
  │
  ▼  ────── 限流段 C：客户端 → broker 在途窗口 ──────
  ack 返回 → ④ release() → 标记 SENT
```

①②③ **全部发生在 `send()` 之前**——限流的主体在"消息进入 Kafka"之前完成。④ 是唯一跨越 `send()` 两侧的一层：在 `send()` 前占用额度，在 ack 回调里释放。

### 3.2 术语澄清

这里的"生产侧"指**事件生产者一侧（应用服务 + Outbox Publisher）**，是相对"消费侧"而言的边界。Kafka 文档中的 "producer-side throttling" 通常指 `buffer.memory`、`max.block.ms` 或 client-id 配额，那是 **Kafka 客户端**层，与本文的段 A/B 不是同一个层次。

### 3.3 写入侧为什么不设运行时限流

事务内那一次 `INSERT outbox_event` 是**裸的**——没有令牌桶、没有信号量，也不应该有：

```java
@Transactional(rollbackFor = Exception.class)
public void handleCommand(BusinessCommand c) {
    Aggregate a = repo.getById(c.aggregateId());
    List<DomainEvent> events = a.handle(c);      // 业务规则已在内存算完
    repo.save(a);
    rateLimiter.acquire();                        // ❌ 事务内阻塞
    events.forEach(e -> outbox.save(factory.create(e)));
}
```

三个后果，每一个都不可接受：

1. **持有连接与行锁的时间不可控**。`acquire()` 一旦阻塞，事务就一直开着，连接被占、业务行锁不释放。限流器越保守，事务堆积越严重——**本意是保护数据库，结果让数据库更惨**。
2. **拒绝的是合法业务**。令牌桶满了抛异常、业务回滚，可这个工单下发在业务上完全正确。**限流不应改变业务的成败，只能改变它生效的快慢**。
3. **污染原子单元的失败语义**。业务状态与事件本是一个原子整体，插入一个可能失败的第三方调用，等于让"业务成功"多了一个与业务无关的前置条件。

写入侧的真正控制是三道**结构性约束**（设计期决定，而非运行期拦截）：

| 手段 | 做法 | 为什么比运行时桶有效 |
|---|---|---|
| 事件粒度设计 | BOM 导入发一条 `BomImported`（带批次摘要），而非每个物料一条 | 最便宜的限流是**不产生流量** |
| 单事务事件数上限 | 约定一个业务命令产出事件数 ≤ 20~50，超出说明粒度设计有问题 | 违反时是**模型缺陷**，应由设计评审发现，不该由运行时兜 |
| 分页提交 | 批量导入按页提交事务，不在一个事务里写十万行 | 数据库物理天花板（连接池、事务耗时、redo）是最后一道约束 |

> "写入太快"的处置不是拒绝写入，而是**接受积压 + 可观测 + 人工降级**：`outbox_pending_count` 与最老 `PENDING` 时长告警，超过阈值由运维暂停批量导入入口。这是一个刻意的取舍——**业务正确性优先于消息时效性**：宁可让表变长、延迟升高，也不能让一张合法的工单下达失败。

### 3.4 为什么入库比出库慢，仍然需要领取限流

一个常见推论是："写 MySQL 比发 Kafka 慢，所以入库速率天然是瓶颈，Kafka 不会被写爆，领取不必限流。"

**稳态下这句话是对的**——`PENDING` 恒为 0 时，领取限流确实是一段永不触发的配置。但推论漏了一个前提：**写入速率与排空速率不是同一条链路，中间隔着一张可蓄水的表**。

```text
入库管道（细）              库容（outbox 表）           出库闸门（宽）
MySQL 事务 INSERT   ────▶    PENDING 行堆积    ────▶   Publisher 批量 send
受限于磁盘 fsync、行锁                          受限于内存操作速度
```

量级对比（设计目标量级，非实测）：

| 环节 | 单次操作成本 | 换算速率 |
|---|---|---|
| 写 outbox | 单事务 20ms 写 5 条事件 | ~250 事件/s（单连接） |
| 领取并发送 | `send()` 只写内存缓冲，~1μs/条 | 单轮 500 条可在 **1ms** 内完成 |
| 差距 | 磁盘 vs 内存 | **出口比入口快两个数量级以上** |

平时水位为 0，看不出差别；一旦蓄水（Kafka 抖动、消费积压、服务重启），开闸就是洪峰——**这个洪峰的速率只受 Publisher 循环速度限制，与 MySQL 写入速率毫无关系**。

四种"天然瓶颈"失效的场景：

| # | 场景 | 为什么入口慢救不了出口 |
|---|---|---|
| ① | **积压排空**（最主要） | 2 万条 `PENDING` 在 2 秒内被全部领取发送；同时 4 万次状态 `UPDATE` 打向主库 |
| ② | **领取本身是高写操作** | `FOR UPDATE SKIP LOCKED` + 批量 `UPDATE status` 是写事务：占行锁、写 undo/redo、产生 binlog。**领取限流的第一保护对象是 MySQL，不是 Kafka** |
| ③ | **多实例扩容** | 单实例 250/s 是天然降速；20 个实例同时扫表时，出口扩容 20 倍，入口速率不变，只有对 DB 的冲击变化 |
| ④ | **异步 send 让 broker 的慢不可见** | `send()` 只写 `RecordAccumulator` 就返回，broker 慢 ≠ `send()` 慢；必须先撑满 `buffer.memory` 才会以 `max.block.ms`（60s）超时的形式暴露 |

第 ④ 点尤其关键：**Kafka 的真实写入能力对应用侧不可见**，它不会让发送自动降速，而是先表现为"一切正常、内存上涨"，再突然表现为"全部线程阻塞 60 秒"。中间没有自然反馈路径——这正是必须用令牌桶 + 在途上限**主动构造反馈**的原因。

结论：**写入慢保证的是"表不会瞬间涨"，不保证"表里的积压不会瞬间排空"。** `batch-size / (fixed-delay/1000)` 给出的正是一个明确的排空速率上限——稳态不生效，积压时是唯一挡住洪峰的东西。系统在稳态和尾部都正确，才算设计完成。

### 3.5 为什么把主限流点前移

因为**限流点越靠前，过载的代价越便宜**：

| 限流点 | 过载时的表现 | 恢复方式 | 代价 |
|---|---|---|---|
| 业务入口 | 用户操作变慢 | 用户重试 | 最便宜 |
| DB 领取（①②） | outbox 表变长 | 表还在，自动追赶 | 低 |
| 客户端入口（③④） | 线程阻塞、内存占用 | 靠 `PUBLISHING` 超时恢复重发 | 中 |
| 在途窗口 | 缓冲堆积、`max.block.ms` 超时 | 靠超时恢复 | 中高 |
| broker | 请求排队、**其它服务受损** | 影响面已扩大 | 高 |
| 下游消费 | rebalance、消费停滞 | 扩分区 / 优化处理 | 最高 |

在 `send()` 之前限住，未发出的消息以 `PENDING` **持久留在 DB**，压力表现为"表多了几行"而非"堆内存满了"。这是把过载降级成"可观测、可自动恢复的积压"。

### 3.6 在途上限为什么必须跨过 `send()`

`producer.send()` 在缓冲满时会阻塞约 `max.block.ms` 后抛 `TimeoutException`。若只靠令牌桶、不控在途数，broker 一变慢，所有发送线程都卡在 `send()` 里，Publisher 的整轮被拖死——此时"限流"变成"阻塞"，连退避的机会都没有。

因此 ④ 的价值不只是"省内存"，而是**把 Kafka 客户端的内部阻塞转换成 Publisher 可感知、可主动退避的信号**：拿不到额度就结束本轮、睡眠、调小批大小。

### 3.7 与顺序保证的正交性

- **生产侧**：令牌桶 / 在途上限 / 公平调度只改变"何时发、发多快、发哪个 topic"，不改变分区内提交顺序。领取按 `created_at`，发送按 `producer.send()` 调用顺序，幂等 Producer 保证分区内即使重试也不乱序。
- **消费侧**：同一分区单线程消费，令牌桶 / Bulkhead / pause 只延迟处理，不跨分区乱序。

结论：**限流是速率维度的控制，顺序是分区维度的保证，两者正交。**

## 4. 两类死信：故障域的分界

### 4.1 位置

```text
业务事务 ──写入──▶ outbox_event ──Publisher──▶ Kafka ──消费──▶ 业务处理
              │                      │                    │
              └─ 生产侧死信：            └──── DLT：消费侧死信 ────┘
                 DEAD_LETTER                     <topic>.DLT
                 消息仍在 DB 里                  消息已被 Kafka 收下
```

### 4.2 为什么 Outbox 救不了消费失败

**Outbox 的成功是"生产者视角的成功"。** `send` 返回成功（`acks=all` 只代表 ISR 已落盘）后即标 `SENT`，Publisher 无法、也不应知道消费者是否处理成功——否则生产者将依赖所有下游，退化为同步调用的耦合。

消费失败的后果因此是：**事件在 Kafka 里按 retention 到期被删除，然后彻底消失**，而生产者侧始终显示 `SENT`，链路看上去一切正常。DLT 是失败消息在 retention 到期前的**唯一持久落脚点**。

### 4.3 两类死信的分工

| 维度 | 生产侧（`outbox_event.DEAD_LETTER`） | 消费侧（`<topic>.DLT`） |
|---|---|---|
| 消息位置 | 生产者数据库 | 已进 Kafka，被转投 DLT topic |
| 故障类型 | 序列化失败、topic 不存在、payload 非法、broker 长期不可用 | 反序列化失败、业务数据不兼容、消费代码 bug、下游依赖持续不可用 |
| 归属 | 生产者 / 运维 | 消费者 / 业务方 |
| 重试主体 | Publisher 自身 | Kafka listener error handler |
| 重放动作 | 重置 `PENDING` | 从 DLT 重投原 topic |
| 可见性 | 生产者自己可见 | 必须靠 DLT + 告警，否则无声无息 |

### 4.4 没有 DLT，毒消息会卡死整个分区

这条比"消息丢失"更致命。为了保序（按 `aggregate_id` 分区），同一分区内**不能跳过失败消息继续处理下一条**——跳过即破坏顺序。于是一条处理不了的消息会让分区**原地停住**：后续全部阻塞、积压无限增长、`max.poll.interval.ms` 超时触发 rebalance、消费近乎停滞。

所以 DLT 不是可选的容错增强，而是**保序设计的必要逃生舱**：既然不能跳过，就必须有地方把毒消息挪走。这也解释了为什么 DLT 投递要落在**同一分区号**（保留局部顺序）。

### 4.5 什么时候不该用 DLT

**业务性拒绝是正常流程，不是异常。** 例如设备已 `RETIRED`，又收到一条 `AssetSuspended`——正确做法是幂等忽略并打点，而不是进 DLT。

| 类型 | 示例 | 处置 |
|---|---|---|
| 预期内的业务状态冲突 | 已报废设备收到停用事件 | 幂等丢弃 + `consumer_noop_total` 打点 |
| 非预期的技术性失败 | 枚举值未同步、模板 ID 已删除、代码 NPE、下游持续不可用 | 重试 → 耗尽进 DLT + 告警 |

把业务拒绝也送进 DLT，会让它变成没人看的垃圾堆，真正的故障反而被埋没——这是 DLT 最常见的失效方式。

### 4.6 消费侧的"状态"在哪里

生产侧的进度记在 `outbox_event.status`，消费侧没有对应的状态表，而是由三样东西共同表达：

| 关注点 | 生产侧 | 消费侧 |
|---|---|---|
| 进度记录 | `outbox_event.status` | consumer offset（手动 ack） |
| 去重记录 | `uk_outbox_event_id` 唯一索引 | `consumed_event(event_id, consumer_group)` 主键 |
| 失败滞留 | `DEAD_LETTER` 状态行 | `<topic>.DLT` 消息 |
| 恢复动作 | 重置为 `PENDING` | 从 DLT 重投 / 换 `consumer_group` 重放 |

这个**对称性**值得注意：两侧都遵循"持久事实 + 单点去重 + 失败滞留 + 人工/自动恢复"四件套，只是载体不同。

### 4.7 DLT 必须配的五件事

1. **保留原始 payload、headers、异常摘要**，否则无法修复；
2. **有告警**，否则等同静默丢弃；
3. **有重放通道**，且重放要处理幂等——`consumed_event` 里已有记录会被跳过，需先删幂等记录或换 `consumer_group`；
4. **retention 长于业务 topic**，留出修复窗口；
5. **DLT 自身投递失败要有兜底**，否则 `DeadLetterPublishingRecoverer` 投递失败会造成无限循环。

## 5. 故障点全景推演

把状态、触发、限流、死信串成一张表——每一行都应能对应到具体的机制：

| # | 故障 | 残留状态 | 系统表现 | 兜底机制 | 归属段 |
|---|---|---|---|---|---|
| 1 | 业务事务未提交即崩溃 | 无残留 | 全部回滚 | 本地事务原子性 | ① |
| 2 | 提交后、唤醒前崩溃 | `PENDING` | 事件暂未发出 | 心跳轮询扫到 | ② |
| 3 | 领取后、`send` 前崩溃 | `PUBLISHING` + `locked_by` | 事件滞留 | 锁超时 → `RETRYABLE` | ② |
| 4 | `send` 成功、标 `SENT` 前崩溃 | `PUBLISHING` | 重复发送 | 锁超时恢复 + 消费端幂等 | ②③ |
| 5 | Kafka 短暂不可用 | `RETRYABLE` + `next_retry_at` | 事件堆积 | 指数退避重试 | ③ |
| 6 | 序列化失败 / topic 不存在 | `DEAD_LETTER` | 事件不再尝试 | 直接死信（不浪费重试） | ③ |
| 7 | 积压一次性排空 | 大量 `PENDING → PUBLISHING` | broker 承压 | 令牌桶 + 领取节流 + 公平调度 | ③④ |
| 8 | broker 变慢 | 在途数上升 | 内存占用升高 | 在途上限 → 主动退避 | ③④ |
| 9 | 只写 leader 后 leader 失效 | — | 潜在数据丢失 | `acks=all` + `min.insync.replicas=2` | ④ |
| 10 | 消费处理失败（可恢复） | offset 未提交 | 分区积压 | 重试（固定/指数退避） | ⑤ |
| 11 | 消费处理失败（不可恢复） | offset 未提交 | 分区**停滞** | 转 `<topic>.DLT` + 告警 | ⑤ |
| 12 | 消费事务提交后、ack 前崩溃 | `consumed_event` 已写 | 消息重投 | 幂等主键冲突 → 直接 ack | ⑤ |
| 13 | 修了逻辑需重跑历史事件 | `consumed_event` 拦截 | 全部被跳过 | 换新 `consumer_group` | ⑤ |

> 第 13 行是唯一的"机制自我冲突"：**幂等保证"不重复执行"，而重放要求"再执行一次"，必须主动绕过幂等。** 这一点在设计时极易遗漏，往往在上线后才发现投影重建不出来。

## 6. 关键结论

1. **每一段都要有持久化的事实载体**——没有载体，该段就没有恢复能力。① outbox 行、② `status`、③④ Kafka ack、⑤ offset + 幂等表 + DLT。
2. **可靠性来源必须可重放**。内存信号、线程回调、JMX 事件都不是；只有"能被重新查询的持久状态"才是。
3. **限流点尽量前移**。拦在 DB 里比拦在 Kafka 里便宜，拦在 Kafka 里比拦在 broker 上便宜，拦在 broker 上比让下游雪崩便宜。
4. **写入侧不设运行时限流，靠结构性约束**。事务内插限流器会拉长事务、拒绝合法业务、污染原子语义；真正有效的是事件粒度（批事件）、单事务事件数上限、分页提交——**最便宜的限流是不产生流量**。
5. **入库慢不推出排空安全**。写入与排空被 outbox 表解耦，积压排空时出口速度可比入口快两个数量级；且 `send()` 异步，broker 的慢对应用侧不可见，只会以缓冲耗尽后的阻塞形式暴露。
6. **状态机只加"改变可领取集合"的状态**，其余用字段表达，避免状态爆炸。
7. **生产侧和消费侧是对称的两套可靠性**：一边保证"不丢"，一边保证"不被静默放弃"，中间由 Kafka retention 连接。
8. **保序与容错天然冲突**（不能跳过 → 必须 DLT），冲突只能靠"把失败消息挪到旁边"化解，不能靠"跳过继续"。

## 7. 决策点 🔴

| 决策点 | 说明 | 默认建议 |
|---|---|---|
| 心跳间隔（`fixedDelay`） | 越短时延越低，但空转 DB 查询越多 | 1s，按业务时延要求调 |
| 是否启用 `afterCommit` 唤醒 | 纯粹延迟优化，不影响正确性 | 启用；低延迟场景必开 |
| `PUBLISHING` 锁超时时长 | 太短会与慢 broker 冲突导致重复发送，太长会延长卡死时间 | 5 分钟，需 > `delivery.timeout.ms` |
| 各 topic 发送配额与权重 | 取决于集群容量与业务紧急度 | 全局 200 事件/s、burst 2×，维修/质量门权重最高 |
| DLT retention | 需覆盖最长故障修复周期 | 长于业务 topic，建议 ≥ 14 天 |
| 消费侧重试次数与退避 | 与 DLT 进入时机关联 | `FixedBackOff(5s, 5)` 起步 |
| 生产侧死信是否自动重放 | 全自动有放大故障风险 | 仅人工触发，重放前校验下游健康 |
