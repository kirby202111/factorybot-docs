# 点检异常 — 事件全流程案例

> **定位**：以"设备点检发现异常"这一条真实业务链路为切片，端到端串起 Outbox + Kafka 事件骨干的**全部关键机制**——事件拆分、同事务写入、异步投递、限流、幂等消费、失败分层、死信与重放、闭环恢复。
>
> **性质**：机制权威口径以《[Outbox 设计方案](Outbox设计方案.md)》为准；本文是**该方案在一个具体场景上的实例化讲解**，不引入新的机制约束。若两者冲突，以设计方案为准。
>
> **建模权威**：[点检保养上下文 - 领域建模](../../领域模型/设备管理服务/领域建模/点检保养上下文.md) §4.2/§5、[设备工装台账上下文 - 领域建模](../../领域模型/设备管理服务/领域建模/设备工装台账上下文.md)、[设备工装台账上下文 - 实现设计](../../领域模型/设备管理服务/实现设计/设备工装台账上下文.md) §用例表。
>
> **口径纪律**：本文出现的吞吐、限流、重试参数均为**设计容量目标 + 假设**，非线上实绩（参见 [Outbox 设计方案](Outbox设计方案.md) §0）。需按真实集群与业务 SLA 拍板的阈值以 🔴 标注。

## 1. 场景定义

点检员在移动端执行某台设备的周期点检，逐项登记结果后签核。若任一项 `verdict=FAIL`，系统必须立刻让这台设备**不可用于生产**，同时通知维修侧介入，并在维修恢复后自动闭环。

| 维度 | 内容 |
|---|---|
| 触发方式 | 人工点击签核（低频：每台设备按点检周期，日均个位数） |
| 入口用例 | `SubmitInspectionResultInfo`（点检保养上下文 `TaskCommandAppService`） |
| 涉及上下文 | 点检保养、设备工装台账（**同属设备管理服务**）；维修、生产执行、计量检定（**跨微服务**） |
| 一致性要求 | 设备停用必须**立刻**生效；维修派工、看板刷新、SPC 标记允许秒级延迟 |
| 不可退让的约束 | 签核成功的那一刻，设备在系统里必须已经不可用——不能等任何消息 |

> 这个场景的价值在于它同时横跨了两种边界：**同一服务内的跨上下文**（可用本地事务）与**跨微服务的集成**（必须走事件）。大量消息设计的错误都源于把这两者混为一谈。

## 2. 关键建模前提：异常不是一条事件，而是三条

"设备异常信号"是业务口语。在领域模型里它被拆成三个语义、发布方、可靠性要求都不同的事件：

| 事件 | 语义 | 发布方（业务事实持有者） | topic | 消费者 | 允许异步？ |
|---|---|---|---|---|---|
| `InspectionCompleted(verdict=FAIL)` | 这次点检已完成，结论为不合格——**点检上下文自身的事实** | `InspectionTask` 聚合根 | `pm.*`（点检结果） | 质量分析 / SPC、追溯、看板 | 是，晚到无害 |
| `AssetSuspended(reason=INSPECTION_FAILED)` | 资产不可用——**台账上下文的资产状态事实** | `Asset` 聚合根（由点检应用服务经可用性端口触发） | `eam.asset.lifecycle` | 生产执行可用性投影、计量检定、点检规则同步 | **否**，见 §6.1 |
| `RepairSuggested(failed_items[])` | 建议维修——**跨上下文的建议，不是命令** | 点检应用服务（策略编排，非聚合根） | `pm.*` 建议类 | 维修上下文（建档派工） | 是，但要及时 |

拆分依据：

1. **聚合根只陈述自己的事实，不指挥别人。** `InspectionTask` 不知道维修上下文存在，无权发出"该建维修工单了"。`RepairSuggested` 由应用服务按"FAIL 项是否属于可维修类型"的策略编排——这是策略，不是不变式，因此不能落在聚合根内。
2. **可靠性等级不同。** 停用是不可逆的业务后果，必须事务内生效；点检结果上报是可延后的分析数据。
3. **追溯粒度不同。** 三条事件共用 `correlation_id = task_id`，排障时可按一次点检整体拉出，又各自保留独立的 `event_type` 供消费者按需订阅。

> 若合成一条 `EquipmentAbnormal` 大事件，消费方必须解析 payload 自己判断"这条消息要不要停用设备"，等于把上游的领域判断下推给每个消费者，且新增一个消费维度就要改上游事件的消费逻辑——典型的贫血事件反模式。

## 3. 上下文与 topic 映射

```text
设备管理服务（同一进程 / 同一数据库事务边界内）
├── 点检保养上下文   发布  pm.*                    （点检结果、建议、到期、超期）
└── 设备工装台账上下文 发布  eam.asset.lifecycle    （AssetSuspended / AssetReinstated / AssetRetired）
                       发布  eam.asset.metric       （运行时长、工装次数累积）
                       发布  eam.asset.availability （可用性变化）

生产执行服务    消费  eam.asset.lifecycle → 可用性投影 → 过点门禁
维修上下文      消费  pm.*（RepairSuggested）→ 建维修工单
               发布  repair.suggestion（InspectionRequested / MaintenanceSuggested，修复后请求复检）
计量检定上下文  消费  eam.asset.lifecycle（AssetSuspended 仅记录，不自动取消待执行任务）
点检保养上下文  消费  eam.asset.lifecycle（AssetReinstated → 资产规则同步）
               消费  repair.suggestion（维修请求 → 加急点检任务，INV-CX-04 合并）
```

命名遵循 `Outbox设计方案.md` §7.1：`<domain>.<aggregate>.<dimension>`，表达业务语义而非技术来源。点检保养域对外统一 `pm.*` 前缀，订阅时使用发布域的实际前缀，不做重写。

## 4. 全流程

### 4.1 总览

```text
[移动端] 提交点检结果（recordItem × N → confirm）
    │
    ▼ ──────── 同一个本地事务（设备管理服务）────────
    ① 幂等校验（commandId）
    ② InspectionTask.confirm() → verdict 计算（INV-12 / INV-20）
    ③ 应用服务策略编排 → 追加 RepairSuggested
    ④ 台账可用性端口：onInspectionCompleted() → Asset.suspend() → AssetSuspended
    ⑤ 三条事件 → INSERT outbox_event(PENDING) × 3
    ▼ COMMIT（业务状态 + 可用性投影 + 3 条 outbox 记录，原子）
    │
    ▼ ──────── 事务后，异步 ────────
    ⑥ afterCommit 仅唤醒 Publisher（定时轮询兜底）
    ⑦ FOR UPDATE SKIP LOCKED 领取 → 置 PUBLISHING
    ⑧ 全局令牌桶 + topic 公平调度 + 在途信号量 → producer.send(key = asset_id)
    ⑨ 成功标 SENT / 失败退避 RETRYABLE / 耗尽转 DEAD_LETTER
    │
    ▼ Kafka（acks=all，min.insync.replicas=2，幂等 Producer）
    │
    ├─▶ [维修]     RepairSuggested  → 建维修工单
    ├─▶ [生产执行] AssetSuspended   → 更新可用性投影 → 过点拦截
    ├─▶ [计量检定] AssetSuspended   → 记录，不自动取消任务
    └─▶ [质量/SPC] InspectionCompleted → 分析与标记
    │
    ▼ ──────── 闭环 ────────
    维修完成 → AssetReinstated → 点检规则同步 → 下个周期点检
```

### 4.2 阶段一：命令接收

移动端逐项调用 `recordItem`（`InspectionItemRecorded`，单聚合事务），最后提交 `confirm`。`confirm` 是本案例的核心事务，前置条件由聚合根守护：

- `INV-12`：所有 item 必须已登记结果才能 `Confirm`；
- `INV-20`：存在任一 `FAIL` 项则整体 `verdict=FAIL`，其余 `PASS` 项结果保留；
- 终态拒收：已签核/已跳过的任务再次 `confirm` 直接拒绝。

入口用 `commandId` 去重，防止移动端弱网重试导致重复签核。

### 4.3 阶段二：事务内编排（核心）

```java
@Transactional(rollbackFor = Exception.class)
public void submitInspectionResult(SubmitInspectionResultInfo info) {

    // ① 入口幂等
    if (commandDedup.exists(info.commandId())) {
        return;                                        // 重复提交，直接返回上次结果
    }

    // ② 聚合根执行，只返回领域事件，不接触任何中间件
    InspectionTask task = inspectionTaskRepository.get(info.taskId());
    List<DomainEvent> events = task.confirm(info.items(), info.signer(), info.signedAt());
    // events: [InspectionCompleted(FAIL, failed_items=[...])]

    // ③ 应用服务做跨上下文策略：可维修类型的 FAIL 项 → 追加建议事件
    if (repairSuggestionPolicy.shouldSuggest(task, events)) {
        events.add(RepairSuggested.of(task, failedItemsOf(events)));
    }

    // ④ 同服务内跨上下文：同步停用，不等 Kafka
    //    台账聚合根产出 AssetSuspendedEvent，同样交回应用层统一处理
    events.addAll(availabilityRecomputeService.onInspectionCompleted(
        task.assetId(), task.id(), failedItemsOf(events)));
    // → Asset.suspend(BlockingReason.INSPECTION_FAILED) → AssetSuspendedEvent

    // ⑤ 业务状态落库 + 全部事件写 outbox，同一事务
    inspectionTaskRepository.save(task);
    for (DomainEvent e : events) {
        outboxEventRepository.save(outboxEventFactory.create(e));
    }

    // ⑥ 只唤醒，不承担可靠性
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() {
            outboxPublishSignal.tryWakeup();
        }
    });
}
```

三个必须守住的点：

1. **聚合根不写 outbox、不依赖 Kafka/ApplicationEventPublisher。** 点检聚合与台账聚合都只 `registerEvent` 并返回事件；写 outbox 统一发生在应用层。这是领域层零中间件依赖的具体落点，也是单测不需要起中间件的前提。
2. **跨上下文但同服务 → 本地事务，不发消息求一致。** 台账可用性投影在同一事务内更新，对应 `INV-28`：提交失败时点检记录与投影同时回滚；提交成功时投影必须**已经**不可用，不能等待 Kafka 消费。
3. **台账上下文不以 `pm.*` 事件作为自身一致性来源**（对应台账上下文 `INV-CX-08`）。消息只用于跨服务通知，不用于服务内一致性。

### 4.4 阶段三：异步投递

事务提交后 Publisher 接管，机制细节见 `Outbox设计方案.md` §6/§9。本场景只需关注三个参数选择：

- **领取**：`SELECT ... WHERE status IN ('PENDING','RETRYABLE') AND next_retry_at <= now ORDER BY created_at LIMIT :batch FOR UPDATE SKIP LOCKED`，多实例并发安全，领取与置 `PUBLISHING` 在同一短事务，`send` 在该事务之外。
- **发送**：`acks=all` + `enable.idempotence=true` + `max.in.flight.requests.per.connection ≤ 5`；`key = partition_key`（见 §6.2）。
- **限流**：全局令牌桶统一节流，按月/按点检周期的批量签核突发不会打满 Producer；按 topic 公平调度保证批量点检的 `pm.*` 积压不饿死维修类 topic。本场景设计目标 🔴：全局 ≤ 200 事件/s、burst 2×，点检 topic 配额 ≤ 100 事件/s。

### 4.5 阶段四：消费侧

```java
@KafkaListener(topics = "eam.asset.lifecycle",
               groupId = "mes-execution.asset-lifecycle-consumer")
public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
    EventEnvelope env = objectMapper.readValue(record.value(), EventEnvelope.class);

    // 一个本地事务：幂等记录 + 业务变更
    boolean first = idempotentHandler.handleOnce(env, () -> {
        if (env.isType("AssetSuspended")) {
            availabilityProjection.markUnavailable(
                env.aggregateId(), env.reason(), env.eventId(), env.occurredAt());
        }
    });

    ack.acknowledge();              // 幂等命中或业务成功，均手动 ack
}
```

处理顺序必须是：

```text
poll → 开本地 MySQL 事务 → INSERT consumed_event(event_id, consumer_group)
     → 主键冲突？是→ 直接 ack（已处理）
     → 否→ 执行业务变更 → COMMIT → ack
```

- 事务提交前失败：不 ack，Kafka 重新投递；
- 提交后、ack 前崩溃：重复投递，被幂等表拦下（`INV-27`：同一外部 `event_id` 重复消费只执行一次）。

### 4.6 阶段五：闭环恢复

维修完成 → 维修上下文发 `AssetReinstated` → 台账聚合恢复 `IN_SERVICE` → 点检保养上下文消费该事件做资产规则同步 → 触发下一次周期点检计划。

若维修方要求复检，维修上下文发 `InspectionRequested`（`repair.suggestion`），点检域 `TaskSchedulingService.onInspectionRequested` 按 `INV-CX-04` 与同资产未执行任务合并，否则新建 `urgency=POST_REPAIR` 的加急任务。

## 5. outbox_event 实际行内容

三条事件写入同一个 `outbox_event` 表（表结构见 `Outbox设计方案.md` §3.1），字段差异如下：

| 字段 | InspectionCompleted | AssetSuspended | RepairSuggested |
|---|---|---|---|
| `event_id` | ULID | ULID | ULID |
| `topic` | `pm.*` | `eam.asset.lifecycle` | `pm.*` 建议类 |
| `aggregate_type` / `aggregate_id` | `InspectionTask` / `IT-8891` | `Equipment` / `EQ-2026-0731` | `InspectionTask` / `IT-8891` |
| `partition_key` | `EQ-2026-0731` | `EQ-2026-0731` | `EQ-2026-0731` |
| `payload` | `task_id, asset_id, verdict=FAIL, failed_items[], completed_by, completed_at` | `asset_id, reason=INSPECTION_FAILED, source_task_id, suspended_at` | `asset_id, task_id, failed_items[], suggested_at` |
| `correlation_id` | `IT-8891` | `IT-8891` | `IT-8891` |
| `causation_id` | 命令 ID | `InspectionCompleted.event_id` | `InspectionCompleted.event_id` |
| `trace_id` | 与移动端请求同一链路 | 同左 | 同左 |
| `status` | `PENDING` | `PENDING` | `PENDING` |

设计说明：

- **`partition_key` 统一用 `asset_id`，而非 `task_id`。** 消费者关心的是"这台设备的可用性状态序列"。若用 `task_id`，同一资产的 suspend / reinstate / 再次 suspend 会散落多个分区，消费方可能先看到恢复、后看到停用，投影状态机直接被写坏。**分区保序单位必须等于业务上需要保序的实体边界 = 聚合根。**
- **`correlation_id` 相同、`event_type` 不同。** 一次点检是一个因果整体，可整体检索；同时保留按类型订阅的能力。
- **`causation_id` 表达因果链。** `AssetSuspended` 由 `InspectionCompleted` 引起，排障时可反向追到起点。

## 6. 关键设计决策

### 6.1 设备停用为什么不能等 Kafka

若把 `AssetSuspended` 当作"让设备停止生产"的执行手段：

```text
点检 FAIL → 发 Kafka → 生产执行消费到 → 投影更新为不可用
                 ↑ 这个窗口内设备仍在过点，带病生产已经发生
```

因此正确切分是：**把"设备立即不可用"放在本地事务里完成，把"通知别人"放在 Kafka 里。**

- 事务成功时，台账 `AvailabilityProjection` 已置为不可用，不需要等任何消息（`INV-28`）。
- Kafka 上的 `AssetSuspended` 只承担下游跟进：维修派工、备件预占、看板刷新、计量器具停用记录。
- 生产执行侧读的是自己本地的可用性投影（异步更新），因此存在滞后窗口。**做关键判定（过点放行）时不能只信投影**——命中"可用"但该资产近期有过 lifecycle 事件时，需同步回溯台账事实源或按版本号校验。具体降级策略 🔴 待定（见 §7）。

### 6.2 为什么 `RepairSuggested` 由应用服务发

若让 `InspectionTask` 直接发 `RepairSuggested`，聚合根就承担了"什么算需要维修"这一跨上下文策略，导致：点检聚合单测要构造维修上下文语义；维修规则变化要改点检聚合。由应用服务编排则相反——**聚合根产出事实，应用服务决定向谁通报什么**，策略集中在应用层，可独立演化与测试。

### 6.3 去重为什么只在消费侧做

投递侧严格 at-least-once：`send` 成功后、标 `SENT` 前崩溃，恢复后会重发同一 `event_id`。让投递侧 100% 去重需要分布式协调，成本高且不可能完全消除窗口。因此约定：**投递侧只保证不丢，重复由消费侧 `event_id + consumer_group` 幂等吸收**，一处兜住全部重复来源（Publisher 恢复重发、Kafka 重投、人为重放）。

## 7. 故障场景推演

每个故障点对应的兜底机制，是这套设计是否闭环的判据：

| # | 故障 | 系统表现 | 兜底机制 |
|---|---|---|---|
| 1 | 签核事务未提交即进程崩溃 | 点检结果、可用性投影、outbox 记录一起回滚 | 事务原子性；用户重新提交（`commandId` 去重） |
| 2 | 事务提交后、`afterCommit` 前崩溃 | 设备已停用，但事件未发 | 定时轮询兜底扫 `PENDING`，秒级后自动发出 |
| 3 | `send` 成功、标 `SENT` 前崩溃 | Kafka 已收到，outbox 仍 `PUBLISHING` | 锁超时恢复为 `RETRYABLE` → 重发 → 消费端幂等吸收 |
| 4 | Kafka 短暂不可用 | 事件堆积在 outbox | 指数退避重试，耗尽转 `DEAD_LETTER` 并告警 |
| 5 | payload 序列化失败 / schema 非法 | 重试永不成功 | 识别为不可恢复，**直接** `DEAD_LETTER`，不浪费 20 次重试 |
| 6 | 维修服务消费者宕机 | offset 未提交，分区积压 | 重启后从上次 offset 继续（手动 ack） |
| 7 | 消费事务提交后、ack 前崩溃 | 消息重投 | `consumed_event` 主键冲突 → 跳过 → ack（`INV-27`） |
| 8 | 维修工单模板变更导致持续拒收 | 反复失败 | 重试耗尽 / 不可恢复异常 → `<topic>.DLT` + 告警 → 修模板后重放 |
| 9 | 批量点检导致事件洪峰 | Producer 与业务库承压 | 四层限流 + 自适应背压（失败率 >5% 或 p99 >2s 时乘性降批）🔴 |
| 10 | 生产执行投影滞后 | 停用后仍有极短窗口可通过 | **残余风险**：需同步校验或版本号闭环 🔴 决策点 |

> 第 10 项是这套链路**唯一不能靠消息机制自身解决**的问题——它属于跨服务的读侧一致性，必须由门禁侧的校验策略兜底。诚实记录这一项，比在文档里宣称"实时一致"更有价值。

## 8. 限流视角：突发出现在哪

| 突发来源 | 特征 | 作用点 |
|---|---|---|
| 月末/季度批量点检签核 | 数百条事件在分钟级入表 | 入口批量提交 + Publisher 全局令牌桶 |
| 换班集中签核 | 短时尖峰，`pm.*` 与 `mes.*` 同时抬升 | 令牌桶 burst 吸收，不影响过点链路 |
| 积压排空（集群抖动后恢复） | 数千 `PENDING` 一次性可领取 | 领取节流（`batch-size` / `fixed-delay`）+ 按 topic 公平调度 |
| 消费侧追不上 | 维修上下文下游建单慢 | `max.poll.records` + Bulkhead + `consumer.pause()` 背压 |

**架构级限流**：本场景的并发量级远低于设备采集链路。设备秒级原始数据**不走 Outbox**（走边缘缓冲 + Kafka 直连），这条排除让 `outbox_event` 始终只承载低频业务契约事件，限流参数才有稳定的定义域。

## 9. 死信与重放

**生产侧死信**（`outbox_event.status = DEAD_LETTER`）：人工修复数据 / schema / 下游后，重置为 `PENDING`、清 `next_retry_at`，Publisher 重新投递；消费端幂等吸收重复。

**消费侧死信**（`<topic>.DLT`）：`DefaultErrorHandler` + `FixedBackOff(5s, 5)`，`IllegalArgumentException` / `EventSchemaException` 等加入不可重试集合。DLT 消息必须保留原始 payload、headers 与异常摘要，且有告警，**不允许静默丢弃**。

**重放的关键陷阱**：若修的是消费侧投影逻辑，需要让已处理事件**重跑一次**——但 `consumed_event` 里已有 `event_id` 记录，幂等会全部跳过。此时必须换新 `consumer_group`（逻辑上等同首次处理）。核心认知：**幂等保证"不重复执行"，想"重复执行"必须主动绕过幂等。**

## 10. 可观测与告警（本场景相关）

| 指标 | 用途 | 告警条件 |
|---|---|---|
| `outbox_pending_count`（按 topic） | 点检签核后事件是否及时发出 | 最老 `PENDING` > 1min |
| `outbox_publish_latency_seconds` | `published_at - created_at` | 点检 topic p99 > 2s |
| `outbox_dead_letter_count` | 停用事件是否漏发 | > 0 持续 5min（高） |
| `outbox_publishing_count` | 卡在 `PUBLISHING` 的残留 | 持续增长 |
| `consumer_duplicate_event_total` | 重复投递频度，验证幂等是否在生效 | 突增说明恢复重发频繁 |
| `consumer_dead_letter_total` | 维修/生产执行侧拒收 | 有新增即告警（高） |
| `consumer_pause_total` | 消费侧背压触发频度 | 频繁触发需扩分区或优化处理 |

业务侧补充一条端到端断言：**签核成功但 5 分钟内生产执行侧未收到该资产的 `AssetSuspended`**，视为链路异常告警——这是唯一能发现"事务成功但事件彻底丢失"的手段。

## 12. 面试问答要点

**Q：点检域和台账域在同一个服务，为什么还要经 Kafka 通知？**
服务内跨上下文用本地事务求强一致（停用即生效），跨微服务用事件求最终一致。两层边界不同：前者解决"投影必须已经更新"，后者解决"别的服务要跟进但不能阻塞签核"。即使今天没有跨服务消费者，事件本身也是业务事实的持久审计记录。

**Q：为什么不直接同步调维修服务建工单？**
那会把维修服务的可用性变成点检签核的前置条件——维修服务抖动，点检员就签不了核。异步事件切断了这种可用性耦合。

**Q：设备异常为什么拆三条事件而不是一条？**
聚合根只陈述自己的事实。停用归属资产聚合、点检结论归属点检聚合、"建议维修"是应用层策略。合成一条会把领域判断下推给所有消费者，新增消费维度就要改上游。

**Q：重复消费建了两张维修工单怎么办？**
投递侧只保证不丢（at-least-once），去重只在消费侧做：`consumed_event(event_id, consumer_group)` 与工单创建同事务，主键冲突即跳过并 ack。去重责任集中一处，不两侧重复做。

**Q：停用了但事件发不出去会怎样？**
设备在系统里已经不可用（本地事务保证），业务不会带病放行；事件留在 `outbox_event` 由轮询兜底重发，重试耗尽进死信并告警。可靠性来自 outbox 表，不来自 Kafka 的即时可达性。

**Q：修了消费侧逻辑要重建投影，怎么重跑历史事件？**
换新 `consumer_group` 从头消费，让旧幂等记录不再拦截；不能复用原组名，否则会被 `consumed_event` 全部跳过。这是"幂等与重放的自我冲突"。
