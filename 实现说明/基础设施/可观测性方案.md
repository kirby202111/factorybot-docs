# 可观测性方案

> **定位**：本文是本 MES 项目（3 微服务 / 单车间部署）**监控与告警**的落地方案，覆盖服务器性能指标、JVM/应用指标、业务 P99/SLO、中间件指标与告警链路。技术选型为 **Prometheus + Grafana + Alertmanager + node_exporter + 各类 exporter**，应用侧以 **Spring Boot Actuator + Micrometer** 暴露指标。
>
> **适用范围**：MES 主体的制造资源 / 设备管理 / 生产执行 3 个服务及其依赖的 MySQL、Redis、Kafka。**不含** Agent / RAG 旁路的五层可观测体系（OTel SDK + Tempo/Jaeger + Loki + Grafana 统一看板），那部分见 [Agent可观测性-设计与实现方案](../../AGENT服务/Agent可观测性-设计与实现方案.md) 与 [整体技术选型与模块划分](../../整体技术选型与模块划分.md) §2.7。
>
> **与既有文档的关系**：
> - 指标的**语义与口径**权威源：Outbox 见 [Outbox设计方案](../业务事件/Outbox设计方案.md) §9.7/§11，采集见 [MES高频数据方案](../高频数据/MES高频数据方案.md) §10，Redis 见 [Redis实现说明](./Redis实现说明.md) §9，Kafka 见 [Kafka配置说明](./Kafka配置说明.md) §10。**本文不重复定义指标含义**，只解决"怎么采集、怎么查询、怎么告警"。
> - 与 [MySQL配置说明](./MySQL配置说明.md)、[Redis实现说明](./Redis实现说明.md)、[Kafka配置说明](./Kafka配置说明.md) 并列，补齐基础设施配置族。
> - 慢日志开关、`long_query_time`、慢日志路径见 [MySQL配置说明](./MySQL配置说明.md) §2；本文只讲指标的采集与慢 SQL 报告链路（§5.3/§5.4）。
>
> **口径纪律**：本文的延迟阈值、保留期、容量数值均为**设计目标 + 假设**，不是线上实绩（口径见 [项目亮点与指标卡片](../../面试指南/项目亮点与指标卡片.md) §0）。需按真实机器规格与业务 SLA 拍板的值用 🔴 标注。

## 1. 设计目标与选型结论

### 1.1 要解决的四个问题

| # | 目标 | 判定标准 |
|---|---|---|
| ① | **服务器性能可观测** | CPU / 内存 / 磁盘 / 网络 / 负载，单机异常 5 分钟内可见 |
| ② | **业务 P99 可量化** | 过点、设备实时查询等关键接口按 SLA 出 P99，能对齐"过点中实时数据查询 ≤200ms、全链路 ≤1s"的设计目标 |
| ③ | **故障可定位** | 从告警 → 看板 → 指标/日志/trace 的跳转路径不超过 2 跳 |
| ④ | **成本可控** | 单机部署，资源占用 ≤4C8G，磁盘 ≤50GB，运维零专职 |

### 1.2 选型结论

```text
采集：node_exporter（主机）+ Micrometer/Actuator（应用）+ mysqld/redis/kafka_exporter（中间件）
存储：Prometheus 单实例（15s 抓取，15 天保留）
展示：Grafana（看板 + 可选统一告警）
告警：Prometheus 规则 + Alertmanager → 钉钉/企业微信（webhook 适配器）
可选：OTel Collector + Tempo（链路追踪）、Promtail + Loki（日志检索）
```

**为什么选 Prometheus 而不是其它**：

| 选项 | 结论 | 理由 |
|---|---|---|
| **Prometheus + Grafana** ✅ | 采用 | 拉模型天然探测存活（`up` 指标）、PromQL 表达力强、exporter 生态覆盖 MySQL/Redis/Kafka、3 服务规模单实例足够 |
| Zabbix | 不采用 | 偏主机与网络设备监控，业务指标（P99 直方图）表达与聚合能力弱 |
| ELK + APM | 不采用 | 资源开销大（3 服务规模过重），日志用 Loki 更轻 |
| Thanos / VictoriaMetrics | 不引入（预留） | 单实例 2~3k 序列无需集群化；序列超 50 万或需跨集群聚合时再演进 |
| 商业 APM（SkyWalking 等） | 不引入 | 需要链路追踪时用 OTel + Tempo 即可，避免厂商绑定 |

**关键认知**：Prometheus 是**指标系统**，不是日志/链路系统。本文只解决 metrics；trace 与 log 作为可选演进（§8/§9），三者共用一套 Grafana 入口。

## 3. 采集矩阵

### 3.1 指标分层

| 层 | 内容 | 采集器 | 典型指标 |
|---|---|---|---|
| L0 主机 | CPU / 内存 / 磁盘 / 网络 / 负载 | `node_exporter` | `node_cpu_seconds_total`、`node_memory_MemAvailable_bytes`、`node_filesystem_avail_bytes`、`node_load1` |
| L1 进程/JVM | 堆内存、GC、线程、连接池 | Actuator + Micrometer | `jvm_memory_used_bytes`、`jvm_gc_pause_seconds_*`、`process_cpu_usage`、`hikaricp_connections_*`、`tomcat_threads_busy_threads` |
| L2 应用接口 | QPS、延迟直方图、错误率 | Actuator + Micrometer | `http_server_requests_seconds_bucket`、`http_server_requests_seconds_count` |
| L3 业务 | Outbox/采集/缓存等业务指标 | 自定义 Micrometer | `outbox_pending_count`、`dc_duplicate_discarded_total`、`redis_cache_hit_total` |
| L4 中间件 | MySQL/Redis/Kafka | 对应 exporter（MySQL 另加 `sql_exporter` 取 digest） | `mysql_global_status_slow_queries`、`mysql_slow_query_latency_seconds_total`、`redis_memory_used_bytes`、`kafka_consumergroup_lag` |
| L5 对象存储 | MinIO 上传成功率 | 业务侧指标（`dc_object_storage_put_*`） | 上传失败率 |

### 3.2 关键 SLA 与监控口径

| 业务链路 | 设计目标 | 依据 | 告警口径 |
|---|---|---|---|
| 过点全链路（扫码→防错→判定→记录→推进→返回） | ≤ 1s（🔴 待 SME 确认） | [在制品执行上下文](../../领域模型/生产执行服务/领域建模/在制品执行上下文.md) §4.1 | `/api/checkpoint/**` P99 > 1s 持续 5min |
| 过点中的设备实时数据查询 | ≤ 200ms（超时即保守拦截） | INV-10 / INV-CX-04，[设备数据接入上下文](../../领域模型/设备管理服务/领域建模/设备数据接入上下文.md) §4.8 | 该段 P99 > 200ms |
| 工艺/BOM 降级查询 | ≤ 500ms | 缓存降级 REST | 降级期间单独看板 |
| 事件投递成功率 | 99.99% | [Outbox设计方案](../业务事件/Outbox设计方案.md) §11 | `outbox_dead_letter_count` 有新增即告警 |
| 采集落库延迟 | 温层 P99 < 1s | [MES高频数据方案](../高频数据/MES高频数据方案.md) §7 | `dc_persist_latency_seconds` P99 |

> **口径说明**：对外简历/项目介绍中的"过点查询 P99 ≤200ms"指**过点链路中的设备实时数据查询与缓存命中路径**；端到端全链路另按 **≤1s** 计。两者口径不同，看板与告警必须分开配置，不能混为一个阈值。
>
> 以上阈值均为**设计目标**，不是线上实绩；上线后按实测重新校准（🔴 见附录 A）。

## 4. 应用侧接入（Spring Boot + Micrometer）

### 4.1 Maven 依赖（3 个服务统一）

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

### 4.2 `application.yml` 基线

```yaml
spring:
  application:
    name: ms-execution            # 每个服务不同：ms-resource / ms-equipment / ms-execution

management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      show-details: when-authorized
  metrics:
    tags:
      application: ${spring.application.name}
    distribution:
      # ① P99 必须靠直方图，Micrometer 默认不输出 _bucket
      percentiles-histogram:
        http.server.requests: true
      # ② 按 SLA 定制桶，200ms/500ms 是关键分界
      slo:
        http.server.requests: 50ms,100ms,200ms,500ms,1s,2s,5s
      # ③ 直方图上界：约束最大桶，避免超长尾把桶数量拉爆
      maximum-expected-value:
        http.server.requests: 10s
    web:
      server:
        # ④ 限制 uri tag 基数（路径参数需先归一化为 /api/orders/{id}）
        max-uri-tags: 100
        request:
          autotime:
            enabled: true
```

**参数说明**：

| 配置 | 建议 | 说明 |
|---|---|---|
| `percentiles-histogram.http.server.requests` | `true` | 不开则没有 `_bucket` 序列，**算不出可分聚合的 P99** |
| `slo` 桶 | 按业务 SLA 设 | 让 200ms 落在桶边界上，`histogram_quantile` 误差更小 |
| `maximum-expected-value` | `10s` | 直方图上界，限制桶数量；超上界请求落入 `+Inf` 桶，不影响 P99 但少一个观测点 |
| `max-uri-tags` | `100` | 限制 uri tag 基数，防止 `/orders/123` 这类路径参数生成海量序列；Boot 3.x 亦可用 `management.observations.http.server.max-uri-tags` |
| `metrics.tags.application` | 服务名 | 多服务共用一个 Prometheus 时用于区分 |
| `exposure.include` | 仅 3 个端点 | 不暴露 `env`/`heapdump` 等敏感端点 |
| 管理端口隔离 | 可选 `management.server.port=8090` | 高安全要求时只对内网开放，业务端口不暴露 actuator |

> **不要同时开客户端分位**（`autotime.percentiles` / `publishPercentiles`）：它输出的 `_p99` 值无法跨实例合并，容易被误当成全局 P99。**统一只走直方图**。

### 4.3 指标名称对照（逻辑名 → Prometheus 名）

| 既有文档逻辑指标 | Micrometer 输出 | 来源 |
|---|---|---|
| `outbox_pending_count` | `outbox_pending_count`（Gauge） | [Outbox §11](../业务事件/Outbox设计方案.md) |
| `outbox_publish_latency_seconds` | `outbox_publish_latency_seconds_*`（Timer） | 同上 |
| `outbox_dead_letter_count` | `outbox_dead_letter_count`（Gauge） | 同上 |
| `consumer_duplicate_event_total` | `consumer_duplicate_event_total`（Counter） | 同上 |
| `dc_duplicate_discarded_total` | `dc_duplicate_discarded_total`（Counter） | [高频数据 §10.1](../高频数据/MES高频数据方案.md) |
| `dc_persist_latency_seconds` | `dc_persist_latency_seconds_*`（Timer） | 同上 |
| `redis_cache_hit_total` | `redis_cache_hit_total`（Counter，tag `cache`） | [Redis §9](./Redis实现说明.md) |
| `redis_hot_query_latency_seconds` | `redis_hot_query_latency_seconds_*`（Timer） | 同上 |

> Micrometer 会把 `outbox.pending.count` 自动转换为 `outbox_pending_count`，**逻辑名与 Prometheus 名保持一致**，避免看板/告警两边对不上。

### 4.4 自定义业务指标示例

```java
@Component
public class OutboxMetrics {

    public OutboxMetrics(MeterRegistry registry, OutboxEventRepository repository) {
        // 积压量：Gauge 直接绑定查询（注意控制查询频率，用缓存值或定时刷新）
        Gauge.builder("outbox.pending.count", repository,
                r -> r.countByStatusIn("PENDING", "RETRYABLE"))
            .description("待发布事件数")
            .register(registry);

        Counter.builder("outbox.publish.success.total")
            .description("发布成功总数")
            .register(registry);

        Timer.builder("outbox.publish.latency")
            .description("created_at -> published_at 延迟")
            .publishPercentileHistogram()
            .register(registry);
    }
}
```

业务方法耗时统一用 `@Timed` / `Timer.Sample`，不要手写 `System.nanoTime()` 拼日志。

### 4.5 端点安全

- Actuator 只对 Prometheus 所在的监控网络开放，不对公网暴露。
- 生产环境关闭 `env`、`configprops`、`heapdump`、`threaddump`。
- 如需鉴权，用独立管理端口 + 网络策略，或在网关层按路径限制（避免在应用内引入额外认证链路）。

## 5. 采集端配置

### 5.1 `prometheus.yml`

```yaml
global:
  scrape_interval: 15s          # 抓取间隔
  evaluation_interval: 15s      # 规则评估间隔
  external_labels:
    cluster: mes-prod
    env: prod

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['alertmanager:9093']

scrape_configs:
  - job_name: 'mes-services'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets:
          - 'ms-resource:8081'
          - 'ms-equipment:8082'
          - 'ms-execution:8083'

  - job_name: 'node'
    static_configs:
      - targets: ['server-1:9100', 'server-2:9100']

  - job_name: 'mysql'
    static_configs:
      - targets: ['mysqld-exporter:9104']

  - job_name: 'redis'
    static_configs:
      - targets: ['redis-exporter:9121']

  - job_name: 'kafka'
    static_configs:
      - targets: ['kafka-exporter:9308']

  - job_name: 'mysql-slow-query'
    static_configs:
      - targets: ['sql-exporter:9399']   # 慢 SQL digest 采集，见 §5.3
```

**参数说明**：

| 配置 | 建议 | 说明 |
|---|---|---|
| `scrape_interval` | `15s` | 与 P99 查询窗口匹配（窗口 ≥ 4×抓取间隔）；SLA 敏感的过点接口可下调到 `10s` |
| `evaluation_interval` | `15s` | 与抓取间隔一致，避免规则评估空转或滞后 |
| `external_labels` | 标注集群/环境 | 多环境共用一个 Grafana 时用于区分 |
| `static_configs` | 3 服务直接写死 | 规模小，无需服务发现；上 K8s 后换 `kubernetes_sd_configs` |
| 保留期 | `--storage.tsdb.retention.time=15d` | 原始指标 15 天；长期趋势用 recording rules 下采样（§6.5） |

### 5.2 exporter 部署

| exporter | 部署位置 | 关键参数 |
|---|---|---|
| `node_exporter` | **每台服务器**（host 网络/pid） | `--path.rootfs=/host`，容器挂载 `/:/host:ro,rslave` |
| `mysqld_exporter` | 与 MySQL 同机或旁路 | `DATA_SOURCE_NAME=exporter:***@(mysql:3306)/`，只读账号 + `PROCESS`/`REPLICATION CLIENT` 权限 |
| `redis_exporter` | 与 Redis 同机 | `REDIS_ADDR=redis://redis:6379`，只读账号（`ACL SETUSER`） |
| `kafka_exporter` | 与 Kafka 同机 | `--kafka.server=kafka-1:9092`，只读 JMX/Admin API |
| `sql_exporter` | 与 MySQL 同机或旁路，端口 9399 | `--config.file=...`，直查 `performance_schema.events_statements_summary_by_digest`（§5.3） |

> 采集账号一律只读；exporter 自身不打业务库，避免监控成为故障放大器。

### 5.3 慢查询采集：`sql_exporter`

**为什么需要它**：`mysqld_exporter` 只暴露 `mysql_global_status_slow_queries` 计数——知道"有慢查询"，但不知道"是哪条 SQL"。`sql_exporter` 用一条 SQL 直查 `performance_schema.events_statements_summary_by_digest`，把 Top SQL 模板导成指标，补齐 SQL 维度。

**账号授权**：

```sql
CREATE USER 'sql_exporter'@'%' IDENTIFIED BY 'change_me';

-- 读 digest 表即可
GRANT SELECT ON performance_schema.* TO 'sql_exporter'@'%';

-- 如需同时读全局状态（连接数、Slow_queries）再补
GRANT PROCESS ON *.* TO 'sql_exporter'@'%';

FLUSH PRIVILEGES;
```

**`sql_exporter.yml`**：

```yaml
global:
  scrape_timeout: 10s
  max_connections: 3
  max_idle_connections: 3
  max_connection_lifetime: 5m

# 单目标模式：一个实例盯一个 MySQL；多库则起多个实例（不同端口/DSN）
target:
  data_source_name: 'sql_exporter:change_me@tcp(mysql:3306)/performance_schema?timeout=5s'
  collectors: [mysql_slow_query_digest]

collectors:
  - collector_name: mysql_slow_query_digest
    metrics:
      # 累计执行次数 → counter，Prometheus 用 rate 算调用速率
      - metric_name: mysql_slow_query_executions_total
        type: counter
        help: 'SQL 模板累计执行次数'
        key_labels: [digest, schema_name]
        values: [count_star]

      # 累计耗时（秒）→ counter，用于算平均耗时与 Top SQL
      - metric_name: mysql_slow_query_latency_seconds_total
        type: counter
        help: 'SQL 模板累计耗时'
        key_labels: [digest, schema_name]
        values: [sum_timer_wait_seconds]

      # 单次最大耗时 → gauge，用于发现长尾
      - metric_name: mysql_slow_query_max_seconds
        type: gauge
        help: 'SQL 模板单次最大耗时'
        key_labels: [digest, schema_name]
        values: [max_timer_wait_seconds]
    query_ref: slow_query_digest

queries:
  - query_name: slow_query_digest
    query: |
      SELECT
        DIGEST                AS digest,
        SCHEMA_NAME           AS schema_name,
        COUNT_STAR            AS count_star,
        SUM_TIMER_WAIT / 1e12 AS sum_timer_wait_seconds,
        MAX_TIMER_WAIT / 1e12 AS max_timer_wait_seconds
      FROM performance_schema.events_statements_summary_by_digest
      WHERE SCHEMA_NAME = 'mes_service'
        AND DIGEST IS NOT NULL
        AND COUNT_STAR > 0
      ORDER BY SUM_TIMER_WAIT DESC
      LIMIT 50;
```

**部署**：

```yaml
  sql-exporter:
    image: burningalchemist/sql_exporter:0.5
    command: ['--config.file=/etc/sql_exporter/sql_exporter.yml']
    volumes:
      - ./sql_exporter/sql_exporter.yml:/etc/sql_exporter/sql_exporter.yml:ro
    ports: ['9399:9399']
    restart: unless-stopped
```

> Prometheus 抓取配置统一放在 §5.1 的 `mysql-slow-query` job（`sql-exporter:9399`），此处不重复列。

**要点**：

| 项 | 说明 |
|---|---|
| `TIMER_WAIT` 单位 | 皮秒，除以 `1e12` 得秒 |
| `key_labels` | 必须是查询结果列；`digest` 是 64 位哈希，**不要**把 `DIGEST_TEXT` 放进 label（高基数且超长） |
| 指标类型 | `COUNT_STAR` / `SUM_TIMER_WAIT` 是累计值 → `counter`；`MAX_TIMER_WAIT` → `gauge` |
| 覆盖范围 | **全部 SQL**（含 200ms 以下），比慢日志更全；但 digest 表只有 AVG/MAX，MySQL 8.0.22+ 才有 `QUANTILE_95/99/99_9` 列（用 `SHOW COLUMNS` 确认版本支持） |
| digest 漂移 | `LIMIT 50` 下 digest 会随热点进出结果集，序列消失导致 `rate` 断点；可放宽阈值或加大 LIMIT |
| 容量 | `performance_schema_digests_size` 默认 10000，超限按 LRU 淘汰；监控其使用量 |
| 重置 | 不要定期 `TRUNCATE` 累计表，会让 `increase()` 出现假尖峰；Prometheus 已能处理 counter reset |

### 5.4 慢日志定时分析：`pt-query-digest`

**定位**：`pt-query-digest` 是 Percona Toolkit 的**命令行工具**（非中间件、非常驻），按 SQL 模板聚合慢日志，输出 Top SQL 报告——给出真实 P95/P99、完整 SQL、扫描行数。它负责"根因与优化"，不负责实时告警。

**前提**：[MySQL配置说明](./MySQL配置说明.md) §2.1 已开 `slow_query_log=ON`。`long_query_time` 按库差异化：业务库 **0.2s**（与 P99 目标对齐，避免漏检 200~999ms 区间），采集/温层库保持 **1s**。

**脚本**：

```bash
#!/bin/bash
# /opt/mysql-report/slow-report.sh
set -euo pipefail

LOG=/var/log/mysql/slow.log
OUT_DIR=/var/log/mysql/report
mkdir -p "$OUT_DIR"

pt-query-digest \
  --since '1 day ago' \
  --order-by Query_time:sum \
  --limit 30 \
  "$LOG" > "$OUT_DIR/$(date +%F).txt"
```

**cron + 日志轮转**：

```bash
# 每天 2:00 分析，报告保留 30 天
0 2 * * * /opt/mysql-report/slow-report.sh
```

```text
logrotate 每天轮转 slow.log 后执行 mysqladmin flush-logs；
cron 解析已轮转的归档文件（slow.log-YYYYMMDD），避免重复扫描在线大文件。
```

**报告怎么读**：

| 段落 | 看什么 |
|---|---|
| `Overall` | 总条数、平均/最大耗时、P95 |
| `Profile` | 按累计耗时排序的 Top SQL 模板（Response time / Calls / R/Call） |
| `Detail` | 每个模板的完整 SQL、`Rows_examined`（扫描行数）、执行计划线索 |

**与 `sql_exporter` 的分工**：

| 维度 | `sql_exporter`（digest 表） | `pt-query-digest`（慢日志） |
|---|---|---|
| 定位 | **实时告警 + 趋势** | **根因分析 + 优化** |
| 覆盖 | 全部 SQL | 仅超 `long_query_time` 的 |
| 延迟指标 | AVG/MAX（8.0.22+ 有分位列） | 真实 P95/P99 |
| SQL 明细 | digest 哈希 | 完整 SQL + 扫描行数 |
| 运行方式 | 常驻容器 + Prometheus 抓取 | cron 一次性执行 |
| 告警 | ✅ Alertmanager | ❌ 只出报告 |

> 结论：**两者互补**——`sql_exporter` 发现"变慢了"，`pt-query-digest` 回答"为什么慢、怎么改"；用 `digest` 把两份结果关联起来。

## 6. P99 与查询

### 6.1 原理：为什么必须用直方图

Micrometer 的 `http.server.requests` 是 Timer。开启 `percentiles-histogram` 后输出累计桶序列：

```text
http_server_requests_seconds_bucket{le="0.05", uri="/api/checkpoint/scan"} 120
http_server_requests_seconds_bucket{le="0.1",  uri="/api/checkpoint/scan"} 380
http_server_requests_seconds_bucket{le="0.2",  uri="/api/checkpoint/scan"} 495
...（+Inf）
```

`histogram_quantile(0.99, ...)` 在桶边界上做线性插值估算分位，**桶越贴近 SLA 越准**。

> 客户端分位（`publishPercentiles`）输出的是 `_p99` 这样的**已算好的值**，多实例之间无法正确合并——只能取平均/最大值，那是错的。**P99 必须用桶**。

### 6.2 标准查询

```promql
# 全局 P99（所有服务、所有接口）
histogram_quantile(0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket{job="mes-services"}[5m]))
)

# 按服务拆分的 P99
histogram_quantile(0.99,
  sum by (le, application) (rate(http_server_requests_seconds_bucket{job="mes-services"}[5m]))
)

# 按接口拆分的 P99（过点链路，全链路对齐 ≤1s SLA）
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket{job="mes-services", uri=~"/api/checkpoint/.*"}[5m]))
)

# 同屏看 P50/P90/P99
histogram_quantile(0.50, sum by (le) (rate(http_server_requests_seconds_bucket{job="mes-services"}[5m])))
histogram_quantile(0.90, sum by (le) (rate(http_server_requests_seconds_bucket{job="mes-services"}[5m])))
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{job="mes-services"}[5m])))
```

**写法要点**：`sum by (le)` 必须在 `histogram_quantile` **内层**，先合并所有实例的桶再估算，才是全局 P99。

### 6.3 常用 PromQL 清单

| 用途 | 查询 |
|---|---|
| 总 QPS | `sum by (application) (rate(http_server_requests_seconds_count{job="mes-services"}[1m]))` |
| 5xx 错误率 | `sum by (application) (rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum by (application) (rate(http_server_requests_seconds_count[5m]))` |
| JVM 堆使用率 | `sum by (application) (jvm_memory_used_bytes{area="heap"}) / sum by (application) (jvm_memory_max_bytes{area="heap"})` |
| 最大 GC 停顿（近 5m） | `max_over_time(jvm_gc_pause_seconds_max[5m])` |
| Hikari 连接池使用率 | `hikaricp_connections_active / hikaricp_connections_max` |
| 等待连接的线程数 | `hikaricp_connections_pending` |
| 服务启动时长 | `time() - process_start_time_seconds` |
| Kafka 消费积压 | `sum by (consumergroup) (kafka_consumergroup_lag)` |
| 副本不足分区 | `sum(kafka_topic_partition_under_replicated_partition)` |
| Redis 内存 | `redis_memory_used_bytes / redis_memory_max_bytes` |
| Redis 淘汰速率 | `rate(redis_evicted_keys_total[5m])` |
| Redis 命中率 | `sum(rate(redis_keyspace_hits_total[5m])) / (sum(rate(redis_keyspace_hits_total[5m])) + sum(rate(redis_keyspace_misses_total[5m])))` |
| MySQL 慢查询速率 | `rate(mysql_global_status_slow_queries[5m])` |
| MySQL 连接使用率 | `mysql_global_status_threads_connected / mysql_global_variables_max_connections` |

### 6.4 P99 的四个坑（面试高频）

| # | 坑 | 正确做法 |
|---|---|---|
| ① | 用平均延迟代表长尾 | 一律看 P99/P95，不看 `avg` |
| ② | 各实例分别算 P99 再取最大/平均 | `sum by (le)` 合并桶后 `histogram_quantile` |
| ③ | 查询窗口过短，锯齿/假告警 | 窗口 ≥ 4×`scrape_interval`（15s → 至少 `[1m]`，建议 `[5m]`），配 `for:` 抑制瞬时抖动 |
| ④ | 不分接口看整体 P99 | 按 `uri` 拆分，关键 SLA 接口单独设告警；同时控制 `uri` 基数（路径参数归一化为 `/api/orders/{id}`，Micrometer 默认最多 100 个 uri tag） |

### 6.5 Grafana 看板

| 看板 | 内容 | 社区模板 ID（导入后改数据源） |
|---|---|---|
| MES 全局概览 | 服务存活、QPS、5xx 错误率、P99 热力图 | 自建 |
| 服务 RED | 每服务 Request/Error/Duration + P50/P90/P99 | 自建 |
| JVM | 堆/非堆、GC、线程、连接池 | `4701` |
| 主机 | CPU/内存/磁盘/网络/负载 | `1860` |
| MySQL | 连接、慢查询、InnoDB、复制 | `7362` |
| Redis | 内存、命中率、QPS、淘汰 | `763` |
| Kafka | broker、分区、消费 lag | `7589` |

**长期趋势的 recordings**（原始指标只留 15 天，SLO 趋势要留更久）：


## 7. 告警

### 7.1 分级

| 级别 | 含义 | 通道 | 响应 |
|---|---|---|---|
| P0 | 服务不可用 / 数据丢失风险 | 钉钉 @所有人 + 电话 | 立即 |
| P1 | 核心 SLA 破线（过点 P99、事件死信） | 钉钉群 | 15min |
| P2 | 资源水位/中间件异常 | 钉钉群 | 1h |
| P3 | 趋势类（磁盘增长、缓存命中率下降） | 邮件/日报 | 次日 |

### 7.2 告警规则清单

| 告警 | 条件 | 级别 | 依据 |
|---|---|---|---|
| 服务实例下线 | `up{job="mes-services"} == 0` 持续 2m | P0 | - |
| 过点全链路 P99 破线 | `/api/checkpoint/**` P99 > 1s 持续 5m | P1 | 设计目标 ≤1s |
| 过点实时数据段超时 | 设备实时数据查询 P99 > 200ms | P1 | INV-10（>200ms 保守拦截） |
| 5xx 错误率 | > 1% 持续 5m | P1 | - |
| Outbox 死信新增 | `outbox_dead_letter_count` 增长 | P1 | [Outbox §11](../业务事件/Outbox设计方案.md) |
| Outbox 积压 | `outbox_pending_count > 1000` 持续 10m | P1 | 同上 |
| 发布延迟 | `outbox_publish_latency_seconds` P99 > 60s | P1 | 同上 |
| 消费 DLT 新增 | `consumer_dead_letter_total` 增长 | P1 | 同上 |
| 采集死信/质量恶化 | `dc_deadletter_total` 新增、`dc_quality_flag_ratio{BAD}` 上升 | P2 | [高频数据 §10.2](../高频数据/MES高频数据方案.md) |
| 缓存命中率下降 | 过点缓存命中率 < 99% 持续 10m | P2 | [Redis §9](./Redis实现说明.md) |
| Redis 内存水位 | `used_memory / maxmemory > 85%` | P2 | [Redis §8.4](./Redis实现说明.md) |
| Kafka 积压 | `kafka_consumergroup_lag > 1000` 持续 10m | P2 | [Kafka §10](./Kafka配置说明.md) |
| 副本不足分区 | `under_replicated_partition > 0` 持续 5m | P2 | 同上 |
| JVM 堆水位 | > 85% 持续 10m | P2 | - |
| GC 停顿 | `max_over_time(jvm_gc_pause_seconds_max[5m]) > 0.5s` | P2 | - |
| 连接池耗尽 | `hikaricp_connections_active / max > 0.9` | P2 | [MySQL配置说明](./MySQL配置说明.md) |
| MySQL 慢查询速率高 | `rate(mysql_global_status_slow_queries[5m]) > 0.083`（≈5 条/分钟）持续 5m | P2 | [MySQL配置说明](./MySQL配置说明.md) |
| 慢 SQL 平均耗时高 | `rate(mysql_slow_query_latency_seconds_total[5m]) / rate(mysql_slow_query_executions_total[5m]) > 0.5` 持续 10m | P2 | §5.3 |
| 慢查询采集失效 | `up{job="mysql-slow-query"} == 0` 持续 5m | P2 | §5.3 |
| 主机 CPU/内存/磁盘 | CPU > 85%（10m）、可用内存 < 10%、磁盘 < 15% | P2 | - |
| 对象存储上传失败 | `rate(dc_object_storage_put_failure_total[5m]) > 0` 持续 10m | P1 | 大载荷丢失风险 |

### 7.3 规则文件示例

```yaml
groups:
  - name: mes-service-slo
    interval: 30s
    rules:
      - alert: MesInstanceDown
        expr: up{job="mes-services"} == 0
        for: 2m
        labels: { severity: P0 }
        annotations:
          summary: "服务实例下线：{{ $labels.instance }}"

      - alert: CheckpointP99High
        expr: |
          histogram_quantile(0.99,
            sum by (le) (rate(http_server_requests_seconds_bucket{job="mes-services", uri=~"/api/checkpoint/.*"}[5m]))
          ) > 1.0
        for: 5m
        labels: { severity: P1 }
        annotations:
          summary: "过点全链路 P99 超过 1s 设计目标（当前 {{ $value | humanize }}s）"
          runbook: "依次检查 Redis 命中率、MySQL 慢查询、JVM GC 停顿、下游 REST 耗时；其中设备实时数据查询段单独按 200ms 告警"

      - alert: Http5xxRateHigh
        expr: |
          sum by (application) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum by (application) (rate(http_server_requests_seconds_count[5m])) > 0.01
        for: 5m
        labels: { severity: P1 }
        annotations:
          summary: "{{ $labels.application }} 5xx 错误率 > 1%"

      - alert: OutboxDeadLetter
        expr: outbox_dead_letter_count > 0
        for: 1m
        labels: { severity: P1 }
        annotations:
          summary: "Outbox 存在死信（{{ $value }} 条），需人工修复后重放"

      - alert: KafkaConsumerLagHigh
        expr: sum by (consumergroup) (kafka_consumergroup_lag) > 1000
        for: 10m
        labels: { severity: P2 }
        annotations:
          summary: "消费组 {{ $labels.consumergroup }} 积压持续增长"

      - alert: HostDiskWillFill
        expr: node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"} < 0.15
        for: 10m
        labels: { severity: P2 }

  - name: mysql-slow
    interval: 30s
    rules:
      - alert: MySQLSlowQueriesHigh
        expr: rate(mysql_global_status_slow_queries[5m]) > 0.083
        for: 5m
        labels: { severity: P2 }
        annotations:
          summary: "MySQL 慢查询速率偏高（{{ $value | humanize }} 条/秒）"
          runbook: "取慢日志 Top SQL；结合 QPS/连接数判断是索引缺失还是突发写入"

      - alert: MySQLSlowQueryAvgHigh
        expr: |
          (
            rate(mysql_slow_query_latency_seconds_total[5m])
            / rate(mysql_slow_query_executions_total[5m])
          ) > 0.5
        for: 10m
        labels: { severity: P2 }
        annotations:
          summary: "SQL 模板 {{ $labels.digest }} 平均耗时超过 500ms"

```

### 7.5 降噪

- **抑制**：`MesInstanceDown` 触发时抑制同实例的 P99/错误率告警（避免雪崩式刷屏）。
- **分组**：按 `alertname + application` 分组，一次故障只发一条聚合消息。
- **静默**：发布窗口、计划内维护用 Grafana/Alertmanager 静默，**不通过降低阈值来"消灭"告警**。
- **告警必须可行动**：每条规则写 `runbook`，指向排查路径；不可行动的告警直接删除。

## 8. 链路追踪（可选演进）

### 8.1 何时引入

| 信号 | 动作 |
|---|---|
| 跨服务调用超过 3 跳、排障靠"猜哪个服务慢" | 引入 OTel + Tempo |
| 需要按 `trace_id` 把日志、指标、事件串起来 | 同步引入（trace_id 注入日志） |
| 当前只有 3 服务、P99 拆到接口级已能定位 | **先不引入**，避免多一套组件 |

### 8.2 形态

```text
Java 服务（OTel javaagent，-javaagent:opentelemetry-javaagent.jar）
  └─ OTLP ─> OTel Collector ─┬─> Tempo（trace 存储，Grafana 查火焰图）
                             └─> Prometheus（可选：span metrics / RED 指标）
```

- Java 侧无侵入接入，`OTEL_SERVICE_NAME` 与 `spring.application.name` 保持一致。
- 跨语言（Python Agent → Java MES）靠 W3C `traceparent` 串联，细则见 [整体技术选型与模块划分](../../整体技术选型与模块划分.md) §1.3。
- 业务链路串联仍以 `correlation_id` / `causation_id` 为准（[Kafka集成全景与实现说明](../Kafka集成全景与实现说明.md) §5.1），trace 是**技术链路**，业务链路不是它。
- 采样：默认 10% 头部采样 + 错误全采；采集链路（高频）不上 trace，避免采样成本打爆 Collector。

## 9. 日志（可选演进）

- 引入时机：需要按 `trace_id` / 订单号 / 设备号检索日志，或审计要求留存。
- 形态：应用输出 JSON 日志（含 `trace_id`/`span_id`/`application`）→ Promtail → Loki → Grafana。
- 保留：热查 7 天，归档 30~90 天（🔴 按审计要求）。
- 与指标的分工：**指标回答"有没有问题"，日志回答"为什么"**；不要用日志做指标统计（成本高、延迟大）。

### 10.3 容量估算

```text
活跃序列 ≈ 3 服务 × 200（HTTP/JVM/Hikari/业务） + node 500 + mysql 200 + redis 100 + kafka 100
        ≈ 1,600 ~ 2,500 条
采样量  ≈ 2,500 × (60/15) × 60 × 24 × 15 ≈ 2.2 亿样本/15 天
磁盘    ≈ 2 ~ 5 GB（压缩后，含索引）
```

结论：**单机 2C4G 足够**，不需要 Thanos/VictoriaMetrics。序列超过 50 万或需要跨集群聚合时再评估横向扩展。

### 10.4 保留与备份

| 项 | 建议 |
|---|---|
| Prometheus 原始指标 | 15 天（`--storage.tsdb.retention.time=15d`） |
| SLO 长期趋势 | recording rules 下采样为 1m 精度，长期保留（或用外部对象存储快照） |
| Grafana 配置 | 用 provisioning 文件（`dashboards/`、`datasources/`）而非手工点，纳入 Git |
| Alertmanager 配置 | 纳入 Git，变更走 review |
| Prometheus 快照 | 升级前 `POST /-/snapshot` 或在停机窗口备份 `prometheus-data` 卷 |

## 12. 关键原则总结

1. **3 服务规模用单机栈**：Prometheus + Grafana + Alertmanager 足够，Thanos/VictoriaMetrics 是序列超 50 万后的选项，不是起步配置。
2. **P99 必须靠直方图**：`percentiles-histogram` 必须开；多实例聚合先 `sum by (le)` 再 `histogram_quantile`；客户端分位不可聚合。
3. **按接口看 SLA，不看整体平均**：过点全链路 ≤1s、其中设备实时数据查询 ≤200ms 分别成规则，整体 P99 会被快接口稀释。
4. **指标、日志、链路分工明确**：指标回答"有没有问题"，日志回答"为什么"，链路回答"慢在哪一跳"；三者共用 Grafana 入口，不重复造采集管道。
5. **告警必须可行动**：每条规则有 runbook、有级别、有通道；不可行动的告警直接删，静默替代降阈值。
6. **监控自身不能成为故障放大器**：exporter 只读、采集与业务隔离、Prometheus 故障不影响业务链路（应用不依赖监控即可运行）。
7. **配置即代码**：Prometheus 规则、Alertmanager 路由、Grafana 看板全部进 Git，环境间可复现。
8. **口径诚实**：SLA 是设计目标就标"设计目标"，没有实测数据就不写"线上 P99 = xx ms"（对齐 [项目亮点与指标卡片](../../面试指南/项目亮点与指标卡片.md) §0）。
9. **慢查询分两层**：指标层（`sql_exporter` + digest 表）负责实时发现与告警，日志层（`pt-query-digest`）负责根因与优化；只有计数没有明细等于没定位。`pt-query-digest` 是命令行工具，不是中间件（§5.3/§5.4）。
