# 重连补传洪峰处理方案

> **项目背景与规模口径**：本项目为解决 PCBA 电子制造 + 整机组装混合车间追溯链断点多、过点防错要求高、产品 BOM/工艺版本组合复杂的问题，基于 DDD 与微服务架构设计并实现车间全流程管理平台。系统面向 **6 条产线、100 多种物料大类、600 多型号产品**的业务规模，拆分为 3 个微服务、14 个限界上下文，覆盖工单、过点执行、工艺、质量、设备运维全流程；跨服务一致性采用 Transactional Outbox + Kafka，高频设备采集与低频过点主事务解耦，过点查询 P99 ≤ 200ms；采集数据包含**环境数据与设备数据**两类，设备数据采集（网关/协议适配侧）由其他团队负责、本方案只管平台接入侧；全车间按 **500 QPS** 速率上传，单条报文**最大不超过 1MB**、全量走 Kafka 直连（topic 级调限，见 §10）。过点拍照（AOI 图像等）大载荷另走文件服务器，归生产执行服务负责、不在本文范围（边界说明见 §9）。本文所有量级推导均基于该规模口径。
>
> **定位**：本文是 [MES 高频数据方案](MES高频数据方案.md) 的**专题深挖**，单讲"网关重连后补传洪峰"这一场景的全流程处理——从断连发生、本地缓冲、游标补传，到洪峰过 Kafka 直连管道、平台去重与乱序矫正、限流背压、下游消费与观测闭环。
>
> **与权威文档的关系**：事实源是 [MES 高频数据方案](MES高频数据方案.md) §4.3/§4.4/§6/§8/§9/§10 与附录 A，本文每节标注 `依据：§X` 回指，不重复其参数实现，只把散落在各节的机制**按"一次重连恢复"的时间轴组装成完整链路**，并给出设计取舍的判断。领域契约（聚合根 / 事件 / 不变式编号 INV-04/05/07/11/15、BIZ-02/03、INV-CX-01/02/09）的权威源是 [设备数据接入上下文 - 领域建模](../../领域模型/设备管理服务/领域建模/设备数据接入上下文.md)，本文只引用不重复定义。面试防守话术见 [MES 高频数据面试问答](MES高频数据面试问答.md)。

## 0. 口径纪律

本文出现的频率、吞吐、保留期数值均为**基于项目业务规模（6 条产线、100 多种物料大类、600 多型号产品；采集数据含环境数据与设备数据、设备采集由网关侧负责，全车间上传约 500 QPS、单条最大 1MB、全量走 Kafka 直连）推导的设计容量目标 + 假设**，不是线上实绩（与 [MES 高频数据方案](MES高频数据方案.md) §0 同口径；该文按单线量级估算，本文按项目全量推导）。需按真实集群容量与车间实测量拍板的阈值用 🔴 标注，交还运维/架构决策，不自行编造 SLA。

## 1. 场景定义：什么是"补传洪峰"

**触发**：网关与设备通道断连后进入缓冲模式，恢复重连时 `BackfillService` 按 `BackfillCursor` 游标**顺序集中重发**缓冲期内的全部报文；且恢复初期 `resuming=true` 期间新报文必须排在补传队列之后（INV-05 先补后新）——于是流量不是匀速恢复，而是**集中一阵打出来**，即"洪峰"（依据：§4.4、领域建模 §1.5/§3.3）。

**量级估算**（🔴 待实测拍板）：补传报文量 = 断连时长 × 单网关峰值速率。以全车间 500 QPS 上传速率计，单线网关均摊约 80~90 QPS；一条产线网关断连 30 分钟，恢复时待补传量约 **15 万条**（单条均为百字节级结构化报文，合计数十 MB）——集中一阵重发，即"洪峰"的规模量级。单条上限 1MB 只是峰值（偶发大消息由 Kafka topic 级调限承接，见 §10.2），洪峰 sizing 按报文条数计、不按峰值字节吓自己。缓冲容量、去重表写入量、温层落库批量均以此为输入（依据：§4.3 缓冲容量 = 最长预估断连时长 × 峰值速率）。

**两个伴生效应**（洪峰之所以难处理的根源）：

| 效应 | 成因 | 由谁吸收 |
|---|---|---|
| **重复** | ① 断连前已发送成功、但网关宕机前未推进 `backfilled_cursor`，恢复后按游标重发同一 `msg_id`；② Producer 内部重试（幂等 Producer 降低但**不能消除**断点续传导致的重复）；③ 补传流程自身重发 | 平台 `msg_id` 去重（BIZ-02） |
| **乱序** | 补传报文的 `source_ts` 属于过去区间，与恢复后的新报文交叉到达 | 平台按设备时间窗乱序矫正（INV-04） |

> 依据：§4.4 注（"不丢换可能重复，由去重兜底"）、§5.3 注（Producer 幂等的边界）、§6.1/§6.2。

## 2. 全流程时序（一次重连恢复的完整链路）

```text
T0 正常态   设备→网关 ProtocolAdapter 解码→DataPacket.seal(msg_id+ts 三元组+质量标)
            →dispatch()→PacketDispatched→Kafka 直连（partition_key=equipment_id 保序）
            └ 环境/设备数据均为结构化报文（单条 ≤1MB）→Kafka 直连（调限见 §10.2；过点拍照走文件服务器，归生产执行服务，见 §9）

T1 断连     HeartbeatMonitorService 心跳超时→Equipment.markSuspect（ONLINE→SUSPECT）
            +CollectionChannel.degradeChannel（ESTABLISHED→DEGRADED）→触发重连
            FrameIngestionService 按连接态分流→enqueueBackfill(cursor)
            →BackfillEnqueued→写本地缓冲，buffered_cursor++（INV-05 单调递增）
            重连失败 N 次→markOffline+enterBufferMode+ChannelEscalated
            （发布 dc.equipment.lifecycle→台账上下文 SuspendAsset，本上下文不停用 INV-CX-02）

T2 缓冲期   报文持续入本地缓冲；水位监控（dc_backlog_pending）
            水位超阈值→向设备侧降速（协议支持时）或打 BAD 质量标+告警
            缓冲容量=最长预估断连时长×峰值速率 🔴；BackfillCompleted 后按位点释放

T3 恢复     ReconnectService.onReconnectSucceeded
            →BackfillService.onChannelRestored→BackfillCursor.beginResume
            →BackfillResuming（resuming=true）
            →按 cursor 顺序逐条 advance 重发 Kafka
            →backfilled_cursor==buffered_cursor→complete()→BackfillCompleted(backfilled_count)
            →解除降级：recoverEquipment/clearSuspect+restoreChannel

T4 洪峰过管道（核心，见 §3/§4）
            网关层：攒批发送+在途上限，防补传瞬间 Producer 缓冲 OOM
            Kafka 层：持久化日志天然吸收堆积；独立 client-id 配额隔离业务 topic
            平台层：PlatformIngestionService 四步管道+限流背压

T5 下游     各上下文按 msg_id 幂等消费；运行时长聚合按 (equipment_id,period)
            去重+区间合并（BIZ-03）；SPC 依赖矫正后的时序；热层最新值覆盖写刷新

持续观测    dc_backlog_pending / dc_backfill_total / dc_duplicate_discarded_total
            / dc_late_arrival_total / dc_consumer_lag + 分级告警（见 §7）
```

依据：§4.4 断点续传时序、§5.5、§8.2、§10；领域建模 §3.2/§3.3/§3.5。

## 3. 洪峰过管道：三层各自兜什么

补传洪峰是**端到端链路压力**，不是某一层单独消化的。§8.1 把采集侧压力分四类，其中"平台去重"的触发场景正是**补传排空**：

| 层 | 洪峰风险 | 手段 | 依据 |
|---|---|---|---|
| **网关**（源头） | 补传瞬间集中发送，Producer 缓冲/Future 堆积 OOM | 攒批发送（`linger.ms=50`+`batch.size=128KB`，§5.3）+ 在途上限 Semaphore 限制未 ack 的 `send()` 数 + 缓冲水位背压 | §8.2 |
| **Kafka** | 突发写击穿 broker、拖累同集群业务 topic | Kafka 作为持久化日志天然吸收堆积（`acks=all`+`min.insync.replicas=2`，3~7 天保留即重放窗口）；真正防的是共享集群被拖累——采集独立 client-id（`*-dc`）设 `producer_byte_rate` 集群配额，broker 延迟响应逼 Producer 退避 | §5.2/§5.3/§8.4 |
| **平台接入**（处理重点） | 补传排空打爆去重表写放大、温层落库 | 去重吞吐上限 + Kafka consumer pause 背压；落库批量化 + 温层写入令牌桶 | §8.1/§8.3 |

> **判断**：洪峰的终点不是 Kafka 而是平台去重与落库——Kafka 只是缓冲，平台侧才是"消化"洪峰的地方。这也是简历/面试中"平台采集接入管道扛住重连补传洪峰"一句的技术实质。

## 4. 平台侧四步管道（消化的核心）

`PlatformIngestionService.onPacketReceived`（领域建模 §3.6）编排四步：`PacketReceived → Deduplicate → BufferReorder → PersistAndPublish`（依据：§6 总述）。

### 4.1 msg_id 去重（BIZ-02）

```text
PacketReceived(msg_id, ...)
  → 查去重表
      命中  → DuplicateDiscarded        （丢弃，不落库不分发）
      未命中 → INSERT 去重表(msg_id)     （占位，防并发重复）
              → PacketAccepted → 进入乱序矫正/落库/分发
```

- **存储选型**：全车间上传约 500 QPS，DB 唯一索引写入余量约两个量级，v1 主推（INSERT 冲突即判重）；Redis 布隆 + DB 兜底预案仅当量级增长到持续 TPS 1000~10000 时评估启用（>10000 必要）；Redis SET + 异步落 DB 需处理一致窗口（依据：§6.1）。
- **关键约束：去重表保留期 ≥ 最长补传窗口 + 安全余量（建议 ≥7 天，与死信保留窗口对齐）**，按 `received_ts` 定期清理超期 `msg_id`——补传报文是"旧 `msg_id` 迟来"，判重依据过期等于去重失效（依据：§6.1）。
- 🔴 去重存储方案与保留期按实测 TPS 与补传窗口拍板（附录 A）。

### 4.2 乱序矫正（INV-04）

```text
BufferReorder:
  按 equipment_id 分组，维护近期 source_ts 窗口
  到达报文:
    source_ts 在窗口内且有序 → 直接通过
    source_ts 落后于窗口已提交位点 → LateArrivalReordered（打 LATE 质量标补入）
    source_ts 超前 → 缓冲等待中间报文，超时则放行（避免无限阻塞）
```

- 窗口数百 ms~数秒 🔴，超时放行阈值取窗口 2~3 倍；过大增延迟、过小矫正失效（依据：§6.2）。
- 只对**需要严格时序的聚合**（SPC、运行时长）启用；纯离散事件（过板、拧紧）按到达顺序处理即可，可绕过窗口；🔴 哪些 topic 启用待定（依据：§6.2）。
- 时钟漂移超阈值（建议 3s）按 `ingest_ts` 修正并记录 `clock_skew`，`source_ts ≤ ingest_ts` 始终成立（INV-11/INV-04，依据：§9.4）。

### 4.3 落库与分发（非原子，刻意设计）

- 去重 + 矫正通过后：`markPersisted → PacketPersisted`（落温层，§7.2）+ `markPublished → PacketPublished`（分发到下游 `dc.*` 主题）（依据：§6.3）。
- **落库与分发不在同一事务**（Kafka 发送不与 DB 事务原子）：落库成功但分发前宕机，靠 Kafka 重投 + 消费端 `msg_id` 幂等兜底——与 Outbox 的可靠性边界同理、不同量级（依据：§6.3）。
- 温层写入**批量化**（攒批 INSERT），减少 DB 往返（依据：§8.3）。
- 热层实时快照在 `PersistAndPublish` 时同步覆盖写刷新（Redis 按 `equipment_id` 存最新值，读过点 ≤200ms INV-CX-04）（依据：§7.1）。

### 4.4 限流与背压（洪峰期的节流阀）

- **去重吞吐上限**：`PlatformIngestionService` 限制单实例去重 QPS，超限则 **Kafka consumer pause**（与 Outbox 慢消费者 pause 同构）——背压让压力显形为 `consumer_lag`，而不是丢数据（依据：§8.3）。
- **温层写入令牌桶**：保护 MySQL/TSDB 不被采集流写爆（依据：§8.3）。
- **集群级配额兜底**：采集 client-id（`*-dc`）独立 `producer_byte_rate`，与业务事件配额隔离（依据：§8.4）。

> **为什么背压用 pause 不用丢弃**：采集"不丢"是硬承诺，洪峰期丢数据违背它；pause 把压力变成可见的 lag，Kafka 3~7 天保留期就是天然重放窗口，消费恢复后自动追平——这是"用延迟换不丢"的显式取舍。

## 5. 下游与聚合的补传兼容

补传数据到达下游时带着"旧时间戳 + 可能重复"两个特征，各消费方的兼容处理：

| 消费方 | 补传影响 | 处理 |
|---|---|---|
| 通用消费 | 重复报文 | 消费端按 `msg_id` 幂等（第三层兜底，依据：§2.3/§9.2） |
| 运行时长聚合 | 补传 ts 落在原始在线区间内 | `RunHourAggregationService` 按 `(equipment_id, period)` 去重 + 在线区间合并，保证不重复聚合（BIZ-03） |
| SPC / 质量分析 | 依赖严格时序 | 依赖 §4.2 乱序矫正后的到达序；迟到点打 LATE 标可被分析端识别 |
| 过点执行（读热层） | 补传的是历史值 | 热层只存最新值（覆盖写），历史值自然不进快照；过点判定不受污染 |

依据：§2.3、§6.2、§7.1、§9.2；领域建模 §3.3 注（补传数据时间戳已在原始区间内）。

## 6. 关键设计决策（面试防守点）

1. **"不丢"与"不重"是取舍关系，不是双全**：先补后新（INV-05）保证顺序与不丢，代价是断连前已发成功但游标未推进的报文会重复发送；重复由平台去重吸收。§4.4 原文即"不丢换可能重复，由去重兜底"——被追问"为什么不做到完全不重"时，这是第一答案（依据：§4.4、§2.2）。
2. **去重表保留期必须 ≥ 最长补传窗口**：这是最容易被忽略的约束——补传是"旧 `msg_id` 迟来"，保留期短于补传窗口时判重依据已过期，去重形同虚设（依据：§6.1）。
3. **背压用 consumer pause 而非丢弃**：换延迟不换丢失；Kafka 保留期即重放窗口（依据：§8.3、§5.2）。
4. **落库与分发刻意非原子**：高频场景 DB 事务 + Kafka 发送原子的代价不可承受，降级为最终一致 + 消费端幂等（与 Outbox 同思路、不同量级）（依据：§6.3）。
5. **容量边界决定洪峰上限**：缓冲容量 = 最长预估断连时长 × 峰值速率；超容量后的丢弃策略需定（建议打 BAD 质量标 + 告警，保链路不阻塞），这是"能扛多久断连"的物理上限（依据：§4.3、附录 A）。
6. **文件服务器的边界**：本文范围（设备/环境数据，单条 ≤1MB）全量走 Kafka 直连、不经过文件服务器，"消息到了、文件没到"的悬空引用风险在架构上不存在；过点拍照（AOI 图像等）大载荷虽需文件服务器，但归过点执行上下文（生产执行服务）负责——被问"拍照/大文件怎么处理"时按此边界回答（§9）。

## 7. 可观测与告警（洪峰期的仪表盘）

**指标**（依据：§10.1）：

| 指标 | 洪峰期的含义 |
|---|---|
| `dc_backlog_pending` | 网关缓冲待补传数量（洪峰蓄积阶段） |
| `dc_backfill_total` / `_bytes` | 补传次数 / 字节数（洪峰规模） |
| `dc_duplicate_discarded_total` | 平台去重命中次数（去重强度；**异常高 = 大量重传，查网关/网络**） |
| `dc_late_arrival_total` | 乱序矫正补入次数（乱序严重度） |
| `dc_consumer_lag{topic}` | 下游消费积压（背压是否生效、恢复速度） |
| `dc_persist_latency_seconds` | 落库延迟（温层是否被写击穿） |

**告警**（依据：§10.2）：边缘缓冲水位持续增长（高，补传跟不上）；`dc_duplicate_discarded_total` 异常高（中，疑大量重传）；`dc_consumer_lag` 持续增长（中，消费方追不上）；温层写入延迟 p99 超阈值（中，存储压力）。

## 8. 决策点 🔴（交还运维/架构）

| 决策点 | 默认建议 |
|---|---|
| 网关本地缓冲载体 | 高吞吐选 RocksDB，简单部署选 SQLite |
| 缓冲容量与超容量丢弃策略 | 按最长预估断连×峰值速率估算；超限建议 BAD 标+告警 |
| 平台去重存储方案 | v1 主推 DB 唯一索引 + 消费端幂等；布隆为 DB 扛不住时预案 |
| 去重表保留期 | ≥ 最长补传窗口，建议 ≥7 天，与死信保留窗口对齐 |
| 乱序矫正窗口及启用范围 | 仅需严格时序的聚合类 topic 启用；窗口数百 ms~数秒按实测定 |
| 采集 topic 单消息上限 | 2MB（topic 级 `message.max.bytes` 覆盖，不动全局）；producer/consumer 三处同步调（§10.2） |

> 以上阈值在真实集群容量与车间实测量明确前，均为**设计目标 + 假设**，不作线上实绩承诺（口径见 §0）。

## 9. 范围外参考：过点拍照的文件服务器（生产执行服务范畴）

> **边界说明**：过点工位（如 AOI）会采集产品拍照数据，属大载荷，**需要文件服务器**——但该业务归**过点执行上下文（生产执行服务）**，不在设备管理服务（本文范围）。本文范围的环境/设备数据（单条 ≤1MB、结构化 KV）全量走 Kafka 直连，不经过文件服务器。
>
> **为何仍记录完整机制**：① 面试被问"拍照/大文件怎么处理"时按边界作答——归过点侧，文件服务器方案与本设计同构（§6 第 6 条）；② 过点侧实现可直接复用或对照本节设计；③ 设备数据若未来出现持续大载荷，判据见 §10.3。
>
> **前提**：文件服务器为自建（非对象存储），无预签名 URL、无 multipart、无服务端生命周期规则——这些能力在方案内自己补。

### 9.1 核心不变式：先传文件、后发引用

上传成功 + `sha256` 校验通过，才 seal 带 `object_uri` 的报文——**引用永不先于对象存在**。这是整个方案的地基，其余机制都是它的兜底。

### 9.2 键设计与上传校验

- **键**：`dc/{kind}/{equipment_id}/{yyyy-MM-dd}/{msg_id}.{ext}`（`kind = curve / aoi-image / log`）。`msg_id` 全局唯一 → 键不冲突、不覆盖，免去版本控制。
- **上传**：`PUT /dc/files/{key}`，请求头带 `X-Content-Sha256`（网关本地计算）；服务端流式边写边算，响应返回 `X-Stored-Sha256` + `X-Stored-Length`，与本地值比对，不一致按失败重试。
- **分块**仅在大文件（>50MB 或跨弱网）时启用：`PUT /dc/chunks/{key}/{n}` + `POST /dc/chunks/{key}/complete`（服务端合并后算总 hash）。

### 9.3 上传失败的降级（文件可丢、事件不丢）

重试 N 次退避仍失败 → **不发坏引用**：事件本身照发（追溯链不断），`quality=BAD` + 不带 `object_uri` + `payload_lost` 标记 + 告警；纯遥测类（A/B/D，单条价值低）可直接丢弃。

### 9.4 悬空引用防护：两个对账任务（每日）

| 任务 | 动作 |
|---|---|
| 正查 | 扫描 DB 已入账报文 → HEAD 文件服务器 → 404 标记 `payload_missing` + 告警（兜住磁盘故障/误删/静默损坏） |
| 反查 | 扫描文件键 → 无任何报文引用且超 TTL → 清理（兜住"传了没发出去"的孤儿文件） |

### 9.5 保留期对齐（无生命周期规则，清理自持）

文件服务器无自动生命周期，清理任务**按报文年龄驱动，不按文件 mtime**：

```text
文件 TTL ≥ max(Kafka 保留期, 去重表保留期) + 最长补传窗口 + 余量
例：max(7 天, 7 天) + 2 小时 + 1 天 ≈ 10 天
```

先查 DB 中引用该文件的最晚报文年龄，超阈值才删——保证补传/重放（旧 `msg_id` 迟来）永远拿不到死引用。这是自建清理唯一要守住的规则。

### 9.6 读取

内网直连静态路径（网络隔离，最简）；要鉴权用后端 HMAC 令牌（`?token=&expires=`，Nginx `secure_link` 或后端签发）或 `X-Accel-Redirect` 内部重定向。404 统一转"文件已过期或缺失"友好降级，不裸报 404。

### 9.7 对补传场景的结论

seal 先于缓冲 → 缓冲/补传的报文只带引用，而 seal 时对象必已上传成功 → **补传不产生悬空引用**。唯一残留是"传了文件但报文没发出去"的孤儿文件，由 §9.4 反查 + TTL 回收兜住。

## 10. 容量核算（500 QPS 口径 → 1000 QPS 展望）

### 10.1 Kafka 直连容量测算

全量结构化报文、均值百字节级，容量按**消息条数与均值字节**算，不按 1MB 峰值算：

| 项 | 500 QPS（当前口径） | 1000 QPS（展望） |
|---|---|---|
| 消息率 | 500 msg/s | 1000 msg/s |
| 均值大小 | ~200B（结构化 KV，环境 + 设备数据同） | 同 |
| 持续字节率 | ~0.1MB/s | ~0.2MB/s |
| 单条峰值 | ≤1MB（偶发） | 同 |
| Kafka 磁盘增量 | ~0.1MB/s × 7 天 ≈ 60GB | ~120GB |
| DB 去重 | 唯一索引余量约两个量级 | 触及"持续 TPS 1000~10000 评估布隆"下沿，压测后定 |

结论：两个量级下 Kafka、DB 唯一索引、温层落库均无压力；磁盘增量由**均值字节率 × 保留期**决定，与 1MB 峰值无关——峰值只影响 broker 瞬时内存与消费端 fetch，见 §10.2。

### 10.2 单消息调限（1MB 峰值的三处同步）

Kafka 默认 `message.max.bytes=1048588`（约 1MB）刚好压线，采集 topic 需**显式调大**，且三处必须同步——漏一处就是经典坑：

```bash
# 1. broker：采集 topic 级覆盖（不动全局，不拖累业务 topic 的内存模型）
kafka-configs --alter --topic dc.env.sample.raw \
  --add-config message.max.bytes=2097152   # 2MB，留协议头余量

# 2. producer
max.request.size=2097152

# 3. consumer（⚠️ 单消息大于 max.partition.fetch.bytes 会卡死消费循环）
max.partition.fetch.bytes=2097152 + fetch.max.bytes 同步
```

成本核算：broker 页缓存/网络缓冲按"峰值消息大小 × 并发连接"算（偶发大消息无感，持续大消息才疼）；消费端注意大消息 fetch 的延迟尖刺，`max.poll.records` 别让一次 poll 拽回几十 MB。

### 10.3 大载荷的归属与演进判据

- **当前归属**：持续大载荷（过点拍照 / AOI 图像）由过点执行上下文（生产执行服务）经文件服务器承载（§9），设备/环境数据路径不涉及。
- **本文范围的演进判据**：若设备/环境数据未来出现持续接近 1MB 的流、字节率上到几十 MB/s，Kafka 的复制放大（3 副本）与页缓存才开始疼——届时按 §9 机制外带，与过点侧文件服务器**合并规划，不新建第二套**。
- **启用是增量改动**：报文加 `payload_ref` 字段 + 网关上流传文件，去重/乱序矫正/落库分发/限流背压全部复用，不建新管道。
- 过渡期可混合：小报文走 Kafka、偶发大载荷外带文件服务器，两者由 `PayloadKind` 字段区分。
