## 0. 核心闪光点速览（先报这组，最硬）

| 闪光点 | 一句话 | 出处 |
|---|---|---|
| **不是"窗口快满做一次摘要"** | 四层按需、各有独立门控，廉价手段先行，不是每轮全跑 | [对照记录](../AGENT服务/Agent上下文压缩分层-市面对照与演进记录.md) §1 |
| **结构完整性是硬约束** | 清旧工具结果必须保留 `tool_use`/`tool_result` 配对，否则请求本身不合法 | §1.2 |
| **缓存状态是"何时压"的一等输入** | 缓存已过期、本来要重算时顺手清理，边际成本近零；缓存热时改前缀反而更贵 | §1.2 / §3.1 |
| **视图 / 记录分离** | 折叠只改本轮模型看到的视图，原始记录仍在 transcript，可回退可重放可审计 | §1.2 |
| **异步准备、同步应用** | 摘要后台备好，但发请求前必须同步取最新，否则用过期摘要或漏新消息 | §1.1 / §3.2 |
| **兜底不在临界点再调 LLM** | 优先用后台维护的 Session Memory + 近期原文，失败才走 Full LLM Compact | §1.2 |
| **压缩后是"重建工作集"** | 常量从磁盘重注入、文件按预算重读，摘要不是唯一信息载体 | §3.3 |
| **懂什么时候不派子 Agent** | 渐进式披露优先，子 Agent 只在三条判据下保留 | §3.4 |
| **本项目对应：模型看摘要 / trace 落全文** | 压缩只作用于喂模型这一路，证据链落 FULL view，红线不碰 | [记忆系统](../AGENT服务/Agent记忆系统-设计与实现方案.md) §0 / §4 |

## 1. 30 秒电梯陈述

"上下文管理最容易做错的一件事，是**等窗口快满了统一做一次摘要**。市面成熟做法是按成本递增分四层按需触发：先做不调 LLM 的轻量裁剪，把旧工具结果换成占位标记但保留消息结构和工具调用配对；再在请求前结合时间间隔和**缓存状态**做微压缩——缓存已过期、本来就要重算时顺手清，缓存热时别动前缀；有相关特性时再对稳定历史片段做局部折叠，交给子 Agent 出摘要，只改本轮上下文视图，原始记录仍留在 transcript；最后接近预算或溢出了才做兜底压缩，优先用后台维护好的会话摘要 + 近期原文，不行再调模型出结构化摘要。四层**各自有门控，不是流水线**，折叠还取决于特性开关，不能当成所有版本固定行为。我们项目对应的是 M2 的'模型看摘要、trace 落全文'双路、prompt cache 分层和工具检索门控——**压缩只作用于喂模型这一路，证据链不碰**。这套目前是设计规划，尚未落地。"

**五个抓手**：成本递增 / 缓存对齐 / 视图-记录分离 / 兜底不额外调 LLM / 压缩不碰证据链。

## 2. 主干讲法：四层按需压缩（2 分钟版）

### 2.1 先给表

| 层 | 触发 | 是否调 LLM | 同步 / 异步 | 一句话 |
|---|---|---|---|---|
| **Snip** | 出现已消费的大块旧工具结果 | 否 | 同步 | 换成短标记，保留结构与配对 |
| **MicroCompact** | 请求前 + 时间间隔 / 缓存状态满足 | 否 | 请求链路内同步 | 清旧结果、保留近期，对齐缓存失效窗口 |
| **Collapse** | **特性启用** + 稳定低风险片段 | 子 Agent 局部摘要 | 异步准备 + **同步应用** | `A B C D E F` → `A B [C—D 摘要] E F` |
| **AutoCompact** | 接近预算上限 / 溢出 | 优先不调，兜底才调 | 触发时同步 | Session Memory 优先，否则 Full LLM Compact |

### 2.2 门控（一句话点破"不是流水线"）

"可以只跑第一层，也可以一二层一起，还可以直接跳到第四层；第三层还多一道特性开关。判定顺序是：请求前依次过 L1、L2、L3 的门控再发请求；发之前预估超预算、或者请求返回上下文溢出，才走 L4 压缩后重试。**L1–L3 是请求前预防，L4 是临界 / 失败后兜底**。"

### 2.3 三个最值钱的洞察（讲完这三个，深度就出来了）

1. **缓存不只是"压多少"，是"何时压"**。提示词缓存按前缀精确匹配，前缀里任何改动都会让后面全部重算。缓存还热时清理 = 把省下的 token 又赔进重算；缓存已过期、本次本来就要重建前缀时清理，边际成本接近零，还能把后续每一轮的基线体积降下来。官方甚至把这件事做成配置项 `clear_at_least`——**清不掉指定 token 数就干脆不清**，专门用来判断"打断缓存值不值"。
2. **临界点是压缩质量最差的时刻**。上下文越长模型越受 context rot 影响，此时让它猜"接下来什么重要"最容易丢东西。所以 2026 年官方反过来建议：在任务之间的自然间歇**带焦点地主动压缩**、空闲时压缩、自定义水位，而不是等任务中途自动触发。
3. **压缩不是把历史换成一段文本，是重建最小工作集**。压缩后常量（`CLAUDE.md`、auto memory、skill 描述、plan、git status）从磁盘重注入，最近改过的文件按预算重读最多 5 个，超大的只留路径引用，后台任务继续跑并提醒模型别重复起一个——**磁盘是常量事实源，摘要只是变量部分**。

## 3. 核心应答话术（高频问题，口语化背熟）

> 每段 40~80 秒。结构：钩子 → 核心 → 深度 → 收口。

### 话术 1：为什么不等窗口快满统一做一次摘要

"三个代价叠在一起。第一是**质量**：临界点上下文最长，context rot 最严重，模型恰恰在它最不聪明的时候被要求判断'什么该留'，而且它猜不到我下一步往哪走，容易把顺手看到的线索丢掉。第二是**成本**：恢复一个缓存已过期的长会话时摘要请求要把历史当未缓存输入重新处理，那时最贵；全量 LLM 摘要本身也是一次额外模型调用。第三是**结构**：一刀切摘要没法保证工具调用和结果的对应关系，也没法只压中段稳定片段。所以成熟做法是分层——先用零 LLM 的手段把大块噪声清掉，让更重的手段尽量不被触发，把'必须全量摘要'推到最后一步。"

### 话术 2：MicroCompact 挑缓存失效时做，那不还是会毁缓存吗

"关键是**本来就要重算**。提示缓存是精确前缀匹配，没有按文件或按段缓存；缓存热的时候你去改前缀，等于主动把已缓存部分作废，省下的 token 又赔进重算。缓存已过期、或者这次请求本来就要重建前缀时，清理是搭便车，边际成本近零，而且此后每一轮都带着更小的基线。官方把这个权衡做成了 `clear_at_least`：清不掉指定数量 token 就干脆不应用这次策略，因为为了几个 token 打断缓存不划算。所以我们项目里也是**固定工具集 + 缓存命中，优于动态裁剪工具 + 缓存未命中**——这条写进了成本方案。"

### 话术 3：Collapse 的摘要为什么必须发请求前同步应用

"因为异步只负责**准备**，不负责**生效**。摘要可以提前在子 Agent 里算好缓存起来，但真正发请求那一刻必须同步取最新、校验版本、替换进视图，否则两种事故：用了过期摘要，或者摘要算完之后又产生了新消息、结果被漏掉。而且折叠只改本轮模型看到的上下文视图，原始记录仍留在 transcript，所以这个替换是可回退、可重放的——**视图是投影，transcript 是事实源**。这一点和我们项目'模型看摘要、trace 落全文'是同一个思路。"

### 话术 4：Snip 只是删文本吗，为什么强调保留对应关系

"不是删文本，是**在协议约束下替换**。工具调用块和工具结果块必须成对，否则请求本身会被拒，或者模型看到'我调过工具却没有结果'的断裂叙事。平台的 `clear_tool_uses` 默认也只清结果、保留原始工具调用（`clear_tool_inputs` 默认 `false`），让模型仍能看到执行过什么动作。所以最轻的那一层其实最讲纪律：**省 token 不能省掉结构**。我们 `ResultCompactor` 的裁剪也一样，截断要标 `_truncated`，让模型知道数据不全，不能基于'看起来只有 20 条'去推理。"

### 话术 5：AutoCompact 为什么优先用 Session Memory

"因为**临界点最不适合再发起一次模型调用**：可能超时、可能自己也溢出、还多一段尾延迟。Session Memory 是会话过程中后台持续维护好的，触发时直接取现成摘要 + 保留近期原文，零额外 LLM 调用，而且近期原文保证'当前正在做的事'不丢。只有这条路不适用或失败，才走 Full LLM Compact，把历史整理成核心请求、涉及文件、错误与修复、待办、当前工作、下一步的结构化摘要——重点是**可续接**，不是概括成一段散文。溢出场景是压缩后重建上下文再重试，属于请求后路径。"

### 话术 6：1M 上下文窗口是不是就不用压缩了

"不是，大窗口不是工作记忆。官方自己讲 context rot：输入变长、无关内容变多，注意力被摊薄，性能持续退化。1M 窗口真正的价值是**给'提前、主动压缩'留了更多时间窗口**，不是免压缩。所以官方给的是一张决策表：同一任务且上下文还承重就继续；走错路用 rewind 回退；中途被陈旧调试信息撑大就带 hint 压缩；真正开新任务就 clear；下一步会产生大量只需结论的输出就派子 Agent。顺带一提，Chroma 2025 那组实验里，200K 窗口的模型约 5 万 token 就明显退化——这是那篇实验的口径，不是我们实测。"

### 话术 7：你们项目里对应做了什么

"对应三条，都是**设计规划，尚未落地**：第一，M2 上下文窗口记忆用 `Offloader` + `ToolOffloadMiddleware` 承载压缩，项目自己的 `OffloadCompactPolicy` 做字段白名单、列表截断、截断标注，核心哲学是**模型看摘要、trace 落全文**——压缩只作用于喂模型这一路，`tool_call_trace.output_payload` 存 FULL view，证据链红线不碰。第二，prompt cache 只标 `system` / `tools` 块，TTL 5m / 1h，动态上下文不进缓存块，工具集动态裁剪会破坏命中，所以默认关闭阶段裁剪。第三，工具侧有检索式门控和描述精简，ADR 里记录了市面口径 49%→74%、工具定义 72K→8.7K。裁剪规则变更要过 `EvalRunner` 回归——**省 token 不能降根因准确率**。"

### 话术 8：2026 年市面还有什么新优化

"增量不在'压得更狠'，在五个新维度。① **可配置化**：清理从 CLI 内部实现变成平台 API，`trigger`/`keep`/`clear_at_least`/`exclude_tools` 可配，还返回 `applied_edits` 清理量。② **时点前移**：空闲压缩、带焦点压缩、自定义水位、`rewind` 截断回已缓存前缀。③ **压缩后重建**：常量从磁盘重注入、按预算重读文件。④ **外部化 + 渐进式披露**：文件式记忆、工具 `defer_loading`、技能按需加载——官方 2026 年甚至建议把子 Agent 折回主循环，因为渐进式披露能让内容压根不进窗口。⑤ **传输层**：Message Threads 让服务端保留会话、每轮只发增量，省首 token 延迟但 **token 用量不变**。这些都是别人的能力，我们只取原则，不照搬实现。"

## 4. 深度问答（技术深挖）

**Q：四层的触发条件具体怎么判？会不会重复执行？**
A：各自独立门控，不重复。L1 看有没有已消费的大块旧结果；L2 看时间间隔 + 缓存状态，条件不成立整层跳过；L3 看特性开关 + 有没有稳定低风险片段；L4 看预估是否超预算或请求是否溢出。前三层的效果是"尽量别让 L4 发生"。任何一层都不是每轮必跑，L3 更不是所有版本都有。**这些名称和阈值是特定版本的实现观察，不是契约**。

**Q：`clear_at_least` 为什么是"清不掉就不清"，而不是能清多少清多少？**
A：因为清理本身有代价——前缀含工具时，清理会让提示缓存失效。如果这次只能清掉几百 token，却要让整个后续前缀重算，净收益是负的。所以设一个最小清理量，达不到就放弃这次编辑。本质是**把缓存失效成本显式纳入压缩决策**，而不是只看 token 数。

**Q：Collapse 的"稳定、低风险片段"怎么判定？**
A：至少三条：这段历史已经结束、没有未决引用、不与当前正在做的任务交错。所以折叠通常落在**中段**——头部是初始意图与系统约束，尾部是近期工作集，都不动。上下文压力过高时还要**背压**：限制继续派生新分支 / 新任务，避免边压边灌的雪崩。

**Q：折叠摘要交给子 Agent，那子 Agent 自己的上下文不也可能爆吗？**
A：会，所以它是"局部、只读、只回结构化结论"的隔离上下文，读原文做语义压缩，只把 1~2k token 的结果回主干。但 2026 年官方的进一步判断是：**能不派就不派**。渐进式披露（工具 / 技能延迟加载）能在单循环里解决大部分上下文隔离需求；子 Agent 只保留三种场景：单循环出现可测的上下文膨胀退化、需要并行且用完即弃的干净上下文、工具选择困难或系统提示冲突。我们 flow 文档里也写了子会话是最后一层、成本高 10~100 倍。

**Q：压缩后系统提示 / 工具定义要不要重新加载？会不会又让缓存失效？**
A：压缩按设计会让**对话层**前缀失效，因为历史换成了摘要、不再共享旧前缀；但**系统提示层和项目上下文层可以保持缓存**——系统提示继续生效，`CLAUDE.md`、auto memory、无作用域规则从磁盘重注入，只有它们自会话开始以来没变过时下一个请求才读缓存。摘要请求本身复用主对话前缀，所以缓存温热时中途压缩的成本远低于上下文大小给人的直觉；恢复一个缓存已冷的旧会话时压缩最贵。

**Q：`/recap` 和 `/compact` 有什么区别？为什么值得单独讲？**
A：`/compact` **替换**消息历史，构建全新前缀；`/recap` 只生成摘要**追加**为命令输出，不替换历史，所以缓存前缀完整。同理 `/rewind` 是截断回较早轮次，下一个请求能命中当时构建的缓存条目，比压缩更省。这三类动作的区别说明一件事：**上下文管理不只有"压缩"一个动作，还有"只读摘要"和"回退"，它们的缓存代价完全不同**。

**Q：Message Threads 省 token 吗？和 prompt cache 什么关系？**
A：不省 token。模型每轮仍读取完整会话历史，计费不变；省的是**重复上传长历史的传输与首 token 延迟**。首个请求发完整会话开线程，之后只发增量 + 上一条响应 ID，服务端保留线程（最后一次请求后 5 分钟过期、最迟 1 小时删除），客户端仍要自己维护历史以便过期后重发全量。它和 prompt cache 是两层：一个省"送过去"的时间，一个省"重新处理"的钱。

## 5. 广度问答（覆盖面，考全局视野）

**Q：这些和你们说的"记忆分层"是什么关系？**
A：两个正交维度。我们 [Agent记忆系统](../AGENT服务/Agent记忆系统-设计与实现方案.md) 的五层是**执行侧记忆**（M1 工作记忆 / M2 上下文窗口记忆 / M3 证据链长期记忆 / 跨会话缓存 / L5 元数据），按"存给谁看、活多久"切；压缩分层是 **M2 内部的处理管线**。另外 [路由对照文](../AGENT服务/Agent路由与多轮上下文-市面对照与演进方向.md) 提的 M0 是**对话侧记忆**，管跨轮实体锚点与指代，五层之外新增的一层。三者不冲突：一个管"哪些记忆存在哪"，一个管"喂模型前怎么瘦身"，一个管"用户在聊哪个实体"。

**Q：外部化记忆和语义缓存有什么区别？MES 里能上吗？**
A：完全不同，而且我们有一条时变性红线。**语义缓存默认关闭**——"批次 B-77 焊接根因 = X"这类答案会随新数据漂移，缓存答案会错给失效结论；`CURRENT` 数据范围一律跳过缓存。外部记忆只记**锚点 / 意图 / 已排除路径**，比如"用户在聊 SN-001""上一轮走了检索""A 方案已排除"，不记答案。所以**记住在聊什么实体可以，缓存根因答案不行**。这条和"模型看摘要、trace 落全文"一起守住了证据链和版本一致性。

**Q：渐进式披露具体怎么做？会不会让模型找不到工具？**
A：工具只放名字或一行描述，完整 schema 用 `defer_loading` 标延迟加载，模型需要时经 tool search 拿 `tool_reference` 再展开；技能同理，只放描述、调用时才注入正文，带 `disable-model-invocation` 的甚至完全不进索引；带 `paths:` 的规则在读到匹配文件时才加载；参考材料放检索工具后面，不要由代码检索后粘进 prompt。风险是工具选择退化——官方经验是系统提示里超过 30~50 个工具定义就会掉准确率，所以要按用户意图给工具分组、并配评测断言"该加载的技能 / 工具是否加载对了"。附带好处：延迟加载时会话中途增删 MCP 服务器不再破坏缓存前缀。

**Q：怎么衡量压缩有没有伤到质量？**
A：把压缩当**可评测组件**，不是隐性优化。三条：① 裁剪 / 折叠规则变更必须过 `EvalRunner` 回归，对比新旧准确率；② 摘要 prompt 调优先**最大化 recall**（宁可多留），再提升 precision，用结构化 schema 而不是自由文本；③ 线上监控 token/会话 P95 漂移、缓存命中率与清理量（`applied_edits` 式回报），并命名最后一次缓存失效原因。我们评测侧还有"安全硬失败用例集 + CI hard gate"（[RAG与Agent评测-面试闪光点.md](RAG与Agent评测-面试闪光点.md)），压缩造成的事实丢失属于要拦的回归。🔴 这些门禁是设计目标，尚未落地。

**Q：研究侧有什么值得关注的新方向？**
A：两篇 ICML 2026。**Context-Folding**：让模型主动分支进子轨迹做子任务、完成后折叠中间步骤只留结果摘要，决策主体从 harness 变成模型自己——是 Collapse 的升级版。**RE-TRAC**：递归轨迹压缩 + 结构化状态，跨轨迹复用证据并**记住失败教训与死路**，解决 ReAct 线性探索反复踩坑。共同点是摘要内容从"记事实"扩到"记经验"，从"被动事后摘要"变成"主动管理自己的上下文"。🔴 我们项目要等有成熟 `EvalRunner` 基线后才会评估这类做法。

## 6. 压力追问（陷阱题 / 追问到底，考诚实和深度）

**Q：这四层是你实现的吗？**
A：不是。四层是市面 Claude Code 特定版本的实现观察，我拿来当对照基线；名字、阈值、开关默认值、Session Memory 是否存在都会随版本变，Collapse 还取决于相关特性是否启用，**不能当成所有版本固定行为，更不是 API 契约**。我们项目里对应的是 M2 的设计规划，全仓标注"📐 设计目标，尚未落地"。我讲四层是为了引出三条可迁移原则和我们的差距清单，不是邀功。

**Q：既然没落地，你讲这些有什么用？**
A：因为它决定了架构顺序。识别出"压缩不是单点动作、而是一条按成本递增的管线"，才知道该先补什么：先把清理门控和清理量回报、压缩后重建清单、缓存失效清单做掉（低成本、与现有 M2 兼容），再谈空闲期调度和外部化记忆，最后才评估换会话模型或换框架。反过来如果一上来就照着做 Full LLM Compact，既贵又会把证据链和缓存前缀毁掉。**架构判断力体现在顺序，不在于抄了几个特性**。

**Q：你说压缩不碰证据链，可摘要里的内容不也是从工具结果来的吗？丢了怎么办？**
A：丢的是**喂给模型的副本**，不是落库的事实。工具执行时 `tool_call_trace.output_payload` 存 FULL view，工程师 UI 回溯看全文；`ResultCompactor` 产出的 compacted view 只用于回灌模型，两条路同一份数据、不同保真度。所以摘要丢细节影响的是模型这一轮的推理，不影响审计与证据引用。真要防"模型因截断误判"，靠三件事：截断标注 `_truncated`、必要时换更窄查询重查、裁剪规则变更过 `EvalRunner`。

**Q：官方说 +39% / −84%，你们也能达到吗？**
A：不能这么讲。那是 Anthropic **自有评测集**（内部 agentic search 评测、100 轮 web search 评测）的口径，场景、模型、工具分布都和我们 MES 诊断不同。我们项目的量化收益一律 🔴 待实测——命中率 SLO ≥80%、父会话 40~50k 触发压缩这些是**设计目标**，不是线上实绩。能讲的只有"覆盖能力 + 设计目标 + 出处"，说不出的数字不说。这也是我们项目一贯的口径纪律。

**Q：为了省 token 改前缀，结果缓存全失效，不是搬石头砸脚吗？**
A：正是这个风险，所以缓存状态是门控条件而不是事后优化。我们成本方案里的结论是"**固定工具集 + 缓存命中，优于动态工具集 + 缓存未命中**"，阶段裁剪默认关闭，工具定义按 capability 裁剪也要权衡命中率；`prompt_version` 变更按内容哈希自然失效。平台侧同理，`clear_at_least` 就是"不值得就别清"。压缩和缓存必须一起设计，不能各做各的。

**Q：压缩把待办、错误修复都塞进摘要，怎么保证它没编？**
A：摘要本来就是有损的，不能当事实源用——所以才强调**视图 / 记录分离**和"磁盘是常量事实源"。结构化摘要的价值是**可续接**（让下一轮能接着干活），不是可审计；可审计靠 transcript 和 M3 证据链。我们评测侧还有"证据非空强约束 / 实体幻觉率"这类安全硬失败用例，模型拿摘要里的内容去编结论会被拦。简单说：**摘要管 continuity，trace 管 truth**。

**Q：既然折叠只改视图，transcript 一直留着，那不还是占空间吗？**
A：transcript 是持久化与审计用的存储，不进本轮请求；占的是磁盘，不是上下文窗口，两者不是一种资源。而且视图是可重建的投影——摘要不满意可以换一种组装方式重来，折叠可回退、可重放。把"上下文压力"和"存储压力"混为一谈，是这个问题常见的坑。

**Q：空闲时压缩，用户突然回来发消息，撞上了怎么办？**
A：这是并发改写同一视图的竞态，必须设计上排除：后台调度只在无在途请求时启动，发请求前同步校验视图版本，压缩产物与用户新消息按序合并；拿不到最新版本就放弃这次后台压缩，退回到请求前的常规门控。**异步准备、同步生效**这条原则就是为此存在的。🔴 具体调度与版本校验方式在我们设计里是待定项（对照记录 §7）。

## 7. 设计权衡题（考架构判断力）

**Q：为什么用分层，而不是只留一层 Full LLM Compact？**
A：三层收益。① **成本**：L1/L2 零 LLM，绝大多数轮次根本不需要惊动模型；② **延迟**：临界点再调一次 LLM 会有尾延迟和再次溢出的风险，用后台备好的 Session Memory 能避开；③ **质量**：全量摘要必然丢细节，而 L1/L2/L3 都是局部、可控、可回退的。分层本质是**把不可逆的全局有损操作尽量往后推**。

**Q：什么时候该用子 Agent 折叠，什么时候用渐进式披露？**
A：默认渐进式披露——它让内容压根不进窗口，也没有交接损失和嵌套模型循环的延迟。只有命中官方三条判据才派子 Agent：单循环有可测的上下文膨胀退化、需要并行且用完即弃的干净上下文、工具选择困难或系统提示冲突。判断口诀是"**我要的是这个工具输出本身，还是只要结论**"；只要结论，且这段输出量大、与主任务弱耦合，才隔离出去。

**Q：为什么压缩后要"从磁盘重注入"，摘要里写清楚不就行了？**
A：因为常量与变量该分开管。`CLAUDE.md`、auto memory、skill 描述、plan 这类内容来自磁盘、有唯一权威版本，写进摘要就是复制了一份可能过期的副本；重注入保证压缩后仍以磁盘为准。而且它们通常在缓存的系统提示 / 项目上下文层，重注入能保住这两层前缀。摘要只承载"这一轮发生了什么"这类变量信息。**别把配置当历史来压缩**。

**Q：为什么兜底优先用 Session Memory 而不是每次现算摘要？**
A：三个理由：省一次 LLM 调用、避开临界点的超时 / 再溢出风险、把摘要成本摊到会话过程中而不是砸在用户等待的那一轮。代价是 Session Memory 要后台维护、可能过期或不适用，所以必须有 Full LLM Compact 作为失败兜底——**两级策略，不是二选一**。

**Q：外部化记忆和你们已有的 M0 对话记忆会不会重复？**
A：不重复但**要划界**，这是开放问题（对照记录 §7）。M0 管跨轮实体锚点与指代消解，属对话侧；外部化记忆管把参考材料 / 中间结论搬出上下文，属执行侧的知识外置。两者都可能落同一个存储组件，但作用域、TTL、写入者、合规要求不同，设计上要分开声明，别混成一个"大而全的 Memory 模块"——我们项目本来就没有单体 `Memory` 类，记忆是分层架构。

## 9. 红线与口径纪律（面试别翻车）

- ❌ "我们实现了 Claude Code 那四层压缩" / "线上已跑 AutoCompact" —— **市面对照 + 设计规划，尚未落地**。
- ❌ "所有版本都是这四层" —— 特性开关、阈值、Session Memory 存在性都随版本变；**Collapse 尤其取决于相关特性是否启用**。
- ❌ "压缩给我们省了 84% token" / "命中率实测 90%" —— 那是**官方自有评测集**；本项目 🔴 待实测，命中率 SLO ≥80% 是设计目标。
- ❌ "压缩会清掉旧证据" —— 压缩只作用于**喂模型这一路**，trace 落 FULL view，证据链红线不碰。
- ❌ "1M 窗口就不用压缩了" / "Memory Tool 可以直接缓存根因答案" —— 前者忽略 context rot，后者踩**时变性红线**。
- ❌ "Message Threads 省 token" —— **token 用量不变**，省的是重复传输与首 token 延迟。
- ✅ 正确讲法："四层是市面某版本的实现观察，我拿它做对照基线；可迁移的是**成本递增、缓存对齐、视图-记录分离**三条原则。我们项目对应的是 M2 双路、prompt cache 分层和工具检索门控，目前是设计规划、尚未落地，量化收益待实测。"

## 10. 一句话定位（收尾用）

"上下文管理的价值不在于多做一次摘要，而在于**识别出'窗口会满、缓存会被打断、摘要必然有损、证据链不能丢'这四重约束，用成本递增的四层按需门控 + 缓存对齐 + 视图与记录分离，把最贵、最不可逆的全量压缩尽量往后推**；再往前一步，是用渐进式披露和外部化记忆让内容压根不进窗口。我们项目把它落成了'模型看摘要、trace 落全文'的 M2 双路和 prompt cache 分层，压缩只作用于喂模型这一路，与 MES 防错理念同构——**摘要管 continuity，trace 管 truth**。这是设计规划阶段的方案，量化收益待上线后用评测数据验证。"
