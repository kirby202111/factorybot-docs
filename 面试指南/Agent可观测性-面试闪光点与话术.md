## 1. 30 秒电梯陈述

"Agent 可观测性不是普通 APM 的翻版。普通 APM 回答'接口慢不慢、服务挂没挂'，Agent 可观测性要额外回答'**这条 AI 给出的根因假设凭什么、谁查的、查到什么、哪条证据支撑哪条结论、为何转人工**'。我用 OTel trace + prometheus 指标 + 结构化日志，把每次 AI 推理串成**可审计的证据链**--假设 -> trace_id -> 工具结果 -> 下游 REST，工程师点假设就能弹证据回溯到具体调用。它还补齐了通用 APM 没有的 Agent 质量维度：**置信度标定**（LLM 自评不可信，三源融合 + Platt 标定 + ECE 监控）、**评测回归**（提示词即代码，改 prompt 必改版本号必过 eval）、**漂移检测**（PSI）、**token 成本**。设计上它是**只读旁路**--不进过点主事务、不旁路写、观测失败不阻断业务、受租户隔离，和 MES 防错理念同构：所有 AI 决策可回溯、可度量、可转人，最终处置仍由工程师确认。"

**五个抓手**：证据链投影 / 只读旁路不进过点 / 置信度标定不单信模型 / 提示词即代码 / 懂什么时候不用 AI。

## 2. 闪光点详解（按主线）

### A. 可审计证据链--把 trace 变成工程师能点的"证据"

#### A.1 证据链 = span 树的业务投影（最大闪光点）

**核心机制**（[可观测方案](../AGENT服务/Agent可观测性-设计与实现方案.md) §4.5 / §7.2）：
- 一次会话产出一棵 span 树（root=会话，子=每步 LLM 调用 + 工具调用）。
- trace span 树给 SRE 看火焰图（Tempo/Jaeger）；**业务侧看的是它的平铺投影**--`tool_call_trace` 表，每个 tool span 落一行。
- 报告里 `Hypothesis.evidence` 存的是 `tool_call_trace.trace_id` 列表，工程师点假设 -> 弹证据 -> 回溯到具体工具入参出参与下游 REST 调用。**两者同源**（都来自 ToolNode 同一次调用），trace 是底、证据链是面。

**为什么是亮点**：这是把"可观测性"从 SRE 的监控工具，重新定位成"**给工艺/质量工程师的 AI 决策审计工具**"。MES 场景下 AI 决策必须可回溯（和防错同构），普通 APM 出的火焰图工程师看不懂也用不上；证据链平铺表才是他们要的--点假设、看证据、查到下游哪条 REST。**受众分治**是关键洞察：SRE 看 span 树、工程师看平铺表、AI 负责人看评测，一套数据三种投影。

**防守话术**："trace 落 Tempo 又落 MySQL 不是重复，是同一份 trace 的两种投影--Tempo 给 SRE 看火焰图是底，`tool_call_trace` 平铺表给工程师 UI 用是面，trace_id 串起来同源，不各说各话。"

#### A.2 证据非空强约束--没有证据的假设不许输出

**核心机制**（§7.2 / §12）：
- `ReportParser` 校验每条 hypothesis 的 `evidence` 列表**必须非空**且至少引用 1 条 `trace_id`，否则判 schema 失败重试。
- `trace_id` 必须真实存在于本会话的 `tool_call_trace` 表--**模型编造的 trace_id 校验不过**（查不到对应行）。
- L2 草稿 `evidence_refs` 引用 `trace_id` + `subgraph_ref`，L3 动作卡 `evidence` 引用 `trace_id` + `agent_hypothesis`，同构约束。

**为什么是亮点**：这是证据链的**完整性保证**。LLM 会"自信地编"--给一个看似合理的假设但压根没查过对应数据。强约束逼它"结论必有据"，编造的 trace_id 因查不到行而被 schema 校验拦下重试。和 L1 报告的 Pydantic 强约束一脉相承：**用 schema 校验守住"证据-结论"的物理绑定**，不是靠提示词劝模型"请给证据"。

**防守话术**："模型可能编 trace_id，但 ReportParser 会校验它必须在本会话 tool_call_trace 里查得到--编的 id 查不到就 schema 失败重试。所以证据不是模型嘴上说有就有，是和真实落库的调用行物理绑定的。"

#### A.3 日志与 trace 关联（点 trace 跳日志，反之亦然）

**核心机制**（§6.1 / §6.4）：
- 结构化 JSON 日志，每行带 `trace_id` / `session_id`，从 OTel context 自动取（`_inject_context` processor 注入）。
- Grafana 里点 trace 能跳对应日志，点日志能跳 trace。

**为什么是亮点**：日志和 trace 不再是两套割裂的系统。排障时"这个会话为什么转人工"-> 点 trace 看步骤 -> 跳日志看当时 prompt 片段/工具入参 -> 跳下游 REST。一条链穿到底。

### B. 只读旁路--观测不反噬业务，不进过点主链

#### B.1 观测是只读旁路，绝不进过点主事务

**核心机制**（§2.3 / §18）：
- 观测只采集只读数据，**不写任何业务表**；trace/指标/日志表是独立观测存储，不与 MES 业务表混用。
- 观测**不进过点主事务**：过点引擎 P99 ≤200ms（[领域总览.md](../领域模型/领域总览.md) §4.1）是硬约束，Agent 本身就不进过点主事务，其观测更不会挂在过点路径上。
- 观测数据携带 `tenant`，落库与查询都按租户隔离--A 车间工程师查不到 B 车间 trace。

**为什么是亮点**：这条是 MES 场景的硬纪律。很多人做可观测会顺手把埋点塞进业务主路径（同步写日志、同步发指标），在过点这种"毫秒级 + 强防错"场景里会直接拖垮 P99。这里把观测明确隔离成旁路：**业务跑业务的事，观测跑观测的事，物理上不交叉**。和"Agent 失败最坏是没诊断出来"一脉相承--观测失败最坏是没记录，绝不反噬业务。

**防守话术**："Agent 本身就不进过点主事务（L1 全程只读、L2 草稿不落库、L3 写动作过 confirmation gate），它的观测更不会挂在过点 P99 路径上。观测是独立旁路，落独立的观测表，不碰业务表。"

#### B.2 DIP：ObservabilityPort 抽象，观测失败不阻断业务

**核心机制**（§2.2 / §14.2）：
- 业务节点（`ToolNode`、`DraftBuilder`、`supervisor`）依赖 `ObservabilityPort` 抽象接口，**不直接依赖 OTel/prometheus 具体实现**。
- 测试时可换 `InMemoryObservability`；生产实现挂了（OTel exporter 挂、prometheus 挂），业务照跑，只是该次无 trace。
- 符合 SRP（`Tracing` / `MetricsCollector` / `LlmCallLogger` / `EvalRunner` 各司一职）+ OCP（新增 L4 或新 LLM provider 不改观测核心，只加 label/维度）。

**为什么是亮点**：把 SOLID 落到观测层是少见但极有说服力的做法。多数项目的埋点是散落在业务代码里的 `prometheus.inc()` / `span.start()`，强耦合、难测试、观测挂了会拖累业务。这里用 DIP 把观测抽象成端口，业务依赖抽象--**观测成了可替换的旁路插件**。面试官一听"观测失败不阻断业务，靠 DIP 保证"就知道你懂解耦。

**防守话术**："业务节点依赖 ObservabilityPort 抽象，不直接碰 OTel/prometheus 原语。具体实现挂了业务照样跑，只是没 trace。测试时换 InMemoryObservability 就能跑离线评测不污染指标。这是 DIP 落到观测层。"

#### B.3 兜底矩阵全分支落观测，无一例外

**核心机制**（§12）：
- 11 类兜底（低置信 / 工具连续失败 / recursion_limit / 整会话超时 / LLM schema 失败 / 写工具被拦 / 证据为空 / subgraph 回查空 / 草稿恒需确认 / gate 超时 / barrier 未 PASS / agent 连续失败）**每条都落 trace 事件 + 指标 + 日志**。
- 写工具被拦（L3 未带有效 confirmation token）触发 **P0 告警**（PagerDuty/钉钉），因为它意味着红线可能被绕过。
- 兜底触发的报告都带 `disclaimer`：辅助假设，最终处置需工程师确认。

**为什么是亮点**：哲学一致性--**兜底是最后一道闸，它自己必须被盯着**。如果兜底动作不可观测，就不知道"转人工"到底转了多少、为什么转、是不是某个兜底失效了。P0 盯写工具被拦体现"懂什么是真正的红线"：MES 防错的红线是"AI 不能绕过确认直接写"，一旦被绕过就是质量事故级，必须 P0。这和 [生产执行服务-面试闪光点.md](生产执行服务-面试闪光点.md) 的"宁可让人判"一脉相承。

### C. 置信度与转人工--不单点信任 LLM 自评

#### C.1 置信度三源融合（模型自评不可信）

**核心机制**（§9.1）：
- 置信度不是模型一句话，是**三源融合**：① 模型自评（报告里输出 confidence）② 证据充分度（实际引用证据数 / 该场景期望证据数）③ 工具成功率（本会话成功工具调用占比）。
- 融合不是简单平均，是标定后的映射；🔴 三源权重与融合函数待评测数据拟合后定，初始版仅用模型自评 + 阈值。

**为什么是亮点**：直击 LLM 的已知缺陷--**RLHF/指令微调后的模型系统性 overconfident**，尤其在它不知道的问题上会"自信地幻觉"。单点信任模型自评会把高置信的错答直接推给操作工，在 MES 防错场景下是灾难。三源融合引入外部信号（证据够不够、工具成没成功）来校验模型自评，是"不单点信任模型"的工程化。这个洞察本身就值很多分--多数候选人会以为"模型说 0.8 就是 80% 准"。

#### C.2 置信度标定（Calibration）--模型说 0.8 不代表 80% 准

**核心机制**（§9.2 / §10.4）：
- 离线用评测集跑，把预测按置信度分桶（0~0.1, 0.1~0.2, ...），算每桶**实际准确率**，画 reliability diagram（可靠性图）。
- 若 overconfident，用标定映射修正：**Platt scaling**（逻辑回归，2 参数，假设特定形状，小样本稳）或 **isotonic regression**（非参数单调映射，灵活但小样本易过拟合）。
- 标定曲线版本化（`calibration_version`），随模型/提示词变更重标。
- 监控 **ECE**（Expected Calibration Error）= Σ(|B_m|/N)×|acc(B_m)−conf(B_m)|，目标 < 0.1。
- 🔴 标定方法（Platt vs isotonic）待评测数据规模确定后选；倾向小样本用 Platt。

**为什么是亮点**：这是全篇最"有深度"的点。把机器学习的标定理论落到 LLM 运维上：模型自评的置信度和实际准确率之间有系统偏差，要**测出来、画出来、用参数化映射修正、版本化、持续监控 ECE**。能讲清 reliability diagram 怎么画、Platt 和 isotonic 的取舍（小样本过拟合所以倾向 Platt）、ECE 怎么算，面试官会认定你既懂 ML 又懂工程。诚实标注 🔴 待标定也加分--说明你知道这是要数据驱动的，不是拍脑袋。

**防守话术**："模型说 0.8 不代表 80% 准，LLM 经过 RLHF 系统性 overconfident。所以离线用评测集分桶算每桶实际准确率画 reliability diagram，overconfident 就用 Platt scaling 修正--小样本用 isotonic 易过拟合，倾向 Platt。标定曲线版本化，监控 ECE < 0.1。这是标定 + 阈值 + 兜底的组合，不是单点信任模型自评。"

#### C.3 转人工盯"突增"不盯"上限"--信号 vs 噪声

**核心机制**（§5.4 / §9.4）：
- 低置信转人工**不告警上限**，而是告警**突增**（同比 +50%，P3）。
- 转人工**占比**（健康兜底信号）与**突增**（异常信号）双监控。
- 转人工的报告进工程师队列，工程师处置结果（采纳/驳回/修改）回写，作为评测正负样本（闭环）。

**为什么是亮点**：体现"可观测不是堆指标，是分清信号和噪声"。转人工本身是**防错在起作用**=健康；盯上限会把正常兜底误报成故障，反而干扰。盯突增才能发现"模型/数据出问题了导致大面积转人工"。这个区别写进告警规则，是观测哲学的成熟标志。同时转人工结果回流评测集，形成"低置信 -> 转人 -> 工程师判定 -> 评测样本 -> 标定模型"的闭环，最有价值的评测样本就来自这里。

**防守话术**："转人工是兜底在工作，是健康的--盯上限会把正常兜底误报成故障。告警盯同比 +50% 突增，那才说明模型或数据出问题了。而且转人工的报告工程师处置结果回写当评测样本，低置信闭环反哺标定。"

### D. 评测与漂移--提示词即代码，变更可回归

#### D.1 提示词即代码（prompt_version + 评测门禁）

**核心机制**（§8.3 / §10）：
- 每个 system prompt 有 `prompt_version`（语义化版本或内容 hash），随 `llm_call_log` 与 span 落库。
- **改提示词必改版本号**，改了必须过 `EvalRunner` 评测集回归，对比新旧版本的准确率/ECE。
- 在线影子评测：生产问题按比例（🔴 如 5%）影子复制给新模型/新提示词跑，不影响线上，只对比差异。
- 评测脚本走 pytest，可进 CI 作为发版门禁（🔴 门禁强度待定）。

**为什么是亮点**：把 DevOps 的"变更可追溯、可回滚、可验证"纪律落到提示词上。多数项目的提示词是散在代码/配置里的字符串，改了不知道改了、没法回归、出事没法定位哪版引入的。这里把 prompt 当版本化制品：每次 LLM 调用都记用了哪版 prompt（`llm_call_log.prompt_version`），变更必过评测，还能影子对比。**"不改版本号就不许改提示词"**是硬纪律，和"过点记录不可变"同构。

**防守话术**："提示词即代码。每个 prompt 有 prompt_version 随 llm_call_log 落库，改 prompt 必改版本号，改了必过 EvalRunner 评测集回归对比新旧准确率/ECE。还能在线影子评测，生产问题按比例复制给新 prompt 跑不影响线上只对比差异。这样提示词变更可追溯可回滚可验证，不是凭感觉改。"

#### D.2 评测集三来源 + LLM-as-judge（事实源在评测方案）

**核心机制**（§10.1，完整设计见 [RAG与Agent评测-设计与实现方案.md](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md)）：
- `eval_case` 表：scenario / question / expected_hypotheses（预期根因类别与排序）/ expected_evidence_types / level。
- 三来源：① 历史真实不良案例（脱敏）② **转人工后被工程师确认/驳回的报告**（最有价值，§9.4 闭环）③ 人工构造边界场景。
- 评测指标：根因准确率 / 证据召回 / 草稿采纳率（L2）/ ECE / 工具调用冗余（实际/最少必要，越接近 1 越好）。
- 🔴 评测集规模与覆盖目标（如 200 case 覆盖 5M1E）待定，分批积累。

**为什么是亮点**：评测集质量是 AI 质量的上限。三来源里"转人工闭环"最有价值--它是真实生产分布下、被工程师判过对错的样本，比人工构造的边界场景更贴近线上。工具调用冗余这个指标也巧：不光看准不准，还看"有没有多查没用的"（Agent 反复查同一上下文是漂移信号）。诚实标 🔴 待积累。

#### D.3 漂移检测（PSI + 突增）

**核心机制**（§11）：
- **输入漂移**：问题分布漂移（5M1E 类别分布变化）、工具调用模式漂移（某工具频率突增/突减=可能反复查同一上下文）。
- **输出漂移**：置信度分布漂移（**PSI** 比较本周与基线，>0.2 告警）、假设类别分布漂移。
- **成本漂移**：token/会话 P95 超基线 1.5× 告警（提示词变长/模型啰嗦/反复重试）。
- 实时 prometheus 突增告警 + 离线每日批处理算 PSI 落 `drift_report`。
- 🔴 基线窗口（如 7 天滚动）与告警阈值待线上数据积累后定。

**为什么是亮点**：把信用风险建模里的 PSI（Population Stability Index）用到 LLM 输出分布监控上。PSI = Σ(actual_i − expected_i)×ln(actual_i/expected_i)，是对称化的 KL 散度，<0.1 稳、0.1~0.2 轻微偏移、>0.2 显著漂移。模型上线后分布会漂（车间物料变了、某类不良突增），不监控就会"上线时准、三个月后悄悄退化"。能讲清 PSI 公式和 0.2 阈值来历，是统计 rigor 的体现。

### E. LLM 观测与成本--provider 无关，懂什么时候不用 AI

#### E.1 ObservableChatModel--多 provider 观测一致性

**核心机制**（§8.4）：
- `llm_factory` 出品的模型统一包一层 `ObservableChatModel`（继承 `BaseChatModel`，拦截 `_agenerate`），拦截所有 provider 调用，统一记 `llm_call_log` + 指标。
- 无论 Claude / 通义千问 / DeepSeek / 本地模型，观测口径一致。
- 不同 provider 的 token 计数口径差异（如中文 token）在包装层**归一化**，避免指标不可比。
- prompt 全文**不落库**（体积大 + 敏感），只落摘要 + `prompt_version`；复跑靠版本号 + 会话 state 重建。

**为什么是亮点**：解决"换了模型就观测口径对不上"的工程痛点。token 计数各 provider 口径不同（OpenAI 用 tiktoken、Anthropic 自有分词、中文 token 数差异大），不归一化就没法横向比成本/延迟。包装层是正确的归一化位置--provider 无关。prompt 不落库是脱敏 + 成本考量，但保留 `prompt_version` 保证可复跑，这是"可复现 vs 不泄密"的平衡。

#### E.2 token 与成本追踪

**核心机制**（§8.2）：
- `agent_token_total` 按 prompt/completion 分桶计数，`agent_cost_usd_total` 按模型单价估算。
- 单价表 `model_pricing` 配置化（🔴 单价来源各 provider 官网实时单价，需定期同步），`CostEstimator` 按 token × 单价算。
- 按租户/车间聚合成本，给管理层看"AI 每月花多少、哪条产线用得多"。
- 成本漂移：token/会话 P95 超基线 1.5× 告警（P3）。

**为什么是亮点**：成本不是事后算账，是实时可追踪 + 漂移可发现。按租户聚合让管理层看到"AI 钱花在哪"，也间接暴露"哪条产线 Agent 用得多=可能问题多"。

#### E.3 "懂什么时候不用 AI"--L3 的核心健康指标（差异化得分点）

**核心机制**（§5.2 / §7.4）：
- L3 的 `node_trace.node_type` 区分 `CODE`（纯 Python 函数节点，不调 LLM）与 `agent`（调 LLM + 工具）。
- `l3_llm_invocation_total` 与 `l3_node_total{node_type=CODE}` 的占比是 L3 核心健康指标：**换线顺利时 LLM 调用应趋近 0**，全靠代码节点跑。
- L3 写动作过 confirmation gate，写工具未带有效 token 被 `WriteToolGate` 拒（`l3_write_rejected_total` +1，P0 告警）。

**为什么是亮点**：这是全篇最有"反直觉洞察"的点。多数人以为"AI 用得越多越智能"，这里反过来--**真正成熟的 L3 编排是"该用代码时绝不调 LLM"**。换线全程 PASS 是确定性流程，跑代码节点又快又省钱又稳，只有遇到异常/不确定才唤起 agent。把"LLM 调用占比"当健康指标（低=健康），体现你懂"AI 是特种部队不是常规军"--贵且不稳，用在刀刃上。这个认知比"我们接了大模型"高一个段位。

**防守话术**："L3 换线顺利时 l3_llm_invocation_total 应该是 0，全靠 CODE 节点跑--懂什么时候不用 AI 才是健康。LLM 调用占比低说明编排成熟，只有异常才唤起 agent。这本身就是最大的省钱和稳定。"

### F. 跨语言链路与集成--不强求 Java 改造

**核心机制**（§4.3 / §1.4 / §15.2）：
- OTel 的 `httpx` instrumentation 在每次出站 REST 自动注入 W3C `traceparent` header。
- Java 侧（生产执行/制造资源服务）若挂了 OTel agent（Spring），从 `traceparent` 续接 span，Tempo 里跨语言连成一条。
- **不要求 Java 改造**：只要透传 W3C TraceContext（行业默认）。没接 OTel 的 Java 服务，链路在那断，但 Agent 侧 span 仍完整自洽--降级可接受。
- ACL 客户端**不手动拼 traceparent**，靠 instrumentation 自动注入，避免人为出错；只额外带 `X-Tenant-*` 做权限。
- Kafka 侧：`aiokafka` 消费时从消息 header 取 `traceparent` 续接，或为自发事件新建 root span。
- 指标/日志各自独立栈（Agent 用 prometheus + Loki，Java 用既有栈），只在 trace 层互通。

**为什么是亮点**：务实的集成哲学--**不为了可观测性强迫全公司改造**。W3C TraceContext 是行业标准，httpx 自动注入，Java 已有的 OTel agent 自然续接。没接的降级可接受（Agent 侧自洽）。这比"要求所有服务统一上某套 APM"现实得多。指标/日志各自独立、只在 trace 互通，也是尊重既有投资。

## 3. 核心应答话术（高频问题，口语化背熟）

> 以下是把设计文档 §19 七问重写为**可直接说出口的完整话术**，每段 40~80 秒。结构：钩子 -> 核心 -> 深度 -> 收口。

### 话术 1：Agent 可观测和普通 APM 区别 / 为什么单独设计

"普通 APM 回答'接口慢不慢、服务挂没挂'，Agent 可观测要额外回答'这条 AI 根因假设凭什么、要不要转人'。**核心区别是产物**--APM 出火焰图，Agent 出证据链，就是假设到 trace_id 到工具结果到下游数据的可审计链。而且 Agent 多了通用服务没有的质量维度：准确率、置信度校准、漂移、token 成本。MES 场景下 AI 决策必须可审计，所以我把可观测性独立成 L1/L2/L3 三个 Agent 共用的底座，而不是各写各的埋点。一句话：APM 盯的是机器，Agent 可观测盯的是 AI 的判断对不对、凭什么。"

### 话术 2：trace 落 Tempo 又落 MySQL 不是重复吗

"不重复，是同一份 trace 的两种投影。Tempo/Jaeger 给 SRE 看火焰图，是底；`tool_call_trace` 是平铺视图给工程师 UI 用，是面。工程师不需要懂 span 树，他点假设、弹证据、看工具入参出参，这个交互用 MySQL 平铺表最直接。**两者同源**，都来自 ToolNode 同一次调用，trace_id 串起来。受众不同--SRE 看 span 树排障，工程师看平铺表审计 AI 决策，AI 负责人看评测，一套数据三种投影。"

### 话术 3：观测挂了会不会影响 Agent 跑

"不会。观测是旁路，业务节点依赖 `ObservabilityPort` 抽象接口，不直接依赖 OTel/prometheus 实现。具体实现挂了--exporter 挂、prometheus 挂--业务照样跑，只是该次没 trace。这和'Agent 失败最坏是没诊断出来'一脉相承，观测失败最坏是没记录，不会反噬业务。靠 DIP 保证：业务依赖抽象不依赖实现，测试时还能换内存实现跑离线评测不污染指标。"

### 话术 4：置信度模型说 0.8 就真 80% 准吗

"不保证，所以要标定。LLM 经过 RLHF 系统性 overconfident，尤其在不知道的问题上会自信地幻觉。所以离线用评测集把预测按置信度分桶，算每桶实际准确率画 reliability diagram，overconfident 就用 Platt scaling 修正--小样本用 isotonic 易过拟合，倾向 Platt。标定曲线版本化，监控 ECE 小于 0.1。再加上 confidence 低于 0.5 转 needs_human_review 不推操作工、报告带 disclaimer--多层兜底，宁可让人判。这不是单点信任模型自评，是三源融合、标定、阈值、兜底的组合。"

### 话术 5：怎么保证提示词改了不出事

"提示词即代码。每个 system prompt 有 prompt_version，随 llm_call_log 和 span 落库，每次调用都记用了哪版。改提示词必改版本号，改了必须过 EvalRunner 评测集回归，对比新旧版本的准确率和校准误差。还能在线影子评测，生产问题按比例复制给新提示词跑，不影响线上只对比差异，发现线上分布下的退化。这样提示词变更可追溯、可回滚、可验证，不是凭感觉改。"

### 话术 6：跨语言怎么把链路串起来，Java 要改吗

"靠 W3C traceparent。Agent 调 Java REST 时 OTel 的 httpx instrumentation 自动注入 header，Java 侧挂了 OTel agent 就续接同一 trace，在 Tempo 里跨语言连成一条。Java 不用为这个改--只要透传 W3C TraceContext，这是行业默认。某个 Java 服务没接 OTel，链路在那断开，但 Agent 侧 span 仍完整自洽，降级可接受。指标和日志各自独立栈，只在 trace 层互通，尊重 Java 侧既有投资。"

### 话术 7：转人工比例为什么不一上来就告警上限

"因为转人工是兜底在工作，是健康的--低置信转人说明防错在起作用。告警应该盯突增，同比 +50%，那才说明模型或数据出问题了。盯上限会把正常的兜底误报成故障，反而干扰。这个区别写进告警规则，体现你懂可观测不是堆指标，是分清信号和噪声。而且转人工的报告工程师处置结果回写当评测样本，低置信闭环反哺标定--转人工不是终点，是数据起点。"

### 话术 8：token 成本怎么管，会不会烧钱

"三层。一是 agent_token_total 按 prompt 和 completion 分桶计数，agent_cost_usd_total 按单价估算，按租户聚合给管理层看。二是成本漂移检测，token/会话 P95 超基线 1.5 倍告警，可能是提示词变长、模型啰嗦或反复重试。三是 recursion_limit 限制最大步数，从根本上限死单会话 token 上限。但最关键的是 L3 换线顺利时 LLM 调用应趋近 0，全靠代码节点跑--懂什么时候不用 AI，就是最大的省钱。"

## 4. 深度问答（技术深挖，考 ML + 工程功底）

**Q：reliability diagram 具体怎么画？ECE 怎么算？**
A：把评测集所有预测按模型给的置信度分到 10 个桶（0~0.1, ..., 0.9~1.0）。每个桶算两个值：该桶样本的平均置信度、该桶样本的实际准确率（预测对不对）。以置信度为 x、准确率为 y 画散点，完美标定是 y=x 对角线。ECE = Σ(|B_m|/N)×|acc(B_m)−conf(B_m)|，就是各桶"置信度-准确率"差距按桶样本量加权平均。ECE < 0.1 是目标。如果点都在对角线下方（置信度高于准确率）就是 overconfident，需要标定。

**Q：Platt scaling 和 isotonic regression 怎么选？**
A：Platt 是用逻辑回归拟合一个 2 参数映射 calibrated = sigmoid(a·conf + b)，假设置信度和准确率是某种单调 logistic 关系，参数少、小样本稳，但表达能力有限。Isotonic 是非参数单调回归，更灵活能拟合任意单调形状，但小样本下容易过拟合（每个点都能被拟合）。我的判断是评测集规模 🔴 待定、初期偏小，倾向 Platt--少参数换稳定性。等评测集上千了再考虑 isotonic。这是典型的偏差-方差权衡。

**Q：PSI 公式是什么？为什么 0.2 阈值？和 KL 散度什么关系？**
A：PSI = Σ(actual_i − expected_i)×ln(actual_i/expected_i)，把基线分布和当前分布按相同分箱，算每箱占比差乘对数比之和。它其实是双向 KL 散度的和：PSI = KL(actual‖expected) + KL(expected‖actual)，对称化版本。行业经验：<0.1 稳定、0.1~0.2 轻微偏移需关注、>0.2 显著漂移告警。这是信用评分领域验证分布稳定性的标准阈值，借用到 LLM 输出分布监控。0.2 不是数学推导，是经验值，🔴 我会在线上数据积累后复验调整。

**Q：ObservableChatModel 怎么实现？token 计数怎么归一化？**
A：继承 LangChain 的 BaseChatModel，在 `_agenerate` 里包一层：调内层模型、计时、从 `resp.usage_metadata` 取 prompt_tokens/completion_tokens、调 `obs.llm_called` 落 `llm_call_log` 和指标，异常调 `llm_failed`。token 归一化在包装层做--不同 provider 的 usage 字段口径不同（有的算系统提示有的不算，中文 token 数因分词器不同差异大），在包装层统一成"输入 token / 输出 token"两个口径，保证指标横向可比。provider 无关是关键--换模型不用改业务节点的埋点。

**Q：trace_id 怎么从 OTel 落到 MySQL 的 tool_call_trace？格式是什么？**
A：OTel span context 的 trace_id 是 128 位整数，格式化成 32 位十六进制串（`f"{ctx.trace_id:032x}"`）。`ToolNode` 调 `trace_repo.save_*` 时把当前 span 的 trace_id 一起存进 `tool_call_trace`，作为证据链的 FK。日志里也通过 `_inject_context` processor 注入同一个 trace_id。所以 trace（Tempo）、日志（Loki）、证据链（MySQL）三方靠同一个 trace_id 串起来。证据引用 trace_id 时 ReportParser 校验它必须在本会话 tool_call_trace 里查得到，保证不是编的。

**Q：recursion_limit 怎么定？和 token 成本什么关系？**
A：LangGraph 的 recursion_limit 限制图的最大迭代轮数，命中抛 GraphRecursionError。它直接等价于"单会话最多调几轮 LLM"= 单会话 token 上限的硬天花板。我会在 root span 记 `agent.recursion_limit_hit` 事件并标 TIMEOUT，转人工。阈值要平衡：太小会误杀真复杂问题，太大会烧钱 + 死循环。配套看工具调用模式漂移（§11.1）--如果某会话反复查同一上下文，是死循环信号不是真复杂。🔴 阈值需线上调参。

**Q：LangGraph checkpointer 和 trace 怎么协同？中断恢复的会话 trace 怎么续？**
A：checkpointer 的 `thread_id = session_id`，使中断恢复的会话与原 trace 同属一棵树--恢复时续 root span，不是新建一棵。这样工程师看一个会话的完整证据链不会因为中途中断/恢复而断成两段。obs_ctx（含 trace_id/session_id/tenant/level/prompt_version）是不可变值对象，随会话流动注入每个节点，保证恢复后属性一致。

**Q：Redactor 为什么是纯函数？怎么按租户配置不同策略？**
A：脱敏是安全相关逻辑，必须是纯函数（输入决定输出、无副作用）才好单测--脱敏错了是合规事故，必须能跑覆盖全部字段类型的单测。按租户配置不同策略靠策略对象注入（ISP 接口隔离）：A 车间可能序列号保留前 4 后 2，B 车间要求全打码，Redactor 接收一个 `RedactionPolicy`，不同租户传不同 policy。纯函数 + 策略注入 = 可测 + 可配置。

## 5. 广度问答（覆盖面，考全局视野）

**Q：五层模型（L0~L4）为什么这么分？**
A：下层为上层供数，各层可独立演进。L0 基础设施（OTel SDK/context/exporter）给所有人供 context 传播；L1 链路（trace/span）是底座；L2 指标（prometheus）从链路和业务节点采数；L3 业务视图（MySQL 平铺表）是 trace 的工程师可读投影；L4 评测质量（pytest + 离线统计）是离线层，消费 L3 的数据做评测标定漂移。分层的意义是**各层受众不同、演进节奏不同**--L0/L1 是 SRE 的，L3 是工程师的，L4 是 AI 负责人的，改一层不牵连其他。

**Q：和 RAG 服务的观测边界怎么划？**
A：Agent 调 RAG 时的 span 衔接约定归本篇（Agent 侧 `tool.invoke` -> RAG 侧），但 RAG 服务自己的内部观测（检索召回、向量库延迟）归 RAG 各路线方案，本篇不替它埋点。边界原则：**每个服务观测自己内部**，跨服务靠 traceparent 串，不互相侵入。和"不替 MES 业务表埋点"同理--Agent 只读它们，不替它们观测。

**Q：SLI/SLO 怎么定？告警怎么分级？**
A：SLI 有会话 P99（L1 ≤60s / L3 ≤120s，P2）、工具错误率（<1%，>5% 告警 P1）、LLM schema 失败率（<0.5%，>2% 告警 P2）、递归上限命中率（<2%，>5% 告警 P2）、低置信转人工（盯突增 P3）、token/会话 P95（超基线 1.5× 告警 P3 成本漂移）、写工具被拦（=0，任意 >0 告警 **P0**）。分级逻辑：P0 是红线越界（AI 绕过确认写），P1 是影响可用性，P2 是质量退化，P3 是趋势性信号。低置信不告警上限告警突增是特别设计的信号-噪声分治。

**Q：K8s 部署怎么搭？观测后端复用还是独立？**
A：`agent-service` Pod 挂 OTel SDK（sidecar 或 SDK 直发 Collector），prometheus `/metrics` 端口被 scrape。观测后端（Collector/Tempo/Prometheus/Grafana/Loki）若 MES 已有则复用，没有则随 Agent 一起部署。Agent 与 Java 共用一个 OTel Collector，trace 在 Tempo 跨语言连成一条；指标各存各 prometheus 或同一 prometheus 不同 job，Grafana 统一画。🔴 后端复用 vs 独立待运维确认。

**Q：数据保留怎么定？增长快的表怎么办？**
A：`llm_call_log` / `tool_call_trace` 增长快，🔴 建议热数据 30 天 + 冷归档 1 年，按合规调整。评测数据（`eval_run`）长期保留，用于版本对比和标定历史。`diagnosis_report` 含证据链，建议随工单归档周期保留便于质量追溯复盘。MySQL 业务可观测表复用 MES MySQL 但独立 schema，不混业务表。

**Q：评测门禁是硬门禁还是软门禁？**
A：🔴 待定。设计上倾向关键变更（模型升级、prompt_version 变更）走 CI 硬门禁--评测不通过不许发；常规定期回归走软门禁只报告。但要诚实：硬门禁的前提是评测集足够覆盖且有金标准，初期评测集没建全时硬门禁会误杀，所以分阶段--先软门禁积累，评测集成熟再转硬。

**Q：在线影子评测流量怎么复制？怎么保证不影响线上？**
A：生产问题按比例（🔴 如 5%）影子复制一份给新模型/新 prompt 跑，**只跑只评测不回写任何业务**，结果落独立的 `eval_run` 对比新旧报告差异。不影响线上的保证：影子调用走独立通道、独立租户上下文（只读）、绝不触发写工具、不进 confirmation gate。用于发现线上真实分布下的退化，补离线评测集覆盖不足。

**Q：LLM-as-judge 怎么用？它自己不准怎么办？**
A：用更强模型当裁判评弱模型输出的根因假设是否合理（完整设计在评测方案）。judge 不准的风险靠三点缓解：① judge 用明确 rubric（评分标准）而非自由发挥；② 关键 case 人工抽检校准 judge；③ judge 结果和人工标注算一致性，一致性低就换 judge 模型或改 rubric。诚实：LLM-as-judge 是评测规模化手段，不是金标准，金标准还是人工标注，judge 是在人工标注不够时的高性价比补充。

**Q：多 provider 切换时观测怎么保持一致？**
A：靠 ObservableChatModel 包装层（§8.4）。所有 provider 的模型都过这一层，统一记 `llm_call_log` + 指标，token 口径在包装层归一化。换 provider 不改业务节点埋点，只改 llm_factory 出品时注入的 inner model。OCP 体现：新增一个 provider 不改观测核心，只多一组 label 维度。

## 6. 压力追问（陷阱题 / 追问到底，考诚实和深度）

**Q：你说观测失败不阻断业务，那如果观测一直挂，你怎么知道观测挂了？谁来观测观测？**
A：好问题，这是 meta-observability。三层：① OTel SDK 自己有 exporter 错误日志和 dropped span 计数，prometheus 也有 scrape 失败指标--观测基础设施的健康度本身要被监控；② `tool_call_trace` 落 MySQL 是独立的，**不依赖 OTel**，所以即使 OTel 全挂、trace span 树缺了，证据链平铺表仍在、证据链仍可回溯--只是缺了 SRE 的火焰图视角；③ 兜底是"业务照跑"--观测是旁路，最坏是该次无 trace，不会反噬业务。所以不是单点：trace 通道挂了证据链还在，证据链也挂了业务还在，分层降级。

**Q：trace_id 是模型输出的，它怎么保证引用的是真实查过的数据，而不是模型编的？**
A：ReportParser 校验。hypothesis.evidence 里的每个 trace_id 必须在本会话的 `tool_call_trace` 表里查得到对应行。模型编造一个不存在的 trace_id，查不到行就 schema 校验失败、重试。所以证据不是模型嘴上说有就有，是和真实落库的调用行物理绑定的。这是证据链完整性的硬保证（§7.2），和"证据非空"强约束一起守"结论必有据"。

**Q：标定曲线也错了怎么办？模型 overconfident 你标定了，但标定曲线本身拟合错了。**
A：不单点信任标定。多层：① PSI 监控置信度分布漂移（§11.2），分布变了说明标定可能失效；② 在线算 ECE 突增告警，ECE 涨了说明标定和实际准确率脱节；③ 在线影子评测对比新旧模型，发现线上分布下的退化；④ 标定曲线版本化（calibration_version），随模型/prompt 变更重标。标定不是一次性拟合就永久有效，是持续监控 + 周期重标。没有单一信任点，是多层交叉验证。

**Q：评测集本身有 bias 怎么办？你的准确率指标是基于一个有偏的集子算的。**
A：诚实说，评测集质量是 AI 质量的上限，这是个持续工程不是一次性。缓解：① 三来源（历史真实/转人工闭环/人工构造边界）降低单一来源 bias，其中转人工闭环最贴近线上真实分布；② 在线影子评测补离线覆盖不足，用线上真实分布对比发现离线集没覆盖的退化；③ 评测集持续积累，转人工报告持续回流当新样本；④ 评测集本身要 review 覆盖度（5M1E 各维度是否均衡）。但我不假装能消除 bias--只能持续扩大覆盖、用多来源对冲、用在线信号兜底。

**Q：recursion_limit 命中转人工，但万一是真复杂问题需要更多步呢？你把真复杂的也转人了。**
A：区分"模型死循环"和"真复杂"。看三个信号：① 工具调用模式--是否反复查同一上下文（漂移信号 §11.1），反复查=死循环不是真复杂；② token 成本--是否在烧钱却没收敛；③ 工具成功率--是否大量失败。真复杂 case 本就该转人--AI 不该硬撑，MES 防错就是"宁可让人判"。recursion_limit 是兜底防失控，不是追求"AI 一定要自己搞定"。🔴 阈值需线上调参平衡误杀和烧钱。

**Q：token 成本告警了，但准确率不能降，你怎么权衡？降本和保准冲突时选哪个？**
A：准确率优先。成本是 P3 趋势信号，准确率回归是发版门禁（更高优先级）--不能为省钱牺牲准确率。但可以分"必要成本"和"浪费成本"：必要的（查够证据得出结论）不能砍，浪费的（提示词啰嗦、模型重复输出、死循环重试）要砍。手段：优化 prompt 长度、简单 case 用代码节点不调 LLM（L3 的 CODE 节点）、recursion_limit 兜底、按场景选模型档位。本质是"该花的钱花、不该花的省"，不是一刀切降本。

**Q：L3 换线全程 PASS 时 LLM 为 0，但万一代码节点有 bug 误判 PASS，放行了不良品呢？AI 没介入反而出事了。**
A：这正是 `node_type` 区分的价值--CODE 节点不是黑盒，它的执行也落 `node_trace`（node_type=CODE），可回溯。代码节点 bug 出事了能查到是哪个节点哪次执行判错的。而且 L3 的**真正放行动作（推放行卡）过 confirmation gate**--代码节点判定 PASS 和物理放行之间还有 gate，写工具未带有效 token 会被 WriteToolGate 拒（P0 告警）。所以"代码节点判定"和"物理放行"是两层，中间有 gate 兜底。代码节点 bug 是代码质量问题靠测试/回归守，不是靠 AI 兜--把 AI 当代码 bug 的兜底是错配。

**Q：跨租户共享评测案例库，但运行时 trace 严格租户隔离，不矛盾吗？**
A：不矛盾，是两个层面。评测数据是**知识资产**（脱敏后的不良案例），跨租户共享让所有车间都能从一个案例库学习，提升评测覆盖；运行时观测数据是**数据安全**（trace/报告/工具调用），严格按租户隔离，A 车间查不到 B 车间 trace。脱敏是桥梁--真实案例脱敏后失去租户归属才能共享。🔴 是否可跨租户共享待合规确认，但设计上"评测数据脱敏共享 + 运行时数据严格隔离"是不矛盾的分层。

**Q：observability 依赖 MySQL/OTel/Prometheus，这些挂了观测全没了，不是单点吗？**
A：不是单点，是分层降级。OTel 挂->无 trace span 树，但 MySQL 证据链仍在（独立落库）；Prom 挂->无指标，但 trace 和日志仍在；MySQL 挂->证据链暂缺，但业务照跑（观测是旁路）。而且观测后端是可替换的--OTel 是标准，trace 后端 Tempo/Jaeger 可换；prometheus 指标也可换 OTel metrics。分层 + 旁路 + 标准化接口，没有单点失效会反噬业务。最坏情况是"某次观测数据缺失"，不是"系统不可用"。

**Q：为什么不用 LLM 自己输出 confidence 就行，要搞三源融合 + 标定，是不是过度工程？**
A：不是过度，是 LLM 已知缺陷的必要应对。RLHF 后的模型系统性 overconfident，尤其在不知道的问题上自信地幻觉--这是有论文支撑的。单点信任会把高置信的错答推给操作工，MES 防错场景下是质量事故。三源融合引入外部信号校验自评，标定修正系统偏差，阈值转人工兜底，是"不单点信任模型"的工程化，和 MES"宁可让人判"同构。成本相对可控（离线标定是批处理），收益是防误导。如果场景是"错了无所谓"的 toC 聊天，确实不需要；但 MES 要可审计可转人，就需要。

## 7. 设计权衡题（考架构判断力）

**Q：为什么选 OpenTelemetry 不自己造埋点框架？**
A：标准 + 跨语言 + 生态。OTel 是 CNCF 标准，httpx instrumentation 自动注入 traceparent，Java 侧 Spring OTel agent 能续接同一 trace--自己造的做不到跨语言互通。生态成熟（Collector/Tempo/Prometheus/Grafana 都原生支持）。而且 OTel 不锁定后端，trace 后端 Tempo/Jaeger 可换。自己造的成本高、没人续接、锁死。除非有极特殊需求，标准方案永远优先。

**Q：为什么 trace 既落 Tempo 又落 MySQL，不只用一个？**
A：受众和查询模式不同。Tempo 是时序 trace 存储，擅长 span 树查询、火焰图、按 trace_id 检索，给 SRE；MySQL 平铺表擅长按 session_id/hypothesis/tenant 关联业务字段做工程师 UI 的证据下钻。如果只用 Tempo，工程师 UI 要跨 Tempo + 业务库 join，慢且复杂；只用 MySQL，丢了 span 树的层次结构和 SRE 火焰图。两套并存、同源（trace_id 串）、各服务各受众，是受众驱动的双投影，不是冗余。

**Q：为什么用 prometheus 而不是 OTel metrics？**
A：历史 + 告警成熟度。prometheus 的 PromQL + Alertmanager 告警链路成熟，SRE 熟悉，Grafana 原生支持。OTel metrics 也在成熟中，且 OTel Collector 可以把指标转给 prometheus。实际可以混用--业务指标走 prometheus，未来可平滑迁 OTel metrics。这不是原则性选择，是阶段性的工程务实。诚实：技术选型可讨论，核心是"指标层抽象在 MetricsCollector，换实现不改业务节点"。

**Q：为什么置信度三源融合而不是单用模型自评？**
A：单点不可信。模型自评 overconfident；证据充分度反映"查没查够"（模型可能自信但证据不足）；工具成功率反映"查的过程顺不顺"（大量工具失败说明数据有问题，结论可信度该降）。三源从不同角度校验，融合后比单源鲁棒。🔴 权重待标定，但结构上三源比单源能捕获更多失效模式。

**Q：为什么转人工盯突增不盯上限？盯上限不是更直接吗？**
A：盯上限会把正常兜底误报成故障。转人工是防错在起作用=健康信号，设上限一旦超过就告警，等于"兜底工作正常"反而触发告警，是误报。盯突增（同比 +50%）才捕获真正的异常--模型/数据出问题导致大面积转人工。这是信号-噪声分治：占比是健康基线信号，突增是异常信号，两者监控目的不同。盯上限是"把正常当异常"，盯突增是"只盯偏离"。

**Q：为什么 DIP 抽象观测，不直接在业务代码里调 OTel/prometheus？**
A：三个收益。① 解耦--业务不依赖观测实现，观测挂了不阻断业务；② 可测--测试换 InMemoryObservability，离线评测不污染线上指标；③ 可演进--换 OTel 版本、换 prometheus、加新维度，不改业务节点。直接调原语会强耦合、难测试、观测成了业务依赖。DIP 在观测层的收益和在业务层一样实在，只是多数人没意识到观测也该抽象。

**Q：为什么用 prompt_version 而不是直接 git diff 追踪提示词变更？**
A：两个维度。git diff 是**开发时**的版本控制（谁改了什么），prompt_version 是**运行时**的锚点--每次 LLM 调用都记用了哪版 prompt（落 llm_call_log），出问题时能定位"这个会话这个调用用的是 p_v7"。git diff 管不到运行时哪个版本被加载了。两者互补：git 管 prompt 仓库的变更历史，prompt_version 管线上实际跑的是哪版。没有 prompt_version，出问题没法把"线上某次错误调用"和"具体哪版 prompt"对应起来。

## 9. 红线与口径纪律（面试别翻车）

> 这是**设计规划阶段**方案，不是已上线。以下话术纪律沿用 [生产执行服务-面试闪光点.md](生产执行服务-面试闪光点.md) §11。

- ❌ "已上线全链路可观测" / "线上 ECE 已拟合到 0.08" / "评测集 200 case 已建好" -- 除非真有。
- ❌ "置信度标定曲线已跑通" / "Platt 参数已定" -- 🔴 待评测数据拟合，**说"待标定"**。
- ❌ "PSI 阈值 0.2 是我定的" -- 0.2 是信用评分行业经验值，🔴 线上数据积累后复验。
- ❌ "转人工占比实测 X%" / "token 成本实测每月 Y 美元" -- 除非有真实监控。
- ❌ 把"五层模型 / SLI 目标 / 评测门禁"说成已落地 -- 它们是**设计目标**，🔴 多处待定。
- ✅ 正确讲法："这是设计阶段的可观测性方案，核心是**把 AI 推理串成可审计证据链，并用标定+评测+漂移补齐通用 APM 没有的 Agent 质量维度**。标定曲线、评测集规模、漂移阈值这些 🔴 待线上数据拟合后定，初版用模型自评 + 阈值。观测本身是只读旁路，不进过点主事务，设计上观测失败不阻断业务。"
- ✅ "证据链落 MySQL 是独立于 OTel 的，设计上即使 OTel 挂了证据链仍可回溯。" -- 讲机制 + "设计上"。

被问"上线跑过吗"时老实说："这是设计阶段方案，重点是**识别出'AI 决策要可审计 + LLM 自评不可信 + 不能拖垮过点主链'的三重矛盾，用证据链投影 + 置信度标定 + 只读旁路 DIP 抽象 + 提示词即代码解掉**，效果需要上线后用评测数据验证。"--**诚实 + 体现架构判断力，比硬吹已落地得分高**。

## 10. 一句话定位（收尾用）

"Agent 可观测性的价值不在于多埋几个点，而在于**识别出'AI 决策既要可审计回溯、又要不拖垮 ≤200ms 过点主链、还要在 LLM 自评不可信的前提下安全转人'的三重矛盾，用证据链业务投影 + 只读旁路 DIP 抽象 + 置信度三源融合标定 + 提示词即代码评测回归，做成了既能让工程师点假设查证据、又不进过点主事务、还能分清'兜底健康'与'模型退化'信号的只读旁路底座**--可追溯、可度量、可干预、可回归、可成本，观测失败不反噬业务，与 MES 防错理念同构：所有 AI 决策可回溯、可转人，最终处置仍由工程师确认。"
