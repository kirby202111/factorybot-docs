## 1. 30 秒电梯陈述（评测版）

"我给 MES 的 RAG 和 Agent 设计了一套评测底座，覆盖 **3 条 RAG 路线 + L1/L2/L3 三个 Agent 层级**，共 6 个被测对象。核心不是堆指标，而是三件事：**① 版本锚定的金标准集**--每条用例钉死 `route_version`，断言 AI 输出引用的工艺版本等于锚点、不取'当前生效版'，把版本一致性从口头约束变成可断言的硬规则；**② 安全硬失败用例集 + CI hard gate**--失效工艺泄漏、写越界、过点侵入、实体幻觉这类红线零容忍，任一非 0 即阻断发版，是 MES 防错理念在 AI 侧的延伸；**③ 转人工反馈闭环**--线上转人工的报告，工程师处置结果回写，变成带真实标签的样本，占比 ≥50%，金标准集越用越贴近线上分布。配套 LLM-as-judge 受人工标定约束（kappa ≥0.8 才当裁判）、置信度标定（ECE <0.1）、漂移检测。整套评测是只读旁路，不进过点主事务、不旁路写。"

**四个抓手**：6 对象共用底座 / 版本锚定金标准 / 安全硬失败 hard gate / 转人工闭环。

## 2. 闪光点一：版本锚定的金标准（最强护城河延伸）

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.1/§4.2）：
- 每条 `EvalCase` 带 `version_anchor`（`route_version` / `bom_version` / `rule_version`），是"该用例判定时所依据的版本"，**绝不允许被测对象取'当前生效版'替代**。
- 判定时强制比对：证据里引用的 `route_version` 必须 == 锚点；假设里建议的工艺版本必须 == 锚点；降级查询必须带 `as_of`。
- 一条"SN-001 焊接不良根因"用例钉死 `route_version=v3`--判定时 AI 引用的工艺必须是 v3，取了"当前生效的 v5"即判**版本快照正确率**失败（v1 目标 100%，硬）。

**为什么是亮点**：通用 RAG 评测没有版本概念--它检索文档不分版本，可能答出已失效 SOP。本 MES 的工艺 / BOM / 质量规则都有版本生命周期（[领域总览.md](../领域模型/领域总览.md) §5.1），错给一条已失效工艺直接批量不良。版本锚定把"版本一致性"从"设计里用快照边兜住"（[追溯型 RAG-详细设计.md](../RAG服务/追溯型 RAG/追溯型 RAG-详细设计.md) §4.4 INV-CX-02）升级为"评测时可断言验收"--评测是版本一致性三道闸（投影闸 / 检索闸 / 输出闸）的**验收方**。这是建立在追溯护城河之上的差异化，别人没有这套领域模型，评测都无从锚定。

> **一句话话术**："我的评测集每条用例钉死 route_version，AI 答的工艺版本必须等于过点当时锁定的版本，取'当前生效版'即判失败--这是把版本一致性从设计兜底变成可断言的验收规则，通用 RAG 评测没有版本概念，答出失效工艺就是批量不良。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.1/§4.2、§5.3 版本快照正确率、§5.8 失效工艺泄漏率。

## 3. 闪光点二：安全硬失败用例集 + CI hard gate（MES 防错延伸）

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §5.8、§6.5）：
- 把分散在各对象里的安全指标收敛成一张**硬失败表**（7 项，全 = 0）：失效工艺泄漏率、写越界率、租户越权率、过点主事务侵入率、PII 泄漏率、实体幻觉率、证据为空率。
- CI 门禁分 **hard / soft**：安全用例 hard gate 零容忍（任一非 0 阻断 merge）；质量用例 soft gate（准确率 <基线×0.95 阻断、ECE >0.1 告警、连续两轮失败升级 block）。
- 安全用例独立成 `safety` 集，主要来自 SYNTHETIC 人工构造（失效工艺 / 越权 / 证据缺失等边界，线上很少自然发生）。

**为什么是亮点**：很多人会把"失效工艺泄漏"和"根因 rank 差一位"混在一起用 soft gate 处理，结果红线问题被质量波动掩盖、悄悄放行。这里**安全与质量分离**--安全是 MES 防错底线（错给失效工艺 = 批量不良、错发返工单 = 批量报废），不可妥协；质量是渐进优化，允许小幅波动。这与过点执行的"200ms 保守拦截、宁可误拦不可漏放"（[生产执行服务-面试闪光点.md](生产执行服务-面试闪光点.md) §2.3）同构--**MES 防错理念从过点侧延伸到了 AI 评测侧**。

> **一句话话术**："失效工艺泄漏、写越界、过点侵入这类红线零容忍，CI 里 hard gate 阻断发版；准确率回归这类质量问题走 soft gate 允许波动。两者分离--安全是防错底线不可妥协，质量是渐进优化，混在一起会让红线问题被质量波动掩盖。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §5.8、§6.5、§1.4 硬边界。

## 4. 闪光点三：转人工反馈闭环（最有价值的数据源）

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §11.2、§4.3）：
- 线上 AI 输出 -> 置信度 < 阈值或证据不足 -> 转人工 -> 工程师在正式界面处置（采纳 / 驳回 / 修改）-> 处置结果回写 `human_label`（is_correct / corrected_root_cause）-> 候选用例入池 -> 评审通过进金标准集。
- 用例来源占比：**HANDOFF（转人工反馈）≥50%**、HISTORY（历史真实案例脱敏）~30%、SYNTHETIC（人工构造边界）~20%。
- HANDOFF 自带"真实正确性标签"--工程师判了对错，不用额外人工标注，且最贴近线上分布。

**为什么是亮点**：纯人工构造的合成用例覆盖不了线上长尾，且标注成本高。转人工闭环把"线上真实问题 + 工程师真实判定"变成评测样本，**金标准集会越用越贴近线上分布、越用越准**。它与可观测（[Agent可观测性-设计与实现方案.md](../AGENT服务/Agent可观测性-设计与实现方案.md) §9.4"转人工报告进工程师队列、处置结果回写作为正负样本"）形成闭环--可观测采集，评测消费。这是把"防错兜底"的副产物（转人工）回收成"评测燃料"，一举两得。

> **一句话话术**："金标准集最有价值的来源是转人工反馈，占比 ≥50%--线上转人工的报告，工程师处置结果回写就是带正确性标签的样本，不用额外标注，还最贴近线上分布。合成用例覆盖不了长尾，真实闭环才能。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §11.2、§4.3、§9.4 引可观测。

## 5. 闪光点四：LLM-as-judge 受人工标定约束（不黑箱）

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §10）：
- judge 按 **MES 专用 rubric** 判（证据可追溯 / 版本正确 / 5M1E 分类 / 无幻觉实体 / 安全 / 可操作性），不是泛泛的"答案好不好"。
- judge 用**与被测不同的模型族**（v1 用 Claude Opus 级当 judge），避免自评偏见。
- judge 上线当裁判前必须与**人工标注对齐**：Cohen's kappa ≥0.8 才允许当裁判，**未达标降级为人工判定**。
- 确定性的事（版本 / 安全 / 实体存在性）不交给 judge，走硬断言；judge 只判生成质量这类主观维度。

**为什么是亮点**：很多团队上 LLM-as-judge 就是"让 GPT-4 判 GPT-3.5"，黑箱裁判，judge 漂移了都不知道。这里 judge **不是黑箱**--它受人工标定约束，kappa 不达标就降级人工，宁可慢不可让不合格的 judge 放行不合格的答案。加上偏见缓解（位置偏见随机化顺序、冗长偏见 rubric 不奖励长度、版本盲区 rubric 显式告知锚点版本只判"是否等于锚点"），judge 的可信度有兜底。这和过点"宁可误拦不可漏放"一脉相承。

> **一句话话术**："judge 不是黑箱裁判--它按 MES 专用 rubric 判，上线前必须与人工标注一致性 kappa ≥0.8，不达标降级人工。确定性的事走硬断言不交给 judge，judge 只判主观维度且受人工标定约束。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §10.2/§10.3/§10.4。

## 6. 闪光点五：置信度标定（0.8 ≠ 80% 准）

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §8）：
- 模型自评的 `confidence` 是主观分数不是客观概率，overconfident（自信但常错）在 LLM 里很常见。
- 离线用评测集跑，每条 case 有 (confidence, is_correct)，按置信度分桶算每桶实际准确率，画 reliability diagram，overconfident 用 **Platt scaling**（v1，小样本稳）或 isotonic 修正。
- **ECE < 0.1** 是校准目标，标定曲线版本化（`calibration_version`），随模型 / 提示词变更重标。
- 可观测侧用标定后 confidence 定 `confidence < 0.5` 转人工的阈值--评测是阈值的"标定方"。

**为什么是亮点**：不标定的话，模型说 0.8 置信度就会被当成"80% 准"推给操作工，实际可能只有 50%--MES 场景下 overconfident 的低质量答案直接误导现场处置。标定把主观分数对齐到客观概率，再配合阈值转人工，是"不单点信任模型自评，而是标定 + 阈值 + 兜底"的组合。阈值不是拍脑袋，是标定后按可接受误报 / 漏报率反推。

> **一句话话术**："模型说 0.8 不等于 80% 准，LLM 常 overconfident。我用评测集分桶算实际准确率画 reliability diagram，用 Platt scaling 修正，ECE <0.1。标定曲线版本化，可观测侧用标定后 confidence 定转人工阈值--阈值是标定反推的，不是拍脑袋。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §8.2/§8.3/§8.4、§9.3 引可观测阈值。

## 7. 闪光点六：6 对象共用底座，指标统一又分化

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §3.2、§5）：
- 共用的是**评测骨架**：用例 schema、`EvalRunner`、`JudgeService`、`CIGate`、评测表族--抽成 `mes-eval` 共享库（monorepo 子模块），RAG 与 Agent 两个 Python 服务共用，口径一致可比。
- 各自特有的是**指标维度**：文档型看引用命中、追溯型看证据召回 + 版本快照、L1 看工具序列、L2 看草稿采纳、L3 看 LLM 占比 + 越界检测。
- 安全红线横切所有对象统一硬失败（§5.8），不因对象不同而放松。

**为什么是亮点**：不是每条路线各写一套评测、口径不可比。共用骨架保证"同一 run 的结果可比"、新增对象只加适配器不改核心（OCP/ISP，§13.1）；特有指标保证"各对象的命门都被卡住"--文档型的命门是版本过滤、L3 的命门是越界进过点。**统一底座 + 分化指标**，比一刀切或各搞各的都强。

> **一句话话术**："6 个对象共用 mes-eval 骨架（用例 schema / runner / judge / CI 门禁），口径一致可比；各自特有指标卡命门--文档型卡版本过滤、L3 卡越界进过点。安全红线横切所有对象统一硬失败。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §3.2、§5.2-§5.8、§13.1。

## 8. 闪光点七：漂移检测 + 安全漂移专门盯

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §9）：
- 漂移五类：输入（问题 / 5M1E 分布）、检索（工具调用模式）、输出（置信度 / 假设类别分布）、安全（安全指标恶化）、成本（token / 会话）。
- 质量漂移用 **PSI**（7 天滚动基线，PSI >0.2 告警）；**安全漂移专门盯**：安全指标本应恒 0，任何抬头（如失效工艺泄漏率周环比 >0）即 **P1 告警，不等 PSI**。
- 漂移发现线上分布变了 -> 触发评测集补样 -> 重跑评测看新版本在新分布下还合不合格；安全漂移触发紧急回归定位是模型还是数据 / 重索引问题。

**为什么是亮点**：质量漂移用 PSI 是常规做法，但**安全漂移不能等 PSI**--PSI 要攒够样本才算，而失效工艺泄漏抬头一天就可能流出批量不良。安全指标恒 0 是设计预期，任何非 0 就是异常，立即 P1。这是"分清信号和噪声"--质量波动是噪声（PSI 兜），安全恶化是信号（立即报）。漂移与评测闭环：漂移 -> 补评测集 -> 评测拦下 -> 修复，评测是活的不是死的。

> **一句话话术**："质量漂移用 PSI 7 天滚动、>0.2 告警；但安全漂移专门盯--失效工艺泄漏率本应恒 0，周环比一旦 >0 立即 P1，不等 PSI，因为 PSI 要攒样本而安全恶化一天就批量不良。漂移触发评测补样，评测集是活的。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §9.1/§9.2/§9.3。

## 9. 闪光点八：离线/在线双轨 + 只读旁路

**核心机制**（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §6/§7、§1.4）：
- **离线金标准（E1）**：已知答案的考题，算准确率 / 召回 / ECE，CI 门禁。
- **在线影子（E2）**：生产流量按 5% 比例复制给候选版本（新模型 / 新提示词），不影响线上，只对比新旧差异（根因类别变 / 安全触发 = HIGH 告警）。影子发现的 case + 人工判定 -> 喂回金标准集。
- 两者互补：离线覆盖不了线上长尾，影子没有标准答案没法算准确率。落地顺序离线先、影子后。
- **只读旁路**：评测只跑只读推理、落评测结果表，不写业务表；L2 评测只验草稿不调下达 API、绝不触发落库；不进过点主事务（过点 P99 ≤200ms 是硬约束）。

**为什么是亮点**：双轨覆盖"已知答案"和"线上真实分布"两个面，缺一不可。只读旁路保证评测本身不引入风险--评测阻断的是"变更发版"不是"线上推理"，评测挂了最坏是没拦住，不会反噬生产。这与可观测"观测失败不阻断业务"（[Agent可观测性-设计与实现方案.md](../AGENT服务/Agent可观测性-设计与实现方案.md) §2.2）同构。

> **一句话话术**："离线金标准是已知答案的考题算准确率，在线影子是按 5% 复制生产流量给候选版本对比差异，两者互补缺一不可。评测是只读旁路--L2 评测只验草稿不落库、不进过点主事务，评测挂了最坏没拦住，不反噬生产。"

依据：[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §6/§7、§1.4 硬边界、§7.3 影子与离线关系。

## 11. 追问防守 Q&A（深度 + 广度）

> 每条都是可直接说的应答话术。被追问时往"机制 + MES 耦合点 + 防守边界"三层答。

### 11.1 评测体系定位类

**Q1：RAG/Agent 评测为什么要独立设计？通用 RAG 评测工具（Ragas）不就够了吗？**
A：不够，差三件事。一是**强版本锚定**--Ragas 检索文档不分版本，我的工艺 / BOM / 质量规则有版本生命周期，每条用例钉死 route_version 断言引用版本等于锚点，Ragas 没这概念。二是**安全硬失败**--失效工艺泄漏、写越界、过点侵入这类 MES 红线零容忍 hard gate，Ragas 只算忠实度 / 相关性这类软指标，红线漏过去了它不知道。三是**Agent 行为**--多步工具序列、L3 越界检测、L2 草稿合规，Ragas 根本不覆盖 Agent。Ragas 我也用，但只当可选适配层接它的忠实度 / 答案相关性，核心是自研的版本锚定 + 安全硬失败 + Agent 行为（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §1.2、§13.1 adapters）。

**Q2：评测和普通软件测试 / 通用 APM 有什么区别？**
A：普通测试回答"功能对不对、接口挂没挂"，APM 回答"接口慢不慢、服务挂没挂"。评测回答的是"AI 给的根因凭什么判合格、版本带没带、有没有把失效工艺当现行答出来、置信度 0.8 是不是真八成准"。核心区别是评测对象多了 Agent 多步行为和写边界、强版本锚定、安全硬失败。APM 出火焰图，评测出**金标准判定 + 标定曲线**--可观测是过程数据（在线），评测是质量数据（离线 + 影子），两者闭环：转人工报告回流成评测样本，评测发现问题改提示词再过评测发（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §1.5）。

**Q3：评测和可观测是不是重复了？可观测里不也有置信度、漂移、转人工？**
A：不重复，是**离线 vs 在线**两面。可观测在线实时采集每次会话的 trace / 指标 / 日志（过程数据），评测离线批量跑金标准 + 影子抽样（质量数据）。可观测回答"这次推理凭什么、要不要转人"，评测回答"这版变更合不合格、能不能发"。两者共用同一套数据底座（mes-eval + 评测表族），可观测的转人工报告是评测样本的来源，评测的标定曲线反过来指导可观测的置信度阈值与告警--闭环不分家。可观测 §9/§10/§11 的标定 / 评测 / 漂移是链路侧视角，**评测的事实源在评测方案**（[Agent可观测性-设计与实现方案.md](../AGENT服务/Agent可观测性-设计与实现方案.md) §10 已收敛指针）。

### 11.2 版本锚定类

**Q4：版本一致性设计里不是已经用快照边（SNAPSHOT_OF_ROUTE）兜住了吗，为什么评测还要再测一遍？**
A：设计兜住是一回事，测得清是另一回事。`CheckpointRecord` 通过 `[:SNAPSHOT_OF_ROUTE {route_version}]` 边指向当时版本（[追溯型 RAG-详细设计.md](../RAG服务/追溯型 RAG/追溯型 RAG-详细设计.md) §4.4 INV-CX-02），这是**检索闸**。但 AI 综合时可能：① LLM 编造一个不存在的版本号；② 降级查询忘了带 as_of 取了当前状态；③ 子图裁剪时把版本边丢了。评测的版本锚定断言这三条都查--证据引用的 route_version 必须 == 锚点、降级查询 as_of 携带率 = 100%、版本快照正确率 = 100% 硬卡。**评测是三道闸（投影闸 / 检索闸 / 输出闸）的验收方**，设计兜底 + 评测验收，双保险（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.2、§5.3）。

**Q5：版本锚点脱敏吗？真实案例脱敏会不会破坏版本判定？**
A：脱敏的是业务实体（SN 保留前 4 后 2、批次 / 供应商 / 工艺阈值打码、PII 不采集），**版本锚点不脱敏**--`route_version` / `bom_version` / `rule_version` 是判定依据，必须保留真值，否则没法断言引用版本等于锚点。这和可观测的 Redactor 同规则，但版本是真值不打码（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.4）。

### 11.3 安全硬失败类

**Q6：准确率回归不也是质量问题吗，为什么安全走 hard gate、质量走 soft gate，不一起 soft？**
A：因为代价不对等。准确率从 0.85 掉到 0.80 是质量退化，可接受小幅波动（LLM 固有方差），soft gate 允许它过、连续两轮才 block。但失效工艺泄漏一次 = 错给一条已失效工艺 = 可能批量不良，写越界一次 = 错发返工单 = 可能批量报废--这些是**不可逆的质量事故**，一次都不能放。混在一起 soft 会让红线问题被质量波动掩盖、悄悄放行。安全 hard gate 零容忍是 MES 防错底线，和过点"200ms 保守拦截宁可误拦不可漏放"（[生产执行服务-面试闪光点.md](生产执行服务-面试闪光点.md) §2.3）同构（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §6.5）。

**Q7：安全用例怎么构造？线上很少自然发生失效工艺泄漏吧？**
A：对，安全用例主要来自 SYNTHETIC 人工构造（占比 ~20%）。线上正常情况下失效工艺泄漏率本应恒 0，自然样本几乎没有。所以要人工构造边界：把一条已 DEPRECATED 的工艺版本喂给检索，断言 AI 不引用它；构造 A 车间查 B 车间数据的越权请求，断言返回空 / 拒绝；构造证据不足的场景，断言拒答 + 转人工而非硬答。HANDOFF（转人工反馈）和 HISTORY 主要补质量样本，SYNTHETIC 专攻红线长尾（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.3、§5.8）。

**Q8：评测会不会拖慢过点？进不进过点主事务？**
A：绝不进。过点 P99 ≤200ms 是硬约束（[领域总览.md](../领域模型/领域总览.md) §4.1），评测跑在离线环境或独立 candidate 实例，不挂过点路径。评测阻断的是"变更发版"不是"线上推理"，评测挂了最坏没拦住，不反噬生产（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §1.4）。

**Q9：L2 草稿型 Agent 怎么评测"写"能力又不真写？**
A：L2 评测调"草稿生成"API，**不调下达 API**。被测的写能力是"草稿质量"--reentry_point / source_work_order_id 字段完整、evidence_refs 非空可回查、intent + draft 结构合规；硬卡旁路写率 = 0（草稿流程不触发直接写 MES）、confirmation 不可绕过率 = 100%（requires_confirmation 恒 True）。草稿采纳率 ≥0.60 是北极星--没人采纳说明质量不行或 gate 太重。写动作的真正落库走返工 / 工单上下文的正常应用服务、过聚合根不变式 + 事务发件箱，那是人确认后的事，评测不碰（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §5.6、§6.3）。

### 11.4 金标准与人工闭环类

**Q10：金标准集怎么来？为什么转人工反馈占比 ≥50%？**
A：三来源：HANDOFF（转人工反馈）≥50%、HISTORY（历史真实案例脱敏）~30%、SYNTHETIC（人工构造边界）~20%。HANDOFF 最有价值是因为它自带"真实正确性标签"--线上转人工的报告，工程师处置结果（采纳 / 驳回 / 修改）回写就是标签，不用额外人工标注，而且最贴近线上分布。合成用例覆盖不了长尾，历史案例要脱敏且有滞后，转人工闭环把"防错兜底的副产物"回收成"评测燃料"，金标准集越用越准（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §11.2、§4.3）。

**Q11：转人工闭环怎么跑通？工程师凭什么愿意标注？**
A：闭环是：线上 AI 输出 -> 置信度 < 阈值转人工 -> 工程师在正式界面处置 -> 结果回写 human_label -> 候选用例入池 -> 双签评审进金标准集。工程师处置本身就是日常工作（转人工的报告本来就要他判），回写只是把判定的对错结构化落库，增量成本不大。但要跑通得把标注纳入 sprint 排期与季度 KPI，归属按上下文认领（工艺类 -> 工艺工程师、质量类 -> 质量工程师），否则闭环会断在"没人回写"。这是管理动作不是纯技术（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §11.2/§11.4）。

**Q12：评测集标错了怎么办？标注者自己判错怎么办？**
A：两道保险。一是**标注一致性**：每条 case 至少 2 名工程师独立标注，Fleiss kappa ≥0.7 才纳入金标准，kappa <0.7 说明标注规范不清或 case 有歧义，修订规范或废弃 case。二是**用例版本化 + 双签**：用例修改必升 case_version，新增 / 修改 / 废弃须 AI 负责人 + 工艺/质量工程师双签。即使标错了，靠漂移检测（该类 case 准确率异常）+ judge 与人工对齐（kappa 监控）能发现端倪，再回溯修订（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §11.3、§4.5）。

### 11.5 LLM-as-judge 与标定类

**Q13：LLM-as-judge 让模型判模型，不会串通 / 偏见吗？**
A：四层防。一是**不同族**：judge 用与被测不同的模型族（v1 Claude Opus 级当 judge），避免同模型自评偏见。二是**MES 专用 rubric**：判证据可追溯 / 版本正确 / 5M1E 分类 / 无幻觉 / 安全 / 可操作性，不是泛泛"答案好不好"；版本盲区靠 rubric 显式告知锚点版本只判"是否等于锚点"，judge 不自行判断哪个版本对。三是**偏见缓解**：位置偏见随机化顺序、冗长偏见 rubric 不奖励长度。四是**人工标定约束**：judge 上线当裁判前必须与人工标注 Cohen's kappa ≥0.8，**不达标降级人工判定**，宁可慢不可让不合格 judge 放行不合格答案（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §10.3/§10.4）。

**Q14：模型说 0.8 置信度就真有 80% 准吗？怎么标定？**
A：不保证，LLM 常 overconfident。标定是离线用评测集跑，每条 case 有 (confidence, is_correct)，按置信度分桶算每桶实际准确率画 reliability diagram，overconfident 用 Platt scaling（v1，case <1000 稳健）修正，ECE <0.1 是目标。标定曲线版本化，模型 / 提示词变更重标。可观测侧用标定后 confidence 定 confidence <0.5 转人工的阈值--阈值是标定后按可接受误报 / 漏报率反推的，不是拍脑袋。三源融合（模型自评 / 证据充分度 / 工具成功率）权重待 case >500 拟合，初始版仅用模型自评 + 阈值（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §8）。

**Q15：judge 模型升级了怎么办？标定曲线失效怎么办？**
A：judge 升级必须重新过人工对齐（重测 kappa ≥0.8），否则降级人工。标定曲线带 calibration_version，模型 / 提示词变更就重标，可观测侧记下用了哪版曲线保证阈值决策可回溯。提示词改一个字也要升 prompt_version、过评测集回归、对比新旧指标--提示词即代码，不改版本号就不许改提示词（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §10.3、§8.3、§6.4）。

### 11.6 漂移与影子类

**Q16：漂移检测为什么安全漂移要专门盯、不等 PSI？**
A：PSI 要攒够样本才能算（7 天滚动基线），但失效工艺泄漏率本应恒 0，**周环比一旦 >0 就是异常**，等 PSI 攒样本可能已经流出批量不良了。所以安全漂移立即 P1 告警、不等 PSI；质量漂移（置信度分布 / 假设类别分布）才用 PSI >0.2 兜。这是分清信号和噪声--质量波动是噪声用 PSI 兜，安全恶化是信号立即报。安全漂移触发紧急回归定位是模型问题还是数据 / 重索引问题（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §9.2）。

**Q17：在线影子评测和离线金标准，能不能互相替代？**
A：不能，互补。离线金标准是"已知答案的考题"，能算准确率 / 召回 / ECE，但覆盖不了线上长尾（合成 + 历史案例有滞后）。影子是"线上没标准答案的真实题"，靠新旧版本对比找异常（根因类别变 / 安全触发 = HIGH），没法算准确率。影子发现的高差异 case + 人工判定 -> 喂回金标准集补长尾。落地顺序离线先（有基准）、影子后（补分布）（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §7.3）。

**Q18：影子评测会不会影响线上？烧钱吗？**
A：不影响线上。影子请求走独立 candidate 实例，不进生产主路径；candidate 的写工具（L2/L3）在影子模式强制降级为草稿 / 不执行，绝不产生写副作用。比例 5%、按租户 + 对象类型均匀采样避免单一车间占满。成本上影子确实多跑一份 LLM 调用，但 5% 比例可控；judge 模型用最强模型成本高，所以只对生成质量主观维度跑 judge，确定性的事走硬断言不烧 judge。整体成本靠 token / 会话 P95 监控 + 成本漂移告警兜（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §7.2、§9.3）。

### 11.7 覆盖与工程类

**Q19：RAG 三路线 + Agent 三层级用一套评测会不会牵强？指标怎么统一又分化？**
A：不牵强，是分层不是一刀切。共用的是骨架（用例 schema / EvalRunner / JudgeService / CIGate / 评测表族）抽成 mes-eval 共享库，口径一致可比。各自特有的是指标维度：文档型卡引用命中 + 版本过滤、追溯型卡证据召回 + 版本快照、L1 卡工具序列 + route_version 携带率、L2 卡草稿采纳 + 旁路写率 = 0、L3 卡 LLM 占比 + 越界进过点率 = 0。安全红线横切所有对象统一硬失败。新增对象只加适配器不改核心（OCP/ISP）（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §3.2、§5、§13.1）。

**Q20：评测集会不会过时？领域事件契约变了怎么办？**
A：评测用例版本化（case_version + 内容 hash），改用例必升版本，eval_run 记所用版本保证结果可比。领域契约变更（比如 MaterialConsumed 补 lot_no、CheckpointReleased 补 route_id）后，相关用例的 expected_evidence_node_ids 同步更新，否则会"假失败"。失效用例标 DEPRECATED 不删（保留历史 run 可回溯）。加上漂移检测发现线上分布变了就触发补样，评测集是活的不是死的（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.5、§9.3）。

**Q21：提示词改了一个字，要不要重跑全评测集？**
A：提示词即代码。改提示词必升 prompt_version，过评测集回归对比新旧指标。全集回归成本高，可分层：安全用例集（200 case 里 SYNTHETIC 红线那部分）每次必跑（hard gate）；质量用例按受影响对象过滤跑（改了追溯型 RAG 的提示词就只跑 TRACEABILITY_RAG 那批）。同一 prompt_version 多次跑的 top-1 准确率标准差应 <0.03，超阈值说明输出不稳定需调温度 / 提示词（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §6.4、§6.5）。

**Q22：多模型 provider（Claude / 通义千问 / DeepSeek / 本地）评测口径一致吗？**
A：一致。被测入口是只读 API 适配器（EvalTarget），不感知底层 provider；BaseChatModel 抽象保证切换零代码改动（[追溯型 RAG-详细设计.md](../RAG服务/追溯型 RAG/追溯型 RAG-详细设计.md) §2.1）。多 provider 的 token 计数口径差异（如中文 token）在可观测的 ObservableChatModel 包装层归一化（[Agent可观测性-设计与实现方案.md](../AGENT服务/Agent可观测性-设计与实现方案.md) §8.4），评测指标口径因此可比。本地化模型和云端 API 用同一套金标准跑，能直接对比谁更准、谁校准更好（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §6.3）。

**Q23：跨租户怎么评？A 车间评测会不会泄到 B 车间？**
A：评测数据带 tenant，默认按租户隔离、不跨租户共享；评测结果表按租户过滤查询，A 车间工程师查不到 B 车间的 trace / 报告。跨租户越权用例显式标注 cross_tenant=True，且只断言"拒绝访问"--这种用例专门验 AI 不会把 B 车间数据答给 A 车间。真实案例脱敏后才入评测集，且不出生产环境、不外发给模型供应商训练（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.4、§16）。

**Q24：拒答用例为什么重要？MES 场景下"该拒不拒"代价多大？**
A：MES 防错理念是宁可拦下让人判、不可错放。AI 在证据不足 / 投影滞后过大 / 跨上下文引用缺失时应该**拒答 + 转人工**而非硬答。拒答正确率 ≥0.90 是软指标，但"该拒不拒"在 MES 里代价是工程师按编造的根因处置、可能批量不良。所以评测专门构造 should_decline 用例：刻意给证据残缺的场景，断言 AI 输出 needs_human_review 而不是编一个答案。这和实体幻觉率 = 0 硬失败配套--不许编证据，也不许没证据硬答（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §4.1 should_decline、§5.3 拒答正确率）。

### 11.8 上线定位类

**Q25：这套评测上线了吗？**
A：这是设计阶段的引入规划，不是已落地。重点是三件事的架构判断：**版本锚定的金标准**（每条用例钉死 route_version，把版本一致性变成可断言规则）、**安全硬失败用例集**（7 项红线零容忍 CI 阻断）、**转人工反馈闭环**（线上真实问题回流成样本）。落地顺序先建金标准集与离线骨架、再接 judge 与标定、再跑 CI 门禁与人工闭环、最后漂移与影子。v1 阈值已落定但标注"上线 3 个月后按数据迭代"。诚实 + 体现"评测是 MES 防错理念在 AI 侧的延伸"，比硬吹"已建成全自动评测拦截发版"得分高（[评测方案](../RAG与Agent评测/RAG与Agent评测-设计与实现方案.md) §14、§1.4 口径纪律）。

## 12. 红线（评测版口径纪律）

- ❌ "我们已有 CI 全自动拦截发版"--这是设计规划，不是已落地。
- ❌ "评测让准确率提升 X%" / "评测拦下了 N 个不良"--除非有真实上线数据。
- ❌ 把 v1 阈值（≥0.85 召回 / ECE <0.1）说成线上实测--它们是**设计目标 / 起步阈值**，待上线后按数据迭代。
- ❌ "LLM-as-judge 完全可靠"--judge 受人工标定约束、kappa ≥0.8 才用，不达标降级人工。
- ❌ "评测进了过点主事务 / 评测自动发返工单"--评测是只读旁路，L2 评测只验草稿不落库，绝不进过点。
- ✅ 正确讲法："我设计了覆盖 6 对象的评测底座，核心是版本锚定金标准 + 安全硬失败 hard gate + 转人工闭环。v1 阈值已定（如安全 7 项 = 0、证据召回 ≥0.85、ECE <0.1），标注设计目标、上线后按数据迭代。评测是只读旁路，不进过点主事务。"
- ✅ "评测是 MES 防错理念在 AI 侧的延伸--宁可让评测拦下不合格的变更，也不盲发一条可能批量不良的答案。" -- 讲理念 + 诚实定位。

被问到"上线跑过吗"时，老实说："这是设计阶段的评测体系规划，重点是版本锚定 + 安全硬失败 + 人工闭环三条架构判断，v1 阈值已落定待上线验证。"--**诚实 + 体现架构判断力，比硬吹"已建成全自动评测"得分高**。
