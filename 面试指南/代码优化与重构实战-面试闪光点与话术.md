# 代码优化与重构实战 · 面试闪光点与话术（mock 遮蔽 / 死代码诚实化 / 三种去重模式）

> **定位**：本文是对 factorybot（MES Agent 服务）一轮真实代码优化的**面试纵深展开**。与前几篇"设计规划阶段"不同，这次是**已经动手做的重构**，可讲过程、改动、结果。但同样守口径纪律：**做了什么如实讲，没做的遗留项诚实交代，不吹"完美重构"**。
>
> **核心矛盾**：一套有 10 个全绿测试、DDD 分层工整、mock/real 双模式的服务，乍看很健康。优化时识别出三类隐性病：① **mock 模式掩盖真实集成缺陷**（测试全绿但切 real 必炸）；② **设计文档宣称"已接线"的机制其实是死代码**；③ **大量重复装配代码**。三个判断贯穿全文：**mock 全绿 ≠ 真实可用、诚实化 > 掩盖、去重必须行为不变**。

---

## 0. 口径纪律（先读这一条）

| 类别 | 能不能讲 | 怎么说 |
|------|---------|--------|
| 已做的改动（接线/去重/测试） | ✅ 直接讲 | 有代码有测试可验证，最硬 |
| 测试增长（10 -> 56） | ✅ 直接给 | 实跑数字 |
| 去重消除的重复（builder/scenario/ACL） | ✅ 直接给 | 有 diff 可查 |
| "重构后零缺陷" / "性能提升 X%" | ❌ 禁止 | 没测性能，不编 |
| 遗留项（ModelRouter 未接线 / fetch real TODO / 3 scenario 无端到端） | ⚠️ 主动交代 | 诚实是加分项，被追问才说不加分反扣分 |
| 真实部署跑过 | ❌ 老实说没上线 | MockTransport 模拟 real 路径，非真实基础设施验证 |

一句话：**做了的讲透，没做的摆明，重构的价值在"识别判断 + 行为不变"不在"改了多少行"**。

## 1. 30 秒电梯陈述

"我对一个 MES Agent 服务做了一轮代码优化，核心是**识别并消除'测试全绿但真实模式会炸'的隐性缺陷**，再用**模板方法 / 声明式 / 泛型三种模式去重**，全程行为不变、测试从 10 涨到 56。最值得讲的不是改了多少行，是三个判断：一是 **mock 模式掩盖了 real 集成缺陷**--HTTP 方法不符、checkpointer 恒用内存、成本路由门禁空转，我用 httpx MockTransport 补真实路径测试把它们暴露出来；二是发现**设计文档宣称'已接线'的成本路由其实是死代码**（route() 从未被调用），我选择诚实化打 warn 而不是假装接线；三是**去重时坚持行为不变**，store 校验的不一致保留差异、不借机统一，3 个无测试的 scenario 先补装配测试再重构。"

**三个抓手**：mock 遮蔽识别 / 死代码诚实化 / 行为不变去重。

## 2. 闪光点详解（按主线）

### A. mock 全绿 ≠ 真实可用（最大亮点）

#### A.1 mock 模式掩盖了四类 real 集成缺陷

**识别过程**：服务有 mock/real 双模式，`is_mock` 时 ACL 走 fixture、LLM 走 MockChatModel、checkpointer 走 MemorySaver。10 个测试全在 mock 下跑，全绿。但逐个核对 real 分支发现：

- **HTTP 方法不符**：factorybot 的 RAG ACL 用 `_get`（GET）调 `/rag/trace/query`，但 FactoryRAG 对应路由是 `POST` + JSON body。mock 下走 fixture 不发真实 HTTP，一切正常；切 real 立刻 `405`。而且 [rag.py](../factorybot/app/infrastructure/acl/rag.py) 注释写"POST /rag/trace/query"代码却用 GET，**注释和代码自相矛盾**。
- **checkpointer 恒用 MemorySaver**：[checkpointer.py](../factorybot/app/infrastructure/persistence/checkpointer.py) 两个分支（含 `if mysql_url and not is_mock`）都 `return MemorySaver()`，SqlSaver 被注释。real 模式 Pod 重启丢全部 interrupt/resume 会话。
- **成本路由门禁空转**：[model_router.py](../factorybot/app/infrastructure/cost/model_router.py) 的 `validate_on_startup` 对未评测模型 `pass`（注释写"生产环境取消注释 raise"）。README 宣传"三层写防线启动断言：ModelRouter EvalGate"实际不生效。
- **httpx 连接泄漏**：[wiring.py](../factorybot/app/infrastructure/acl/wiring.py) 创建 `httpx.AsyncClient`，但 lifespan shutdown 只打日志不 `aclose`。

**为什么是亮点**：这是"测试通过 ≠ 软件正确"的活样本。多数人看到 10 测试全绿 + mock/real 双模式工整就放心了。但 mock 模式的本质是"绕过真实集成点"--当所有测试都不发真实 HTTP、不连真实 DB、不调真实 LLM 时，集成契约的错误对测试不可见。**识别出"mock 是测试盲区"本身是工程成熟度的体现**。很多候选人只会写更多 mock 测试堆绿条，看不到 mock 恰好遮蔽了最危险的集成缺陷。

**防守话术**："mock 模式不是测试，是 demo。它让服务能离线跑起来，但所有真实集成点（HTTP 方法、DB 持久化、连接生命周期）都被绕过了。10 个测试全绿只证明 mock 路径自洽，不证明 real 模式能用。所以我去补了真实路径测试。"

#### A.2 用 MockTransport 补真实路径回归测试

**机制**（[test_real_mode_paths.py](../factorybot/tests/test_real_mode_paths.py)）：用 `httpx.MockTransport` 注入一个假的 HTTP handler，让 ACL client 以 `mock=False` 跑真实 `_post_read` / `_get_view` 代码路径，但不打真实网络。handler 捕获请求方法/path/body，返回构造的 FactoryRAG 响应，验证：
- 请求方法是 POST（不是 GET）、path 是 `/rag/trace/expand`、body 是 `{"kind":"WipUnit","value":...}`
- real mapper 把 FactoryRAG 的 `TraceSubgraph`（clusters/edges）正确映射成 `TraceGraphView`（nodes/edges/subgraph_ref/version）
- ModelRouter real 模式（allow_mock=False）未评测模型不 raise（诚实化不阻断启动）

**为什么是亮点**：这是"在 CI 里抓住 real 集成缺陷"的正确手段。`httpx.MockTransport` 让真实代码路径（非 mock 分支）可测、可断言、不依赖真实基础设施。**它测的是"real 分支的逻辑正确性"，而非"mock 分支的透传"**。这套测试以后任何人在 mock 下改坏 real 契约（比如又改回 GET、又改 body 字段）都会被 CI 拦下。比"加更多 mock 测试"高一个段位。

**防守话术**："MockTransport 不是 mock，是 fake--它跑的是 real 分支的真实代码，只是把网络层换成了假 handler。这样 HTTP 方法、body 构造、response mapper 这些 real 逻辑都能在 CI 里断言。不依赖真实 FactoryRAG 跑起来，但能抓住'GET 改 POST 又改回去'这类回归。"

### B. 死代码诚实化 vs 掩盖（体现职业诚实）

#### B.1 ModelRouter/EvalGate 是未接线的死代码

**识别**：grep 全仓发现 `ModelRouter.route()` **从未被任何地方调用**，`EvalGate.register()` 也从未被调用，且没有评测数据源。[llm_factory.py](../factorybot/app/infrastructure/ai/llm_factory.py) 注释声称"任何模型降级必须过 EvalGate（ModelRouter 启动时查）"，但实际所有 Agent 统一用 `settings.llm_model`，跟路由表无关。README 还把"ModelRouter EvalGate"列为三层写防线启动断言之一。

**处理决策**（三个选项，选了诚实化最小改动）：
- 完整接线（route 接进每个 LLM 调用点 + 建评测数据源）：工作量大且缺评测数据，接了也无意义。
- 删除死代码：最干净，但这是面试项目的"成本优化"设计亮点，删了可惜。
- **诚实化最小改动（选定）**：real 模式启动时对未评测模型打 warn（不再静默 pass），mock 模式豁免；保留设计但不假装 route 已接入。warn 文案明确"成本路由未启用（route() 未接入调用链），统一使用 llm_model"。

**为什么是亮点**：这是**诚实 > 面子**的工程伦理。面对"设计文档说接了、README 宣传了、实际没接"的死代码，最差的选择是假装它工作（注释里写"取消注释 raise"假装是临时关闭）。诚实化让它**现状可见**：运维启动看到 warn 就知道"成本路由没生效，统一用配置的模型"，不会被 README 误导以为有门禁。这个判断比"补全接线"更务实--没有评测数据源，接 route 也没用；比"删掉"更尊重设计意图。**面试官问"你为什么不直接接上"时，能答出"缺评测数据源，接线是空转，诚实化是当前最负责任的状态"**，体现你不做表面功夫。

**防守话术**："完整接线需要评测数据源，项目还没有评测流程，接了 route 也是空转。删掉又放弃了成本路由的设计意图。所以我选诚实化：real 模式打 warn 让现状可见，mock 豁免，不假装门禁生效。等评测数据就绪再接 route 启用 raise，是渐进式的。"

#### B.2 顺带消除冗余调用（eight_d builder）

**识别**：[eight_d.py](../factorybot/app/application/builders/eight_d.py) 原代码 `nodes = await self._rag.fetch_subgraph_nodes(...)` 但 `nodes` 后续**从未使用**（只用 report.hypotheses + history）。是一次多余的 ACL 调用。重构时去掉。

**为什么是亮点**：重构不只是消除重复，也是**消除冗余**。一次无用的 ACL 调用在 mock 下无害，real 下是额外的网络往返 + 日志噪声。能发现并去掉，体现"读懂代码而非机械搬"。

### C. 契约对齐的深度（ACL mapper 真正落地）

#### C.1 不是 GET->POST 那么简单，是结构性契约差异

**识别**：用户最初以为是"GET 改 POST"的小改。读 FactoryRAG schema 后发现 mock fixture（`rag/trace_graph.json`）的数据形状与 FactoryRAG 真实 `/expand` API **完全不同**：
- 节点：mock 用 `{id, label, properties}`，FactoryRAG 用 `{node_id, label, bounded_context, props}`
- 边：mock 用 `{source, target, type}`，FactoryRAG 用 `{rel, from_id, to_id, version}`
- 子图：mock 是扁平 nodes list，FactoryRAG 是 5M1E `clusters` 分类
- `subgraph_ref`/`version`：mock 顶层有，FactoryRAG `/expand` 响应**没有**（是 `@property`/方法，pydantic 不序列化）

**处理**：这恰是 ACL mapper 的职责。[views.py](../factorybot/app/infrastructure/acl/views.py) 注释明确"mock 下透传，真实下做字段映射"。于是 real 模式写 `_map_subgraph_to_graph_view`：把 `TraceSubgraph.clusters` 五维展平成 nodes、`TraceEdge` 字段重命名、从 `seed`+`as_of` 计算 `subgraph_ref`（镜像 FactoryRAG 的 property 逻辑）、从 `clusters.method` 的 RouteVersion 节点提取 version 三字段。**View 契约和 Agent 都不变**，mock/real 产出形状一致。

**为什么是亮点**：多数人写 ACL 就是"调接口 + model_validate"，从不处理"mock 数据形状 ≠ 真实 API 形状"。结果 mock 测试全绿，real 一调字段全对不上。这里真正落地了防腐层的 mapper 职责--**mock fixture 是 factorybot 自己的理想形状，real mapper 把 FactoryRag 真实形状翻译过去**，Agent 对底层差异无感。这才是 ACL（Anti-Corruption Layer）的本意。而且处理了 `@property` 不序列化这个隐蔽坑（subgraph_ref/version 不在 JSON 里，要自己算）。

**防守话术**："mock fixture 和真实 API 形状不一致是 ACL 要解决的核心问题。mock 下 fixture 直接是 View 形状透传；real 下 FactoryRag 返回 TraceSubgraph，mapper 把 clusters 展平、字段重命名、computed 字段（subgraph_ref/version）自己算，产出和 mock 一致的 View。Agent 看到的契约不变，底层换数据源无感。这才是防腐层。"

### D. 三种去重模式（OOD/SOLID 实战）

**核心**：三处重复形态不同，用三种对应模式，不是一刀切。

| 重复形态 | 去重模式 | 落地 |
|---------|---------|------|
| 3 个 builder 的 `build()` 骨架相同（fetch->anchor->prompt->LLM->evidence->apply_anchor），差异在 fetch 什么 + prompt 文案 | **模板方法**（BaseDraftBuilder） | 子类只实现 `_fetch_context` + `_build_prompts` |
| 4 个 scenario graph 装配 ~80% 雷同（StateGraph->add_node->add_edge->compile） | **声明式 spec**（ScenarioGraphBuilder + dataclass） | 新增场景只加一个 ScenarioSpec，不写装配代码 |
| 13 个 ACL 只读方法 `_get+to_view` 重复 + 5 个写方法 token 校验重复 | **泛型方法**（BaseAclClient `_get_view` / `_validate_confirmation`） | 子类方法缩为一行委托 |

#### D.1 builder 模板方法

[base.py](../factorybot/app/application/builders/base.py) 加 `BaseDraftBuilder.build()` 固化骨架，子类（ReworkOrder/EightD/SOP）只实现 `_fetch_context`（取图节点/历史文档）+ `_build_prompts`（构造 system/user）。SOP 还有独立的 `build_from_route_activated`（无 report，不共享骨架）保留。

#### D.2 scenario 声明式 spec

[specs.py](../factorybot/app/orchestration/scenarios/specs.py) 用 `NodeSpec`/`EdgeSpec`/`ScenarioSpec` dataclass 声明节点/边，`ScenarioGraphBuilder.build()` 统一装配。三种条件边（并行派发 / barrier 分流 / gate retry）由 builder 分类处理。删除 4 个 `build_*_graph.py`，顺带去掉 `fault_response._fault_barrier` 死代码（定义未用）。新增场景只加一个 spec。

#### D.3 ACL 泛型

[base.py](../factorybot/app/infrastructure/acl/base.py) 加 `_get_view`（只读 GET+to_view 一体）+ `_validate_confirmation`（写校验泛型）。13 个只读 client 方法缩为一行委托；5 个写方法消除 token 校验重复。

**为什么是亮点**：能根据重复形态选对模式，而不是见重复就抽函数。模板方法适合"骨架固定、步骤可变"；声明式 spec 适合"结构同构、配置驱动"；泛型方法适合"入参模式一致"。三种模式都是 OOD/SOLID 的标准武器（模板方法=好莱坞原则、spec=数据驱动、泛型=DIP+DRY）。面试官问"你怎么决定用哪种去重"，能答出**按重复形态选模式**就比"我抽了个公共函数"高一个段位。

### E. 行为不变的去重纪律（重构的本质）

**纪律**：每次去重后跑全测试验证行为不变；遇到行为差异**保留现状不借机改**。

- **store.validate 不一致保留**：`ReworkWriteAclClient` 做 `valid_for` + `store.validate` 双校验，`ProcessWriteAclClient`/`PassExecutionWriteAclClient` 只 `valid_for`。去重抽 `_validate_confirmation` 时，**保留这个差异**（用 `self._store` 是否注入判断），不借去重之名统一成全做 store.validate。统一是独立的安全增强决策，不在去重范围。
- **fetch_subgraph_nodes real 模式标 TODO 不硬接**：FactoryRAG 无按 subgraph_ref 查端点，real 模式 `raise NotImplementedError` + TODO，不假装实现。mock 下仍可用。
- **3 scenario 无端到端，先补装配测试再去重**：scenario 去重前补 `test_scenario_specs.py`（4 spec build+compile 不抛 + changeover 拓扑完整），有安全网再重构。

**为什么是亮点**：**重构 = 行为保持的代码变换**，这是 Martin Fowler 的定义。很多人借"重构"夹带行为改变（顺手修 bug、顺手统一逻辑），把重构变成风险源。这里严守"去重只改结构不改行为"，store 差异、fetch TODO 都明确保留/标注，不夹带。被问"你重构时有没有顺便修点别的"，答"没有，行为不变是重构的契约，要改行为另开一次"--这正是资深与初级的分水岭。

**防守话术**："去重是行为保持的。store 校验不一致我保留差异没统一，因为统一会改变安全语义，那是独立决策不是去重的附带品。3 个 scenario 没端到端测试，我先补 build+compile 装配测试再重构，确保装配不退化。重构契约就是行为不变，要改行为我另做。"

---

### F. 测试网先行（无测试不重构）

**纪律**：去重前先建安全网。

- 去重前补 **cost/obs 横切模块单测**（38 个：EarlyStop/ResultCompactor/CacheControl/EvalGate/ModelRouter.route/PhaseToolBinder + redactor/observability/metrics），这些是宣称的亮点但 0 测试。
- scenario 去重前补 spec 装配测试（4 个）。
- 最终测试 10 -> 56。

**为什么是亮点**：**无测试不重构**是铁律。这个项目原本只有 4 个端到端冒烟测试，50+ 横切/基础设施源文件 0 单测。直接去重等于裸奔。先补测试网（尤其纯逻辑横切模块，快速且确定性高），有保护再动结构。能讲清"先建网再拆"的顺序，体现你不是莽撞改代码。

## 3. 核心应答话术（高频问题，口语化背熟）

### 话术 1：你这次优化最核心的发现是什么

"最核心是**mock 模式掩盖了真实集成缺陷**。这套服务有 mock/real 双模式，10 个测试全绿，看着很健康。但我逐个核 real 分支发现：RAG ACL 用 GET 调一个 POST 接口、checkpointer 恒用内存不持久化、成本路由门禁是空 pass、httpx 连接从不关闭。mock 下这些都绕过了所以测试绿，切 real 必炸。所以我去补了真实路径测试，用 httpx MockTransport 跑 real 分支代码但不打真实网络，把 HTTP 方法、body 构造、response mapper 都断言住。**测试全绿不代表软件正确，mock 是测试盲区**--这是这次最大的判断。"

### 话术 2：发现死代码你怎么处理的

"ModelRouter 和 EvalGate，设计文档和 README 都说接了成本路由门禁，实际 grep 发现 route() 从未被调用、register 从未被调用、也没有评测数据源。三个选择：完整接线、删除、诚实化。完整接线缺评测数据是空转，删了放弃设计意图，所以我选诚实化--real 模式打 warn 让现状可见，不假装门禁生效，mock 豁免。运维启动看到 warn 就知道成本路由没启用、统一用配置的模型。这是当前最负责任的状态，等评测数据就绪再接 route。**不假装接线，比假装工作强**。"

### 话术 3：去重用了什么设计模式

"三种重复用了三种模式。builder 是骨架相同步骤可变，用模板方法--BaseDraftBuilder 固化 build 骨架，子类只实现 fetch 和 prompt。scenario 是结构同构配置不同，用声明式 spec--dataclass 声明节点边，ScenarioGraphBuilder 统一装配，新增场景只加一个 spec。ACL 是入参模式一致，用泛型方法--_get_view 和 _validate_confirmation 收口，子类一行委托。**按重复形态选模式**，不是见重复就抽函数。三种模式分别对应好莱坞原则、数据驱动、DIP+DRY。"

### 话术 4：重构怎么保证不改坏

"两条。一是**行为不变的契约**--去重只改结构不改行为，store 校验的不一致我保留差异没借机统一，fetch real 模式没实现就标 TODO raise 不硬接。要改行为我另开一次，不夹带在重构里。二是**测试网先行**--去重前先补 cost/obs 横切模块 38 个单测和 scenario 装配测试，有安全网再动结构。每次去重完跑全测试，10 到 56 全绿才继续。无测试不重构。"

### 话术 5：mock 和真实路径测试有什么区别

"mock 测的是 mock 分支的透传--fixture 进 View 出，逻辑没经过真实集成点。MockTransport 测的是 real 分支的真实代码--HTTP 方法、body 构造、response mapper 这些 real 逻辑都跑，只是网络层换假 handler。mock 全绿只证明 mock 路径自洽，MockTransport 才证明 real 路径的逻辑对。两者都跑，前者保证 mock 模式可用（离线 demo），后者保证 real 集成契约不退化。"

## 4. 深度问答（技术深挖）

**Q：httpx MockTransport 和 unittest.mock.patch 有什么区别，为什么选前者？**
A：MockTransport 是 httpx 原生的 fake transport，注入一个 handler 函数处理请求返回 Response。它跑的是**真实的 httpx.AsyncClient + 真实的 _post_read/_get_view 代码**，只是网络 IO 被替换。unittest.mock.patch 是替换整个方法，被替换的方法体根本不执行--测不到 body 构造、header 注入这些内部逻辑。我要验证的是"real 分支构造的请求对不对"，必须让真实代码跑，所以用 MockTransport。它更像"假的网络"而非"假的方法"。

**Q：为什么 query_traceability_graph 映射到 /expand 而不是 /query？**
A：FactoryRAG 有两个端点：`/query` 返回 TraceAnswer（LLM 综合的 5M1E 假设 + subgraph_ref + version），`/expand` 返回 TraceSubgraph（原始 clusters + edges）。factorybot 的诊断 Agent 自己用 ReAct 推理，要的是**原始子图**让它自己出假设，不能让 RAG 替它综合（否则诊断 Agent 就没存在意义了）。所以映射到 /expand 拿原始子图。但 /expand 响应没有 subgraph_ref/version（是 @property 不序列化），mapper 要从 seed+as_of 算 subgraph_ref、从 clusters.method 提 version。这是契约不对齐的深度处理。

**Q：scenario spec 怎么处理三种条件边？**
A：EdgeSpec 用字段区分：`to=str` 是普通边、`to=list` 是并行派发（`add_conditional_edges(from, lambda s, t=to: t)`）、`cond + path_map` 是分流条件边。builder 里按这三个分支处理。并行派发的 lambda 用默认参数 `t=e.to` 捕获避免闭包陷阱。path_map 里的 "END" 字符串用 `_resolve` 映射到 langgraph END。changeover 的 barrier 分流（suspend->END）和 gate_disposition retry 都走 cond+path_map 分支。

**Q：store.validate 不一致为什么不顺便统一？**
A：因为统一改变安全语义。rework_write 做 store.validate（token 存在性 + action 一致性双校验），process_write/pass_write 只做 valid_for。统一成全做 store.validate 是安全增强，但它改变了 process/pass 的启动依赖（需要注入 confirmation_store）和行为（多一次 Redis 校验）。去重的契约是行为不变，夹带安全变更会让"去重"这个 PR 难以审查--reviewer 不知道哪行是去重哪行是改行为。所以保留差异，统一另开 PR 单独评估。这是**变更原子性**的纪律。

**Q：ModelRouter 诚实化具体怎么做的？**
A：原来 `validate_on_startup` 对未评测模型 `pass`（注释"生产取消注释 raise"）。改成：mock 模式（allow_mock）直接 return 豁免全部；real 模式遍历路由表，对 `eval_gate.passed(model)` 返回 False 的打 warn（capability/model/active_model + hint"成本路由未启用，统一用 llm_model"），不 raise。注入 active_model=settings.llm_model 让 warn 说清"当前实际用哪个模型"。不 raise 是因为没评测流程，raise 会让 real 模式无法启动。等评测数据就绪把 pass 改 raise 即可。

**Q：3 个 scenario 没端到端测试就重构，不怕改坏运行时行为吗？**
A：用"装配测试 + 忠实迁移"双层保护。装配测试（test_scenario_specs.py）验证 4 个 spec 都能 build+compile 不抛 + changeover 节点 13/边 14 完整 + 2 条分流边存在，抓 compile 期错误。忠实迁移指 spec 的节点/边与原 build_*_graph 一一对应（我逐行对照过），拓扑不变。changeover 有端到端测试验证运行时。其余 3 个运行时未验证是诚实遗留--但装配正确 + 拓扑忠实，运行时行为应一致。要 100% 保证需补端到端，那是后续。

## 5. 压力追问（陷阱题，考诚实）

**Q：你说 mock 遮蔽了 real 缺陷，那你怎么保证你补的 MockTransport 测试本身就对？万一你的 handler 返回的假数据也不符真实 FactoryRAG 呢？**
A：诚实的局限：MockTransport 验证的是"real 分支代码逻辑对给定响应的处理正确"，**handler 返回的假数据是我按 FactoryRAG schema 构造的**，如果 schema 我理解错了，测试仍绿但真实仍错。所以 MockTransport 抓的是"代码逻辑回归"（GET 改回 POST、body 字段改错、mapper 改坏），抓不了"schema 理解错误"。后者只能靠真实 FactoryRAG 集成测试。我没跑真实集成，这是遗留。但 MockTransport 把"代码逻辑"这层的风险消除了，比只跑 mock 强。

**Q：你识别出 ModelRouter 是死代码，为什么不直接删了更干净？留个 warn 不伦不类。**
A：三个考虑。一是这是面试项目，成本路由是设计亮点，删了讲不出"我设计过模型分派 + 评测门禁"。二是完整接线缺评测数据源是空转，现在接没意义。三是 warn 让现状可见--运维启动看到 warn 知道"成本路由没生效"，比删掉（运维不知道曾经有这设计）或假装接了（运维以为有门禁）都负责任。不伦不类是过渡态，等评测数据就绪接 route 启用 raise 就完整了。**诚实的过渡态好于虚假的完成态**。

**Q：去重后行数没减多少（净 -15 行），你确定这叫去重？**
A：行数不是去重的指标。scenario 去重删 4 个文件但新增 specs.py（含 dataclass + builder + 4 spec 声明），行数持平。但价值是**装配逻辑集中一处**（ScenarioGraphBuilder）+ **新增场景成本骤降**（加一个 spec vs 写一个 build_*_graph 装配函数）。builder 去重把 3 个 build 方法骨架上移，子类只剩两段钩子。ACL 去重 13 个方法各缩一行。去重的收益是**结构改善和可维护性**，不是行数。Fowler 说过"重构让代码更易读更易改，不一定是更短"。

**Q：store.validate 不一致是 bug 吧？process/pass 只做 valid_for 不做 store 校验，token 可能重放，你保留这个差异是不是放过了一个安全漏洞？**
A：好问题。这确实是个安全一致性问题--rework 双校验、process/pass 单校验，process/pass 的 token 理论上可重放。但我的判断是：**去重 PR 不夹带安全变更**。保留差异让现状可见（代码里 _store 注入与否决定校验强度），统一成全做 store.validate 是独立的安全增强，需要单独评估 process/pass 是否注入 confirmation_store、Redis 依赖是否可接受、对现有编排流程的影响。我会在遗留项里明确标出"store 校验不一致待统一"，让安全增强被看见、被单独处理，而不是混在去重里悄悄改。**放过不是不管，是不在这个 PR 里改**。

## 7. 红线与遗留（面试别翻车）

**红线**：
- ❌ "重构后零缺陷" / "性能提升 X%" -- 没测性能，不编。
- ❌ "真实部署验证过" -- MockTransport 是 fake，非真实基础设施。
- ❌ "ModelRouter 已接线" -- 诚实化 warn，route() 仍未接入。
- ✅ 正确讲法："这是一轮真实做过的代码优化，核心是识别 mock 遮蔽的 real 缺陷并用三种模式去重，测试 10 到 56 全绿。有几处遗留（ModelRouter 未接线、fetch real 未实现、3 scenario 无端到端）我主动交代，它们是渐进式推进的待办，不是隐藏问题。"
