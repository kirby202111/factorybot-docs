# 制造资源服务 · 面试闪光点（对齐最新设计）

> 面向场景：被追问"制造资源服务具体做了什么、有什么技术含量"时，分层输出"闪光点 + 可辩护指标"。
>
> **服务定位（最新口径）**：它是 Java MES 主体三服务之一（生产执行 / 制造资源 / 设备管理，共 14 个限界上下文），持有**唯一业务写权限**（[ADR-03](../架构设计v2/00-架构决策记录ADR.md)），是工艺路线、BOM、质量门禁规则、物料主数据与库存事实的权威源。它不扛高并发采集（那是设备管理服务），也不扛现场过点事务（那是生产执行服务）；它要解的是**"配置型主数据如何既给毫秒级过点供数、又给只读 AI 旁路供可断言的历史事实"**。
>
> **本文对齐的最新设计基线（旧稿口径已回收）**：
> 1. 缓存载体由"本地进程内缓存"改为 **2026-07-28 拍板的路线 B：共享 Redis 一份 + 事件刷新 + REST 降级，不引入 Caffeine / 多级缓存**（[Redis 实现说明](../实现说明/基础设施/Redis实现说明.md) §2.2 / 附录 A）。
> 2. 降级语义由笼统的"不阻塞过点主事务"细化为 **缓存 miss + REST 失败一律保守拦截 `CheckpointBlocked`**（INV-CX-05）；过点侧 fail-closed，与 [ADR-08](../架构设计v2/00-架构决策记录ADR.md) Agent 侧"fail-open = 不给建议"恰是两套边界。
> 3. Outbox 从"设计原则"落到**六状态机 + 四层限流 + 9 指标 6 告警**的实现口径（[Outbox 设计方案](../实现说明/业务事件/Outbox设计方案.md)）。
> 4. 版本快照升级为**三段版本锚点一等公民**（`route_version` / `bom_version` / `rule_version`），贯穿诊断→草稿→写意图→trace→评测，取不到锚点即拒答（ADR-06）。
> 5. 制造追溯从 `rag-service` 迁出，固定为**只读工具 + 只读数据面**；本服务的数据是它的事实与锚点来源（ADR-13、[制造追溯-需求与实现效果](../制造追溯-需求与实现效果.md)）。
> 6. 规模数字补上**按 6 条产线交付规模推算的量级**（§1），带算式、标"推算"，不再只给设计规模。
>
> **核心纪律**：说得出处的数字才说，说不出的说能力；推算量级必须带算式，设计目标必须标口径，线上实绩没跑过别编。

## 0. 口径纪律（先读这一条）

面试里最容易翻车的不是机制讲错，而是**把设计说成实绩、把 gap 说成已实现、把推算说成监控数据**。全篇按五级标注：

| 标记 | 含义 | 讲法 |
|---|---|---|
| ✅ | 已拍板 / 已落定（权威文档明确） | 讲机制 + 标"设计上 / v1 起步值"，不讲"线上验证过" |
| 🟡 | 设计已写明，上线前需验证 | "方案里有，阈值要压测确认" |
| ❌ | gap / 未落定 | "这是文档明确标出的缺口，上线前要补" |
| ⛔ | 已评估不选 | "评估过，明确不选，理由是……"（比"待补强"更准确） |
| 📐 | 演进方向（未拍板） | "下一步可以……，当前未授权" |

| 类别 | 能不能给具体数 | 怎么说 |
|------|--------------|--------|
| 设计规模（上下文 / 聚合 / 不变式 / 状态机数） | ✅ 直接给 | 文档可验证，最硬（§4 卡片 A） |
| 已拍板参数（TTL、限流、副本、保留期） | ✅ 直接给 | 标"v1 起步值 / 已拍板"（§4 卡片 B） |
| **按 6 线推算的量级**（配置读次数、读写比、主数据行数） | ✅ 给，但**必须带算式 + 标"推算"** | 见 §1；这是本文新增的规模口径，不是监控实测 |
| 架构 SLA（过点 P99、降级延迟、消息可靠性） | ✅ 给，但标"设计目标" | 区分"单次查询 / 全链路 / 降级兜底"三个不同指标 |
| 业务效果（良率提升、缺料下降、命中率实绩） | ⚠️ 没数据就别给 | 改说"覆盖能力"：全链路追溯、六维防错、批量异常识别 |
| 自造数字（"缓存命中 99.9%"、"零丢消息实测"） | ❌ 禁止 | 追问"怎么测的"立刻露馅 |

> **两套项目阶段口径要分清**：MES 主体三服务按 [简历-项目介绍](简历-项目介绍.md) 的"6 条产线交付口径"讲规模；Agent / RAG / 制造追溯只读旁路是**设计阶段的引入规划**（[rag-service 整体设计](../RAG服务/rag-service-整体设计.md) 文首口径纪律自述"不是线上已落地能力"），不能说已上线。本文所有推算量级都不是监控数据。

## 1. 规模基线：按 6 条产线推算（开口先报这组）

> **口径**：输入基数取自仓库已记录的交付规模（[简历-项目介绍](简历-项目介绍.md) §五）；下表是本服务侧的**量级推算，附算式，面试可当场演算**，不是源文档数字，更不是线上实绩。被追问就老实说"按 6 条线、单线 6~10s 节拍推算的量级"。

**输入基数（有出处）**：6 条 SMT+整机线、单线节拍 6~10s/板、两班制约 20h/日、每板 8~10 个过点站点、600 多型号产品、100 多种物料、核心用户 200 多人；日过板约 5 万块、日过点写入 40~50 万次（均值约 6 TPS、峰值 50~60 TPS）、采集报文日均约 700 万条。

| # | 指标（本服务侧） | 推算量级 | 算式 / 依据 |
|---|---|---|---|
| 1 | 过点配置读放大 | **日均 120~150 万次** | 40~50 万次过点 × 每次并行校验六维缓存中来自本服务的 3 项（`ProcessRouteCache` / `QualityGateCache` / 物料防错-BOM 投影） |
| 2 | 配置读峰值 | **150~180 次/s** | 峰值 50~60 TPS × 3 项；若六维全 miss 回源，按 6 项算即 **300~360 QPS 量级**（[缓存雪崩防治](缓存雪崩防治-面试问答.md) Q2 原文"几百 QPS"） |
| 3 | 配置读写比 | **万级 : 1** | 按 600+ 型号、ECN/NPI 常态变更取"日均几十次版本生效"这一**估算假设**：120~150 万次读 ÷ 约 30 次写 ≈ 4~5 万 : 1 |
| 4 | 工艺路线 / 步骤定义 | **约 700~900 条路线、6~9 千步骤** | 600+ 型号 × 1 条主路线 + 少量变体；每路线 8~10 工序（对齐每板过点站点数） |
| 5 | 版本行（工艺 / BOM / 规则） | **千级 / 万级 / 百级** | 每路线按 2~3 个历史版本 → RouteVersion 约 1.5~2.7 千行；BOM 600+ 型号 × 20~80 料号 × 2~3 版本 → 3~10 万 BomItem 行；质量门禁按工序×检验项 → 百级 `rule_id`、数百版本行 |
| 6 | 库存 / 预占行 | **约 600~1000 行库存事实** | 100+ 物料 × 6 条线线边仓 `location`；齐套预占另按 `(work_order_id, part_no, location)` 建行 |
| 7 | 读侧缓存容量 | **活跃配置 key 千级；过点缓存 <100MB** | Redis 实现说明 §8.4 v1 估算"热层 <10MB + 过点缓存 <100MB ≈ <200MB"，`maxmemory` 4GB；✅ 已拍板 |
| 8 | 事件面占比 | **13 个命名空间中占 3 个** | `process.*` / `material.*` / `quality.*`；全系统近百领域事件，走 Outbox 的低频契约事件约 8 成（[Kafka 集成全景](../实现说明/Kafka集成全景与实现说明.md) §0） |
| 9 | 与执行数据的量级差 | **约 3 个数量级** | 过点记录年增千万级行 vs 配置版本行千~万级——这就是"配置基座"的物理含义，也是读侧可做投影、写侧可做 Outbox 的依据 |

**一句话用法**："按 6 条线推算，本服务每天要接约 150 万次配置读，而版本发布写入只有几十次，读写比万级——所以我把读侧做成共享 Redis 读投影、写侧做成 Outbox 同事务投递，两边按不同并发特征设计。"

## 2. 30 秒电梯陈述

"制造资源服务是 MES 的**生产执行数据基座**，也是 Java 主体里**唯一持有该域业务写权限**的服务。我用事件风暴 + DDD 把它拆成 **3 个限界上下文（工艺管理 / 物料 / 质量）**，一共 **17 个聚合根、45 条三段式不变式、14 个领域服务**。按 6 条产线的实际规模推算，它每天要接 **120~150 万次配置读**，但版本发布写入只有几十次——技术含量就在这个万级读写比上：**① 不可变版本 + 过点锁三段版本锚点**，工艺变更不撕裂在制品，且 `route_version`/`bom_version`/`rule_version` 现在是贯穿诊断、追溯、评测的一等公民，取不到锚点即拒答；**② 共享 Redis 六维读投影 + REST 降级 + 保守拦截**，配置查询不进过点主事务，缓存挂了宁可拦也不误放；**③ Transactional Outbox 六状态机 + 四层限流**，版本生效事件与状态变更同库事务投递。质量上下文还做了**同步门禁（快、权威）与异步判定（深、记录性）分治**，过点不被深度判定拖慢。最新的架构里它又多了一个身份：**Agent / 制造追溯只读旁路的事实与版本锚点源**，通过只读 REST + 只读 Kafka 事件供数，四道舱壁保证 AI 侧不碰过点 200ms 红线。"

**四个抓手**：17 聚合 / 45 不变式 / 不可变版本+三段锚点 / 共享 Redis 保守拦截保 200ms。

## 3. 闪光点深聊（按维度展开）

### 3.1 高可靠 · 不可变版本 + 三段版本锚点（最大闪光点）

> 三个姊妹上下文（工艺路线 / BOM / 质量门禁规则）共用同一套版本模型。最新设计把这套模型从"过点追溯用"升级为**全链路可断言的锚点层**。

**核心机制**：
- **版本化 + 生效后不可变**：`RouteVersion` / `Bom` / `QualityGateRule` 都走 `DRAFT -> SUBMITTED -> ACTIVATED -> DEPRECATED -> ARCHIVED` 同构状态机，**ACTIVATED 后内容连同所有绑定冻结**（INV-04，三上下文同号）。一旦生效，步骤 / BomItem / 判定逻辑谁都不能改。
- **过点记录锁版本快照**：每条 `CheckpointRecord` 绑定 `route_version` + BOM 快照 + 规则版本快照。工艺后续怎么改，已过点的在制品按锁定版本走完，历史追溯按当时版本永久回放。
- **版本一致性（INV-CX-01）**：版本变更仅影响**变更后首次过点**的在制品；已在制的按原版本推进。三个上下文是同一条不变式，语义同构。
- **三段锚点一等公民（ADR-06，最新）**：`route_version` / `bom_version` / `rule_version` 贯穿 `诊断 → 草稿 → 写意图 → trace → 评测`，每环可断言；追溯侧解析结果固定返回 `version_kind` + `version` + `version_ref_id` 三段。**取不到锚点即拒答**，任何"默认取当前生效版本"的代码路径判为缺陷；`ProcessRouteActivated` 只用于**新版本建 key，旧 key 不失效**；RAG 证据带 `[valid_from, valid_to]` 与 supersession 链，**由确定性规则过滤，不由相似度过滤**。
- **为什么必须确定性过滤**：嵌入相似度区分"被推翻的事实"与"重复表述"仅 AUROC 0.59（近似随机），过期事实被服务率 15~40%（ADR-06 引 arXiv:2606.26511）。指望向量检索自动排除失效工艺，物理上不成立——所以"版本对不对"必须由本服务的不可变版本数据 + 确定性规则保证，不能交给模型。
- **引用而非复制**：步骤绑定只存 `quality_gate_rule_id` / `spec_keys` / `bom_item_ref` 引用；上下文外规则弃用不回写已生效版本，只给 DRAFT 标 `stale_reference` 警告，已生效版本永远干净。

**为什么是亮点**：很多 MES 的工艺变更是个噩梦——改一条路线，线上在制的板子按新还是旧？历史按哪个版本？这里用"不可变版本 + 过点锁快照 + 只影响新过点"一次性解掉；最新设计再把同一份版本事实变成 AI 侧可断言的锚点，**把"版本一致性"从人工自觉变成跨链路的结构保证**。

依据：[工艺管理上下文](../领域模型/制造资源服务/领域建模/工艺管理上下文.md) §1.3/§6、[物料上下文](../领域模型/制造资源服务/领域建模/物料上下文.md) §1.3/§6、[质量上下文](../领域模型/制造资源服务/领域建模/质量上下文.md) §1.3/§6、[ADR-06](../架构设计v2/00-架构决策记录ADR.md)、[制造追溯](../制造追溯-需求与实现效果.md) §2.4。

### 3.2 高可用 · 共享 Redis 六维读投影 + 保守拦截（旧稿"本地缓存"已回收）

> 这是本次重写**改动最大**的一节。2026-07-28 已拍板：**路线 B「Redis 共享缓存为主 + 事件刷新 + REST 降级」，不引入 Caffeine 进程内缓存、不做多级缓存**（Redis 实现说明 §2.2 / §11 / 附录 A）。领域总览里写的"本地缓存"是逻辑归属（生产执行服务持有的读投影），**不是进程内内存**。

**核心机制（✅ 已拍板部分）**：
- **六个过点校验缓存**：`ProcessRouteCache`（订阅 `process.route.lifecycle`）、`QualityGateCache`（`quality.gate.lifecycle`）、`EquipmentAvailabilityCache`、`WorkOrderStatusCache`、`KitStatusCache`、`FirstArticleGateProjection`；另有 BOM / 替代料生效驱动的物料防错投影（`material.bom.lifecycle` / `material.substitute.lifecycle`）。其中工艺、质量门禁、物料三项的事实源是本服务。
- **载体与容量**：所有实例共享一份 Redis，key 统一 `mes:cache:{context}:{type}:{id}`，String(JSON)，DB 0；**TTL 30min + 基准 ±20% 随机抖动**（防整批同时过期）、事件驱动覆盖写刷新（无 `refreshAfterWrite`、无 `maxSize`）；`maxmemory` 4GB / allkeys-lru、**主从 + 哨兵**、持久化关闭、车间规模 ≤10 线。过点缓存 <100MB 是 v1 估算。
- **防雪崩三件套**：**启动预热回填**（活跃工单 / 当前生效工艺版本 / 在制设备可用性）+ 新消费组 `earliest` 补投影；**Redis SETNX 分布式单飞**；**空值缓存短 TTL（如 60s，举例值）** + ID 前置有效性校验。降级查询配**起步即启用的 Redis 分布式令牌桶**（Lua + `INCRBY`/`EXPIRE` 原子判桶）。
- **降级语义（关键，别答反）**：`缓存读 -> Redis 不可用 -> REST 直查源上下文（六维各自降级，本服务侧读模型 ≤500ms 单次） -> REST 失败 => CheckpointBlocked(RouteCacheMiss / EquipmentCacheMiss)`。**一律保守拦截，不是放行**（INV-CX-05，Redis §2.5）。误拦只停线几秒且留 `blocking_reason` + `failed_checks[]` 可追溯、有 `OverrideCheckpoint` 授权放行逃生通道；误放会流出不良品。
- **Redis 是主路径一等依赖**：路线 B 下 Redis 故障被单列为"过点主路径不可用"，不是旁路加速；持久化/AOF 兜底因此不是重点（§8.3 明确关闭），重点是降级链与预热。
- **CQRS 读模型**：写模型是版本化聚合，读模型是投影快照（`RouteVersionReadModel` / `BomReadModel` / `QualityGateRuleReadModel`），最终一致；降级查读模型不碰写聚合。

**三个不同的 SLA，别混着讲**：过点查询 P99 **≤200ms**（设计目标）、单次降级 REST **≤500ms**（兜底、单次）、过点全链路 **≤1s**（Redis §1.1，含扫码→防错→判定→记录→推进→累计）。批量回源的排队延迟会吃掉全链路预算，所以"有降级链"≠"降级链扛得住尖峰"。

**为什么这套扛得住**：配置读是万级读写比的主路径，共享一份 Redis 让多实例天然一致、miss 风暴天然被单点吸收，代价是 Redis 成为一等依赖（用主从+哨兵 + 预热 + 限流兜住）；`rule_id+version` 粒度的缓存键让规则弃用可精确失效；`source_event_id` 刷新幂等避免重复覆盖。

依据：[Redis 实现说明](../实现说明/基础设施/Redis实现说明.md) §1/§2/§6.2/§8/附录 A、[Kafka 集成全景](../实现说明/Kafka集成全景与实现说明.md) §3 模式 A、[领域总览](../领域模型/领域总览.md) §4.1/§5.1、[缓存雪崩防治](缓存雪崩防治-面试问答.md) Q2/Q3/Q12。

### 3.3 高可靠 · Outbox 落地口径（六状态机 + 限流 + 可观测）

> 跨服务一致性不靠分布式事务。最新设计已把"事务发件箱"从原则落成可讲参数的实现。

**核心机制**：
- **同事务原子（INV-CX-02 / BIZ-02）**：`ProcessRouteActivated` / `BomActivated` / `QualityGateRuleActivated` 的发布，与版本状态变更（SUBMITTED→ACTIVATED）+ 旧版本弃用（`superseded_by` 指向新版本）写在**同一本地事务**通过 outbox 投递；要么一起成功要么一起回滚，崩溃窗口零丢失。`QualityGateDeprecated(superseded_by=null)` 才广播移除缓存，规则修订不广播，避免噪声。
- **六状态机**：`PENDING → PUBLISHING → SENT`，异常分支 `RETRYABLE` / `DEAD_LETTER` / `DISCARDED`；**只有 PUBLISHING 能迁到 SENT**，PUBLISHING 锁超时（5min）可恢复，DEAD_LETTER 人工修复后重放。生产侧 `event_id` 唯一键去重，消费侧 `(event_id, consumer_group)` 主键幂等且**幂等记录与业务处理同事务**，手动 ack offset。
- **Publisher 四层限流 + 自适应背压**：领取节流 `1000ms / batch 100`（≤100 事件/s/实例）→ 全局令牌桶 **≤200 事件/s（burst 2×）** → 按 topic 公平（过点 topic **≤100 事件/s**、维修 ≥20 事件/s）→ `Semaphore` 在途上限；失败率 >5% 或 p99 >2s 触发乘性缩减、恢复加性回升。
- **可观测闭环**：**9 项指标 + 6 类告警**（`DEAD_LETTER>0` 持续 5min、最老 PENDING >1min、PENDING 持续增长、PUBLISHING 锁超时增长、send failure rate、消费 DLT 新增）；`SENT` 保留 3~7 天、DLT retention ≥14 天、幂等表保留 ≥7 天；统一 Envelope（`event_id` / `correlation_id` / `causation_id`）。
- **零分布式事务**：过点主事务内只写本地 DB；版本生效是独立发布事务，不进过点主事务；高频采集明确**不走 Outbox**（会把 outbox 表写爆）。

**为什么制造资源服务适合**：全是配置发布，频率低、契约性强（日均几十次量级），正好是 Outbox 的理想场景；代价是多一次 DB 写与异步延迟，在万级读写比下完全可忽略。

依据：[Outbox 设计方案](../实现说明/业务事件/Outbox设计方案.md) §3/§4/§9/§11/§13、[消息全生命周期设计](../实现说明/业务事件/消息全生命周期设计.md) §1、[Kafka 集成全景](../实现说明/Kafka集成全景与实现说明.md) §3 模式 A/G。

### 3.4 实时 · 同步门禁 vs 异步判定 分治（质量上下文）

> 本服务里最接近"高并发 / 实时流处理"的闪光点。质量上下文是"配置型主数据 + 业务判定"混合，判定随每次过点 `TestResult` 中频写入，既要快又要深。

- **同步门禁（快、权威）**：过点执行上下文基于 `QualityGateCache` 缓存规则做同步判定（`QualityGateEvaluated` → PASS/HOLD/BLOCK），在过点主事务内驱动放行 / 拦截。
- **异步业务判定（深、记录性）**：质量上下文消费 `TestResult`，用完整规则 + 缺陷分类字典翻译成 `QualityVerdict`（含缺陷分类 + 严重度），秒级延迟，供首件汇总 / 缺陷统计 / SPC。
- **不要求强一致（INV-CX-04）**：门禁权威驱动过点决策；异步 BLOCK 到达时过点可能已放行，**不回溯拦截**（否则要回滚过点主事务，破坏零分布式事务），而是记入缺陷统计供批量异常分析触发返工。
- **准实时流式批量异常检测**：每条 `QualityVerdict` 到达即按 `(work_order_id, station_id, defect_code)` 增量累积频次 + 阈值判定（非周期批量），识别 `SINGLE_INCIDENT`（单件偶发，过点分流返修）vs `BATCH_SYSTEMIC`（批次系统性，发 `BatchQualityAnomalyDetected` 触发批量返工工单）；**保守判定**，宁可多返工不可漏检系统性缺陷。

**为什么是亮点**：把"门禁（要快）"和"判定（要深）"拆成两条链，用"不要求强一致 + 异步 BLOCK 不回溯"化解时序矛盾，再用准实时流式把批量异常识别做出来——这是对"延迟 vs 深度"的清醒取舍。

依据：[质量上下文](../领域模型/制造资源服务/领域建模/质量上下文.md) §0/§3.3/§3.4/§6、[质量上下文事件风暴](../领域模型/制造资源服务/事件风暴/质量上下文.md) §2.4/§2.5。

### 3.5 高可靠 · 物料消耗最终一致 + 负库存 + 齐套预占（物料上下文）

- **消耗最终一致（INV-CX-04）**：物料扣减**不在过点主事务内**。过点发布 `CheckpointReleased`，物料上下文按 BOM 异步扣减，秒级延迟；过点防错读的是扣减前快照。
- **允许负库存但告警（INV-13）**：若消耗延迟导致超扣，允许 `available_qty` 为负并告警，**由物控人工补料 / 盘点**。禁止扣减就得跨服务回滚过点，会逼出分布式事务——这是刻意的可用性取舍。
- **齐套预占三招**：按 `location` 锁到具体线边仓；预占锁 `locked_qty`、可用 `available_qty` 两套量分离；过点消耗**直接扣 `locked_qty`**，不走"先释放再扣减"中间态。
- **多层幂等**：消耗按 `(sn, work_order_id, source_event_id)`（BIZ-04）；预占按 `(work_order_id, part_no, location)`（BIZ-05）；库存变更按 `source_event_id` 去重且**无变化不发布**（BIZ-03）。
- **消耗规则 `consumption_rule`**：`per_unit` / `per_panel`（拼板按板扣减，不逐 SN）/ `per_batch` / `proportional`（辅料按量），覆盖 PCBA 拼板、辅料损耗场景。

**为什么是亮点**：物料扣减是 MES 里最容易逼出分布式事务的地方；用"最终一致 + 允许负库存 + 多层幂等"把过点主事务彻底解放，又用预占三招保证开工前齐套判定的准确性。

依据：[物料上下文](../领域模型/制造资源服务/领域建模/物料上下文.md) §1.6/§1.7/§3.3/§3.4/§6、[领域总览](../领域模型/领域总览.md) §5.3。

### 3.6 建模深度 · 三段式不变式 + 同构状态机 + 聚合根纯洁

- **三段式不变式**：`INV-XX`（单聚合内、事务内强一致，聚合根前置条件 / 状态机守护）、`BIZ-XX`（本上下文跨聚合 / 跨实例、最终一致，领域服务 + 唯一索引 / 事件去重表，**禁止挂聚合根**）、`INV-CX`（跨上下文、事件订阅 + ACL）。本服务共 **45 条**（工艺 12 + 物料 17 + 质量 16）。
- **每个领域服务必答"为什么不放在聚合根内"**：如 `RouteActivationService` 管"唯一 ACTIVE 版本"，因为单条 `RouteVersion` 无权查同 route 的其它版本实例。全服务 **14 个领域服务**（工艺 3 + 物料 6 + 质量 5，`IqcService` 已含在质量 5 个内，不另计）。
- **3 套同构状态机**：工艺路线 / BOM / 质量门禁规则版本生命周期完全同构，便于跨上下文对齐审核 SLA 与权限模型。
- **聚合根纯洁 + ACL**：聚合根只表达状态 / 行为 / 不变式 / 领域事件，**不依赖 Spring / MQ / HTTP**；应用服务只做编排和事务边界；上下文外引用（`ProductId` / `QualityGateRuleId` / `FixtureMatchingRuleId`）经防腐层翻译，不持有其聚合。

依据：三个上下文领域建模 §3/§6、[领域总览](../领域模型/领域总览.md) §2。

### 3.7 新架构位 · 只读旁路的事实源（ADR-03 / 08 / 09 / 13）

> 这是**最新设计新增**、旧稿完全没有的一层。Agent 侧 v2 架构不重做 MES 主体，而是给它加一条只读旁路；本服务从"给过点供数"扩展为"给诊断与追溯供可断言的事实"。

- **写权限矩阵**：`agent-service` / `rag-service` / `mes-eval` 三个 Python 服务**没有任何 MES 业务写权限**；14 上下文与全部业务写路径归 Java 主体，靠聚合根不变式 + Outbox。两边只经 **REST 只读 + Kafka 只读事件**解耦，出站封装为 `Toolkit` Tool，Agent 不碰 MES 原始表。
- **工具边界对齐限界上下文（ADR-09）**：Agent 能调的工具 = 14 个上下文暴露的 toolset；**不开放任意查询**，追溯走白名单查询计划，非法计划 / 缺种子 / 超时间窗 / 超记录数一律拒绝；工具定义版本化 + 出参脱敏。
- **四道舱壁守住 200ms 红线（ADR-05/08）**：① 数据舱壁——Agent 只查独立只读副本 / 读模型，不碰主库；② 算力舱壁——独立服务身份 + 每租户信号量 + 并发上限；③ 查询预算——每工具时间窗 / 行数 / 超时 ≤2s 硬上限；④ 背压——Kafka **独立消费组** + pause，熔断后 **fail-open = 不给建议**，绝不阻塞人工界面。**过点主事务 200ms P99 不得被任何编排层触碰**。
- **制造追溯只读数据面**：MySQL 独立 schema 读模型（`trace_route_binding` / `trace_unit_operation` / `trace_test_result` 等 7 张表），Kafka 只读订阅 → 单事务"写读模型 + 记幂等 + 落位点"；四类白名单查询计划 `unit_overview` / `unit_5m1e` / `lot_units` / `work_order_history`，关联深度 2~3 跳、`max_rows` 200/300/500/300、超时 2000/3000/2500/2500ms；单次取证 P95 ≤2.0s（补数 ≤3.0s）、读模型新鲜度 ≤30s、越权返回 0、对 MES 写调用 0。**不用图数据库、不让模型生成 SQL**。
- **锚点单向流动 + 证据集单点签发**：三段 `VersionAnchor` 由追溯侧产出、`agent-service` 透传、文档检索消费；统一 `evidence_set_id` 由 EvidenceRegistry 签发。锚点冲突（追溯给 v3、入参给 v4）时编排层必须停下，不自动选一个。
- **失败语义**：版本无法解析 → `VERSION_UNRESOLVED` 缺口 + 拒绝给规范结论；读模型延迟 → 证据带 `freshness_lag_seconds` 而不静默返回旧数据；MES 只读补数不可用 → 返回已有部分 + 缺口，**不编造补齐**。

**为什么是亮点**：同一份不可变版本数据，既支撑现场毫秒级防错，又支撑旁路秒级取证，且**两套负载在物理上隔离**——这是"配置基座"在 AI 时代的第二价值，也解释了为什么版本锚点必须做成模型外的确定性层。

依据：[ADR-03/05/06/08/09/13](../架构设计v2/00-架构决策记录ADR.md)、[制造追溯](../制造追溯-需求与实现效果.md) §1~§4、[整体技术选型与模块划分](../整体技术选型与模块划分.md) §1.2/§5。

## 5. 追问防守 Q&A

**Q：制造资源服务就是个配置 CRUD，有什么技术含量？**
A：CRUD 是表象。按 6 条线推算，它每天接 120~150 万次配置读、只有几十次版本写入，而每次过点要求 P99 ≤200ms。三件事：① 不可变版本 + 过点锁三段锚点，工艺变更不撕裂在制品，且锚点现在贯穿诊断/追溯/评测；② 共享 Redis 六维读投影 + REST 降级 + 保守拦截，配置查询不进过点主事务；③ Outbox 六状态机 + 四层限流，版本生效事件崩溃零丢失。质量上下文还有同步门禁 vs 异步判定分治。最新的架构里它同时是 Agent 只读旁路的事实源，靠四道舱壁做到"供数但不侵入过点"。这是"配置基座如何支撑实时执行 + 智能诊断"的架构能力。

**Q：工艺变更时线上在制的板子按新工艺还是旧工艺？**
A：按**它首次过点锁定的版本**走完（INV-CX-01）。版本生效后不可变（INV-04），过点记录绑的是不可变快照，后续怎么改都不影响已过点记录。三个上下文（工艺 / BOM / 质量规则）是同一条不变式。最新设计更进一步：`ProcessRouteActivated` 只建新版本 key、旧 key 不失效，追溯侧按三段锚点解析"当时版本"，取不到就报 `VERSION_UNRESOLVED` 缺口并拒答，绝不回退"当前生效版"。

**Q：为什么用共享 Redis，而不是进程内本地缓存 / Caffeine 多级缓存？**
A：2026-07-28 拍板时评过三条路线。多实例部署下进程内缓存要为每个副本都维护一份，版本生效事件要么广播失效、要么各副本 TTL 各自到期，一致性窗口不可控；两级缓存还要再解决"两级失效 + 事件广播"。选**路线 B**：所有实例共享一份 Redis，事件驱动覆盖写天然一致，miss 风暴被单点吸收，pipeline 六次查询约 1ms 在 ≤1s 全链路预算内很充裕。代价是 **Redis 成了过点主路径一等依赖**，所以用主从+哨兵、启动预热回填 + `earliest` 补投影、起步即启用的分布式令牌桶、SETNX 单飞、空值缓存把故障面兜住。⚠️ 多级缓存是**已评估不选**，不是"待补强"。

**Q：缓存挂了 / 降级查询失败，过点是放行还是拦截？**
A：**保守拦截**。`缓存读 -> Redis 不可用 -> REST 直查源上下文 -> REST 失败 => CheckpointBlocked(RouteCacheMiss / EquipmentCacheMiss)`（INV-CX-05）。这是防错门禁，误拦只停线几秒且留 `blocking_reason` + `failed_checks[]`，有 `OverrideCheckpoint` 授权放行逃生通道；误放会流出不良品。注意别和 ADR-08 的 Agent 侧混淆——那边熔断后是 **fail-open = 不给建议，绝不阻塞人工界面**，两个边界两套语义。旧稿把"降级失败语义"列为 gap 是不准的，这条已落定。

**Q：降级 ≤500ms 不还是慢吗？怎么保证过点 200ms？**
A：≤500ms 是**单次兜底**，不是主路径；过点查询 P99 ≤200ms、过点全链路 ≤1s 是另外两个指标，别混着讲。主路径是命中共享 Redis 读投影，配置型主数据万级读写比、版本生效是低频事件，命中率天然极高（**>99% 是告警阈值 / 设计目标，不是实测**）。只有冷启动、版本刚切换才降级。真正的风险是**批量回源**：峰值 50~60 TPS × 六维 ≈ 几百 QPS 全砸向源上下文 MySQL，排队延迟会吃掉 ≤1s 预算——所以才要 ±20% TTL 抖动、分批预热、SETNX 单飞、空值缓存和降级限流。详见 [缓存雪崩防治](缓存雪崩防治-面试问答.md) Q2/Q3。

**Q：Outbox 比直接发 Kafka 好在哪？为什么本服务适合？**
A：解决"DB commit 成功但 Kafka 没发出去"的崩溃窗口——状态变更和 outbox 事件同本地事务。落地不是一句原则：六状态机（PUBLISHING 锁超时可恢复、DEAD_LETTER 人工重放）、四层限流 + 自适应背压、`(event_id, consumer_group)` 幂等且幂等记录与业务同事务、9 指标 6 告警。代价是多一次 DB 写与异步延迟，所以**只用于低频业务契约事件**；本服务全是配置发布（日均几十次量级，按 6 线推算），高频原始采集明确不走 Outbox。

**Q：唯一 ACTIVE 版本怎么保证不出现两个同时生效？**
A：双保险（BIZ-02）：`RouteActivationService` 生效时查读模型看同 `(route_id, route_type)` 有无现存 ACTIVATED，**同时**数据库唯一索引兜底；新版本生效时**同事务自动弃用旧版本**（发 `ProcessRouteDeprecated`，`superseded_by` 指向新版本）。聚合根无权查其它版本实例，所以归领域服务 + 唯一索引，不挂聚合根。

**Q：质量判定为 BLOCK 时过点已经放行了怎么办？**
A：立场是**过点同步门禁为权威**（INV-CX-04）。异步 BLOCK 不回溯拦截已放行过点——那要回滚过点主事务、破坏零分布式事务。而是记入缺陷统计供准实时流式累积；累积到 `BATCH_SYSTEMIC` 发 `BatchQualityAnomalyDetected` 触发批量返工工单，单件偶发走过点拦截分流单件返修。快和深分治，时序矛盾用"不回溯 + 后续兜底"化解。

**Q：物料扣减不在过点事务里，库存不准怎么办？**
A：消耗最终一致、秒级延迟，过点防错读扣减前快照。延迟导致超扣时**允许 `available_qty` 为负但告警**（INV-13），物控人工补料 / 盘点。禁止扣减就得跨服务回滚过点，违反零分布式事务。准确性靠齐套预占在开工前保证：派工时按线边仓锁定 `locked_qty`，过点消耗直接扣 `locked_qty`。

**Q：三段版本锚点为什么要做成模型外的确定性层？**
A：因为指望检索/模型自动排除失效工艺不成立——嵌入相似度区分"被推翻的事实"与"重复表述"仅 AUROC 0.59，过期事实被服务率 15~40%。所以锚点 `route_version`/`bom_version`/`rule_version` 是一等公民，RAG 证据带 `[valid_from, valid_to]` 与 supersession 链由**确定性规则**过滤；取不到锚点即拒答，回退"当前生效版"判为缺陷；评测集逐条钉锚点，版本不一致 hard fail。错给一条已失效工艺 = 批量不良，这条不能交给概率。

**Q：追溯为什么不用图数据库、不让模型生成 SQL？**
A：实测关联深度只有 2~3 跳，MySQL 关系型 JOIN + 白名单固定查询计划足够；图库带来建模与运维成本、查询易退化为全图扇出。不让模型生成 SQL 是注入面 + 性能不可控 + 租户越权三重风险：只允许四类枚举计划，每步 SQL 都带租户过滤、`LIMIT` 与超时，列白名单禁止 `SELECT *`，超预算返回"结果过多 + 建议收窄"而不放大查询。

**Q：Agent / 追溯侧会不会拖慢过点 200ms？**
A：物理上不会，ADR-05 把"过点主事务 200ms P99 不得被任何编排层触碰"写成红线，ADR-08 给四道舱壁：独立只读副本（不碰主库）、独立服务身份 + 并发上限、每工具查询预算（超时 ≤2s）、Kafka **独立消费组** + pause 背压。追溯容忍读模型 ≤30s 新鲜度，是离线旁路；熔断后 fail-open = 不给建议，不阻塞人工界面。Agent 侧查询还打点独立池占用，能与过点 P99 曲线做相关性验证。

**Q：批量异常检测是实时的还是批量的？**
A：**准实时流式**——每条 `QualityVerdict` 到达即按 `(work_order_id, station_id, defect_code)` 增量累积 + 阈值判定，不是周期批量。判定立场**保守**，倾向 `BATCH_SYSTEMIC`，宁可多返工不可漏检系统性缺陷，再由质量工程师定期复核调优阈值。流式压力大时可退化为分钟级窗口批量。

**Q：三个上下文为什么不合一个？**
A：关注点、生命周期、干系人都不同：工艺管理是"工序怎么排、版本怎么发"（工艺工程师），物料是"物料是什么、BOM 怎么配、库存多少"（物控 / 采购），质量是"检验标准、缺陷分类、门禁规则、TestResult 业务语义"（质量工程师）。混在一起，改一条质量门禁规则会动到工艺路线版本代码。但三者都是配置型主数据，所以共用同一套版本模型（同构状态机 + INV-CX-01/02），解耦即可协作，不必合并。

**Q：三段式不变式（INV / BIZ / INV-CX）有必要分这么细吗？**
A：有必要，因为**守护机制不同**。`INV` 单聚合内、事务内强一致，聚合根前置条件就能守；`BIZ` 跨聚合 / 跨实例（如唯一 ACTIVE 版本），单事务守不住，要领域服务 + 唯一索引 + 事件去重表，**禁止挂聚合根**；`INV-CX` 跨上下文，要事件订阅 + ACL。混在一起就会把"该用唯一索引保证的"误写成"聚合根前置条件"，看着对、实则守不住。45 条分三段，是让守护机制和约束边界对齐。

## 6. 真实部署补强：从"设计正确"到"线上扛得住"

> 被追问"上线还要补什么"时用。**每一项都按 §0 五级标注讲**：已拍板的讲机制，⛔ 说"评估过不选"，❌ 说"文档明确标出的缺口"，📐 说"演进方向、未授权"。**别把 gap 说成已实现，也别把"已评估不选"说成"待补强"。**

### 6.4 一句话小结

## 7. 红线：这些数字不能编

- ❌ "缓存命中 99.9% 线上实测"——`>99%` 是**告警阈值 / 设计目标**（Redis §9、在制品执行 §3.6 🔴），没有监控数据就别报数。
- ❌ "Outbox 零丢消息线上验证过" / "防雪崩已上线压测验证过"——六状态机与预热单飞是**已拍板设计**，不是压测结论。
- ❌ "我们用了 Caffeine + Redis 多级缓存" / "校验缓存迁到 MySQL 读模型"——与 2026-07-28 拍板直接冲突，已回收为「已评估不选」。
- ❌ "熔断已上线" / "批量快照加载是冷启动主路径" / "熔断后返回旧值保可用"——前者是 gap 或未采纳建议，后者把 ADR-08 的 Agent 侧 fail-open 套到了过点侧。
- ❌ "批量异常识别准确率 X%" / "物料扣减延迟 <1s 实测" / "良率提升 X%"——除非有真实 SPC / 埋点 / 上线前后对比。
- ❌ 把 §1 的推算量级（150 万次配置读、万级读写比、3~10 万 BomItem 行）说成"监控数据 / 线上实测"——**必须带"按 6 条线推算"+ 算式**。
- ❌ 把 `>99%` 命中率、50 工位并发扫码"无超时雪崩"这类来自 [简历核心贡献](简历核心贡献.md) 的表述当实绩引用——该文档自述量化数据为示例值，且已登记为不要引用。

**正确讲法**：
- ✅ "过点查询 P99 **设计目标** ≤200ms、单次降级 REST **设计目标** ≤500ms、全链路 ≤1s；配置型主数据按 6 线推算万级读写比，命中共享 Redis 是主路径，降级是兜底。"
- ✅ "Outbox 六状态机保证版本生效事件与状态变更同库事务，**设计上**崩溃窗口零丢失，消费端 `(event_id, consumer_group)` 幂等。"
- ✅ "按 6 条产线、单线 6~10s 节拍**推算**，本服务日均约 150 万次配置读、几十次版本发布——这是量级估算，不是线上实绩。"
- ❌ "我们系统缓存命中 99.9%、零丢消息、扛了几百万 QPS。"——没口径没实测，一问就穿。

被问到"上线跑过吗"时，划清边界："MES 主体三服务按 6 条产线交付口径讲设计规模与推算量级；Agent / RAG / 制造追溯是设计阶段的只读旁路引入规划，没上线。重点是**识别出配置基座与实时过点的矛盾，用共享 Redis 读投影 + 不可变版本 + Outbox 解掉，再把同一份版本事实做成 AI 侧可断言的锚点**；运行时 SLA 与业务效果需要在真实车间用监控与 SPC 数据验证。"——**诚实 + 体现架构判断力，比硬吹数字得分高**。

## 8. 一句话定位（收尾用）

"制造资源服务的价值不在于配置 CRUD，而在于**把一套按 6 线推算日均百万次读、日均几十次写的配置基座，用不可变版本 + 三段版本锚点 + 共享 Redis 读投影与保守拦截 + Outbox 六状态机，做成了既能保证全链路追溯、又不拖垮 ≤200ms 现场过点、还能给只读 AI 旁路供可断言事实的执行数据基座**——配置稳且版本可断言，执行才能快，诊断才敢信。"
