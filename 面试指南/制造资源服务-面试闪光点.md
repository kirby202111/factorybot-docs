# 制造资源服务 · 面试闪光点

> 面向场景：被追问"制造资源服务具体做了什么、有什么技术含量"时，分层输出"闪光点 + 可辩护指标"。
> **服务定位**：制造资源服务是 MES 的**生产执行数据基座**--工艺路线、产品 BOM、质量门禁规则、物料主数据与库存事实的权威源。它不是高并发采集链路（那是设备管理服务），但它在**高可靠、高可用、实时判定分治**上有一套成体系的设计，是"配置型主数据如何不拖垮现场执行"的范本。
> **核心纪律**：设计规模类指标（聚合数、不变式数、文档数）现在就能给；架构 SLA 是"设计目标"，需明确口径；良率/返工率等业务数字没跑过就一律说"覆盖能力 + 设计 SLA"，**绝不编造百分比**。

## 0. 口径纪律（先读这一条）

| 类别 | 能不能给具体数 | 怎么说 |
|------|--------------|--------|
| 设计规模（上下文数、聚合数、不变式数、状态机数） | ✅ 直接给 | 文档可验证，最硬 |
| 架构 SLA（降级查询延迟、消息可靠性、过点延迟） | ✅ 给，但标注"设计目标" | 来自 [领域总览.md](../领域模型/领域总览.md) §4.1/§5.3/§5.4 |
| 高可用设计（缓存命中率、降级兜底） | ✅ 讲机制 + 标注"设计目标" | 配置型主数据写少读多，缓存命中是主路径，降级是兜底 |
| 业务效果（良率提升、缺料下降） | ⚠️ 没数据就别给 | 改说"覆盖能力"：全链路追溯、四道防错、批量异常自动识别 |
| 自造数字（"缓存命中 99.9%"、"零丢消息实测"） | ❌ 禁止 | 追问"怎么测的"立刻露馅 |

一句话原则：**说得出处的数字才说，说不出的说能力；设计目标可以讲，线上实绩没跑过别编**。

## 1. 30 秒电梯陈述

> 用在被问"制造资源服务里你做了什么"时。

"制造资源服务是整个 MES 的数据基座，我用 **事件风暴 + DDD** 把它拆成 **3 个限界上下文（工艺管理 / 物料 / 质量）**，一共 **17 个聚合根、45 条三段式不变式**。它表面是'配置型主数据、写少读多'，但真正的技术含量在**怎么让这套配置不拖垮现场过点**：过点要求 **P99 ≤200ms**，而工艺路线 / BOM / 质量门禁全在这里。我的解法是三件事--**① 不可变版本 + 过点记录锁版本快照**，工艺变更不会撕裂在制品，历史追溯永久可回放；**② 本地缓存 + ≤500ms 降级查询**，把配置查询挡在过点主事务之外，降级不阻塞过点；**③ Transactional Outbox + 零分布式事务**，版本生效事件与状态变更同库事务投递，崩溃零丢失。质量上下文还做了一件更细的--**同步门禁（快、权威）和异步判定（深、记录性）分治**，过点不被深度判定拖慢，批量异常靠准实时流式累积识别。"

**四个抓手**：17 聚合 / 45 不变式 / 不可变版本+快照 / 缓存降级保 200ms。

## 2. 闪光点深聊（按维度展开）

### 2.1 高可靠 · 不可变版本 + routeVersion 快照绑定（最大闪光点）

> 这是制造资源服务**最值得讲**的设计。三个姊妹上下文（工艺路线 / BOM / 质量门禁规则）共用同一套版本模型，体现的是对"制造追溯"本质的理解。

**核心机制**：
- **版本化 + 生效后不可变**：工艺路线版本（`RouteVersion`）、BOM 版本（`Bom`）、质量门禁规则（`QualityGateRule`）都走 `DRAFT -> SUBMITTED -> ACTIVATED -> DEPRECATED -> ARCHIVED` 状态机，**ACTIVATED 后内容连同所有绑定冻结**（INV-04）。一旦生效，步骤 / BomItem / 判定逻辑谁都不能改。
- **过点记录锁版本快照**：每条过点记录（`CheckpointRecord`）绑定 `route_version` + BOM 快照 + 规则版本快照。工艺后续怎么改、BOM 怎么升版本，**已过点的在制品按它锁定的版本走完**，历史追溯按当时版本永久回放。
- **版本一致性不变式（INV-CX-01）**：版本变更**仅影响变更后首次过点**的在制品；已在制的按原版本推进，新版本只对"变更后第一次过点"的单件生效。工艺变更不会"撕裂"在制品。
- **引用而非复制**：步骤绑定只存 `quality_gate_rule_id` / `spec_keys` / `bom_item_ref` 这些引用，**不复制**上下文外实体。所以上下文外规则弃用**不回写已生效版本**，只给 DRAFT 草稿标 `stale_reference` 警告--已生效版本永远干净。

**为什么这是亮点**：很多 MES 的工艺变更是个噩梦--改一条工艺路线，线上在制的板子按新工艺还是旧工艺？历史追溯按哪个版本？这里用"不可变版本 + 过点锁快照 + 变更只影响新过点"一次性解掉，而且**三个上下文语义同构、统一编号**（INV-CX-01 在工艺/物料/质量里是同一条不变式），不是各写各的。

依据：[工艺管理上下文.md](../领域模型/制造资源服务/领域建模/工艺管理上下文.md) §1.3/§6（INV-04、INV-CX-01）、[物料上下文.md](../领域模型/制造资源服务/领域建模/物料上下文.md) §1.3/§6、[质量上下文.md](../领域模型/制造资源服务/领域建模/质量上下文.md) §1.3/§6。

### 2.2 高可靠 · Transactional Outbox 可靠消息 + 零分布式事务

> 跨服务一致性怎么不靠分布式事务做扎实--这是项目级最大架构闪光点在制造资源服务的落地。

**核心机制**：
- **事务发件箱（INV-CX-02）**：`ProcessRouteActivated` / `BomActivated` / `QualityGateRuleActivated` 的发布，与版本状态变更（SUBMITTED->ACTIVATED）+ 旧版本弃用，**写在同一个数据库事务**里通过 outbox 投递。要么一起成功要么一起回滚，**崩溃窗口零丢失**。
- **至少一次 + 幂等消费**：消费端按 `source_event_id` 去重表保证幂等，业务处理与幂等记录同事务。
- **唯一 ACTIVE 版本（BIZ-02）**：同 `(route_id, route_type)` / `(product_id, bom_type)` / `rule_id` 同时只允许一个生效版本。靠**领域服务查读模型 + 数据库唯一索引双保险**，新版本生效时**同事务自动弃用旧版本**--不会出现两个版本同时 ACTIVE 的脏态。
- **零分布式事务**：过点主事务内只写本地 DB，跨服务一律走事件订阅或 REST 查询。版本生效是独立发布事务，不进过点主事务。

**为什么不用直接发 Kafka**：直接发有"DB commit 成功但 Kafka 没发出去"的崩溃窗口。Outbox 多一次 DB 写、有异步延迟，**只用于版本生效这类低频业务契约事件**。制造资源服务全是配置发布，频率低、契约性强，正好是 Outbox 的理想场景。

依据：[工艺管理上下文.md](../领域模型/制造资源服务/领域建模/工艺管理上下文.md) §3.2/§6（INV-CX-02、BIZ-02）、[领域总览.md](../领域模型/领域总览.md) §5.4。

### 2.3 高可用 · 本地缓存 + 降级查询，保护过点 ≤200ms

> 制造资源服务是"写少读多"的配置基座，但要喂给"每板毫秒级"的过点引擎。怎么不让配置查询拖垮过点--这是高可用的核心。

**核心机制**：
- **本地缓存优先**：过点执行上下文订阅 `ProcessRouteActivated` / `BomActivated` / `QualityGateRuleActivated`，把工艺路线 / BOM / 质量门禁 / 替代料规则维护成**本地缓存副本**（`RouteCache` / `QualityGateCache` / 物料防错缓存）。过点命中缓存就是本地内存查询--这是主路径。
- **缓存未命中降级 REST**：未命中时降级查询制造资源服务的只读读模型（`RouteVersionReadModel` / `BomReadModel` / `QualityGateRuleReadModel`），**SLA ≤500ms（设计目标）**。这是兜底，不是主路径。
- **降级不阻塞过点主事务（INV-CX-05）**：降级查询是 REST，**不进过点主事务**；校验 / 查询失败不产生半成品状态（拒绝命令回 DRAFT 或走拦截 + 告警），过点主事务始终不被跨服务调用阻塞。
- **CQRS 读模型**：写模型是版本化聚合，读模型是投影快照，最终一致。过点降级查的是读模型，不碰写聚合。

**为什么这套扛得住**：配置型主数据写少读多，版本生效是低频事件，缓存命中率天然极高。降级 ≤500ms 是兜底设计目标，过点 ≤200ms 才是主路径目标--两者解耦，配置查询的延迟波动传不到过点主链。

依据：[领域总览.md](../领域模型/领域总览.md) §4.1/§5.1、[工艺管理上下文.md](../领域模型/制造资源服务/领域建模/工艺管理上下文.md) §0/§6（INV-CX-05）。

### 2.4 高并发 / 实时 · 同步门禁 vs 异步判定 分治（质量上下文）

> 这是制造资源服务里**最接近"高并发 / 实时流处理"**的闪光点。质量上下文是"配置型主数据 + 业务判定"混合，判定是中频写入（每次过点 TestResult 都触发），既要快又要深--用分治解。

**核心机制**：
- **同步门禁（快、权威）**：过点执行上下文基于本地 `QualityGateCache` 缓存规则做**同步门禁判定**（`QualityGateEvaluated` -> PASS/HOLD/BLOCK），在过点主事务内，驱动放行 / 拦截。这是"流量控制"，要求快，是**权威**。
- **异步业务判定（深、记录性）**：质量上下文消费 `TestResult`，用**完整规则 + 缺陷分类字典**翻译成业务判定（`QualityVerdict`，含缺陷分类 + 严重度），秒级延迟，供首件检验汇总 / 缺陷统计 / SPC。这是"质量评估与记录"，要求深，是**记录性**。
- **两者不要求强一致（INV-CX-04）**：门禁权威驱动过点决策，判定记录性不覆盖过点决策。异步 BLOCK 判定到达时过点可能已放行--**不回溯拦截**，而是记入缺陷统计，供批量异常分析触发返工。快和深分治，互不拖累。
- **准实时流式批量异常检测**：每条 `QualityVerdict` 到达即按 `(work_order_id, station_id, defect_code)` **增量累积缺陷频次 + 阈值判定**（不是周期批量）。识别 `SINGLE_INCIDENT`（单件偶发，过点拦截分流返修）vs `BATCH_SYSTEMIC`（批次性系统性，发信号触发批量返工工单）。**保守判定**--倾向于批量异常，宁可多返工不可漏检系统性缺陷。

**为什么是亮点**：很多人会把"质量判定"做成一个同步重逻辑，结果过点被拖慢。这里把"门禁（要快）"和"判定（要深）"拆成两条链，用"不要求强一致 + 异步 BLOCK 不回溯"化解时序矛盾，再用准实时流式把批量异常识别做出来。这是对"延迟 vs 深度"的清醒取舍。

依据：[质量上下文.md](../领域模型/制造资源服务/领域建模/质量上下文.md) §0/§3.3/§3.4/§6（INV-CX-04）、[质量上下文事件风暴](../领域模型/制造资源服务/事件风暴/质量上下文.md) §2.4/§2.5。

### 2.5 高可靠 · 物料消耗最终一致 + 负库存 + 齐套预占（物料上下文）

> 物料上下文是"配置型主数据 + 库存事实源"混合，库存进出是中频写入。怎么让物料扣减不逼出分布式事务、不在过点卡死--这是高可靠 + 解耦的亮点。

**核心机制**：
- **物料消耗最终一致（INV-CX-04）**：物料扣减**不在过点主事务内**。过点执行上下文发布 `CheckpointReleased`（过点放行），物料上下文消费后按 BOM **异步扣减**，秒级延迟。过点放行不阻塞等扣减--过点防错读的是"扣减前的库存快照"（可能略滞后），但过点主事务不被跨服务阻塞。
- **允许负库存但告警（INV-13）**：若过点放行时本上下文库存已不足（消耗延迟导致超扣），**允许 `available_qty` 为负并告警**，由物控人工补料 / 盘点。**禁止扣减会逼出跨服务事务回滚过点**，违反零分布式事务原则--这是刻意的可用性取舍。
- **齐套预占三招**：① 按 `location` 锁定到具体线边仓（避免跨仓挪用）；② 预占锁 `locked_qty`、可用是 `available_qty`，两套量分离；③ 过点消耗时**直接扣 `locked_qty`**（预占即已锁定），不走"先释放再扣减"的中间态。
- **多层幂等**：消耗按 `(sn, work_order_id, source_event_id)` 去重（BIZ-04）；预占按 `(work_order_id, part_no, location)` 不重复创建（BIZ-05）；库存变更按 `source_event_id` 去重且无变化不发布（BIZ-03）。
- **消耗规则 `consumption_rule`**：`per_unit` / `per_panel`（拼板按板扣减，不逐 SN）/ `per_batch` / `proportional`（辅料按量）--覆盖 PCBA 拼板、辅料损耗等复杂消耗场景。

**为什么是亮点**：物料扣减是 MES 里最容易逼出分布式事务的地方（过点放行一件 -> 跨服务扣库存）。这里用"最终一致 + 允许负库存 + 多层幂等"把过点主事务彻底解放，又用预占三招保证齐套判定的准确性。

依据：[物料上下文.md](../领域模型/制造资源服务/领域建模/物料上下文.md) §1.6/§1.7/§3.3/§3.4/§6（INV-13、BIZ-03/04/05、INV-CX-04）、[领域总览.md](../领域模型/领域总览.md) §5.3。

### 2.6 建模深度 · 三段式不变式 + 同构状态机 + 聚合根纯洁

> 不直接是"高并发 / 高可用"，但这是**设计能力**的硬证据，被追问"DDD 怎么落的"时拿得出手。

**核心机制**：
- **三段式不变式编号**：把"必须始终为真"的约束按一致性边界分三段，分别编号、不可混列--
  - `INV-XX`（聚合不变式）：落在单一聚合内，事务内强一致，由聚合根前置条件 / 状态机守护。
  - `BIZ-XX`（业务不变式）：本上下文内跨聚合 / 跨实例，最终一致，由领域服务 + 唯一索引 / 事件去重表守护，**禁止挂在聚合根上**。
  - `INV-CX`（跨上下文不变式）：跨限界上下文，最终一致，由事件订阅 + ACL 守护。
  - 制造资源服务共 **45 条**（工艺 12 + 物料 17 + 质量 16）。
- **每个领域服务必答"为什么不放在聚合根内"**：跨聚合编排、跨实例唯一性、跨服务集成才上领域服务。如 `RouteActivationService` 管"唯一 ACTIVE 版本"是因为单条 `RouteVersion` 无权查同 route 其它版本实例。
- **3 套同构状态机**：工艺路线 / BOM / 质量门禁规则的版本生命周期完全同构（`DRAFT->SUBMITTED->ACTIVATED->DEPRECATED->ARCHIVED`），便于跨上下文对齐审核 SLA 与权限模型。
- **聚合根纯洁**：聚合根只表达业务状态 / 行为 / 不变式 / 领域事件，**不依赖 Spring / MQ / HTTP**；应用服务只做编排和事务边界，不含业务逻辑。
- **引用而非复制 + ACL**：上下文外引用（`ProductId` / `QualityGateRuleId` / `FixtureMatchingRuleId`）经防腐层翻译，本上下文不持有其聚合。

依据：[工艺管理上下文.md](../领域模型/制造资源服务/领域建模/工艺管理上下文.md) §6、[物料上下文.md](../领域模型/制造资源服务/领域建模/物料上下文.md) §6、[质量上下文.md](../领域模型/制造资源服务/领域建模/质量上下文.md) §6。

### 卡片 C：业务能力（讲覆盖，不给百分比）

| 能力 | 表述 |
|------|------|
| 追溯 | 不可变版本 + 过点锁版本快照，工艺 / BOM / 规则变更不撕裂在制品，历史永久可回放 |
| 防错 | 步骤多维绑定（物料 / 工装 / 设备准入 / 首件门禁 / 前置工序 / 实时数据），过点综合各缓存执行 |
| 实时 | 同步门禁（快、权威）+ 异步判定（深、记录性）分治，过点不被深度判定拖慢 |
| 异常识别 | 准实时流式累积缺陷频次，单件偶发 vs 批量系统性自动判定，保守不漏检 |
| 物料 | 齐套预占按线边仓锁定 + 多层幂等消耗，过点不被跨服务扣减阻塞 |

## 4. 追问防守 Q&A

**Q：制造资源服务就是个配置 CRUD，有什么技术含量？**
A：CRUD 是表象，技术含量在**怎么让配置不拖垮现场过点**。过点要 ≤200ms，而工艺路线 / BOM / 质量门禁全在这里。三件事：① 不可变版本 + 过点锁快照，工艺变更不撕裂在制品；② 本地缓存 + ≤500ms 降级，配置查询不进过点主事务；③ Outbox + 零分布式事务，版本生效事件崩溃零丢失。质量上下文还做了同步门禁 vs 异步判定分治。这是"配置基座如何支撑实时执行"的架构能力，不是 CRUD。

**Q：工艺变更时线上在制的板子按新工艺还是旧工艺？**
A：按**它首次过点锁定的版本**走完，新版本只对"变更后首次过点"的单件生效（INV-CX-01）。因为版本生效后不可变（INV-04），过点记录绑的 `route_version` 是不可变快照，工艺后续怎么改都不影响已过点记录和在制品。历史追溯按当时版本永久回放。三个上下文（工艺 / BOM / 质量规则）是同一条不变式。

**Q：降级查询 ≤500ms 不还是慢吗？怎么保证过点 200ms？**
A：≤500ms 是**兜底路径**，不是主路径。配置型主数据写少读多，版本生效是低频事件，过点执行上下文订阅生效事件维护本地缓存，命中缓存就是本地内存查询--这才是主路径。只有缓存未命中（冷启动 / 版本刚切换）才降级 REST 查读模型。而且降级查询不进过点主事务（INV-CX-05），失败不产生半成品状态，过点主链不被它阻塞。两者解耦，配置查询的延迟波动传不到过点。

**Q：Outbox 比 直接发 Kafka 好在哪？制造资源服务为什么适合用？**
A：Outbox 解决"DB commit 成功但 Kafka 没发出去"的崩溃窗口--版本状态变更和 outbox 事件写同一本地事务，要么一起成功要么一起回滚。代价是多一次 DB 写、有异步延迟，所以只适合低频业务契约事件。制造资源服务全是配置发布（工艺 / BOM / 规则生效），频率低、契约性强，正是 Outbox 理想场景。高频原始采集数据不走 Outbox（那是设备管理服务的事）。

**Q：唯一 ACTIVE 版本怎么保证不出现两个同时生效？**
A：双保险（BIZ-02）：领域服务 `RouteActivationService` 生效时查读模型看同 `(route_id, route_type)` 有没有现存 ACTIVATED，**同时**数据库上有唯一索引 `(route_id, route_type, status=ACTIVATED)`。新版本生效时**同事务自动弃用旧版本**（发 `ProcessRouteDeprecated`，superseded_by 指向新版本）。聚合根自身无权查其它版本实例，所以这归领域服务 + 唯一索引，不挂聚合根。

**Q：质量判定为 BLOCK 时过点已经放行了怎么办？**
A：这是同步门禁和异步判定的时序问题，立场是**过点同步门禁为权威**（INV-CX-04）。异步 BLOCK 判定不回溯拦截已放行的过点--那样要回滚过点主事务，破坏零分布式事务。而是把这条 BLOCK 记入缺陷统计，供准实时流式的批量异常分析累积；如果累积到 `BATCH_SYSTEMIC`，发 `BatchQualityAnomalyDetected` 信号触发批量返工工单。单件偶发的走过点拦截分流单件返修。快和深分治，时序矛盾用"不回溯 + 后续兜底"化解。

**Q：物料扣减不在过点事务里，库存不准怎么办？**
A：物料消耗是**最终一致**，秒级延迟，过点防错读的是扣减前的库存快照。如果延迟导致超扣，**允许 `available_qty` 为负但告警**（INV-13），物控人工补料 / 盘点。为什么不禁止扣减？因为禁止扣减就得跨服务回滚过点，逼出分布式事务，违反过点主事务零分布式事务原则。这是刻意的可用性取舍--过点不能因为物料延迟而卡死。准确性靠齐套预占（派工时按线边仓锁定 `locked_qty`）在开工前保证，过点消耗直接扣 `locked_qty`。

**Q：批量异常检测是实时的还是批量的？**
A：**准实时流式**--每条 `QualityVerdict` 到达即按 `(work_order_id, station_id, defect_code)` 增量累积缺陷频次 + 阈值判定，不是周期批量。这样批量异常能及时识别。判定立场是**保守**--倾向于判 `BATCH_SYSTEMIC`，宁可多返工不可漏检系统性缺陷，再由质量工程师定期复核调优阈值。流式压力大时可退化为分钟级窗口批量。

**Q：三个上下文为什么不合一个？**
A：关注点、生命周期、干系人都不同。工艺管理是"工序怎么排、版本怎么发"（工艺工程师），物料是"物料是什么、BOM 怎么配、库存多少"（物控 / 采购），质量是"检验标准、缺陷分类、门禁规则、TestResult 业务语义"（质量工程师）。混在一起，改一条质量门禁规则会动到工艺路线版本代码。但三者又都是配置型主数据，所以共用同一套版本模型（同构状态机 + 同构不变式 INV-CX-01/02），解耦即可协作，不必合并。

**Q：三段式不变式（INV / BIZ / INV-CX）有必要分这么细吗？**
A：有必要，因为**守护机制不同**。`INV` 落在单一聚合内，事务内强一致，聚合根前置条件就能保证；`BIZ` 跨聚合 / 跨实例（如唯一 ACTIVE 版本），单事务守不住，要领域服务 + 唯一索引 + 事件去重表，**禁止挂聚合根**（否则聚合根要查别的实例，破坏一致性边界）；`INV-CX` 跨上下文，要事件订阅 + ACL。混在一起就会把"该用唯一索引保证的"误写成"聚合根前置条件"，看着对、实则守不住。分三段是让守护机制和约束边界对齐。

## 5. 真实部署补强：从"设计正确"到"线上扛得住"

> 被追问"这套设计上线还要补什么"时用。制造资源服务自己的写入不高频，真实车间 HA/HR/HC 压力几乎全来自**消费侧峰值读取 + 对共享事实的并发争夺**。下面场景区分"设计已覆盖"与"真实部署需补强"两类--讲的时候分清，**别把 gap 说成已实现**。

### 5.1 高并发（基座被峰值读取 / 争夺）

| 场景 | 真实触发 | 当前设计 | 真实部署需补强 |
|------|---------|---------|--------------|
| 换线 / 班次启动缓存雪崩 | 早班开机、午餐复工、集中换线，所有工位同时起过点，本地缓存未预热，集中降级查询 | 降级 ≤500ms 是**单次** SLA | 启动**批量预热**（一把加载 ACTIVE 路线/BOM/规则）、降级**限流+熔断**、多级缓存（进程内+Redis）。文档 gap |
| ECN 批量版本发布风暴 | 工程变更日 / NPI，一次性生效几十上百个版本 | `RouteActivationService` 是**单版本**编排 | outbox **限速**、下游刷新按 `(route_id,version)` 去重合并、读模型批量加载。文档 gap |
| 齐套预占并发争夺 | 多工单混线 / 紧急插单，同时预占同 `part_no×location` | BIZ-05 唯一索引+去重 | 热门物料**库存分桶**（按批次/库位细分）、预占失败部分开工、退避重试。热点分桶 gap |
| 高节拍消耗吞吐 | SMT 高速线每秒过板，`CheckpointReleased` 密集 | `per_panel` 聚合+幂等+"无变化不发布" | 再加**事件合并窗口**（如 200ms 内多次变更合并一条）。已部分覆盖 |

### 5.2 高可用（基座故障 / 不一致时过点能否继续）

| 场景 | 真实触发 | 当前设计 | 真实部署需补强 |
|------|---------|---------|--------------|
| 服务宕机的过点生存 | 滚动发布、MySQL/Redis 故障、网络分区 | 本地缓存命中即继续过点 | 明确**降级失败语义**：非强防错维度（工艺路线详情）放行+告警，强防错维度（质量门禁）拦截；缓存足够 TTL/容量。语义 gap |
| 缓存与源头版本不一致窗口 | 工艺/规则刚切换瞬间，缓存还没收到生效事件 | INV-CX-01 保证变更只影响新过点 | 缓存带 `version`+短 TTL，**主动失效**而非等过期。已部分覆盖 |
| 投影延迟下的齐套一致性 | 实时改 BOM/库存，KitStatus 重算滞后 | 派工齐套走**强一致**预占（直接锁 `locked_qty`，不走投影） | 展示层 `missing_items` 若读投影要标"实时性"。强一致路径已覆盖 |

### 5.3 高可靠（事实变更准确性 + 端到端一致）

| 场景 | 真实触发 | 当前设计 | 真实部署需补强 |
|------|---------|---------|--------------|
| 版本生效原子性 / 并发生效竞争 | 两工程师同时生效同 route；生效中途崩溃 | BIZ-02 唯一 ACTIVE 双保险 + INV-CX-02 outbox 同事务 + 同事务弃旧版本。**已扎实覆盖** | 验证唯一索引部分索引 + outbox 崩溃恢复（PUBLISHING 锁超时） |
| 跨服务事件端到端一致 | Kafka rebalance、消费者崩溃、补传乱序 | outbox 至少一次 + `source_event_id` 幂等 + 乱序窗口。**已扎实覆盖** | 验证幂等表与业务表同事务边界 + 手动 ack 崩溃恢复 |
| 拼板 / 辅料按量扣减准确性 | SMT 拼板多 SN、锡膏/红胶按实际用量 | `consumption_rule`(per_unit/per_panel/per_batch/proportional) 已建模 | **proportional 用量数据链路**：接设备数据接入按周期/事件聚合；per_panel 要拼板配置随工单。用量链路 gap |
| 批量异常检测漏检 / 误报权衡 | 新缺陷模式阈值未覆盖；阈值过低吃产能 | 保守判定 + 人工复核已表态 | 保守判定加**返工成本上限刹车**（超阈值转人工）；阈值调优 SPC 数据回流。代价控制 gap |
| 替代料启用齐套重算风暴 | 供应链突变，主料缺货启用替代料 | 发 `material.substitute.lifecycle` 驱动重算 | **增量重算**（只重算引用该 part_no 的在制工单）+ 限流。重算限流 gap |

### 5.4 一句话小结

当前设计把**正确性骨架**（版本一致性、消息可靠性、幂等）做得很扎实--这是最难的部分；真实上线主要补**峰值与故障下的韧性**（预热、限流、熔断、热点分桶、降级失败语义）。**讲法纪律**：已覆盖的讲机制，gap 要说"真实部署需补强 / 这是上线前要验证的"，**别说成已实现**。

## 6. 红线：这些数字不能编

- ❌ "缓存命中 99.9%"--除非有真实监控数据。
- ❌ "Outbox 零丢消息线上验证过"--除非真上线压测过。这是设计阶段项目，没上线就是没上线。
- ❌ "批量异常识别准确率 X%"--除非有真实 SPC 复核数据。
- ❌ "物料扣减延迟 < 1s 实测"--除非有线上埋点。

**高可用 / 高可靠数字的正确讲法**：
- ✅ "降级查询 SLA **设计目标** ≤500ms，过点 P99 **设计目标** ≤200ms，配置型主数据写少读多，缓存命中是主路径，降级是兜底。" -- 标"设计目标"。
- ✅ "Outbox 保证版本生效事件与状态变更同库事务，**设计上**崩溃窗口零丢失，消费端幂等。" -- 讲机制 + "设计上"。
- ❌ "我们系统缓存命中 99.9%、零丢消息。" -- 没口径没实测，一问就穿。

被问到"上线跑过吗"时，老实说："这是设计阶段的架构方案，重点是**识别出配置基座与实时过点的矛盾，用缓存降级 + 不可变版本 + Outbox 解掉**，业务效果需要在真实车间上线后用 SPC 数据验证。"--**诚实 + 体现架构判断力，比硬吹数字得分高**。

## 7. 一句话定位（收尾用）

"制造资源服务的价值不在于配置 CRUD，而在于**把一套'写少读多'的配置基座，用不可变版本 + 过点锁快照 + 本地缓存降级 + Outbox 可靠消息，做成了既能保证全链路追溯、又不拖垮 ≤200ms 现场过点的实时执行基座**--配置稳，执行才能快。"
