# 后台任务异常静默丢失修复 · 面试闪光点与话术（异步错误可见性 / 观测旁路"吞而不静默" / 崩溃兜底防孤儿）

> **定位**：本文是对 factorybot（MES Agent 服务）一条 **P0 运行时正确性缺陷**的面试纵深展开。与"多租户越权"那轮安全修复不同，这次是**异步错误处理的盲区**：`asyncio.create_task` 点火的后台任务，其内部异常只存在 task 对象上、从未被读取，GC 时仅打印一句 `'Task exception was never retrieved'`，生产"瞎飞"。守口径纪律：做了什么如实讲（两处 done-callback 兜底 + 崩溃尽力 mark_failed + 死代码现代化），不确定的决策点交还用户拍板（崩溃恢复范围 / loop 检测改法），残留项诚实交代（mark_failed 自身可失败、real 集成未测、孤儿回收未做）。
>
> **核心矛盾**：一套 try/except 工整、DDD 分层的服务，后台任务异常却"看不见"。`create_task` 后的 `except` 只捕获"创建任务"本身的异常，捕不到任务体里抛的异常；`add_done_callback` 只用来清理 `_active_tasks` 字典，从不取 `t.exception()`。两个判断贯穿全文：**"吞" ≠ "静默"（观测旁路要不反噬但要可见）**、**兜底链自身不能再次静默丢失**。

## 1. 30 秒电梯陈述

"我在 MES Agent 服务里修了一个 P0：后台任务异常静默丢失。`create_task` 点火的两个后台任务--观测侧落 LLM 调用日志、编排侧驱动会话--内部异常只存在 task 对象上从不被读取，GC 时只打一句 'Task exception was never retrieved'，生产完全瞎飞。原因是 `create_task` 后的 except 只捕创建本身异常，`add_done_callback` 只清理字典不取 `t.exception()`。我的处理分三块：一是观测侧给 task 挂 done-callback，异常取出来记 ERROR--观测的不变量是'不反噬业务'，但'吞'不等于'静默'，传播可以吞、可见性不能丢；二是编排侧 `_drive` 崩溃后 done-callback 记 CRITICAL 并尽力 mark_failed 把会话转 FAILED，避免崩溃后卡 RUNNING 成为孤儿（运维轮询会一直等）；三是兜底链自身防再次静默--finalize 再失败仅记日志不再传播，且用集合持有 task 引用防 GC 提前回收。顺手把 `get_event_loop()`（3.12 弃用）改 `get_running_loop()` 并删掉一条死代码 run_until_complete 分支。两个不确定的决策--崩溃恢复到哪一步、loop 检测怎么改--我列了选项交还用户拍板。测试 62 到 65。残留我诚实交代：mark_failed 自身也可能失败、real 模式落库没集成验证、Pod 重启的孤儿回收没做。"

**三个抓手**：异常 "never retrieved" 盲区识别 / 观测"吞而不静默" / 崩溃兜底防孤儿。

## 2. 闪光点详解（按主线）

### A. 异步错误处理的盲区（"never retrieved" 识别）

#### A.1 create_task 的 except 捕不到任务体异常

**识别过程**：代码审查时看 [orchestration_service.py](../factorybot/app/application/orchestration_service.py) 的 `start()`：`task = asyncio.create_task(self._drive(...))` 后面紧跟 `task.add_done_callback(lambda t: self._active_tasks.pop(...))`。乍看有 try/except、有 done-callback，很完备。但两个细节：

- **done-callback 只 pop 不取异常**：lambda 拿到 task 只做 `_active_tasks.pop`，从不调 `t.exception()`。task 体抛的异常存在 task 对象上，没人取 -> asyncio 在 GC 时打印 `Task exception was never retrieved`，**仅 stderr 一行 warning，无结构化日志、无 session 上下文**。
- **_drive 的 try/except 有逃逸路径**：`_drive` 确实用 `except Exception as e: await self._repo.mark_failed(...)` 兜了 `graph.ainvoke`，但有四类异常逃得出 try：① `graph = self._graphs[scenario.value]` 在 try **之前**，graph 未注册抛 `KeyError`；② except handler 里 `mark_failed` 自身失败（DB down）；③ `_after_invoke` 里 `dispatcher.push` / `update_status` / `mark_done` 无 try 保护；④ `CancelledError`。

观测侧 [observability.py](../factorybot/app/infrastructure/obs/observability.py) 的 `_safe_async` 同病：`loop.create_task(fn(...))` fire-and-forget，外层 `except Exception: pass` 只捕"创建任务"的异常（如无运行循环），**捕不到 task 体里 `LlmCallLogger.log` 写失败的异常**。

**为什么是亮点**：这是"同步思维写异步代码"的典型盲区。同步代码里 `try/except` 包住调用就能兜异常；但 `create_task` 是"点火即走"，task 体在**另一个事件循环轮次**执行，外层 try/except 早就退出了，根本包不住。多数人看到 `create_task` 外面有 try 就以为兜住了，其实那个 try 只在"创建 task 对象"那一瞬间有效。**识别出"create_task 的 try 是假的兜底、done-callback 才是真兜底"**，体现的是对 asyncio 错误传播模型的理解，不是堆 try/except 的本能反应。面试官问"你怎么发现的"，答"我看 done-callback 干了什么--只 pop 不取 exception，就知道 task 体异常没人管；再追 `_drive` 的 try 边界，发现 graph 查找在 try 之外、_after_invoke 没保护，逃逸路径很多"。

**防守话术**："create_task 是点火即走，task 体在另一个轮次跑，外层 try 早就退出了包不住。那个 except 只捕'创建 task'瞬间的异常，比如没有运行循环。真正能兜 task 体异常的是 done-callback 里取 t.exception()。原来的 lambda 只 pop 字典不取异常，所以 task 体一抛就 'never retrieved' 静默丢失。"

### B. 观测旁路：吞 ≠ 静默（不反噬但要可见）

#### B.1 "不反噬业务"不等于"异常不可见"

**问题**：`Observability` 的类注释写死"观测是只读旁路，内部异常一律吞掉"。这个不变量是对的--观测挂了不能把业务调用也带挂。但原来的实现把"吞"做成了"静默"：`_safe` 和 `_safe_async` 都是 `except Exception: pass`，异常连日志都不记。

**处理**：`_safe_async` 改成--传播仍然吞（done-callback 里不 raise，业务无感），但 task 体异常取出来记 **ERROR** 日志（含 fn 名、error repr、error_type）。`_safe`（同步路径）保持原样 `pass`，因为同步埋点异常本来就同步可见、调用方能感知；异步 fire-and-forget 才是"无人可见"的重灾区。

**为什么是亮点**：区分了两个被混为一谈的概念--**"不反噬"（不向调用方传播）和"不可见"（不留任何痕迹）**。观测旁路要前者不要后者：LLM 调用日志写失败不该让诊断 Agent 跟着挂（不反噬），但必须让运维知道"观测数据在丢"（可见），否则就是"瞎飞"--观测系统挂了自己都不知道，等于没有观测。原来 `except: pass` 把两者打包成了"什么都不做"。改成"吞传播 + 记日志"后，观测的健壮性不变量（不反噬）保住，可见性补回。面试官问"观测不是该吞异常吗"，答"吞的是传播不是可见性--不让观测拖垮业务，但观测自己出问题得让人看见，否则观测挂了静悄悄等于没有"。

**防守话术**："观测旁路的不变量是'不反噬业务'，不是'异常不可见'。原来 except pass 把传播和可见性一起吞了，LlmCallLog 写失败谁都不知道。我改成 done-callback 里取异常记 ERROR，传播还是吞（不 raise，业务无感），但异常可见了。观测挂了自己得让人知道，不然等于没观测。"

### C. 崩溃兜底防孤儿会话（done-callback + mark_failed）

#### C.1 _drive 崩溃后会话卡 RUNNING 成孤儿

**问题**：`_drive` 在 `start()` 里 `create_task` 点火后，HTTP 立即返回 session_id。如果 `_drive` 因逃逸路径（A.1 列的四类）崩溃，task 静默死掉，但会话状态留在 `RUNNING`（`start()` 里 `update_status(session_id, "RUNNING", "PLAN")` 设的）。后果：运维侧的 `_wait_pending` 轮询会一直等"pending gate 或会话结束"，但会话既没 pending、也没转 DONE/FAILED，**卡在 RUNNING 永远等不到**--一个看起来活着、实际已经死的孤儿会话。

**处理**（决策点 1，用户拍板"记 CRITICAL + 尽力 mark_failed"）：`_on_drive_done(session_id)` 返回的 done-callback 做三件事--① `pop` 清理 `_active_tasks`；② `task.exception()` 非空时记 **CRITICAL**（含 session_id、error、error_type）；③ 调度 `_finalize_crashed_session` 尽力 `mark_failed(session_id, "驱动任务崩溃: {exc}")` 把会话转 FAILED。CRITICAL 是因为"编排会话死了"是业务级故障；转 FAILED 让孤儿会话状态正确，`_wait_pending` 能立即识别结束。

**为什么是亮点**：体现了**最后防线 + 状态自愈**思维。`_drive` 自己的 try/except 是第一道防线（兜 graph.ainvoke 的常见异常），done-callback 是第二道（兜第一道漏掉的逃逸路径）。但光记日志不够--日志告诉人"会话死了"，会话状态却还是 RUNNING，运维系统按状态判断会以为它活着。**记日志是给人看的，转 FAILED 是给系统看的**。两者都做，人和系统都能正确感知。面试官问"为什么不只记日志"，答"日志让人知道，但 _wait_pending 按状态轮询，状态不转 FAILED 它就一直等，孤儿会话。mark_failed 让状态也正确，人和系统都兜住"。

**防守话术**："_drive 崩溃后会话卡 RUNNING 成孤儿，运维轮询一直等。done-callback 不只记 CRITICAL，还尽力 mark_failed 转 FAILED--日志给人看，状态给系统看，两个都兜。CRITICAL 因为编排会话死了是业务级故障。"

### D. 兜底链自身不能再次静默丢失

#### D.1 finalize 自身失败仅记日志不再传播

**问题**：done-callback 里调度的 `_finalize_crashed_session` 调 `mark_failed`，但 `mark_failed` 自己也可能失败（DB down、repo 异常）。如果它抛出来，这个 finalize task 又成了"never retrieved"的静默丢失--**兜底链自己重蹈覆辙**。

**处理**：`_finalize_crashed_session` 内部 `try/except` 包住 `mark_failed`，自身失败仅记 **ERROR**（`orchestration.finalize_crashed_session_failed`），不再传播。即：第一道兜底（done-callback 记 CRITICAL）已确保"人知道会话死了"；第二道兜底（finalize mark_failed）是"尽力转状态"，失败了也不破坏第一道的可见性。

#### D.2 _finalize_tasks 集合防 GC 提前回收

**问题**：done-callback 是同步函数（asyncio 调用），里面 `asyncio.create_task(self._finalize_crashed_session(...))` 创建的 task 如果不持有引用，可能被 GC 提前回收（CPython 文档明确警告"Save a reference to the result, to avoid a task disappearing mid-execution"）。

**处理**：`__init__` 加 `self._finalize_tasks: set[asyncio.Task]`，finalize task `add` 进集合，再 `add_done_callback(self._finalize_tasks.discard)` 完成后移除。持有引用防 GC，完成后自动清理不泄漏。

**为什么是亮点**：两处都体现**"兜底要可靠，否则兜底本身就是新漏洞"**。很多人加 done-callback 记日志就收工，没想"兜底里调的异步操作会不会又静默丢失""创建的 task 会不会被 GC"。这里把兜底链当成需要自证可靠的一等公民：finalize 自己 try/except（防再次 never retrieved）+ 集合持引用（防 GC 中断）。面试官问"你的兜底靠谱吗"，答"兜底链自身也防静默丢失--finalize 再失败记 ERROR 不传播，task 引用用集合持有防 GC，不会兜底自己又瞎飞"。

**防守话术**："兜底链自己也得防静默丢失。finalize 调 mark_failed 可能再失败，我里面 try/except 记 ERROR 不传播，不让它又 never retrieved。还有 done-callback 是同步的，里面 create_task 不持引用会被 GC 回收，我用 _finalize_tasks 集合持有、完成后 discard。兜底不可靠就是新漏洞。"

### E. 顺手识别死代码 + 现代化（get_event_loop 弃用）

#### E.1 run_until_complete 分支是死代码

**识别**：`_safe_async` 原来是 `loop = asyncio.get_event_loop(); if loop.is_running(): create_task else: run_until_complete`。我 grep 全仓调用方，`_safe_async` 唯一被 `llm_called` 调用，而 `llm_called` 只在 `ObservableChatModel.ainvoke` / `ainvoke_structured` 两个 `async def` 里调--**永远在运行循环内**，`else: run_until_complete` 分支根本走不到（而且在运行循环里调 run_until_complete 会直接抛 RuntimeError）。是死代码。

**处理**（决策点 2，用户拍板"改 get_running_loop + 删死分支"）：改用 `asyncio.get_running_loop()`（3.12 下 `get_event_loop()` 无运行循环时已弃用），无运行循环时记 `obs.safe_async.no_running_loop` warning 后跳过（防御性兜底，当前无 sync 调用方）。删除 `run_until_complete` 死分支。

**为什么是亮点**：**改 bug 时顺手清死代码 + 现代化 API**，但不越界。`get_event_loop()` 在 3.12 弃用、`run_until_complete` 分支是死代码，这是顺手能修的；但没去动 `_safe`（同步路径）的 `except pass`--那个是有意设计（同步埋点异常调用方能感知），不属于这次"异步静默丢失"的范围。**改动的边界跟问题边界对齐**，不顺手重构无关代码（与"去重不夹带行为变更"同构的纪律）。面试官问"为什么顺带改 get_event_loop"，答"它 3.12 弃用且那个 else 分支是死代码，我核实了唯一调用方永远在 async 内，删了不影响行为还消了弃用告警；但没动 _safe 的 pass，那是有意设计不在这次范围"。

**防守话术**："get_event_loop 3.12 弃用，run_until_complete 分支我 grep 过唯一调用方 llm_called 只在 async 里跑，是死代码。改 get_running_loop、删死分支、无循环时记 warning 跳过。顺手现代化但不越界--_safe 的 except pass 是有意设计没动，那不在'异步静默丢失'范围。"

### F. 诚实：不确定的决策交还用户拍板

**两个决策点**：修之前我没自行假设，而是把选项和权衡列给用户：

**防守话术**："两个决策我没自己拍：崩溃恢复是只记日志还是加 mark_failed 防孤儿、loop 检测是现代化删死代码还是保留只补回调，都有取舍。我列选项和权衡交还用户，用户选了我执行。不确定的不假设，让用户定。"

## 3. 核心应答话术（高频问题，口语化背熟）

### 话术 1：你这次最核心的发现是什么

"最核心是**识别 create_task 的异常盲区**。两个后台任务--观测侧落 LLM 日志、编排侧驱动会话--都是 create_task 点火即走，task 体异常只存在 task 对象上没人取，GC 时打一句 'never retrieved' 就没了，生产瞎飞。原因是 create_task 后的 except 只捕'创建'那一瞬，task 体在另一个轮次跑包不住；done-callback 只 pop 字典不取 exception。我给两处都挂了 done-callback 取异常记日志--观测侧记 ERROR（吞传播但不静默），编排侧记 CRITICAL 还尽力 mark_failed 防孤儿。**create_task 的 try 是假兜底，done-callback 才是真兜底**--这是最大的判断。"

### 话术 2：观测不是该吞异常吗，你怎么又记日志

"吞的是传播不是可见性。观测的不变量是'不反噬业务'--LlmCallLog 写失败不能让诊断 Agent 跟着挂。但原来 except pass 把传播和可见性一起吞了，观测挂了谁都不知道，等于没观测。我改成 done-callback 取异常记 ERROR，传播还是吞（不 raise，业务无感），但异常可见了。**不反噬不等于不可见**，观测自己出问题得让人看见。"

### 话术 3：编排侧为什么不只记日志还要 mark_failed

"日志给人看，状态给系统看。_drive 崩溃后会话卡 RUNNING 成孤儿，运维的 _wait_pending 按状态轮询，状态不转 FAILED 它就一直等，永远等不到。done-callback 记 CRITICAL 让人知道'会话死了'，再 mark_failed 转 FAILED 让系统也知道。两个都兜，人和系统都能正确感知。CRITICAL 是因为编排会话死了是业务级故障。"

### 话术 4：兜底的 mark_failed 自己失败怎么办

"兜底链自身也防静默丢失。finalize 调 mark_failed 可能再失败，我里面 try/except 记 ERROR 不传播，不让它又 never retrieved。而且第一道兜底（done-callback 记 CRITICAL）已经保证'人知道会话死了'，第二道（finalize mark_failed）是尽力转状态，失败也不破坏第一道的可见性。还有 done-callback 是同步的，里面 create_task 不持引用会被 GC 回收，我用 _finalize_tasks 集合持有、完成后 discard。**兜底不可靠就是新漏洞**。"

### 话术 5：get_event_loop 为什么顺带改了

"它 3.12 弃用，而且那个 else run_until_complete 分支我 grep 过--_safe_async 唯一调用方 llm_called 只在 async def 里跑，永远在运行循环内，else 分支走不到，是死代码。改 get_running_loop、删死分支、无循环时记 warning 跳过。顺手现代化但不越界--_safe 的 except pass 是有意设计（同步埋点异常调用方能感知），不在'异步静默丢失'范围，没动。改动边界跟问题边界对齐。"

## 4. 深度问答（技术深挖）

**Q：done-callback 里调 t.exception() 会不会抛？**
A：不会。done-callback 只在 task 完成后由事件循环调用，此时 task 已 done，`exception()` 不会抛 `InvalidStateError`。唯一要处理的是 `cancelled()`--如果 task 被取消，`exception()` 会抛 `CancelledError`，所以先 `if task.cancelled(): return` 再取 exception。我两处都先判 cancelled。

**Q：done-callback 是同步的，里面 asyncio.create_task 怎么拿到循环？**
A：done-callback 由事件循环在循环线程上同步调用，此刻有运行循环，`asyncio.create_task` 内部 `get_running_loop()` 能拿到。所以 done-callback 里调度异步 finalize 是合法的。关键是持有的 task 引用不能丢（否则 GC），所以用 `_finalize_tasks` 集合持有 + 完成后 discard。

**Q：_drive 的 try/except 已经兜了 graph.ainvoke，为什么还逃逸？**
A：因为 try 的边界没覆盖全部。`graph = self._graphs[scenario.value]` 在 try **之前**（graph 未注册抛 KeyError 逃逸）；except handler 里 `mark_failed` 自身可能失败（逃逸）；try 之后的 `_after_invoke` 里 `dispatcher.push` / `update_status` / `mark_done` 没 try 保护（逃逸）。done-callback 是兜这些逃逸路径的第二道防线。我没把 graph 查找移进 try--那是可选的内部加固，done-callback 兜底已经覆盖，移不移进 try 是风格选择，我留给后续。

**Q：为什么不直接修 _drive 的 try 边界，而要靠 done-callback 兜底？**
A：两层都要，职责不同。`_drive` 的 try/except 是"知道可能出什么错、知道怎么优雅降级"（GraphRecursionError -> mark_failed"步数超限"、TimeoutError -> "整体超时"），它能给会话一个**精确的失败原因**。done-callback 是"不知道出什么错、只知道 task 死了"的**最后防线**，给的是"驱动任务崩溃: {exc}"这种兜底原因。前者精确后者兜底，互补。只靠 done-callback 会丢失"步数超限"这种精确语义；只靠 try 又兜不住逃逸路径。所以 try 给精确降级、done-callback 兜逃逸，两层各司其职。

**Q：mark_failed 尽力而为，失败了会话还是孤儿，这算修了吗？**
A：算"可见性修复 + 尽力自愈"，不算"绝对保证"。mark_failed 失败意味着 DB 都 down 了，这种情况下会话状态确实转不了 FAILED--但 done-callback 的 CRITICAL 日志已经让人知道"这个会话死了"，运维能介入。绝对的孤儿回收要靠**Pod 重启时扫 RUNNING 超时会话转 FAILED**这种独立机制，我没做（列了遗留）。这次修的是"异常不可见 + 典型崩溃会孤儿"，mark_failed 自身失败是极端情况，靠日志兜底。**诚实讲：修了 95% 的盲区，极端的 DB 全挂靠日志 + 后续孤儿回收**。

**Q：观测侧记 ERROR、编排侧记 CRITICAL，级别怎么定的？**
A：按"对业务的影响"定。观测侧是只读旁路，LlmCallLog 写失败业务不受影响，只是观测数据丢--ERROR（严重但非致命）。编排侧 `_drive` 崩溃意味着编排会话死了、用户工单卡住--CRITICAL（业务级故障）。structlog 的 filtering logger 是 INFO+，ERROR 和 CRITICAL 都会输出。级别区分让运维能按严重度分诊。

## 5. 压力追问（陷阱题，考诚实）

**Q：你说 done-callback 兜底防孤儿，但 mark_failed 自身可能失败，那会话还是孤儿，你这兜底不是白做了？**
A：没白做，做了两件事只成一件也算收益。done-callback 的 CRITICAL 日志是同步记的、不依赖 DB，**一定成**--人一定知道"会话死了"。mark_failed 转 FAILED 依赖 repo，可能失败--状态可能没转。所以是"可见性 100% 兜住、状态自愈尽力而为"。绝对的孤儿回收（扫 RUNNING 超时转 FAILED）是独立机制我没做，列了遗留。**诚实地讲：这次让崩溃不再静默，但没保证状态一定自愈，极端情况靠日志 + 后续孤儿回收**。比原来"完全瞎飞"强，不是完美。

**Q：_drive 的 graph 查找在 try 之外，你识别了却没移进去，是不是漏修了？**
A：没漏，是边界选择。graph 查找抛 KeyError 是"配置错误"（scenario 没注册对应 graph），不是运行时偶发故障--这种该让 done-callback 兜成 CRITICAL 暴露出来（运维看到"graph 未注册"去修配置），而不是 try 吞掉变成"步数超限"那种模糊降级。done-callback 已经兜住了它的可见性。移进 try 是另一种风格（吞 KeyError 也 mark_failed），但会掩盖配置错误。我选择让它走 done-callback 暴露，配置错误不该被优雅降级隐藏。**不是漏修，是让配置错误大声报出来**。

**Q：你改了 get_event_loop 删了 run_until_complete 分支，万一以后有 sync 调用方怎么办？**
A：当前没有 sync 调用方（grep 核实 llm_called 只在 async 内）。如果以后真有 sync 调用方，它会走到"无运行循环"分支，记 `obs.safe_async.no_running_loop` warning 后跳过--观测这次不记，但不会崩，且 warning 让开发者知道"你在 sync 上下文调了异步观测，没生效"。比原来 `run_until_complete`（在运行循环里会抛 RuntimeError、无循环会阻塞调用方）安全。真要支持 sync 调用方，正确做法是那个调用方自己 `asyncio.run` 包一层，不是让观测旁路去 `run_until_complete` 阻塞业务。**删死分支 + warning 兜底，比留一个会抛错的假兜底强**。

**Q：你两个决策都交还用户拍板，是不是自己没主见？**
A：不是没主见，是知边界。这两个决策我都有推荐（崩溃恢复推荐加 mark_failed 防孤儿、loop 检测推荐现代化删死代码），但它们有真实取舍--防孤儿多一层依赖、现代化有行为变化--影响的是用户的系统该长什么样，不是纯技术对错。把推荐 + 权衡摆给用户定，既尊重决策权，也避免我猜错用户意图后返工。**有推荐但不替用户拍板**，是"技术上有判断、责任上知边界"。用户选完我执行，决策有据可查。

**Q：测试只加了 3 个（62->65），覆盖够吗？**
A：覆盖了核心路径，但有边界没测，诚实交代。测了三个：观测侧 task 体异常被记 ERROR（不再 never retrieved）、观测侧无运行循环走 warning 兜底、编排侧 _drive 崩溃（清空 _graphs 触发 KeyError）记 CRITICAL + 转 FAILED。没测的：mark_failed 自身失败时 finalize 记 ERROR（这条路径靠 try/except 保护，逻辑简单但没显式断言）、real 模式落 MySQL 的崩溃恢复（mock 进程内验证，real 集成未测，列遗留）。3 个测试覆盖了"可见性"和"防孤儿"两个核心不变量，极端路径靠代码审查 + 遗留跟踪。**不吹覆盖全面，测了核心、标了未测**。
