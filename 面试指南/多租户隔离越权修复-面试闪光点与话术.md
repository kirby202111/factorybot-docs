# 多租户隔离越权修复 · 面试闪光点与话术（漏洞链识别 / 纵深防御 / 身份不可伪造）

> **定位**：本文是对 factorybot（MES Agent 服务）一轮**安全越权修复**的面试纵深展开。与"代码优化与重构"那轮不同，这次是**识别并堵一条多租户越权漏洞链**：任意调用方无需认证即可跨租户读编排状态、确认/驳回 gate、读草稿证据，还能伪造确认人身份。守口径纪律：做了什么如实讲（三端点隔离 + service 层归属校验 + 身份 header + 统一 404 + mismatch 日志 + real 模式强制），残留项诚实交代（动作卡投递 push 侧未修、real 强制依赖 is_mock 语义、scope 仍全权限）。
>
> **核心矛盾**：一套 DDD 分层、`start` 端点有 `tenant=Depends(tenant_from_headers)` 的服务，confirm / state / evidence 三个端点却都漏了；叠加 `ConfirmRequest.user_id` 默认 `"u_zhang"`，任意调用方既能跨租户读、又能伪造身份确认。这不是单点漏校验，是**一条链**。三个判断贯穿全文：**漏洞是链不是点、归属校验下沉到 service 做纵深防御、身份只能从可信源（header）取不能从请求体取**。

## 1. 30 秒电梯陈述

"我在 MES Agent 服务里发现并修复了一条多租户越权漏洞链。start 端点有租户注入，但 confirm / state / evidence 三个端点漏了，叠加 confirm 的 user_id 默认 'u_zhang' 可伪造，任意调用方无需认证就能跨租户读编排状态、确认或驳回 gate、读草稿证据，还能伪造确认人。我的处理是三层：一是三端点统一注入租户、身份 user_id 从 header 取不再走请求体；二是归属校验下沉到 service 层做纵深防御--resume / get_session / get_evidence 都比对 session / 草稿的归属租户，跨租户统一抛异常返 404 隐藏存在性，并记 warning 供安全审计；三是 real 模式强制身份 header，mock 保留回退。草稿原本没有归属字段，我在 DraftRepo 记 draft_id->tenant_id 映射而不是污染 Draft 领域模型。测试 56 到 62，含跨租户隔离回归。残留我诚实交代：动作卡投递侧的跨租户误投还没修、real 强制依赖 is_mock 语义只在全 real 时生效。"

## 2. 闪光点详解（按主线）

### A. 漏洞是链不是点（威胁建模能力）

#### A.1 不是"漏了个 tenant 参数"，是一条越权链

**识别过程**：代码审查时发现 `start` 端点有 `tenant=Depends(tenant_from_headers)`，但 [orchestration_router.py](../factorybot/app/api/orchestration_router.py) 的 `confirm_gate` / `get_state` 和 [draft_router.py](../factorybot/app/api/draft_router.py) 的 `draft_evidence` 三个端点都没有 tenant 依赖。单独看每个端点"漏了参数"像小问题，但叠在一起构成一条链：

- **越权读**：`get_state` 无 tenant，任意调用方拿 session_id 就能读任意租户的编排状态（scenario / status / current_step / suspend_reason）。
- **越权写 + 伪造身份**：`confirm_gate` 无 tenant + `ConfirmRequest.user_id` 默认 `"u_zhang"`，任意调用方既能确认 / 驳回任意租户的 gate，又能伪造确认人身份（token 里记的 user_id 是请求体传的，不是认证的）。
- **越权读证据**：`draft_evidence` 无 tenant，任意调用方拿 draft_id 就能读任意租户的草稿证据（subgraph_ref / trace_id）。

**为什么是亮点**：多数人看到"某端点缺参数"会当成单点补上 `Depends(tenant_from_headers)` 就完事。但**安全漏洞的价值在"链"**--读 + 写 + 伪造身份三个能力组合，才是真实攻击面。识别出"这不是三个独立小遗漏，是一条越权链"，并追到 `user_id` 默认值这个身份伪造点，体现的是**威胁建模思维**而非打补丁思维。面试官问"你怎么发现的"，答"我先看鉴权一致的端点（start / diagnose 都有 tenant），再核对所有写和读敏感数据的端点，发现 confirm / state / evidence 三个漏了，然后追 confirm 的 user_id 来源发现默认值可伪造"--这是系统性审查路径，不是运气好撞见的。

**防守话术**："这不是漏了一个参数，是一条链。start 有 tenant 但 confirm / state / evidence 没有，加上 confirm 的 user_id 走请求体还有默认值，组合起来任意调用方能跨租户读状态、确认 gate、读证据，还能伪造确认人。我按'鉴权一致的端点有哪些、不一致的有哪些、不一致的能做什么'这个路径审出来的，不是单看一个端点。"

### B. 归属校验下沉到 service（纵深防御）

#### B.1 为什么不只在 router 校验

**决策**：三个端点注入 tenant 后，归属校验放哪一层有两个选择：

- router 层校验：路由取到 session / draft 后比对 tenant，service 签名不变、测试不动。改动最小，但安全只靠边界。
- **service 层校验（选定）**：`resume` / `get_session` / `get_evidence` 收 `TenantContext`，内部比对 `session.tenant_context["tenant_id"]` / 草稿归属租户，跨租户抛 `ResourceAccessError`。同步改 2 个测试文件传 tenant。

**为什么是亮点**：**纵深防御**。router 是边界，但 service 是真正执行写 / 读的地方。如果只在 router 校验，未来新增一个调用 service 的入口（内部任务、admin 接口、消息消费）就会绕过校验。把归属校验放进 service，service 持有自己的不变量（"这个 session 只能被归属租户操作"），任何调用方都绕不过。这对应 DDD 里**聚合根守自己的不变量**--不依赖外部调用方"记得"校验。代价是要改测试，但测试本来就该传 tenant（之前没传是漏）。面试官问"为什么不只在路由校验省事"，答"路由校验是边界防御，service 校验是纵深防御；新增入口绕过路由校验时 service 仍兜底，安全不能只靠一层"。

**防守话术**："归属校验放 service 是纵深防御。router 是边界，但 service 是真正读写的地方。只在 router 校验，将来加个内部入口或消息消费调 service 就绕过了。放 service 让它持自己的不变量--session 只能被归属租户操作--任何调用方都绕不过。代价是改两个测试传 tenant，但那本来就该传。"

#### B.2 草稿没有归属字段，怎么校验（SRP 决策）

**问题**：session 侧已有归属数据（start 时存了 `tenant_context=tenant.model_dump()`），但 [Draft](../factorybot/app/domain/draft.py) 领域模型没有 tenant 字段，[DraftRepo](../factorybot/app/infrastructure/persistence/repos.py) 只按 draft_id 存。要校验 `get_evidence` 归属，得先知道草稿属于哪个租户。两个选择：

- 给 Draft 加 tenant_id 字段：实现直接，但污染了"不落库"的值对象，还会透出到 DraftResponse 输出 schema。
- **DraftRepo 维护映射（选定）**：`archive` 时在 repo 内并行记 `draft_id -> tenant_id`，`get_evidence` 据此校验。Draft 领域模型保持干净。

**为什么是亮点**：这是 **SRP + 领域模型纯净度**的取舍。Draft 是值对象（草稿不落业务库，只归档），给它加 tenant_id 是把基础设施关注点（归属校验）塞进领域模型。归属是"谁存的"这个存储事实，归 repo 管；Draft 本身表达"草稿内容"。把映射放 repo，Draft 保持纯净，DraftResponse 也不泄漏 tenant_id。面试官问"为什么不直接给 Draft 加字段省事"，答"Draft 是不落库的值对象，tenant_id 是存储归属不是领域属性，塞进去污染模型还透出 API；映射放 repo 是让存储关注点留在基础设施层"。

**防守话术**："Draft 是值对象，tenant_id 是'谁存的'这个存储事实，不是领域属性。给 Draft 加字段会污染模型还透到响应 schema。我在 DraftRepo.archive 时记 draft_id->tenant_id 映射，get_evidence 查映射校验，Draft 保持干净。归属是存储关注点，归 repo。"

### C. 身份只能从可信源取（user_id 移出 body）

#### C.1 ConfirmRequest.user_id 默认值的危害

**问题**：`ConfirmRequest.user_id: str = "u_zhang"`--请求体字段带默认值。危害双重：一是默认值让不传 user_id 的请求也能过（记成 u_zhang）；二是 user_id 从请求体来，调用方可任意伪造"谁确认的"。确认 token 里记的 user_id 是审计依据（谁放行了 gate），伪造它就破坏了审计链。

**处理**：把 `user_id` 从 `ConfirmRequest` 移除，router 改传 `tenant.user_id`（来自 `X-Tenant-User-Id` header）。身份只从可信的 header（经网关注入）取，禁止请求体传入。

**为什么是亮点**：**身份与授权数据只从可信源取**是安全基本功。请求体是用户可控的，把 user_id 放请求体等于让用户自己声明"我是谁"。header 的 `X-Tenant-User-Id` 在真实部署里由网关 / 鉴权中间件注入（用户改不了），才是可信源。默认值 `"u_zhang"` 更是雪上加霜--它让"忘了传"变成"默认以 u_zhang 身份操作"。移到 header 后，确认人身份不可伪造，审计链可信。

**防守话术**："user_id 在请求体还有默认值，调用方能伪造确认人，token 审计就不可信了。我把 user_id 移出 ConfirmRequest，router 用 tenant.user_id，它来自 X-Tenant-User-Id header。真实部署里 header 由网关注入用户改不了，是可信源。身份只能从可信源取，不能让用户自己声明。"

### D. 跨租户统一 404 + mismatch 日志（隐藏存在性 + 可观测）

#### D.1 为什么跨租户返 404 不返 403

**处理**：跨租户访问（session / draft 不属于当前租户）统一抛 `ResourceAccessError`，全局 handler 映射为 **404**，不是 403。

**为什么是亮点**：**多租户隔离要隐藏存在性**。返 403 等于告诉攻击者"这个 session_id 存在但你没权限"--攻击者能枚举 session_id 探测哪些存在。返 404 让"不存在"和"不属于你"不可区分，攻击者探测不到。这是多租户系统的标准实践（GitHub 私有仓库返 404 不返 403 同理）。`ResourceAccessError` 同时覆盖"真不存在"和"跨租户"，两者对外都是 404。

#### D.2 mismatch 记 warning，not-found 不记

**处理**：在 `get_session` / `get_evidence` 的**真实跨租户不匹配**处记 warning（含 resource id、owner_tenant、caller_tenant），供安全审计；not-found（真不存在）不记日志。

**为什么是亮点**：**安全事件要可观测，但要区分信号与噪音**。跨租户访问企图是安全信号（可能是攻击），值得记 warning 含双租户 id 供审计追溯。not-found 是良性 404（用户输错 id），记了是噪音。分开处理--mismatch 记、not-found 不记--让安全日志高信噪比。否则要么全记（噪音淹没攻击信号），要么全不记（攻击不可见）。

**防守话术**："跨租户返 404 不返 403，是隐藏存在性--返 403 等于告诉攻击者 id 存在，能枚举；404 让不存在和没权限不可区分。同时 mismatch 记 warning 含 owner 和 caller 租户供审计，not-found 不记避免噪音。安全要可观测但信号要干净。"

### E. real 模式强制 header（is_mock 双模式的边界）

#### E.1 mock 回退 vs real 强制

**问题**：`tenant_from_headers` 在 header 缺失时回退默认租户 `WS-A / u_zhang`（mock 模式便利）。但这意味着 real / prod 下无鉴权调用方也会被当 WS-A。

**处理**：抽纯函数 `resolve_tenant_context`（脱离 FastAPI Header 依赖，可单测）。real 模式（`is_mock=False`）强制 `X-Tenant-Id` + `X-Tenant-User-Id`，缺失返 400；mock 模式保留回退。workshop / line / role 缺失用空串，不泄漏 mock 默认值。

**为什么是亮点**：**模式分流 + 可测性**。mock 模式回退是 dev / test 便利（离线跑不用传 header），real 模式强制是安全要求。用 `is_mock` 分流兼顾两者。抽纯函数是因为 FastAPI 的 `Header()` 依赖直接调用会拿到 FieldInfo 对象而非 None，没法单测；抽出纯逻辑后 real 强制的 400 路径能用 4 个单测覆盖（mock 回退 / mock 用传入值 / real 拒缺身份 / real 用传入值且可选置空）。**安全控制要有测试**，否则改坏无感知。

#### E.2 诚实边界：is_mock 语义让强制仅在全 real 生效

**残留（主动交代）**：`is_mock = run_mode=="mock" or llm_provider=="mock"`，所以 real 强制只在"全 real"（run_mode=real 且 LLM 非 mock）时生效。一个"real 依赖 + mock LLM"的 staging 配置仍按 mock 处理（不强制 header）。这与代码库的模式模型一致（任何 mock 即视为非生产），但需知悉：staging 混合配置下 header 不强制。

**为什么讲这个**：这是**知边界**。强制 header 这条控制有生效前提（is_mock=False），不是无条件生效。讲清"什么时候生效、什么时候不生效"比吹"已强制鉴权"诚实得多。面试官追问"那 mock LLM 的 staging 怎么办"，答"要么 staging 也用 real LLM，要么单独加 run_mode 维度的强制开关--这是遗留，我标出来了"。

**防守话术**："real 模式强制身份 header，mock 回退。但 is_mock 是 run_mode 或 llm_provider 任一为 mock 即真，所以强制只在全 real 生效。real 依赖 + mock LLM 的 staging 仍按 mock 不强制--这与代码库模式模型一致，是已知边界，不是 bug。要更严可以加 run_mode 维度开关，我列遗留了。"

### F. 诚实遗留（动作卡投递 push 侧未修）

**残留**：修越权链时发现 `ActionCardDispatcher` 的 `assignee_user_id` 硬编码默认 `"u_zhang"`，`_resolve_assignee` 完全忽略 card，所有动作卡（含 WS-B 会话的 draft_payload）都投到 u_zhang 收件箱--这是 **push 侧的跨租户误投**，与 #1 的 read 侧越权不同域。我**没有顺手改**，而是单列 #32 跟踪（待拍板路由来源：ActionCard 加 assignee 字段 vs dispatcher 查 session）。

**为什么讲这个**：两个诚实点。一是**变更原子性**--#1 是 read / confirm 侧越权，push 侧误投是另一个问题，混在一起改会让 PR 难审查（与"去重不夹带行为变更"同构）。二是**知 scope**--push 侧修法涉及 ActionCard 加字段或 dispatcher 注入 repo，改动面大于 #1，需要拍板路由来源，不是顺手能定的。单列跟踪让问题可见、被单独处理，而不是悄悄混进来或漏掉。

**防守话术**："修 #1 时发现动作卡投递侧也有跨租户问题--assignee 硬编码 u_zhang，card 被忽略，WS-B 的卡投给 u_zhang。但那是 push 侧，和 #1 的 read 侧越权不同域，修法要拍板（ActionCard 加字段还是 dispatcher 查 repo），改动面更大。我没顺手改，单列 #32 跟踪。变更要原子，混进来 PR 难审查。"

"隐藏存在性。返 403 等于告诉攻击者这个 id 存在只是没权限，能枚举探测；404 让不存在和没权限不可区分，探测不到。多租户隔离的标准实践，GitHub 私有仓库也返 404。同时 mismatch 记 warning 含 owner 和 caller 租户供审计，not-found 不记避免噪音。安全要可观测但信号要干净。"

### 话术 5：real 模式强制 header 怎么做的，有什么边界

"抽了纯函数 resolve_tenant_context 可单测。real 模式强制 X-Tenant-Id 和 X-Tenant-User-Id 缺失返 400，mock 保留回退。边界是 is_mock 是 run_mode 或 llm_provider 任一 mock 即真，所以强制只在全 real 生效，real 依赖 + mock LLM 的 staging 仍按 mock 不强制。这与代码库模式模型一致，是已知边界不是 bug。要更严加 run_mode 开关，我列遗留了。"

## 4. 深度问答（技术深挖）

**Q：service 层校验和 router 层校验能不能都做？**
A：能，而且更稳。我这次在 service 层做了归属校验（resume / get_session / get_evidence 收 tenant），router 层注入 tenant 本身就是"边界校验"（real 模式无 header 直接 400）。两层不冲突--router 挡住无身份的请求，service 挡住有身份但跨租户的请求。纵深防御就是多层独立校验，任一层漏了另一层兜底。我没在 router 额外加归属比对，因为 service 已经做了，router 重复比对是冗余；router 的职责是"有没有身份"，service 的职责是"身份对不对资源"。

**Q：get_session 跨租户抛异常，但 not-found 返 None，为什么不统一？**
A：故意区分。not-found 返 None 是保留"fetch 语义"（内部调用如 pending_step 用 repo 裸取，service get_session 返 None 表示不存在），跨租户抛异常是安全控制。两者在 router 都映射 404（None -> HTTPException(404)，ResourceAccessError -> 全局 handler 404），对外一致。内部区分让 service 的 fetch 语义不被安全异常污染，测试也能区分"不存在"和"跨租户"两种情况。

**Q：DraftRepo 映射在 real 模式（SQLAlchemy）怎么落地？**
A：mock 模式是进程内 dict + 并行 dict 映射。real 模式 DraftRepo 换 SQLAlchemy 实现时，映射就是 draft 表加一列 tenant_id，archive 时写入，owner_tenant_id 查询就是 SELECT tenant_id。接口（archive / get / owner_tenant_id / get_evidence）不变，只是实现换。这也是把归属放 repo 而非 Draft 的好处--real 模式加列是存储层的事，Draft 领域模型不用动。当前 real DraftRepo 未实现是遗留（与 #17 ORM 未接通同源）。

**Q：为什么用全局 exception handler 而不是每个 router try/except？**
A：DRY + 一致性。三个端点（confirm / state / evidence）都会抛 ResourceAccessError，每个 try/except 重复且容易漏。全局 handler 注册一次，所有 ResourceAccessError 统一 404，新增端点只要 service 抛异常就自动 404，不用记得加 try/except。代价是 handler 看不到是哪个端点抛的，但安全上 404 响应本来就该统一（不泄漏端点信息）。

**Q：resolve_tenant_context 为什么抽成纯函数？**
A：可测性。FastAPI 的 `tenant_from_headers` 用 `Header(None)` 做默认值，直接调用拿到的 x_tenant_id 是 FieldInfo 对象不是 None，没法在单测里模拟"header 缺失"。抽纯函数后，real 强制的 400 逻辑能直接传 None 测，4 个单测覆盖 mock 回退 / real 拒绝 / real 用传入值。安全控制没测试就是裸奔--改 is_mock 分流逻辑时没测试会改坏无感知。这是 SRP 的附带收益：Header 收集（FastAPI 关注点）和租户解析（业务逻辑）分离。

**Q：动作卡投递的跨租户误投为什么不当场修？**
A：变更原子性 + scope。#1 是 read / confirm 侧越权，push 侧误投是另一个问题（assignee 路由）。混在一个 PR 里，reviewer 分不清哪行修 read 侧哪行修 push 侧。而且 push 侧修法要拍板（ActionCard 加 assignee 字段，gate 节点建卡时填；还是 dispatcher 注入 repo 按 session_id 查），改动面大于 #1。我单列 #32 跟踪，让 push 侧问题可见、被单独评估，而不是悄悄混进来或漏掉。**放过不是不管，是不在这个 PR 里改**。

## 5. 压力追问（陷阱题，考诚实）

**Q：你说 service 层校验是纵深防御，那 router 层是不是就没必要注入 tenant 了？**
A：不，两层都要。router 注入 tenant 是"有没有身份"的边界校验（real 模式无 header 直接 400，挡住无身份请求）；service 校验是"身份对不对资源"的归属校验（跨租户 404）。去掉 router 注入，real 模式连"有没有身份"都拦不住，service 拿不到 tenant 也没法校验归属。两层职责不同：router 管"你是谁"，service 管"你能动这个吗"。纵深防御是多层独立校验，不是有 service 就能省 router。

**Q：跨租户返 404 隐藏存在性，但 mismatch 你又记了 warning 含 session_id，这不是矛盾吗？攻击者看不到日志但内部能看到？**
A：不矛盾。404 是对**调用方**的响应（不泄漏存在性），warning 是对**内部运维 / 安全**的日志（供审计）。两者受众不同。调用方只看到 404，探测不到存在性；运维在日志里看到"caller_tenant=WS-B 试图访问 owner_tenant=WS-A 的 session S-xxx"，能发现攻击企图。安全日志是给防守方看的，不是给攻击方看的。如果连内部都不记，攻击不可见；如果对外泄漏，存在性暴露。404 + warning 是"对外隐藏、对内可见"的正确组合。

**Q：你在 real 模式强制 header，但 is_mock 让 mock LLM 的 staging 不强制，这不就是个漏洞吗？你为什么不当场修？**
A：是边界不是漏洞。is_mock 的语义是"任何 mock 即非生产"--这是代码库既有的模式模型（ACL / checkpointer / LLM 都按 is_mock 分流）。staging 用 mock LLM 本身就是"非生产"配置，header 不强制与"mock 模式回退"一致。要堵这个边界有两种做法：staging 用 real LLM（让 is_mock=False），或加 run_mode 维度的强制开关（与 llm_provider 解耦）。后者是独立改动，我没夹带进 #1，列了遗留。**知边界并标出来，比假装"已全面强制"诚实**。

**Q：service 层校验要改测试，你改了，但有没有可能漏了别的调用方？**
A：我 grep 过全仓调用方。resume 的调用方只有 router 和一个测试；get_session 只有 router 和测试（service 内部 pending_step 用的是 repo 裸取不是 service 方法，不受影响）；get_evidence 只有 router 和测试。没有内部 service 代码调这三个方法，所以改签名只动 router + 2 测试，无遗漏。但说实话，这是 grep + 人工核对，不是编译期保证--如果将来有人新增调用方忘了传 tenant，service 签名要求 tenant 会让他必须传（不传报错），这是签名层面的兜底。

**Q：你说身份从 header 取可信，但 header 不也能伪造吗？客户端随便加个 X-Tenant-User-Id？**
A：对，header 本身客户端能加。可信的前提是**真实部署有网关 / 鉴权中间件注入并覆盖这些 header**，客户端传的会被网关重写。我这次的修复是把 user_id 从"请求体（一定不可信）"移到"header（在网关存在时可信）"，是**把信任源从最不可信的地方挪到更可信的地方**。真正的端到端鉴权（网关验签、token 校验）是独立的基础设施层，不在应用层这个 PR 范围。我诚实说：应用层做到"身份不从请求体取"，但"header 防伪造"要靠网关，那是部署架构的事。
