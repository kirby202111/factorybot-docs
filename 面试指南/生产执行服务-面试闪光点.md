## 1. 30 秒电梯陈述（生产执行域版）

"生产执行服务是 MES 的现场执行引擎，我用事件风暴 + DDD 把它拆成 **7 个限界上下文、20 个聚合根、122 条三段式不变式**。它的核心矛盾不是高并发吞吐--过点是低频人工扫码（每工位几秒一次）--而是'**过点既要 ≤200ms 实时、又要六维度强防错、又要全链路追溯可回放、还要零分布式事务**'。解法是四件事：**① 过点主事务五聚合同事务 + Outbox**，把过站瞬间做成一个原子业务事务，零分布式事务；**② routeVersion 快照绑定**，工艺变更不撕裂在制品，历史永久可回放；**③ 设备数据查询超时 200ms 保守拦截**（INV-10 硬阈值），宁可误拦不可漏放 + 工程师授权放行通道；**④ CQRS 写侧（过点）权威 + 读侧（在制品）投影**，秒级最终一致、可从事件流重放重建。防错侧还有首件闸口系统硬拦截、返修（单件）vs 返工（批量）严格分离、再入点重判死循环防护。"

**四个抓手**：7 上下文 / 20 聚合 / 122 不变式 / 五聚合同事务零分布式事务 / routeVersion 时光机 / 200ms 保守拦截。

## 2. 实时性：过点 ≤200ms × 强防错 × 零分布式事务

> 这是面试时**最能体现架构判断力**的部分。关键不是喊 QPS，而是识别出"**过点不是吞吐问题，是低并发下的强一致 + 低延迟 + 强防错问题**"--很多候选人会把过点误当成高并发场景，准确分类本身就是得分点。

### 2.1 五聚合同事务 + 零分布式事务（最大闪光点）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) BIZ-01/BIZ-02、§4.1）：
- 过点判定时，**CheckpointRecord（过点记录）+ CheckpointDecision（放行/拦截决策）+ RoutingProgress（工艺路线推进）+ WorkOrderProgress（工单进度）+ TestResult（测试结果，若已到达）** 五个聚合在**同一本地事务**中写入 + Outbox 发布事件。
- 过点主事务内**只写本地 DB**，跨服务一律走事件订阅或 REST 查询，**零分布式事务**（[领域总览.md](../领域模型/领域总览.md) §5.3）。
- 消息投递走 **Transactional Outbox**：聚合事件与业务状态变更同库事务投递，至少一次 + 崩溃窗口零丢失（§5.4）。

**为什么是亮点**：过点是车间**最高频的业务事务**（每板几秒级），分布式事务（Saga/2PC）会直接拖垮过点吞吐与延迟。五聚合同事务把"过站瞬间"作为一个**原子业务事务**--过点事实、判定、路线推进、进度累计、测试结果要么一起成功要么一起回滚，这是 MES 中最核心的架构决策。注意它和"高频采集不走 Outbox"（设备管理服务）形成对照：**低频业务契约走 Outbox 换一致，高频采集走边缘缓冲换吞吐**（[Outbox设计方案.md](../实现说明/业务事件/Outbox设计方案.md) §9.1）。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) §4.1 / BIZ-01 / BIZ-02、[领域总览.md](../领域模型/领域总览.md) §5.3/§5.4。

### 2.2 本地缓存 + 降级查询解耦（≤500ms 兜底）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) §2.13 / §3.6、BIZ-05）：
- 工艺 / 设备可用性 / 质量门禁 / 齐套四类数据**写少读多**，过点执行上下文维护 4 个本地缓存（`ProcessRouteCache` / `EquipmentAvailabilityCache` / `QualityGateCache` / `KitStatusCache`），订阅上下文外事件**秒级刷新**。
- **缓存命中即本地内存查询--这是主路径**；缓存未命中降级 REST 同步查询制造资源服务只读读模型，**SLA ≤500ms（源文档写死）**，回填缓存后继续判定。
- **降级查询不进过点主事务**（BIZ-05）：缓存未命中时 REST 查询是同步降级路径，但**不在过点主事务中引入分布式事务**；查询失败保守拦截过点（拒绝命令回 DRAFT 或走拦截 + 告警），不产生半成品状态。

**为什么扛得住**：配置型主数据写少读多，版本生效是低频事件，缓存命中率天然极高（设计目标 >99%）。降级 ≤500ms 是**兜底**，过点 ≤200ms 才是主路径目标--两者解耦，配置查询的延迟波动传不到过点主链。这与制造资源服务的缓存降级设计同构（见 [制造资源服务-面试闪光点.md](制造资源服务-面试闪光点.md) §2.3）。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) §0/§2.13/§3.6、BIZ-05、[领域总览.md](../领域模型/领域总览.md) §4.1/§5.1。

### 2.3 设备数据 200ms 保守拦截 + Override 授权放行（INV-10 硬阈值）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-10、§2.4/§3.1）：
- 关键工序过点时按需 REST 查询设备数据接入上下文获取实时数据（当前温度、当前程序等），**超时 >200ms 则 `CheckpointBlocked(blocking_reason=EquipmentDataTimeout)`，保守拦截**。
- **200ms 是写死的硬阈值（INV-10），不是建议**--宁可误拦不可漏放，体现"安全侧"设计哲学。
- 同时提供 **`OverrideCheckpoint` 工程师授权放行通道**（发布 `CheckpointOverridden` 事件记录例外），防止单点故障阻塞全线。

**为什么是亮点**：很多人会把"设备数据查不到"做成"放行 + 告警"以保产能，这里反过来--**查不到就拦**，因为漏放一件不良品的代价（质量事故 / 客诉）远大于误拦一件的产能损失。但纯拦截会因设备数据接入上下文故障导致全线停产，所以补一条授权放行通道平衡可用性。这是"安全侧 + 逃生通道"的完整取舍，不是一刀切。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-10 / §2.4 / §3.1。

### 2.4 六维度并行防错判定（≤1s SLA）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-02、§3.1/§3.2）：
- **六维度防错校验并行执行**（`AntiErrorCheckService`）：工艺版本 / 物料工装 / 设备准入 / 首件门禁 / 前置工序 / 实时数据，汇总为 `AntiErrorCheckResult`。
- 再叠加**质量门禁（PASS/HOLD/BLOCK）+ 设备可用性 + 测试结果 + 跳站校验**，五维度综合判定 PASS/BLOCK。
- **BLOCK 必带 `blocking_reason` + `failed_checks[]`**（INV-02），12 种 `BlockingReason` 枚举覆盖全部拦截场景，精确到每一项失败原因。
- 整体 SLA 建议 ≤1s（设计目标）；单个维度超时（如设备实时数据）计为 FAIL **不阻塞整体返回**。

**为什么是亮点**：不是"扫一下码就过"，是六维度并行 + 五维度综合判定。并行执行保证 SLA，BLOCK 精确到失败项便于现场快速排故。注意"质量门禁"这里指的是**同步门禁**（快、权威，驱动过点决策），与质量上下文的**异步业务判定**（深、记录性）分治--见 [制造资源服务-面试闪光点.md](制造资源服务-面试闪光点.md) §2.4，过点不被深度判定拖慢。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-02 / §3.1 / §3.2 / §2.2。

## 3. 追溯性：routeVersion 时光机 + CQRS + 全链路回放

> 追溯性是 MES 的核心价值，也是 CLAUDE.md 关注点之首。生产执行服务的追溯设计集中在"routeVersion 快照绑定 + 过点记录不可变 + 在制品 CQRS 投影"三件事上。

### 3.1 routeVersion 快照绑定--"时光机"追溯（INV-CX-02）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-CX-02、§1.1/§1.3）：
- **CheckpointRecord 写入时携带 routeVersion 快照**；`RoutingProgress` 在**首次过点时锁定**该 routeVersion，后续推进沿同一版本。
- **工艺版本变更仅影响变更后首次过点的在制品**：已过点产品按它锁定的版本走完，历史追溯按当时版本永久回放。
- 缓存刷新（秒级）与版本锁定解耦--`ProcessRouteActivated` 只刷只读缓存，**不回写已锁定版本的在制品**。

**为什么是亮点**：解决了"工艺变更后历史在制品该按哪个版本推进"的经典噩梦。每条过点记录自带工艺版本快照，实现审计追溯的"时光机"效果。这条不变式（INV-CX-02）在工艺管理 / 物料 / 质量三个上下文同构存在（见 [制造资源服务-面试闪光点.md](制造资源服务-面试闪光点.md) §2.1），生产执行是消费侧落地。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-CX-02 / §1.1 / §1.3 / §2.13。

### 3.2 CQRS 写侧（过点）权威 + 读侧（在制品）投影

**核心机制**（[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) §0、INV-CX-01/03）：
- **过点执行是写侧权威**（`RoutingProgress` = 过站瞬间事实），**在制品追踪是读侧投影**（`WipUnit.position` = 位置累积）。
- 两者通过**异步事件解耦**（`mes.routing.progress`），秒级最终一致，**互不调用对方接口**（INV-CX-03：本上下文不调过点执行的"过点"接口，过点执行不调本上下文的"更新位置"接口）。
- **投影可重放重建**（INV-CX-01 / INV-13）：`WipUnit` 的位置 / 状态 / 历史可从 `mes.routing.progress` 事件流**完全重放重建**，不依赖本地状态--读侧丢了能从事件流恢复。

**为什么是亮点**：过点主事务不引入分布式事务，投影可独立重放重建，写侧不受读侧故障影响。`WipUnit` 是**投影型聚合根**--状态转移由消费事件类型映射，**不做业务判定**，只守护一致性边界（身份唯一 / 历史只增 / 终态拒收）。这是 CQRS 的正确落地：写侧重一致性与防错，读侧重查询与追溯，各自演进。

依据：[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) §0 / §1.1 / INV-CX-01/03 / INV-13。

### 3.3 流转历史只增不可改不可删（INV-02）

**核心机制**（[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) INV-02、§2.3）：
- 每条 `RoutingProgressed` 都追加一条 `WipHistoryEntry`（含 from_station / to_station / timestamp / route_version / source_event_id），**即使 `from_station == to_station`（同工位复测）也记录**，保留完整轨迹。
- `WipHistoryEntry` **只增不可改不可删**，按 `timestamp` 单调递增（INV-02）。
- 任意时刻 `WipUnit.position` = 该 SN 最后一条历史的 `to_station`，历史可重放重建位置。

**为什么是亮点**：溯源链**不串不丢**。很多系统的"当前位置"是个独立字段被反复覆盖，一旦出错无法还原。这里把位置建模成"历史的投影"--历史是不可变事实，位置是派生值，天然一致、天然可审计。

依据：[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) INV-02 / §2.3 / §1.1。

### 3.4 正向追溯 + 反向圈定

**核心机制**（[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) §2.8/§2.9/§4.2）：
- **正向追溯（板 -> 料 -> 站）**：`WipHistoryProjection` 读模型按 SN 查询完整流转历史。
- **反向圈定（异常时段 -> 受影响批次）**：`BatchLocationView` 按 `work_order_id + batch_id` 聚合工位分布与状态汇总，可定位异常时段受影响批次。
- 读模型层不污染写模型聚合，查询直接走投影，最终一致但可重放。

**为什么是亮点**：追溯不是单向的。客诉时既要"这块板用了哪批料、过哪些站"（正向），也要"炉温超标那段时间生产的板要能圈定并隔离"（反向）。`BatchLocationView` 提供了反向圈定的查询能力。**但需诚实标注**：受影响批次的"隔离操作"（暂停某批次继续过站）不在在制品追踪上下文职责内--这是真实车间待补强项（见 §10）。

依据：[在制品追踪上下文.md](../领域模型/生产执行服务/领域建模/在制品追踪上下文.md) §2.8 / §2.9 / §4.2。

### 3.5 不可变过点记录 + SN 防错（INV-12 / BIZ-04）

**核心机制**（[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-12 / BIZ-04、§1.1/§1.5）：
- **过点记录不可变**（INV-12）：一经写入不可修改（含 TestResult 同事务写入）；补传数据迟到**不回填已关单过点记录**，而是发布 `TestResultLateArrived` 供返修 / 质量上下文评估。
- **SN 防错**（BIZ-04）：同一 SN 在同一工单内**不可重复过点同站**（`(sn, work_order_id, station_id)` 业务唯一键去重）。
- HOLD 拦截后人工放行走 `OverrideCheckpoint` 命令发布 `CheckpointOverridden` 事件记录例外，**而非修改原记录**。

**为什么是亮点**：过点记录是**不可变事实**--不修改、不删除、不回填。这保证完整审计链，满足汽车电子 / 医疗器械等行业的合规追溯要求。例外走"叠加事件"而非"改原记录"，是事件溯源思想的落地。

依据：[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-12 / BIZ-04 / §1.1 / §1.5。

## 4. 防错闭环：四道门禁 + 首件闸口 + 返修/返工分流

> 防错是 CLAUDE.md 第二个关注点。生产执行服务的防错不是单点校验，而是一条"**过点拦截 -> 首件闸口 -> 返修/返工分流 -> 再入校验**"的闭环。

### 4.1 防错四道门禁

**核心机制**（[项目亮点与指标卡片.md](项目亮点与指标卡片.md) §2.4、[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-02）：
- 过点引擎内**四道门禁闭环拦截**：**设备可用性 / 工艺路线版本 / 质量门禁规则 / 首件放行**，任一不通过即拦截。
- 设备可用性来自设备工装台账的 9 维可用性投影（订阅 `AssetAvailabilityChanged`，见 [设备管理服务-面试闪光点.md](设备管理服务-面试闪光点.md) §3.1）；工艺路线 / 质量门禁来自制造资源服务的不可变版本（本地缓存 + 降级）；首件放行来自首件处理上下文（`fai.article.released`）。
- 强防错维度（如设备 CRITICAL 故障）在同服务部署时走**本地事务强同步**（台账 INV-CX-08），不走异步消息--避免 Kafka 延迟期间过点引擎读到旧状态错误放行。

**为什么是亮点**：四道门禁横跨三个服务（制造资源 / 设备管理 / 生产执行），但过点引擎通过"本地缓存 + 降级查询 + 同服务强同步"把它们收敛到过点主事务内一次性判定，不引入分布式事务。这是"跨服务防错一致性"的范本。

依据：[项目亮点与指标卡片.md](项目亮点与指标卡片.md) §2.4、[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-02 / §2.13、[领域总览.md](../领域模型/领域总览.md) §4.1/§5.3。

### 4.2 首件闸口系统硬拦截 + 零窗口期默认拒绝

**核心机制**（[首件处理上下文.md](../领域模型/生产执行服务/领域建模/首件处理上下文.md) §0、INV-03/05/14、[事件风暴/首件处理上下文.md](../领域模型/生产执行服务/事件风暴/首件处理上下文.md) §0）：
- **首件闸口强制是系统硬拦截，不是人工检查**：未放行首件的工单，其批量单元在过点执行上下文被首件门禁校验强制拦截。过点执行消费 `fai.article.released` 执行 `EnableBatchProduction`（解除门禁），消费 `fai.article.blocked` 执行 `EnforceFirstArticleGate`（强制拦截）。
- **零窗口期默认拒绝**：`FirstArticleRequested` 发布后即隐式进入"门禁待放行"状态，过点执行可消费 `fai.article.requested` 建立"该工单首件门禁待放行"投影，期间批量单元过点时首件门禁校验 FAIL。**不是等首件放行后才生效门禁，而是首件请求一发出就默认拦截**。
- **门禁作用域固化为 `gate_scope=WORK_ORDER`**（工单级，INV-CX-03），避免产线级门禁误伤并行工单。
- 失败回路完整：HOLD 可经 `OverrideGate` 授权放行（INV-14 必带 `override_authorizer` + `override_reason`），BLOCK 可经 `ReopenInspection` 回退再检（INV-05 必带 `reopen_reason` + `reopened_by`）。

**为什么是亮点**：把首件从"人工检查表"升级为"系统硬拦截 + 默认拒绝安全模型"。换线后首件不通过则批量生产无法过点，防错级别远高于人工表单确认。"默认拒绝"是车间防错的经典安全模型--放行是显式动作，不是默认行为。

依据：[首件处理上下文.md](../领域模型/生产执行服务/领域建模/首件处理上下文.md) §0 / INV-03/05/14 / INV-CX-03 / §2.9、[事件风暴/首件处理上下文.md](../领域模型/生产执行服务/事件风暴/首件处理上下文.md) §0。

### 4.3 返修（单件）vs 返工（批量）严格分离

**核心机制**（[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) §0、[返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) §0）：

| 维度 | 返修（rework） | 返工（brework） |
|------|---------------|----------------|
| 粒度 | **单件级**（一个 SN 一个 `ReworkTask`） | **订单/批次级**（一张 `BatchReworkOrder` 覆盖一批 SN） |
| 触发 | 过点质量类拦截**自动分流**（`mes.unit.routed-to-rework`） | 质量批量异常 / ECN / 人工决策（`BatchQualityAnomalyDetected`） |
| 聚合 | `ReworkTask`（5 聚合根） | `BatchReworkOrder`（2 聚合根） |
| 主题前缀 | `rework.*` | `brework.*` |
| 再入点 | 单件级判定（读返修规则） | 批量级（返工工单定义返工路线起点） |

- 两者粒度 / 触发 / 聚合 / 主题前缀**完全不同**，严禁合并。
- **拦截后质量类自动分流返修**（过点执行 INV-CX-05）：仅 `blocking_reason ∈ 质量类` 时自动发布 `UnitRoutedToRework`；设备 / 物料类由通知服务推送人工处理。

**为什么是亮点**：很多人会把"返修"和"返工"做成一个流程，结果单件偶发和批量系统性混在一起，统计 / 路线 / 再入全乱。这里按"粒度 + 触发"严格拆分，与制造资源服务质量上下文的"单件偶发（`SINGLE_INCIDENT`）vs 批量系统性（`BATCH_SYSTEMIC`）"判定呼应（见 [制造资源服务-面试闪光点.md](制造资源服务-面试闪光点.md) §2.4）--过点拦截分流转单件返修，批量异常信号转批量返工。

依据：[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) §0 / [返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) §0、[过点执行上下文.md](../领域模型/生产执行服务/领域建模/过点执行上下文.md) INV-CX-05。

### 4.4 再入点重判死循环防护--reeval_count 阈值 3

**核心机制**（[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) INV-CX-05、[返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) INV-CX-02、§3.4）：
- 返修 / 返工完成后需回主线再入，**再入点"判定"与"校验"职责分离**：本上下文只**判定**再入点（读返修 / 返工路线配置），过点执行上下文**校验**再入点是否在 routeVersion 合法步序内。
- 过点执行拒绝再入点时发布 `ReentryRejected`，本上下文重判时 `reeval_count += 1`，**阈值 = 3**：若 < 3 重新查询再入点配置重判；**若 ≥ 3 或仍无合法再入点，发布 `ReentryPointExhausted` 升级人工处理**，任务停留原态，不再自动重判。
- 返修验证失败重试上限也是 3 次（BIZ-06），超过升级返修主管评估是否转报废。

**为什么是亮点**：用聚合内字段 + 前置条件（`reeval_count < 3`）在**领域层**实现分布式死循环防护，不需要外部调度器或超时机制。再入点"判定 vs 校验"分离也避免了两边职责重叠--本上下文不持有 routeVersion 步序定义故无法自校验，过点执行不持有返修路线故无法自判定，接力而非重复。

依据：[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) INV-CX-05 / §1.5 / BIZ-06、[返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) INV-CX-02 / §3.4。

### 4.5 三种报废语义严格区分（rework / brework / repair）

**核心机制**（[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) INV-CX-03/06、[返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) INV-CX-06）：
- **批量产品报废**（`brework.order.scrapped`，消费方=过点执行 + WIP）
- **单件产品报废**（`rework.task.scrapped`，消费方=过点执行 + WIP）
- **设备报废建议**（`repair.scrap.recommendation`，消费方=台账审批）
- 三者**事件名、主题前缀、消费方均不同，严禁混用**。`RepairAction` 同名不同义：返修上下文是产品级修理（补焊 / 换元器件），维修上下文是设备级维修（换设备部件 / 调参数）。

**为什么是亮点**：MES 中"维修"一词极易混淆（修产品 vs 修机器），用主题前缀、事件名、聚合归属、消费方**四重隔离**彻底杜绝事件路由错误。这是限界上下文边界落到事件契约层面的体现。

依据：[返修上下文.md](../领域模型/生产执行服务/领域建模/返修上下文.md) INV-CX-03/06 / §7、[返工上下文.md](../领域模型/生产执行服务/领域建模/返工上下文.md) INV-CX-06 / §7。

## 5. 工单与排产编排

> 过点是"毫秒级实时判定"，工单是"天到周级生命周期"，排产是"天到小时级滚动"--三者频率 / 视角完全不同，靠事件解耦协作。

### 5.1 工单来自 SAP + 产品流水号超产门禁（BIZ-04）

**核心机制**（[工单管理上下文.md](../领域模型/生产执行服务/领域建模/工单管理上下文.md) §0、BIZ-04、§1.2）：
- **全部工单来自 SAP，MES 不允许创建工单**；`WorkOrderReceptionService` 按 `source_event_id` 幂等去重接收（BIZ-01）。
- **产品流水号超产门禁**：开工前按 `target_qty` **等量生成 `ProductSerialNo`**（BIZ-04），首工序必须绑定有效产品流水号才能过点。**未发放流水号的产品无法进入首工序，从根本上杜绝超产**，不需要 `allow_overcomplete` 参数。
- MES 工单流水号按前缀递增、已生成不可回收（BIZ-03），`(serial_no_prefix, sequence_no)` 唯一索引保证。

**为什么是亮点**：超产是 MES 经典痛点，很多系统靠"完工后比对数量"被动发现。这里用"开工前等量发号 + 首工序绑号"把超产在**入口**就堵死--号发完了就过不了点，物理上不可能超产。

依据：[工单管理上下文.md](../领域模型/生产执行服务/领域建模/工单管理上下文.md) §0 / BIZ-01/03/04 / §1.2。

### 5.2 完工自动结案 + 状态刚性（INV-11/03/16/07）

**核心机制**（[工单管理上下文.md](../领域模型/生产执行服务/领域建模/工单管理上下文.md) INV-03/07/11/16、§2.5）：
- **完工自动结案**：`COMPLETED` 后立即自动 `CLOSED`（INV-11），**不允许跳过完工口径直接结案**。完工产品 = 最后一道工序过点完成 + 无未关闭质量单 / 返修单等关联异常的汇总状态。`completed_product_qty` 由过点执行上下文汇总（INV-CX-01），本上下文不重复累计。
- **状态刚性**：`CLOSED` / `CANCELLED` 为终态，之后任何事件拒收（INV-03）；`IN_PROGRESS` 后禁止调整 `target_qty`（INV-16）、禁止变更 BOM / 工艺路线版本（INV-07）；状态单向流转，仅 `Pause` / `Resume` 可逆（INV-06）。
- 变更拒绝时发出专属拒绝事件（`WorkOrderQuantityChangeRejected` / `WorkOrderBindingChangeRejected`），引导走返工 / 取消剩余量 / 拆分新建工单。

**为什么是亮点**：工单状态机的刚性是车间防错的体现--已结案的工单不能被随手重开，在制后字段锁定保证执行口径不漂移。完工自动结案省掉人工确认环节，但口径严格（达标 + 无关联异常）。

依据：[工单管理上下文.md](../领域模型/生产执行服务/领域建模/工单管理上下文.md) INV-03/07/11/16 / INV-CX-01 / §2.5。

### 5.3 排产半自动建议 + 计划员确认 + 咨询性不门禁过点（INV-CX-05）

**核心机制**（[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) §0/§1.1、INV-CX-05、[事件风暴/排产上下文.md](../领域模型/生产执行服务/事件风暴/排产上下文.md) §2.3）：
- **半自动建议 + 计划员确认**：`SchedulingSuggestionService` 按排产规则产出 `PENDING` 建议槽位，但 PENDING **不产生任何下游效果**（不回写工单、不触发齐套预占）；只有**计划员确认**（PENDING -> CONFIRMED）才发布 `ScheduleConfirmed` 触发下游。**权威在人不在算法**。
- **排产咨询性不门禁过点**（INV-CX-05）：过点执行上下文**不订阅 `schedule.*` 做硬校验**，过点放行 / 拦截仍按 `wo.order.*` 工单状态。MES 排产快照仅供看板与物料预 stage。
- **事件驱动重排**：订阅三类 disruptions--工单（急单 / 变更）、物料（缺料 `material.kit.reservation-failed`）、设备台账（故障 `eam.asset.availability`）--由 `SchedulingRescheduleService` 按 `RescheduleTrigger` 四类枚举自动重排未开工槽位。

**为什么是亮点**：排产是 MES 里最容易"过度自信"的模块--很多人想上全自动 APS。这里清醒地把算法定位为"建议"、把决策权留给计划员，避免算法误排产生连锁反应。更关键的是"**排产咨询性不门禁过点**"--排产错了最多元数据错，不会导致产线停线，这是架构级安全边界。

依据：[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) §0 / §1.1 / §3.1/§3.2 / INV-CX-05、[事件风暴/排产上下文.md](../领域模型/生产执行服务/事件风暴/排产上下文.md) §2.3。

### 5.4 齐套预占触发点从"下达"收敛到"排产确认"（INV-CX-02）

**核心机制**（[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) INV-CX-02、[事件风暴/排产上下文.md](../领域模型/生产执行服务/事件风暴/排产上下文.md) §2.3）：
- 引入排产上下文后，**`schedule.confirmed` 即"派工"事件**，物料上下文齐套预占的触发源由 `wo.*` 收敛为 `schedule.confirmed`（确认排到线 + 时间才锁料）。
- `schedule.rescheduled` 触发释放旧预占 + 重新预占，`schedule.released` 触发释放预占。
- 工单的 `mes_schedule` 快照与 SAP 下发的 `planned_start_at` / `planned_finish_at` / `production_line_id` **并存互不覆盖**（工单 INV-CX-08）。

**为什么是亮点**：排产确认后才锁料，比"工单下达即锁料"更精准，减少无效预占（工单下达了但还没排到线就锁料是浪费）。这是排产上下文引入后对物料上下文契约的**重新锚定**，体现了新增上下文对相邻契约的正面影响。

依据：[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) INV-CX-02、[工单管理上下文.md](../领域模型/生产执行服务/领域建模/工单管理上下文.md) INV-CX-08。

### 5.5 同线已确认槽位不重叠--收敛到聚合内强一致（INV-01）

**核心机制**（[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) §0、INV-01）：
- 把"**跨工单非重叠**"约束收敛到 `LineSchedule` 聚合内：`confirmSlot` 在事务内校验本线所有 CONFIRMED 槽位与待确认时段是否重叠，重叠则拒绝。PENDING 建议槽位不参与此校验。
- 这是典型的 DDD 聚合设计决策--将跨工单产能约束**收敛到单聚合事务边界内**，用强一致而非最终一致守护，避免跨实例协调的复杂度。
- 配套：**已开工工单冻结不重排**（INV-05），消费 `wo.order.started` 后 `freezeSlot`，所有重排方法校验 `frozen=false`，保证在制工单执行口径不因排产漂移。

**为什么是亮点**：跨工单约束本来容易做成跨实例 BIZ（最终一致 + 唯一索引），这里通过聚合边界设计把它降维成聚合内 INV（事务内强一致）。这是"用建模换一致性强度"的功夫，比堆中间件高级。

依据：[排产上下文.md](../领域模型/生产执行服务/领域建模/排产上下文.md) §0 / INV-01/05 / §1.1。

## 6. 领域建模深度（差异化得分点）

### 6.1 三段式不变式编号方案（INV / BIZ / INV-CX）

生产执行域 7 上下文已**全部迁移完成三段式编号**（排产为新建即三段式，无旧编号残留）：

| 层级 | 一致性边界 | 一致性强度 | 守护机制 | 生产执行数量 |
|------|-----------|-----------|---------|------------|
| **INV-XX**（聚合不变式） | 单一聚合 | 事务内强一致，始终为真 | 聚合根前置条件 / 状态机 / 规约 | **46 条** |
| **BIZ-XX**（业务不变式） | 本上下文内跨聚合 / 跨实例 | 最终一致 | 领域服务 + 唯一索引 / 事件去重表 / Saga，**禁止挂聚合根** | **34 条** |
| **INV-CX**（跨上下文不变式） | 跨限界上下文 | 最终一致 | 事件订阅 + ACL + 跨服务协调 | **42 条** |
| **合计** | | | | **122 条** |

每段分布（上下文：INV / BIZ / INV-CX）：
- 过点执行 7/6/5、工单管理 10/8/9、排产 5/3/8、在制品追踪 7/3/3、首件处理 8/6/3、返修 5/6/6、返工 4/2/8。

**为什么是亮点**：多数项目的不变式是一锅 `INV-01~N` 平铺，看不出一致性边界。三段式把"聚合内强一致 / 上下文内最终一致 / 跨上下文最终一致"显式分层，每条不变式直接告诉你"它靠什么守护、崩了影响多大"。**INV-CX 编号在双方上下文保持一致**（如过点执行 INV-CX-02 ↔ 工艺管理上下文同指 routeVersion 锁定），跨服务协作一眼对齐。

依据：各上下文领域建模 §6。

### 6.2 限界上下文边界判断（经典"为什么不合并"）

| 问题 | 答案（出处） |
|------|------------|

**为什么是亮点**：每个"拆"都有**可辩护的非主观理由**（粒度 / 触发 / 视角 / 频率 / 一致性边界），不是为拆而拆。这是 DDD 落地成熟度的标志。

### 6.3 状态机刚性设计

| 上下文 | 状态机 | 终态 | 可逆边 | 刚性要点 |
|--------|--------|------|--------|---------|
| 工单管理 | CREATED->RELEASED->IN_PROGRESS->PAUSED->COMPLETED->CLOSED + CANCELLED | CLOSED / CANCELLED | 仅 PAUSED<->IN_PROGRESS | 终态拒收（INV-03），在制后锁 target_qty / 版本（INV-16/07） |
| 过点执行 RoutingProgress | NOT_STARTED->IN_PROGRESS->BLOCKED_SKIP->COMPLETED | COMPLETED | BLOCKED_SKIP->IN_PROGRESS（授权跳站） | COMPLETED 后任何推进拒收（INV-05） |
| 返修 ReworkTask | CREATED->DIAGNOSED->IN_REPAIR->PENDING_REENTRY->COMPLETED + PENDING_SCRAP_DECISION->SCRAPPED | COMPLETED / SCRAPPED | 3 条（报废驳回 / ReentryRejected / 验证 FAILED） | 终态拒收（INV-05），仅 3 条可逆（INV-10） |
| 返工 BatchReworkOrder | CREATED->ROUTE_ASSIGNED->IN_REWORK->PENDING_REENTRY->RELEASED->COMPLETED + PENDING_SCRAP_DECISION->SCRAPPED | COMPLETED / SCRAPPED | 2 条（再入点被拒 / 报废驳回） | 终态拒收（INV-05），仅 2 条可逆（INV-10） |
| 首件 FirstArticle | REQUESTED->INSPECTING->PENDING_DECISION->RELEASED/BLOCKED | RELEASED | BLOCKED->INSPECTING（授权回退） | RELEASED 终态不可逆（INV-03），BLOCKED 可回退再检（INV-05） |
| 排产 ScheduleSlot | PENDING->CONFIRMED->RELEASED（+frozen 子状态） | RELEASED | 无 | 单向不可回退（INV-02），冻结后不重排（INV-05） |

**为什么是亮点**：所有状态机都遵循"**终态拒收 + 极少可逆边 + 无管理员强制 reopen**"的刚性原则。可逆边对应的是真实业务回退（没修好 / 报废没批 / 再入点被拒），不是操作便利。这符合车间防错--已关单的工单 / 已完成的过点不能被随手重开，否则追溯链断裂。

依据：各上下文领域建模 §2 状态机章节。

## 8. 追问防守 Q&A（生产执行域专属）

**Q：生产执行 7 个上下文会不会过度设计？**
A：每个拆分都有非主观理由。返修 vs 返工--粒度（单件 vs 批量）和触发不同；返修 vs 设备维修--修产品 vs 修机器；过点 vs 在制品--CQRS 写侧 / 读侧；首件 vs 质量--编排门禁 vs 判定标准；排产 vs 工单--跨工单产能约束无法在单工单聚合内检查；工单 vs 过点--频率天差地别（天级 vs 毫秒级）。**拆都按"粒度 / 触发 / 视角 / 频率 / 一致性边界"判断，不是按"看着大"**。

**Q：过点是高并发场景吗？**
A：**不是吞吐场景，是低并发下的强一致 + 低延迟 + 强防错问题**。过点是每工位几秒一次人工扫码（[项目亮点卡片 §2.5](项目亮点与指标卡片.md)），真正的高并发是设备数据采集（万级报文 / 秒，归设备管理服务）。过点的难点不在扛吞吐，在"既要 ≤200ms 实时、又要六维度强防错、又要全链路追溯、还要零分布式事务"--这四个约束同时满足才是功夫。很多人把过点误当高并发，方向就错了。

**Q：过点 200ms 怎么保证？**
A：三件事：① 本地缓存优先--工艺 / 设备 / 质量 / 齐套四类配置型数据写少读多，订阅事件维护本地缓存副本，命中缓存即本地内存查询，这是主路径；② 降级 ≤500ms 兜底--缓存未命中才降级 REST 查读模型，且不进过点主事务（BIZ-05）；③ 零分布式事务--过点主事务五聚合同事务 + Outbox，不引入跨服务事务。设备实时数据（非缓存）按需 REST 查询，超时 >200ms 保守拦截（INV-10）。

**Q：工艺变更时线上在制的板子按新工艺还是旧工艺？**
A：按**它首次过点锁定的 routeVersion 走完**，新版本只对"变更后首次过点"的单件生效（过点执行 INV-CX-02）。`CheckpointRecord` 写入时携带 routeVersion 快照，`RoutingProgress` 首次过点锁定版本，后续推进沿同一版本；`ProcessRouteActivated` 只刷只读缓存，不回写已锁定版本的在制品。历史追溯按当时版本永久回放。这条不变式在工艺管理 / 物料 / 质量上下文同构存在。

**Q：设备数据查询超时 200ms 就拦截，误拦怎么办？**
A：这是"安全侧"设计--宁可误拦不可漏放，漏放一件不良品的代价（质量事故 / 客诉）远大于误拦一件的产能损失。但纯拦截会因设备数据接入上下文故障导致全线停产，所以补了 `OverrideCheckpoint` 工程师授权放行通道，发布 `CheckpointOverridden` 事件记录例外（不修改原记录）。200ms 是 INV-10 写死的硬阈值，不是建议。

**Q：过点为什么走 Outbox，而设备采集不走？**
A：两种并发特征不同（[设备管理服务-面试闪光点.md](设备管理服务-面试闪光点.md) §2.1）。过点是低频业务契约事件（每工位几秒一次），走 Outbox 换"DB commit 与事件发布同事务、崩溃零丢失"，代价是多一次 DB 写可接受。采集是高频原始数据（万级 / 秒），走 Outbox 会先把 outbox 表写爆，所以用边缘缓冲 + Kafka 直连换吞吐。**低频走 Outbox 换一致，高频走边缘缓冲换吞吐**--这是用两套方案对应两种并发特征的刻意选择。

**Q：五聚合同事务会不会太重？**
A：不会，反而比分布式事务轻。过点判定本来就要同时写过点记录 / 决策 / 路线推进 / 工单进度 / 测试结果，这五者是"过站瞬间"的原子业务事实，要么一起成功要么一起回滚。同库本地事务的开销远低于 Saga / 2PC 的跨服务协调。真正会拖垮过点的是把跨服务调用塞进主事务（如同步扣库存），所以物料消耗走最终一致、配置查询走缓存降级，主事务内只写本地 DB。

**Q：首件没验，批量过点会怎样？**
A：**首件门禁强制拦截**。首件未放行的工单，其批量单元在过点执行上下文被首件门禁校验拦截。而且不是"等首件放行后才生效门禁"，是"首件请求一发出就默认拦截"（零窗口期默认拒绝）--`FirstArticleRequested` 发布后即进入"门禁待放行"状态。门禁作用域固化为工单级（`gate_scope=WORK_ORDER`），避免误伤并行工单。把首件从人工检查表升级为系统硬拦截，是防错级别的提升。

**Q：返修和返工为什么分开？**
A：粒度 / 触发 / 聚合 / 主题前缀全不同。返修是单件级（一个 SN 一个 `ReworkTask`，过点质量类拦截自动分流触发，`rework.*`）；返工是订单 / 批次级（一张 `BatchReworkOrder` 覆盖一批 SN，质量批量异常 / ECN 触发，`brework.*`）。合并会单件偶发和批量系统性混在一起，统计 / 路线 / 再入全乱。这和质量上下文"单件偶发 `SINGLE_INCIDENT` vs 批量系统性 `BATCH_SYSTEMIC`"判定呼应。

**Q：再入点重判会不会死循环？**
A：不会，有 `reeval_count` 阈值防护（返修 INV-CX-05 / 返工 INV-CX-02，阈值 = 3）。过点执行拒绝再入点时发 `ReentryRejected`，本上下文重判时 `reeval_count += 1`；< 3 重新查询再入点配置重判，**≥ 3 发布 `ReentryPointExhausted` 升级人工处理**，任务停留原态不再自动重判。用聚合内字段 + 前置条件在领域层防死循环，不需要外部调度器。再入点"判定归返修 / 返工上下文、校验归过点执行"的职责分离也避免了重复校验。

**Q：工单超产怎么防？**
A：**开工前按 `target_qty` 等量生成产品流水号**（BIZ-04），首工序必须绑定有效产品流水号才能过点。号发完了就过不了点，物理上不可能超产，不需要 `allow_overcomplete` 参数。这是"入口堵死"而非"完工后被动比对"。MES 工单流水号按前缀递增、已生成不可回收（BIZ-03）。

**Q：排产会不会卡住过点？**
A：不会，**排产咨询性不门禁过点**（INV-CX-05）。过点执行上下文不订阅 `schedule.*` 做硬校验，过点放行 / 拦截仍按 `wo.order.*` 工单状态。MES 排产快照仅供看板与物料预 stage。这样排产错了最多元数据错，不会导致产线停线--这是架构级安全边界。排产本身也是半自动建议 + 计划员确认，权威在人不在算法。

**Q：在制品追踪和过点执行为什么不合并？**
A：CQRS 写侧 / 读侧分离。过点执行是写侧权威（过站瞬间事实，毫秒级），在制品追踪是读侧投影（位置累积，秒级最终一致）。两者频率 / 职责不同，合并会让毫秒级写事务被读查询拖累，且写侧故障会连累读侧。投影可从事件流重放重建（INV-CX-01/INV-13），读侧丢了能恢复，互不耦合。

**Q：三段式不变式（INV / BIZ / INV-CX）有什么用？**
A：把一致性边界显式分层。INV 是聚合内强一致（事务内始终为真，聚合根前置条件守护）；BIZ 是上下文内跨聚合最终一致（靠唯一索引 / 去重表，**禁止挂聚合根**--否则聚合根要查别的实例，破坏一致性边界）；INV-CX 是跨上下文最终一致（靠事件 + ACL）。混在一起就会把"该用唯一索引保证的"误写成"聚合根前置条件"，看着对、实则守不住。生产执行 122 条全这么分，比一锅 INV-01~N 平铺可维护得多。

|------|---------------|------|---------|
| 追溯"不串不丢可还原" + 受影响批次圈定 | 客诉时 100% 还原某板用了哪批料、过哪些站；炉温超标那段时间的板要能圈定并隔离 | 🟡 | 正向追溯 + `BatchLocationView` 反向圈定已有，但**隔离操作**（暂停某批次继续过站）不在在制品追踪职责内。讲"正向追溯 + 反向圈定 + 隔离操作"三段 |
| 炉温实时 SPC + 超标停线 | 回流焊多温区秒级采集 + 实时 SPC + 超标停线指令 | 🟡 | 采集侧"只搬运不解释"对，过点有设备数据 200ms 校验，但 **SPC 实时判定归谁、超标停线指令怎么实时下发**未串全。讲"采集只搬运 / SPC 判定归质量 / 停线指令走防错通道"三段职责 |
| SN 端到端防重防错 | 烧录 SN 与镭雕 SN 一致性、重号检测、错配拦截 | 🟡 | 过点有"同 SN 不可重复过点同站"（BIZ-04）+ 不可变记录（INV-12），但 SN 平台预分配 -> 镭雕 -> 烧录校验 -> 过点查主键的端到端链路未串全 |
| 数据一致性边界（DB + 缓存 + 事件 + 指令） | 过点判定要写 DB、刷缓存、投事件、下发设备指令，四者部分失败怎么办 | 🟡 | Outbox 解决了 DB + 事件，但**缓存 + 指令**的一致性未讲。讲"Outbox 管 DB + 事件、缓存靠事件订阅最终一致、指令靠确认 + 联锁，三者失败语义不同" |

### 9.3 高并发（被低估的真实尖峰）

| 场景 | 为什么是高并发 | 覆盖 | 话术价值 |
|------|---------------|------|---------|
| 过站"开线潮 / 换班潮" | 开线瞬间、换班交接瞬间，全场几十~上百工位**同时**扫码过站，瞬时尖峰 | 🟡 | 过点稳态是低并发，但尖峰未显式建模。讲"过点既有稳态也有尖峰，尖峰靠连接池 / 批量写 / 排队吸收" |
| 缓存雪崩（换线 / 班次启动） | 早班开机、集中换线，所有工位同时起过点，本地缓存未预热，集中降级查询 | ❌ | 降级 ≤500ms 是**单次** SLA，缺批量预热 + 限流 + 熔断 + 多级缓存。文档 gap |
| 在制品快照消息风暴 | 大工单数千板高频位置变更 | ✅ | 已有"增量 + 周期全量"防风暴（≤50 即时增量 / >50 仅周期 30s 全量，BIZ-04）。**已较好覆盖** |

### 9.4 优先补强建议

**最值得补的 4 个（真车间、高话术价值、当前盲区）**：

1. **过点引擎离线降级 / 断网自治**（HA）-- 制造业 HA 头牌，一讲就知道下过车间。当前文档明确列为暂缓。
2. **防错指令可靠送达 + 设备物理联锁**（HR + HA）-- 把"逻辑门禁"升级到"物理联锁"三级防错，段位明显高。
3. **炉温实时 SPC + 超标停线**（实时 + 追溯 + 防错三高叠加）-- 采集 / 判定 / 指令三段职责讲清，最显架构力。
4. **追溯反向圈定 + 受影响批次隔离**（HR）-- 客诉场景，MES 核心价值的杀手锏。当前有查询能力但缺隔离操作。

这 4 个共同点：都是**过站执行 + 物料防错物理级**侧的盲区，正好补上"实时 / 防错 / 追溯"三角在物理落地层的最后一块。**讲法纪律**：已覆盖的讲机制，gap 要说"真实部署需补强 / 这是上线前要验证的"，**别说成已实现**。

## 11. 红线（生产执行域版）

- ❌ "过点线上扛了 N 万 QPS"--过点是低并发人工扫码，不是吞吐场景。这是设计阶段项目。
- ❌ "缓存命中 99.9%" / "过点 P99 实测 ≤200ms"--除非有真实监控埋点。
- ❌ "良率提升 X%" / "返工下降 Y%" / "首件通过率 Z%"--除非有真实 SPC 复核数据。
- ❌ 把"≤1s 全链路 / 5s TestResult 窗口 / >99% 缓存命中"说成源文档写死--它们是**设计目标 / 估算**，待 SME 确认。
- ✅ 正确讲法："过点 P99 **设计目标** ≤200ms，过点是低并发人工扫码场景，重点在强防错 + 低延迟 + 零分布式事务，不是吞吐。配置型数据缓存命中是主路径，降级 ≤500ms 是兜底。设备数据查询超时 200ms 保守拦截是 INV-10 写死的硬阈值。"
- ✅ "Outbox 保证过点五聚合事件与状态变更同库事务，**设计上**崩溃窗口零丢失，消费端幂等。" -- 讲机制 + "设计上"。

被问到"上线跑过吗"时，老实说："这是设计阶段的架构方案，重点是**识别出过点'实时 + 防错 + 追溯 + 零分布式事务'的四重矛盾，用五聚合同事务 + routeVersion 快照 + 缓存降级 + CQRS 解掉**，业务效果需要在真实车间上线后用 SPC 数据验证。"--**诚实 + 体现架构判断力，比硬吹数字得分高**。

## 12. 一句话定位（收尾用）

"生产执行服务的价值不在于把过点做成 CRUD，而在于**识别出过点'既要 ≤200ms 实时、又要六维度强防错、又要全链路追溯可回放、还要零分布式事务'的四重矛盾，用五聚合同事务 + routeVersion 时光机 + 本地缓存降级 + CQRS 写读分离 + 首件闸口硬拦截，做成了既能保证全链路追溯、又不拖垮 ≤200ms 现场过点的实时执行引擎**--配置稳、追溯清、防错硬，执行才能快。"
