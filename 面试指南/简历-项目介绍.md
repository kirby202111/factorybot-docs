# 简历 · 项目介绍

> **用途**：简历项目栏 + 面试开场自我介绍。
> **范围**：仅覆盖 MES 主体三服务（制造资源 / 设备管理 / 生产执行）的领域建模与架构设计，不含 Agent / RAG 旁路部分。

---

## 一、项目概况（简历项目栏可直接用）

**项目名称**：混合型制造车间 MES 系统（PCBA 电子制造 + 整机组装）
**项目角色**：架构设计 / 领域建模负责人
**项目阶段**：已交付上线（领域建模 + 架构设计 + 核心链路实现 + 落地运行）

**项目描述**：

> 为解决车间流程不规范、产品生命周期难管理的问题，基于 **DDD 领域驱动设计**与**微服务架构**，设计并实现车间全流程管理平台。系统上线后**管控 6 条产线、100 多种物料、600 多型号产品**的生产制造，**服务核心用户 200 多人**。
>
> 采用**事件风暴 + DDD** 完成战略建模，拆分为 **3 个微服务、14 个限界上下文**，覆盖工单管理、过点执行、在制品追踪、首件、返修、返工、排产、物料、工艺、质量、设备台账、设备数据接入、点检保养、计量检定、维修全场景。
>
> 核心解决三类问题：**全链路追溯**（物料→批次→过点→测试→单件身份贯通）、**过点防错**（设备可用性 / 工艺版本 / 质量门禁 / 首件放行四道门禁拦截）、**实时生产执行**（过点查询 P99 ≤200ms）。跨服务一致性采用 **Transactional Outbox + Kafka**，业务状态与事件原子投递、消费端幂等；高频设备采集走边缘网关缓冲 + Kafka 直连链路，与低频过点主事务彻底解耦，稳定支撑全线设备数据实时接入。
>
> 累计输出 **40+ 篇**设计与实现文档（14 篇事件风暴 + 14 篇领域建模 + 12 篇实现说明），每个限界上下文均有完整的聚合根 / 领域事件 / 不变式定义。

## 二、核心职责

1. **领域建模**：主持 14 个限界上下文的事件风暴与聚合设计，定义聚合根、实体、值对象、领域事件与不变式（三段式：INV 业务规则 / BIZ 流程规则 / INV-CX 跨上下文契约），如维修上下文 5 个聚合根 + 23 条不变式。
2. **架构设计**：设计三服务拆分（按变化频率与延迟要求）、跨服务协作模型（事件编排 + REST 查询 + 缓存投影）、事务边界与一致性策略（过点主事务零分布式事务）。
3. **可靠消息设计**：设计 Transactional Outbox 六状态机（PENDING→PUBLISHING→SENT / RETRYABLE / DEAD_LETTER）、限流四层、消费幂等框架、DLT 治理与重放机制。
4. **高并发采集链路设计**：设计边缘网关（协议适配策略模式、边缘缓冲、断点续传）、平台去重与乱序矫正、热/温/冷存储分层、大载荷对象存储卸载。
5. **工程落地**：完成核心链路的 Java/Spring 实现、Kafka 集群与中间件配置、可观测性指标与告警体系，并保障系统平稳上线运行。

## 三、核心贡献

> 简历项目栏挑 3~4 条即可，其余留作面试展开。**口径说明**：量级指标按产线规模推算（推算依据随附，面试可当场演算）；延迟与可靠性指标为交付口径。

### 业务架构设计

- **主导 DDD 战略建模**：以事件风暴将混合型车间 MES 拆解为制造资源 / 设备管理 / 生产执行 **3 大微服务、14 个限界上下文**，按变化频率与延迟要求划定服务边界；产出 28 篇事件风暴 + 领域建模文档，每个上下文均定义聚合根、领域事件与三段式不变式（如维修上下文 5 个聚合根 + 23 条不变式）。
- **攻克 600+ 型号的版本管理复杂度**：设计工艺路线版本生命周期机制，过点记录绑定 `routeVersion` 快照——工艺变更仅影响变更后首次过点的在制品，历史追溯完全免疫后续变更，版本一致性从"人工自觉"变为"结构保证"。
- **设计双向可逆状态机与防死循环机制**：工单齐套状态（KitStatus）由工单管理单一判定方汇聚多源物料事件重算，READY↔NOT_READY 双向可逆；返修/返工再入点被拒后自动重判并以 `reeval_count` 阈值封顶，杜绝"拒绝→重判→再拒绝"无限循环。
- **构建上下文内 CQRS 与无中心事件编排**：在制品执行上下文写侧 5 聚合 + 读侧 `WipUnit` 位置投影；跨上下文流程（工单下达→过点→进度→完工）跨 6+ 上下文、近百个领域事件 choreography 串联，无中心编排器、零分布式事务。
- **落地运维 SLA 管控闭环**：维修上下文按故障分级映射 SLA（CRITICAL 响应 15min / 修复 2h），超时自动升级 L1→L2→L3→外协，报废建议与审批执行跨上下文分离，全流程事件驱动。

### 性能优化

- **满产承载能力**：按客户 6 条产线、单线 6~10s 节拍推算，系统日均可承载约 **5 万块过板、40~50 万次过点记录写入**（均值约 6 TPS、峰值 50~60 TPS）与 **700 万级设备采集报文落库**（均值约 100 TPS、峰值约 400 TPS）；过点记录单表年增千万级，采用月度分区 + 热温冷分层保障长期查询性能。
- **采集链路吞吐与成本**：`dc.*` 采集 topic 日均 700 万条、峰值约 400 msg/s（字节率峰值 <1MB/s，按 10 倍余量规划分区与集群配额）；日均约 25GB 大载荷（扭矩曲线 / AOI 图像 / 烧录日志）卸载 MinIO，主流只承载 `object_uri + sha256`，单条消息控制在 KB 级。
- **过点查询压到 P99 ≤200ms**：设计工艺路线 / 设备状态 / 质量门禁 / 齐套 / 工单五大读侧缓存投影，过点优先读本地缓存，未命中才降级 REST（工艺/BOM ≤500ms）兜底；过点主事务内零分布式事务、零跨服务同步调用，TestResult 写入与过点判定同本地事务。
- **高/低频链路架构级分流**：识别高频采集（秒级持续流）与低频过点（人工触发）两种并发特征，高频数据走"边缘缓冲 + Kafka 直连"、**明确不走 Outbox**，避免 outbox 表写爆拖垮业务 DB；进度 事件仅在工单状态变化时发布，防止过点高频场景打爆 topic。
- **采集吞吐优化**：大载荷（扭矩曲线数百点/枪、AOI 图像、烧录日志）卸载 MinIO，主流只承载 `object_uri + sha256`；采集 Producer 独立 client-id，50ms 攒批 + 128KB batch + zstd 压缩；热层 Redis 实时快照支撑过点按需同步查询（≤200ms）。
- **防缓存雪崩**：新消费组 `earliest` 偏移补投影实现缓存预热，降级查询配限流熔断，冷启动或缓存大面积失效时不击穿权威源。

### 高可靠保障

- **Transactional Outbox 可靠消息**：业务状态与 outbox_event 同本地事务原子提交，崩溃窗口零丢失；设计 PENDING→PUBLISHING→SENT 六状态机（含 RETRYABLE / DEAD_LETTER / PUBLISHING 超时恢复重发），Publisher 限流四层 + 自适应背压；聚合根不依赖 KafkaTemplate，只返回领域事件由应用服务编排 outbox 写入。
- **至少一次 + 幂等消费 = 等效一次处理**：业务事件按 `event_id + consumer_group` 同事务幂等、手动 ack offset；幂等键按业务语义设计（KitStatus 重算 `work_order_id+source_event_id`、设备阻塞 `(asset_id, reason, source_event_id)`），不一刀切；PUBLISHING 超时重发造成的重复窗口由消费端幂等吸收。
- **高频采集"不丢不重"三支柱**：边缘缓冲 + 断点续传（游标单调递增、先补后新）+ Kafka `acks=all` / `min.insync.replicas=2` 保不丢；平台 `msg_id` 去重 + 乱序矫正窗口（迟到报文打 LATE 质量标补入不丢弃）+ 消费端 `msg_id` 幂等保不重；每条报文强制质量标（GOOD/SUSPECT/BAD/LATE）。
- **可观测与 DLT 治理闭环**：Outbox 9 项指标 + 6 类告警、采集侧 13 项指标 + 8 类告警；死信保留原始 payload 与异常摘要，人工修复后可重放；统一 Envelope（`event_id` / `correlation_id` / `causation_id`）支撑端到端链路还原，事件 schema 演进规范（新增字段可选、不删不改语义）。

## 四、架构设计亮点（面试深挖用）

### 1. DDD 战略设计：3 服务 14 上下文，按变化频率划分

| 服务 | 定位 | 上下文 |
|---|---|---|
| 制造资源服务 | 生产执行数据基座（配置型主数据） | 物料、工艺管理、质量 |
| 设备管理服务 | 设备全生命周期与运维中心 | 设备工装台账、设备数据接入、点检保养、计量检定、维修 |
| 生产执行服务 | 现场生产活动执行引擎 | 工单管理、在制品执行、首件处理、返修、返工、排产 |

拆分依据是**变化频率与延迟要求差异**：配置数据（工艺/质量）写少读多，单独成服务避免被高频过点拖垮；设备运维（资产视角）与现场执行（执行视角）关注点不同，合并会互相污染。

### 2. 事件驱动架构：统一事件骨干

- **近百个领域事件、13 个 topic 命名空间**，命名按业务语义（`mes.*` `wo.*` `eam.*` `material.*` …）而非技术来源；`wo.*`（工单）/ `brework.*`（返工）/ `rework.*`（返修）/ `repair.*`（设备维修）语义相近，靠前缀物理隔离防串台。
- **统一 Envelope**：`event_id` / `event_type` / `event_version` / `trace_id` / `correlation_id` / `causation_id`，支撑幂等去重、schema 演进、端到端链路串联。
- **`partition_key=聚合根ID`** 保证同聚合根事件分区内有序；幂等 Producer 保证重试不乱序。
- 跨上下文流程推进**无中心编排器**（事件 choreography），每个上下文自治响应上游事件。

### 3. 两条可靠性路径刻意分工（架构级决策）

| 维度 | 低频业务契约事件 | 高频设备采集 |
|---|---|---|
| 管道 | DB 事务 + Outbox + Publisher | 边缘缓冲 + Kafka 直连 |
| 一致性 | 与业务状态同事务原子 | 不丢不重 |
| 不重手段 | `event_id + consumer_group` 消费幂等 | 平台 `msg_id` 去重 + 消费幂等 |
| 顺序 | 分区内有序 | 分区内有序 + 乱序矫正窗口 |

高频采集**明确不走 Outbox**——秒级持续流会把 outbox 表写爆（写放大 + 行锁竞争），这条架构级排除是 Outbox 限流参数可定的前提。不丢靠"边缘缓冲 + 断点续传（先补后新）+ `acks=all` + `min.insync.replicas=2`"，不重靠"平台去重 + 消费幂等"双保险。

### 4. CQRS 读侧缓存投影 + 降级 REST，过点 ≤200ms

- 工艺路线、设备状态、质量门禁、齐套状态、工单状态五大缓存，均通过订阅领域事件本地维护；过点优先读本地缓存，**未命中才降级 REST 查权威源**（工艺/BOM ≤500ms，设备实时数据 ≤200ms）。
- 缓存是读优化投影而非事实源，丢失可从权威源重建；过点主事务内**零分布式事务**、零跨服务同步调用。
- **版本快照不可变**：600+ 型号 × 多版本 BOM/工艺路线组合下，过点记录锁定 `routeVersion`，工艺变更只影响变更后首次过点的在制品，历史追溯免疫后续变更——版本一致性从"人工自觉"变成"结构保证"。

### 5. 设备可用性聚合：强防错本地事务 vs 跨服务异步的精细切分

- 台账上下文是设备可用性**唯一事实源**，汇聚点检/保养/寿命/检定/维修/通信/报警七个维度的阻塞信号综合重算，任一维度阻塞即停用，全部解除才恢复。
- **同服务 + 强防错 → 本地事务同步**（点检异常/超期、保养超期、寿命超限、CRITICAL 故障）；**跨服务或非强防错 → 事件解耦**（检定、维修恢复、报废审批）。强防错场景绝不让事件最终一致的滞后窗口放过本应拦截的过点。
- 通信故障二级处理：先停用资产，再生成草稿维修单待人工确认，避免通信抖动误报。

### 6. 高频采集链路：把吞吐压力挡在边缘

- **采集只搬运不解释**（INV-CX-01）：网关/平台不做 PASS/FAIL 判定、不推进过站、不停用资产——协议适配器因此免疫工艺变更。
- **协议适配策略模式**：`DecodingStrategy` 按设备类型实现（SECS/GEM 印刷机/AOI、OPC-UA 波峰焊/老化房、TCP 镭雕机、Agent+HTTP 烧录电脑、MQTT 智能电批、REST 线边仓），纯计算可单测，协议画像热重载不中断通道。
- **边缘缓冲 + 断点续传**：`BackfillCursor` 单调游标，恢复后先补后新；"不丢"换"可能重复"，由平台 `msg_id` 去重吸收。
- **平台去重 + 乱序矫正**：补传数据天然乱序，按 `source_ts` 窗口矫正，迟到报文打 LATE 质量标补入不丢弃；每条报文强制质量标（GOOD/SUSPECT/BAD/LATE）。
- **大载荷卸载 MinIO**：扭矩曲线（数百点/枪）、AOI 图像、烧录日志不进 Kafka（1MB 上限），网关预签名 PUT 直传，主流只承载 `object_uri + sha256`，"对象先于引用存在"。
- **存储热/温/冷分层**：热层 Redis 实时快照供过点查询；温层 MySQL 结构化表供 SPC；冷层对象存储归档；TSDB 按实测写入量触发引入。
- **限流四层 + 集群级配额**：网关在途上限 / Producer 令牌桶 / 平台去重吞吐上限 / 温层写入限流，采集与业务 client-id 配额隔离；限流是速率维度、顺序是分区维度，两者正交。
