## 项目背景

主导面向 PCBA 电子制造 + 整机组装混合型车间的 MES 系统后端建设，覆盖工单、过点执行、设备采集与运维全链路。

## 核心贡献
● 基于 DDD 的领域建模：主导平台遗留系统改造，通过事件风暴识别核心域与子域，按变化频率与一致性边界划分 14 个限界上下文（归并为制造资源、设备管理、生产执行 3 个微服务）；设计层面，以聚合根不变规则保障强一致性，以领域事件实现跨上下文最终一致，使跨上下文回归缺陷下降约 80%。

● Outbox + Kafka 事件骨干：聚合根只产事件、应用层编排 Outbox，业务与消息同事务提交；六状态机 + SKIP LOCKED 多实例领取 + 指数退避死信治理，实现 99.99% 可靠投递；按聚合根分区保序、Producer 幂等发送，13 Topic / 近百事件统一契约，支撑 6+ 上下文零分布式事务解耦；四层限流 + 自适应背压扛住 2000+ 事件/分钟突发；物料齐套重算去抖合并，批量 BOM 导入重算下降 90%。
● 事件通信层设计（Outbox + Kafka）：业务状态与 outbox_event 同本地事务原子提交，消除"库已提交、消息未发出"的崩溃窗口；Publisher 以 FOR UPDATE SKIP LOCKED 多实例领取、六状态机收敛投递，acks=all + 幂等 Producer + 四层生产侧限流（领取节流 / 全局令牌桶 / 按 topic 公平调度 / 在途信号量）叠加自适应背压，批量下发突发下不打爆 Kafka 与业务库；消费侧手动 ack + event_id 与业务变更同事务幂等，实现"至少一次投递 + 消费幂等 = 等效一次"；失败按可恢复性分流——可恢复指数退避重试、不可恢复直入死信并告警，死信保留原始报文与异常摘要，支持修复后重放。
● 设计并实现 Transactional Outbox 事件骨干：业务表与 outbox 同事务原子提交消除崩溃窗口，六状态机 + SKIP LOCKED 多实例领取 + 指数退避死信治理，event_id 幂等消费 + 分区键保序，四层限流与自适应背压护住 DB/Kafka，实现跨 6+ 上下文字段级零分布式事务，14 topic / 近百事件统一契约。
● 跨服务事件协作：设计业务状态与事件同库事务原子投递机制，聚合根 ID 分区保序 + 幂等 Producer，14 个语义化 topic 承载近百个领域事件，四层限流（领取节流 / 全局令牌桶 / 按 topic 公平调度 / 在途上限）稳定兜住 500+ 事件/分钟突发流量，实现跨服务协作零分布式事务，支撑工单下达→过点→完工跨 6+ 上下文长链路异步解耦。
● 消息可靠投递：Outbox 六状态机（PENDING→PUBLISHING→SENT，失败指数退避重试、耗尽入死信可修复重放、PUBLISHING 超时恢复重发）保障至少一次投递，消费端 event_id 幂等且与业务处理同事务，事件投递成功率 99.99%、宕机恢复零丢失、重复处理率 < 0.01%，业务流在宕机下不断裂、不重复。


● 过点全链路优化：写侧将过点记录、放行决策、路线推进、工单进度、测试结果五聚合同事务原子提交（主事务仅写本地 DB），配合上下文内 CQRS 写读分离与采集/业务双链路架构级分流，使“过站瞬间”成为不受高频采集冲击的原子业务事实；读侧工艺版本与物料/工装按工单下达时绑定的不可变版本快照读取，从机制上消除配置缓存一致性窗口，设备可用性、质量门禁、齐套状态等实时状态投影本地缓存化并以降级 REST 兜底，实现过点全链路 P99 ≤ 200ms、缓存命中率 > 99%，换班高峰 50 个工位并发扫码无超时雪崩；齐套状态重算引入去抖合并，批量 BOM 导入场景重算次数下降约 90%。

● 高并发采集链路：平台接入侧落地，Kafka 直连管道分区保序 + 幂等攒批、msg_id 去重与乱序矫正；大载荷按形态分流卸载，配合三层存储分流，支撑峰值 1.2 万报文/秒、落库延迟 P99 < 1s、Kafka 主流流量下降约 70%，实现秒级入库与实时 SPC 分析。

● 业务表容量治理：过点记录随产线投用与数据积累单表超亿行、索引膨胀导致写入与查询双向劣化，按工单号 + 月度双维水平分表并做路由层透明化，SN 跨工单轨迹查询由二级映射表兜底、跨分片统计改为汇总表预计算，规避全表扫描；配合历史月份分表冷归档与在线 DDL 变更，单表规模压至千万级，写入 P99 与慢 SQL 数分别下降约 40%/70%，加字段的锁表窗口从小时级降到分钟级且不中断生产。

● 可观测性体系：为 3 个服务从 0 建立 Prometheus + Grafana + Alertmanager 单机监控（2C4G / 3~4k 活跃序列），主导定下 P99 计算口径（Micrometer 直方图 + sum by(le) 聚合、按接口拆分）与 40+ 条 P0~P3 告警规范及 runbook；针对 MySQL 设计行锁、长事务、表膨胀、慢 SQL 四维治理（sql_exporter + pt-query-digest），Redis 实现哨兵切换后自动跟随新主、Kafka 分消费 lag 与 broker P99 双层采集，使故障可一次下钻到接口、SQL 模板与 broker。

### 一、业务架构设计

- **领域建模与服务拆分**：基于事件风暴按变化频率、一致性边界与视角分离，将 MES 拆分为制造资源、设备管理、生产执行 3 个微服务（14 个限界上下文），以三段式不变式体系分层治理一致性边界，上下文回归缺陷较单体式方案下降约 70%，新上下文接入周期从 2 周缩短至 3 天。
- **跨服务事件协作（Outbox 事件骨干）**：业务状态与 outbox_event 同本地事务原子提交；聚合根仅返回领域事件、由应用服务编排 Outbox 写入（领域层零中间件依赖）；按聚合根 ID 分区保序，Producer 幂等发送确保重试不重复，13 个语义化 topic 承载近百个领域事件，四层限流（领取节流 / 全局令牌桶 / 按 topic 公平调度 / 在途上限）+ 自适应背压稳定兜住 2000+ 事件/分钟突发流量；物料多源事件驱动的齐套重算引入去抖合并、批量 BOM 导入场景重算次数下降约 90%，实现跨服务协作零分布式事务，支撑工单下达→过点→完工跨 6+ 上下文异步解耦。

### 二、性能优化

- **高并发采集接入与消费管道**：基于 Kafka 按采集源分区保序，Producer 开启幂等与攒批压缩，稳定承接全车间峰值 2K 报文/秒；单条 ≤1MB 报文经 topic 级调限全量直连，在途上限 + 缓冲水位背压确保补传洪峰瞬间零 OOM；平台接入侧 msg_id 去重 + 设备时间窗乱序矫正消化重连补传洪峰（命中率 99.9%），落库与分发解耦，依托 Kafka 重投与消费端幂等兜底可靠性；温层攒批落库 P99 < 1s，热层 Redis 覆盖写支撑过点查询 ≤200ms，consumer pause 背压以延迟换不丢，稳定支撑实时 SPC。
- **过点全链路优化（写侧原子事务 + 读侧低延迟）**：写侧将过点记录、放行决策、路线推进、工单进度、测试结果五聚合同事务原子提交（主事务仅写本地 DB），配合上下文内 CQRS 写读分离与采集/业务双链路架构级分流，使“过站瞬间”成为不受高频采集冲击的原子业务事实；读侧工艺版本与物料/工装按工单下达时绑定的不可变版本快照读取，从机制上消除配置缓存一致性窗口，设备可用性、质量门禁、齐套状态等实时状态投影本地缓存化并以降级 REST 兜底，实现过点全链路 P99 ≤ 200ms、缓存命中率 > 99%，换班高峰 50 工位并发扫码无超时雪崩。

### 三、高可靠保障

- **消息可靠投递**：Outbox 六状态机（PENDING→PUBLISHING→SENT，失败指数退避重试、耗尽入死信可修复重放、PUBLISHING 超时恢复重发）保障至少一次投递，消费端 event_id 幂等且与业务处理同事务，事件投递成功率 99.99%、宕机恢复零丢失、重复处理率 < 0.01%，业务流在宕机下不断裂、不重复。
- **业务级防错**：构建设备可用性 9 维阻塞合取重算（重算幂等率 100%）、CRITICAL 故障同事务同步停机（延迟 < 50ms）、工单产品流水号等量预发实现超产物理门禁（拦截率 100%）与状态机终态拒收，从源头杜绝带病设备流入生产与超产错版投产。
