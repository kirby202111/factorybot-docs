## 一、问题定义：三分法与本项目的真实风险

### Q1. 雪崩、击穿、穿透分别是什么？在本项目各对应什么？

**A**：三者触发条件不同，别混成"缓存没命中"一句话：

| 问题 | 机制 | 本项目对应场景 | 权威文档里的措辞 |
|---|---|---|---|
| **击穿** | 单个**热点 key** 失效瞬间，并发请求同时回源 | 换线瞬间某工单/工艺版本缓存刚过期，多个过点终端并发 REST 查源上下文 | Redis §2.4「缓存击穿」行 |
| **雪崩** | **大批 key 同时失效**（批量工单同时下达/同时刷新导致 TTL 集中到期）**或缓存整体不可用**（Redis 重启、主从+哨兵整体故障） | 换班开机集中起过点；Redis 重启后六个校验缓存全空 | Redis §2.4「缓存雪崩」「冷启动 miss 风暴」「Redis 故障」三行 |
| **穿透** | 请求的 key **永远不存在**，每次都打到源 | 异常 SN / 不存在的 `work_order_id` 反复 miss，六维度校验全落空 | Redis §2.4「缓存穿透」行 |

补充一个术语边界：Redis 整体故障在 Redis 实现说明 §2.4 里被单列为「**Redis 故障 = 过点主路径不可用**」，因为路线 B 下 Redis 是**主路径一等依赖**而不是旁路加速——所以它比普通缓存雪崩更严重，答案不是"重建缓存"，而是 §2.5 的降级链（Q12）。

### Q2. 为什么说雪崩在这个项目是真实风险，不是背八股？

**A**：三个可追溯的依据：

1. **触发真实**：早班开机、午餐复工、集中换线，全场几十~上百工位**同时**起过点，缓存未预热（生产执行 §9.3、制造资源 §5.1）。
2. **放大倍数可算**：均值约 6 TPS、峰值 50~60 TPS（简历 §三，推算值），每次过点**并行校验六维度**（Redis §2.1 六缓存表）。全 miss 时回源不是 50 QPS，而是几百 QPS 量级，且全部砸向制造资源 / 设备台账 / 质量 / 工单上下文的 MySQL。
3. **SLA 口径有坑**：降级 REST ≤500ms 是**单次**设计目标，批量回源的排队延迟会瞬间吃掉 ≤1s 全链路预算（制造资源 §5.1 原话："降级 ≤500ms 是单次 SLA"）。所以"有降级链"不等于"降级链能扛住尖峰"。

### Q3. 本项目和互联网缓存题最大的不同是什么？

**A**：**降级语义相反**。互联网读场景缓存挂了常走 fail-open（返回兜底内容/旧值，保可用）；MES 过点是**防错门禁**，缓存 miss + REST 失败一律 `CheckpointBlocked(RouteCacheMiss / EquipmentCacheMiss)` **保守拦截**（INV-CX-05，Redis §2.5、架构 QA Q11.1）。误拦只停线几秒并留 `blocking_reason` + `failed_checks[]` 可追溯、有 `OverrideCheckpoint` 授权放行逃生通道；误放会流出不良品。

这条约束决定了后面几乎所有取舍：**宁可慢、宁可拦，不可拿不确定数据放行**。注意别和 [ADR-08](../架构设计v2/00-架构决策记录ADR.md) 的 Agent 侧混淆——那里熔断后是 **fail-open = 不给建议，绝不阻塞人工界面**，与过点侧 fail-closed 恰好相反，是两个边界的两套语义。

另一个根约束：缓存是**读优化投影、不是事实源**（Redis §1.3「三不」），丢失可重建；所以"缓存持久化/AOF 兜底"在本项目反而不是重点（§8.3 明确过点校验缓存持久化**关闭**，纯缓存丢失回源）。

## 二、最新设计：路线 B 的六层防线

### Q4. 一句话讲清整套方案？

**A**：**共享 Redis 一份投影 + 事件刷新 + TTL 兜底 + 精确失效，把三类失效分别用最便宜的手段挡住，最后用限流与保守拦截给权威源兜底**。分层如下：

```text
写入侧（一致性）
  源上下文 Outbox 同事务发事件 → CacheRefreshService(source_event_id 幂等)
  → 覆盖写共享 Redis（刷新 TTL），失败不阻塞过点
读取侧（正常路径）
  过点 → Redis pipeline 合并六维查询 → 命中则判定
  Redis miss → REST 查源上下文 → 回填 Redis（带 TTL）→ 判定
防失效（雪崩 / 击穿 / 穿透）
  TTL 30min 兜底 + ±20% 抖动 + 分批/启动预热     ← 雪崩
  SETNX 单飞 + §6.2 令牌桶 + pipeline            ← 击穿
  空值缓存（短 TTL）+ 前置 SN/工单有效性校验     ← 穿透
失效粒度
  rule_id + version 粒度缓存键，弃用只精确移除该条目，不整批失效
过载保护
  Redis + Lua 分布式令牌桶（起步即启用）；故障时降级本地令牌桶（宽松）
兜底（fail-closed）
  Redis 不可用 → REST 直查源上下文 → 失败则 CheckpointBlocked 保守拦截
```

依据：Redis 实现说明 §2.4/§2.5/§6.2/§8.3/§10、Kafka 全景 §3 模式 A 重难点 1~4。

### Q5. 载体为什么是 Redis 共享一份，而不是 Caffeine / 多级缓存？

**A**：这是 **2026-07-28 拍板**的架构判断（Redis §2.2，附录 A「翻转原 Caffeine 为主」）：

| 路线 | 优势 | 劣势 | 状态 |
|---|---|---|---|
| A. 进程内 Caffeine 为主 | 亚毫秒读、零网络 RTT、无外部依赖 | 多实例内存冗余；冷启动/事件延迟窗口内实例间不一致 | ⛔ 备选未选用 |
| **B. Redis 共享为主** | 实例间天然一致（共享一份）；无内存冗余；多实例 miss 风暴天然吸收 | 每次过点 6 次 Redis RTT（pipeline ~1ms，在 ≤1s SLA 内充裕）；Redis 成为吞吐瓶颈与**故障域** | ✅ **v1 采用** |
| C. Caffeine + Redis 二级 | 兼顾低延迟与一致性 | 复杂度高；两级一致性需事件广播 + 失效 | ⛔ 备选未选用 |

决策原文：「**不引入 Caffeine 进程内缓存**」（§2.2/§2.5/§10/§11），连"两级 Redis 启用阈值"都已作废（附录 A）；Redis 故障时是 **REST 直查，无 Caffeine 兜底**。

**面试要主动讲代价**：选 B 换来的确定性，代价是把 Redis 抬成了过点主路径一等依赖。所以必须配 §6.2 起步即启用的分布式限流、§2.5 REST 降级链、主从+哨兵自动故障转移——这三样不是可选项，是选 B 的**对价**。顺带一提，[MySQL 配置说明](../实现说明/基础设施/MySQL配置说明.md) 的 `cache-enabled: false`（默认关闭二级缓存，避免一致性问题）也是同一取向：本项目对"多一层缓存"很克制。

### Q6. 六层防线分别解决什么，哪一层是本项目的特色？

**A**：

| 层 | 机制 | 解决 | 状态 |
|---|---|---|---|
| ① 写入侧 | 事件驱动覆盖写 + `source_event_id` 幂等 + `rule_id+version` 精确失效 | 乱序/重复刷新、整批失效 | ✅ |
| ② 读路径 | pipeline 合并六维查询；miss → REST → 回填 | 常态延迟、偶发 miss | ✅ |
| ③ 过期 | TTL 30min 强制回源 + ±20% 抖动 | 事件丢失陈旧、整批到期 | ✅（抖动落地 🟡） |
| ④ 回源合并 | Redis SETNX 单飞 + 令牌桶 | 热点 key 并发回源 | ✅ 机制 / 🟡 细节 |
| ⑤ 过载 | Redis + Lua 分布式令牌桶；故障时本地宽松令牌桶 | 回源速率超过源容量 | ✅ |
| ⑥ 兜底 | REST 失败 → `CheckpointBlocked` 保守拦截 | 源被打挂时防错放 | ✅ |

最有项目特色的是 **⑥ fail-closed** 与 **① 版本化精确失效**：`routeVersion` 快照锁定历史追溯（Redis §2.3），工艺/规则是版本化不可变对象，缓存键带版本，读到要么是当前生效版、要么明确 miss 回源，**不存在"半新半旧"**（架构 QA Q11.1）。市面上"缓存不一致"的多数噩梦，在这里被 DDD 的版本模型从源头削掉了。

## 三、按场景拆解：每个问题用最便宜的手段

### Q8. 整批 key 同时过期（典型雪崩）怎么治？

**A**：两招，一招消灭触发条件，一招压低重建峰值：

- **TTL 加随机抖动（基准 30min ±20%）**：让批量工单/规则的到期时刻散开，雪崩失去"同时"这个前提（Redis §2.4 雪崩行）。基准值已由附录 A 拍板，**不要再自己编一个"base TTL 🔴"**。
- **分批预热**：新版本批量生效 / 重建时按批回填，而不是一次性全量刷新把源和 Redis 同时打满（Redis §2.4）。批次大小与并发 🔴 交运维按实测定。
- 第三重保险是**事件刷新覆盖写尽量在 TTL 到期前完成**（§2.4 击穿行）——常态下热点 key 根本不该等到期。

**为什么不用"永不过期 / 逻辑过期"**：见 Q17。一句话：本项目靠 TTL 到期**强制 REST 回源**兜"事件丢失导致投影永远停在旧值"，把 TTL 拿掉就等于把一致性自愈机制拿掉，防错场景不能接受。

### Q9. 热点 key 失效瞬间并发回源（击穿）怎么治？

**A**：Redis §2.4 击穿行给了三条，按作用顺序：

1. **互斥锁（Redis `SETNX` 单飞）**：同一 key 只放一个请求回源，其余**读旧值 / 等**。注意这是**分布式单飞**——所有过点实例共享同一把锁；进程内 `Map<key, Future>` 只能合并单实例的并发，在多实例部署下仍会按实例数放大回源。
2. **§6.2 令牌桶收敛**：即便单飞被击穿（锁超时、key 分散），回源 QPS 仍被压在源容量之下。
3. **事件刷新覆盖写 + pipeline**：常态不产生 miss；六维查询合并为一次 Redis 往返，降低热点期间的 Redis 侧压力。

**必须主动答的追问**：「其余读旧值」会不会和 Q3 的 fail-closed 冲突？会，所以要**按维度分级**（架构 QA Q11.1）：只有**弱一致维度**（如 `KitStatus` 提示性齐套、工艺版本这类不可变版本快照）允许在 TTL 内读旧值；**强防错维度**（设备可用性、质量门禁）不能拿旧值放行，应当等待单飞结果或转 REST 精确回源，仍失败则 `CheckpointBlocked`。这个分级是当前设计里需要落地时显式编码的约束，🟡 上线前验证。

### Q10. 不存在的 key 反复穿透（穿透）怎么治？

**A**：Redis §2.4 穿透行三层，成本从低到高：

1. **前置校验**：过点先校 SN / `work_order_id` 有效性，把明显非法请求挡在缓存之前。
2. **空值缓存（null placeholder，短 TTL，文档举例 60s）**：主路径。同一个不存在 ID 的重复请求在短窗口内直接命中占位符，不打源；短 TTL 保证 ID 后来真的创建时不会被长期挡住。具体 TTL 🔴 按真实 ID 分布实测。
3. **布隆过滤器前置判存在性**（工单/设备 ID 集合）：文档列为可选项。**注意别把两处布隆混为一谈**——§4 的「0.1% / ≤1.1GB / 滚动按天分桶」是**采集 `msg_id` 去重的预案，非 v1 启用**，不是过点穿透场景的既有配置。若未来在过点穿透侧启用布隆，参数与治理需单独拍板 🔴。

### Q11. 冷启动 / 缓存大面积失效：`earliest` 补投影预热到底怎么用？

**A**：仓库里有**两条互补**的预热路径，别只讲一条：

| 路径 | 出处 | 机制 | 适用 |
|---|---|---|---|
| **启动预热回填 Redis** | Redis §2.4 冷启动行 | 加载活跃工单 / 当前生效工艺版本 / 在制设备可用性，直接回填共享 Redis；配合分批预热 | 新实例启动、Redis 重启后快速恢复"当前生效状态" |
| **新消费组 `auto-offset-reset=earliest` 补投影** | Kafka 全景 §3 模式 A 实施重难点 2、§9 原则 5、Outbox §13②、Q11、简历 §三 | 换一个没用过的 `group.id`，从 topic 当前保留的最老消息全量重放，把读侧投影历史完整重建 | 读侧投影整体重建、投影逻辑大改后的全量重建 |

`earliest` 的语义依据要讲准：[Kafka 配置说明](../实现说明/基础设施/Kafka配置说明.md) §6 的**通用默认是 `latest`**，`earliest` 是"需要补投影或从头追赶的消费者"的特例；Outbox §8.1 因业务契约事件需补投影，把消费侧默认设为 `earliest`；而设备热层重建走的是 `latest` + 回溯近 5min（Redis §3.5，附录 A 落定 5min）——**三处是分工，不是互相矛盾**。

**代价要主动复盘（加分项）**：

1. **就绪时间 ∝ topic 历史长度**：`retention.ms` 7~30 天（Kafka 配置说明 §3），重放窗口越久，预热越慢，运维上难承诺"几点前预热完"，赶不上开线潮就等于没预热。
2. **消费组生命周期**：每次重建换 `group.id`，`__consumer_offsets` 堆积废弃组、每次触发 rebalance；组名事实上成了隐式版本号。
3. **与幂等耦合**：`consumed_event(event_id + consumer_group)` 与业务表同事务落库，重放时已处理事件被幂等跳过——**安全，不会重跑业务、产生重复副作用**；但"修了投影逻辑要重跑"必须换组（Outbox §13③，"幂等保证不重复执行，重放想重复执行必须主动绕过幂等"）。
4. **追赶窗口读"半成品"**：见 Q27。

### Q12. Redis 整体故障（比雪崩更严重）怎么办？

**A**：走 §2.5 故障降级链，顺序不能乱：

```text
Redis 不可用 → REST 直查源上下文（六维各自降级查询）
  → 降级查询经 §6.2 令牌桶限流（Redis 同样不可用时降级本地令牌桶，宽松）
  → REST 失败 → CheckpointBlocked(RouteCacheMiss/EquipmentCacheMiss) 保守拦截
```

配套：主从 + 哨兵自动故障转移缩短不可用窗口（§2.4、附录 A 部署形态落定）；**过点校验缓存持久化关闭**（§8.3），因为它是纯缓存，事实源在 MySQL 聚合 + Kafka 事件流，丢失回源即可，开 AOF 只是给"可重建的派生数据"增加恢复复杂度。

这里有个**要主动点破的自指问题**：限流本身也跑在同一个 Redis 上，Redis 整体挂时 §6.2 分布式令牌桶一并失效，所以权威文档给的兜底是「**本地令牌桶（宽松）+ 下游熔断/背压**」（§6.2 重难点）。本地宽松限流保护力弱于分布式精确限流，因此真正兜住源上下文的最后一道仍是 **fail-closed 保守拦截**——这恰好说明为什么"熔断"值得作为上线前补强项（Q14）。设备热层同理但语义不同：超时计 `EquipmentDataTimeout`（INV-10）。

### Q13. 事件丢失 / 滞后导致缓存陈旧，和雪崩有什么关系？

**A**：这是"防雪崩"最容易被忽略的隐藏面——**重建出来的投影如果对不上权威源，预热得再快也没用**。Redis §2.4 与架构 QA Q11.1 给了五层：

| 层 | 失效模式 | 机制 |
|---|---|---|
| ① 乱序/重复 | 旧事件后到覆盖新值 | `asset_id + version` 乐观锁 + `source_event_id` 去重；无变化不发事件 |
| ② 事件丢失 | 投影永远停在旧值 | **TTL 30min 强制 REST 回源**（这也是不能"逻辑过期"的原因） |
| ③ 在途窗口 | 变更已发生、事件在路上 | 关键变更后短暂**双读取严**（🔴 强防错场景启用、常态关） |
| ④ 回源失败 | 源超时/不可用 | fail-closed 保守拦截，降级查询不进过点主事务（BIZ-05） |
| ⑤ 长期漂移 | 累积偏差 | 投影定期与聚合根对账；可幂等重放重建 |

再加两条结构性防线：版本化不可变对象 + `rule_id+version` 缓存键（不整批失效）；以及"该同步的地方源头就同步"——设备可用性的几类硬阻塞由台账在**同一本地事务**内同步更新投影，根本不过 Kafka 最终一致窗口（台账 INV-CX-08）。一致性窗口的权威表述见 Kafka 全景 §5.3：① miss 降级 REST ② 关键变更后短暂双读 🔴 ③ 接受最终一致（过点记录锁 `routeVersion`）。

### Q14. 限流和熔断各防什么？仓库里的状态怎么说清？

**A**：两者正交，防两种死法：

| | 限流 | 熔断 |
|---|---|---|
| 防什么 | **慢死**：回源速率超源容量，把源拖垮 | **快死 / 级联**：源持续失败，每次还傻等 500ms 超时 |
| 手段 | Redis + Lua 分布式令牌桶（✅ 已落定，§6.2 起步即启用）；Redis 故障降级本地令牌桶（宽松） | 失败率/慢调用比例超阈 → 开路快速失败 → 半开探测恢复 |
| 维度 | 速率维度（与分区内顺序正交，Outbox §9.5 / Kafka 全景 §9 原则 11） | 状态维度 |
| 状态 | ✅ 已落定 | ❌ **gap**（制造资源 §5.1、生产执行 §9.3）；Redis §6.2 仅在"限流是自律非强制，需下游自我保护"处提及「熔断/背压」 |

阈值（失败率窗口、半开间隔、最小请求数）🔴 交运维按实测定；太灵敏会把源侧偶发抖动放大成大面积拦截，太钝则保护不了——**而本项目的拦截是停线，代价远高于互联网返回兜底页**，所以熔断阈值必须比常见教程更保守。面试被追问"简历不是写了限流熔断吗"，按本文 §7.3 的差异登记诚实作答。

## 四、市面常见方案优劣势对比（展开讲解）

> **对比方法**：不是"哪个方案更高级"，而是逐层问「**这一层解决不了的下一个问题是什么**」。每节先列市面做法的机制/优势/劣势，再讲本项目取舍（附权威章节），最后给一句追问话术。所有第三方方案**非本仓库依赖**，引用仅为对照。

### Q15. 缓存载体：本地缓存、多级缓存、共享缓存、读模型、分片集群怎么选？

| 市面做法 | 机制 | 优势 | 劣势 / 典型坑 | 适用 |
|---|---|---|---|---|
| **进程内缓存**（Caffeine / Guava / Ehcache） | 每实例内存一份，miss 回源 | 亚毫秒、零网络 RTT、无外部依赖、缓存故障不波及别处 | 多实例内存冗余；实例间不一致窗口；缓存容量受堆限制；**每个实例都要各自回源**，miss 风暴按实例数放大 | 单体 / 少实例、允许最终一致 |
| **多级缓存**（Caffeine L1 + Redis L2，或 CDN + 本地 + 分布式） | 依次查 L1→L2→源 | 低延迟 + 共享一份，热点读几乎不出进程 | 两级一致性需事件广播/失效；失效风暴、脏读排查难；**多一个故障域**；内存与运维成本叠加 | 读多写少、超高频热点、容忍秒级不一致 |
| **共享分布式缓存**（Redis / Memcached） | 所有实例读同一份 | 天然一致、无冗余、miss 风暴天然吸收；容量与实例数解耦 | 每次读一次网络 RTT；缓存成为吞吐瓶颈与全局故障域；需 HA 与限流配套 | 多实例、一致性优先 |
| **本地读模型 / 物化视图**（MySQL 表、CQRS 投影） | 事件驱动写表，读直接查表 | 重启不丢、可查询可关联、无"缓存整体失效"概念 | 写放大、表结构维护、延迟高于内存；投影重建与一致性窗口仍在 | 查询频率不高、需持久化/追溯 |
| **Redis Cluster / 分片 + 多副本** | 数据分片、水平扩展 | 容量与吞吐可扩展、故障域分片隔离 | 运维复杂度大幅上升；跨槽 pipeline/事务受限；小集群收益不抵成本 | 超单机内存 / 超高吞吐 |

**本项目的取舍（✅ 已拍板）**：过点校验六缓存选**共享 Redis 一级**（Redis §2.2 路线 B）；Caffeine 与 Caffeine+Redis 二级**明确不选**，理由就是多级缓存的"两级一致性 + 事件广播 + 失效"复杂度，且本项目靠 `source_event_id` 幂等 + 覆盖写 + 版本键已把一致性做简单了，不值得再叠一层。pipeline 6 查 ~1ms，在 ≤1s 全链路 SLA 内余量充裕，**省下的 RTT 换不来架构简洁性**。

读模型不是不用，而是**按场景限定**：`WipUnit` 位置快照走 MySQL 读模型（§5.2 路线 A 已拍板，理由"车间可视化查询秒级/分钟级，MySQL 够用，不额外投影 Redis 加速"）。把它外推到过点六缓存是未经授权的推广——可视化低频与过点毫秒级 SLA 不是一类负载。Cluster 同样：附录 A 定的是**主从 + 哨兵**（≤10 线 / 单 MES），超单机内存再评估。

**追问话术**：「多级缓存不是不好，是它的收益（省 1ms 级 RTT）小于代价（两级一致性 + 多一个故障域），而我们的预算是 1s，所以拍板选共享一份」。

### Q16. 缓存更新模式：Cache Aside / Read-Through / Write-Behind / 延迟双删，为什么本项目是事件驱动覆盖写？

| 市面做法 | 机制 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|
| **Cache Aside**（旁路缓存） | 读：miss 读 DB 回填；写：更新 DB 后删缓存 | 简单、无额外组件；事实源永远在 DB | 并发读写下的脏读经典问题；"先删缓存还是先更新 DB"两难；删除失败留脏数据 |
| **Read/Write Through** | 应用只跟缓存层交互，由缓存组件回源 | 应用层逻辑干净 | 需要缓存组件支持；跨服务事实源时组件无法代写多个上下文 |
| **Write Behind**（异步回写） | 先写缓存，异步刷 DB | 写吞吐高 | 缓存故障丢数据、一致性最弱；事务型系统禁用 |
| **延迟双删 / 订阅 binlog 失效** | 写前后各删一次，或 CDC 驱动失效 | 缓解 Cache Aside 脏读 | 延迟时间难定；只是"删"，下次读仍要回源，尖峰时正是雪崩触发器 |
| **事件驱动覆盖写**（本项目） | 源上下文 Outbox 同事务发事件 → 消费侧幂等 → **覆盖写缓存并刷新 TTL** | 读侧几乎不产生 miss；跨服务解耦；失效粒度可控（`rule_id+version`）；事件失败还有 TTL + REST 双兜底 | 依赖事件链路可靠性；存在秒级滞后窗口；需要幂等表与重放设计 |

**本项目的取舍（✅）**：六个缓存的事实源分属**不同限界上下文**（制造资源 / 设备台账 / 质量 / 工单），生产执行服务只是读投影持有者，根本没有权限"更新 DB 后删缓存"——Cache Aside / Write Through 在跨服务边界上不成立。所以走 Kafka 全景 §3 模式 A「发布—缓存刷新」投影：写侧 Outbox 同事务保证"新版本生效 + 旧版本失效 + 通知下游"原子（INV-CX-02），读侧 `CacheRefreshService` 用 `source_event_id` 去重后覆盖写（Redis §2.5）。事件刷新失败不阻塞过点，靠 TTL 30min 强制回源 + REST 降级兜底（§2.4）。

**关键差异要讲透**：市面方案多数是「**失效**（删 key）」，本项目是「**刷新**（覆盖写新值）」。删 key 会把回源压力推给下一个请求——在换线尖峰时这正是击穿/雪崩的引信；覆盖写则是把回源成本前移到低频的配置变更时刻。**写少读多的配置型主数据，用刷新比用失效便宜得多**。

### Q17. 过期策略：固定 TTL / 随机抖动 / 逻辑过期 / refreshAfterWrite / 主动失效怎么选？

| 市面做法 | 机制 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|
| **固定 TTL** | 统一过期时间 | 最简单、行为可预测 | 批量写入 → 同时到期 → 雪崩的标准成因 |
| **TTL 随机抖动**（本项目） | base ± 随机比例 | 一行配置消灭同步性；对业务零侵入 | 到期时刻不再可预测；只能缓解、不能消除大面积故障导致的全清 |
| **逻辑过期 / 永不过期** | value 内带逻辑过期时间，物理不删；发现过期则异步刷新、先返回旧值 | 热点 key 永不 miss，击穿近乎消失；读延迟稳定 | **返回旧值**是防错场景的红线；需要额外刷新线程；事件永久丢失时旧值永不被纠正；内存需治理 |
| **refreshAfterWrite**（Caffeine） | 命中时异步刷新 | 热点无感刷新 | 绑定进程内缓存组件；本项目已排除 Caffeine，附录 A 明确 **refreshAfterWrite 作废** |
| **主动失效 / 精确删除** | 变更时按 key 删/改 | 一致性最好、无等待窗口 | 依赖事件可靠到达；删除范围过大 = 人为制造雪崩 |
| **影子键 / 双 key 切换** | 新版本写 v2，就绪后原子切指针 | 重建期间无半成品窗口 | 双份内存 + 切换一致性 machinery；低频事件不值这个复杂度 |

**本项目的取舍（✅）**：**固定 TTL 30min（兜底）+ ±20% 抖动 + 事件刷新 + `rule_id+version` 精确失效**四件套（Redis §2.4/§2.5、附录 A、Kafka 全景 §3 重难点 3）。TTL 在这里不是"缓存寿命管理"，而是**防事件丢失的自愈机制**——到期强制 REST 回源，把"投影永远停在旧值"变成"最多陈旧 30min 且可监控"。因此"逻辑过期/永不过期"在本项目**⛔ 不选**：它用"永远返回旧值"换零 miss，而 MES 强防错维度宁可拦截也不能拿旧值放行（Q3）。影子键同理：Redis 重启是低频事件，为它常备双轨 machinery 的复杂度大于收益，重建期间用降级链（Q12/Q27）覆盖。

**追问话术**：「我们不追求零 miss，追求的是 miss 之后不会误放。TTL 是我们的一致性兜底，不是性能参数，所以不能拿掉」。

### Q18. 击穿防护：SETNX 单飞 / 进程内 singleflight / 请求合并 / 限流，差别在哪？

| 市面做法 | 并发合并范围 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|
| **进程内 singleflight**（Go `singleflight`、Caffeine `LoadingCache`） | 单实例内同 key | 零额外依赖、实现几行代码；本地合并且响应快 | **跨实例不合并**，N 个实例仍最多 N 次回源；实例重启/扩缩容时合并效果重置 |
| **分布式单飞**（Redis `SETNX` 互斥锁，本项目） | 全部实例同 key | 跨实例塌缩成 1 次回源；与共享缓存同一组件 | 锁超时/续期、锁粒度、死锁与"其余请求怎么办"要设计；Redis 故障时单飞也失效 |
| **热点探测 + 永不过期 / 提前异步续期** | 从源头不产生 miss | 无锁、无等待 | 需热点识别；与 TTL 兜底冲突（Q17） |
| **请求合并 / pipeline / 批量接口** | 把多个 key 合成一次往返 | 降低缓存与网络压力 | 不减少回源次数，只减少往返；需源侧支持批量 |
| **限流**（令牌桶/漏桶/滑动窗口） | 不合并，只削峰 | 实现成熟、可跨实例；对任何 key 分布都有效 | 被限的请求要排队/拒绝；单独用不能把 N 次回源变 1 次 |

**本项目的取舍（✅/🟡）**：Redis §2.4 击穿行选**分布式 SETNX 单飞 + §6.2 令牌桶 + pipeline**，三条同时存在且各管一段：单飞管"同 key 的 N→1"，令牌桶管"不同 key 同时 miss 的总速率"，pipeline 管"六维查询的 Redis 往返数"。因为载体是共享 Redis（Q15），进程内 singleflight 在这里收益有限——多实例才是常态。**"其余读旧值/等"必须按 Q9 的维度分级**，不能一刀切读旧值。

**别被追问噎住的一点**：§6.3 说"MES 业务建模基本不需要 Redis 分布式锁"，指的是**业务并发控制**（排产槽位、可用性重算、单活跃通道已由聚合内事务 / DB 唯一索引 / 乐观锁解决）；这里的 SETNX 是**缓存击穿的技术层单飞锁**，不协调任何业务状态，两者不矛盾。

**追问话术**：「单飞解决的是并发放大，限流解决的是总量过载，两个正交；少任何一个，另一种死法都还在」。

### Q19. 冷启动与重建：批量快照 / Kafka 重放 / 分批预热 / 懒加载 / 持久化与 HA，怎么权衡？

| 市面做法 | 就绪时间 | 运维成本 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|---|
| **批量快照 / 全量接口一把加载** | 秒级（一次批量 REST） | 低（若源侧已有批量接口） | 直接给"当前生效状态"，语义最直观；可全量到位再开流量，无半成品窗口 | **要求源侧提供批量接口**（本项目源上下文分散在 4 个服务，无统一批量接口）；大批量同样会打满源与网络；快照与增量事件之间的衔接窗口要处理 |
| **Kafka `earliest` 全量重放**（本项目正式方案之一） | ∝ topic 保留期（7~30 天），不可控 | 中高（组管理、rebalance、幂等耦合） | 复用既有事件骨干；能重演完整状态机；修了投影逻辑可换组重跑 | 就绪慢；追赶窗口是半成品；组名变隐式版本号；单纯重放**修不了投影逻辑 bug**（Outbox §13③） |
| **分批 / 启动预热回填**（本项目正式方案之一） | 可控（按批） | 低 | 只加载"当前生效状态"（活跃工单 / 生效工艺版本 / 在制设备可用性），不重演历史；可与事件增量衔接 | 需要枚举"当前生效集合"；批次大小/并发 🔴 待实测 |
| **懒加载 + 限流**（不预热） | 无 | 零 | 实现最省 | 尖峰全部回源，正是本项目要防的场景；≤500ms 是单次 SLA，批量排队会吃掉 ≤1s 预算 |
| **缓存持久化 RDB/AOF** | 重启加载后较快 | 中 | 缩短冷启动空窗 | 恢复的是**可能过期的旧投影**；防错场景仍需回源校验；本项目 §8.3 明确关闭缓存持久化 |
| **双集群 / Cluster / 异地多活** | 故障切换快 | 高 | 把"整体不可用"概率压到很低 | 成本与一致性代价大；附录 A 定主从+哨兵（≤10 线），Cluster 属超规模再评估 |

**本项目的取舍（✅）**：**启动预热回填 + `earliest` 补投影 + 降级限流**三者并存（Redis §2.4、Kafka 全景 §3 重难点 2、简历 §三）。旧版问答把"批量快照"升为冷启动主路径、把 `earliest` 降为兜底，**仓库里没有这个拍板**：批量快照只出现在制造资源 §5.1 被标「文档 gap」的补强建议里，且源侧批量接口并不存在；按 Q7 的口径应归为 ⛔/📐，不能说成主路径。

**为什么不全靠 AOF**：缓存是派生数据、事实源在 MySQL + Kafka（§1.3），"丢失即回源"在设计上就成立，为可重建的数据付持久化与恢复一致性的成本不划算（§8.3）。这也是"防雪崩"在本项目被简化成"**预热 + 限流 + 降级**"三件事的根源。

**追问话术**：「我们不做无缝重建，因为缓存不是事实源；重建期间慢但可用、不确定就拦截，比保缓存不丢更符合防错语义」。

### Q20. 穿透防护：空值缓存 / 布隆 / 布谷鸟 / 参数校验，怎么选？

| 市面做法 | 优势 | 劣势 / 典型坑 |
|---|---|---|
| **参数/业务前置校验** | 零成本，挡掉格式非法与明显不存在的 ID | 挡不住"格式合法但不存在"的 ID |
| **空值缓存**（本项目主路径） | 实现一行；对任意 ID 分布有效；短 TTL 自愈 | 占用 key 空间；恶意随机 ID 会撑大缓存（需配合 `allkeys-lru` 与短 TTL）；TTL 内新建同 ID 会被短暂误挡 |
| **布隆过滤器**（RedisBloom / Guava BloomFilter） | 内存极省、O(1) 判存在；适合超大规模 ID 集合 | **有误判**（误判只会放行到 DB，不会漏判）；**标准布隆不支持删除**，ID 失效/新增需重建或滚动分桶；需要与事实源同步维护；多一个组件与运维面 |
| **布谷鸟过滤器** | 支持删除、误判率相近、查询更快 | 实现与生态成熟度不如布隆；删除仍受容量/装填因子限制 |

**本项目的取舍（✅ 空值缓存 / 🟡 布隆可选）**：Redis §2.4 把空值缓存列为主路径，布隆只作"前置判存在性（工单/设备 ID 集合）"的可选项；§4 的布隆是**采集 `msg_id` 去重的预案且非 v1 启用**（附录 A：0.1% / ≤1.1GB / 按天滚动分桶）。别把这两处的角色与参数混用。本项目的 ID 集合规模（工单 / 设备台账）远不到"不用布隆就扛不住"的量级，且空值缓存对"不存在的 SN 反复扫"已经够用——**省一个组件比省一点内存重要**（与 §11 原则 7「Redis-first 但不滥用」同向）。

### Q21. 过载保护与降级语义：限流、熔断、舱壁、fail-open / fail-closed 怎么组合？

| 市面做法 | 防什么 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|
| **单机限流**（Resilience4j / Guava RateLimiter） | 单实例速率 | 无外部依赖、延迟极低 | 多实例下总配额 = 单实例配额 × 实例数，扩缩容即失真 |
| **分布式限流**（Redis + Lua 令牌桶，本项目） | 集群总速率 | 跨实例精确配额；与本项目共享 Redis 复用零新中间件 | Redis 故障时一并失效（§6.2 已给本地宽松兜底）；Lua 脚本正确性要单测 |
| **熔断**（Sentinel / Resilience4j 三态） | 下游持续失败导致的等待与级联 | 快速失败、半开自愈，避免"傻等 500ms" | 阈值敏感；**对 MES 而言开路 = 大面积拦截停线**，误判代价高；本项目 ❌ 未落定 |
| **舱壁 / 隔离**（独立连接池、信号量、消费组） | 故障不扩散 | 一条链路拖垮全系统的概率大降 | 资源划分与容量规划成本；[ADR-08](../架构设计v2/00-架构决策记录ADR.md) 四道舱壁即此思路（Agent 侧边界） |
| **背压**（consumer pause / 排队） | 上游过快 | 不丢请求，优于丢弃 | 延迟上升；需要上游可暂停（[重连补传洪峰处理方案](../实现说明/高频数据/重连补传洪峰处理方案.md) §5 用 pause 而非丢弃） |
| **fail-open 降级**（返回兜底/旧值/空建议） | 保可用 | 互联网读场景用户体验好 | **防错门禁禁用**：可能放行本应拦截的过点 |
| **fail-closed 保守拦截**（本项目） | 保正确 | 宁可停线，不流不良品；留 `blocking_reason` 可追溯 + 授权放行逃生通道 | 可用性代价；需要明确的运营处置流程 |

**本项目的取舍（✅ 限流 / ❌ 熔断 / ✅ fail-closed）**：§6.2 起步即启用 Redis 分布式令牌桶，故障降级本地宽松令牌桶 + 下游自我保护（熔断/背压）；Redis §2.5 + INV-CX-05 定 fail-closed。这里最值得讲的"反常识"是：**同一套熔断组件，在 Agent 侧（ADR-08）开路是 fail-open「不给建议、绝不阻塞人工界面」，在过点侧开路则必须收敛到 `CheckpointBlocked`**——熔断后的语义不是技术参数，是业务正确性决策。把两者混答，面试官一听就知道没分清边界。

### Q22. 重建期间的"半成品窗口"：影子读模型 / 版本水位线 / stale 标记 / 就绪探针，市面怎么做？

| 市面做法 | 机制 | 优势 | 劣势 / 典型坑 |
|---|---|---|---|
| **影子表 / 双轨切换** | 重建写新表，完成后原子切读指针 | 读侧永远看到完整快照 | 双份存储 + 切换一致性；低频重建不值 |
| **版本号 / 水位线单调校验** | 每个投影带 `projection_version`，拒绝低于本地版本的写入 | 滞后可度量、乱序可拒 | 需要事实源提供单调版本；跨 4 个源上下文统一水位线成本高 |
| **stale / lag 显式标记** | 证据或响应带 `freshness_lag_seconds`，调用方自行决策 | 不静默把旧数据当实时；实现轻 | 需要调用方配合；强防错维度仍需明确的兜底动作 |
| **就绪探针 / 按 key 判断** | 加载完成才切流量；或按 key 就绪度决定读投影还是降级 | 实现直接 | 全量就绪标志在分布式多实例下要共享；按 key 判断需要额外的就绪元数据 |
| **重建期间旧版本继续服务** | 旧读模型不下线，重建在旁路进行 | 读不中断、可回滚 | 旧版本持续陈旧，需要滞后标记配合 |

**本项目的取舍（✅ 已有 / 📐 演进）**：

- 过点校验缓存的现成答案是**降级链而非影子键**：重放追赶期间投影增量覆盖写、部分 key 就绪部分没有，未就绪的自然 miss → REST 降级 → 失败保守拦截（Redis §2.5）；设备热层重建期间"降级查温层（慢但可用）或保守拦截"（§3.4），具体走 `latest` + 回溯近 5min（§3.5）。**语义天然正确，不需要影子键**。
- 仓库里更成熟的成文设计在 [制造追溯-需求与实现效果](../制造追溯-需求与实现效果.md) §3.1/§4.4：「读模型可重建：从 Kafka 重放 + MES 只读 REST 补数，**重建期间旧读模型继续服务**」「位点落后超阈值：标 stale，证据带 `freshness_lag_seconds`」「不允许静默返回旧数据当成实时」。但要讲清**边界**：那是 Agent 侧追溯读模型（独立消费组、独立只读副本，ADR-08），不是过点校验缓存的已落地实现，只能作为 📐 演进借鉴。
- 架构 QA Q11.1 已把「没有投影序号/水位线单调校验」「没有显式 stale/lag 标记读路径」列为**已知缺口**——面试主动说出来，比被追问出来强。

### Q24. 明确不选什么，理由各一句？

| 不选 | 理由 |
|---|---|
| Caffeine / Caffeine+Redis 多级缓存 | Redis §2.2 拍板不选：两级一致性需事件广播 + 失效，收益（省 1ms 级 RTT）小于代价，且 ≤1s SLA 余量充裕 |

### Q25. 上线前怎么验证（不编实绩，只给验证项）？

**A**：四个混沌场景 + 一组指标，全部 🔴 阈值按实测拍板：

1. **冷启动**：清缓存起新实例，测启动预热与 `earliest` 重放各自的就绪时间、回源 QPS 曲线；验证就绪时间与 `retention` 窗口的关系。
2. **Redis 整体 down**：杀主，测哨兵切换窗口、降级链 QPS、本地宽松令牌桶实际保护力、权威源负载余量、恢复后切回时延。
3. **换班尖峰**：模拟百工位并发起过点，验证 SETNX 单飞把同 key 回源塌缩到 1 次、pipeline 六维往返数、抖动后是否还有到期尖刺。
4. **源侧异常**：注入延迟/错误，验证令牌桶削峰与（补强后的）熔断开路—半开—恢复行为；确认开路后一律收敛到保守拦截而非放行。

指标：缓存命中率（`redis_cache_hit/miss_total`）、降级 REST 次数（`redis_cache_fallback_rest_total`）、回源 QPS、保守拦截率、预热就绪时长、Redis 内存与 `evicted_keys`（Redis §9 可观测清单）。告警基线"命中率 <99% 持续"是**设计阈值**，不是实测结论。

## 六、被追问预案

### Q26. 降级 REST 把权威源也打挂了怎么办？

**A**：三层，顺序不能乱：

1. **前置**：令牌桶把回源 QPS 压在源容量之下；SETNX 单飞削掉同 key 并发；熔断（❌ 待补强）在源持续失败时快速失败，别每次傻等超时。
2. **兜底**：真挂了只能保守拦截——`CheckpointBlocked(RouteCacheMiss / EquipmentCacheMiss)`（INV-CX-05）；设备实时数据超时标 `EquipmentDataTimeout`（INV-10）。**停线风险是业务权衡，不是技术能消灭的**。
3. **善后**：拦截记录带 `blocking_reason` + `failed_checks[]`，`OverrideCheckpoint` 授权放行作为逃生通道（记录例外而非改原记录），恢复后无需数据修补——因为降级查询不进过点主事务，失败不产生半成品状态（BIZ-05）。

### Q27. 预热/重建期间读到"半成品"投影怎么办？

**A**：分两条路径答，别自创机制：

- **过点校验缓存**：按 key 判断——已就绪的读投影，未就绪的自然 miss → REST 降级 → 失败保守拦截（Redis §2.5）。事件刷新是覆盖写，不存在"写一半的 value"。**降级链本身就是半成品窗口的答案**，不需要影子键。
- **设备热层**：`latest` + 回溯近 5min 重建最新值；重建期间降级查温层（慢但可用）或保守拦截（Redis §3.4/§3.5）。
- **📐 借鉴（未拍板）**：制造追溯 §3.1「重建期间旧读模型继续服务 + `freshness_lag_seconds` 显式标注」——若未来给投影加 stale 标记，可以让"慢但可用"变成"慢且可度量"。这是 Agent 侧追溯读模型的成文设计，**不是过点缓存的既有实现**，说清边界反而是加分项。

### Q28. 既然 Redis 是全局故障域，为什么不把它从主路径拿掉？

**A**：这是拍板时已经付过的对价，正面答三层：

1. **为什么选它**：多实例一致性 + 无内存冗余 + miss 风暴天然吸收；pipeline 6 查 ~1ms，在 ≤1s 内余量充裕（§2.2）。换成进程内缓存，一致性与内存冗余问题会回到每个实例上。
2. **代价怎么补**：主从+哨兵缩短不可用窗口；REST 直查降级链保可用；起步即启用的分布式限流保护源；fail-closed 保守拦截保正确（§2.4/§2.5/§6.2）。
3. **诚实边界**：限流与缓存共用同一 Redis，整体故障时都失效，只能靠本地宽松令牌桶 + 下游自我保护；这就是「熔断」被列为上线前补强项的原因（Q14）。**不假装这个耦合不存在**，比强行说"多层兜底万无一失"得分高。

### Q29. 简历写了"限流熔断"，但你说熔断是 gap，怎么圆？

**A**：直说，别绕：「限流是方案里已落定的机制（Redis + Lua 分布式令牌桶，起步即启用）；熔断在设计文档里被列为上线前要补强/验证的项，实现状态我按文档口径说明，不把它当已上线的功能讲。面试里我把两者分别防什么、阈值为什么敏感讲清楚。」把 gap 说成 gap 是加分（制造资源 §5.4「讲法纪律」、生产执行 §9 同句）。仓库内部确有不一致（本文 §7.3），按最保守口径答不会错。

### Q30. Agent 侧那些缓存（语义缓存、答案缓存、熔断 fail-open）跟这篇有关系吗？

**A**：**没关系，别混**。本文只覆盖 MES 主体过点校验读侧缓存（Redis 实现说明文首「适用边界」已把 Agent/RAG Python 侧排除）。Agent 侧的工具结果/答案缓存按 `data_scope` 闸门策略化开关、`CURRENT` 一律跳过（[AgentToken 成本优化](../AGENT服务/AgentToken成本优化-设计与实现方案.md) §8），熔断后 fail-open（ADR-08），属另一套边界、另一套正确性语义。唯一可类比的是"读模型重建期间继续服务 + stale 标记"（制造追溯 §3.1），且只能作为 📐 演进借鉴。
