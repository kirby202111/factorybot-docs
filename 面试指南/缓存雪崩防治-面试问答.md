>
> **与既有文档错位**：闪光点文档把"批量预热 + 限流熔断 + 多级缓存"标为 gap（待补强），本文给出**补强方案本身**的设计与问答；本文不重复 Redis 场景选型论证（§2.2 已拍板路线 B），只讲缓存建成之后的防失效。

## 口径

- **已落定**（可直接讲机制）：降级链（Redis miss → REST 回填 → 失败保守拦截 INV-CX-05）、Redis + Lua 分布式令牌桶限流（Redis 实现说明 §6.2）、`WipUnit` 位置投影 MySQL 读模型模式（§5）、事件重放三场景与幂等语义（Outbox 设计方案 §13）。
- **gap / 待补强**（必须说"上线前需验证"，不能说成已实现）：批量预热、熔断、多级缓存（制造资源 §5.1、生产执行 §9.3 均标 ❌ 文档 gap）。
- **重设计建议**（本文提出，非已拍板）：载体分层调整（校验族读侧 = 进程内缓存 + 本地 MySQL 读模型）、singleflight、随机 TTL、批量快照加载替代 earliest 为主路径。

## 一、问题定义

### Q1. 缓存雪崩、击穿、穿透分别是什么？在本项目各对应什么场景？

**A**：三个词机制不同，别混：

| 问题 | 机制 | 本项目对应场景 |
|---|---|---|
| **击穿** | 单个**热点 key** 失效瞬间，并发请求同时回源 | 一条 ACTIVE 工艺路线被全场工位同时读到 miss |
| **雪崩** | **大批 key 同时失效**或缓存整体不可用 | 换班重启、Redis 重启/故障，热 key 全清 |
| **穿透** | 请求的 key 缓存里**永远不会有**（不存在的数据），每次都被击穿到源 | 扫码一个不存在的 SN/工单，防错校验六维度全 miss |

本项目主要风险是前两个；穿透顺手用"负缓存（短 TTL 缓存空结果）+ 保守拦截"解决（依据：制造资源 §5.1 场景同构、INV-CX-05）。

### Q2. 为什么说缓存雪崩在这个项目是真实风险，不是纸上谈兵？

**A**：有三个数字撑着：

- **触发是真实的**：早班开机、午餐复工、集中换线时全场几十~上百工位**同时**起过点，本地缓存未预热（生产执行 §9.3、制造资源 §5.1）。
- **量级不可忽略**：过点均值约 6 TPS、峰值 50~60 TPS（简历 §三），每次过点并行校验六维度（工艺路线/设备可用性/质量门禁/工单状态/齐套/首件，Redis §2.1）——全 miss 时回源压力是几百 QPS，且全部砸在权威源上下文（制造资源/设备台账/质量/工单）的 MySQL 上。
- **SLA 口径有坑**：降级 REST ≤500ms 是**单次** SLA，不等于批量命中的 SLA——批量回源的排队延迟会瞬间吃掉过点 ≤1s 总预算（制造资源 §5.1 原话："降级 ≤500ms 是单次 SLA"）。

## 二、原方案复盘：新消费组 earliest 补投影预热

### Q3. 原方案是什么？`earliest` 在其中起什么作用？

**A**：原方案（简历 §三"防缓存雪崩"、Kafka 全景 §实施重难点②）= **新消费组 `earliest` 偏移补投影实现缓存预热，降级查询配限流熔断**。

`earliest` 的语义：换一个没用过的 `group.id` + `auto.offset.reset=earliest`，Kafka 从该 topic 当前保留的**最老消息**开始全量重放，把读侧投影历史完整重建出来——即"预热"（依据：[Kafka 配置说明](../实现说明/基础设施/Kafka配置说明.md) 消费配置表、[业务事件 Kafka 配置说明](../实现说明/业务事件/Kafka配置说明.md) §消费配置、Outbox 设计方案 §13②）。

### Q4. 这个方案复杂在哪？（主动复盘自己方案的代价）

**A**：四个真实复杂点，面试主动讲出来是加分项：

1. **消费组生命周期管理**：每次重建换 `group.id`，`__consumer_offsets` 堆积废弃组、每次触发 rebalance。
2. **追赶窗口读"半成品"**：重放追赶期间投影是建一半的状态，读请求可能读到残缺投影——原方案没回答这个窗口怎么处理（见 Q13）。
3. **就绪时间不可控**：预热完成时间 ∝ topic 历史长度，运维上无法承诺"几点前预热完"，赶不上开线潮就是没预热。
4. **与幂等机制耦合**：重放被 `consumed_event(event_id + consumer_group)` 幂等跳过——安全，但也意味着"修了投影逻辑要重跑，必须换组"（Outbox §13③），组名变成隐式版本号。

### Q5. earliest 重放重建投影，会重跑业务、产生重复副作用吗？

**A**：**不会**。消费幂等表 `consumed_event(event_id + consumer_group)` 与业务表同事务落库，重放时已处理事件被幂等跳过——这正好避免重复副作用。但反过来说，**单纯重放也修不了投影逻辑的 bug**（想重跑必须换新 `consumer_group`，Outbox §13②③）。所以 earliest 重建是"安全但笨"的手段。

## 三、重新设计：按场景拆分，各用最便宜的手段

> 设计原则：缓存是**读优化投影而非事实源**（Redis 实现说明 §1.3"三不"），丢失本就可重建——所以重建/预热手段应该选**运维成本最低**的，而不是最"重"的。原方案的失误在于想用一个 Kafka 机制解决三个问题。

### Q6. 重新设计后的总览是什么？

**A**：一张表——每个场景一个最便宜的手段：

| 场景 | 触发 | 手段 | 增量成本 |
|---|---|---|---|
| 冷启动预热 | 新实例/新部署 | **批量快照加载**（一把 REST 拉全量 ACTIVE 数据）+ 事件订阅增量维护 | 一次批量调用 |
| 单点 miss | 稳态偶发 | **singleflight 回源合并** + **L1 进程内缓存** | 几行代码 |
| 缓存大面积失效 | Redis 重启 | **承认降级**：REST + 令牌桶限流 + 保守拦截，后台异步重建后切回 | 复用已落定降级链 |
| 整批过期 | TTL 整点到期 | **随机 TTL** 打散 | 一个配置 |
| 源过载 | 回源量超源容量 | **熔断** → 快速失败转保守拦截 | 复用限流体系 |

### Q7. 冷启动为什么改用"批量快照加载"而不是 earliest 重放？

**A**：三个理由：

- **就绪时间可控**：批量加载 = 一次批量 REST（秒级）；earliest 重放 ∝ topic 历史长度，可能几分钟到几小时，赶不上开线潮（依据：制造资源 §5.1 原话"一把加载 ACTIVE 路线/BOM/规则"）。
- **零运维负担**：不碰 `group.id`、不触发 rebalance、不存在重放与实时流量交织的窗口。
- **语义更直接**：预热要的是"当前生效状态"，批量接口直接给当前生效版；重放还要在消费侧重演历史状态机。

代价：依赖源侧提供批量接口；没有批量接口时才退化为 earliest 重放兜底。

### Q8. earliest 重放还留不留？留作什么用？

**A**：**留，但定位降级**——从"常规预热路径"降为"兜底重建手段"。两个场景才用它：① 源侧没有批量接口；② 投影逻辑大改需要全量重建（此时配合换 `consumer_group` 绕过幂等跳过，Outbox §13③）。平时不消耗它，也就没有组管理和追赶窗口的日常成本。

### Q9. 单点 miss 怎么治？singleflight + L1 缓存 + 随机 TTL 各自解决什么？

**A**：

- **singleflight（单飞）**：同一个 key 的并发 miss 只放**一个**请求回源，其余等待它的结果（进程内 `Map<key, Future>` 即可，key 粒度 = 缓存键，如 `route_id+version`）。**击穿的标准解法**，把"热点 key 失效瞬间的 N 个并发回源"塌缩成 1 个。
- **L1 进程内缓存（Caffeine）**：挡在 Redis/读模型前，回源量从 `QPS × key` 降为 `实例数 × key`——多实例 miss 风暴天然被摊薄（制造资源 §5.1"多级缓存（进程内+Redis）"同向）。一致性靠**事件驱动刷新**（各实例订阅各自刷）+ TTL 兜底，接受秒级窗口——这与 Redis 共享方案的最终一致语义相同，但**少一个故障域**。
- **随机 TTL**：base TTL ± 20% 🔴 抖动，消灭"同一批 key 整点整批过期"的同步性，雪崩失去触发条件。

### Q10. 缓存大面积失效（Redis 重启）怎么办？为什么要"承认降级"？

**A**：Redis 重启是**低频**事件，为它搭"无缝重建"的 machinery（影子键切换、双轨一致性）复杂度大于收益。正确姿势是承认降级、快速自愈：

1. 降级链**已经落定**：Redis 不可用 → REST 直查源上下文 → 令牌桶限流 → REST 失败则 `CheckpointBlocked` 保守拦截（Redis §2.5、INV-CX-05）。
2. 后台异步重建，建完切回——重建期间过点照常进行（慢但可用，不停线）。
3. 与设备热层的重建策略同构（`latest` + 回溯近 N 分钟，Redis §3.4），只是投影要的是全量状态。

### Q11. 投影载体为什么建议演进为"本地 MySQL 读模型"？和现有拍板矛盾吗？

**A**：把校验族六缓存的载体从"Redis 唯一载体"演进为 **L1 进程内缓存 + 本地 MySQL 读模型**：

- **重启不丢数据** → "缓存大面积失效"这个场景**直接消失**，不需要任何重建机制——从"防雪崩"变成"没有雪崩"。
- 与 `WipUnit` 位置投影**已落定**的模式一致（MySQL 读模型为主、不加 Redis，Redis §5）——不是新发明，是既有模式的扩展。
- Redis 保留给**设备实时热层**（跨服务共享写，进程内缓存替代不了，Redis §3）。

代价要讲清：事件 → MySQL 有写放大、读模型表要维护、查询个位数 ms（对 ≤1s SLA 够用，Redis pipeline ~1ms 的优势在 1s 预算里不关键）；多实例一致性同 Q9。

**口径**：当前拍板是路线 B（Redis 共享为主，Redis §2.2，2026-07-28）——这是"下一步演进/如果重来"的答法，**不是推倒重来**，更不是说已实施。

### Q12. 限流和熔断分别防什么？为什么两个都要？

**A**：两者正交，防的是两种死法：

| | 限流 | 熔断 |
|---|---|---|
| 防什么 | **慢死**：回源速率超过源容量，把源拖垮 | **快死/级联**：源持续失败，每次请求还傻等 500ms 超时 |
| 手段 | Redis + Lua 分布式令牌桶（**已落定**，§6.2；Redis 不可用时降级本地令牌桶宽松限流） | 失败率/慢调用比例超阈 → 开路快速失败 → 半开探测恢复 |
| 语义 | 速率维度（不改变分区内顺序，与 Outbox 限流同构） | 状态维度 |

阈值 🔴 交还运维：如 10s 窗口失败率 50% 开路、半开间隔 30s——太灵敏会把源的偶发抖动放大成大面积拦截，太钝则保护不来（依据：Redis §2.5 降级链、§6.2）。

## 四、被追问预案

### Q13. 重建期间（投影"建一半"）的读请求怎么办？

**A**：这是**原方案没答上来的题**，新设计必须答：

- earliest 重放追赶期间，投影是增量覆盖写、部分 key 已就绪部分没有——读请求按 key 判断：**就绪的读投影，没就绪的自然走降级**，语义天然正确，不需要影子键。
- 批量快照加载则从根上绕开：**全量加载到位再开流量**（加载完成标志 = 缓存就绪探针），不存在半成品窗口。
- 若两者叠加（重建中 + 批量兜底），以批量接口的就绪标志为切换闸刀。

### Q14. 降级 REST 把权威源也打挂了，怎么办？

**A**：分两层——**前置靠限流熔断，兜底靠保守拦截**：

- 前置：限流把回源 QPS 压在源容量之下，熔断在源持续失败时快速失败，两者合力避免"打挂"（Q12）。
- 兜底：真挂了也只能保守拦截——`CheckpointBlocked(RouteCacheMiss/EquipmentCacheMiss)`（INV-CX-05），设备实时数据超时标 `EquipmentDataTimeout`（INV-10）。**停线风险是业务权衡，不是技术能消灭的**——这也是为什么"不击穿权威源"值得花力气：拦截是最后手段，不是常规路径。

### Q15. 这套方案上线前怎么验证？

**A**：四个混沌场景 + 一组指标：

1. **冷启动**：清缓存启新实例，测批量加载就绪时间、回源 QPS 曲线（验证就绪时间与 topic 长度解耦）。
2. **Redis down**：杀 Redis，测降级链 QPS 与权威源负载余量、恢复后切回时延。
3. **换班尖峰**：模拟百工位并发起过点，验证 singleflight 命中率与 L1 命中率（回源量应 ≈ 实例数 × 活跃 key 数）。
4. **熔断阈值**：源侧注入延迟/错误，验证开路-半开-恢复行为。

指标：回源 QPS、降级率、熔断次数、保守拦截率、预热就绪时长。🔴 阈值按实测拍板。

## 五、横向对比：四种预热/重建手段

| 手段 | 就绪时间 | 运维成本 | 新依赖 | 定位 |
|---|---|---|---|---|
| earliest 重放 | ∝ topic 长度，不可控 | 高（组管理/追赶窗口/幂等耦合） | 无（复用 Kafka） | **兜底全量重建** |
| 批量快照加载 | 秒级（一次批量 REST） | 低 | 源侧批量接口 | **冷启动主路径** |
| MySQL 读模型 | 重启即就绪 | 中（表维护/写放大） | 无（本地 DB） | **消灭失效场景** |
| 纯 REST 降级 | 无 | 零 | 无 | 小流量兜底 |

**选型结论**：主路径 = 读模型 + L1 + singleflight + 随机 TTL；earliest 退兜底；限流熔断全场景兜底。

### 6.1 已落定 vs gap，别混着说

| 内容 | 状态 |
|---|---|

### 6.2 红线

- ❌ "缓存命中率 99.9%"——除非有真实监控数据。
- ❌ "防雪崩已上线验证过"——批量预热/熔断是文档明确标注的 gap，说过 = 翻车。
- ❌ 把 Q11 的载体演进说成"已实施"——当前拍板仍是 Redis 共享为主。

### 6.3 简历口径修订建议

[简历-项目介绍](简历-项目介绍.md) §三 现口径：

> - **防缓存雪崩**：新消费组 `earliest` 偏移补投影实现缓存预热，降级查询配限流熔断，冷启动或缓存大面积失效时不击穿权威源。

建议改为：

> - **读侧缓存防雪崩**：冷启动批量快照预热 + singleflight 回源合并 + 进程内/Redis 多级缓存 + 随机 TTL 打散过期，降级查询经分布式令牌桶限流与熔断；Kafka `earliest` 全量重放降级为兜底重建手段，冷启动或缓存大面积失效时不击穿权威源。

面试讲到此条主动补一句："批量预热与熔断是上线前待验证项，设计文档里已标 gap"——把 gap 说成 gap 是加分，不是减分。
