## 1. 30 秒电梯陈述（设备域版）

"设备管理服务是这套 MES 里**唯一真正高并发**的所在，也是**资产可用性**的唯一权威源。我把它拆成 5 个限界上下文：**设备数据接入**扛万级报文/秒的采集流（边缘缓冲 + 断点续传 + 大文件分流，明确不走 Outbox），**设备工装台账**是可用性中枢（9 维阻塞投影 + 重算中枢，CRITICAL 故障同事务强停机），**维修 / 点检保养 / 计量检定**是三条事件驱动的运维流——被动修复、主动预防、合规检定——共用一套三段式不变式（INV/BIZ/INV-CX）和状态机刚性设计。整个设备域 27 个聚合根、121 条不变式，跨上下文协作零分布式事务，靠 Outbox + 幂等消费兜底。"

**三个抓手**：采集链路高并发解耦（不走 Outbox）/ 台账 9 维可用性重算中枢 / 三段式不变式 + 状态机刚性。

## 2. 高并发：设备数据接入上下文（项目唯一真正高并发链路）

> 这是面试时**最能体现架构判断力**的部分。关键不是喊 QPS，而是**识别出"高频采集"与"低频过点"两种并发特征，用两套完全不同的方案**。

### 2.1 两种并发特征的识别（最值钱的判断）

| 维度 | 高频采集链路（设备数据接入） | 低频业务链路（过点 / 工单 / 维修） |
|------|-------------------------------|--------------------------|
| 触发源 | 设备主动上报 / 秒级状态流 / 每板事件 | 人工扫码、人工派工 |
| 吞吐量级 | 万级报文/秒（设计容量） | 每工位几秒一次 |
| 可靠性方案 | 边缘缓冲 + 断点续传 + Kafka 直连 | Transactional Outbox + 幂等消费 |
| **是否走 Outbox** | **不走**（高频原始数据走 Outbox 会拖垮 DB） | 走 |
| 事务边界 | 采集与过点解耦，独立服务独立事务 | 过点主事务内零分布式事务 |

依据：[领域总览.md](../领域模型/领域总览.md) §5.3、[Outbox设计方案.md](../实现说明/业务事件/Outbox设计方案.md) §9.1。

**话术**："这套设计真正难的不是扛吞吐，是**识别出两条链路并发特征不同、然后克制地用不同方案**——高频采集用边缘缓冲换吞吐、低频过点用 Outbox 换一致。很多人一上来所有事件都走 Outbox，采集量一起 DB 先被 outbox 表写爆。"

### 2.2 边缘-平台分离 + 大文件分流（INV-15）

- **边缘侧**（网关-协议适配-封装-缓存）只做"搬运"：`RawSignalEmitted -> DataPacketSealed -> EdgeBuffered -> PacketDispatched`。
- **平台侧**（去重-乱序矫正-落库-分发）只做"整形"：`PacketReceived -> Deduplicate -> BufferReorder -> PersistAndPublish`。
- **大文件分流**（INV-15，[领域建模/设备数据接入上下文.md](../领域模型/设备管理服务/领域建模/设备数据接入上下文.md) §6.1.4）：烧录日志、电批扭矩曲线（数百点/枪）、AOI 图像走**对象存储**，采集主流（DataPacket）只承载 `URI + sha256`。`PayloadKind` 分 `STRUCTURED / OBJECT_STORAGE` 两类。

**为什么是亮点**：这是**吞吐与成本的核心折衷**。全量曲线进时序库成本不可接受；剥离后主流只过摘要值 + URI，实时链路轻、离线分析走对象存储。被追问"对象存储 URI 失效怎么办"——答"URI 生命周期与报文保留窗口绑定，由存储策略统一管理，不在事件载荷里硬编码"。

### 2.3 边缘缓冲 + 断点续传（INV-05，No-Data-Loss）

- 连接正常：`PacketDispatched` 直接上行。
- 连接异常：`BackfillEnqueued` 进断连缓冲，`BackfillCursor` 聚合根维护 `buffered_cursor / backfilled_cursor` **单调递增**游标（INV-05，§6.1.5）。
- 恢复后：`BackfillResuming -> BackfillCompleted`，**先补齐再放新**（INV-05），携带 `backfilled_msg_count`。

**为什么是亮点**：网络抖动不丢数据、不堵主流程。`BackfillCursor` 单调递增是断点续传正确性的不变式——补传数据按游标追平后才能放新报文，避免新数据盖过补传造成时序错乱。

### 2.4 平台层去重 + 乱序矫正（BIZ-02）

- **去重**：`msg_id` 全局唯一（BIZ-02，跨实例，由平台去重表唯一索引保证），重复报文发 `DuplicateDiscarded`。
- **乱序矫正**：补传数据时间戳在原始区间内、但到达平台会乱序。平台 `BufferReorder` 按 `source_ts` 排序，迟到报文打 `LATE` 质量标后补入，发 `LateArrivalReordered`。
- **时钟漂移**（INV-11）：`source_ts` 为事件时间基准；漂移超阈值（建议 3s）按 `ingest_ts` 修正并记 `clock_skew`；`source_ts <= ingest_ts` 始终成立（INV-04）。

**为什么是亮点**：补传天然会乱序，平台层显式建模"乱序窗口"而不是假装有序——这是工业采集的真实痛点，很多系统在这里算错运行时长。运行时长聚合按 `equipment_id + period` 不重复聚合（BIZ-03），补传时段不重复计算（时间戳已在原始区间内）。

### 2.5 采集只搬运不解释（INV-CX-01）+ 质量强制打标（INV-04）

- **只搬运不解释**（INV-CX-01）：焊接温度阈值、NG 判定、报警分级一概不写进采集器，业务语义留下游。否则工艺一改就要改驱动，采集器成了演化瓶颈。
- **severity 配置驱动**（INV-09）：`设备型号 × alarm_code -> severity` 映射表可热更新，不在事件载荷硬编码。
- **质量强制打标**（INV-04）：每帧必须打 `GOOD/SUSPECT/BAD/LATE`（`DataQualityFlag`），下游可按质量过滤。
- **阻塞投递防脏数据**：镭雕失败时不发 `SerialNumberMarked`（防脏 SN 流入）；固件指纹不匹配时只发 `ProgrammingFingerprintMismatch`，不发 `ProgrammingSessionCompleted`。

**为什么是亮点**：四条加在一起，把采集器从"业务耦合重灾区"变成"纯管道"。这是采集链路能长期演化的根因——驱动代码不背业务变化。

### 2.6 设计容量目标（带假设，标注口径）

> **前提假设**（开口先报）：单车间 10 条 SMT+整机线，每线 8~10 台可采设备，单线节拍 6~10s/板。

| 指标 | 设计容量目标 | 估算依据 / 出处 |
|------|------------|---------------|
| 在线采集设备（长连接） | 200~500 台 | 10 线 × 8~10 台 + 老化房/线边仓控制器；`CollectionChannel` 单设备单活跃通道（BIZ-01） |
| 采集报文吞吐 | **~1 万报文/秒**（峰值） | 秒级状态流（数百台 × 1fps）+ 每板事件 + 测试项采样 |
| 单设备最高采样 | 秒级状态 + 每板事件 | A 类工业设备秒级状态流 + 离散过板事件（§1） |
| 老化房采样周期 | 建议 5min | 老化房控制器事件说明（§5.6.9），数据量极大，原始落冷热分层 |
| 扫码枪去重窗口 | 800ms | 线边仓热点（§3.8），同 `bin_id+lot_no` 去重 |
| 时钟漂移修正阈值 | 建议 3s | INV-11 / §2.10 |
| 死信保留窗口 | 7 天滚动 | INV-07，解码失败原始字节 + `raw_bytes_ref + reason + retain_until` |
| 运行时长聚合周期 | 每班（8h），1 位小数 | §2.4，如 7.5h |
| 过点实时数据查询 | **P99 ≤200ms**（设计目标） | 与过点执行上下文协作、§4.8 |

> **诚实口径**：⚠️ 设备数据接入源文档**只给出单设备采样特征与各类时间窗口**，并未直接给出"设备总数 / 万级 QPS / 并发连接数"——上表的 200~500 台、1 万报文/秒是**按车间规模假设的容量估算**，不是源文档数据，更不是线上实绩。被问"线上跑过吗"老实说"这是设计阶段容量规划，按 10 条线假设估算，没上线实测"。源文档真正写死的、可硬给的是右侧带 §/INV 出处的那些时间窗口。

## 3. 高可用：资产可用性中枢 + 断连韧性

### 3.1 台账 9 维可用性投影（INV-13）

`AvailabilityProjection`（[领域建模/设备工装台账上下文.md](../领域模型/设备管理服务/领域建模/设备工装台账上下文.md) §1.4）维护 9 个布尔阻塞维度：

```
lifecycle_blocked / inspection_overdue / maintenance_overdue / calibration_blocked /
malfunction_active / life_exceeded / comm_lost / critical_alarm / (资产状态阻塞)
```

**INV-13**：`AssetAvailabilityChanged.available = true` **当且仅当** 9 个维度全为 false——这是**合取**，任一维度阻塞即不可用。

**为什么是亮点**：可用性不是单一布尔，是 9 个维度的合取。一台设备可能"没故障、没超期"但"通信中断"——照样不可用。把多维度阻塞显式建模成投影，避免了"只看状态机"的误判。

### 3.2 三种不可用机制（设计精髓）

同一个"不可用"，台账用**三种不同机制**对应三种业务语义（[事件风暴/设备工装台账上下文.md](../领域模型/设备管理服务/事件风暴/设备工装台账上下文.md) §2.6）：

| 机制 | 状态影响 | available | 适用场景 | 不变式 |
|------|---------|-----------|---------|--------|
| **SuspendAsset**（硬阻塞） | IN_SERVICE -> SUSPENDED | =false | 故障 / 校准不合格 / 通信中断 / 寿命超标 | BIZ-03 双重不可用 |
| **AddBlockingReason**（叠加阻塞） | 已 SUSPENDED，仅追加 `blocking_reasons` | 仍 false | 多阻塞并存（如通信中断 + 报修 + 校准过期同时发生） | BIZ-06 不重复状态变更 |
| **MarkAssetUnavailable**（条件阻塞） | 状态保持 IN_SERVICE | =false | 点检/保养过期——资产本身能用但不合规 | INV-17 仅置 available=false |

**为什么是亮点**：多数系统只有"停用/启用"两态。这里区分"硬停用（状态变）"和"条件不可用（状态不变、仅合规位翻转）"——点检过期不该把资产扔进 SUSPENDED（它物理上还能跑），只该翻合规位。这种**语义精度**是 MES 防错的核心。

### 3.3 AvailabilityRecomputeService —— 可用性重算中枢

[领域建模/设备工装台账上下文.md](../领域模型/设备管理服务/领域建模/设备工装台账上下文.md) §3.2 的 `AvailabilityRecomputeService` 是**消费 5 个上下文事件**的中央领域服务：

- 点检保养：`InspectionCompleted / MaintenanceCompleted / InspectionOverdue / MaintenanceOverdue / FixtureLifeExceeded`
- 计量检定：`CalibrationCertificateIssued / CalibrationFailed / CalibrationExpired / CalibrationDispatched`
- 维修：`RepairCompleted / ScrapRecommendation / MalfunctionReported`
- 设备数据接入：`ChannelEscalated / EquipmentAlarmRaised(severity=CRITICAL)`
- 生产执行：`MalfunctionReported`

**关键设计**：所有"可能恢复"的事件**不直接 `reinstate()`**，而是先 `clearBlocking` 再 `recomputeAndDecideReinstate`——**仅当所有阻塞维度均不成立且当前 SUSPENDED 时才恢复**。防止"校准通过了就恢复"但"其实还有通信中断"的错误恢复。

**为什么是亮点**：恢复决策是"重算"而非"事件驱动直查"。这是多源阻塞并存时的正确性保证——任何一个恢复事件都只是"清掉自己那维阻塞"，能不能真恢复要综合全部 9 维。

### 3.4 同服务强一致（INV-CX-08 / 维修 INV-CX-09 / 点检 INV-CX-06）—— 防 Kafka 延迟误放行

同一概念在三个上下文各有一条跨上下文不变式（编号在双方上下文一致）：

- **台账 INV-CX-08**：当点检保养 / 维修与台账同属一个部署单元时，`INSPECTION_ANOMALY / INSPECTION_OVERDUE / MAINTENANCE_OVERDUE / LIFE_EXCEEDED / CRITICAL 故障` 等强防错阻塞**不走异步消息**，由 `AssetAvailabilityWriteAppService` 在**同一本地事务**内同步更新 `AvailabilityProjection`。
- **维修 INV-CX-09**：CRITICAL 故障工单创建时，应用服务同事务委托台账 `SuspendAsset(reason=CriticalFault)`——停线故障必须立即阻断生产。
- **点检 INV-CX-06**：点检异常/超期、保养超期、寿命超限与台账 `AvailabilityProjection` 必须同一本地事务同步。

**为什么是亮点**：这是**对"Outbox + 异步消息"边界的清醒认知**。强防错场景（停线、寿命超限）如果走 Kafka，延迟几秒才扣可用性，期间过点引擎读到旧状态会错误放行。所以"同服务部署时强防错走本地事务、跨服务才走事件"——**一致性强度按部署拓扑分级**，不是一刀切。

### 3.5 数据接入断连韧性：SUSPECT 保守策略 + 边缘缓存 No-Data-Loss

设备在线状态机（[事件风暴/设备数据接入上下文.md](../领域模型/设备管理服务/事件风暴/设备数据接入上下文.md) §2.2.1）：

```
ONLINE -> SUSPECT（心跳超时，保守计在线）-> OFFLINE（重连失败 N 次，进边缘缓存模式）
      <- 重连成功 + 补传完成 <- 
```

- **SUSPECT 保守计在线**：短暂抖动不触发离线，运行时长仍计入该时段——避免抖动导致时长被反复扣除。
- **边缘缓存模式**：OFFLINE 时 `entered_buffer_mode=true`，报文走断连缓冲（§2.3）；恢复后 `BackfillCompleted` 补齐，`EquipmentRecovered` 携带 `gap_window, backfilled_msg_count`。
- **告警升级**：重连失败超阈值发 `ChannelEscalated`（LINE/WORKSHOP/FACTORY），台账 `SuspendAsset(reason=CommunicationLost)`。

**为什么是亮点**：把"断连"建模成**三级状态 + 缓存降级 + 自动补传**，而不是"断线即丢"。SUSPECT 的"保守策略"是个有意识的不对称权衡——宁可多计在线时长，也不因抖动反复扣减。

### 3.6 资产 vs 通信双视角（INV-CX-04 台账 / INV-CX-08 数据接入）

- `EquipmentOnline`（通信视角，数据接入）：连接通不通、报文进没进来。
- `AssetCommissioned`（资产视角，台账）：它是谁、归谁、能不能用。

一台资产可能 **Commissioned 但 Offline**（断网），也可能 **Online 但 Suspended**（维修自检中）。两者**独立状态机，互不为充要条件**。

**为什么是亮点**：这是把"设备数据接入"从"台账"独立出来的根因（[事件风暴/设备数据接入上下文.md](../领域模型/设备管理服务/事件风暴/设备数据接入上下文.md) §0）。混在一起会把"离线"误判成"未投用"、把"在线"误判成"可用"。两个视角分离后，断网只触发通信降级，资产可用性由台账综合 9 维判定。

## 4. 高可靠：三条事件驱动运维流 + 状态机刚性

### 4.1 维修上下文（被动 / 事件驱动）

**SLA 升级链**（[领域建模/维修上下文.md](../领域模型/设备管理服务/领域建模/维修上下文.md) INV-11、§3.6）：

| 故障分级 | 响应 SLA | 修复 SLA | 超时升级 |
|---------|---------|---------|---------|
| CRITICAL（停线） | **15min** | **2h** | 30min 无响应 -> 自动升级主管 |
| HIGH（降级运行） | 30min | 4h | 1h 无响应 |
| MEDIUM（可带病运行） | 2h | 24h | 4h 无响应 |
| LOW（轻微） | 8h | 72h | 不自动升级 |

升级链：`L1 一线工程师 ->（SLA 超时）-> L2 维修主管/高级工程师 ->（超时）-> L3 工程经理（决定外协）->（内部修不了）-> 外协维修商`。

**三个高可靠设计**：

1. **升级建模为属性而非状态**（INV-12）：事件风暴原本把 `[ESCALATED]` 画成状态节点；领域建模改成 `escalation: Escalation` 属性。升级时主状态机停在 `DISPATCHED/IN_REPAIR`，不用纠结"升级完回哪个状态"。升级幂等：按 `(order_id, escalation_level, 超时窗口)` 去重（BIZ-03）。
2. **CRITICAL 同步停机 vs 正常异步恢复**：CRITICAL 故障 `SuspendAsset(reason=CriticalFault)` 走**本地事务强同步**（INV-CX-09），立即阻断生产；正常 `RepairCompleted -> ReinstateAsset` 走**异步事件**（INV-CX-08），台账综合判定后可能因其它阻塞原因（如检定超期）而不恢复——台账保留可用性判定唯一权威。
3. **状态机刚性**（INV-02）：7 态 `CREATED -> DISPATCHED -> DIAGNOSED -> IN_REPAIR -> VERIFIED -> CLOSED` + `PENDING_SCRAP_DECISION` 分支。**仅 2 条可逆边**：`ReopenRepairOrder`（验证失败回退维修）、`ReopenForRediagnosis`（报废驳回退回诊断）。`CLOSED` 终态，之后任何事件拒收（INV-03）。无"管理员强制 reopen"——刻意的刚性，符合车间防错。

**7 层幂等**：commandId 命令级 / source_event_id 跨源 / (asset_id,symptom,窗口) 人工报修 / (order_id,escalation_level,窗口) 升级 / application_id 报废审批 / (action_id,part_code) 备件消耗 / consumed_event 表通用跨上下文（INV-CX-06）。

### 4.2 点检保养上下文（主动 / 计划驱动）

与维修的边界：**触发机制不同**（主动计划驱动 vs 被动事件驱动）、**流程骨架不同**（rule->plan->task->execute->signoff vs report->dispatch->diagnose->repair->verify->close）、SLA 逻辑不同——合并会互相污染（[事件风暴/点检保养上下文.md](../领域模型/设备管理服务/事件风暴/点检保养上下文.md) §0）。

**四个高可靠设计**：

1. **规则变更快照语义**（BIZ-06，§6.2）：规则 `update` 仅从下个周期生效，已生成的计划/任务持规则快照不受影响——避免执行中途规则变更导致混乱。
2. **OVERDUE 可逆、SKIPPED 终态**（INV-19，§6.1.5）：漏做任务进 `OVERDUE` 仍可 `recordItem + confirm` 补做闭环；`SKIPPED`（资产退役/报废）才是终态。`OverdueScanAppService` 定时扫 `PENDING/IN_PROGRESS` 超 `deadline` 的任务标 OVERDUE，同事务驱动台账 `MarkAssetUnavailable`（INV-CX-06）。
3. **部分失败保留**（INV-20，§6.1.6）：10 项点检 1 项 FAIL -> 整体 verdict=FAIL，但 9 项 PASS 结果全保留，`failed_items[]` 随完成事件发布——便于事后分析与维修定位。FAIL 只发 `RepairSuggested` 建议报修，**不直接建维修工单**（保上下文自治）。
4. **工装寿命 80% 预警**（§2.9）：`accumulated_cycles >= life_limit * 0.8` 发 `FixtureLifeWarning`（仅预警不状态变更）；`>= life_limit` 发 `FixtureLifeExceeded` 同事务 `SuspendAsset`。

**度量重置机制**：台账只记 `reset_baseline` 基准点、不改绝对累积值；本上下文算偏移量 `accumulated_value - reset_baseline >= 阈值`（INV-CX-02/03）。翻修清零时 `FixtureRefurbished` 驱动 `MetricBaselineSyncService` 刷新寿命视图，避免误判超限。

### 4.3 计量检定上下文（合规驱动）

与台账的边界：**法规属性不同**（受国家计量法规强制约束、证书具法律效力）、流程特征不同（涉及外部实验室、法定证书、溯源链）——独立成上下文换法规合规边界清晰（[事件风暴/计量检定上下文.md](../领域模型/设备管理服务/事件风暴/计量检定上下文.md) §0）。

**四个高可靠设计**：

1. **三级过期预警**（§2.4）：黄色（`valid_until - 30天 <= now`，通知准备送检）-> 橙色（`valid_until - lead_time_days <= now`，自动触发 `CalibrationDue`）-> 红色（`valid_until < now`，发 `CalibrationExpired` + 台账 `SuspendAsset` + 紧急检定）。
2. **送检即暂停**（INV-CX-04）：`CalibrationDispatched` 后台账 `SuspendAsset(reason=Calibrating)`——送检期间器具不可用是硬约束。
3. **FAIL 后器具保持冻结**（INV-CX-05）：`CalibrationFailed` 后台账 `SuspendAsset(reason=CalibrationFailed)`；`RepairFeasibility` 为 `NOT_ECONOMICAL / NOT_REPAIRABLE` 时台账可发起报废审批。收回事件仅作物理回位登记，**资产冻结状态由台账维护**。
4. **证书有效期权威源**（INV-CX-02）：本上下文是证书有效期权威源，过期检测由本上下文定时器独立执行，不依赖台账事件触发——台账仅存 `cert_valid_until` 快照。**只发布事件、不直接指挥台账恢复/冻结**（INV-CX-03）：恢复决策由台账 `RecomputeAndDecideReinstate` 综合所有阻塞维度后判定。

**ABC 分类**（§1.1）：A 类（强制检定，法定证书，超期立即冻结+法规违规告警）/ B 类（依法管理，可内检）/ C 类（首件检定后免周期检定）。

> 计量检定是**设备域里唯一已完整迁移三段式编号的范本**（9 INV + 5 BIZ + 5 INV-CX = 19 条），其 §6 是其它上下文迁移的参照。

### 4.4 报废审批：四来源统一审批 + 只建议不执行

`ScrapApplication` 聚合根（[领域建模/设备工装台账上下文.md](../领域模型/设备管理服务/领域建模/设备工装台账上下文.md) §1.5）统一审批来自四个上下文的报废建议：

- 来源：`INSPECTION`（寿命超标）/ `REPAIR`（维修不经济）/ `CALIBRATION`（校准不合格且不可修复）/ `ADMINISTRATIVE`（管理决策）。
- 四种审批流模板按来源自动匹配（如 REPAIR 走 工程主管 -> 财务 -> 厂级）。
- **驳回即结束整个申请，不允许退回上一步**——避免审批循环。
- 跨实例约束：同一资产不可有未决报废申请（BIZ-02），由 `uk_pending_scrap(asset_id, pending_flag)` 唯一索引保证。
- 审批通过后 `AssetRetired` 与申请审批**同一事务**提交（INV-18 / BIZ-04）。

**只建议不执行**（维修 INV-CX-05）：维修上下文只发 `ScrapRecommendation`，审批与执行归台账。维修工单进 `PENDING_SCRAP_DECISION` 等待台账决策——通过则 `close(AssetScrapped)`（INV-CX-01），驳回/撤回则 `reopenForRediagnosis()`（INV-CX-02）。

**为什么是亮点**：报废是资产生命周期终态，不是维修活动。把审批集中到台账（资产视角），让维修保持"只管修不管报废"的纯粹——这是 DDD 限界上下文边界的经典应用。

## 5. 领域建模深度（差异化得分点）

### 5.1 三段式不变式编号方案（INV / BIZ / INV-CX）—— 方法论亮点

[计量检定领域建模 §6](../领域模型/设备管理服务/领域建模/计量检定上下文.md) 定义了三段式，设备域 5 上下文已全部迁移完成：

| 层级 | 一致性边界 | 一致性强度 | 守护机制 |
|------|-----------|-----------|---------|
| **INV-XX**（聚合不变式） | 单一聚合 | 事务内强一致，始终为真 | 聚合根前置条件 / 状态机 / 规约 |
| **BIZ-XX**（业务不变式） | 本上下文内跨聚合/跨实例 | 最终一致 | 领域服务 + 唯一索引 / 事件去重表 / Saga |
| **INV-CX**（跨上下文不变式） | 跨限界上下文 | 最终一致 | 事件订阅 + ACL + 跨服务协调 |

**为什么是亮点**：多数项目的不变式是一锅 `INV-01~N` 平铺，看不出一致性边界。三段式把"聚合内强一致 / 上下文内最终一致 / 跨上下文最终一致"显式分层，每条不变式直接告诉你"它靠什么守护、崩了影响多大"。**INV-CX 编号在双方上下文保持一致**（如台账 INV-CX-04 ↔ 数据接入 INV-CX-08 同指"双视角"），跨服务协作一眼对齐。

### 5.2 限界上下文边界判断（四个经典"为什么不合并"）

| 问题 | 答案（出处） |
|------|------------|
| 维修为什么不并入点检保养？ | 触发机制（被动事件 vs 主动计划）、流程骨架、SLA 逻辑全不同，合并互相污染（[维修事件风暴 §0](../领域模型/设备管理服务/事件风暴/维修上下文.md)） |
| 设备数据接入为什么不并入台账？ | 视角不同（通信 vs 资产）、变化频率不同（协议高频演化 vs 主数据低频）、"只搬运不解释"硬约束（[数据接入事件风暴 §0](../领域模型/设备管理服务/事件风暴/设备数据接入上下文.md)） |
| 计量检定为什么不并入台账？ | 法规属性、流程特征、证书管理、判定法律含义全不同（[计量事件风暴 §0](../领域模型/设备管理服务/事件风暴/计量检定上下文.md)） |
| 设备台账与工装台账为什么不拆？ | 生命周期同构、可用性引擎共用、对外契约一致、组织同一团队（[台账事件风暴 §0](../领域模型/设备管理服务/事件风暴/设备工装台账上下文.md)） |

**为什么是亮点**：每个"拆/不拆"都有**可辩护的非主观理由**（触发机制、视角、法规、生命周期同构），不是为拆而拆。这是 DDD 落地成熟度的标志。

### 5.3 聚合根纯洁 + Outbox + ACL（台账实现设计 doc 独有）

台账是设备域**唯一有实现设计文档**的上下文，落地了全套工程模式（[实现设计/设备工装台账上下文.md](../领域模型/设备管理服务/实现设计/设备工装台账上下文.md)）：

- **八层分层**（facade -> utility）：领域层零 Spring/MyBatis/Kafka/HTTP 依赖；@Transactional 只在应用服务；领域服务加载聚合 + 调行为 + 写仓储。
- **聚合根纯洁**：聚合根不依赖 KafkaTemplate / OutboxRepository，只 `registerEvent` 返回领域事件，应用服务编排 outbox 写入。
- **Outbox 模式**（§7.2）：聚合事件 -> 同事务写 `outbox_event` -> `OutboxPublisher` 异步发 Kafka；资产状态、报废审批、投影更新与 outbox 写入同一 DB 事务——崩溃零丢失。
- **ACL 防腐层**（§8.2）：外部事件 DTO 不进 `domain.model`；接口定义在 `domain.acl`，实现在 infrastructure。
- **投影聚合**（§9）：`AvailabilityProjection` 作为**独立聚合根**（非数据库视图）与资产 1:1——因为可用性重算的一致性边界不同于资产主数据。CQRS：暂缓独立读库，先用同库投影表。
- **乐观锁**（BIZ-07）：所有聚合根 + 投影带 `version`，Repository update 带 version 条件；外部事件 `consumed_event` 表 `uk(source, event_id)` 幂等。

**为什么是亮点**：能讲到"投影为什么是独立聚合根而不是视图"这一层，说明真正理解了一致性边界，而不是套 CQRS 模板。

## 7. 追问防守 Q&A（设备域专属）

**Q：设备域 5 个上下文会不会过度设计？**
A：每个拆分都有非主观理由。维修 vs 点检——触发机制（被动 vs 主动）不同；数据接入 vs 台账——视角（通信 vs 资产）和变化频率不同；计量 vs 台账——法规属性不同。反过来台账和工装没拆，因为生命周期同构、引擎共用、契约一致。**拆与不拆都按"变化频率 + 视角 + 法规"判断，不是按"看着大"**。

**Q：采集 1 万报文/秒怎么扛？**
A：压力挡在边缘网关，不是平台硬抗。①边缘缓冲 + 断点续传（BackfillCursor 单调递增，先补齐再放新）；②大文件/曲线不进主流（扭矩曲线只带峰值+URI，固件走对象存储）；③采集只搬运不解释，业务判定留下游。到平台的是已结构化、已去重、已瘦身的事件流，平台只做去重/乱序/落库/分发。1 万是**设计容量目标**，按 10 条线假设估算，非线上实测。

**Q：高频采集为什么不走 Outbox？**
A：Outbox 代价是每条事件多一次 DB 写（业务表+outbox 同事务），适合低频业务契约事件。高频采集走 Outbox 会先把 outbox 表写爆。所以采集用"边缘缓冲 + Kafka 直连"换吞吐，可靠性靠边缘断点续传 + 平台 msg_id 去重 + 幂等消费。这是用两套方案对应两种并发特征的刻意选择（[Outbox设计方案.md](../实现说明/业务事件/Outbox设计方案.md) §9.1）。

**Q：设备掉线了，资产还算不算可用？**
A：两个视角，不能混。`EquipmentOnline`（通信视角）≠ `AssetCommissioned`（资产视角），独立状态机、互不为充要条件（台账 INV-CX-04 / 数据接入 INV-CX-08）。掉线只触发通信降级和补传，资产可用性由台账综合 9 维阻塞判定。一台资产可能 Commissioned 但 Offline（断网），也可能 Online 但 Suspended（维修中）。

**Q：9 维可用性投影，为什么不用状态机一个状态搞定？**
A：因为多个阻塞维度会**并存**。一台设备可能同时通信中断 + 报修 + 校准过期。状态机只能记一个"当前态"，并存场景要么丢信息要么频繁切换。投影用 9 个布尔合取（INV-13：全 false 才 available），每种阻塞独立记。而且恢复要"重算"——清掉自己那维后还要看其它 8 维，不能收到一个恢复事件就 reinstate。

**Q：CRITICAL 故障为什么走本地事务同步，不走 Kafka？**
A：停线故障必须立即阻断生产。如果走 Kafka，延迟几秒才扣可用性，期间过点引擎读到旧状态会错误放行。所以同服务部署时 CRITICAL 的 `SuspendAsset` 在工单创建的同一本地事务里同步完成（维修 INV-CX-09 / 台账 INV-CX-08）。代价是两个上下文在同服务部署时事务耦合——但这是用"强防错一致性"换"防错零延迟"的刻意权衡。跨服务部署时才退化为异步事件 + 业务兜底。

**Q：维修工单状态机为什么只有两条可逆边？**
A：刻意刚性，符合车间防错。只有 `ReopenRepairOrder`（验证失败回退维修）和 `ReopenForRediagnosis`（报废驳回退回诊断）可逆，其余单向，CLOSED 终态拒收任何事件（INV-02/03）。没有"管理员强制 reopen"——车间里一个已关单的维修不能被随手重开，否则追溯链断裂。两条可逆边对应的是真实业务回退（没修好、报废没批），不是操作便利。

**Q：报废审批为什么放台账不放维修？**
A：报废是资产生命周期终态，不是维修活动。维修视角是"故障怎么修"，只发 `ScrapRecommendation`（INV-CX-05 只建议不执行）；台账是资产视角，统一审批来自 4 个来源（点检/维修/校准/管理）的报废建议。审批通过 `AssetRetired` 与审批同事务提交（INV-18）。两个上下文共享 asset_id 但视角不同，靠 `ScrapDecisionProjection` 读模型订阅回流驱动关单/退回诊断（维修 INV-CX-01/02）。

**Q：点检过期，资产该不该进停用状态？**
A：不该。点检过期是**合规问题不是物理故障**——资产物理上还能跑。所以用 `MarkAssetUnavailable`（条件阻塞）：状态保持 IN_SERVICE，只翻 `available=false`（INV-17）。只有故障/校准不合格这类才用 `SuspendAsset` 把状态切到 SUSPENDED（BIZ-03 双重不可用）。区分"硬停用"和"条件不可用"是 MES 防错的语义精度。

**Q：规则改了，在执行的点检计划怎么办？**
A：快照语义（BIZ-06）。计划/任务在生成时持规则快照，规则 `update` 只从下个周期生效，在执行的不受影响。避免执行中途规则变更导致判定标准混乱。这是用"变更延迟生效"换"执行一致性"。

**Q：补传数据乱序到达，运行时长会不会算重？**
A：不会。平台层两件事：①`msg_id` 去重，重复补传直接 `DuplicateDiscarded`；②乱序窗口缓冲按 `source_ts` 矫正（`LateArrivalReordered`）。运行时长聚合按 `equipment_id + period` 不重复聚合（BIZ-03），补传时段时间戳在原始区间内，不重复计算。

**Q：三段式不变式编号 INV/BIZ/INV-CX 有什么用？**
A：把一致性边界显式分层。INV 是聚合内强一致（事务内始终为真），BIZ 是上下文内跨聚合最终一致（靠唯一索引/去重表），INV-CX 是跨上下文最终一致（靠事件+ACL）。每条不变式直接告诉你"它靠什么守护、崩了影响多大"。INV-CX 编号在双方上下文一致，跨服务协作一眼对齐。设备域 121 条全这么分，比一锅 INV-01~N 平铺可维护得多。

**Q：台账实现设计里投影为什么是独立聚合根不是数据库视图？**
A：因为可用性重算的一致性边界跟资产主数据不同。投影要消费 5 个上下文的事件做多维合取，还要支持同服务强防错的本地事务同步更新（INV-CX-08）。如果做成视图，强防错同步写就没法在同一事务里落库，会退化成异步。独立聚合根 + 乐观锁（BIZ-07）才能既保证重算幂等又支持本地事务强一致。

## 10. 真实车间待补强场景（专家视角的三高 gap 分析）

> **视角**：设备管理服务把"采集高并发 + 资产高可用"做得很扎实。但真实 SMT/PCBA+整机车间里，三高压力最集中的其实是**过站执行**和**物料/防错物理级**两侧--这几块是当前事件风暴的相对盲区，也是面试时能拉开差距的"真车间"素材。
> **覆盖度标记**：✅ 已较好覆盖 / 🟡 有事件或已提及，但未被作为"三高"显式建模 / ❌ 未见显式设计。

### 10.1 高并发（被低估的真实尖峰）

| 场景 | 为什么是高并发 | 覆盖 | 话术价值 |
|------|---------------|------|---------|
| 过站"开线潮/换班潮" | 不是单工位几秒一次的稳态--开线瞬间、换班交接瞬间，全场几十~上百工位**同时**扫码过站，是瞬时尖峰 | 🟡 | 体现"过站既有稳态也有尖峰"，尖峰靠连接池/批量写/排队吸收，不是堆 DB |
| AOI/SPI 图像实时判定流 | AOI 每板多张高分辨率图、SPI 3D 锡膏扫描，**既要大文件落对象存储，又要 NG 实时拦截**。当前把图像简单归到"大文件分流"，但 NG 判定结论必须走主流实时拦截 | 🟡 | "高频+大文件+实时判定"三者叠加，比纯采集难；讲清"图像 URI 走对象存储、判定结论走主流"的分流 |
| 炉温/关键工艺参数实时 SPC | 回流焊多温区秒级采集 + 实时 SPC 控制图 + Cpk + 超标停线。采集层"只搬运不解释"对，但 **SPC 实时判定归谁、超标停线指令怎么实时下发**没讲清 | ❌ | 三高叠加典型；讲"采集只搬运、SPC 判定归质量上下文、停线指令走防错通道"的三段职责 |
| 测试数据 (ICT/FCT) 明细写入压力 | 每板几十~几百测试项，高节拍线多台测试机并行，明细表写入密集。当前"会话级事件+明细落 MySQL"方向对，但明细表高节拍下的写入削峰没讲 | 🟡 | 讲"会话事件走主流轻量化、明细走结构化表批量写"的读写分离 |
| 报警风暴 (Alarm Storm) | 一条线停 -> 关联设备级联报警，瞬间几十上百条。当前有 severity 配置映射，但**风暴期限流/聚合/去重/抑制窗口**没有 | ❌ | 经典车间场景；讲"同源报警抑制窗口、级联根因聚合、风暴期降级只发 CRITICAL" |
| 看板/大屏实时聚合读 | 车间大屏 + 多终端实时刷 OEE/良率/进度，高并发**读**。当前 CQRS 投影方向对，但实时聚合读的物化视图/刷新策略没讲 | 🟡 | 区分"命令侧低频写、查询侧高频聚合读"，投影该物化 OEE/良率而非现算 |

### 10.2 高可用（制造业头号场景，当前最薄弱）

| 场景 | 为什么是高可用 | 覆盖 | 话术价值 |
|------|---------------|------|---------|
| **过站引擎离线降级 / 断网自治** | **制造 HA 头号场景**。MES 挂了=停线=按分钟计损失。车间断网/MES 抖动时产线必须能继续过站：工位级缓存过站记录 + 防错规则快照 + 恢复后补传对账。当前强调"过点主事务本地 DB"，但**本地 DB 也不可用时怎么办**没讲 | ❌ | 一讲就知道下过车间。讲"工位离线缓存 + 规则快照 + 补传对账 + 离线期防错降级到本地白名单" |
| 车间网络分区下的产线自治 | 车间网络与中心机房分区时产线自治运行。当前边缘缓冲是**数据接入侧**的，**过站侧**的分区自治没有 | ❌ | 与上条互补；讲"采集断网有边缘缓冲、过站断网要有工位自治，两侧不能混" |
| 防错指令可靠送达 + 设备联锁 | 拦截指令（不合格品禁放行、设备停机）必须可靠送达设备，**丢了就是不良品流出的质量事故**。需要"指令确认+重试+超时降级到物理联锁"。当前过点门禁是**逻辑判定**，**判定结果怎么可靠作用到物理设备**没讲 | ❌ | 防错的物理级；讲"逻辑门禁 + 指令送达确认 + 超时物理联锁降级"三级防错，比纯软件门禁高一个段位 |
| SN 池高可用与水位 | SN 不能耗尽否则停线。当前"平台预分配下发"，但**水位监控+提前补段+补段期间不中断**的高可用没讲 | 🟡 | 讲"SN 段预分配 + 水位阈值触发补段 + 补段与消费并发不冲突" |
| 时钟同步 (NTP/PTP) | 追溯、时序、跨设备事件排序依赖精确时钟。当前 INV-11 处理了**采集侧**时钟漂移，但**过站侧、跨设备事件时序**的时钟基准没讲 | 🟡 | 讲"采集侧漂移修正已有、车间级 PTP 主时钟 + 事件 source_ts 基准" |

### 10.3 高可靠（MES 核心价值，几个经典防错缺口）

| 场景 | 为什么是高可靠 | 覆盖 | 话术价值 |
|------|---------------|------|---------|
| 追溯"不串、不丢、可还原" + 受影响批次圈定 | 客诉时要 100% 还原某板用了哪批料、过哪些站、测试结果。更要命的是**炉温超标那段时间生产的板要能圈定并隔离**。当前有两段式追溯 + routeVersion，但**受影响批次反向圈定**没讲 | 🟡 | MES 核心价值；讲"正向追溯（板->料->站）+ 反向圈定（异常时段->受影响批次->隔离）"双向 |
| MSD 潮敏器件暴露时间管控 | 潮敏器件拆封后有暴露时限，超时必须烘烤否则回流焊爆米花。当前采集侧有 `MoistureExposureTimerStarted/Expired` 事件，但**超时禁用判定归谁、与过点门禁怎么联动**没串起来 | 🟡 | 经典物料防错；讲"采集侧计时、物料侧规则、过点侧门禁"三段联动 |
| 首件验证 (FAI) 闸口 | 首件未过验，批量必须硬拦截。当前"首件放行"是四道门禁之一，但**首件验证流程本身的可靠性**（谁验、验什么、失败回路）没展开 | 🟡 | 讲"首件未验->批量拦截、首件失败->退回诊断、首件通过->放行批量"的状态闸口 |
| SN 端到端防重防错 | 当前有"镭雕失败不发 SN"。但**烧录 SN 与镭雕 SN 一致性校验、重号检测、错配拦截**的端到端链路没讲全 | 🟡 | 讲"SN 平台预分配->镭雕->烧录校验一致性->过点查 SN 主键"端到端防错 |
| 返工品追溯隔离 | 返工板要有返工身份标记，不能混入正常追溯流；返工次数超限要拦截。当前有返工/返工上下文，但**返工品与正常品的追溯隔离边界**没强调 | 🟡 | 讲"返工身份贯穿追溯、返工次数上限拦截、返工品单独追溯视图" |
| 数据一致性边界（DB+缓存+事件+指令） | 过站判定要写 DB、刷缓存、投事件、下发设备指令，**四者部分失败时**怎么保证不出"判定通过但没拦住"的灾难。当前 Outbox 解决了 DB+事件，但**缓存+指令**的一致性没讲 | 🟡 | 讲"Outbox 管 DB+事件、缓存靠事件订阅最终一致、指令靠确认+联锁，三者失败语义不同" |

### 10.4 优先补强建议

**最值得补的 4 个（真车间、高话术价值、当前盲区）**：

1. **过站离线降级 / 断网自治**（HA）-- 制造业 HA 头牌，一讲就知道下过车间。
2. **防错指令可靠送达 + 设备联锁**（HR+HA）-- 把"逻辑门禁"升级到"物理联锁"三级防错，段位明显高。
3. **炉温实时 SPC + 超标停线**（HC+HR+HA 三高叠加）-- 采集/判定/指令三段职责讲清，最显架构力。
4. **追溯反向圈定（受影响批次隔离）**（HR）-- 客诉场景，MES 核心价值的杀手锏。

这 4 个共同点：都不是"采集侧"的事，而是**过站执行 + 物料防错**侧--正好补上设备管理服务之外的盲区，让"高并发/高可用/高可靠"三条腿在过站侧也立起来。后续生产执行服务、物料上下文事件风暴补全时，建议优先把这 4 个场景显式建模。
