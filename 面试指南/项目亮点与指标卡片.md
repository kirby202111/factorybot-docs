## 1. 30 秒电梯陈述

> 用在简历项目描述开头、面试开场自我介绍。

"我用 **事件风暴 + DDD** 设计了一套面向 **PCBA 电子制造 + 整机组装** 混合型车间的 MES 系统，拆分为 **3 个微服务、14 个限界上下文**，每个上下文都有完整的事件风暴文档和聚合建模。核心解决三件事：**全链路追溯**（物料->批次->过点->测试->单件）、**过点防错**（设备/工艺/质量/首件四道门禁）、**实时生产执行**（过点查询 P99 设计目标 ≤200ms）。跨服务一致性用 **Transactional Outbox + Kafka** 保证业务状态与事件原子投递，消费端 event_id 幂等。**高并发场景识别得很清楚**：高频设备采集（设计容量目标 200 台设备在线 / 万级报文每秒）走边缘网关缓冲 + Kafka 直连，与低频过点主事务解耦，且明确不走 Outbox。"

**四个抓手**：14 上下文 / Outbox 可靠消息 / 过点 200ms / 采集链路高并发解耦设计。

## 2. 5 分钟深聊（按模块展开）

### 2.1 领域建模深度

- **3 服务 14 限界上下文**，事件风暴文档全覆盖（[领域模型/](../领域模型/) 目录可查）。
- 服务划分依据**变化频率与延迟要求**：
  - 制造资源服务：生产执行数据基座，**配置型主数据为主 + 混合形态**--工艺/质量规则写少读多，但物料含库存事实源（中频写入 + 最终一致消耗）、质量含业务判定（中频 + 准实时流式批量异常识别）。相对过点/采集仍属低频，但**非纯写少读多**。闪光点见 [制造资源服务·面试闪光点](制造资源服务-面试闪光点.md)。
  - 设备管理服务：设备全生命周期 + 运维中心（台账/数据接入/点检保养/计量检定/维修）。
  - 生产执行服务：现场执行引擎（工单/过点/在制品/首件/返修/返工）。
- 每个上下文明确**聚合根 / 实体 / 值对象 / 领域事件 / 不变式**，例如维修上下文有 5 个聚合根 + 23 条不变式（三段式：11 INV + 3 BIZ + 9 INV-CX），状态机含单向流转与两条可逆边。
- **限界上下文边界讲得清**：为什么维修不放进点检保养？——触发机制不同（被动事件驱动 vs 主动计划驱动）、流程骨架不同、SLA 管控逻辑不同，混合会互相污染（[维修上下文.md](../领域模型/设备管理服务/事件风暴/维修上下文.md) §0）。

### 2.2 跨服务协作与一致性

- **零分布式事务**：过点主事务内只写本地 DB，跨服务一律走事件订阅或 REST 查询（[领域总览.md](../领域模型/领域总览.md) §5.3）。
- **缓存 + 降级**：工艺路线、设备状态本地缓存优先，缓存未命中降级远程查询（工艺 ≤500ms，设备 ≤200ms）。
- **版本一致性**：过点记录绑定 `routeVersion`，工艺变更只影响变更后首次过点的在制品，历史追溯不受影响（§5.1）。
- **领域事件驱动协作**：工艺版本生效事件刷新工艺缓存；设备状态变更事件刷新设备缓存；维修完成事件驱动台账恢复资产。

### 2.3 可靠消息（最大架构闪光点）

- **Transactional Outbox**：业务状态变更与 outbox_event 写入同一本地事务，崩溃窗口零丢失（[消息处理实现说明.md](../实现说明/业务事件/消息处理实现说明.md) §1）。
- **Outbox 状态机**：PENDING -> PUBLISHING -> SENT，失败 RETRYABLE，重试耗尽 DEAD_LETTER，PUBLISHING 锁超时可恢复。
- **至少一次 + 幂等**：消费端 `event_id + consumer_group` 去重，业务处理与幂等记录同事务，手动 ack offset。
- **聚合根纯洁**：聚合根不依赖 KafkaTemplate / OutboxRepository，只返回领域事件，由应用服务编排 outbox 写入。
- **可观测闭环**：9 项指标 + 6 类告警（DEAD_LETTER>0、最老 PENDING 超 1 分钟、PENDING 持续增长等）。

### 2.4 业务能力（讲覆盖面，不编数字）

- **两段式全链路追溯**：前段 PCBA（SMT/AOI/SPI）+ 后段整机组装，物料->批次->过点->测试结果->单件身份贯通。
- **过点防错四道门禁**：设备可用性、工艺路线版本、质量门禁规则、首件放行——任一不通过即拦截。
- **运维 SLA 管控**：维修工单按故障分级映射 SLA（CRITICAL 响应 15min/修复 2h），超时自动升级 L1->L2->L3->外协（[维修上下文.md](../领域模型/设备管理服务/事件风暴/维修上下文.md) §2.1）。
- **跨上下文自治协作**：维修上下文只发布 `ScrapRecommendation` 建议但不执行报废，报废审批归台账上下文，审批结果回流驱动工单关单/退回诊断。

### 2.5 高并发采集链路（真正的吞吐挑战）

> 这是项目里**唯一**真正高并发的链路。关键不是喊 QPS，而是**识别出"高频采集"与"低频过点"两种并发特征，用不同方案**——这才是架构能力。

**两种链路对比**：

| 维度 | 高频采集链路（设备数据接入上下文） | 低频业务链路（过点/工单/维修） |
|------|-------------------------------|--------------------------|
| 触发源 | 设备主动上报/秒级状态流/每板事件 | 人工扫码、人工派工 |
| 吞吐量级 | 万级报文/秒（设计容量） | 每工位几秒一次 |
| 可靠性方案 | 边缘缓冲 + 断点续传 + Kafka 直连 | Transactional Outbox + 幂等消费 |
| 是否走 Outbox | **不走**（高频原始数据走 Outbox 会拖垮 DB） | 走 |
| 事务边界 | 采集与过点解耦，独立服务独立事务 | 过点主事务内零分布式事务 |

依据：[领域总览.md](../领域模型/领域总览.md) §5.3"设备级高频数据采集属于设备管理服务，与生产过点解耦"；[消息处理实现说明.md](../实现说明/业务事件/消息处理实现说明.md) §14 第 5 条"高频原始采集数据不要走 Outbox"。

**高并发架构决策（每个都绑一个吞吐/成本问题）**：

1. **采集只搬运不解释**——焊接温度阈值、NG 判定不写进采集器，业务语义留下游。否则工艺一改就要改驱动，采集器成了演化瓶颈（[设备数据接入.md](../领域模型/设备管理服务/事件风暴/设备数据接入上下文.md) §0）。
2. **边缘网关缓冲 + 断点续传**——`EdgeBuffered` -> `BackfillCursor` 单调递增游标，断网时数据落边缘缓存，恢复后 `BackfillCompleted` 补齐再放新。网络抖动不丢数据、不堵主流程（§2.3）。
3. **大文件/曲线不进主流**——电批扭矩曲线（数百点/枪）只携带峰值 + URI；固件文件、烧录日志走对象存储，主流只承载 URI + 校验和。**这是吞吐与成本的核心折衷**（§3.5、§3.7）。
4. **平台层去重 + 乱序矫正**——`msg_id` 全局唯一去重（INV-04），乱序窗口缓冲 `LateArrivalReordered`。补传数据天然会乱序到达（§2.3）。
5. **冷热分层**——老化房数据极易撑爆时序库，原始数据落冷热分层，降采样/聚合由存储策略统一规则，不在事件载荷里"提前聚合"（§3.9）。
6. **采集与资产视角分离**——`EquipmentOnline ≠ AssetCommissioned`（INV-CX-08 设备数据接入 / INV-CX-04 台账），通信视角与资产视角独立状态机。断网时资产仍 Commissioned 但 Offline，两套状态不互相污染（§2.2.1）。

**为什么这套设计扛得住高并发**：把吞吐压力挡在边缘网关（缓冲、聚合、大文件剥离），到平台的是已结构化、已去重、已瘦身的事件流；平台侧只做去重/乱序/落库/分发，不解释业务。过点链路因为不被采集拖累，才能稳在 ≤200ms。

## 4. 追问防守 Q&A

**Q：14 个限界上下文会不会过度设计？**
A：不是为拆而拆。划分依据是**变化频率和延迟要求**差异：配置数据（工艺/物料）写少读多，单独成服务避免被高频过点拖垮；设备运维和现场执行的关注点完全不同（资产视角 vs 执行视角）。每个上下文有独立的统一语言和聚合，边界清晰——比如维修和点检保养虽然都碰设备，但触发机制（被动 vs 主动）、流程骨架、SLA 逻辑完全不同，合并会互相污染。

**Q：Outbox 比直接发 Kafka 好在哪？具体解决什么问题？**
A：解决"DB commit 成功但 Kafka 没发出去"的崩溃窗口。把业务表更新和 outbox_event 插入放同一本地事务，要么一起成功要么一起回滚。未发布事件留在 outbox 表，后台 Publisher 继续投递。代价是多一次 DB 写和异步延迟，所以**只用于业务契约事件，高频原始采集数据不走 Outbox**（[消息处理说明](../实现说明/业务事件/消息处理实现说明.md) §14 第 5 条）。

**Q：消费端怎么保证幂等？**
A：`event_id + consumer_group` 唯一键。消费时先插幂等记录再执行业务，同事务提交后手动 ack offset。唯一键冲突说明处理过，直接 ack。commit 成功但 ack 前崩溃，Kafka 重投后靠幂等表跳过（§6）。

**Q：过点 200ms 怎么保证？**
A：本地缓存优先（工艺路线、设备状态都订阅事件维护本地副本），命中缓存就是本地内存查询。缓存未命中才降级远程 REST，那是 ≤500ms 的兜底路径，不是主路径。过点主事务内不引入跨服务调用，TestResult 写入与过点判定同本地事务（§5.3）。

**Q：工艺变更会不会影响在制品？**
A：不会。过点记录保存 `routeVersion`，历史追溯按当时版本回放。工艺版本变更只影响**变更后首次过点**的在制品，已经在制的按原版本走完（§5.1）。

**Q：报废流程为什么不在维修上下文里做完？**
A：职责分离。维修上下文的视角是"故障怎么修"，只发布 `ScrapRecommendation` 建议；资产报废审批与执行归台账上下文（资产管理视角）。审批结果通过 `eam.asset.scrap` 主题回流，维修工单靠 `ScrapDecisionProjection` 读模型订阅后驱动关单或退回诊断（[维修上下文.md](../领域模型/设备管理服务/事件风暴/维修上下文.md) §2.6、INV-CX-01/02）。两个上下文共享 asset_id 但视角不同，避免事件混淆。

**Q：状态机里哪些边可逆？**
A：维修工单状态机里只有两条可逆边：`ReopenRepairOrder`（验证失败回退维修）和报废驳回后 `ReopenForRediagnosis`（退回诊断）。其余单向流转，CLOSED 是终态，之后任何事件拒收（INV-03）。可逆边少说明流程刚性，符合车间防错要求。

**Q：采集链路 1 万报文/秒怎么扛？**
A：压力主要挡在边缘网关，不是平台硬抗。三招：①边缘缓冲 + 断点续传，断网数据落网关本地，恢复后按 `BackfillCursor` 补齐；②大文件和高密度曲线不进主流——电批扭矩曲线数百点/枪只带峰值+URI，固件和烧录日志走对象存储，主流只过 URI+校验和；③采集只搬运不解释，业务判定留下游，采集器不背业务变化。到平台的是已结构化、已瘦身的事件流，平台只做去重/乱序/落库/分发。所以这个 1 万是**设计容量目标**，按 10 条线假设估算，不是线上实测。

**Q：高频采集为什么不走 Outbox？**
A：Outbox 的代价是每条事件多一次 DB 写（业务表+outbox 表同事务），适合低频业务契约事件。高频采集如果走 Outbox，DB 会先被 outbox 表写爆。所以采集链路用"边缘缓冲 + Kafka 直连"换吞吐，可靠性靠边缘断点续传 + 平台 `msg_id` 去重 + 幂等消费保证，不靠 Outbox 的强一致（[消息处理说明](../实现说明/业务事件/消息处理实现说明.md) §14 第 5 条）。这是用两种方案对应两种并发特征的刻意选择。

**Q：采集和过点为什么必须解耦？**
A：两者的并发特征和 SLA 完全不同。采集是高频持续流（秒级状态+每板事件），过点是低频人工触发但要求 ≤200ms 响应。如果耦合，采集的吞吐压力会拖垮过点主事务，过点就不可能稳在 200ms。所以 [领域总览](../领域模型/领域总览.md) §5.3 明确"设备级高频数据采集属于设备管理服务，与生产过点解耦"，过点主事务内零分布式事务，需要设备实时数据时按需 REST 查询采集侧（≤200ms）。

**Q：断网恢复后数据乱序怎么处理？**
A：补传数据的时间戳在原始区间内，但到达平台会乱序。平台层做两件事：①`msg_id` 去重，重复补传的直接丢弃（`DuplicateDiscarded`）；②乱序窗口缓冲，按 `source_ts` 矫正（`LateArrivalReordered`）。运行时长聚合那边，补传时段不重复计算，因为时间戳已在原始区间内（[设备数据接入.md](../领域模型/设备管理服务/事件风暴/设备数据接入上下文.md) §2.3、§2.4）。

**Q：设备掉线了，资产还算不算可用？**
A：这是两个视角，不能混。采集侧 `EquipmentOnline` 是通信视角（连接通不通），台账侧 `AssetCommissioned` 是资产视角（能不能用）。一台资产可能 Commissioned 但 Offline（断网），也可能 Online 但 Suspended（维修自检中）。两者独立状态机，互不为充要条件（INV-CX-04 台账 / INV-CX-08 设备数据接入）。掉线只触发通信降级和补传，资产可用性由台账综合所有阻塞维度判定。

## 5. 红线：这些数字不能编

- ❌ "良率提升 X%"——除非有真实车间 SPC 数据。
- ❌ "返工率下降 Y%"——除非有上线前后对比。
- ❌ "线上跑了 N 万 QPS / 我们扛住了 1 万并发"——**除非真上线压测过**。这是设计阶段项目，没上线就是没上线。
- ❌ "节省 N 万成本"——除非财务口径确认。

**高并发数字的正确讲法**（这是唯一可以给具体数字又不怕追问的口径）：
- ✅ "按 10 条线车间规模**假设**，采集链路**设计容量目标**约 1 万报文/秒、200~500 台设备在线。" —— 带"假设"和"设计目标"两个限定词。
- ❌ "我们系统支持 1 万 QPS。" —— 没假设、没口径，听着像线上实绩，一问就穿。

被问到"线上跑过吗"时，老实说："这是设计阶段的容量规划，按车间规模假设估算，没上线实测。重点是架构上识别出高频采集和低频过点两种并发特征，用不同方案应对。"——**诚实 + 体现架构判断力，比硬吹数字得分高**。

**替代话术**：被问到业务效果时，说"这是设计阶段项目，重点是架构和领域建模的完整度，业务效果需要在真实车间上线后用 SPC 数据验证"——诚实且不丢分。
