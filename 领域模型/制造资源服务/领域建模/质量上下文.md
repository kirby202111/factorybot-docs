## 0. 建模总览

本域是制造资源服务下的**质量标准与业务判定子域**，是 PCBA + 整机组装混合型车间所有"质量怎么判、缺陷怎么分、门禁怎么配、TestResult 的业务语义是什么、批量异常怎么识别"的权威源。核心职责管理两类问题：**(1) 配置问题**——检验标准、缺陷分类字典、质量门禁规则、放行授权策略的定义与发布；**(2) 判定问题**——消费过点执行上下文 `TestResult` 翻译为业务判定（`QualityVerdict` + 缺陷分类），并基于缺陷累积分析识别批量质量异常。即"**检验标准是什么、缺陷怎么分类、门禁规则怎么配、TestResult 的业务判定结果是什么、批量异常怎么识别**"；**不负责**工序定义与工艺路线编排（归工艺管理上下文，本上下文以 `quality_gate_rule_id` 被其步骤绑定引用）、物料主数据与库存事实源（归物料上下文）、过点判定与防错校验执行与放行/拦截决策（归过点执行上下文，本上下文仅发布规则供其 `QualityGateCache` 缓存消费；过点级同步门禁判定 `QualityGateEvaluated` 由过点执行上下文基于缓存规则执行，本上下文不参与过点主事务）、测试数据接入适配层与 TestResult 结构化（归过点执行上下文，本上下文仅消费其产出的 `TestResult` 做业务判定）、在制品位置投影（归在制品追踪上下文）、首件检验流程编排与首件放行门禁判定（归首件处理上下文，本上下文仅发布首件检验标准与首件单元业务判定结果）、单件返修任务执行（归返修上下文，本上下文仅提供缺陷分类字典辅助诊断）、批量返工工单执行（归返工上下文，本上下文仅发布批量异常信号供其评估生成返工工单）。本上下文是**配置型主数据 + 业务判定**混合上下文，写少读多（主数据）与中频写入（业务判定/异常分析）并存，对外以"规则生效/弃用事件 + 检验标准变更事件 + 质量业务判定事件 + 批量异常信号事件"为协作契约。

本上下文与过点执行上下文的协作是本域最关键的边界：**同步门禁 vs 异步判定职责切分**。过点执行上下文基于 `QualityGateCache` 做**同步门禁判定**（`QualityGateEvaluated` PASS/HOLD/BLOCK，驱动过点放行/拦截，在过点主事务内，"流量控制"功能，要求快，**权威**）；本上下文消费 `TestResult` 做**异步业务判定**（`QualityVerdictIssued` PASS/HOLD/BLOCK + 缺陷分类，供首件检验汇总/缺陷统计/SPC，"质量评估与记录"功能，要求深，**记录性**）。两者**不要求强一致**（INV-CX-04）——同步门禁为权威驱动过点决策，异步判定为记录性不覆盖过点决策；异步 BLOCK 判定不回溯拦截已放行的过点，而是记入缺陷统计供后续批量异常分析触发返工。

## 1. 聚合根

### 1.1 InspectionStandard（检验标准）

**一致性边界**：单个检验标准的身份、类型、检验项与接收准则、生命周期状态。

**职责**：定义可复用检验标准（首件检验/来料检验 IQC/常规过点检验）；含检验项（`InspectionItem`）与接收准则（`AcceptanceCriterion`）；ACTIVE/DEPRECATED 生命周期；首件检验标准变更通知首件处理上下文刷新 `InspectionStandardCache`。

```yaml
InspectionStandard:
  # ─── 标识 ───
  standard_id:    InspectionStandardId   # 检验标准唯一标识（聚合根ID）
  name:           String
  type:           InspectionStandardType  # FIRST_ARTICLE / IQC / ROUTINE（不可变更 INV-01）
  segment:        Segment?                # PCBA / ASSEMBLY（段标签，缺陷字典统一性）

  # ─── 检验项（聚合内实体）───
  inspection_items[]:   List<InspectionItem>
  acceptance_criteria[]: List<AcceptanceCriterion>

  # ─── 状态 ───
  state:          InspectionStandardState  # ACTIVE / DEPRECATED

  # ─── 审计 ───
  defined_by:     String
  defined_at:     DateTime
  updated_at:     DateTime?
```

**行为**：
- `define(name, type, inspection_items, acceptance_criteria, defined_by)` -> 发出 `InspectionStandardDefined`（前置：`standard_id` 全局唯一 BIZ-01；`type` 不可变更；-> `ACTIVE`）
- `update(changed_fields, updated_by)` -> 发出 `InspectionStandardUpdated`（前置：当前 `ACTIVE`；影响引用该标准的草稿规则；首件检验标准变更通知首件处理上下文刷新缓存）
- `deprecate(reason)` -> 发出 `InspectionStandardDeprecated`（前置：当前 `ACTIVE`；-> `DEPRECATED`；限制新草稿规则引用，已生效规则不受影响 INV-04）

> 首件检验标准（`FirstArticleInspectionStandard`，`type=FIRST_ARTICLE`）变更时额外发布 `FirstArticleInspectionStandardUpdated`/`Deprecated` 到 `quality.standard.fai`，供首件处理上下文刷新 `InspectionStandardCache`。IQC 标准（`IqcStandard`，`type=IQC`）供 `IqcRequest` 引用。

> 🔴 **热点：检验标准的粒度**（事件风暴 §2.1）——建议立场已固化：**通用工序级标准 + 门禁规则承载产品差异**（与工艺管理上下文工序粒度同构），避免标准爆炸。

> 🔴 **热点：缺陷分类字典的统一性**（事件风暴 §2.1）——建议立场已固化：**统一字典 + 段标签**（`segment: PCBA/ASSEMBLY`），便于跨段缺陷统计，同时支持按段过滤。

### 1.2 DefectCatalog（缺陷分类字典）

**一致性边界**：单个缺陷分类字典的分类项、严重度与生命周期状态。

**职责**：定义可复用缺陷分类字典（如 SMT 焊点缺陷字典、组装缺陷字典）；含缺陷分类项（`DefectCategory`）与严重度分级；ACTIVE/DEPRECATED 生命周期。供 `QualityGateRule.DefectMapping` 引用 + 返修上下文 REST 查询辅助诊断。

```yaml
DefectCatalog:
  # ─── 标识 ───
  catalog_id:     DefectCatalogId        # 字典唯一标识（聚合根ID）
  name:           String
  segment:        Segment?               # PCBA / ASSEMBLY 段标签

  # ─── 分类项（聚合内实体）───
  categories[]:   List<DefectCategory>

  # ─── 状态 ───
  state:          DefectCatalogState     # ACTIVE / DEPRECATED

  # ─── 审计 ───
  defined_by:     String
  defined_at:     DateTime
  updated_at:     DateTime?
```

```yaml
DefectCategory:
  code:       String                     # 缺陷编码（如 solder_bridge / missing_component）
  name:       String                     # 缺陷名称（如 桥接 / 缺件）
  severity:   DefectSeverity             # CRITICAL / MAJOR / MINOR
```

**行为**：
- `define(name, categories[], defined_by)` -> 发出 `DefectCatalogDefined`（-> `ACTIVE`）
- `update(changed_categories[], updated_by)` -> 发出 `DefectCatalogUpdated`（影响引用该字典的草稿规则；业务判定使用最新字典）
- `deprecate(reason)` -> 发出 `DefectCatalogDeprecated`（限制新草稿规则引用；已生效规则不受影响）

> 业务判定使用最新字典（已生效规则引用的字典变更不回写规则 INV-04，但判定时读最新字典做缺陷分类）。

### 1.3 QualityGateRule（质量门禁规则·版本化）

**一致性边界**：单个规则版本的范围绑定、判定逻辑、缺陷映射、HOLD 授权绑定与完整生命周期。**本上下文核心配置聚合根**。

**职责**：编排质量门禁规则（含判定逻辑 `GateLogic` + 缺陷映射 `DefectMapping` + HOLD 授权绑定 `HoldAuthorizationBinding`）；承载 DRAFT->SUBMITTED->ACTIVATED->DEPRECATED->ARCHIVED 完整状态机（与工艺管理 RouteVersion、物料 Bom 同构）；生效后内容不可变（INV-04）；生效发布 `QualityGateRuleActivated` 供过点执行刷新 `QualityGateCache` + `QualityGateDeprecated` 供工艺管理标记 stale。

```yaml
QualityGateRule:
  # ─── 标识 ───
  rule_id:        QualityGateRuleId      # 规则逻辑标识（跨版本共享，不变）
  version_no:     Integer                # 版本号（同 rule 内递增）
  rule_version_id: QualityGateRuleVersionId  # 规则版本唯一标识（聚合根ID）

  # ─── 范围 ───
  rule_type:      RuleType               # 规则类型
  station_type:   StationType            # 工位类型
  product_scope:  ProductScope           # 产品范围（product_id / product_family）

  # ─── 判定逻辑（聚合内实体，仅 DRAFT 态可变更 INV-04）───
  gate_logic:           GateLogic        # 判定逻辑（verdict_rules + hold_conditions）
  defect_mapping:       DefectMapping    # 原始判定/测量项 -> 缺陷分类映射
  hold_authorization:   HoldAuthorizationBinding?  # HOLD 授权绑定

  # ─── 状态 ───
  state:          QualityGateRuleState   # DRAFT / SUBMITTED / ACTIVATED / DEPRECATED / ARCHIVED
  effective_at:   DateTime?
  superseded_by:  QualityGateRuleVersionId?  # 被哪个新版本取代（DEPRECATED 时；null=整体弃用）
  rejection_notes: String?

  # ─── 审计 ───
  created_by:     String
  created_at:     DateTime
  submitted_by:   String?
  submitted_at:   DateTime?
  activated_by:   String?
  deprecated_at:  DateTime?
```

**行为**：
- `create(rule_type, station_type, product_scope, created_by)` -> 发出 `QualityGateRuleCreated`（前置：同 rule 无 ACTIVATED 冲突或为显式升级；-> `DRAFT`）
- `configureGateLogic(verdict_rules, hold_conditions, updated_by)` -> 发出 `GateLogicConfigured`（前置：当前 `DRAFT` INV-04）
- `configureDefectMapping(mapping_entries, updated_by)` -> 发出 `DefectMappingConfigured`（前置：当前 `DRAFT`；映射引用的缺陷分类来自 `DefectCatalog`）
- `bindHoldAuthorization(policy_id, updated_by)` -> 发出 `HoldAuthorizationBound`（前置：当前 `DRAFT`；`OverrideAuthorizationPolicy` 存在且有效 INV-08）
- `submitReview(submitted_by)` -> 发出 `RuleReviewSubmitted`（前置：当前 `DRAFT`；判定逻辑完整（GateLogic 非空）且引用校验满足（InspectionStandard/DefectCatalog 非 DEPRECATED，OverrideAuthorizationPolicy 存在有效）INV-06；-> `SUBMITTED`；经 `RuleValidationService` 预校验）
- `activate(activated_by)` -> 发出 `QualityGateRuleActivated`（前置：当前 `SUBMITTED`；引用校验全通过 INV-07/INV-08；-> `ACTIVATED`；设置 `effective_at`；生效后内容不可变 INV-04；同 rule_id 唯一 ACTIVE BIZ-02，经 `RuleActivationService` 同事务弃用旧版本）
- `rejectReview(rejection_notes, rejected_by)` -> 发出 `RuleReviewRejected`（前置：当前 `SUBMITTED`；-> `DRAFT`）
- `rejectActivation(failed_refs[])` -> 发出 `ActivationRejected`（前置：当前 `SUBMITTED`；生效校验失败；-> `DRAFT`）
- `rejectSubmission(failed_checks[])` -> 发出 `ReviewSubmissionRejected`（前置：当前 `SUBMITTED`；提交预校验失败；-> `DRAFT`）
- `deprecate(reason, superseded_by?, deprecated_by)` -> 发出 `QualityGateDeprecated`（前置：当前 `ACTIVATED`；-> `DEPRECATED`；`superseded_by`——新版本生效自动触发则非 null（被取代，内部），手动整体弃用则 null（整体退役，通知工艺管理标记 stale + 过点执行移除缓存）；弃用不删除内容 INV-04）
- `archive()` -> 发出 `QualityGateRuleArchived`（前置：当前 `DEPRECATED` 或 `DRAFT`；-> `ARCHIVED`，终态 INV-03）
- `abandonDraft()` -> 发出 `QualityGateRuleArchived`（前置：当前 `DRAFT`；-> `ARCHIVED`，终态）

> **唯一 ACTIVE 版本是跨实例不变式（BIZ-02）**：`QualityGateRule` 聚合自身无法校验"同 rule_id 仅一个 ACTIVATED"——由 `RuleActivationService` 在生效时查询读模型 + 数据库唯一索引 `(rule_id, status=ACTIVATED)` 共同保证，新版本生效同事务自动 Deprecate 旧版本（outbox）。

> **生效后不可变（INV-04）**：`QualityGateRule` 在 `ACTIVATED`/`DEPRECATED`/`ARCHIVED` 态拒收任何 `configureGateLogic`/`configureDefectMapping`/`bindHoldAuthorization` 命令，保证过点执行上下文 `CheckpointRecord` 的规则快照可永久回溯。

> 🔴 **热点：是否允许同 rule 并存多个 ACTIVATED 版本**（事件风暴 §2.2）——建议立场已固化：**按 rule_id 维度唯一 ACTIVE**，同一规则同时只能有一个生效版本；新版本生效自动 Deprecate 旧版本。与工艺管理 RouteVersion `(route_id, route_type)`、物料 Bom `(product_id, bom_type)` 维度一致。BIZ-02。

> 🔴 **热点：规则"修订"与"弃用"的语义区分**（事件风暴 §2.2）——建议立场已固化：**修订 = 新版本生效**（`QualityGateRuleActivated`，rule_id 不变，version 递增），过点执行上下文刷新缓存，工艺管理上下文不标记 stale（rule_id 引用仍有效）；**弃用 = 规则整体退役**（`QualityGateDeprecated`，`superseded_by=null`，无后继版本），工艺管理上下文标记 stale_reference，过点执行上下文移除缓存。两者事件不同，消费方按需订阅。

### 1.4 QualityVerdict（质量业务判定）

**一致性边界**：单次业务判定的 TestResult 关联、业务判定结果、缺陷记录。

**职责**：消费过点执行上下文 `TestResult`（含 `raw_verdict` 原始判定），结合 `DefectCatalog` 与 `QualityGateRule`，翻译为业务判定（`business_verdict` + `defect_records[]`）；不可变；中频写入。发布 `QualityVerdictIssued` 供首件处理上下文汇总 + 数据应用上下文缺陷统计/SPC。

```yaml
QualityVerdict:
  # ─── 标识 ───
  verdict_id:     VerdictId              # 业务判定唯一标识（聚合根ID）

  # ─── 关联 ───
  test_id:        TestId                 # 关联 TestResult（过点执行上下文）
  source_test_result_id: SourceTestResultId  # 幂等去重键（BIZ-03）
  sn:             String                 # 单件序列号
  station_id:     String
  work_order_id:  WorkOrderId
  product_id:     ProductId

  # ─── 业务判定 ───
  business_verdict: GateVerdict          # PASS / HOLD / BLOCK
  defect_records[]: List<DefectRecord>   # 缺陷记录（含分类 + 严重度）

  # ─── 规则快照 ───
  rule_id:        QualityGateRuleId      # 判定所依据的规则
  rule_version:   Integer                # 规则版本快照

  # ─── 审计 ───
  verdict_ts:     DateTime
```

```yaml
DefectRecord:
  defect_code:    String                 # 缺陷编码（与 DefectCatalog 对齐）
  severity:       DefectSeverity         # CRITICAL / MAJOR / MINOR
  location:       String?                # 缺陷位置（如位号）
  measured_value: Decimal?               # 测量值
```

**行为**：
- `issue(test_id, sn, station_id, work_order_id, product_id, raw_verdict, measured_items, rule_id, rule_version, defect_records, business_verdict)` -> 发出 `QualityVerdictIssued`（前置：同一 TestResult 不重复判定 BIZ-03；判定不可变；含缺陷分类与业务判定结果；经 `QualityVerdictService` 编排）

> **判定不可变**（BIZ-03）：一经发布不可修改。`business_verdict=BLOCK` 异步到达时过点可能已放行——**不回溯拦截已放行的过点**，而是记入缺陷统计供后续批量异常分析（§1.5）触发返工（🔴 §2.4 热点立场）。

> 🔴 **热点：业务判定是否对所有过点 TestResult 执行**（事件风暴 §2.4）——建议立场已固化：**对所有 TestResult 执行业务判定**（缺陷统计需要全量数据），判定逻辑轻量（规则匹配 + 缺陷映射，无复杂计算）。若性能压力，可按工位/产品配置采样判定。

> 🔴 **热点：raw_verdict 与 business_verdict 的映射复杂度**（事件风暴 §2.4）——建议立场已固化：**简单映射走 `DefectMapping` 查表**（规则内配置），**复杂判定走策略引擎**（本上下文内嵌轻量策略引擎，支持阈值/逻辑表达式）。

### 1.5 BatchQualityAnomaly（批量质量异常）

**一致性边界**：单次批量异常识别的影响范围、受影响 SN 清单、缺陷频次。

**职责**：基于缺陷累积（`QualityVerdict.defect_records[]` + 返修诊断回流 + 首件结果回写）分析缺陷影响范围（单件偶发 vs 批次性系统性），识别批量异常并发布信号供返工上下文评估生成返工工单。

```yaml
BatchQualityAnomaly:
  # ─── 标识 ───
  anomaly_id:     AnomalyId              # 异常唯一标识（聚合根ID）

  # ─── 范围 ───
  work_order_id:  WorkOrderId
  station_id:     String
  defect_code:    String                 # 缺陷编码

  # ─── 影响范围 ───
  anomaly_scope:  AnomalyScope           # SINGLE_INCIDENT / BATCH_SYSTEMIC
  affected_sn_list[]: List<String>       # 已确认缺陷 SN + 疑似范围 SN（🔴 §2.5 热点立场）

  # ─── 检测依据 ───
  defect_frequency: Decimal              # 缺陷频次/占比
  threshold_breached: String             # 触发的阈值规则
  source_verdict_ids[]: List<VerdictId>  # 来源业务判定

  # ─── 审计 ───
  detected_at:    DateTime
```

**行为**：
- `detect(work_order_id, station_id, defect_code, anomaly_scope, affected_sn_list, defect_frequency, threshold_breached, source_verdict_ids)` -> 发出 `BatchQualityAnomalyDetected`（前置：同一 `(work_order_id, station_id, defect_code)` 异常不重复识别 BIZ-05；`anomaly_scope=BATCH_SYSTEMIC` 必带 `affected_sn_list[]` + `defect_frequency` + `threshold_breached`；经 `BatchAnomalyDetectionService` 编排）

> **单件返修 vs 批量返工的边界判定**（事件风暴 §2.5/§10）：本上下文做缺陷影响范围分析——
> - **单件偶发缺陷**（`SINGLE_INCIDENT`）：**不发布批量异常信号**；通过过点执行上下文的质量类拦截分流（`mes.unit.routed-to-rework`）触发返修上下文单件返修。
> - **批次性系统性缺陷**（`BATCH_SYSTEMIC`）：发布 `BatchQualityAnomalyDetected` 信号触发返工上下文批量返工工单。
>
> 判定逻辑归本上下文，返修/返工上下文只接收已判定的触发信号。

> 🔴 **热点：异常检测的阈值与规则配置**（事件风暴 §2.5）——建议立场已固化：**归本上下文**（`BatchAnomalyDetectionService` 内嵌规则，质量工程师配置阈值），阈值按工序/产品段差异化。

> 🔴 **热点：异常检测的时效性**（事件风暴 §2.5）——建议立场已固化：**准实时流式**（每条 `QualityVerdict` 到达即增量累积 + 阈值判定），保证批量异常及时识别。若流式压力大，退化为分钟级窗口批量分析。

> 🔴 **热点：affected_sn_list 的准确性**（事件风暴 §2.5）——建议立场已固化：**已确认缺陷 SN + 疑似范围 SN**（按工序位置推断），返工上下文消费后决定返工 SN 清单。

> 🔴 **热点：缺陷影响范围判定的准确性**（事件风暴 §10）——建议立场已固化：**保守判定**（倾向于批量异常，宁可多返工不可漏检系统性缺陷），并由质量工程师定期复核异常识别记录调优阈值。

### 1.6 IqcRequest（来料质检请求）

**一致性边界**：单次来料质检请求的物料批次关联、检验标准、检验结果与处置。

**职责**：消费采购/仓管系统入库前的质检请求，执行来料检验（IQC），发布结果（PASSED/FAILED）。物料上下文 §2.4.1 已声明"来料质检执行归质量上下文，物料上下文仅接收质检通过后入库的事实"。

```yaml
IqcRequest:
  # ─── 标识 ───
  iqc_request_id: IqcRequestId           # 质检请求唯一标识（聚合根ID）

  # ─── 关联 ───
  part_no:        PartNo                  # 物料编码
  lot_no:         String                  # 批次号
  supplier_id:    SupplierId
  received_qty:   Integer
  iqc_standard_id: InspectionStandardId  # IQC 检验标准（type=IQC）
  source_event_id: String?                # 来源事件ID（幂等去重键 BIZ-04）

  # ─── 状态与结果 ───
  state:          IqcRequestState         # PENDING / PASSED / FAILED
  passed_items[]: List<String?            # PASSED 时
  failed_items[]: List<String>?           # FAILED 时必填
  defect_records[]: List<DefectRecord>?   # FAILED 时
  disposition:    Disposition?            # FAILED 时必填：RETURN/REWORK/SCRAP

  # ─── 审计 ───
  requested_at:   DateTime
  performed_by:   String?
  completed_at:   DateTime?
```

**行为**：
- `request(part_no, lot_no, supplier_id, received_qty, iqc_standard_id?, source_event_id?)` -> 发出 `IqcRequested`（前置：同一触发信号不重复创建 BIZ-04；-> `PENDING`；若未指定 iqc_standard_id 则按 part_no 查 IqcStandard）
- `recordResult(PASSED, passed_items, performed_by)` -> 发出 `IqcCompleted`（前置：当前 `PENDING`；-> `PASSED`；发布到 `quality.iqc.lifecycle`，物料上下文经采购/仓管系统接收入库）
- `recordResult(FAILED, failed_items, defect_records, disposition, performed_by)` -> 发出 `IqcFailed`（前置：当前 `PENDING`；`failed_items[]` + `disposition` 必填 BIZ-04；-> `FAILED`；物料不入库，按 disposition 处理：退货/返修/报废）

> 🔴 **热点：IQC 的触发方式**（事件风暴 §2.6）——建议立场已固化：**采购/仓管系统触发**（来料登记时发起 IQC 请求），IQC 通过后由采购/仓管系统发入库指令到物料上下文。本上下文不直接调用物料上下文入库接口，通过事件解耦。

> 🔴 **热点：IQC 失败后的处理**（事件风暴 §2.6）——建议立场已固化：**本上下文记录检验结果 + 建议 disposition**，最终 disposition 由采购/质量主管审批决定（参考返修上下文报废审批模式）。

> 🔴 **热点：IQC 是否纳入当前阶段**（事件风暴 §2.6）——建议立场已固化：**当前阶段保留 IQC 链路框架**（请求->执行->结果发布），详细检验项配置与 disposition 审批流待后续展开。

### 1.7 OverrideAuthorizationPolicy（放行授权策略）

**一致性边界**：单个放行授权策略的角色权限配置。**完整权限模型暂缓**（事件风暴 §11）。

**职责**：定义 HOLD 状态的人工放行权限规则（哪些角色可授权放行 HOLD 状态的过点）；供 `QualityGateRule.HoldAuthorizationBinding` 引用；供过点执行上下文 `OverrideCheckpoint` 与首件处理上下文 `OverrideGate` 校验授权人权限。

```yaml
OverrideAuthorizationPolicy:
  # ─── 标识 ───
  policy_id:      OverrideAuthorizationPolicyId  # 策略唯一标识（聚合根ID）
  name:           String
  description:    String?

  # ─── 权限配置（完整模型暂缓：角色/双签/多级授权待 SME 决策）───
  authorized_roles[]: List<String>       # 可授权放行的角色（当前阶段轻量模型）
  requires_dual_sign: Boolean            # 是否需双签（暂缓细化）
  effective_from:  DateTime?
  effective_until: DateTime?

  # ─── 状态 ───
  state:          PolicyState            # ACTIVE / DEPRECATED

  # ─── 审计 ───
  defined_by:     String
  defined_at:     DateTime
```

**行为**：
- `define(name, authorized_roles, requires_dual_sign, defined_by)` -> 发出 `OverrideAuthorizationPolicyDefined`（-> `ACTIVE`）
- `update(changed_fields, updated_by)` -> 发出 `OverrideAuthorizationPolicyUpdated`
- `deprecate(reason)` -> 发出 `OverrideAuthorizationPolicyDeprecated`（-> `DEPRECATED`；引用该策略的草稿规则标记 stale，已生效规则不受影响 INV-04）

> 🔴 **热点：HOLD 人工放行的权限模型**（事件风暴 §7）——建议立场已固化：**HOLD 放行权限归本上下文配置**（`OverrideAuthorizationPolicy`）。过点执行上下文的 `OverrideCheckpoint` 与首件处理上下文的 `OverrideGate` 引用本上下文策略校验授权人权限。权限校验是同步 REST 查询（过点放行需实时校验），建议过点执行上下文缓存权限策略。完整权限模型（角色/双签/多级授权）暂缓（事件风暴 §11），待与权限设计/SME 决策。

### 2.2 InspectionStandardType / Segment / RuleType（分类枚举）

```yaml
InspectionStandardType:
  - FIRST_ARTICLE    # 首件检验标准（FirstArticleInspectionStandard）
  - IQC              # 来料检验标准（IqcStandard）
  - ROUTINE          # 常规过点检验标准

Segment:
  - PCBA             # PCBA 段（SMT 焊接/检测类缺陷为主）
  - ASSEMBLY         # 整机组装段（装配/功能类缺陷为主）

RuleType:
  - GATE             # 门禁规则（驱动过点放行/拦截）
  # （随规则类型扩展）
```

> 不可变枚举。`InspectionStandardType` 一经确定不可变更（INV-01）。双段生产架构：PCBA 段与整机组装段的检验标准与缺陷分类分别维护（`segment` 标签），质量门禁规则按工位 × 产品段配置。

### 2.3 状态枚举（基础对象）

```yaml
InspectionStandardState:
  - ACTIVE / DEPRECATED
DefectCatalogState:
  - ACTIVE / DEPRECATED
PolicyState:
  - ACTIVE / DEPRECATED
IqcRequestState:
  - PENDING          # 待检验
  - PASSED           # 检验通过
  - FAILED           # 检验失败（必带 failed_items + disposition）
```

> 不可变枚举。`DEPRECATED` 为终态。弃用限制新草稿规则引用，不回写已生效规则（INV-04）。`IqcRequestState` 单向流转：PENDING -> PASSED/FAILED。

### 2.4 QualityGateRuleState（规则版本状态）

```yaml
QualityGateRuleState:
  - DRAFT            # 草稿，可配置判定逻辑/缺陷映射/授权绑定
  - SUBMITTED        # 已提交审核，待主管决策
  - ACTIVATED        # 已生效，内容不可变（INV-04）
  - DEPRECATED       # 已弃用（被新版本取代 superseded_by≠null / 手动整体弃用 superseded_by=null）
  - ARCHIVED         # 已归档（终态，INV-03）
```

**状态机**（与工艺管理 `RouteVersionState`、物料 `BomVersionState` 同构）：

```
                         [DRAFT]
                           |
            ┌──────────────┼────────────── AbandonDraft ───────────┐
            │              │                                        │
            │      SubmitRuleReview                                  │
            │       (前置: 判定逻辑完整且引用校验满足, INV-06)        │
            │              │                                        │
            │              v                                        │
            │        [SUBMITTED]                                    │
            │              │                                        │
            │     ┌────────┴───────────────┐                        │
            │     v                         v                        │
            │  ActivateQualityGateRule   RejectRuleReview             │
            │  (前置: 引用校验通过,        (审核驳回, 回 DRAFT,        │
            │   INV-07/INV-08)            带 rejection_notes)        │
            │     │                         │                        │
            │     │ ActivationRejected       │                        │
            │     │ (生效校验失败, 回 DRAFT)  │                        │
            │     v                         v                        │
            │  [ACTIVATED]              [DRAFT]                       │
            │     │                                                    │
            │     │ DeprecateQualityGateRule                            │
            │     │ (新版本生效自动触发 superseded_by≠null              │
            │     │  / 手动整体弃用 superseded_by=null)                 │
            │     v                                                    │
            │  [DEPRECATED]                                            │
            │     │                                                    │
            │     │ ArchiveQualityGateRule                             │
            │     v                                                    │
            └─▶ [ARCHIVED] ◀──────────────────────────────────────────┘
                  (终态—之后任何事件均拒收, INV-03)
```

**不变式**：
- `-> DRAFT`（新建）：`create()`，规则类型/工位/产品范围明确、同 rule 无冲突或显式升级
- `DRAFT -> SUBMITTED`：`submitReview()`，前置判定逻辑完整且引用校验满足（INV-06）
- `SUBMITTED -> ACTIVATED`：`activate()`，前置引用校验通过（INV-07/INV-08）；同 rule_id 唯一 ACTIVE（BIZ-02，跨实例）
- `SUBMITTED -> DRAFT`：`rejectReview()`/`rejectActivation()`/`rejectSubmission()`
- `ACTIVATED -> DEPRECATED`：`deprecate()`，新版本生效自动触发（`superseded_by≠null`，被取代）或手动整体弃用（`superseded_by=null`，整体退役）
- `DEPRECATED -> ARCHIVED`：`archive()`
- `DRAFT -> ARCHIVED`：`abandonDraft()`
- `ARCHIVED` 之后任何事件均拒收（终态 INV-03）

### 2.5 GateVerdict / DefectSeverity / AnomalyScope / Disposition（判定枚举）

```yaml
GateVerdict:
  - PASS             # 通过
  - HOLD             # 暂留（待人工放行/复检）
  - BLOCK            # 拦截

DefectSeverity:
  - CRITICAL         # 严重
  - MAJOR            # 主要
  - MINOR            # 次要

AnomalyScope:
  - SINGLE_INCIDENT  # 单件偶发（不发布批量异常信号，过点拦截分流返修）
  - BATCH_SYSTEMIC   # 批次性系统性（发布 BatchQualityAnomalyDetected 触发返工）

Disposition:         # IQC 失败处置
  - RETURN           # 退货
  - REWORK           # 返修
  - SCRAP            # 报废
```

> `GateVerdict` 同时用于过点执行上下文同步门禁（`QualityGateEvaluated`，权威）与本上下文异步判定（`QualityVerdict.business_verdict`，记录性），两者不要求强一致（INV-CX-04）。`AnomalyScope` 决定单件返修 vs 批量返工的边界判定（§1.5）。

### 2.6 GateLogic / DefectMapping / HoldAuthorizationBinding（规则内实体）

```yaml
GateLogic:
  verdict_rules[]:   List<VerdictRule>     # 判定规则（阈值/逻辑表达式 -> PASS/HOLD/BLOCK）
  hold_conditions[]: List<HoldCondition>   # HOLD 条件

VerdictRule:
  condition:    String                     # 逻辑表达式（如 "measured_value > threshold"）
  verdict:      GateVerdict                # 命中时判定结果
  inspection_standard_ref: InspectionStandardId?  # 引用检验标准

HoldCondition:
  condition:    String                     # HOLD 触发条件
  description:  String

DefectMapping:
  mapping_entries[]: List<DefectMappingEntry>  # 原始判定/测量项 -> 缺陷分类映射

DefectMappingEntry:
  source:       String                     # raw_verdict 或 measured_item 键
  defect_code:  String                     # 映射到的缺陷编码（与 DefectCatalog 对齐）
  severity:     DefectSeverity

HoldAuthorizationBinding:
  policy_id:    OverrideAuthorizationPolicyId  # 引用放行授权策略
```

> 隶属于 `QualityGateRule`，仅在 DRAFT 态可变更（INV-04）。`GateLogic` 产出 PASS/HOLD/BLOCK；`DefectMapping` 将原始判定/测量项映射到缺陷分类；`HoldAuthorizationBinding` 引用 HOLD 放行授权策略。简单映射走 `DefectMapping` 查表，复杂判定走策略引擎（🔴 §2.4 热点立场）。

### 2.7 InspectionItem / AcceptanceCriterion / DefectCategory（标准/字典内实体）

```yaml
InspectionItem:
  item_key:     String                     # 检验项键
  name:         String
  method:       String                     # 检验方法

AcceptanceCriterion:
  item_key:     String                     # 关联检验项
```

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 RuleValidationService（规则版本校验服务）

**职责**：编排规则引用完整性校验——提交审核时预校验（INV-06）、生效时引用校验（INV-07/INV-08）。校验失败拒绝 `SubmitRuleReview`/`ActivateQualityGateRule`。

```yaml
RuleValidationService:
  方法:
    precheckOnSubmit(rule_version_id):

      # 1. GateLogic 非空（判定逻辑完整）？
      # 2. InspectionStandard 非 DEPRECATED？
      # 3. DefectCatalog 非 DEPRECATED？
      # 4. OverrideAuthorizationPolicy 存在且有效？

    validateOnActivate(rule_version_id):
      # 生效时引用校验（INV-07/INV-08），同步查本上下文
      # 1. 所有 InspectionStandard 非 DEPRECATED？（INV-07）
      # 2. 所有 DefectCatalog 非 DEPRECATED？（INV-08）
      # 3. OverrideAuthorizationPolicy 存在且有效？（INV-08）

```

> **为什么不放在聚合根内**：引用校验需查询本上下文其它 `InspectionStandard`/`DefectCatalog`/`OverrideAuthorizationPolicy` 实例——单条 `QualityGateRule` 聚合无权查询其它聚合实例。校验是跨聚合编排，归本服务。与工艺管理 `RouteValidationService`、物料 `BomValidationService` 同构。

### 3.2 RuleActivationService（规则版本生效服务）

**职责**：编排规则版本生效——校验通过后激活版本、同事务弃用同 rule 旧版本（BIZ-02 跨实例）、通过事务发件箱发布 `QualityGateRuleActivated` + `QualityGateDeprecated`（INV-CX-02）。

```yaml
RuleActivationService:
  方法:
    activate(rule_version_id, activated_by):
      # 1. 委托 RuleValidationService.validateOnActivate（INV-07/INV-08）
      #    失败 -> rejectActivation -> ActivationRejected（回 DRAFT）
      # 2. 加载 QualityGateRule -> activate(activated_by) -> QualityGateRuleActivated（-> ACTIVATED）
      # 3. 跨实例唯一 ACTIVE 校验（BIZ-02）：
      #    查读模型同 rule_id 的当前 ACTIVATED 版本
      #    + 数据库唯一索引 (rule_id, status=ACTIVATED)
      # 4. 若存在旧 ACTIVATED 版本 -> 同事务 deprecate(superseded_by=新版本) -> QualityGateDeprecated
      # 5. 事务发件箱（INV-CX-02）：QualityGateRuleActivated + QualityGateDeprecated 与状态变更同事务 outbox
      # 6. 发布到 quality.gate.lifecycle
      #    - 过点执行上下文订阅 QualityGateRuleActivated -> RefreshQualityGateCache（rule_id + version 去重）
      #    - 过点执行上下文订阅 QualityGateDeprecated(superseded_by=null) -> 移除 QualityGateCache 中该 rule_id 条目
      #    - 工艺管理上下文订阅 QualityGateDeprecated(superseded_by=null) -> FlagAffectedDrafts（标记 DRAFT stale, INV-04）
```

> **为什么不放在聚合根内**：唯一 ACTIVE 版本是跨实例不变式（BIZ-02），单条 `QualityGateRule` 无权查询同 rule 其它版本实例；自动弃用旧版本是跨聚合编排；事务发件箱发布是跨服务集成。归本服务 + 读模型查询 + 唯一索引共同保证。

> 🔴 **热点：生效事件的载荷大小**（事件风暴 §2.3）——建议立场已固化：**事件载荷只含版本元数据 + 规则摘要**，过点执行上下文刷新缓存时若需详情再 REST 查询本上下文 `QualityGateRuleReadModel`。

> 🔴 **热点：生效发布的事务发件箱**（事件风暴 §2.3，INV-CX-02）——`QualityGateRuleActivated` 的发布与 `QualityGateRule` 状态变更（SUBMITTED->ACTIVATED）+ 旧版本 Deprecate 在同一数据库事务内通过 outbox 保证至少一次投递，消费端幂等处理。与工艺管理 `ProcessRouteActivated`、物料 `BomActivated` 同理（跨上下文统一编号）。

### 3.3 QualityVerdictService（质量业务判定服务）

**职责**：消费过点执行上下文 `TestResultStructured`（含 `raw_verdict` 原始判定），结合 `QualityGateRule`（完整规则）+ `DefectCatalog`（缺陷字典），翻译为业务判定 `QualityVerdict`（含缺陷分类 + 业务判定结果），发布 `QualityVerdictIssued` 供首件处理上下文汇总 + 数据应用上下文缺陷统计/SPC。

```yaml
QualityVerdictService:
  方法:
    onTestResultStructured(test_id, sn, station_id, work_order_id, product_id, raw_verdict, measured_items, source_test_result_id):
      # 来源：过点执行上下文 mes.testresult.structured TestResultStructured
      # 1. 幂等去重：source_test_result_id 去重表（BIZ-03）
      # 2. 查询该 station_id × product_scope 的 ACTIVE QualityGateRule + DefectCatalog
      # 3. 应用 gate_logic + defect_mapping 翻译业务语义：
      #    - 简单映射走 DefectMapping 查表（raw_verdict/measured_item -> defect_code）
      #    - 复杂判定走策略引擎（阈值/逻辑表达式）
      #    (raw_verdict + measured_items -> business_verdict + defect_records[])
      # 4. 创建 QualityVerdict -> issue(...) -> QualityVerdictIssued
      # 5. 发布到 quality.inspection.verdict
      #    - 首件处理上下文订阅 -> AggregateInspectionResults 汇总首件检验结果（首件处理 §2.3）
      #    - 数据应用上下文订阅 -> 缺陷统计 / SPC / 良率分析
      # 6. 驱动缺陷累积分析（BatchAnomalyDetectionService.accumulateDefectSignal, §3.4）
```

> **为什么不放在聚合根内**：业务判定需查询 `QualityGateRule`（按 station × product_scope 找 ACTIVE 规则）+ `DefectCatalog`（缺陷字典）+ 应用 `gate_logic`/`defect_mapping` 翻译——跨 `QualityVerdict` + `QualityGateRule` + `DefectCatalog` 三聚合。幂等去重（BIZ-03）是跨实例不变式，由本服务 + `source_test_result_id` 去重表保证。

> **同步门禁 vs 异步判定**（INV-CX-04）：本服务做**异步业务判定**（`QualityVerdictIssued`，记录性），与过点执行上下文的**同步门禁判定**（`QualityGateEvaluated`，权威）不要求强一致。`business_verdict=BLOCK` 异步到达时过点可能已放行——不回溯拦截，记入缺陷统计供批量异常分析触发返工（🔴 §2.4 热点立场）。

> 🔴 **热点：BLOCK 判定与过点拦截的时序**（事件风暴 §2.4）——建议立场已固化：**过点同步门禁为权威**，异步 BLOCK 判定不回溯拦截已放行的过点，而是记入缺陷统计供后续批量异常分析（§3.4）触发返工。

> 🔴 **热点：业务判定的事件驱动 vs 查询驱动**（事件风暴 §2.7）——建议立场已固化：**订阅事件**（`mes.testresult.structured` 已发布，本上下文订阅消费），与过点执行上下文解耦。

### 3.4 BatchAnomalyDetectionService（批量异常检测服务）

**职责**：消费缺陷累积信号（`QualityVerdictIssued` + 返修诊断回流 `DiagnosisResultRecorded` + 首件结果回写 `InspectionResultsAggregated`），按 `(work_order_id, station_id, defect_code)` 维度增量累积缺陷频次，超阈值时识别批量异常发布 `BatchQualityAnomalyDetected` 信号供返工上下文评估生成返工工单。

```yaml
BatchAnomalyDetectionService:
  方法:
    accumulateDefectSignal(source, work_order_id, station_id, defect_code, sn, source_event_id):
      # 缺陷累积增量更新（准实时流式）
      # 来源：
      #   - QualityVerdictIssued（本上下文 §3.3 产出的缺陷记录）
      #   - rework.diagnosis: DiagnosisResultRecorded（返修上下文诊断结论回流）
      #   - fai.flow.completed: InspectionResultsAggregated（首件处理上下文首件结果回写）
      # 1. 幂等去重：(source, source_event_id) 去重表
      # 2. 按 (work_order_id, station_id, defect_code) 维度累积缺陷频次
      # 3. 异常检测（阈值/规则配置）：
      #    - 缺陷频次超阈值？（如某缺陷在工单内占比 > 5%）
      #    - 缺陷模式聚类？（同类缺陷在连续 SN 上重复）
      # 4. 影响范围判定：
      #    - SINGLE_INCIDENT（单件偶发）-> 不发布批量异常信号（过点拦截分流返修）
      #    - BATCH_SYSTEMIC（批次性系统性）-> detectBatchAnomaly(...)

    detectBatchAnomaly(work_order_id, station_id, defect_code, affected_sn_list, defect_frequency, threshold_breached, source_verdict_ids):
      # 1. 创建 BatchQualityAnomaly -> detect(...) -> BatchQualityAnomalyDetected
      #    anomaly_scope=BATCH_SYSTEMIC，必带 affected_sn_list + defect_frequency + threshold_breached
      # 2. 幂等去重：同 (work_order_id, station_id, defect_code) 异常不重复识别（BIZ-05）
      # 3. 发布到 quality.anomaly.batch
      #    - 返工上下文订阅 -> 评估生成 BatchReworkOrder（返工上下文 §2.1）
      #    - 数据应用上下文订阅 -> 批量异常统计
```

> **为什么不放在聚合根内**：缺陷累积分析需跨实例查询所有 `QualityVerdict`（按 work_order × station × defect_code 累积）+ 跨上下文消费返修/首件结果回流 + 阈值判定——跨 `BatchQualityAnomaly` + `QualityVerdict` 多聚合 + 跨上下文编排。异常识别幂等（BIZ-05）是跨实例不变式，由本服务 + 去重表保证。

> 🔴 **热点：异常检测的阈值与规则配置 / 时效性 / affected_sn_list 准确性 / 缺陷影响范围判定准确性**（事件风暴 §2.5/§10）——建议立场已固化：阈值归本上下文配置（质量工程师配置，按工序/产品段差异化）；准实时流式；affected_sn_list = 已确认缺陷 SN + 疑似范围 SN；保守判定（倾向批量异常，宁可多返工不可漏检系统性缺陷）。

> 🔴 **热点：返修诊断回流的消费**（事件风暴 §10）——建议立场已固化：**返修上下文诊断时引用本上下文缺陷分类字典**（REST 查询），`DiagnosisResultRecorded` 携带 `defect_code`（与本上下文字典对齐），本上下文消费后直接累积。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文是配置型主数据 + 业务判定混合上下文，与过点执行/首件处理/工艺管理/返工上下文的协作经**异步事件解耦** + **降级查询**，同步门禁归过点执行上下文（不在过点主事务内，INV-CX-04）。

> **主题命名约定**：本域**对外发布**使用 `quality.*` 前缀。本域**订阅**使用各发布域实际前缀（`mes.*`/`rework.*`/`fai.*`/采购仓管前缀待对齐），不重写。

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 质量上下文](../事件风暴/质量上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 InspectionStandard（检验标准）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-01 | `InspectionStandardType` 一经确定不可变更；DEPRECATED 后新草稿规则不可引用、已生效规则不受影响（见 INV-04） | `InspectionStandard.define` 前置 + `type` 不可变；DEPRECATED 限制新草稿，不回写已生效规则（`standard_id` 全局唯一见 BIZ-01） |

#### 6.1.2 QualityGateRule（质量门禁规则·版本化）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-03 | `ARCHIVED` 为终态，之后任何事件均拒收 | `QualityGateRuleState` 状态机；允许从 DEPRECATED / DRAFT 转入 |
| INV-04 | ACTIVATED 后判定逻辑与映射不可变（保证过点记录规则快照完整性） | `QualityGateRule` 在 ACTIVATED/DEPRECATED/ARCHIVED 态拒收任何 `configureGateLogic`/`configureDefectMapping`/`bindHoldAuthorization` 命令；保证过点执行上下文 `CheckpointRecord` 的规则快照可永久回溯 |
| INV-06 | 提交审核前置：判定逻辑完整（GateLogic 非空）且引用校验满足（InspectionStandard/DefectCatalog 非 DEPRECATED，OverrideAuthorizationPolicy 存在有效） | `QualityGateRule.submitReview` 前置 + `RuleValidationService.precheckOnSubmit` |
| INV-07 | 生效前置：所有 InspectionStandard 非 DEPRECATED | `RuleValidationService.validateOnActivate`（查本上下文） |
| INV-08 | 生效前置：所有 DefectCatalog 非 DEPRECATED、OverrideAuthorizationPolicy 存在且有效 | `RuleValidationService.validateOnActivate`，校验失败拒绝 ActivateQualityGateRule |

> DefectCatalog / QualityVerdict / BatchQualityAnomaly / IqcRequest / OverrideAuthorizationPolicy 无聚合不变式；其跨实例唯一性 / 幂等见 §6.2，跨上下文协作见 §6.3。

### 6.2 业务不变式（Business Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| BIZ-01 | InspectionStandard | `standard_id` 全局唯一 | 跨实例，由数据库唯一索引 `(standard_id)` 保证；非聚合根自身可校验 |
| BIZ-02 | QualityGateRule | 同 `rule_id` 同时仅一个 ACTIVATED 版本 | 跨实例，由 `RuleActivationService` 在生效时查询读模型 + 数据库唯一索引 `(rule_id, status=ACTIVATED)` 共同保证；新版本生效自动 Deprecate 旧版本（同事务 outbox） |
| BIZ-03 | QualityVerdict | 同一 TestResult 不重复判定（`source_test_result_id` 去重）；判定不可变（一经发布不可修改） | 跨聚合，由 `QualityVerdictService` + `source_test_result_id` 去重表保证 |
| BIZ-04 | IqcRequest | 同一触发信号不重复创建 IqcRequest（`source_event_id` 去重）；PENDING -> PASSED/FAILED 单向流转；FAILED 必带 `failed_items[]` + `disposition` | 跨聚合，由 `IqcService` + `source_event_id` 去重表保证 |
| BIZ-05 | BatchQualityAnomaly | 同一 `(work_order_id, station_id, defect_code)` 异常不重复识别；`anomaly_scope=BATCH_SYSTEMIC` 必带 `affected_sn_list[]` + `defect_frequency` + `threshold_breached` | 跨聚合，由 `BatchAnomalyDetectionService` + 去重表保证 |
| BIZ-06 | -（基础设施，各事件消费聚合） | 上下文外事件消费幂等 | `consumed_event` 表 + 业务键去重（BIZ-03/04/05 的通用机制） |

### 6.3 跨上下文不变式（Cross-Context Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| INV-CX-01 | QualityGateRule（本），过点执行上下文 | 规则版本一致性--质量门禁规则变更仅影响变更后首次过点的在制品；已过点的在制品按其 `CheckpointRecord` 锁定的规则版本继续，不受新版本影响 | 由过点引擎在首次过点时固化版本保证（主责在过点执行上下文）；本上下文发布 `QualityGateRuleActivated`（与工艺管理 / 物料上下文同构不变式） |
| INV-CX-02 | QualityGateRule（本），下游上下文 | 事务发件箱至少一次投递--`QualityGateRuleActivated`/`QualityGateDeprecated` 的发布与 QualityGateRule 状态变更 + 旧版本 Deprecate 在同一数据库事务内通过 outbox 保证 | outbox 模式 + 消费端幂等（source_event_id 去重表）；与工艺管理 / 物料上下文同构不变式 |
| INV-CX-03 | 各事件消费聚合（本），下游上下文 | 上下文外事件只消费不重发--本上下文将订阅事件包装为本上下文语义事件后发布，下游凭主题前缀区分来源 | `QualityEventConsumeAppService` 包装发布；主题前缀 `quality.*` vs `mes.*`/`rework.*`/`fai.*` |
| INV-CX-04 | QualityGateRule / QualityVerdict（本），过点执行上下文 | 同步门禁权威 + 异步判定记录性，不要求强一致--过点执行上下文同步门禁 `QualityGateEvaluated`（基于缓存规则，权威，驱动过点放行/拦截）；本上下文异步业务判定 `QualityVerdict`（基于完整规则 + 缺陷字典，记录性）。异步 BLOCK 判定不回溯拦截已放行的过点，记入缺陷统计供批量异常分析触发返工 | 区别于过点执行上下文内部同步门禁；门禁=流量控制（快），判定=质量评估与记录（深）；两者语义不同不要求强一致（🔴 §0/§2.4 热点立场） |

## 9. 领域服务与应用服务的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                           外部调用入口                                  │
│                                                                      │
│  REST/质量设计器 ──▶ QualityCommandAppService (应用服务)              │
│                      ├─ 单聚合操作：直接委托聚合根方法                   │
│                      ├─ 跨聚合编排：委托领域服务（校验/生效/判定/异常/IQC）│
│                      └─ 同事务推进状态 + 发布集成事件（outbox）          │
│                                                                      │
│  消息消费 ───▶ QualityEventConsumeAppService (应用服务)               │
│                 └─ 翻译 mes.*/rework.*/fai.* 事件 -> 委托领域服务       │
│                   （包装为本上下文语义事件后发布，INV-CX-03）               │
│                                                                      │
│  查询请求 ───▶ QualityQueryAppService (应用服务，读模型)              │
│                 └─ 直接查询读模型投影（含过点/首件降级查询 ≤500ms）     │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  RuleValidationService │ RuleActivationService │ QualityVerdictService│
│  BatchAnomalyDetectionService │ IqcService                          │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  InspectionStandard / DefectCatalog / QualityGateRule                │
│  QualityVerdict / BatchQualityAnomaly / IqcRequest                   │
│  OverrideAuthorizationPolicy                                         │
│  └─ 表达业务状态、行为、不变式、领域事件；不依赖 Spring/MQ/HTTP          │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 同步门禁权威 + 异步判定记录性，不要求强一致（INV-CX-04）；配置型主数据生效经 outbox（INV-CX-02）
