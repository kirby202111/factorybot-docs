# 排产上下文（Scheduling Bounded Context）

> **限界上下文**：排产上下文
> **统一语言**：LineSchedule（产线排产·按产线聚合的槽位集合）, ScheduleSlot（排产槽位·工单+起止时间+状态）, SlotStatus（槽位状态·PENDING 建议 / CONFIRMED 已确认 / RELEASED 已释放）, SchedulingSuggestion（排产建议·半自动产出供计划员确认）, ProductionLineCapacity（产线产能日历·可用时段/班次/维护窗）, LineCapacityResolver（产线产能解析·领域辅助组件）, RescheduleTrigger（重排触发源·RushOrder / MaterialShortage / EquipmentUnavailable / WorkOrderChanged）, CriticalAssetRef（关键资产引用·停用即影响产线产能）
> **核心关注**：以"事件风暴"方式刻画 **工单级、半自动、咨询性、事件驱动重排** 的 MES 排产--工单下达后生成排产建议、计划员确认落槽、缺料/设备故障/插单触发未开工部分重排、确认后排产快照回写工单并触发齐套预占。本上下文只对"**一张已下达工单排到哪条线、什么时间、何时该重排**"负责；**不负责**工单身份与状态生命周期（归工单管理上下文，本上下文消费 `wo.order.*`）、**不负责**工序级时间排产与资源/设备槽位建模（当前粒度仅工单级）、**不负责**过点放行/拦截门禁（归过点执行上下文；排产咨询性，`schedule.*` 不被过点执行消费做硬门禁）、**不负责**物料主数据与库存事实源（归物料上下文，本上下文消费其缺料事件）、**不负责**齐套状态判定（归工单管理上下文 `KitStatus`，本上下文消费 `wo.kit.status`）、**不负责**资产台账与可用性事实源（归设备工装台账上下文，本上下文消费其 `AssetAvailabilityChanged`）。

> **变更说明**：本上下文为新建。§「已识别约束」按事件风暴去编号化约定--只发现不定型、不编号、不分类、不写守护机制；编号与守护机制权威移交领域建模 §6。

## 0. 设计原则与边界澄清

排产上下文是生产执行服务下的**工单级排产子域**，是 PCBA + 整机组装混合型车间"已下达工单排到哪条线、什么时间跑、何时因 disruptions 重排"的建议与确认权威源。工单经工单管理上下文审核下达为 `RELEASED` 后进入本上下文的排产积压；本上下文按产线产能日历与排产规则**半自动产出建议槽位**，由**计划员确认**后落槽（权威在计划员确认，不在算法）；确认后发布排产事件回写工单的 MES 排产快照并触发物料上下文齐套预占。排产**咨询性**：不门禁过点，过点执行上下文不消费 `schedule.*` 做硬校验。

**排产深度画像（已确认）**：

| 维度 | 取值 | 含义 |
|------|------|------|
| 自动化程度 | 半自动建议 | 系统按规则/优先级产出建议，计划员确认后生效 |
| 排产粒度 | 工单级 | 只排"工单-产线-开完工时间"，不排工序级时间、不建模资源槽位 |
| 重排触发 | 事件驱动重排 | 插单/急单、缺料、设备故障、工单变更触发未开工部分局部重排 |
| 权威性 | 咨询性 | 排产不门禁过点/齐套，仅供排产员参考；权威在计划员确认 |

**上下文内职责**（本上下文负责）：
- **排产积压维护**--消费工单管理上下文 `wo.order.released` 接收待排工单（携带 SAP 建议产线/计划时间作为提示），消费 `wo.order.changed` / `wo.order.cancelled` 同步变更/移除
- **排产建议生成**--`SchedulingSuggestionService` 按产线产能日历 + 排产规则（急单优先、目标数量、SAP 建议时间、产线适用性、换线偏好）半自动产出 `PENDING` 建议槽位，发布 `ScheduleSuggested` 供排产员工作台
- **计划员确认落槽**--计划员确认建议后，`LineSchedule.confirmSlot` 将 `PENDING` 升为 `CONFIRMED`，校验同线已确认槽位不重叠，发布 `ScheduleConfirmed`
- **MES 排产快照回写**--`ScheduleConfirmed` / `ScheduleRescheduled` / `ScheduleReleased` 由工单管理上下文消费，回写工单的 MES 排产快照（与 SAP 建议字段并存）
- **齐套预占触发**--`ScheduleConfirmed` 由物料上下文消费触发齐套预占；`ScheduleRescheduled` / `ScheduleReleased` 触发释放/重预占
- **事件驱动重排**--`SchedulingRescheduleService` 消费缺料（`material.kit.reservation-failed`）、设备故障（`eam.asset.availability`）、插单（`wo.order.released` 含急单）、工单变更，重排受影响**未开工**槽位

**上下文外职责**（本上下文**不**负责）：
- 工单身份、状态生命周期、完工判定 -> 工单管理上下文（本上下文消费 `wo.order.*`，不修改工单状态）
- 工序级时间排产、工序甘特、资源/设备/人员槽位建模 -> 当前粒度工单级，不展开（见暂缓）
- 过点放行/拦截、工单状态对过点的门禁 -> 过点执行上下文（排产咨询性，过点执行不消费 `schedule.*`）
- 物料主数据、BOM、库存事实源、齐套预占执行 -> 物料上下文（本上下文发布 `schedule.confirmed` 触发其预占，消费其 `reservation-failed`）
- 工单级齐套状态判定 -> 工单管理上下文（本上下文消费 `wo.kit.status`）
- 资产台账、资产可用性事实源、停用/恢复决策 -> 设备工装台账上下文（本上下文消费 `eam.asset.availability`，不决策停用）
- 产线/工作中心主数据权威源 -> 当前以本上下文薄配置字典起步，预留迁移到"工厂建模上下文"（见 🔴 热点）

**为什么不把排产并入工单管理上下文**：
1. **一致性边界根本不同**--`WorkOrder` 聚合守护单工单生命周期；排产守护"同条产线已确认槽位不可时间重叠"，这是**跨工单**的产能/非重叠不变式，无法在任一 `WorkOrder` 聚合内检查（与 `MesSerialNumberService` 因"聚合无权查询其它实例"而独立的理由同构，但跨工单可见性需求更强）。
2. **事件驱动重排是跨域汇聚点**--重排触发源来自工单（插单/变更）、物料（缺料）、设备台账（故障）三个域。若折进工单上下文，工单上下文将凭空背上对物料、设备台账事件的订阅依赖，破坏其刻意收窄的订阅面（当前仅 `mes.*` / `brework.*`）。
3. **统一语言不同**--排产的产线产能日历、槽位、建议、重排触发源在工单模型中不存在；折进等于让工单上下文同时背负"工单生命周期"与"资源产能分配"两个变化轴，违反 SRP。
4. **相邻上下文已预留契约**--物料上下文 `InventoryReservationService` 标注"消费排产/工单派工/开工事件"🔴 待对齐、`material.kit.reservation-failed` 主消费方"排产/工单上下文"、工单管理 `wo.kit.status` 主消费方"排产上下文（投放决策）"--三处悬空契约均等待独立排产上下文接续。

**为什么排产归生产执行服务而非制造资源服务**：
1. **数据性质**--制造资源服务管配置性数据（BOM/工艺路线/质量规则，写少读多）；排产是事务性数据（高频建议/确认/重排，与生产执行强绑定）。
2. **协作紧密度**--排产与工单（积压）、物料（齐套预占）、在制品（齐套状态）、设备台账（产能）同属生产执行链条与现场执行，归生产执行服务减少跨服务事务。
3. **节奏**--排产建议/重排是天到小时级、随 disruptions 滚动，与生产执行同节奏；与制造资源的配置生命周期不同。

## 1. 主语清单与触发入口

排产上下文的主语是 `LineSchedule`（按产线）。入口是已下达工单与 disruptions 事件。这一节是后续事件链的"主语清单"--没有它，事件就悬空。

### 1.1 上下文外触发源

```
┌──────────────────────────────────────────────────────────────────┐
│ 排产入口                                                          │
│                                                                  │
│  【来源1:工单管理上下文 (wo.*)】                                   │
│    wo.order.released -> 待排工单入积压（携带 SAP 建议产线/时间）   │
│    wo.order.changed  -> 工单数量/建议产线/建议时间变更，重排       │
│    wo.order.cancelled-> 移除该工单槽位，释放                       │
│    wo.order.started  -> 工单已首次过点进入在制，冻结/归档其槽位    │
│                                                                  │
│  【来源2:计划员】                                                   │
│    确认/拒绝排产建议，或手动触发重排                              │
│    -> PENDING 升 CONFIRMED / 释放槽位                            │
│                                                                  │
│  【来源3:物料上下文 (material.*)】                                 │
│    material.kit.reservation-failed -> 已确认工单缺料，往后重排    │
│                                                                  │
│  【来源4:工单管理上下文 (wo.*)】                                │
│    wo.kit.status (kit_ready=false) -> 已排工单齐套失效，重排     │
│                                                                  │
│  【来源5:设备工装台账上下文 (eam.*)】                              │
│    eam.asset.availability (available=false, 关键资产)            │
│      -> 产线产能受损，重排该线未开工槽位                          │
│    eam.asset.availability (available=true)                       │
│      -> 产能恢复，可重新接纳重排工单                              │
│                                                                  │
│  【来源6:本上下文产线产能配置（薄配置字典）】                       │
│    LineCapacityResolver 解析产线可用时段/班次/维护窗              │
│    -> 建议生成与槽位合法性校验的产能依据                          │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 聚合根主语清单

| 聚合根 | 典型对象 | 关键管理特征 | 上下文外触发源 |
|--------|---------|-------------|---------------|
| **LineSchedule**（产线排产） | 一条产线的槽位集合 | 按产线聚合；持有 `PENDING`/`CONFIRMED`/`RELEASED` 槽位；守护同线已确认槽位不重叠；建议与确认都建模为槽位状态，不另起建议聚合 | 工单 / 计划员 / 缺料 / 故障 |
| ScheduleSlot（排产槽位·值对象） | 单个工单在某线的占用 | work_order_id + planned_start/finish + status；PENDING->CONFIRMED->RELEASED 单向 | 由 LineSchedule 触发 |
| ProductionLineCapacity（产线产能日历·配置） | 产线可用时段/班次/维护窗 | 薄配置字典起步；`LineCapacityResolver` 读取解析；槽位须落在可用时段内 | 配置维护（🔴 权威源待迁移） |

**产线排产模型**：

```
LineSchedule
├── line_id                 : 产线 ID（聚合根 ID）
├── slots[]                 : ScheduleSlot 集合（PENDING/CONFIRMED/RELEASED）
│   ├── work_order_id       : 工单 ID（引用工单管理上下文）
│   ├── planned_start_at    : 计划开工时间（MES 排产）
│   ├── planned_finish_at   : 计划完工时间（MES 排产）
│   ├── status              : PENDING | CONFIRMED | RELEASED
│   ├── sap_hint            : SAP 建议产线/时间（参考提示）
│   └── trigger             : RescheduleTrigger?（重排时记录触发源）
├── capacity                : ProductionLineCapacity（产能日历引用，🔴 薄配置）
└── last_updated_at         : 最后变更时间
```

> **聚合边界已确认**：`LineSchedule` 按产线聚合，把"同线已确认槽位不可重叠"这一核心不变式收敛到**聚合内**事务强一致（而非跨实例 BIZ）。建议（PENDING）与确认（CONFIRMED）都建模为槽位状态值对象，不另起 `SchedulingProposal` 聚合，避免聚合碎片化（与工单上下文"明细/绑定/结案折叠为值对象"的哲学一致）。若后续建议生命周期（建议->确认/驳回/被插单 supersede）复杂度涌现，再升格为独立聚合。

> **MES 排产快照与 SAP 建议并存已确认**：工单保留 SAP 下发的 `planned_start_at` / `planned_finish_at` / `production_line_id`（参考），另由本上下文 `ScheduleConfirmed` 回写 MES 排产快照（`mes_scheduled_line_id` / `mes_scheduled_start_at` / `mes_scheduled_finish_at`）。两套字段并存，SAP 建议不覆盖、MES 排产不回写 SAP 字段。

> **咨询性边界已确认**：排产不门禁过点。过点执行上下文**不消费** `schedule.*` 做硬校验，仍按 `wo.order.*` 缓存的工单状态放行/拦截。MES 排产快照仅供排产员看板与齐套预占（物料按计划产线预 stage）。权威在计划员确认，不在算法。

> **已开工工单不重排已确认**：消费 `wo.order.started`（工单首次过点进入 `IN_PROGRESS`）后，该工单槽位冻结/归档，重排只影响**未开工**（`RELEASED`）工单。这尊重工单上下文 INV-10（首次过点自动转态）与 INV-16（在制后禁调 target_qty）。

## 2. 事件风暴 - 主链

事件风暴使用以下色块语义，文中以 `【】` 标注：

- **【事件】** 已发生的事实（过去时）
- **【命令】** 触发事件的意图（动词原形）
- **【参与者】** 触发命令的人或系统
- **【聚合】** 一致性边界
- **【策略】** 当某事件发生时自动触发某命令
- **【外部系统】** 上下文外协作方
- **【读模型】** 投影出的视图
- **【热点】** 待对齐 / 有争议点，正文用 🔴 前缀

### 2.1 排产建议生成与确认（主链第一段）

```
【外部系统:工单管理上下文】
        -- wo.order.released(work_order_id, target_qty, work_order_type,
                             sap_hint: production_line_id/planned_start_at/planned_finish_at)
                |
                v
【策略:工单下达后生成排产建议】（读产线产能日历 + 排产规则）
                |
                v
【命令:生成排产建议 GenerateSchedulingSuggestion】--> 【聚合:LineSchedule】
        |
        ┌──── 建议生成时读取辅助 ─────────────────────────────┐
        v                             v                       v
【读模型:待排工单积压】         【策略:解析产线产能日历】     【读模型:各线已确认槽位】
（wo.order.released 累积）      LineCapacityResolver          （本上下文各 LineSchedule）
        |                             |                       |
        └──────────────┬──────────────┴──────────────┬────────┘
                       v                             v
        产出 PENDING 建议槽位（选定 line_id + planned_start/finish）
                       |
                       v
        【事件:排产建议已生成 ScheduleSuggested】
         (work_order_id, line_id, planned_start_at, planned_finish_at, sap_hint, suggested_at)
                |
                v
        发布到 schedule.suggested
                |
                v
【参与者:计划员】（排产员工作台审阅建议）
        --【命令:确认排产 ConfirmSchedule】--> 【聚合:LineSchedule】
        |   （校验：PENDING 槽位仍存在且未被 supersede；同线已确认槽位不重叠）
        v
        【事件:排产已确认 ScheduleConfirmed】
         (work_order_id, line_id, planned_start_at, planned_finish_at, confirmed_by, confirmed_at)
                |
                v
        发布到 schedule.confirmed
                |
                v
【外部系统:工单管理上下文】订阅
（回写工单 MES 排产快照 mes_scheduled_*，与 SAP 建议字段并存）
【外部系统:物料上下文】订阅
（触发 InventoryReservation 齐套预占，按计划产线预 stage 物料）
```

**关键事件**

| 事件 | 何时发生 | 关键载荷 | 后续策略 |
|------|---------|---------|----------|
| ScheduleSuggested | 工单下达后或重排时，系统半自动产出建议槽位 | work_order_id, line_id, planned_start_at, planned_finish_at, sap_hint, suggested_at | 推送排产员工作台待确认 |
| ScheduleConfirmed | 计划员确认建议，PENDING 升 CONFIRMED | work_order_id, line_id, planned_start_at, planned_finish_at, confirmed_by, confirmed_at | 回写工单 MES 排产快照 + 触发齐套预占 |
| ScheduleRejected | 计划员驳回建议（可选） | work_order_id, line_id, reject_reason | 释放 PENDING 槽位，重新生成建议或人工指定 |

> **已确认：半自动建议 + 计划员确认**--系统按排产规则产出 `PENDING` 建议，但**建议不产生任何下游效果**（不回写工单、不触发齐套预占）；只有计划员确认（`PENDING -> CONFIRMED`）才发布 `ScheduleConfirmed` 触发下游。权威在计划员确认，不在算法。

> **已确认：建议生成依据**--`SchedulingSuggestionService` 读取待排工单积压（`wo.order.released` 累积）、各线已确认槽位（避免冲突）、产线产能日历（`LineCapacityResolver`），按排产规则（急单优先、目标数量、SAP 建议时间提示、产线适用性、换线偏好）选定 `line_id + planned_start/finish`。排产规则的具体权重为实现细节，不在事件风暴定型。

> 🔴 **热点：产线产能日历权威源**--当前以本上下文薄配置字典起步（复刻工单上下文 `ProductSerialPrefixResolver` 先例）。预留迁移到"工厂建模上下文"（设备工装台账上下文已引用该域但未建）。迁移时 `LineCapacityResolver` 改为 REST 查询工厂建模上下文，本上下文聚合不变。待工厂建模上下文落地后对齐。

> 🔴 **热点：产能受损到产线的映射**--台账发布的是资产级 `AssetAvailabilityChanged`，排产是产线级。需维护"产线关键资产"配置（哪些资产停用即影响哪条线产能）。当前以本上下文薄配置起步；台账资产有 `line` 属性可辅助映射。待与设备工装台账上下文确认是否提供产线级可用性汇总事件。

### 2.2 事件驱动重排

工单确认排产后，下列 disruptions 触发**未开工部分**局部重排。已开工（`IN_PROGRESS`）工单槽位冻结，不重排。

```
【外部系统:物料上下文】
        -- material.kit.reservation-failed(work_order_id, missing_items[])
                |

### 2.3 排产快照回写与齐套预占（跨上下文协作）

排产确认/重排/释放后，工单管理上下文与物料上下文各自消费 `schedule.*` 完成回写与预占。本上下文**不直接调用**这两个上下文的接口，全部经事件异步解耦。

本上下文 ──schedule.confirmed──▶ 物料上下文（触发 InventoryReservation 齐套预占）
本上下文 ──schedule.rescheduled──▶ 工单管理上下文（更新 MES 排产快照）
本上下文 ──schedule.rescheduled──▶ 物料上下文（释放旧预占 + 按新计划重新预占）
本上下文 ──schedule.released──▶ 工单管理上下文（清空 MES 排产快照）
本上下文 ──schedule.released──▶ 物料上下文（释放齐套预占）

物料上下文 ──material.kit.reservation-failed──▶ 本上下文（缺料重排）
工单管理 ──wo.kit.status(kit_ready=false)──▶ 本上下文（齐套失效重排）

工单管理上下文 ──wo.order.released/changed/cancelled/started──▶ 本上下文（积压/变更/移除/冻结）
```

> **已确认：齐套预占触发点迁移到排产确认**--物料上下文 `InventoryReservationService` 此前标注"消费排产/工单派工/开工事件"🔴 待对齐。引入本上下文后，`schedule.confirmed` 即"派工"事件，齐套预占由"下达"迁移/收敛到"排产确认"（确认排到线+时间才锁料更合理）。物料上下文订阅源由 `wo.*` 收敛为 `schedule.confirmed`。

> **已确认：排产咨询性不门禁过点**--过点执行上下文**不订阅** `schedule.*`。过点放行/拦截仍按 `wo.order.*` 缓存的工单状态（`RELEASED`/`IN_PROGRESS` 放行，`PAUSED`/`COMPLETED`/`CLOSED`/`CANCELLED` 拦截）。MES 排产快照不参与过点硬校验，仅供排产员看板与物料预 stage。

## 与工单管理上下文的协作边界

本上下文与工单管理上下文是"排产建议/确认"与"工单生命周期"的分工关系，通过事件契约解耦。

| 维度 | 本上下文（排产上下文） | 工单管理上下文 |
|------|------------------|--------------|
| 视角 | 排产视角（"工单排哪条线、什么时间、何时重排"） | 工单生命周期视角（"工单怎么下、状态怎么流转、何时完工结案"） |
| 存储 | 产线排产 / 槽位 / 产能日历配置 / 排产建议读模型 | 工单 / 工单绑定 / 工单结案 / MES 排产快照（回写） |
| 谁判定 | 排产建议生成、计划员确认、重排决策 | 工单状态流转、完工判定 |
| 事件性质 | 排产事实：ScheduleSuggested / Confirmed / Rescheduled / Released | 工单生命周期事实：WorkOrderReleased / Changed / Cancelled / Started |
| 流程所有权 | 接收待排->建议->确认->重排->释放 | 接收->建档->绑定->下达->流转->完工->结案 |
| 进度口径 | 槽位计划起止时间（MES 排产） | target_qty + completed_product_qty（完工判定） |

**事件流向**：

```
工单管理上下文 ──wo.order.released──▶ 本上下文（待排工单入积压）
工单管理上下文 ──wo.order.changed──▶ 本上下文（重排该工单槽位）
工单管理上下文 ──wo.order.cancelled──▶ 本上下文（释放槽位）
工单管理上下文 ──wo.order.started──▶ 本上下文（冻结槽位，停止重排）
本上下文 ──schedule.confirmed/rescheduled/released──▶ 工单管理上下文（回写/更新/清空 MES 排产快照）
```

**职责切分要点**：
- **本上下文管**：产线槽位分配 + 排产建议 + 计划员确认 + 事件驱动重排
- **工单管理上下文管**：工单身份/状态/完工 + MES 排产快照回写（消费 `schedule.*`）
- **不互相调用的操作**：本上下文不修改工单状态（归工单上下文）；工单上下文不修改槽位（归本上下文）。全部经事件异步解耦。
- **MES 排产快照最终一致**：工单的 `mes_scheduled_*` 由 `schedule.*` 事件驱动回写，允许短暂延迟；SAP 建议字段与 MES 排产快照并存，互不覆盖。

## 与物料上下文的协作边界

本上下文是物料齐套预占的**触发源**（`schedule.confirmed` 即"派工"事件），物料上下文是预占**执行方**。

| 维度 | 本上下文（排产上下文） | 物料上下文 |
|------|------------------|-----------|

## 与工单管理上下文、设备工装台账上下文的协作边界

| 协作方 | 本上下文订阅 | 用途 |
|--------|------------|------|
| 工单管理上下文 | `wo.kit.status`（KitStatusChanged, kit_ready=false） | 已排工单齐套失效，触发重排（次要缺料信号，主源为 `material.kit.reservation-failed`） |
| 设备工装台账上下文 | `eam.asset.availability`（AssetAvailabilityChanged） | 关键资产停用 -> 重排该线未开工；恢复 -> 重新接纳 |

> **主/次缺料信号**：`material.kit.reservation-failed` 是缺料重排**主源**（确认排产后预占失败，明确缺料）；`wo.kit.status` 是**次要源**（齐套状态变化，可能因库存变动）。两者均触发重排，本上下文以 `work_order_id + source_event_id` 幂等去重。

> 🔴 **热点：产能受损到产线的映射**--台账发布资产级可用性，需"产线关键资产"配置映射到产线。当前薄配置起步。
