## 0. 建模总览

本域是生产执行服务下的**核心子域**，是 PCBA + 整机组装混合型车间所有"过站活动"的执行权威源。核心职责是管理**扫码过点、防错校验、放行/拦截决策、过点记录、工艺路线推进与跳站校验、工单执行进度累计、测试数据接入适配层、本地缓存维护、工装使用上报、设备故障上报、在制品身份建档与位置投影、流转历史累积、位置快照发布**——即"**过站瞬间怎么判定、怎么记录、怎么推进、怎么累计**"；**不负责**工艺路线定义与版本生命周期（归工艺管理上下文）、质量门禁规则配置（归质量上下文）、设备资产身份与可用性事实源（归设备工装台账上下文）、设备原始信号采集（归设备数据接入上下文）、工单齐套状态判定（归工单管理上下文 `KitStatus`）、首件检验流程编排（归首件处理上下文）、单件返修任务（归返修上下文）、批量返工工单（归返工上下文）。

本上下文是生产执行服务的**核心枢纽**，与工艺管理/质量/设备工装台账/设备数据接入/首件处理/返修/返工共七个上下文通过事件契约协作。工艺与设备数据写少读多，采用"**本地缓存 + 降级查询**"解耦——订阅上下文外事件刷新缓存（秒级），缓存未命中降级 REST 查询（≤500ms），不在过点主事务中引入分布式事务（领域总览 §5.3）。测试数据接入适配层是本上下文的端口适配层（防腐层性质），从 FTP 文件/HTTP 回调/手工填报等异构渠道汇集数据并结构化为 `TestResult`，与过点判定同事务——因其唯一消费方为过点引擎、与过点判定同属一个业务事务、无独立业务价值，故不独立成限界上下文。

## 1. 聚合根

### 1.1 CheckpointRecord（过点记录）

**一致性边界**：单次过点记录的身份、绑定关系、工艺版本快照与审计信息。

**职责**：不可变地持久化过点事实；绑定 SN × 工单 × 工位 × 设备；携带 `routeVersion` 快照保证历史追溯不受后续工艺变更影响；与 `TestResult` 同事务写入；扫码后触发防错校验。

```yaml
CheckpointRecord:
  # ─── 标识 ───
  record_id:        CheckpointId          # 过点记录唯一标识（聚合根ID）

  # ─── 绑定 ───
  sn:               String                # 产品序列号（INV-01 必填）
  work_order_id:    WorkOrderId           # 关联工单（INV-01 必填）
  station_id:       StationId             # 过点工位（INV-01 必填）
  equipment_id:     EquipmentId?          # 过点设备（可选）

  # ─── 工艺版本快照 ───
  route_version_id: RouteVersionId        # 过点时锁定的工艺路线版本（INV-CX-02）
  route_id:         RouteId               # 逻辑路线标识

  # ─── 扫描信息 ───
  scanned_at:       DateTime              # 扫码时间
  scanned_by:       String                # 操作员

  # ─── 状态（不可变，一经写入不可修改 INV-12）───
  decision:         Decision              # PASS / BLOCK（来自 CheckpointDecision 判定）
  blocking_reason:  BlockingReason?       # BLOCK 时必填（INV-02）
  failed_checks[]:  List<AntiErrorCheckItem>?  # BLOCK 时失败校验项明细

  # ─── 审计 ───
  created_at:       DateTime
```

**行为**：
- `scan(sn, work_order_id, station_id, equipment_id, scanned_by)` -> 发出 `CheckpointScanned`（前置：`sn` 非空 + `work_order_id` 有效 + `station_id` 有效，INV-01；`sn` 同工单不可重复过点同站 BIZ-04；-> 记录创建；触发策略：`RunAntiErrorChecks`）
- `recordDecision(decision, blocking_reason?, failed_checks?)` -> 发出 `CheckpointReleased` / `CheckpointBlocked`（前置：`decision=PASS` 需所有防错维度通过 + 质量门禁 PASS + 设备可用，INV-02/BIZ-01；`decision=BLOCK` 必带 `blocking_reason` + `failed_checks`，INV-02；-> 记录决策固化，不可变 INV-12）
- `overrideCheckpoint(override_reason, authorized_by)` -> 发出 `CheckpointOverridden`（前置：当前 `decision=BLOCK`；授权人 + 原因必填；记录例外）

> **不可变（INV-12）**：`CheckpointRecord` 一经写入不可修改，HOLD 拦截后人工放行通过 `CheckpointOverridden` 事件记录例外而非修改原记录；补传数据迟到不回填已关单过点记录，而是发布 `TestResultLateArrived` 供返修/质量上下文评估。

> **与 TestResult 同事务（BIZ-02）**：过点判定时若 `TestResult` 已到达则同事务写入 `CheckpointRecord` + `CheckpointDecision`；若 `TestResult` 在等待窗口内到达则同事务补入；窗口超时则 `CheckpointBlocked(blocking_reason=TestResultTimeout)`。

### 1.2 CheckpointDecision（放行/拦截决策）

**一致性边界**：单次过点判定的综合决策结果、拦截原因与失败校验项明细。

**职责**：综合防错校验、质量门禁、设备可用性、测试结果、跳站校验多维度判定 PASS / BLOCK；BLOCK 必带 `blocking_reason` + `failed_checks`；质量类拦截自动分流返修。

```yaml
CheckpointDecision:
  # ─── 标识 ───
  decision_id:      DecisionId            # 决策唯一标识（聚合根ID）

  # ─── 关联 ───
  record_id:        CheckpointId          # 关联过点记录（BIZ-01 同事务）
  sn:               String
  station_id:       StationId

  # ─── 判定结果 ───
  decision:         Decision              # PASS / BLOCK
  blocking_reason:  BlockingReason?       # BLOCK 时必填（INV-02）
  failed_checks[]:  List<AntiErrorCheckItem>  # BLOCK 时失败校验项明细

  # ─── 判定依据 ───
  anti_error_result:   AntiErrorCheckResult   # 防错校验结果（INV-02）
  quality_gate_result: QualityGateResult?     # 质量门禁判定结果
  equipment_available: Boolean                # 设备可用性
  test_result_available: Boolean              # TestResult 是否可用

  # ─── 审计 ───
  decided_at:       DateTime
```

**行为**：
- `decide(anti_error_result, quality_gate_result, equipment_available, test_result_available)` -> 发出 `CheckpointReleased` / `CheckpointBlocked`（前置：`anti_error_result.passed=true` 且 `quality_gate_result=QualityGateResult.PASS` 且 `equipment_available=true` 且 `test_result_available=true` -> `PASS`，BIZ-01；否则 -> `BLOCK`，INV-02，必带 `blocking_reason` + `failed_checks`；-> 策略：`PASS` 触发 `AdvanceRouting` + `AccrueWorkOrderProgress` + `ReportFixtureUsage`；`BLOCK` 且 `blocking_reason ∈ 质量类` 触发 `RouteToRework`）

> **BLOCK 必带原因（INV-02）**：`blocking_reason` 枚举涵盖 `AntiErrorFailed` / `QualityGateFail` / `QualityHold` / `EquipmentUnavailable` / `EquipmentCacheMiss` / `EquipmentDataOutOfRange` / `EquipmentDataTimeout` / `RouteCacheMiss` / `TestResultTimeout` / `SkipViolation` / `MissViolation` / `KitNotReady`，每种原因对应特定 `failed_checks` 明细。

> **质量类拦截自动分流**：仅当 `blocking_reason ∈ {QualityGateFail, TestResultTimeout}`（质量类）时自动发布 `UnitRoutedToRework`；设备/物料类拦截由通知服务推送人工处理（安灯告警），不自动进返修。

### 1.3 RoutingProgress（工艺路线推进）

**一致性边界**：单件在工艺路线上的当前步序、跳站状态、再入标记与版本锁定。

**职责**：推进单件在路线上的当前步序；校验跳站/漏站违规；跟随单件首次过点锁定的 `routeVersion`；响应返修/返工再入；COMPLETED 终态拒收推进。

```yaml
RoutingProgress:
  # ─── 标识 ───
  progress_id:      ProgressId            # 推进记录唯一标识（聚合根ID）

  # ─── 绑定 ───
  sn:               String                # 产品序列号
  work_order_id:    WorkOrderId

  # ─── 路线版本锁定（INV-CX-02）───
  route_version_id: RouteVersionId        # 首次过点时锁定的工艺路线版本
  route_id:         RouteId

  # ─── 当前步序 ───
  current_step_no:  Integer               # 当前步序号
  current_station_id: StationId?          # 当前工位

  # ─── 状态 ───
  state:            RoutingProgressState  # NOT_STARTED / IN_PROGRESS / BLOCKED_SKIP / COMPLETED
  reentered_from:   ReentrySource?        # 再入来源（Rework / BatchRework，null=首次推进）
  reentry_task_id:  String?               # 再入关联任务ID（返修 task_id / 返工 order_id）

  # ─── 审计 ───
  started_at:       DateTime?             # 首次过点时间
  completed_at:     DateTime?             # 最终步序完成时间
  updated_at:       DateTime
```

**行为**：
- `start(sn, work_order_id, route_version_id, route_id, current_step_no, station_id)` -> 发出 `RoutingProgressStarted`（前置：当前 `NOT_STARTED`；-> `IN_PROGRESS`；首次过点放行时由 `RoutingProgressService` 编排）
- `advance(from_step, to_step, station_id)` -> 发出 `RoutingProgressed`（前置：当前 `IN_PROGRESS`；经 `StationSequenceCheck` 校验步序正确，INV-06；-> 更新 `current_step_no`；若 `to_step` 为最终步序则 -> `COMPLETED`，INV-05）
- `blockSkip(expected_step, actual_step)` -> 发出 `StationSkipViolation`（前置：当前 `IN_PROGRESS`；跳站（越序前进）检出；-> `BLOCKED_SKIP`；同时触发 `CheckpointBlocked(blocking_reason=SkipViolation)`）
- `blockMiss(expected_step, actual_step)` -> 发出 `StationMissViolation`（前置：当前 `IN_PROGRESS`；漏站（越序后退）检出；-> `BLOCKED_SKIP`；同时触发 `CheckpointBlocked(blocking_reason=MissViolation)`）
- `reenterFromSkip(step_no, station_id, authorized_by)` -> 发出 `SkipReentered`（前置：当前 `BLOCKED_SKIP`；人工纠正或授权跳站；-> `IN_PROGRESS`；授权跳站需记录 `authorized_by`）
- `reenterFromRework(reentry_point, rework_task_id)` -> 发出 `UnitReworkReentered`（前置：`reentry_point` 在当前 `routeVersion` 合法步序内，INV-CX-01；`reentry_point` 与当前步序不同；-> 更新 `current_step_no` 为 `reentry_point`；`reentered_from=Rework`）
- `reenterFromBatchRework(reentry_point, rework_order_id)` -> 发出 `BatchReworkReentered`（前置：同 `reenterFromRework`，INV-CX-01；`reentered_from=BatchRework`）
- `markScrapped()` -> 发出 `RoutingProgressScrapped`（前置：当前非 `COMPLETED`；消费 `UnitScrappedAfterRework` / `BatchReworkOrderScrapped`；-> 标记终态，不再推进）
- `complete()` -> 发出 `RoutingProgressCompleted`（前置：当前步序为最终步序，INV-05；-> `COMPLETED`，终态——之后任何推进均拒收 INV-05）

> **状态机隐含驱动**：`NOT_STARTED->IN_PROGRESS` 由首次过点放行时 `RoutingProgressService.start()` 编排；`IN_PROGRESS->IN_PROGRESS`（推进）由每次过点放行后 `advance()` 驱动；`IN_PROGRESS->BLOCKED_SKIP` 由跳站/漏站校验检出；`BLOCKED_SKIP->IN_PROGRESS` 由人工纠正/授权跳站；`->COMPLETED` 由最终步序放行。`COMPLETED` 之后任何事件均拒收（终态 INV-05）。

> **返修/返工再入的步序跳转**：再入后 `current_step_no` 跳至 `reentry_point`，不保留中间步序——返修/返工已完成离线处理，跳过中间步序是合理的。

### 1.4 WorkOrderProgress（工单执行进度）

**一致性边界**：单个工单维度的完成量、良品量、不良品量、返修量、报废量的累计值。

**职责**：按过点放行结果累计工单进度；`good_qty` 仅由 `CheckpointReleased` 累计；`CheckpointBlocked` 计入 `bad_qty`；返修/返工再入后放行计入 `reworked_qty`（不重复计入 `good_qty`）；单件报废计入 `scrapped_qty`。

```yaml
WorkOrderProgress:
  # ─── 标识 ───
  progress_id:      ProgressId            # 进度记录唯一标识（聚合根ID）

  # ─── 绑定 ───
  work_order_id:    WorkOrderId           # 工单唯一标识

  # ─── 累积值（非状态机，INV-08）───
  completed_qty:    Integer = 0           # 总完成量（good + reworked）
  good_qty:         Integer = 0           # 良品量（仅 CheckpointReleased 首次放行累计）
  bad_qty:          Integer = 0           # 不良品量（CheckpointBlocked 累计）
  reworked_qty:     Integer = 0           # 返修再入后放行量（不重复计入 good_qty）
  scrapped_qty:     Integer = 0           # 报废量（消费 UnitScrappedAfterRework / BatchReworkOrderScrapped）

  # ─── 审计 ───
  last_accrued_at:  DateTime?
  updated_at:       DateTime
```

**行为**：
- `initialize(work_order_id)` -> 发出 `WorkOrderProgressInitialized`（前置：工单首次过点放行；-> 初始化为 0）
- `accrueGood(sn)` -> 发出 `WorkOrderProgressAccrued`（前置：`CheckpointReleased` 且 `sn` 首次放行（非再入）；-> `good_qty += 1`，`completed_qty += 1`，INV-08）
- `accrueBad(sn)` -> 发出 `WorkOrderProgressAccrued`（前置：`CheckpointBlocked`；-> `bad_qty += 1`，INV-08）
- `accrueReworked(sn)` -> 发出 `WorkOrderProgressAccrued`（前置：`CheckpointReleased` 且 `sn` 为返修/返工再入后放行；-> `reworked_qty += 1`，`completed_qty += 1`，不重复计入 `good_qty`，INV-08）
- `accrueScrapped(count)` -> 发出 `WorkOrderProgressAccrued`（前置：消费 `UnitScrappedAfterRework` / `BatchReworkOrderScrapped`；-> `scrapped_qty += count`）

> **进度累计口径（INV-08）**：`good_qty` 仅由 `CheckpointReleased` 首次放行累计；`CheckpointBlocked` 计入 `bad_qty`；返修/返工再入后再次过点放行的，计入 `reworked_qty`（单独计数，不重复计入 `good_qty`）；报废计入 `scrapped_qty`。`completed_qty = good_qty + reworked_qty`。

> **🔴 热点：分流时是否扣减工单进度**——单件分流至返修后，`bad_qty` 是否立即 +1？建议：分流时计入 `bad_qty`，返修完成再入后再次过点放行计入 `reworked_qty`。具体口径待与 SME 确认。

### 1.5 TestResult（测试结果·适配层聚合）

**一致性边界**：单件在工位的测试结果结构化数据，来源渠道、原始判定、测量项明细。

**职责**：从 FTP 文件/HTTP 回调/手工填报等异构渠道汇集数据；解析 + 字段映射 + 单位归一化；保留 `raw_verdict` 原始判定（不翻译 PASS/FAIL 业务语义）；与过点判定同事务（BIZ-02）。

```yaml
TestResult:
  # ─── 标识 ───
  test_id:          TestId                # 测试结果唯一标识（聚合根ID）

  # ─── 绑定 ───
  sn:               String                # 产品序列号
  station_id:       StationId             # 测试工位

  # ─── 测试类型 ───
  test_type:        TestType              # AOI / SPI / FCT / PROGRAMMING / SCREW_TORQUE / OTHER

  # ─── 原始判定（透传，不翻译）───
  raw_verdict:      RawVerdict            # 设备原始判定（如 "PASS"/"FAIL"/"0"/"1"/数值），不翻译

  # ─── 测量项 ───
  measured_items[]: List<MeasuredItem>    # 测量项明细（键值对 + 单位）

  # ─── 来源 ───
  source_channel:   TestResultChannel     # FTP / HTTP_CALLBACK / MANUAL_ENTRY
  source_ts:        DateTime              # 数据源时间戳
  structured_ts:    DateTime              # 结构化完成时间

  # ─── 审计 ───
  created_at:       DateTime
```

**行为**：
- `structure(sn, station_id, test_type, raw_verdict, measured_items, source_channel, source_ts)` -> 发出 `TestResultStructured`（前置：`sn` + `station_id` 非空；-> 结构化完成；落入查询表供过点引擎同事务查询）
- `markLateArrived()` -> 发出 `TestResultLateArrived`（前置：对应过点已拦截关单；-> 不回填已关单过点记录 INV-12；供返修/质量上下文评估补救）

> **适配层职责边界**：文件/回调解析、字段映射、单位归一化归本适配层（纯结构化，不做业务判定）；`raw_verdict` 保留设备原始判定，不翻译；PASS/FAIL 业务语义解释归质量上下文；`TestResult` 与过点判定的事务一致性归本上下文（BIZ-02）。

> **🔴 热点：TestResult 与过点的时间窗匹配**——`TestResult` 写入与过点扫码可能存在时序差。建议：过点扫码后开启等待窗口（如 5s），窗口内 `TestResult` 到达则同事务判定；窗口超时则 `CheckpointBlocked(blocking_reason=TestResultTimeout)`。待与 SME 确认窗口长度。

> **🔴 热点：补传数据的过点回填**——设备数据接入上下文断连补传后到达的 `TestResult`，若对应过点已拦截关单，是否回填修正？建议：不回填已关单过点记录（INV-12），而是发布 `TestResultLateArrived` 供返修/质量上下文评估。待与返修上下文确认。

### 1.6 WipUnit（在制品·单件·读侧投影型聚合根）

**一致性边界**：单件在制品的身份、位置投影、状态与流转历史（读侧投影型，最终一致）。

**职责**：消费本上下文写侧事件建立身份（首次建档）；投影位置（最终一致于 `RoutingProgress` 写侧权威）；维护状态机（由消费事件驱动转移，不做业务判定）；累积只增流转历史（`WipHistoryEntry`）；标记返修/返工离线与再入；标记工位拦截。

```yaml
WipUnit:
  # ─── 标识 ───
  sn:               String              # 单件序列号（聚合根ID，与 work_order_id 联合唯一 INV-03）
  work_order_id:    WorkOrderId         # 所属工单

  # ─── 位置投影（最终一致于写侧 RoutingProgress）───
  position:         WipPosition         # 当前工位/位置（station + held_at_station + reentry_source）

  # ─── 状态 ───
  status:           WipUnitStatus       # NOT_STARTED / IN_FLOW / AT_REWORK / REENTERED / COMPLETED / SCRAPPED
  route_version:    String              # 建档时锁定的工艺路线版本（来自首次 RoutingProgressed）
  reentered_count:  Integer             # 再入次数（默认 0）
  reentered_from:   ReentrySource?      # 最近一次再入来源（Rework / BatchRework）

  # ─── 流转历史（只增不可改不可删 INV-04）───
  history[]:        List<WipHistoryEntry>  # 按 timestamp 单调递增

  # ─── 审计 ───
  registered_at:    DateTime            # 建档时间
  last_updated_at:  DateTime            # 最后位置变更时间
  source_event_id:  String              # 最后一条来源事件ID（幂等去重键）
```

**行为**：
- `register(sn, work_order_id, route_version, initial_station, source_event_id)` -> 发出 `WipUnitRegistered`（前置：`(sn, work_order_id)` 全局唯一建档 INV-03；-> `IN_FLOW`；首次位置记录追加首条 `WipHistoryEntry`）
- `updatePosition(new_position, source_event_id)` -> 发出 `WipPositionChanged`（前置：非终态 `COMPLETED`/`SCRAPPED` INV-07/INV-13；`source_event_id` 幂等去重 BIZ-07；追加 `WipHistoryEntry`；按 `timestamp` 单调递增 INV-04）
- `markAtRework(reentry_source, source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `IN_FLOW` INV-09；-> `AT_REWORK`；`position=REWORK_AREA`；追加历史 reason=ReworkRouted/BatchReworkCreated）
- `markReentered(reentry_point, source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `AT_REWORK` INV-11；-> `REENTERED`；`reentered_count++`；`position=reentry_point`；追加历史 reason=ReworkReentered/BatchReworkReentered）
- `markInFlowFromReentered()` -> 状态 `REENTERED -> IN_FLOW`（前置：当前 `REENTERED`；由后续 `RoutingProgressed` 触发，经 `WipProjectionService` 编排）
- `markCompleted(source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `IN_FLOW`；`RoutingProgressed.to_step=最终步序`；-> `COMPLETED`，终态 INV-07）
- `markScrapped(source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `AT_REWORK` INV-13；`source_event_id` 去重；-> `SCRAPPED`，终态 INV-13；`position=SCRAP_AREA`）
- `markHeldAtStation(held)` -> 内部标记 `position.held_at_station`（前置：不改 `status`；仅位置标记；由 `CheckpointBlocked` 触发设置，后续 `RoutingProgressed` 或 `UnitRoutedToRework` 清除）

> **投影型聚合的本质**：`WipUnit` 不做业务判定——状态转移由消费的写侧事件类型映射，位置由 `RoutingProgressed` 载荷投影。聚合根只负责守护一致性边界（身份唯一、历史只增、终态拒收），不决策"该不该过点"。

> **身份建档判据**：本上下文以 **`(sn, work_order_id)` 是否已存在 `WipUnit`** 为建档判据，`from_step=null` 仅作辅助信号——若 SN 已建档则按位置变更处理，未建档则建档。已固化为 `register()` 前置 + INV-03。

> **CheckpointBlocked 投影语义**：`CheckpointBlocked` 表示过点被拦截，在制品物理上仍停留在当前工位。消费后**不改 `WipUnit.status`**（仍是 `IN_FLOW`），仅在 `WipPosition.held_at_station=true` 标记，供车间可视化区分"正常过站中"与"拦截待处理"。该标记在后续 `RoutingProgressed` 或 `UnitRoutedToRework` 到达时清除。

> **不变式编号迁移（2026-07-10 并入）**：原在制品追踪上下文 INV-01/02/05/06/07/11/13 -> 本上下文 INV-03/04/07/09/11/13/14（避开写侧聚合已占用的 INV-01/02/05/06/08/10/12，保留空号不重排）；原 BIZ-01/03/04 -> BIZ-07/（并入 BIZ-06）/BIZ-08；原 INV-CX-01/02/03（在制品↔过点执行跨上下文）降级为 BIZ-09/10（上下文内跨聚合、最终一致）。

### 2.2 Decision（判定结果）

```yaml
Decision:
  - PASS    # 放行
  - BLOCK   # 拦截
```

> 不可变枚举。`PASS` 触发路线推进 + 进度累计 + 工装上报；`BLOCK` 必带 `blocking_reason` + `failed_checks`（INV-02）。

### 2.3 BlockingReason（拦截原因）

```yaml
BlockingReason:
  - AntiErrorFailed          # 防错校验失败
  - QualityGateFail          # 质量门禁 BLOCK
  - QualityHold              # 质量门禁 HOLD（待人工放行）
  - EquipmentUnavailable     # 设备不可用（缓存命中且 available=false）
  - EquipmentCacheMiss       # 设备可用性缓存未命中且降级查询超时
  - EquipmentDataOutOfRange  # 设备实时数据不符合工艺要求
  - EquipmentDataTimeout     # 设备实时数据查询超时（INV-10）
  - RouteCacheMiss           # 工艺路线缓存未命中且降级查询超时/失败
  - TestResultTimeout        # 测试结果等待窗口超时
  - SkipViolation            # 跳站违规（越序前进）
  - MissViolation            # 漏站违规（越序后退）
  - KitNotReady              # 首次过点齐套未就绪
```

> 不可变枚举。`BLOCK` 决策时必填，与 `failed_checks` 明细对应。`QualityHold` 为 HOLD 状态（非永久 BLOCK），待人工放行后走 `OverrideCheckpoint` 通道。

### 2.4 AntiErrorDimension（防错校验维度）

```yaml
AntiErrorDimension:
  - MATERIAL         # 物料/工装校验（BOM 替代料、工装匹配）
  - FIXTURE          # 工装匹配（工装绑定校验）
  - EQUIPMENT_ADM    # 设备准入（EquipmentAvailabilityCache: available=true 且在目标工位）
  - FA_GATE          # 首件门禁（消费首件处理上下文门禁）
  - PRECEDENCE       # 前置工序（RoutingProgress: 前序步序已完成）
  - REALTIME_DATA    # 实时数据（关键工序设备实时数据校验）
```

> 不可变枚举。与工艺管理上下文 §2.6 `AntiErrorDimension` 一一对应。本上下文不定义维度内容，仅按维度执行校验——维度配置归工艺管理上下文 `RouteStep.anti_error_items[]`，本上下文从 `ProcessRouteCache` 读取。

### 2.5 AntiErrorCheckItem / AntiErrorCheckResult（防错校验项与结果）

```yaml
AntiErrorCheckItem:
  dimension:  AntiErrorDimension
  passed:     Boolean
  detail:     String?          # 失败时明细（如 "spec_key zone_count not matched"）

AntiErrorCheckResult:
  passed:         Boolean
  failed_checks[]: List<AntiErrorCheckItem>
  checked_at:     DateTime
```

> 不可变。`AntiErrorCheckResult` 是防错校验的汇总输出，由 `AntiErrorCheckService` 编排各维度并行校验后聚合。`passed=false` 时 `failed_checks` 非空。

### 2.6 QualityGateResult（质量门禁判定结果）

```yaml
QualityGateResult:
  - PASS     # 放行
  - HOLD     # 待人工放行（质量门禁 HOLD）
```

> 不可变枚举。由 `QualityGateCache` 读取规则 + `TestResult` 数据综合判定。HOLD 与 BLOCK 的区别：HOLD 可人工授权放行（`OverrideCheckpoint`），BLOCK 不可。

### 2.8 RoutingProgressState（路由推进状态）

```yaml
RoutingProgressState:
  - NOT_STARTED     # 未开始
  - IN_PROGRESS     # 推进中
  - BLOCKED_SKIP    # 跳站/漏站阻塞
  - COMPLETED       # 已完成（终态 INV-05）
```

**状态机**：

```
                     [NOT_STARTED]
                           |
              首次过点放行 AdvanceRouting
                           |
                           v
                ┌──▶ [IN_PROGRESS] ◀── 返修/返工再入 ReenterFromRework/BatchRework ───┐
                │            │                                                         │
                │     过点放行 AdvanceRouting                                          │
                │            │                                                         │
                │            v                                                         │
                │   ┌── 步序校验 ──┐                                                   │
                │   v              v                                                   │
                │ 下一站正确     跳站/漏站                                              │
                │   |              |                                                   │
                │   v              v                                                   │
                │ 推进成功     StationSkipViolation / StationMissViolation              │
                │   |              | (拦截, 不推进)                                     │
                │   v              v                                                   │
                │ [IN_PROGRESS]  [BLOCKED_SKIP]                                        │
                │   |              |                                                   │
                │   |       人工纠正/授权跳站 ReenterFromSkip                          │
                │   |              |                                                   │
                │   v              v                                                   │
                │ 最终步序放行                                                        │
                │   |                                                                │
                │   v                                                                │
                └─[COMPLETED] ◀──────────────────────────────────────────────────────┘
                      (终态—单件完成全部步序, INV-05)
```

**不变式**：
- `NOT_STARTED -> IN_PROGRESS`：`start()`，首次过点放行驱动
- `IN_PROGRESS -> IN_PROGRESS`（推进）：`advance()`，步序校验通过
- `IN_PROGRESS -> BLOCKED_SKIP`：`blockSkip()` / `blockMiss()`，跳站/漏站检出
- `BLOCKED_SKIP -> IN_PROGRESS`：`reenterFromSkip()`，人工纠正/授权跳站
- `IN_PROGRESS -> COMPLETED`：`advance()` 到达最终步序，终态 INV-05
- 任意非终态 -> `IN_PROGRESS`：`reenterFromRework()` / `reenterFromBatchRework()`，再入点校验通过 INV-CX-01
- 任意非终态 -> 终态（标记报废）：`markScrapped()`，消费 `UnitScrappedAfterRework` / `BatchReworkOrderScrapped`
- `COMPLETED` 之后任何事件均拒收（终态 INV-05）

### 2.9 WorkOrderProgressState（工单进度·非状态机）

```yaml
WorkOrderProgressState:
  - ACTIVE    # 活跃中（工单在制）
  - CLOSED    # 已完结（工单完工/关单）
```

> 工单进度本身不是状态机（累积值），`ACTIVE/CLOSED` 仅表示是否接受新的进度累计。`CLOSED` 后拒收进度累计。

```yaml
ReentrySource:
```

### 2.12 FixtureUsedPayload / MalfunctionReportedPayload（上报事件载荷）

```yaml

MalfunctionReportedPayload:
```

### 2.14 WipPosition / WipHistoryEntry / WipUnitStatus / 读模型（WIP 投影值对象）

> 本节为读侧投影聚合 `WipUnit`（§1.6）的值对象与读模型，由消费写侧事件维护，最终一致。`ReentrySource` 复用 §2.10（Rework / BatchRework）。

```yaml
WipPosition:
  station:          String              # 当前工位/位置（来自 RoutingProgressed.to_step）
  held_at_station:  Boolean             # 是否当前工位拦截中（由 CheckpointBlocked 设置，后续推进清除）
  reentry_source:   ReentrySource?      # 最近离线来源（仅 AT_REWORK/REENTERED 时非空）
  updated_at:       DateTime            # 位置更新时间

  from_station:    String              # 来源工位（首次建档时为 null）
  to_station:      String              # 目标工位
  timestamp:       DateTime            # 过点时间（来自 RoutingProgressed.timestamp）
  route_version:   String              # 过点时的工艺路线版本
  reason:          HistoryReason?      # null=普通过点 / ReworkRouted / BatchReworkCreated / ReworkReentered / BatchReworkReentered / Scrapped
  source_event_id: String              # 来源事件ID（可追溯）

  - ReworkRouted           # 分流至返修
  - BatchReworkCreated     # 分流至返工
  - ReworkReentered        # 返修再入
  - BatchReworkReentered   # 返工再入
  - Scrapped               # 报废

WipUnitStatus:
  - NOT_STARTED   # 未开始（消费首次 RoutingProgressed 建档后进入 IN_FLOW）
  - IN_FLOW       # 在流程中（正常过站中 / 工位拦截中）
```

> `WipPosition` 是最终一致的投影值对象，与写侧 `RoutingProgress`（当前步序权威）存在秒级延迟。`held_at_station` 不改 `status`，仅标记位置拦截状态。`WipHistoryEntry` 只增不可改不可删（INV-04），按 `timestamp` 单调递增；历史可重放重建 `WipPosition`，任意时刻 `WipUnit.position` = 该 SN 最后一条历史的 `to_station`（BIZ-09）。每条 `RoutingProgressed` 都追加一条历史（保留完整轨迹，即使 `from_station == to_station`）。

**WipUnit 状态机**：`NOT_STARTED -> IN_FLOW`（首次建档 INV-03）；`IN_FLOW -> IN_FLOW`（推进，BIZ-09）；`IN_FLOW -> AT_REWORK`（`UnitRoutedToRework` / `BatchReworkOrderCreated`，INV-09）；`AT_REWORK -> REENTERED`（`UnitReworkReentered` / `BatchReworkReentered`，INV-11）；`AT_REWORK -> SCRAPPED`（`rework.task.scrapped` / `brework.order.scrapped`，INV-13）；`REENTERED -> IN_FLOW`（再入后首个 `RoutingProgressed`）；`IN_FLOW -> COMPLETED`（`RoutingProgressed.to_step=最终步序`，INV-07）。`COMPLETED`/`SCRAPPED` 之后任何位置变更均拒收。状态由消费事件类型映射，本聚合不做业务判定。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 AntiErrorCheckService（防错校验编排服务）

**职责**：编排多维度防错校验——并行校验工艺版本/物料工装/设备准入/首件门禁/前置工序/实时数据六个维度，汇总为 `AntiErrorCheckResult`。

```yaml
AntiErrorCheckService:
  方法:
    runAntiErrorChecks(sn, work_order_id, station_id, equipment_id):
      # 前置：CheckpointScanned 已发出
      # 1. 并行校验六个维度（INV-01）：
      #    a. 工艺版本校验：ProcessRouteCache 命中且 routeVersion 有效
      #    b. 物料/工装校验：BOM 替代料、工装匹配（读 ProcessRouteCache 步骤配置）
      #    c. 设备准入校验：EquipmentAvailabilityCache 查询 equipment_id 可用性
      #    d. 首件门禁校验：FirstArticleGateProjection 查询工单门禁状态（BIZ-03）
      #    e. 前置工序校验：RoutingProgress 查询前序步序已完成
      #    f. 实时数据校验：关键工序按需 REST 查询设备数据接入上下文（≤200ms，超时拦截 INV-10）
      # 2. 汇总各维度结果为 AntiErrorCheckResult(passed, failed_checks[])
      # 3. 发出 AntiErrorChecked(sn, station_id, passed, failed_checks[])
      # 4. 返回 AntiErrorCheckResult 供 CheckpointDecisionService 判定
      # 注：设备实时数据查询超时则计为该校验项 FAIL（保守拦截 INV-10），不阻塞防错校验整体返回
```

> **为什么不放在聚合根内**：防错校验需跨多个缓存/投影（`ProcessRouteCache` / `EquipmentAvailabilityCache` / `FirstArticleGateProjection` / `KitStatusCache`）查询 + 跨上下文 REST 查询（设备实时数据）——单条 `CheckpointRecord` 无权访问这些外部数据源。校验是多维度并行编排，归本服务。

> **🔴 热点：防错校验的同步 vs 异步**——建议同步执行（过点是同步交互），设备实时数据查询超时则计为 FAIL（保守拦截），避免过点长时间阻塞。整体需在过点 SLA 内完成（建议 ≤1s），待与 SME 确认。

> **🔴 热点：设备实时数据校验范围**——仅关键工序启用实时数据校验，其余仅做准入校验。校验项配置归工艺管理上下文，本上下文只执行。待与工艺管理上下文/质量上下文确认关键工序清单。

### 3.2 CheckpointDecisionService（过点判定服务）

**职责**：综合防错校验、质量门禁、设备可用性、测试结果、跳站校验多维度判定 PASS/BLOCK。

```yaml
CheckpointDecisionService:
  方法:
    decideCheckpoint(record_id, anti_error_result, quality_gate_result, equipment_available, test_result_available, station_sequence):
      # 1. 综合判定：
      #    anti_error_result.passed=true
      #    AND quality_gate_result=QualityGateResult.PASS
      #    AND equipment_available=true
      #    AND test_result_available=true
      #    AND station_sequence=CORRECT
      #    -> PASS（BIZ-01）
      #    否则 -> BLOCK（INV-02）
      # 2. BLOCK 时构造 blocking_reason + failed_checks[]（按优先级：跳站 > 防错 > 质量 > 设备 > 测试超时）
      # 3. 创建 CheckpointDecision -> decide(...) -> CheckpointReleased / CheckpointBlocked
      # 4. PASS -> 同事务触发：AdvanceRouting + AccrueWorkOrderProgress + ReportFixtureUsage（BIZ-01）
      # 5. BLOCK + blocking_reason ∈ 质量类 -> 触发 RouteToRework（分流至返修）
      # 6. BLOCK + blocking_reason=QualityHold -> 仅记录拦截，等待人工 OverrideCheckpoint
      # 注：QualityHold 不自动分流，人工放行通过 OverrideCheckpoint 命令
```

> **为什么不放在聚合根内**：判定需综合 5 个维度（防错/质量/设备/测试/跳站）的查询结果，这些结果来自不同聚合/缓存/外部查询——单条 `CheckpointDecision` 无权聚合多方数据。PASS 后同事务推进 `RoutingProgress` + `WorkOrderProgress` 是跨聚合编排，归本服务。

> **🔴 热点：拦截后是否自动分流返修**——仅 `blocking_reason ∈ 质量类` 时自动分流；设备/物料类拦截由通知服务推送人工处理（安灯告警），不自动进返修。已固化。

> **🔴 热点：HOLD 与人工放行**——`QualityHold` 后的人工放行作为独立命令 `OverrideCheckpoint`（带授权人、原因），发布 `CheckpointOverridden` 事件，不绕过质量上下文规则而是记录例外。待与质量上下文确认放行权限模型。

### 3.3 RoutingProgressService（路线推进服务）

**职责**：编排过点放行后的路线推进——站序校验、推进、跳站/漏站拦截、COMPLETED 判定。

```yaml
RoutingProgressService:
  方法:
    advanceRouting(sn, work_order_id, station_id, route_version_id, route_id):
      # 1. 加载 RoutingProgress（按 sn）
      # 2. 若不存在 -> start(sn, work_order_id, route_version_id, route_id, step_no, station_id) -> IN_PROGRESS
      # 3. 若存在 -> CheckStationSequence(当前步序+1 vs 过点工位对应步序)
      #    a. 一致 -> advance(from_step, to_step, station_id) -> RoutingProgressed
      #       - 若 to_step 为最终步序 -> complete() -> COMPLETED（终态 INV-05）
      #    b. 跳站 -> blockSkip(expected, actual) -> StationSkipViolation
      #       - 同时 CheckpointBlocked(blocking_reason=SkipViolation)
      #    c. 漏站 -> blockMiss(expected, actual) -> StationMissViolation
      #       - 同时 CheckpointBlocked(blocking_reason=MissViolation)
      # 4. 发布 mes.routing.progress（供本上下文读侧投影位置 + 外部追溯/数据应用）

    reenterFromSkip(sn, step_no, station_id, authorized_by):
      # 前置：RoutingProgress.state=BLOCKED_SKIP
      # 1. reenterFromSkip(step_no, station_id, authorized_by) -> SkipReentered
      # 2. -> IN_PROGRESS

    reenterFromRework(sn, reentry_point, rework_task_id):
      # 前置：消费 UnitReworkCompleted，INV-CX-01
      # 1. 校验 reentry_point ∈ 当前 routeVersion 合法步序
      # 2. 合法 -> reenterFromRework(reentry_point, rework_task_id) -> UnitReworkReentered
      # 3. 非法 -> 发布 ReentryRejected(sn, rework_task_id, reason=InvalidReentryPoint)
      #    返修上下文订阅，重新判定再入点

    reenterFromBatchRework(sn, reentry_point, rework_order_id):
      # 同上，BatchReworkReentered / ReentryRejected

    markScrapped(sn, source_id):
      # 前置：消费 UnitScrappedAfterRework / BatchReworkOrderScrapped
      # 1. markScrapped() -> RoutingProgressScrapped
      # 2. WorkOrderProgress.accrueScrapped(1)
```

> **为什么不放在聚合根内**：路线推进需跨聚合协调——站序校验需查 `ProcessRouteCache`（读模型），推进结果需驱动 `CheckpointDecision`（判定拦截）和 `WorkOrderProgress`（进度累计），再入需校验 `routeVersion` 合法性（跨聚合缓存查询）。归本服务编排。

> **🔴 热点：授权跳站**——某些场景需授权跳站。`reenterFromSkip` 支持带 `authorized_by`，跳过站序校验但仍记录 `StationSkipViolation(authorized=true)`，保证可追溯。待与工艺管理上下文确认授权跳站规则。

### 3.5 ReentryService（再入服务）


### 3.10 WipProjectionService（在制品投影服务）

**职责**：消费本上下文写侧事件（`RoutingProgressed` / `CheckpointBlocked` / `UnitRoutedToRework` / `UnitReworkReentered` / `BatchReworkReentered`）与上下文外事件（`rework.task.scrapped` / `brework.order.created` / `brework.order.scrapped` / `ProcessRouteActivated`），投影 `WipUnit` 位置、状态与流转历史；幂等去重（`source_event_id` 去重表 BIZ-07）；首次推进建档（INV-03）。

```yaml
WipProjectionService:
  方法:
    onRoutingProgressed(sn, from_step, to_step, route_version, work_order_id, timestamp, source_event_id):
      # 来源：本上下文写侧 RoutingProgressed（mes.routing.progress）
      # 1. 幂等去重：sn + source_event_id（BIZ-07）
      # 2. 未建档 -> register() -> WipUnitRegistered（INV-03）-> updatePosition() -> WipPositionChanged（同事务）
      # 3. 已建档 + 非终态：
      #    - REENTERED -> markInFlowFromReentered() -> IN_FLOW
      #    - to_step=最终步序 -> markCompleted() -> COMPLETED（INV-07）
      #    - 否则 -> updatePosition(to_step) -> WipPositionChanged（BIZ-09）
      # 4. 已建档 + 终态 -> 拒收，记日志（INV-07/INV-13）
      # 5. 追加 WipHistoryEntry；若 held_at_station=true -> 清除

    onCheckpointBlocked(sn, station, checkpoint_record_id, work_order_id):
      # 来源：本上下文写侧 CheckpointBlocked
      # 幂等：sn + checkpoint_record_id；markHeldAtStation(true)（不改 status）；不追加历史

    onUnitRoutedToRework(sn, from_station, defect_reason, work_order_id, routed_at, source_event_id):
      # 来源：本上下文写侧 UnitRoutedToRework（mes.unit.routed-to-rework）
      # 幂等：sn + source_event_id（INV-09）；IN_FLOW -> markAtRework(Rework) -> AT_REWORK；追加历史 reason=ReworkRouted

    onUnitReworkReentered(sn, reentry_point, rework_task_id, route_version):
      # 来源：本上下文写侧 UnitReworkReentered（mes.reentry.reworked）
      # 幂等：sn + rework_task_id（INV-11）；AT_REWORK -> markReentered() -> REENTERED；追加历史 reason=ReworkReentered

    onBatchReworkOrderCreated(rework_order_id, sn_list[], work_order_id):
      # 来源：返工上下文 brework.order.created（上下文外）
      # 逐 SN：幂等 sn + rework_order_id；IN_FLOW -> markAtRework(BatchRework) -> AT_REWORK；追加历史 reason=BatchReworkCreated

    onBatchReworkReentered(rework_order_id, sn_list[], reentry_point, route_version):
      # 来源：本上下文写侧 BatchReworkReentered（mes.reentry.reworked）
      # 逐 SN：AT_REWORK -> markReentered() -> REENTERED；追加历史 reason=BatchReworkReentered

    onUnitScrappedAfterRework(sn, task_id, work_order_id):
      # 来源：返修上下文 rework.task.scrapped（上下文外）
      # 幂等：sn + task_id；AT_REWORK -> markScrapped() -> SCRAPPED（INV-13）；追加历史 reason=Scrapped

    onBatchReworkOrderScrapped(rework_order_id, sn_list[], work_order_id):
      # 来源：返工上下文 brework.order.scrapped（上下文外）
      # 逐 SN：AT_REWORK -> markScrapped() -> SCRAPPED（INV-13）；追加历史 reason=Scrapped

    onProcessRouteActivated(route_version_id, route_id, version_no, product_id):
      # 来源：工艺管理上下文 process.* ProcessRouteActivated（上下文外）
      # 刷新 route_version 只读引用缓存；不影响已建档 WipUnit（其 route_version 建档时锁定）
```

> **为什么不放在聚合根内**：`WipProjectionService` 需消费多个写侧/上下文外事件，按事件类型路由到不同 `WipUnit` 行为；单条 `WipUnit` 聚合无权自我驱动事件消费或查询其它 SN 实例。幂等去重（BIZ-07）是跨实例不变式；首次建档判据需查询 `(sn, work_order_id)` 是否已存在。归本服务 + 事件去重表保证。

> **上下文内 vs 上下文外事件**：`RoutingProgressed` / `CheckpointBlocked` / `UnitRoutedToRework` / `UnitReworkReentered` / `BatchReworkReentered` 由本上下文写侧聚合发布，`WipProjectionService` 进程内订阅（上下文内 CQRS 读侧投影）；`rework.task.scrapped` / `brework.order.created` / `brework.order.scrapped` / `ProcessRouteActivated` 由上下文外发布，经 ACL 翻译消费。再入事件不直接消费返修/返工上下文，而是经本上下文写侧 `ReentryService`（§3.5）统一处理后发布 `mes.reentry.reworked`，保证再入点校验权威归写侧。

> 🔴 **热点：事件乱序处理**：`UnitRoutedToRework` 与 `UnitReworkReentered` 可能因事件投递延迟导致乱序。建议维护事件序号或过点时间戳，乱序事件暂存缓冲按序重放；缓冲超时仍乱序，按"以最新状态为准"策略接受并记日志告警。待与平台运维确认事件投递有序性保证。

> 🔴 **热点：返工批量再入的 SN 集合来源**：`BatchReworkReentered` 是否携带受影响 SN 列表？建议事件载荷携带 SN 列表（或 `rework_order_id` + 批量标识），按 SN 维度逐个处理。待与返工上下文确认事件载荷。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文是核心枢纽，与工艺管理/质量/设备工装台账/设备数据接入/首件处理/返修/返工共七个上下文通过事件契约协作，不在过点主事务中引入分布式事务（领域总览 §5.3）。

### 4.1 CheckpointCommandAppService（过点命令应用服务）

**职责**：处理扫码过点、防错校验、判定放行/拦截、人工放行、跳站纠正、设备故障上报的写操作命令（REST/终端入口，发命令者：操作员/工程师）。

```yaml
CheckpointCommandAppService:
  方法:
    # ─── 扫码过点 ───
    scanCheckpoint(cmd):
      # -> CheckpointRecord.scan -> 写仓储 -> Outbox
      # 幂等：commandId；sn 同工单不可重复过点同站（BIZ-04）
      # 策略：自动触发 RunAntiErrorChecks -> AntiErrorCheckService

    # ─── 人工放行（HOLD 拦截后）───
    overrideCheckpoint(record_id, override_reason, authorized_by):
      # -> CheckpointRecord.overrideCheckpoint -> CheckpointOverridden
      # 前置：当前 decision=BLOCK 且 blocking_reason=QualityHold

    # ─── 跳站纠正 ───
    reenterFromSkip(sn, step_no, station_id, authorized_by):
      # -> RoutingProgressService.reenterFromSkip

    # ─── 设备故障上报 ───
    reportMalfunction(asset_id, symptom, severity, reported_by):
      # -> MalfunctionReportService.reportMalfunction -> 发布 MalfunctionReported
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|──────|─────────-|────────────——|─────────-|─────────-|
| 扫码过点 | 单聚合事务 | `CheckpointRecord.scan` | `CheckpointScanned` | `commandId`；`(sn, work_order_id, station_id)` 去重（BIZ-04） |
| 过点判定（自动化） | 多聚合同事务 | `CheckpointDecisionService` + `RoutingProgressService` + `WorkOrderProgressService` + `FixtureUsageReportService` | `CheckpointReleased`/`Blocked` + `RoutingProgressed`/`StationSkipViolation` + `WorkOrderProgressAccrued` + `FixtureUsed` | `commandId`；`CheckpointRecord` 不可变 INV-12 |
| 人工放行 | 单聚合事务 | `CheckpointRecord.overrideCheckpoint` | `CheckpointOverridden` | `commandId`；前置 QualityHold |
| 跳站纠正 | 单聚合事务 | `RoutingProgressService.reenterFromSkip` | `SkipReentered` | `commandId` |
| 设备故障上报 | 无聚合（仅事件发布） | `MalfunctionReportService.reportMalfunction` | `MalfunctionReported` | `commandId` |

> **过点判定的事务边界**：`CheckpointDecision` + `CheckpointRecord` + `RoutingProgress` + `WorkOrderProgress` + `TestResult`（若已到达）同事务写入 + Outbox（BIZ-01/BIZ-02）。这是本上下文最核心的事务边界——五聚合同事务，保证过点事实、判定、推进、进度、测试结果的一致性。

> **🔴 热点：过点 SLA**——建议 ≤1s，涵盖扫码->防错校验->判定->记录->推进->累计->工装上报全链路。待与 SME 确认。

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.7 消费策略逐条迁入）。

```yaml
    # 质量上下文

      # 幂等：rule_id + version 去重

    # 首件处理上下文（主题前缀 fai.*）
    fai.article.released (FirstArticleReleased):

    fai.article.blocked (FirstArticleBlocked):

    rework.task.completed (UnitReworkCompleted):

      # 幂等：sn + rework_task_id 去重（INV-CX-01）
    rework.task.scrapped (UnitScrappedAfterRework):
```

> **降级查询不算"消费事件"**：过点时 `ProcessRouteCache` / `EquipmentAvailabilityCache` 未命中触发的 REST 查询是同步降级路径，不在本表事件消费范畴，但需保证不引入分布式事务。

> **🔴 热点：制造资源服务各上下文的主题前缀**——工艺管理上下文与质量上下文的事件风暴已落地，其主题前缀 `process.*` / `quality.*` 已确认。本上下文订阅 `ProcessRouteActivated` 与质量门禁规则变更事件，前缀以制造资源服务最终约定为准。

## 5. 领域事件

### 5.1 扫码过点与防错校验事件

| 事件 | 载荷 | 发出者 |
|──────|──────|──────——|
| `CheckpointScanned` | record_id, sn, work_order_id, station_id, equipment_id, scanned_by, scanned_at | CheckpointRecord |
| `AntiErrorChecked` | sn, station_id, passed, failed_checks[], checked_at | AntiErrorCheckService（编排） |

> `CheckpointScanned` 触发策略 `RunAntiErrorChecks`（AntiErrorCheckService）。`AntiErrorChecked` 的 `passed` 决定进入 `DecideCheckpoint(release)` 或 `DecideCheckpoint(block)`。

### 5.2 过点判定事件

| 事件 | 载荷 | 发出者 |
|──────|──────|──────——|
| `CheckpointReleased` | record_id, sn, work_order_id, station_id, route_version_id, decision=PASS, released_at | CheckpointDecision（经 CheckpointDecisionService 编排） |

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 在制品执行上下文](../事件风暴/在制品执行上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

- 本上下文**订阅**：使用各发布限界上下文自己的前缀，不重写——`process.*`（工艺管理上下文）、`eam.*`（设备工装台账上下文）、`quality.*`（质量上下文）、`fai.*`（首件处理上下文）、`rework.*`（返修上下文）、`brework.*`（返工上下文）、`wo.*`（工单管理上下文）。

> **读模型**：本上下文对外提供 `ProcessRouteCache` / `EquipmentAvailabilityCache` / `QualityGateCache` / `KitStatusCache` 的只读投影（最终一致），供生产执行服务内其他上下文（如工单管理）查询，不对外服务。

```
│  AntiErrorCheckService │ CheckpointDecisionService                    │

│  ReentryService │ CacheRefreshService │ ReworkRoutingService          │
│  MalfunctionReportService │ FixtureUsageReportService                 │
│  WipProjectionService（读侧投影）                                     │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  CheckpointRecord / CheckpointDecision / RoutingProgress              │
│  WorkOrderProgress / TestResult                                       │
│  WipUnit（读侧投影型聚合根）                                          │

└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 过点判定是五聚合同事务（BIZ-01），不在过点主事务中引入分布式事务
- 缓存刷新与再入经异步事件解耦（INV-CX-03/16/18），降级查询不引入分布式事务
