## 0. 建模总览

本域是生产执行服务下的**读模型/投影子域**，是 PCBA + 整机组装混合型车间所有"在制品在哪儿、什么状态、能不能齐套开工"的查询权威源。核心职责是**消费过点执行上下文的事件投影单件位置与流转历史（投影型聚合），以及消费物料上下文事件重算工单齐套状态（判定型聚合）**——即"**在制品身份建档、位置投影、流转历史累积、齐套状态判定与发布**"；**不负责**过点判定与放行/拦截（归过点执行上下文）、工艺路线推进（归过点执行上下文）、物料主数据与库存事实源（归物料上下文）、单件返修任务执行（归返修上下文）、批量返工工单（归返工上下文）、首件检验流程编排（归首件处理上下文）。

本上下文与过点执行上下文是**写侧/读侧**的 CQRS 式协作——过点执行是写侧权威（过站瞬间事实），在制品追踪是读侧投影（位置累积）。`WipUnit.position` 是**最终一致**的投影，与过点执行上下文的 `RoutingProgress`（写侧权威）存在秒级延迟，本上下文只保证**幂等重放可重建**（INV-CX-01）。`KitStatus` 是**判定型**聚合——消费物料上下文事件重算 `kit_ready`，双向可逆（INV-08），与 `WipUnit` 的终态单向性形成本质差异。

## 1. 聚合根

### 1.1 WipUnit（在制品·单件）

**一致性边界**：单件在制品的身份、位置投影、状态与流转历史。

**职责**：消费过点执行上下文事件建立身份（首次建档）；投影位置（最终一致于 `RoutingProgress`）；维护状态机（由消费事件驱动转移，不做业务判定）；累积只增流转历史（`WipHistoryEntry`）；标记返修/返工离线与再入；标记工位拦截。

```yaml
WipUnit:
  # ─── 标识 ───
  sn:               String              # 单件序列号（聚合根ID，与 work_order_id 联合唯一 INV-01）
  work_order_id:    WorkOrderId         # 所属工单

  # ─── 位置投影（最终一致于过点执行 RoutingProgress）───
  position:         WipPosition         # 当前工位/位置（station + held_at_station + reentry_source）

  # ─── 状态 ───
  status:           WipUnitStatus       # NOT_STARTED / IN_FLOW / AT_REWORK / REENTERED / COMPLETED / SCRAPPED
  route_version:    String              # 建档时锁定的工艺路线版本（来自首次 RoutingProgressed）
  reentered_count:  Integer             # 再入次数（默认 0）
  reentered_from:   ReentrySource?      # 最近一次再入来源（Rework / BatchRework）

  # ─── 流转历史（只增不可改不可删 INV-02）───
  history[]:        List<WipHistoryEntry>  # 按 timestamp 单调递增

  # ─── 审计 ───
  registered_at:    DateTime            # 建档时间
  last_updated_at:  DateTime            # 最后位置变更时间
  source_event_id:  String              # 最后一条来源事件ID（幂等去重键）
```

**行为**：
- `register(sn, work_order_id, route_version, initial_station, source_event_id)` -> 发出 `WipUnitRegistered`（前置：`(sn, work_order_id)` 全局唯一建档 INV-01；-> `IN_FLOW`；首次位置记录追加首条 `WipHistoryEntry`）
- `updatePosition(new_position, source_event_id)` -> 发出 `WipPositionChanged`（前置：非终态 `COMPLETED`/`SCRAPPED` INV-05/INV-11；`source_event_id` 幂等去重 BIZ-01；追加 `WipHistoryEntry`；按 `timestamp` 单调递增 INV-02）
- `markAtRework(reentry_source, source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `IN_FLOW` INV-06；`source_event_id` 去重；-> `AT_REWORK`；`position=REWORK_AREA`；追加 `WipHistoryEntry` reason=ReworkRouted/BatchReworkCreated）
- `markReentered(reentry_point, source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `AT_REWORK` INV-07；`source_event_id` 去重；-> `REENTERED`；`reentered_count++`；`position=reentry_point`；追加 `WipHistoryEntry` reason=ReworkReentered/BatchReworkReentered）
- `markInFlowFromReentered()` -> 状态 `REENTERED -> IN_FLOW`（前置：当前 `REENTERED`；由后续 `RoutingProgressed` 触发，经 `WipProjectionService` 编排）
- `markCompleted(source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `IN_FLOW`；`RoutingProgressed.to_step=最终步序`；-> `COMPLETED`，终态 INV-05）
- `markScrapped(source_event_id)` -> 发出 `WipPositionChanged`（前置：当前 `AT_REWORK` INV-11；`source_event_id` 去重；-> `SCRAPPED`，终态 INV-11；`position=SCRAP_AREA`）
- `markHeldAtStation(held)` -> 内部标记 `position.held_at_station`（前置：不改 `status`；仅位置标记；由 `CheckpointBlocked` 触发设置，后续 `RoutingProgressed` 或 `UnitRoutedToRework` 清除）

> **投影型聚合的本质**：`WipUnit` 不做业务判定——状态转移由消费的过点执行事件类型映射，位置由 `RoutingProgressed` 载荷投影。聚合根只负责守护一致性边界（身份唯一、历史只增、终态拒收），不决策"该不该过点"。

> **身份建档判据**（事件风暴 §2.1 热点）：本上下文以 **`(sn, work_order_id)` 是否已存在 `WipUnit`** 为建档判据，`from_step=null` 仅作辅助信号——若 SN 已建档则按位置变更处理，未建档则建档。已固化为 `register()` 前置 + INV-01。

> **CheckpointBlocked 投影语义**：`CheckpointBlocked` 表示过点被拦截，在制品物理上仍停留在当前工位。本上下文消费后**不改 `WipUnit.status`**（仍是 `IN_FLOW`），仅在 `WipPosition.held_at_station=true` 标记，供车间可视化区分"正常过站中"与"拦截待处理"。该标记在后续 `RoutingProgressed` 或 `UnitRoutedToRework` 到达时清除。

### 1.2 KitStatus（工单齐套状态）

**一致性边界**：单个工单的物料齐套判定状态。

**职责**：消费物料上下文事件重算 `kit_ready` 与 `missing_items[]`；双向可逆（齐套后可因缺料回到 NOT_READY INV-08）；幂等去重（`work_order_id + source_event_id`，无变化不发布 BIZ-02）；发布 `KitStatusChanged` 供过点执行/排产消费。

```yaml
KitStatus:
  # ─── 标识 ───
  work_order_id:    WorkOrderId         # 工单标识（聚合根ID）

  # ─── 齐套判定 ───
  kit_ready:        Boolean             # 是否齐套（true ⇔ missing_items 为空 INV-08）
  missing_items[]:  List<KitItem>       # 缺料明细（kit_ready=true 时为空）

  # ─── 审计 ───
  last_source_event_id: String          # 最后一条来源事件ID（幂等去重键 BIZ-02）
  last_changed_at:  DateTime            # 最后齐套状态变更时间
```

**行为**：
- `recompute(items[], source_event_id)` -> 发出 `KitStatusChanged`（前置：`source_event_id` 幂等去重 BIZ-02；按 `items[]` 判定 `kit_ready` 与 `missing_items`；新旧状态比较——无变化则不发布 BIZ-02；`kit_ready` 双向可逆 INV-08）

> **判定型聚合的本质**：`KitStatus` 是**可逆**的——与 `WipUnit` 的终态不同，`kit_ready` 可从 `true` 回到 `false`（若物料上下文报告缺料/替代料失效）。这是齐套判定型聚合与位置投影型聚合的本质差异。`KitStatus` 不做 BOM 解析或库存查询——这些是物料上下文的职责，本上下文仅消费其事件判定结果。

> **齐套状态不设独立读模型**：`KitStatus` 聚合本身数据量小（每个工单一条记录），查询直接读聚合即可，无需额外投影。`KitStatusChanged` 事件发布到 `wip.kit.status` 供过点执行/排产消费。

## 2. 值对象

### 2.1 WorkOrderId / SourceEventId（标识）

```yaml
WorkOrderId:   { value: String }    # 工单标识（引用工单管理上下文，经 ACL 翻译）
SourceEventId: { value: String }    # 来源事件ID（幂等去重键）
```

> 不可变。`WorkOrderId` 是上下文外引用，经防腐层（ACL）从工单管理上下文翻译为本上下文语义，本上下文不持有工单聚合。`SourceEventId` 用于跨事件幂等去重（BIZ-01/BIZ-02）。

### 2.2 WipPosition（在制品位置投影）

```yaml
WipPosition:
  station:          String              # 当前工位/位置（来自 RoutingProgressed.to_step）
  held_at_station:  Boolean             # 是否当前工位拦截中（由 CheckpointBlocked 设置，后续推进清除）
  reentry_source:   ReentrySource?      # 最近离线来源（Rework / BatchRework，仅在 AT_REWORK/REENTERED 时非空）
  updated_at:       DateTime            # 位置更新时间
```

```yaml
ReentrySource:
  - Rework       # 单件返修离线
  - BatchRework  # 批量返工离线
```

> `WipPosition` 是**最终一致**的投影值对象，与过点执行上下文的 `RoutingProgress`（写侧权威）存在秒级延迟。`held_at_station` 不改 `status`，仅标记位置拦截状态。`reentry_source` 用于区分离线来源（返修 vs 返工），供流转历史追溯。

### 2.3 WipHistoryEntry（流转历史条目）

```yaml
WipHistoryEntry:
  from_station:    String              # 来源工位（首次建档时为 null）
  to_station:      String              # 目标工位
  timestamp:       DateTime            # 过点时间（来自 RoutingProgressed.timestamp）
  route_version:   String              # 过点时的工艺路线版本
  reason:          HistoryReason?      # 流转原因（null=普通过点 / ReworkRouted=返修离线 / BatchReworkCreated=返工离线 / ReworkReentered=返修再入 / BatchReworkReentered=返工再入 / Scrapped=报废）
  source_event_id: String              # 来源事件ID（可追溯）
```

```yaml
HistoryReason:
  - ReworkRouted           # 分流至返修
  - BatchReworkCreated     # 分流至返工
  - ReworkReentered        # 返修再入
  - BatchReworkReentered   # 返工再入
  - Scrapped               # 报废
```

> 隶属于 `WipUnit` 的值对象集合。**只增不可改不可删**（INV-02），按 `timestamp` 单调递增。历史可重放重建 `WipPosition`——任意时刻 `WipUnit.position` = 该 SN 最后一条历史的 `to_station`（INV-CX-01）。`(from_station, to_station)` 必须与触发它的来源事件载荷一致。

> **流转历史粒度**（事件风暴 §2.3 热点）：每条 `RoutingProgressed` 都追加一条历史（保留完整轨迹，便于正反向追溯），即使 `from_station == to_station`（如同工位复测）也记录。已固化。

### 2.4 KitItem（齐套明细项）

```yaml
KitItem:
  item_code:       String              # 物料编码
  item_name:       String              # 物料名称
  required_qty:    Integer             # 需求数量
  available_qty:   Integer             # 可用数量
  shortage_qty:    Integer             # 缺料数量（= required_qty - available_qty，>0 时出现在 missing_items）
```

> 隶属于 `KitStatus.missing_items[]` 的值对象。`missing_items` 为空 ⇔ `kit_ready=true`（INV-08）。仅记录缺料项（`shortage_qty > 0`），齐套项不出现在 `missing_items` 中。

### 2.5 WipUnitStatus（在制品状态）

```yaml
WipUnitStatus:
  - NOT_STARTED   # 未开始（初始值，消费首次 RoutingProgressed 建档后立即进入 IN_FLOW）
  - IN_FLOW       # 在流程中（正常过站中 / 工位拦截中）
  - AT_REWORK     # 离线返修/返工中（位置标记为 REWORK_AREA）
  - REENTERED     # 已再入（位置已更新到再入点，待后续 RoutingProgressed 推进至 IN_FLOW）
  - COMPLETED     # 已完成（终态，INV-05）
  - SCRAPPED      # 已报废（终态，INV-11）
```

**状态机**：

```
                   [NOT_STARTED]
                         |
                首次 RoutingProgressed
                (from_step=null, SN 未建档)
                建档 + 首次位置变更
                         |
                         v
              ┌─▶ [IN_FLOW] ◀── 再入后 RoutingProgressed ───┐
              │            │      (REENTERED -> IN_FLOW)       │
              │            │                                   │
              │     RoutingProgressed                         │
              │     (后续推进)                                 │
              │            │                                   │
              │            v                                   │
              │     ┌─ 事件类型分流 ─┐                         │
              │     v                 v                        │
              │   普通过点推进     分流至返修/返工离线             │
              │     |       (UnitRoutedToRework                │
              │     |        或 BatchReworkOrderCreated)        │
              │     |                 |                        │
              │     v                 v                        │
              │  [IN_FLOW]      [AT_REWORK]                    │
              │     |                 |                        │
              │     |          ┌──────┴───────┐                │
              │     |          v              v                │
              │     |     返修/返工再入     返修/返工报废         │
              │     |     (UnitReworkReentered  (rework.task.  │
              │     |      或 BatchReworkReentered) scrapped 或 │
              │     |          |          brework.order.       │
              │     |          v          scrapped)            │
              │     |   [REENTERED]         |                  │
              │     |     (reentered_count++, v                 │
              │     |      reentered_from) [SCRAPPED]          │
              │     |          |          (终态, INV-11)        │
              │     |          v                                │
              │     └── 再入后 RoutingProgressed ──────────────┘
              │
              │   最终步序完成
              │   (RoutingProgressed.to_step=最终步序)
              │         |
              │         v
              └─[COMPLETED]
                    (终态, INV-05)
```

**不变式**：
- `NOT_STARTED -> IN_FLOW`：`register()` + `updatePosition()`，由首次 `RoutingProgressed(from_step=null)` 触发（INV-01）
- `IN_FLOW -> IN_FLOW`（推进）：`updatePosition()`，由后续 `RoutingProgressed` 触发（INV-CX-01）
- `IN_FLOW -> AT_REWORK`：`markAtRework()`，由 `UnitRoutedToRework` 或 `BatchReworkOrderCreated` 触发（INV-06）
- `AT_REWORK -> REENTERED`：`markReentered()`，由 `UnitReworkReentered` 或 `BatchReworkReentered` 触发（INV-07）
- `AT_REWORK -> SCRAPPED`：`markScrapped()`，由 `rework.task.scrapped` 或 `brework.order.scrapped` 触发（INV-11）
- `REENTERED -> IN_FLOW`：`markInFlowFromReentered()`，由再入后首个 `RoutingProgressed` 触发
- `IN_FLOW -> COMPLETED`：`markCompleted()`，由 `RoutingProgressed(to_step=最终步序)` 触发（INV-05）
- `COMPLETED` / `SCRAPPED` 之后任何位置变更均拒收（终态 INV-05/INV-11）
- 状态由消费事件类型映射，本上下文**不做业务判定**

> **返工批量离线与再入的处理**：返工 SN 通过消费 `BatchReworkOrderCreated` 逐 SN 标记为 `AT_REWORK`（`reentry_source=BatchRework`），与返修 SN 通过 `UnitRoutedToRework` 进入 `AT_REWORK` 路径同构；再入时 `BatchReworkReentered` 与 `UnitReworkReentered` 同构，每个受影响 SN 走 `AT_REWORK -> REENTERED -> IN_FLOW` 路径。

> 🔴 **热点：事件乱序处理**——`UnitRoutedToRework` 与 `UnitReworkReentered` 可能因事件投递延迟导致乱序（再入事件先于分流事件到达）。建议：本上下文维护一个**事件序号**或**过点时间戳**，乱序到达的事件暂存缓冲，按序号重放；若缓冲超时仍乱序，按"以最新状态为准"策略接受再入事件并记日志告警。待与平台运维确认事件投递有序性保证。

### 2.6 KitReadyStatus（齐套判定状态）

```yaml
KitReadyStatus:
  - READY       # 齐套（kit_ready=true, missing_items=[]）
  - NOT_READY   # 未齐套（kit_ready=false, missing_items 非空）
```

> `KitStatus` 不是严格状态机而是**判定值**（`kit_ready: bool` + `missing_items[]`），由物料上下文事件驱动重算。**双向可逆**（INV-08）——齐套后若物料上下文报告缺料/替代料失效，`kit_ready` 可从 `true` 回到 `false`。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 WipProjectionService（在制品投影服务）

**职责**：消费过点执行上下文事件（`mes.*` / `rework.*` / `brework.*`），投影 `WipUnit` 位置、状态与流转历史；幂等去重（`source_event_id` 去重表 BIZ-01）；事件乱序缓冲补偿（🔴 热点）；首次推进建档（INV-01）。

```yaml
WipProjectionService:
  方法:
    onRoutingProgressed(sn, from_step, to_step, route_version, work_order_id, timestamp, source_event_id):
      # 来源：过点执行上下文 mes.routing.progress RoutingProgressed
      # 1. 幂等去重：sn + source_event_id 去重表（BIZ-01）
      # 2. 查询 WipUnit：
      #    a. 未建档（(sn, work_order_id) 不存在）-> register() -> WipUnitRegistered（INV-01）
      #       -> updatePosition(initial_station) -> WipPositionChanged（首次位置变更，同事务）
      #    b. 已建档 + 非终态：
      #       - 若 status=REENTERED -> markInFlowFromReentered() -> IN_FLOW
      #       - 若 to_step=最终步序 -> markCompleted() -> COMPLETED（INV-05）
      #       - 否则 -> updatePosition(to_step) -> WipPositionChanged（INV-CX-01）
      #    c. 已建档 + 终态（COMPLETED/SCRAPPED）-> 拒收，记日志（INV-05/INV-11）
      # 3. 追加 WipHistoryEntry（from_step, to_step, timestamp, route_version, source_event_id）
      # 4. 若 held_at_station=true -> 清除（推进后拦截标记自然解除）

    onCheckpointBlocked(sn, station, checkpoint_record_id, work_order_id):
      # 来源：过点执行上下文 mes.checkpoint.lifecycle CheckpointBlocked
      # 1. 幂等去重：sn + checkpoint_record_id
      # 2. 查询 WipUnit（已建档 + 非终态）-> markHeldAtStation(true)（不改 status）
      # 3. 不追加 WipHistoryEntry（未推进，仅位置标记）

    onCheckpointReleased(sn, station, checkpoint_record_id, work_order_id):
      # 来源：过点执行上下文 mes.checkpoint.lifecycle CheckpointReleased
      # 1. 幂等去重：sn + checkpoint_record_id
      # 2. 辅助位置投影（若 RoutingProgressed 缺失时的兜底，🔴 可选）
      #    -> updatePosition(station)（若与当前 position.station 不同）

    onUnitRoutedToRework(sn, from_station, defect_reason, work_order_id, routed_at, source_event_id):
      # 来源：过点执行上下文 mes.unit.routed-to-rework UnitRoutedToRework
      # 1. 幂等去重：sn + source_event_id（INV-06）
      # 2. 查询 WipUnit：
      #    a. 已建档 + IN_FLOW -> markAtRework(Rework, source_event_id) -> AT_REWORK
      #       -> WipPositionChanged(to_station=REWORK_AREA)，追加 WipHistoryEntry(reason=ReworkRouted)
      #    b. 未建档 -> 记日志（边界场景，先建档再标记）
      #    c. 非 IN_FLOW -> 忽略（记日志，不改状态）

    onUnitReworkReentered(sn, reentry_point, rework_task_id, route_version):
      # 来源：过点执行上下文 mes.reentry.reworked UnitReworkReentered
      # 1. 幂等去重：sn + rework_task_id（INV-07）
      # 2. 查询 WipUnit：
      #    a. 已建档 + AT_REWORK -> markReentered(reentry_point, rework_task_id) -> REENTERED
      #       -> WipPositionChanged(to_station=reentry_point)，追加 WipHistoryEntry(reason=ReworkReentered)
      #    b. 非 AT_REWORK -> 可能事件乱序（🔴），缓冲补偿或记日志告警

    onBatchReworkOrderCreated(rework_order_id, sn_list[], work_order_id):
      # 来源：返工上下文 brework.order.created BatchReworkOrderCreated
      # 1. 逐 SN 处理：幂等去重 sn + rework_order_id
      # 2. 每个 SN：已建档 + IN_FLOW -> markAtRework(BatchRework, rework_order_id) -> AT_REWORK
      #    -> WipPositionChanged(to_station=REWORK_AREA)，追加 WipHistoryEntry(reason=BatchReworkCreated)

    onBatchReworkReentered(rework_order_id, sn_list[], reentry_point, route_version):
      # 来源：过点执行上下文 mes.reentry.reworked BatchReworkReentered
      # 1. 逐 SN 处理：幂等去重 sn + rework_order_id
      # 2. 每个 SN：已建档 + AT_REWORK -> markReentered(reentry_point, rework_order_id) -> REENTERED
      #    -> WipPositionChanged(to_station=reentry_point)，追加 WipHistoryEntry(reason=BatchReworkReentered)

    onUnitScrappedAfterRework(sn, task_id, work_order_id):
      # 来源：返修上下文 rework.task.scrapped UnitScrappedAfterRework
      # 1. 幂等去重：sn + task_id
      # 2. 查询 WipUnit：已建档 + AT_REWORK -> markScrapped(task_id) -> SCRAPPED（INV-11）
      #    -> WipPositionChanged(to_station=SCRAP_AREA)，追加 WipHistoryEntry(reason=Scrapped)

    onBatchReworkOrderScrapped(rework_order_id, sn_list[], work_order_id):
      # 来源：返工上下文 brework.order.scrapped BatchReworkOrderScrapped
      # 1. 逐 SN 处理：幂等去重 sn + rework_order_id
      # 2. 每个 SN：已建档 + AT_REWORK -> markScrapped(rework_order_id) -> SCRAPPED（INV-11）
      #    -> WipPositionChanged(to_station=SCRAP_AREA)，追加 WipHistoryEntry(reason=Scrapped)

    onProcessRouteActivated(route_version_id, route_id, version_no, product_id):
      # 来源：工艺管理上下文 process.* ProcessRouteActivated
      # 1. 刷新本上下文持有的 route_version 只读引用缓存
      # 2. 不影响已建档 WipUnit（其 route_version 在建档时锁定）
```

> **为什么不放在聚合根内**：`WipProjectionService` 需消费多个上下文外事件（`mes.*` / `rework.*` / `brework.*` / `process.*`），按事件类型路由到不同 `WipUnit` 行为——单条 `WipUnit` 聚合无权自我驱动事件消费或查询其它 SN 实例。幂等去重（BIZ-01）是跨实例不变式，需查询事件去重表。事件乱序处理（🔴）需跨实例缓冲与补偿。首次建档判据需查询 `(sn, work_order_id)` 是否已存在。归本服务 + 事件去重表保证。

> **本上下文直接消费返修/返工报废与创建事件**：返修/返工的**创建与报废事件**（`rework.task.scrapped` / `brework.order.created` / `brework.order.scrapped`）由本上下文直接消费，用于 WIP 离线标记与报废状态标记。但**再入事件**不直接消费——返修/返工的再入通过**过点执行上下文**统一处理（`UnitReworkReentered` / `BatchReworkReentered`）后发布 `mes.reentry.reworked`，本上下文只消费过点执行的事件。这保证"再入点校验"的权威归过点执行上下文。

> 🔴 **热点：事件乱序处理**——`UnitRoutedToRework` 与 `UnitReworkReentered` 可能因事件投递延迟导致乱序。建议：本上下文维护事件序号或过点时间戳，乱序到达的事件暂存缓冲，按序号重放；若缓冲超时仍乱序，按"以最新状态为准"策略接受并记日志告警。待与平台运维确认事件投递有序性保证。

> 🔴 **热点：CheckpointBlocked 是否消费**——过点执行上下文已发布 `CheckpointReleased`/`CheckpointBlocked` 到 `mes.checkpoint.lifecycle`。建议**消费**（车间可视化需区分拦截状态），但作为**辅助投影**，位置权威仍以 `RoutingProgressed` 为准。待与车间可视化团队确认。

> 🔴 **热点：返工批量再入的 SN 集合来源**——`BatchReworkReentered` 是否携带受影响 SN 列表？建议：`BatchReworkReentered` 事件载荷**携带 SN 列表**（或至少 `rework_order_id` + 批量标识），本上下文按 SN 维度逐个处理。待与返工上下文确认事件载荷。

### 3.2 KitStatusService（齐套状态服务）

**职责**：消费物料上下文事件重算 `KitStatus`；幂等去重（`work_order_id + source_event_id` 去重表 BIZ-02）；新旧状态比较（无变化不发布 BIZ-02）；处理双向可逆（INV-08）。

```yaml
KitStatusService:
  方法:
    onMaterialEvent(work_order_id, items[], source_event_id):
      # 来源：物料上下文 material.* 物料齐套相关事件（🔴 主题待对齐）
      # 1. 幂等去重：work_order_id + source_event_id 去重表（BIZ-02）
      # 2. 加载或新建 KitStatus(work_order_id)
      # 3. recompute(items[], source_event_id)：
      #    a. 按 items[] 判定 kit_ready（全部齐套 -> true，否则 -> false）
      #    b. 计算 missing_items[]（shortage_qty > 0 的项）
      #    c. 比较新旧状态：
      #       - 无变化 -> 不发布，不更新（幂等 BIZ-02）
      #       - 有变化 -> 更新聚合 -> KitStatusChanged（发布到 wip.kit.status）
      # 4. KitStatus 双向可逆（INV-08）：kit_ready 可从 true -> false（缺料/替代料失效）
```

> **为什么不放在聚合根内**：`KitStatusService` 需消费物料上下文事件（跨上下文），按 `work_order_id + source_event_id` 做幂等去重——单条 `KitStatus` 聚合无权查询去重表或自我驱动事件消费。齐套重算需综合 BOM + 库存 + 替代料（物料上下文职责），本服务编排"接收物料事件 -> 判定 -> 发布"的完整链路，聚合根只负责 `recompute()` 的内部判定逻辑。

> 🔴 **热点：物料上下文事件契约**——物料上下文（制造资源服务）的事件风暴尚未编写，其主题前缀（建议 `material.*`）与事件命名待落地后对齐。本上下文消费的"物料齐套相关事件"具体包括：BOM 生效、库存变更、替代料生效/失效等。当前全部以 🔴 标注。

> 🔴 **热点：齐套判定所需物料数据范围**——齐套判定需要哪些物料事件？建议至少订阅：BOM 生效（`material.bom.activated`）、库存变更（`material.inventory.changed`）、替代料生效/失效（`material.substitute.*`）。是否需要"齐套预占"（派工时锁库存）由物料上下文决定，本上下文仅消费其发布的齐套相关事件。待物料上下文落地后对齐。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文是读模型/投影子域，无 REST 写操作入口——所有写操作由事件消费驱动，查询操作由读模型直接服务。

### 4.1 WipEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.5 消费策略逐条迁入）。本上下文**只消费**上下文外事件以驱动位置投影、状态转移与齐套重算，**不重发**这些事件——必须包装成本上下文语义的事件（INV-CX-02）。

```yaml
WipEventConsumeAppService:
  订阅主题与处理:
    # 过点执行上下文（主题前缀 mes.*）
    mes.routing.progress (RoutingProgressed):
      -> WipProjectionService.onRoutingProgressed
      # 幂等：sn + source_event_id 去重表（BIZ-01）
      # 首次建档 INV-01 / 位置投影 INV-CX-01 / 完成标记 INV-05
    mes.checkpoint.lifecycle (CheckpointBlocked):
      -> WipProjectionService.onCheckpointBlocked
      # 幂等：sn + checkpoint_record_id
      # 辅助投影：标记 held_at_station=true（不改 status）
    mes.checkpoint.lifecycle (CheckpointReleased):
      -> WipProjectionService.onCheckpointReleased
      # 幂等：sn + checkpoint_record_id
      # 辅助投影：兜底位置更新（🔴 可选）
    mes.unit.routed-to-rework (UnitRoutedToRework):
      -> WipProjectionService.onUnitRoutedToRework
      # 幂等：sn + routed_event_id（INV-06）
    mes.reentry.reworked (UnitReworkReentered):
      -> WipProjectionService.onUnitReworkReentered
      # 幂等：sn + rework_task_id（INV-07）
    mes.reentry.reworked (BatchReworkReentered):
      -> WipProjectionService.onBatchReworkReentered
      # 幂等：sn + rework_order_id（INV-07）

    # 返工上下文（主题前缀 brework.*）
    brework.order.created (BatchReworkOrderCreated):
      -> WipProjectionService.onBatchReworkOrderCreated
      # 幂等：sn + rework_order_id
    brework.order.scrapped (BatchReworkOrderScrapped):
      -> WipProjectionService.onBatchReworkOrderScrapped
      # 幂等：sn + rework_order_id（INV-11）

    # 返修上下文（主题前缀 rework.*）
    rework.task.scrapped (UnitScrappedAfterRework):
      -> WipProjectionService.onUnitScrappedAfterRework
      # 幂等：sn + task_id（INV-11）

    # 物料上下文（主题前缀待对齐，🔴）
    material.* (物料齐套相关事件):
      -> KitStatusService.onMaterialEvent
      # 幂等：work_order_id + source_event_id（BIZ-02）

    # 工艺管理上下文（主题前缀待对齐，🔴）
    process.* (ProcessRouteActivated):
      -> WipProjectionService.onProcessRouteActivated
      # 幂等：route_id + route_version
      # 仅刷新 route_version 只读引用缓存，不影响已建档 WipUnit
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 消费 RoutingProgressed | 单聚合事务 | `WipProjectionService` | `WipUnitRegistered`(首次) / `WipPositionChanged` | `sn + source_event_id`（BIZ-01） |
| 消费 CheckpointBlocked | 单聚合事务 | `WipProjectionService` | 无（仅位置标记） | `sn + checkpoint_record_id` |
| 消费 UnitRoutedToRework | 单聚合事务 | `WipProjectionService` | `WipPositionChanged` | `sn + routed_event_id`（INV-06） |
| 消费 UnitReworkReentered / BatchReworkReentered | 单聚合事务 | `WipProjectionService` | `WipPositionChanged` | `sn + rework_task_id` / `sn + rework_order_id`（INV-07） |
| 消费 BatchReworkOrderCreated | 单聚合事务（逐 SN） | `WipProjectionService` | `WipPositionChanged`（每个 SN） | `sn + rework_order_id` |
| 消费 rework.task.scrapped / brework.order.scrapped | 单聚合事务（逐 SN） | `WipProjectionService` | `WipPositionChanged`（每个 SN） | `sn + task_id` / `sn + rework_order_id`（INV-11） |
| 消费物料齐套事件 | 单聚合事务 | `KitStatusService` | `KitStatusChanged`（有变化时） | `work_order_id + source_event_id`（BIZ-02） |
| 消费 ProcessRouteActivated | 单聚合事务 | `WipProjectionService` | 无（仅刷新缓存） | `route_id + route_version` |

> **上下文外事件只消费不重发**（INV-CX-02）：本上下文将订阅事件包装为 `WipUnitRegistered` / `WipPositionChanged` / `KitStatusChanged` 等本上下文语义事件后发布，下游可凭主题前缀区分来源。主题前缀隔离：本上下文只发 `wip.*`，订阅 `mes.*` / `rework.*` / `brework.*` / 物料上下文 / 工艺管理上下文。

> **降级查询不算"消费事件"**：本上下文若需展示 `missing_items` 详情，可能 REST 查询物料上下文获取实时库存——这是同步降级路径，不在事件消费范畴，但需保证不引入分布式事务（领域总览 §5.3）。

### 4.3 WipSnapshotPublishAppService（快照发布应用服务）

**职责**：周期性/事件触发发布 `WipLocationSnapshot` 读模型，供车间可视化与过点执行派工查询。

```yaml
WipSnapshotPublishAppService:
  方法:
    publishSnapshotOnPositionChanged(work_order_id, sn):
      # 事件触发：单件位置变更后
      # 若该工单在制品数 ≤ 阈值（如 50）-> 即时发布增量快照（仅变更的 SN）
      # 若超阈值 -> 仅周期发布，避免风暴

    publishPeriodicSnapshot():
      # 周期性触发（默认每 30s，可配置）
      # 全量快照：按 work_order_id 分组，发布 WipLocationSnapshot
      # 发布到 wip.location.snapshot
```

> 🔴 **热点：快照发布的频率与风暴风险**——大工单（数千板）的位置变更事件高频，若每条都发快照会造成消息风暴。建议**增量快照 + 周期全量**结合：位置变更发增量（仅变更的 SN），周期发全量对账。待与车间可视化团队确认消费能力。

> 🔴 **热点：快照与位置投影的一致性**——`WipLocationSnapshot` 是 `WipUnit.position` 的二次投影，存在双重延迟（事件 -> WipUnit -> Snapshot）。建议快照**直接从 `WipUnit` 聚合读取当前值**生成，不引入额外事件链，保证快照与 `WipUnit` 在同一读模型层。

## 5. 领域事件

### 5.1 在制品身份与位置事件

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 在制品追踪上下文](../事件风暴/在制品追踪上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 WipUnit（在制品·单件）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-01 | 同一 `(sn, work_order_id)` 全局唯一建档 | `WipUnit.register` 前置；以 `(sn, work_order_id)` 是否已存在为建档判据，`from_step=null` 仅作辅助信号 |
| INV-02 | `WipHistoryEntry` 只增不可改不可删，按 `timestamp` 单调递增 | `WipUnit.history[]` 集合；`(from_station, to_station)` 必须与触发它的来源事件载荷一致 |
| INV-05 | `COMPLETED` 为终态，之后任何位置变更均拒收 | `WipUnit` 状态机；`markCompleted` 后拒收任何 `updatePosition`/`markAtRework`/`markReentered`/`markScrapped` |
| INV-06 | 分流离线标记需 SN 处于 `IN_FLOW` | `WipUnit.markAtRework` 前置；`WipProjectionService` 状态校验 + 事件去重表；若 SN 未建档或非 IN_FLOW，记日志不强行变更 |
| INV-07 | 再入需 SN 处于 `AT_REWORK` | `WipUnit.markReentered` 前置；`WipProjectionService` 状态校验 + `rework_task_id`/`rework_order_id` 去重；乱序事件走缓冲补偿（🔴） |
| INV-11 | `SCRAPPED` 为终态，之后任何位置变更均拒收 | `WipUnit` 状态机；`markScrapped` 后拒收任何位置变更；`WipProjectionService` 状态校验 + `rework.task.scrapped`/`brework.order.scrapped` 去重 |
| INV-13 | 投影幂等重放可重建——`WipUnit` 位置/状态/历史可从 `mes.routing.progress` 事件流完全重放重建，不依赖本地状态 | 投影型聚合的本质属性；`source_event_id` 去重表 + `WipHistoryEntry` 不可变追加保证 |

#### 6.1.2 KitStatus（工单齐套状态）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-08 | `kit_ready=true` 当且仅当 `missing_items` 为空；双向可逆——可从 `true` 回到 `false` | `KitStatus.recompute` 行为内判定；齐套后若物料上下文报告缺料/替代料失效，`kit_ready` 可逆 |

### 6.2 业务不变式（Business Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| BIZ-01 | WipUnit | 投影幂等——相同 `source_event_id` 不重复变更位置/追加历史 | 跨实例，由 `WipProjectionService` + `sn + source_event_id` 事件去重表保证（**禁止挂聚合根**） |
| BIZ-02 | KitStatus | 重算幂等——相同 `(work_order_id, source_event_id)` 不重复发布 `KitStatusChanged`；无状态变化时不发布 | 跨实例，由 `KitStatusService` + `(work_order_id, source_event_id)` 去重表 + 新旧状态比较保证（**禁止挂聚合根**） |
| BIZ-03 | -（基础设施，各事件消费聚合） | 上下文外事件消费幂等——`consumed_event` 表 + 业务键去重（BIZ-01/INV-06/INV-07/BIZ-02/INV-11 的通用机制） | 由 `consumed_event` 表保证（**禁止挂聚合根**） |
| BIZ-04 | -（基础设施，WipLocationSnapshot 读模型） | 快照一致性——`WipLocationSnapshot` 直接从 `WipUnit` 聚合当前值生成，不引入额外事件链 | 由 `WipSnapshotPublishAppService` 读取 `WipUnit` 聚合当前值；快照与 `WipUnit` 在同一读模型层（**禁止挂聚合根**） |

### 6.3 跨上下文不变式（Cross-Context Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| INV-CX-01 | WipUnit（本），过点执行上下文 | `WipUnit.position` 最终一致，必须与最近一次 `mes.routing.progress` 一致；可从事件流重放重建 | 由 `WipProjectionService` 投影幂等 + 事件去重表保证；任意时刻 `WipUnit.position` = 该 SN 最后一条历史的 `to_station`；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-02 | WipUnit, KitStatus（本），过点执行/返修/返工/物料/工艺管理上下文 | 上下文外事件只消费不重发——本上下文将订阅事件包装为本上下文语义事件后发布，下游凭主题前缀区分来源 | 由 `WipEventConsumeAppService` 包装发布；主题前缀 `wip.*` vs `mes.*`/`rework.*`/`brework.*`/`material.*`/`process.*`；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-03 | WipUnit（本），过点执行上下文 | 位置投影与过点执行经异步事件解耦——本上下文不调用过点执行上下文的"过点"接口，过点执行上下文不调用本上下文的"更新位置"接口 | 位置投影由事件驱动，不引入分布式事务（领域总览 §5.3）；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |

```

│                    事件 -> 委托领域服务                                 │

│                                                                      │

                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  WipProjectionService │ KitStatusService                              │
│  └─ 封装跨聚合/跨上下文规则，加载聚合，调用聚合行为，写仓储，返回领域事件  │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  WipUnit / KitStatus                                                  │

└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 位置投影与过点执行经异步事件解耦，不在过点主事务中引入分布式事务（领域总览 §5.3）
