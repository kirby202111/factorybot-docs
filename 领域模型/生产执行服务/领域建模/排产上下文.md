# 排产上下文 - 领域建模（Scheduling Domain Model）

> **限界上下文**：排产上下文
> **统一语言**：LineSchedule（产线排产·按产线聚合的槽位集合）, ScheduleSlot（排产槽位·工单+起止时间+状态）, SlotStatus（槽位状态·PENDING 建议 / CONFIRMED 已确认 / RELEASED 已释放）, SchedulingSuggestion（排产建议·半自动产出供计划员确认）, ProductionLineCapacity（产线产能日历·可用时段/班次/维护窗）, LineCapacityResolver（产线产能解析·领域辅助组件）, RescheduleTrigger（重排触发源·RushOrder / MaterialShortage / EquipmentUnavailable / WorkOrderChanged）, CriticalAssetRef（关键资产引用·停用即影响产线产能）, ScheduleSnapshotProjection（排产快照读模型·供排产员看板）
> **建模依据**：[事件风暴 - 排产上下文](../事件风暴/排产上下文.md)

---

## 0. 建模总览

本域是生产执行服务下的**工单级排产子域**，是 PCBA + 整机组装混合型车间"已下达工单排到哪条线、什么时间跑、何时因 disruptions 重排"的建议与确认权威源。核心职责是管理**工单下达后排产积压维护、半自动建议生成、计划员确认落槽、事件驱动重排（缺料/设备故障/插单/工单变更）、排产快照回写工单并触发齐套预占**--即"**工单排哪条线、什么时间、何时重排**"；**不负责**工单身份与状态生命周期（归工单管理上下文，本上下文消费 `wo.order.*`）、不负责工序级时间排产与资源/设备槽位建模（当前粒度工单级）、不负责过点放行/拦截门禁（归在制品执行上下文；排产咨询性，`schedule.*` 不被在制品执行消费做硬门禁）、不负责物料主数据与库存事实源（归物料上下文，本上下文消费其缺料事件并发布 `schedule.confirmed` 触发其齐套预占）、不负责齐套状态判定（归工单管理上下文 `KitStatus`，本上下文消费 `wo.kit.status`）、不负责资产台账与可用性事实源（归设备工装台账上下文，本上下文消费其 `AssetAvailabilityChanged`）。

本上下文与工单管理上下文是"排产建议/确认"与"工单生命周期"的分工关系，通过事件契约解耦：本上下文消费 `wo.order.released/changed/cancelled/started` 维护排产积压；本上下文发布 `schedule.confirmed/rescheduled/released` 供工单管理上下文回写 MES 排产快照、供物料上下文触发齐套预占。本上下文是事件驱动重排的**跨域汇聚点**--订阅工单（插单/变更）、物料（缺料）、设备台账（故障）三类 disruptions，故独立成上下文以保住工单上下文收窄的订阅面。MES 排产快照与 SAP 建议字段在工单上并存，互不覆盖。

### 聚合划分

```
┌──────────────────────────────────────────────────────────────────────────┐
│                            排产上下文                                        │
│                                                                          │
│  ┌────────────────────────────────────────────────────────────────────┐  │

│  │  ┌──────────────────────────────────────────────────────────┐      │  │
│  │  │                  ScheduleSlot (值对象)                    │      │  │
│  │  │  work_order_id + planned_start/finish + status(PENDING/  │      │  │
│  │  │  CONFIRMED/RELEASED) + sap_hint + trigger                 │      │  │
│  │  └──────────────────────────────────────────────────────────┘      │  │

│                                                                          │
│  共享值对象：SlotStatus / ProductionLineCapacity / RescheduleTrigger      │
│            / CriticalAssetRef / LineId / WorkOrderId                     │
│  领域服务：SchedulingSuggestionService / SchedulingRescheduleService      │
│           / LineCapacityResolver（领域辅助组件）                          │
│  读模型：ScheduleSnapshotProjection / SchedulingBacklogProjection         │
└──────────────────────────────────────────────────────────────────────────┘
```

> **聚合边界说明**：事件风暴统一语言中的 `ScheduleSlot` / `SchedulingSuggestion` / `ProductionLineCapacity` **不是独立聚合根**--`ScheduleSlot` 建模为 `LineSchedule.slots[]` 的值对象集合（工单+起止+状态），`SchedulingSuggestion` 建模为 `SchedulingSuggestionService` 的产出（PENDING 槽位 + 读模型，不另起聚合），`ProductionLineCapacity` 建模为薄配置值对象（由 `LineCapacityResolver` 读取）。`LineSchedule` 按产线聚合，把"同线已确认槽位不可重叠"这一核心不变式收敛到**聚合内**事务强一致（而非跨实例 BIZ）。这样 1 个聚合根守护单一一致性边界，槽位/建议/产能日历不另起聚合，避免聚合碎片化（与工单上下文"明细/绑定/结案折叠为值对象"的哲学一致）。若后续建议生命周期（建议->确认/驳回/被插单 supersede）复杂度涌现，可将 `SchedulingSuggestion` 升格为第二个聚合。

## 1. 聚合根

### 1.1 LineSchedule（产线排产）

**一致性边界**：单条产线的槽位集合、产能日历引用、同线已确认槽位不重叠不变式。

**职责**：维护该产线的 `PENDING`/`CONFIRMED`/`RELEASED` 槽位；守护同线已确认槽位不重叠；承载计划员确认（PENDING->CONFIRMED）；承载重排（迁移/释放未开工槽位）；承载工单取消/开工的槽位释放/冻结；发布排产生命周期事件供下游消费。

```yaml
LineSchedule:
  # ─── 标识 ───
  line_id:           LineId               # 产线 ID（聚合根ID）

  # ─── 产能日历 ───
  capacity:          ProductionLineCapacity   # 产线产能日历（可用时段/班次/维护窗，🔴 薄配置起步）

  # ─── 槽位集合 ───
  slots[]:           List<ScheduleSlot>   # 槽位集合（PENDING/CONFIRMED/RELEASED）

  # ─── 审计 ───
  last_updated_at:   DateTime             # 最后变更时间
  source_event_id:   String?              # 最后一条来源事件ID（幂等去重键）
```

**行为**：
- `suggestSlot(work_order_id, planned_start_at, planned_finish_at, sap_hint, source_event_id)` -> 发出 `ScheduleSuggested`（前置：该 `work_order_id` 当前无有效 PENDING/CONFIRMED 槽位 INV-04；时段落在产能日历可用时段内 INV-03；-> 新增 `PENDING` 槽位；经 `SchedulingSuggestionService` 编排）
- `confirmSlot(work_order_id, confirmed_by, source_event_id)` -> 发出 `ScheduleConfirmed`（前置：存在该 `work_order_id` 的 `PENDING` 槽位；同线已确认槽位不与该时段重叠 INV-01；-> `PENDING` 转 `CONFIRMED`）
- `rescheduleSlot(work_order_id, new_line_id, new_start_at, new_finish_at, trigger, source_event_id)` -> 发出 `ScheduleRescheduled`（前置：该 `work_order_id` 存在 `CONFIRMED` 槽位且工单未开工 INV-05；记录 `old_*` 与 `new_*` 与 `trigger`；-> 释放原槽位 + 新增/迁移 `CONFIRMED` 槽位；若 `new_line_id ≠ 本线` 则跨 `LineSchedule` 实例，经 `SchedulingRescheduleService` 编排）
- `releaseSlot(work_order_id, reason, source_event_id)` -> 发出 `ScheduleReleased`（前置：该 `work_order_id` 存在有效槽位；-> `RELEASED`；用于工单取消或槽位被完全释放）
- `freezeSlot(work_order_id, source_event_id)` -> 内部标记槽位冻结（前置：该 `work_order_id` 存在 `CONFIRMED` 槽位；由 `wo.order.started` 触发；冻结后不再参与重排 INV-05；不发独立生命周期事件，仅状态标记）

> **核心不变式 INV-01**：同条产线已确认（`CONFIRMED`）槽位不可时间重叠。这是把"跨工单非重叠"约束收敛到**聚合内**事务强一致的关键--`confirmSlot` 在事务内校验本线所有 `CONFIRMED` 槽位与待确认时段是否重叠，重叠则拒绝。`PENDING` 建议槽位不参与不重叠校验（建议可被 supersede）。

> **建议与确认都建模为槽位状态**：`PENDING` 是系统半自动产出的建议槽位，`CONFIRMED` 是计划员确认后的有效槽位。只有 `CONFIRMED` 触发下游（回写工单快照、齐套预占）；`PENDING` 无下游效果。权威在计划员确认，不在算法。

> **跨线重排经领域服务编排**：`rescheduleSlot` 若 `new_line_id ≠ 本线`，需同时操作两个 `LineSchedule` 实例（原线释放 + 目标线新增），单聚合无权跨实例，经 `SchedulingRescheduleService` 在同事务内编排两个聚合。

> 🔴 **热点：产线产能日历权威源**--`capacity` 当前由本上下文薄配置字典维护（`LineCapacityResolver` 读取），复刻工单上下文 `ProductSerialPrefixResolver` 先例。预留迁移到"工厂建模上下文"（设备工装台账上下文已引用该域但未建）；迁移时 `LineCapacityResolver` 改为 REST 查询，`LineSchedule` 聚合不变。

## 2. 值对象

### 2.1 LineId / WorkOrderId（标识）

```yaml
LineId:        { value: String }    # 产线唯一标识
WorkOrderId:   { value: String }    # 工单标识（引用工单管理上下文，经 ACL 翻译）
```

> 不可变。`LineId` 是本上下文聚合根标识。`WorkOrderId` 是上下文外引用，经防腐层（ACL）从工单管理上下文翻译为本上下文语义，本上下文不持有工单聚合。

### 2.2 ScheduleSlot（排产槽位）

```yaml
ScheduleSlot:
  work_order_id:      WorkOrderId        # 工单 ID（引用工单管理上下文）
  planned_start_at:   DateTime           # 计划开工时间（MES 排产）
  planned_finish_at:  DateTime           # 计划完工时间（MES 排产）
  status:             SlotStatus         # PENDING / CONFIRMED / RELEASED
  sap_hint:           SapHint?           # SAP 建议产线/时间（参考提示）
  trigger:            RescheduleTrigger? # 重排触发源（重排时记录）
  confirmed_by:       String?            # 确认人（CONFIRMED 时填充）
  confirmed_at:       DateTime?          # 确认时间
  frozen:             Boolean            # 是否已冻结（工单开工后）
```

> 隶属于 `LineSchedule.slots[]` 的值对象集合。`PENDING` 是建议槽位，`CONFIRMED` 是计划员确认后的有效槽位（参与不重叠校验 INV-01），`RELEASED` 是已释放（工单取消/重排迁移）。`frozen` 标记工单开工后的冻结状态，冻结槽位不再参与重排（INV-05）。`sap_hint` 保留 SAP 建议产线/时间供建议生成参考与看板对照。

### 2.3 SapHint（SAP 建议提示）

```yaml
SapHint:
  production_line_id:  String?    # SAP 建议产线（参考）
  planned_start_at:    DateTime?  # SAP 建议开工时间（参考）
  planned_finish_at:   DateTime?  # SAP 建议完工时间（参考）
```

> 不可变。来自工单管理上下文 `wo.order.released` 载荷。仅作建议生成参考与看板对照，MES 排产不回写 SAP 字段（MES 排产快照与 SAP 建议并存，互不覆盖）。

### 2.4 SlotStatus（槽位状态）

```yaml
SlotStatus:
  - PENDING     # 建议（系统半自动产出，待计划员确认，无下游效果）
  - CONFIRMED   # 已确认（计划员确认，触发回写快照+齐套预占，参与不重叠校验）
  - RELEASED    # 已释放（工单取消或重排迁移）
```

**状态机**：

```
[建议生成] ──GenerateSchedulingSuggestion──▶ [PENDING] ──ConfirmSchedule──▶ [CONFIRMED] ──ReleaseSlot──▶ [RELEASED]
                                                   │                                    │
                                                   └──RejectSchedule──▶ [RELEASED]      └──RescheduleSlot──▶ (迁移至新槽位，原槽 RELEASED)
                                                          (建议驳回)

[CONFIRMED] ──FreezeSlot(wo.order.started)──▶ [CONFIRMED + frozen=true]（冻结，不再重排 INV-05）
```

**不变式**：
- `-> PENDING`：`suggestSlot()`，前置该工单无有效槽位（INV-04）
- `PENDING -> CONFIRMED`：`confirmSlot()`，前置同线已确认槽位不重叠（INV-01）
- `PENDING -> RELEASED`：建议驳回（`releaseSlot`）
- `CONFIRMED -> RELEASED`：工单取消（`releaseSlot`）或重排迁移（`rescheduleSlot` 原槽释放）
- `CONFIRMED -> CONFIRMED(frozen)`：工单首次过点（`freezeSlot`），冻结后不再重排（INV-05）
- 状态单向流转，`RELEASED` 为终态（INV-02）
- 仅 `CONFIRMED` 槽位参与同线不重叠校验；`PENDING` 不参与

### 2.5 ProductionLineCapacity（产线产能日历）

```yaml
ProductionLineCapacity:
  line_id:            LineId              # 产线 ID
  available_windows[]: List<TimeWindow>   # 可用时段（班次/工作时段）
  maintenance_windows[]: List<TimeWindow> # 维护窗（不可排产）
  product_compatibility[]: List<ProductLineFit>  # 产品-产线适用性
```

```yaml
TimeWindow:
  start_at:  DateTime    # 时段开始
  end_at:    DateTime    # 时段结束

ProductLineFit:
  product_id:  String    # 产品 ID
  feasible:    Boolean   # 该产线是否支持该产品/工艺
```

> 不可变配置值对象。由 `LineCapacityResolver` 读取解析。槽位的计划起止时间必须落在 `available_windows` 内且不与 `maintenance_windows` 重叠（INV-03）。当前由本上下文薄配置字典维护（🔴 权威源待迁移到"工厂建模上下文"）。

### 2.6 RescheduleTrigger（重排触发源）

```yaml
RescheduleTrigger:
  - RushOrder              # 急单插单（wo.order.released 含急单类型）
  - MaterialShortage       # 缺料（material.kit.reservation-failed / wo.kit.status kit_ready=false）
  - EquipmentUnavailable   # 设备故障（eam.asset.availability available=false）
  - WorkOrderChanged       # 工单变更（wo.order.changed 数量/建议变更）
```

> 不可变枚举。重排时记录于 `ScheduleSlot.trigger` 与 `ScheduleRescheduled` 事件载荷，供追溯与看板区分重排原因。

### 2.7 CriticalAssetRef（关键资产引用）

```yaml
CriticalAssetRef:
  asset_id:  String    # 资产 ID（引用设备工装台账上下文）
  line_id:   LineId    # 所属产线（该资产停用即影响此线产能）
```

> 不可变配置值对象。维护"产线关键资产"映射--哪些资产停用即影响哪条线产能。当前由本上下文薄配置字典维护（🔴）。台账发布资产级 `AssetAvailabilityChanged`，本上下文据此配置映射到产线级产能影响。

### 2.8 ScheduleSnapshotProjection（排产快照读模型）

```yaml
ScheduleSnapshotProjection:
  work_order_id:        WorkOrderId
  line_id:              LineId?
  planned_start_at:     DateTime?
  planned_finish_at:    DateTime?
  status:               SlotStatus        # PENDING/CONFIRMED/RELEASED
  sap_hint:             SapHint?
  trigger:              RescheduleTrigger?
  last_event_ts:        DateTime
```

> 读模型投影，供排产员工作台与数据应用看板。由 `schedule.*` 事件到达时刷新，不进入 `LineSchedule` 聚合。以 `work_order_id` 唯一（同一工单同一时刻一个有效槽位 INV-04）。

### 2.9 SchedulingBacklogProjection（待排积压读模型）

```yaml
SchedulingBacklogProjection:
  work_order_id:        WorkOrderId
  target_qty:           Integer           # 目标数量（来自 wo.order.released）
  work_order_type:      String            # 工单类型（急单优先级判定）
  sap_hint:             SapHint?
  received_at:          DateTime          # 入积压时间
  suggested:            Boolean           # 是否已生成建议
```

> 读模型投影，供 `SchedulingSuggestionService` 读取待排工单积压。由 `wo.order.released` 累积，`wo.order.cancelled` 移除。`suggested=false` 的工单为待生成建议。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 SchedulingSuggestionService（排产建议生成服务）

**职责**：读取待排工单积压与各线已确认槽位，按产线产能日历与排产规则半自动产出 `PENDING` 建议槽位。

```yaml
SchedulingSuggestionService:
  方法:
    generateSuggestion(work_order_id, target_qty, work_order_type, sap_hint, source_event_id):
      # 来源：工单管理上下文 wo.order.released（经 SchedulingEventConsumeAppService 触发）
      # 1. 幂等去重：work_order_id + source_event_id 去重表（BIZ-01）
      # 2. 解析产线产能日历：LineCapacityResolver.resolve() -> 各线 ProductionLineCapacity
      # 3. 读各线已确认槽位（避免冲突）+ 产品-产线适用性过滤
      # 4. 按排产规则选定 line_id + planned_start/finish：
      #    - 急单优先（work_order_type=RUSH）
      #    - SAP 建议时间/产线作为提示（sap_hint）
      #    - 目标数量影响占用时长
      #    - 产线适用性（product_compatibility）
      #    - 换线偏好（同产品连续排）
      # 5. 校验时段落在产能日历可用时段内（INV-03）
      # 6. LineSchedule.suggestSlot(...) -> ScheduleSuggested（PENDING 槽位）
      # 7. Outbox 发布到 schedule.suggested
```

> **为什么不放在聚合根内**：建议生成需跨实例读取待排工单积压（`SchedulingBacklogProjection`）、各线已确认槽位（多个 `LineSchedule` 实例）、产线产能日历（配置）--单条 `LineSchedule` 聚合无权跨实例查询或跨线决策。排产规则（急单优先/换线偏好等）是跨聚合编排逻辑，归本服务。

> **排产规则权重为实现细节**：半自动建议的规则权重（急单 vs SAP 提示 vs 换线）不在领域建模定型，由实现层配置。本服务只保证产出合法 `PENDING` 槽位（时段可用、产线适用）。

> 🔴 **热点：产线产能日历权威源**--`LineCapacityResolver` 当前读本上下文薄配置字典；待"工厂建模上下文"落地后改为 REST 查询，本服务签名不变。

### 3.2 SchedulingRescheduleService（事件驱动重排服务）

**职责**：消费缺料/设备故障/插单/工单变更事件，重排受影响**未开工**槽位；跨线重排时同事务编排两个 `LineSchedule` 实例。

```yaml
SchedulingRescheduleService:
  方法:
    onKitReservationFailed(work_order_id, missing_items[], source_event_id):
      # 来源：物料上下文 material.kit.reservation-failed
      # 1. 幂等去重：work_order_id + source_event_id 去重表（BIZ-01）
      # 2. 加载该工单 CONFIRMED 槽位；若已冻结（工单开工）-> 忽略（INV-05）
      # 3. trigger=MaterialShortage；按缺料预计齐套时间（🔴 expected_ready_at）重排至更晚槽位
      # 4. 跨线或同线 rescheduleSlot(...) -> ScheduleRescheduled（old_*/new_*/trigger）

    onKitStatusChanged(work_order_id, kit_ready, source_event_id):
      # 来源：工单管理上下文 wo.kit.status
      # 1. 幂等去重：work_order_id + source_event_id
      # 2. 若 kit_ready=false 且该工单有 CONFIRMED 未开工槽位 -> trigger=MaterialShortage 重排
      # 3. 若 kit_ready=true -> 可重新接纳（生成新建议）

    onAssetAvailabilityChanged(asset_id, available, source_event_id):
      # 来源：设备工装台账上下文 eam.asset.availability
      # 1. 幂等去重：asset_id + source_event_id
      # 2. 查 CriticalAssetRef 配置：asset_id -> line_id 映射（🔴）
      # 3. 若 available=false（关键资产停用）：
      #    - 加载该线所有未开工 CONFIRMED 槽位
      #    - trigger=EquipmentUnavailable；降级为 PENDING 或迁移至他线 -> ScheduleRescheduled/ScheduleReleased
      # 4. 若 available=true（产能恢复）：
      #    - 重新生成该线被迁移走工单的建议 -> GenerateSchedulingSuggestion

    onWorkOrderChanged(work_order_id, changed_fields, source_event_id):
      # 来源：工单管理上下文 wo.order.changed
      # 1. 幂等去重：work_order_id + source_event_id
      # 2. 若 target_qty 变更 -> 影响占用时长，trigger=WorkOrderChanged 重排
      # 3. 若工单已开工 -> 忽略（INV-05）

    onRushOrderInserted(work_order_id, work_order_type, source_event_id):
      # 来源：工单管理上下文 wo.order.released（work_order_type=RUSH）
      # 1. 急单优先占槽；trigger=RushOrder
      # 2. 被挤占的未开工 CONFIRMED 槽位往后顺延或迁移他线 -> ScheduleRescheduled
```

> **为什么不放在聚合根内**：重排需消费多个上下文外事件、跨实例查询受影响槽位（多条 `LineSchedule`）、跨线重排需同事务编排两个聚合、查询 `CriticalAssetRef` 配置映射--单条 `LineSchedule` 聚合无权跨实例或跨线。归本服务 + 事件去重表保证。

> **只重排未开工部分**：所有重排方法均校验槽位未冻结（工单未开工，INV-05）。已开工工单的槽位冻结，不参与重排，保证在制工单执行口径不漂移。

> 🔴 **热点：缺料预计齐套时间**--`onKitReservationFailed` 需预计缺料何时齐套以确定重排目标时间。`material.kit.reservation-failed` 当前不携带 `expected_ready_at`。待与物料上下文确认载荷扩展。

> 🔴 **热点：产能受损到产线的映射**--`onAssetAvailabilityChanged` 需 `asset_id -> line_id` 映射（`CriticalAssetRef` 配置）。当前薄配置起步；待与设备工装台账上下文确认是否提供产线级可用性汇总事件。

### 3.3 LineCapacityResolver（产线产能解析·领域辅助组件）

**职责**：读取产线产能日历配置，解析为 `ProductionLineCapacity` 供建议生成与槽位校验。

```yaml
LineCapacityResolver:
  方法:
    resolve(line_id):
      # 1. 读取产线产能日历配置（当前：本上下文薄配置字典；🔴 未来：REST 查询工厂建模上下文）
```

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与工单/物料/在制品/设备台账上下文经**异步事件解耦**（消费 `wo.*`/`material.*`/`eam.*`，发布 `schedule.*`），不在他上下文主事务中引入分布式事务。

### 4.1 SchedulingCommandAppService（排产命令应用服务）

**职责**：处理计划员确认/驳回/手动重排的写操作命令（REST/终端入口，发命令者：计划员/排产员）。

```yaml
SchedulingCommandAppService:
  方法:
    # ─── 确认/驳回建议 ───
    confirmSchedule(work_order_id, confirmed_by):
      # 加载含该工单 PENDING 槽位的 LineSchedule
      # -> LineSchedule.confirmSlot(work_order_id, confirmed_by, source_event_id)
      #    -> ScheduleConfirmed -> schedule.confirmed
      # 同事务 Outbox 发布

    rejectSchedule(work_order_id, reject_reason):
      # -> LineSchedule.releaseSlot(work_order_id, reason=SuggestionRejected)
      #    -> ScheduleReleased -> schedule.released
      #    （建议驳回，无下游预占效果，因 PENDING 本就无预占）

    # ─── 手动重排 ───
    manualReschedule(work_order_id, new_line_id, new_start_at, new_finish_at, reason):
      # -> SchedulingRescheduleService 跨线编排（同事务两个 LineSchedule）
      #    -> ScheduleRescheduled -> schedule.rescheduled
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 确认建议 | 单聚合事务 | `LineSchedule.confirmSlot` | `ScheduleConfirmed` | `commandId`；`work_order_id` |
| 驳回建议 | 单聚合事务 | `LineSchedule.releaseSlot` | `ScheduleReleased`（reason=SuggestionRejected） | `commandId` |
| 手动重排 | 双聚合事务（跨线） | `SchedulingRescheduleService` | `ScheduleRescheduled` | `commandId` |

> **确认用例的事务边界**：单聚合事务（`LineSchedule` 状态变更 + Outbox）。`confirmSlot` 在事务内校验同线已确认槽位不重叠（INV-01），重叠则拒绝，不产生半确认状态。

### 4.2 SchedulingEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理。

```yaml
SchedulingEventConsumeAppService:
  订阅主题与处理:
    # 工单管理上下文（主题前缀 wo.*）
    wo.order.released (WorkOrderReleased):
      -> SchedulingSuggestionService.generateSuggestion（急单走 onRushOrderInserted 分支）
      # 幂等：work_order_id + source_event_id 去重表（BIZ-01）
    wo.order.changed (WorkOrderChanged):
      -> SchedulingRescheduleService.onWorkOrderChanged
      # 幂等：work_order_id + source_event_id
    wo.order.cancelled (WorkOrderCancelled):
      -> LineSchedule.releaseSlot(reason=WorkOrderCancelled) -> ScheduleReleased
      # 幂等：work_order_id
    wo.order.started (WorkOrderStarted):
      -> LineSchedule.freezeSlot -> 冻结，停止重排（INV-05）
      # 幂等：work_order_id

    # 物料上下文（主题前缀 material.*）
    material.kit.reservation-failed (KitReservationFailed):
      -> SchedulingRescheduleService.onKitReservationFailed
      # 幂等：work_order_id + source_event_id（BIZ-01）

    # 工单管理上下文（主题前缀 wo.*，齐套状态）
    wo.kit.status (KitStatusChanged):
      -> SchedulingRescheduleService.onKitStatusChanged
      # 幂等：work_order_id + source_event_id

    # 设备工装台账上下文（主题前缀 eam.*）
    eam.asset.availability (AssetAvailabilityChanged):
      -> SchedulingRescheduleService.onAssetAvailabilityChanged
      # 幂等：asset_id + source_event_id
```

> **不直接消费上下文外事件来做状态变更**（INV-CX-04）：本上下文将订阅事件包装为本上下文语义事件（`ScheduleSuggested`/`ScheduleConfirmed`/`ScheduleRescheduled`/`ScheduleReleased`）后发布，下游凭主题前缀 `schedule.*` 区分来源。

> **主题命名约定**：本上下文**对外发布**使用 `schedule.*` 前缀（与 `wo.*`/`wip.*`/`brework.*`/`rework.*` 严格区分）。本上下文**订阅**使用各发布限界上下文自己的前缀，不重写--`wo.*`（工单管理）、`material.*`（物料）、`eam.*`（设备工装台账）。

### 4.3 SchedulingQueryAppService（查询应用服务）

**职责**：提供读模型查询，支撑排产员工作台、排产看板、下游消费方降级查询。

```yaml
SchedulingQueryAppService:
  方法:
    getScheduleSnapshot(work_order_id):               ScheduleSnapshotProjection
    listPendingSuggestions(line_id?):                 List<ScheduleSnapshotProjection>  # PENDING 待确认
    listConfirmedByLine(line_id):                     List<ScheduleSnapshotProjection>  # 该线已确认槽位（甘特）
    getLineGantt(line_id, from, to):                  List<ScheduleSnapshotProjection>  # 产线甘特视图
    getSchedulingBacklog():                           List<SchedulingBacklogProjection> # 待排积压
    listReschedulesByTrigger(trigger):                List<ScheduleSnapshotProjection>  # 按重排触发源追溯
```

> 读模型围绕排产快照（排产员工作台/看板）、待排积压（建议生成）、重排追溯组织投影，不反向污染写模型聚合。

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 排产上下文](../事件风暴/排产上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 LineSchedule（产线排产）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-01 | 同条产线已确认（`CONFIRMED`）槽位不可时间重叠 | `LineSchedule.confirmSlot` 前置；事务内校验本线所有 `CONFIRMED` 槽位与待确认时段不重叠，重叠则拒绝。`PENDING` 建议槽位不参与此校验 |
| INV-02 | 槽位状态单向流转 `PENDING -> CONFIRMED -> RELEASED`，`RELEASED` 为终态 | `SlotStatus` 状态机；`RELEASED` 之后任何变更均拒收 |
| INV-03 | 槽位计划起止时间必须落在产线产能日历可用时段内，且不与维护窗重叠 | `LineSchedule.suggestSlot`/`confirmSlot` 前置；`LineCapacityResolver` 解析 `ProductionLineCapacity` 校验 |
| INV-04 | 同一工单同一时刻只有一个有效槽位（`PENDING` 或 `CONFIRMED`），跨 `LineSchedule` 实例 | `suggestSlot` 前置该工单无有效槽位；跨实例唯一性由 BIZ-02 保证 |
| INV-05 | 已开工工单的槽位冻结，不再参与重排 | `freezeSlot`（由 `wo.order.started` 触发）置 `frozen=true`；重排方法均校验 `frozen=false`，冻结槽位拒收重排 |

### 6.2 业务不变式（Business Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| BIZ-01 | LineSchedule | 事件消费幂等--相同 `(work_order_id/asset_id, source_event_id)` 不重复变更槽位 | 跨实例，由 `SchedulingSuggestionService`/`SchedulingRescheduleService` + `consumed_event` 去重表保证（**禁止挂聚合根**） |
| BIZ-02 | LineSchedule | 同一工单同一时刻只有一个有效槽位（跨 `LineSchedule` 实例唯一性）--`work_order_id` 数据库唯一索引（status ∈ {PENDING, CONFIRMED}） | 跨实例唯一性，由 `LineSchedule` + 唯一索引保证（与 INV-04 跨实例同构；**禁止挂聚合根**） |
| BIZ-03 | LineSchedule | 排产建议读模型最终一致--`ScheduleSnapshotProjection` 由 `schedule.*` 事件驱动刷新，允许短暂延迟 | 读模型最终一致；排产员工作台优先读投影，降级查询聚合（**禁止挂聚合根**） |

### 6.3 跨上下文不变式（Cross-Context Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| INV-CX-01 | LineSchedule（本），WorkOrder（工单管理上下文） | MES 排产快照最终一致--工单的 `mes_scheduled_*` 由 `schedule.confirmed`/`rescheduled`/`released` 事件驱动回写，与 SAP 建议字段并存、互不覆盖 | 由工单管理上下文 `WorkOrderEventConsumeAppService` 消费 `schedule.*` 回写；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-02 | LineSchedule（本），物料上下文 | 齐套预占由"排产确认"触发--`schedule.confirmed` 触发物料上下文 `InventoryReservation` 预占；`schedule.rescheduled`/`released` 触发释放/重预占；不由"工单下达"触发 | 物料上下文订阅 `schedule.*`（此前 🔴"排产/工单派工事件待对齐"收敛为 `schedule.confirmed`）；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-03 | LineSchedule（本），物料上下文/工单管理上下文 | 缺料重排基于缺料信号--主源 `material.kit.reservation-failed`，次源 `wo.kit.status`(kit_ready=false)；两者均触发未开工槽位往后重排 | 由 `SchedulingRescheduleService.onKitReservationFailed`/`onKitStatusChanged` 消费；以 `work_order_id + source_event_id` 幂等去重；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-04 | LineSchedule（本），工单管理上下文/物料上下文 | 上下文外事件只消费不重发--本上下文将订阅事件包装为 `schedule.*` 语义事件后发布，下游凭主题前缀 `schedule.*` 区分来源 | 由 `SchedulingEventConsumeAppService` 包装发布；主题前缀 `schedule.*` vs `wo.*`/`material.*`/`eam.*`；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-05 | LineSchedule（本），在制品执行上下文 | 排产咨询性不门禁过点--在制品执行上下文不消费 `schedule.*` 做硬校验，过点放行/拦截仍按 `wo.order.*` 工单状态（RELEASED/IN_PROGRESS 放行，PAUSED/COMPLETED/CLOSED/CANCELLED 拦截） | 架构级约束：`schedule.*` 主消费方仅工单管理上下文+物料上下文+数据应用，在制品执行不订阅；MES 排产快照仅供看板与物料预 stage |
| INV-CX-06 | LineSchedule（本），设备工装台账上下文 | 设备故障重排基于资产可用性--`eam.asset.availability`(available=false, 关键资产) 重排该线未开工槽位；available=true 重新接纳 | 由 `SchedulingRescheduleService.onAssetAvailabilityChanged` 消费；`asset_id -> line_id` 经 `CriticalAssetRef` 配置映射（🔴）；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-07 | LineSchedule（本），工单管理上下文 | 已开工工单不重排--消费 `wo.order.started` 冻结槽位，重排只影响未开工（RELEASED）工单 | `freezeSlot` + INV-05；尊重工单上下文 INV-10（首次过点转态）与 INV-16（在制后禁调 target_qty）；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |
| INV-CX-08 | LineSchedule（本），各相邻上下文 | 跨上下文事件消费幂等--`consumed_event` 表 + 各事件既定去重键（BIZ-01 的通用机制） | 由 `consumed_event` 表保证；跨服务走事件订阅+ACL，同服务可走本地事务强一致 |

## 7. 对外契约（发布主题）

下游消费方只看以下投影，不直接读本上下文聚合：

| 主题 | 事件 | 主消费方 |
|------|------|----------|
| `schedule.suggested` | ScheduleSuggested(work_order_id, line_id, planned_start_at, planned_finish_at, sap_hint, suggested_at) | 排产员工作台（待确认建议）、数据应用上下文（排产看板） |
| `schedule.confirmed` | ScheduleConfirmed(work_order_id, line_id, planned_start_at, planned_finish_at, confirmed_by, confirmed_at) | **工单管理上下文**（回写 MES 排产快照）、**物料上下文**（触发齐套预占）、数据应用上下文（排产看板） |
| `schedule.rescheduled` | ScheduleRescheduled(work_order_id, old_*, new_*, trigger, rescheduled_at) | **工单管理上下文**（更新 MES 排产快照）、**物料上下文**（释放旧预占+重新预占）、数据应用上下文 |
| `schedule.released` | ScheduleReleased(work_order_id, line_id, reason, released_at) | **工单管理上下文**（清空 MES 排产快照）、**物料上下文**（释放齐套预占）、数据应用上下文 |
| `schedule.rejected` | ScheduleRejected(work_order_id, line_id, reject_reason, rejected_at) | 排产员工作台、数据应用上下文（建议驳回审计） |

**主题命名约定**：
- 本上下文**对外发布**：`schedule.<aggregate>.<event-class>`（`schedule` = 排产缩写，**与工单管理 `wo.*`、在制品 `wip.*`、返工 `brework.*`、返修 `rework.*` 严格区分**），表示"已经过排产语义解释"。
- 本上下文**订阅**：使用各发布限界上下文自己的前缀，不重写--`wo.*`（工单管理上下文）、`material.*`（物料上下文）、`eam.*`（设备工装台账上下文）。

> **已确认：排产咨询性不门禁过点**--`schedule.*` 主消费方为工单管理上下文（回写快照）+ 物料上下文（齐套预占）+ 数据应用上下文（看板）。在制品执行上下文**不订阅** `schedule.*`，过点放行/拦截仍按 `wo.order.*` 工单状态。MES 排产快照不参与过点硬校验（INV-CX-05）。

> 🔴 **热点：产线产能日历权威源**--当前薄配置字典起步；待"工厂建模上下文"落地后 `LineCapacityResolver` 改为 REST 查询，前缀与契约再对齐。

## 9. 领域服务与应用服务的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                           外部调用入口                                  │
│                                                                      │
│  REST/终端 ──▶ SchedulingCommandAppService (应用服务)                 │
│                ├─ 单聚合操作：直接委托聚合根方法（confirmSlot/release）│
│                ├─ 跨聚合编排：委托 SchedulingRescheduleService（跨线） │
│                └─ 同事务推进状态 + 发布集成事件（Outbox）              │
│                                                                      │
│  消息消费 ───▶ SchedulingEventConsumeAppService (应用服务)            │
│                └─ 翻译 wo.*/material.*/eam.* 事件 -> 委托领域服务│
│                  （包装为 schedule.* 语义事件后发布，INV-CX-04）        │
│                                                                      │
│  查询请求 ───▶ SchedulingQueryAppService (应用服务，读模型)           │
│                └─ 直接查询读模型投影（排产快照/积压/重排追溯）        │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  SchedulingSuggestionService │ SchedulingRescheduleService            │
│  LineCapacityResolver (领域辅助组件)                                  │
│  └─ 封装跨聚合/跨上下文规则，加载聚合，调用聚合行为，写仓储，返回事件  │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  LineSchedule                                                        │
│  └─ 表达业务状态、行为、不变式、领域事件；不依赖 Spring/MQ/HTTP        │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 排产与工单/物料/在制品/设备台账经异步事件解耦，不在他上下文主事务中引入分布式事务
