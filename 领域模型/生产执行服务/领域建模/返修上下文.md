# 返修上下文 — 领域建模（Rework Domain Model）

> **限界上下文**：返修
> **统一语言**：ReworkTask（返修任务·单件级）, FaultDiagnosis（故障诊断·产品缺陷定位）, RepairAction（返修动作·产品修理执行）, ReworkVerification（返修验证）, ReentryPoint（再入点·修后回主线的工位）, ReworkRule（返修规则·工艺管理上下文只读引用）, ReentryRule（再入点配置·工艺管理上下文只读引用）, ScrapDecision（单件报废决策·返修后判废）
> **建模依据**：[事件风暴 — 返修上下文](../事件风暴/返修上下文.md)

> **变更说明（2026-07-08）**：§6 不变式由主题式单段 `INV-XX` 拆为三段--聚合不变式 `INV-XX`（按聚合根分子节归位）、业务不变式 `BIZ-XX`（本上下文跨聚合 / 跨实例，最终一致）、跨上下文不变式 `INV-CX`（跨限界上下文）。旧 `INV-XX` 归类迁移：聚合内（INV-05/08/09/10/14）保留原号；跨聚合 / 跨实例（旧 BIZ-01/02/03/04/07/16）-> `BIZ-01..06`；跨上下文（旧 INV-CX-01/11/12/13/15/17）-> `INV-CX-01..06`。正文内联引用同步更新。事件风暴侧已降级为无编号"已识别约束"清单，编号权威以本节 §6 为准。

## 0. 建模总览

本域是生产执行服务下的**单件离线再处理子域**，是 PCBA + 整机组装混合型车间所有"单件返修活动"的执行权威源。核心职责是管理**返修任务接单、故障诊断与可修复性分流、产品级返修动作执行、返修验证、再入点判定、返修后单件报废**——即"**单件产品怎么修、修后从哪再入、修不好怎么报废**"；**不负责**过点判定与拦截决策（归过点执行上下文，本上下文仅消费其分流事件 `mes.unit.routed-to-rework`，向其发布 `rework.task.completed` / `rework.task.scrapped`）、不负责批量返工工单（归返工上下文，粒度根本不同）、**不负责设备维修（归设备管理服务维修上下文 `repair.*`，那是修机器，本上下文修的是产品单件）**、不负责返修规则与再入点配置的维护（归工艺管理上下文，本上下文只读引用）、不负责在制品位置投影（归在制品追踪上下文）。

本上下文与过点执行上下文是"离线返修"与"在线过点"的接力关系，通过事件契约解耦。返修任务在返修区独立执行，可能跨班次、跨操作员，与过点的在线同步交互模型完全不同。**再入点的"判定"与"校验"分离**：本上下文**判定**再入点（基于工艺管理上下文的返修规则配置），过点执行上下文**校验**再入点（基于当前 routeVersion 步序合法性）。

## 1. 聚合根

### 1.1 ReworkTask（返修任务）

**一致性边界**：单个返修任务的身份、来源、状态流转、报废属性与关单。

**职责**：关联过点拦截分流事件；承载单件级返修主轴状态机；锁定 routeVersion；管理报废决策状态；驱动诊断->修理->验证->再入判定->完成的完整闭环。

```yaml
ReworkTask:
  # ─── 标识 ───
  task_id:          TaskId                # 返修任务唯一标识（聚合根ID）

  # ─── 来源 ───
  sn:               String                # 单件序列号（一个 SN 一个任务, BIZ-01）
  work_order_id:    String                # 来源工单
  defect_reason:    String                # 缺陷原因（来自过点拦截事件）
  source_station:   String                # 拦截工位（来自过点拦截事件）
  source_event_id:  SourceEventId         # 来源事件 ID（UnitRoutedToRework 事件 ID, 幂等去重键 BIZ-02）

  # ─── 工艺版本锁定 ───
  route_id:         String                # 工艺路线 ID
  route_version:    String                # 工艺路线版本（CREATED 时锁定, INV-14）

  # ─── 状态 ───
  state:            ReworkTaskState       # CREATED / DIAGNOSED / IN_REPAIR / PENDING_REENTRY / PENDING_SCRAP_DECISION / COMPLETED / SCRAPPED

  # ─── 报废属性（PENDING_SCRAP_DECISION 时）───
  scrap_reason:     ScrapReason?          # NotEconomical / NotRepairable
  scrap_diagnosis_summary: String?        # 报废诊断摘要

  # ─── 审计 ───
  created_at:       DateTime
  completed_at:     DateTime?             # COMPLETED / SCRAPPED 时填
```

**行为**：
- `accept(sn, work_order_id, defect_reason, source_station, source_event_id, route_id, route_version)` -> 发出 `ReworkTaskCreated`（前置：幂等去重通过 BIZ-01/BIZ-02；-> `CREATED`；锁定 routeVersion INV-14）
- `markDiagnosed()` -> 状态 `CREATED` -> `DIAGNOSED`（前置：当前 `CREATED`；诊断 `feasibility=REPAIRABLE`；**不发独立生命周期事件**，由 `DiagnosisResultRecorded` 隐含驱动，经 `DiagnosisService` 编排）
- `startRepair()` -> 状态 `DIAGNOSED` -> `IN_REPAIR`（前置：当前 `DIAGNOSED` 且诊断 `feasibility=REPAIRABLE`；**不发独立生命周期事件**，由首条 `RepairActionPerformed` 隐含驱动，经 `ReworkExecutionService` 编排）
- `markPendingReentry()` -> 状态 `IN_REPAIR` -> `PENDING_REENTRY`（前置：当前 `IN_REPAIR`；验证 `VERIFIED` + 再入点已判定；**不发独立生命周期事件**，由 `ReworkVerificationSubmitted(VERIFIED)` + `ReentryPointDetermined` 隐含驱动）
- `complete()` -> 发出 `UnitReworkCompleted`（前置：当前 `PENDING_REENTRY`；-> `COMPLETED`，终态 INV-05）
- `recommendScrap(reason, diagnosis_summary)` -> 发出 `ScrapRecommended`（前置：当前 `DIAGNOSED` 且诊断 `feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}`；-> `PENDING_SCRAP_DECISION`）
- `approveScrap()` -> 发出 `UnitScrappedAfterRework`（前置：当前 `PENDING_SCRAP_DECISION`；报废审批通过；-> `SCRAPPED`，终态 INV-05）
- `rejectScrapRediagnosis()` -> 发出 `ScrapDecisionRejected`（前置：当前 `PENDING_SCRAP_DECISION`；报废审批驳回/撤回；-> `DIAGNOSED`，重新评估方案 INV-09）
- `reopenForReevaluation()` -> 状态 `PENDING_REENTRY` -> `IN_REPAIR`（前置：消费过点执行 `ReentryRejected`；**不发独立生命周期事件**，由 `ReentryPointReevaluated` 隐含驱动，经 `ReentryPointService` 编排）
- `resumeRepair()` -> 状态 `IN_REPAIR` -> `IN_REPAIR`（回退，前置：当前 `IN_REPAIR`；验证 `FAILED` 且带原因 BIZ-05；**不发独立生命周期事件**，由 `ReworkVerificationSubmitted(FAILED)` 隐含驱动）

> **状态机隐含驱动说明**：`CREATED->DIAGNOSED`、`DIAGNOSED->IN_REPAIR`、`IN_REPAIR->PENDING_REENTRY`、`PENDING_REENTRY->IN_REPAIR`（ReentryRejected）、`IN_REPAIR->IN_REPAIR`（FAILED 回退）五条边不发独立工单生命周期事件，分别由 `DiagnosisResultRecorded` / 首条 `RepairActionPerformed` / `ReworkVerificationSubmitted(VERIFIED)` + `ReentryPointDetermined` / `ReentryPointReevaluated` / `ReworkVerificationSubmitted(FAILED)` 隐含驱动（状态机内部推进，任务状态在读模型投影中反映）。这与事件风暴 §2.2 状态图一致。

> **routeVersion 锁定（INV-14）**：返修任务在 `CREATED` 时锁定 `routeVersion`（参考过点执行上下文 INV-CX-02 模式），再入点判定基于锁定版本。若过点执行上下文因版本变更拒绝再入点，本上下文重判时读取**最新版本**的返修规则。

> **COMPLETED / SCRAPPED 为终态（INV-05）**：终态之后任何事件均拒收。`ReentryRejected` 在 `PENDING_REENTRY` 态消费（尚未 `complete()`），不存在终态回退。

### 1.2 FaultDiagnosis（故障诊断）

**一致性边界**：单次故障诊断的根因、维修方案、可修复性判定。

**职责**：关联 `ReworkTask`；记录产品缺陷根因与 `repair_feasibility`；驱动修理/报废分流；一个 ReworkTask 可多次诊断（首次诊断后报废驳回可再诊断 BIZ-03）。

```yaml
FaultDiagnosis:
  # ─── 标识 ───
  diagnosis_id:     DiagnosisId           # 诊断唯一标识（聚合根ID）

  # ─── 关联 ───
  task_id:          TaskId                # 关联返修任务

  # ─── 诊断结论 ───
  fault_cause:      FaultCause            # 故障原因（分类编码 + 自由描述）
  repair_plan:      String                # 返修方案
  repair_feasibility: RepairFeasibility   # REPAIRABLE / NOT_ECONOMICAL / NOT_REPAIRABLE
  estimated_duration: Duration?           # 预估返修时长

  # ─── 成本（供报废建议判定）───
  estimated_repair_cost: Decimal?         # 返修预估成本（NOT_ECONOMICAL 判定输入）

  # ─── 审计 ───
  started_at:       DateTime?
  diagnosed_by:     String?
  diagnosed_at:     DateTime?
```

**行为**：
- `start(task_id, started_by)` -> 发出 `DiagnosisStarted`（前置：任务当前 `CREATED`；创建诊断记录）
- `recordResult(fault_cause, repair_plan, feasibility, estimated_duration, estimated_repair_cost?, diagnosed_by)` -> 发出 `DiagnosisResultRecorded`（前置：当前已 `start`；每次必填 `feasibility` BIZ-03；经 `DiagnosisService` 编排任务 `markDiagnosed()` 并分流）

> **可修复性判定（BIZ-03 / 事件风暴 §2.1 热点）**：`repair_feasibility` 判定逻辑（"返修成本 ≥ 单件价值 × 阈值" 等）不在本上下文硬编码——本上下文只记录诊断结论与 `estimated_repair_cost`，阈值判定由策略引擎/工程标准执行，结论写入 `feasibility`。`REPAIRABLE` -> 进入返修执行；`NOT_ECONOMICAL/NOT_REPAIRABLE` -> `RecommendScrap`。

> **多次诊断**：报废驳回后再诊断时新建 `FaultDiagnosis` 实例（BIZ-03），最新一条的 `feasibility` 驱动任务当前分流。历史诊断保留作为返修知识沉淀（供数据应用上下文缺陷分析）。

### 1.3 RepairAction（返修动作·产品级）

**一致性边界**：单个返修动作的类型、描述与执行证据。

**职责**：关联 `IN_REPAIR` 任务；记录**产品级**修理动作（补焊/更换元器件/重做工序/调整）；**不消耗备件库存**（元器件由返修区物料管理，归物料上下文）。

```yaml
RepairAction:
  # ─── 标识 ───
  action_id:        ActionId              # 动作唯一标识（聚合根ID）

  # ─── 关联 ───
  task_id:          TaskId                # 关联返修任务（BIZ-04）

  # ─── 动作（产品级）───
  action_type:      ActionType            # REFLOW_SOLDER / REPLACE_COMPONENT / REDO_PROCESS / ADJUST / OTHER
  description:      String                # 动作描述
  parts_replaced[]: List<ReplacedPart>?   # 更换的元器件（仅记录追溯，不扣减库存）

  # ─── 审计 ───
  performed_by:     String
  started_at:       DateTime
  completed_at:     DateTime
  evidence_urls[]:  List<String>          # 照片/视频证据
  repair_station_id: String?              # 返修区工位（🔴 热点：是否纳入台账管理）
```

**行为**：
- `perform(task_id, action_type, description, parts_replaced, performed_by, evidence_urls, repair_station_id?)` -> 发出 `RepairActionPerformed`（前置：任务 `IN_REPAIR` BIZ-04）。若为首条动作，由 `ReworkExecutionService` 编排——先 `task.startRepair()` 再创建 `RepairAction`，二者同事务。

> **关键区分**：本上下文的 `RepairAction` 是**产品级修理**（修一块 PCBA 的焊点/换一个元器件），与设备管理服务维修上下文的 `RepairAction`（修一台设备、消耗备件）**完全不同**——前缀不同（`rework.*` vs `repair.*`）、聚合归属不同、动作类型不同。本上下文的返修动作**不消耗备件库存**（元器件归物料上下文），若涉及元器件领用另走物料上下文，不在本上下文展开。

> **首条动作驱动 IN_REPAIR**：任务首条 `RepairAction` 由 `ReworkExecutionService` 编排——若任务仍 `DIAGNOSED`，先 `task.startRepair()` 再创建 `RepairAction`，二者同事务。后续动作任务已在 `IN_REPAIR`，直接创建。

> 🔴 **热点：返修区物料/元器件管理**（事件风暴 §2.3）——返修更换的元器件是否需要领用记录与库存扣减？建议：**需要**——但归物料上下文（或返修区物料子域），本上下文只在 `RepairAction` 记录 `parts_replaced[]` 用于单件维修历史追溯，不直接扣减库存。待与物料上下文确认返修区物料管理模式。

> 🔴 **热点：返修动作是否需关联原工位/设备**（事件风暴 §2.3）——建议：**记录** `repair_station_id`（返修区工位），便于质量追溯与返修设备利用率分析。但不与设备工装台账上下文的 asset_id 强绑定。待与台账上下文确认返修设备是否纳入资产台账。

### 1.4 ReworkVerification（返修验证）

**一致性边界**：单次返修验证的方式、结果与失败原因。

**职责**：关联有 `RepairAction` 的任务；`VERIFIED/FAILED` 分流；`FAILED` 必须有原因说明；`VERIFIED` 驱动再入点判定。

```yaml
ReworkVerification:
  # ─── 标识 ───
  verification_id:  VerificationId        # 验证唯一标识（聚合根ID）

  # ─── 关联 ───
  task_id:          TaskId                # 关联返修任务

  # ─── 验证 ───
  method:           VerificationMethod    # RETEST / REINSPECT / LINE_RETRY
  result:           VerificationResult    # VERIFIED / FAILED
  failed_reason:    String?               # FAILED 时必填（BIZ-05）

  # ─── 审计 ───
  verified_by:      String
  verified_at:      DateTime
  evidence_urls[]:  List<String>?
```

**行为**：
- `submit(task_id, method, result, failed_reason?, verified_by)` -> 发出 `ReworkVerificationSubmitted`（前置：任务 `IN_REPAIR` 且至少一条 `RepairAction` BIZ-04；`result=FAILED` 时 `failed_reason` 必填 BIZ-05）。经 `VerificationService` 编排：`VERIFIED` -> 触发 `ReentryPointService.determineReentryPoint`；`FAILED` -> `task.resumeRepair()`（回退继续修理，重试上限 3 次 BIZ-06）

> **LINE_RETRY 与再入点的关系**（事件风暴 §3 热点）：`LINE_RETRY` 是返修区**主动选择**让单件回主线某工位复测作为验证手段（验证失败则不完成再入）；再入点判定是验证通过后**根据规则**确定修后从哪再入主线。两者顺序：先验证（可能 LINE_RETRY），通过后再判再入点。若 LINE_RETRY 的工位与再入点恰好一致，可合并流程。

> 🔴 **热点：返修验证失败的重试上限**（事件风暴 §3）——`ResumeRepair` 回退后可无限次重试吗？建议：**重试上限=3 次**（BIZ-06），超过则升级返修主管评估是否转报废（`repair_feasibility` 重判为 NOT_REPAIRABLE）。待与 SME 确认重试上限。

### 1.5 ReentryPoint（再入点判定）

**一致性边界**：单次再入点判定的工位、规则命中、重判计数。

**职责**：关联 `ReworkTask`；读取工艺管理上下文的返修规则与再入点配置；判定修后应从哪个工位再入主线；处理 `ReentryRejected` 后的重判逻辑（`reeval_count` 阈值 3，INV-CX-05）。

```yaml
ReentryPoint:
  # ─── 标识 ───
  reentry_id:       ReentryId             # 再入点判定唯一标识（聚合根ID）

  # ─── 关联 ───
  task_id:          TaskId                # 关联返修任务
  sn:               String                # 单件序列号

  # ─── 判定结果 ───
  reentry_point:    String                # 再入工位（来自返修规则与再入点配置）
  rule_id:          String?               # 命中的返修规则 ID
  route_id:         String                # 工艺路线 ID
  route_version:    String                # 工艺路线版本
  defect_reason:    String                # 原缺陷原因（用于规则匹配）
  repair_result:    String                # 返修结果（REPAIRED，用于规则匹配）

  # ─── 重判控制 ───
  reeval_count:     Integer               # 重判次数（防 ReentryRejected 死循环, INV-CX-05）

  # ─── 审计 ───
  determined_at:    DateTime
```

**行为**：
- `determine(task_id, sn, route_id, route_version, defect_reason, repair_result, reentry_point, rule_id?)` -> 发出 `ReentryPointDetermined`（前置：任务 `IN_REPAIR` 且验证 `VERIFIED`；`reeval_count=0`；经 `ReentryPointService` 编排任务 `markPendingReentry()`）
- `reevaluate(new_reentry_point, rule_id?)` -> 发出 `ReentryPointReevaluated`（前置：消费过点执行 `ReentryRejected`；`reeval_count < 3` INV-CX-05；`reeval_count += 1`；经 `ReentryPointService` 编排任务 `reopenForReevaluation()`）
- `markExhausted()` -> 发出 `ReentryPointExhausted`（前置：`reeval_count ≥ 3` 或仍无合法再入点 INV-CX-05；升级人工处理，任务停留 `IN_REPAIR`）

> **再入点"判定"与"校验"分离**：本上下文**判定**再入点（基于工艺管理上下文的返修规则配置），过点执行上下文**校验**再入点（基于当前 routeVersion 步序合法性）。两者职责不重叠——本上下文不持有 routeVersion 的步序定义，无法自校验；过点执行上下文不持有返修规则，无法自判定。

> **reeval_count 死循环防护（INV-CX-05）**：`ReentryRejected` 后重判再入点，若新再入点仍被过点执行拒绝，`reeval_count` 递增。阈值=3，超过则发布 `ReentryPointExhausted` 升级人工处理，不再自动重判。

> 🔴 **热点：返修规则与再入点配置的具体形态**（事件风暴 §2.5）——工艺管理上下文的"返修规则与再入点配置"尚未定义事件风暴，其数据结构与查询接口形态未确定。建议：本上下文定义一个 `ReworkRuleQuery` 端口接口（输入 route_id/route_version/defect_reason/repair_result，输出 reentry_point + rule_id），具体实现由工艺管理上下文提供。待工艺管理上下文事件风暴落地后对齐。

> 🔴 **热点：再入点判定的默认回退**（事件风暴 §2.5）——若返修规则未命中（如该缺陷原因无配置再入点），如何处理？建议：**回退到拦截工位的下一工位**（保守再入，避免跳站），并发布 `ReentryPointFallbackApplied` 事件记录默认回退。待与工艺管理上下文确认默认回退策略。

## 2. 值对象

### 2.1 TaskId / DiagnosisId / ActionId / VerificationId / ReentryId（标识）

```yaml
TaskId:          { value: String }    # 返修任务唯一标识
DiagnosisId:     { value: String }    # 诊断唯一标识
ActionId:        { value: String }    # 返修动作唯一标识
VerificationId:  { value: String }    # 验证唯一标识
ReentryId:       { value: String }    # 再入点判定唯一标识
```

> 不可变。由系统在各自 `ReworkTaskCreated` / `DiagnosisStarted` / `RepairActionPerformed` / `ReworkVerificationSubmitted` / `ReentryPointDetermined` 事件时生成。

### 2.2 ReworkTaskState（返修任务状态）

```yaml
ReworkTaskState:
  - CREATED                 # 已创建，待诊断
  - DIAGNOSED               # 已诊断（REPAIRABLE），待修理
  - IN_REPAIR               # 修理中
  - PENDING_REENTRY         # 验证通过 + 再入点已判定，待过点执行确认
  - PENDING_SCRAP_DECISION  # 待报废审批
  - COMPLETED               # 已完成（终态，INV-05）
  - SCRAPPED                # 已报废（终态，INV-05）
```

**状态机**：

```
                         [CREATED]
                            |
           DiagnosisResultRecorded(REPAIRABLE)
                            |
                            v
                        [DIAGNOSED]
                            |
           ┌────────────────┼────────────────────┐
           |                |                    |
   feasibility=      首条 RepairAction      feasibility ∈
   REPAIRABLE        (ReworkExecution-      {NOT_ECONOMICAL,
           |          Service 编排)          NOT_REPAIRABLE}
           |                |                    |
           v                v                    v
      [IN_REPAIR] ◀──reopenForReevaluation──┐  [PENDING_SCRAP_DECISION]
           │  ▲              (ReentryRejected)  │       │
           │  │                                 │       │
   Verify  │  │ resumeRepair            Approve │       │ RejectScrap
   VERIFIED│  │ (FAILED 回退,            Scrap  │       │ Rediagnosis
           │  │  BIZ-05)                        │       │ (INV-09)
           v  │                                 v       │
    [PENDING_REENTRY] ──complete()──▶ [COMPLETED]       │
           │                           (终态)            │
           │                                             v
           └──ReevaluateReentryPoint(reeval_count<3)──▶ [SCRAPPED]
                                                         (终态)

   COMPLETED / SCRAPPED 之后任何事件均拒收（INV-05）
```

**不变式**：
- `CREATED -> DIAGNOSED`：`markDiagnosed()`，由 `DiagnosisResultRecorded(REPAIRABLE)` 驱动
- `DIAGNOSED -> IN_REPAIR`：`startRepair()`，前置 `feasibility=REPAIRABLE`，由首条 `RepairActionPerformed` 驱动
- `IN_REPAIR -> PENDING_REENTRY`：`markPendingReentry()`，由 `ReworkVerificationSubmitted(VERIFIED)` + `ReentryPointDetermined` 驱动
- `PENDING_REENTRY -> COMPLETED`：`complete()`，同时发布 `UnitReworkCompleted`（INV-05）
- `DIAGNOSED -> PENDING_SCRAP_DECISION`：`recommendScrap()`，前置 `feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}`
- `PENDING_SCRAP_DECISION -> SCRAPPED`：`approveScrap()`，报废审批通过（INV-05）
- `PENDING_SCRAP_DECISION -> DIAGNOSED`：`rejectScrapRediagnosis()`，报废驳回/撤回（INV-09），可逆回退
- `PENDING_REENTRY -> IN_REPAIR`：`reopenForReevaluation()`，消费过点执行 `ReentryRejected`（INV-CX-01），可逆回退
- `IN_REPAIR -> IN_REPAIR`：`resumeRepair()`，验证 FAILED 回退继续修理（BIZ-05）
- `COMPLETED` / `SCRAPPED` 之后任何事件均拒收（终态 INV-05）
- 状态单向流转，仅 `ReevaluateReentryPoint` / `ResumeRepair` / `RejectScrapRediagnosis` 允许回退（INV-10）

### 2.3 RepairFeasibility（可修复性判定）

```yaml
RepairFeasibility:
  - REPAIRABLE       # 返修成本 < 单件价值 × 阈值 -> 进入返修执行
  - NOT_ECONOMICAL   # 返修成本 ≥ 单件价值 × 阈值 -> 建议报废
  - NOT_REPAIRABLE   # 技术上无法修复（如 PCB 烧毁）-> 建议报废
```

> 不可变枚举。由诊断工程师/策略引擎判定，写入 `FaultDiagnosis.repair_feasibility`。判定阈值不在本上下文硬编码（事件风暴 §2.1 热点）。

### 2.4 ActionType（返修动作类型·产品级）

```yaml
ActionType:
  - REFLOW_SOLDER      # 补焊/修复焊点
  - REPLACE_COMPONENT  # 更换元器件
  - REDO_PROCESS       # 重做工序
  - ADJUST             # 调整
  - OTHER              # 其它
```

> 不可变枚举。**产品级**修理动作，与设备维修上下文的 `ActionType`（REPLACE/REPAIR/ADJUST/CLEAN/LUBRICATE/OTHER）**完全不同**。仅 `REPLACE_COMPONENT` 可能涉及元器件更换（记录 `parts_replaced[]`，不扣减库存）。

### 2.5 VerificationMethod（验证方式）

```yaml
VerificationMethod:
  - RETEST       # 返修区复测（同工位测试设备复跑）
  - REINSPECT    # 返修区复检（AOI/X-Ray 复检）
  - LINE_RETRY   # 回主线工位复测（再入点测试）
```

> 不可变枚举。`LINE_RETRY` 是返修区主动选择让单件回主线某工位复测作为验证手段，与再入点判定不重叠（先验证，通过后再判再入点）。

### 2.6 VerificationResult（验证结果）

```yaml
VerificationResult:
  - VERIFIED   # 验证通过
  - FAILED     # 验证失败
```

> 不可变枚举。`VERIFIED` -> 触发再入点判定；`FAILED` -> 退回修理（`ResumeRepair`，重试上限 3 次 BIZ-06）。

### 2.7 ScrapReason（单件报废原因）

```yaml
ScrapReason:
  - NotEconomical    # 返修不经济（NOT_ECONOMICAL）
  - NotRepairable    # 无法修复（NOT_REPAIRABLE）
```

> 不可变枚举。**单件产品报废**原因，与设备维修上下文的 `ScrapReason`（设备资产报废）**完全不同**。单件报废事件 `UnitScrappedAfterRework` 发布到 `rework.task.scrapped`，消费方为过点执行上下文 + 在制品追踪上下文。

### 2.8 FaultCause / SourceEventId / ReplacedPart（辅助值对象）

```yaml
FaultCause:
  category_code: String     # 故障原因分类编码
  description:   String     # 自由描述

SourceEventId:
  value: String             # 来源事件 ID（幂等去重键）

ReplacedPart:
  part_code: String
  part_name: String
  quantity:  Integer
```

> `FaultCause.category_code` 供数据应用上下文做缺陷分析。`SourceEventId` 用于 `UnitRoutedToRework` 幂等去重（BIZ-02）。`ReplacedPart` 仅记录追溯，不触发库存扣减。

### 2.9 ReworkTaskLifecycleView（返修任务生命周期视图）

```yaml
ReworkTaskLifecycleView:
  task_id:          TaskId
  sn:               String
  work_order_id:    String
  state:            ReworkTaskState
  defect_reason:    String
  source_station:   String
  reentry_point:    String?
  reeval_count:     Integer?
  created_at:       DateTime
  completed_at:     DateTime?
```

> 读模型投影，供返修看板、在制品追踪上下文（WIP 标记）、数据应用上下文查询，不进聚合。由 `ReworkTaskLifecycleProjection` 在 `rework.task.*` 事件到达时刷新。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 ReworkTaskService（返修任务接单服务）

**职责**：消费过点执行上下文 `UnitRoutedToRework`，经幂等去重后创建 `ReworkTask`；保证一个 SN 同时只有一个未终态任务（BIZ-01）。

```yaml
ReworkTaskService:
  方法:
    onUnitRoutedToRework(sn, work_order_id, defect_reason, source_station, source_event_id, route_id, route_version):
      # 来源：过点执行上下文 mes.unit.routed-to-rework
      # 1. 幂等去重：source_event_id 去重表（BIZ-02）
      # 2. 唯一性校验：同 SN 是否存在未终态 ReworkTask（BIZ-01）
      # 3. task.accept(...) -> ReworkTaskCreated（锁定 routeVersion, INV-14）
      # 4. 策略：触发诊断 -> StartDiagnosis
```

> **为什么不放在聚合根内**：接单需跨实例查询去重表（`source_event_id` / SN 唯一性）——单条 `ReworkTask` 聚合无权查询其它任务实例，也无法自我驱动来源路由。幂等去重（BIZ-02）与 SN 唯一性（BIZ-01）是跨实例不变式，由本服务 + 事件去重表保证。

---

### 3.2 DiagnosisService（故障诊断服务）

**职责**：编排诊断流程——创建诊断、记录结论、驱动任务 `CREATED->DIAGNOSED`、按 `feasibility` 分流（REPAIRABLE 待修理 / NOT_ECONOMICAL·NOT_REPAIRABLE 发起报废建议）。

```yaml
DiagnosisService:
  方法:
    startDiagnosis(task_id, started_by):
      # 前置：任务 CREATED
      # 1. 创建 FaultDiagnosis -> DiagnosisStarted
      # 2. （可联动质量上下文缺陷分类字典辅助诊断，REST 只读）

    recordDiagnosisResult(task_id, fault_cause, repair_plan, feasibility, estimated_duration, estimated_repair_cost?, diagnosed_by):
      # 1. 加载当前 FaultDiagnosis -> recordResult(...) -> DiagnosisResultRecorded
      # 2. 加载 ReworkTask -> task.markDiagnosed()（CREATED -> DIAGNOSED，同事务）
      # 3. 分流：
      #    feasibility=REPAIRABLE -> 等待首条 RepairAction（ReworkExecutionService）
      #    feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE} -> ScrapDecisionService.recommendScrap(task, diagnosis)
```

> **为什么不放在聚合根内**：诊断结论记录在 `FaultDiagnosis` 聚合，但其结果是驱动 `ReworkTask` 状态流转（`CREATED->DIAGNOSED`）与报废分流——跨 `FaultDiagnosis` + `ReworkTask` 两个聚合，单聚合无权推进对方状态。`feasibility` 分流策略跨聚合，归本服务编排。

> **可修复性阈值不在本上下文硬编码**（事件风暴 §2.1 热点）：本服务只记录 `estimated_repair_cost` 与 `feasibility` 结论，"返修成本 ≥ 单件价值 × 阈值"的判定由策略引擎/工程标准执行后传入。

---

### 3.3 ReworkExecutionService（返修执行服务）

**职责**：编排返修动作执行——首条动作驱动任务 `DIAGNOSED->IN_REPAIR`、创建 `RepairAction`（产品级）。

```yaml
ReworkExecutionService:
  方法:
    performRepairAction(task_id, action_type, description, parts_replaced, performed_by, evidence_urls, repair_station_id?):
      # 1. 加载 ReworkTask
      # 2. 若 task.state=DIAGNOSED -> task.startRepair()（DIAGNOSED -> IN_REPAIR，首条动作驱动）
      #    若 task.state=IN_REPAIR -> 直接创建动作
      #    否则 -> 拒收（BIZ-04）
      # 3. 创建 RepairAction -> RepairActionPerformed
      # 4. parts_replaced 仅记录追溯，不触发库存扣减
```

> **为什么不放在聚合根内**：首条 `RepairAction` 需先推进 `ReworkTask` 状态（跨聚合），且 `RepairAction` 与 `ReworkTask` 在不同聚合。单聚合无权推进对方状态。

> 🔴 **热点：返修区物料/元器件管理**（事件风暴 §2.3）——返修更换的元器件归物料上下文，本上下文不发布 `PartsConsumed` 事件（与设备维修上下文不同）。`parts_replaced[]` 仅记录追溯。

---

### 3.4 VerificationService（返修验证服务）

**职责**：编排返修验证——提交验证结果、`VERIFIED` 驱动再入点判定、`FAILED` 驱动退回修理。

```yaml
VerificationService:
  方法:
    submitVerification(task_id, method, result, failed_reason?, verified_by):
      # 1. 前置校验：任务 IN_REPAIR 且至少一条 RepairAction（BIZ-04）；FAILED 必填 failed_reason
      # 2. 创建 ReworkVerification -> ReworkVerificationSubmitted
      # 3. 分流：
      #    result=VERIFIED -> 委托 ReentryPointService.determineReentryPoint(task_id)
      #    result=FAILED -> task.resumeRepair()（回 IN_REPAIR，重试上限 3 次 BIZ-06）
      #      若重试次数超限 -> 升级返修主管评估转报废
```

> **为什么不放在聚合根内**：验证结果需驱动 `ReworkTask` 状态流转（跨聚合），且 `VERIFIED` 分流需触发再入点判定（跨 `ReworkVerification` + `ReworkTask` + `ReentryPoint` 三个聚合）。单聚合无权编排跨聚合流程。

> 🔴 **热点：返修验证失败的重试上限**（事件风暴 §3）——`ResumeRepair` 回退后可无限次重试吗？建议：**重试上限=3 次**（BIZ-06），超过则升级返修主管评估是否转报废。已固化为 BIZ-06。

---

### 3.5 ReentryPointService（再入点判定服务）

**职责**：编排再入点判定——读取工艺管理上下文返修规则配置、判定再入点、驱动任务 `IN_REPAIR->PENDING_REENTRY`；消费过点执行 `ReentryRejected` 重判再入点（`reeval_count` 阈值 3，INV-CX-05）。

```yaml
ReentryPointService:
  方法:
    determineReentryPoint(task_id):
      # 前置：任务 IN_REPAIR + 验证 VERIFIED
      # 1. 加载 ReworkTask -> 获取 sn / route_id / route_version / defect_reason
      # 2. REST 查询工艺管理上下文返修规则与再入点配置
      #    （输入 route_id/route_version/defect_reason/repair_result -> 输出 reentry_point + rule_id）
      # 3. 若规则命中 -> 创建 ReentryPoint -> ReentryPointDetermined（reeval_count=0）
      #    若规则未命中 -> 默认回退到拦截工位下一工位（🔴 热点）-> ReentryPointFallbackApplied
      # 4. task.markPendingReentry()（IN_REPAIR -> PENDING_REENTRY，同事务）
      # 5. 策略：task.complete() -> UnitReworkCompleted（发布到 rework.task.completed）

    onReentryRejected(task_id, sn, rejection_reason):
      # 来源：过点执行上下文 mes.reentry.rejected
      # 1. 幂等去重：task_id + rework_task_id 去重（防止同一拒绝重复触发）
      # 2. 加载 ReentryPoint -> reevaluate(new_reentry_point) -> ReentryPointReevaluated
      #    （reeval_count += 1，重新 REST 查询返修规则）
      # 3. task.reopenForReevaluation()（PENDING_REENTRY -> IN_REPAIR）
      # 4. 重新 task.complete() -> UnitReworkCompleted(new_reentry_point)
      # 5. 若 reeval_count ≥ 3 或仍无合法再入点：
      #    -> ReentryPointExhausted + 升级人工处理（任务停留 IN_REPAIR, INV-CX-05）
```

> **为什么不放在聚合根内**：再入点判定需 REST 查询工艺管理上下文（跨上下文）、消费过点执行 `ReentryRejected` 事件（跨上下文）、驱动 `ReworkTask` 状态流转（跨聚合）——单聚合无权跨上下文查询或推进其它聚合状态。`reeval_count` 阈值判定（INV-CX-05）是跨实例不变式，由本服务 + 去重表保证。

> 🔴 **热点：再入点判定的默认回退**（事件风暴 §2.5）——若返修规则未命中，回退到拦截工位的下一工位（保守再入），并发布 `ReentryPointFallbackApplied` 事件。已固化为本服务默认回退逻辑。

> 🔴 **热点：工艺版本变更对在制返修任务的影响**（事件风暴 §2.6）——返修任务在 CREATED 时锁定 routeVersion（INV-14），再入点判定基于锁定版本；若过点执行因版本变更拒绝再入点，本上下文重判时读取**最新版本**的返修规则。待与过点执行上下文确认再入点校验是用锁定版本还是最新版本。

### 3.6 ScrapDecisionService（单件报废决策服务）

**职责**：诊断不可修复/不经济时发布 `ScrapRecommended` 建议；消费报废审批结果驱动任务关单（通过）/退回诊断（驳回/撤回）。

```yaml
ScrapDecisionService:
  方法:
    recommendScrap(task, diagnosis):
      # 前置：task DIAGNOSED，diagnosis.feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}
      # 1. 构造 scrap_reason + diagnosis_summary
      # 2. task.recommendScrap(scrap_reason, diagnosis_summary) -> ScrapRecommended -> PENDING_SCRAP_DECISION
      # 3. 发布到 rework.task.scrapped（待审批通过后发布 UnitScrappedAfterRework）
      # 本上下文只发布建议，审批归返修主管/质量主管（🔴 热点：审批流归属）

    onScrapApproved(task_id):
      # 来源：报废审批通过（审批流形态待定，🔴 热点）
      # 1. 幂等去重：task_id 去重
      # 2. task.approveScrap() -> UnitScrappedAfterRework -> SCRAPPED
      # 3. 发布到 rework.task.scrapped（过点执行上下文 + 在制品追踪上下文消费）

    onScrapRejectedOrWithdrawn(task_id):
      # 来源：报废审批驳回/撤回
      # 1. 幂等去重：task_id 去重
      # 2. task.rejectScrapRediagnosis() -> ScrapDecisionRejected -> DIAGNOSED（重新评估方案, INV-09）
```

> **为什么不放在聚合根内**：报废建议需发布跨上下文集成事件、消费审批结果驱动任务状态流转（跨聚合 + 跨上下文），审批结果去重是跨实例不变式，由本服务 + 去重表保证。

> **报废审批与执行归外部**：本上下文只发布 `ScrapRecommended` 建议与 `UnitScrappedAfterRework` 结论，审批流程归返修主管/质量主管（🔴 热点：是否独立成上下文还是本上下文内嵌）。

> **关键区分——单件报废 vs 设备报废**：本上下文的 `UnitScrappedAfterRework` 是**单件产品报废**（一个 SN 报废，主题 `rework.task.scrapped`），与设备管理服务维修上下文的 `ScrapRecommendation`（设备资产报废建议，主题 `repair.scrap.recommendation`）**完全不同**。两者事件名、主题前缀、消费方均不同，**严禁混用**（INV-CX-03）。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与过点执行上下文的协作经**异步事件解耦**（返修完成/报废事件由过点执行上下文消费后自行校验），不在过点主事务中引入分布式事务。

### 4.1 ReworkCommandAppService（返修命令应用服务）

**职责**：处理诊断、返修执行、验证、再入判定、完成、报废建议的写操作命令（REST/移动端入口，发命令者：返修工程师/质检/返修主管）。

```yaml
ReworkCommandAppService:
  方法:
    # ─── 诊断 ───
    startDiagnosis(task_id, started_by):
      # -> DiagnosisService.startDiagnosis
    recordDiagnosisResult(task_id, ...):
      # -> DiagnosisService.recordDiagnosisResult（同事务推进任务 DIAGNOSED + 分流）

    # ─── 返修执行 ───
    performRepairAction(task_id, ...):
      # -> ReworkExecutionService.performRepairAction
      #   （首条动作同事务推进任务 IN_REPAIR）

    # ─── 验证 ───
    submitVerification(task_id, method, result, failed_reason?, verified_by):
      # -> VerificationService.submitVerification
      #   VERIFIED -> 同事务触发 ReentryPointService + task.markPendingReentry() + task.complete()
      #   FAILED -> 同事务 task.resumeRepair()

    # ─── 再入判定 ───
    determineReentryPoint(task_id):
      # -> ReentryPointService.determineReentryPoint
      #   同事务推进任务 PENDING_REENTRY -> COMPLETED + 发布 UnitReworkCompleted

    # ─── 完成 ───
    completeReworkTask(task_id):
      # -> task.complete() -> UnitReworkCompleted（发布到 rework.task.completed）

    # ─── 报废 ───
    recommendScrap(task_id):
      # 前置：task DIAGNOSED 且 feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}
      # -> ScrapDecisionService.recommendScrap
    approveScrap(task_id):
      # -> ScrapDecisionService.onScrapApproved
    rejectScrapRediagnosis(task_id):
      # -> ScrapDecisionService.onScrapRejectedOrWithdrawn
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 开始诊断 | 单聚合事务 | `DiagnosisService.startDiagnosis` | `DiagnosisStarted` | `commandId` |
| 记录诊断结论 | 诊断 + 任务同事务 | `DiagnosisService.recordDiagnosisResult` | `DiagnosisResultRecorded`（+任务内部推进 DIAGNOSED） | `commandId` |
| 执行返修动作 | 动作 + 任务同事务 | `ReworkExecutionService.performRepairAction` | `RepairActionPerformed` | `commandId` |
| 提交验证 | 验证 + 任务同事务 | `VerificationService.submitVerification` | `ReworkVerificationSubmitted` + `UnitReworkCompleted`(VERIFIED) | `commandId`；任务终态拒收 |
| 判定再入点 | 再入点 + 任务同事务 | `ReentryPointService.determineReentryPoint` | `ReentryPointDetermined` + `UnitReworkCompleted` | `commandId` |
| 完成返修任务 | 单聚合事务 | `ReworkTask.complete` | `UnitReworkCompleted` | `commandId`；终态拒收 |
| 建议报废 | 单聚合事务 | `ScrapDecisionService.recommendScrap` | `ScrapRecommended` | `commandId` |
| 批准报废 | 单聚合事务 | `ScrapDecisionService.onScrapApproved` | `UnitScrappedAfterRework` | `commandId`；终态拒收 |
| 驳回报废重诊断 | 单聚合事务 | `ScrapDecisionService.onScrapRejectedOrWithdrawn` | `ScrapDecisionRejected` | `commandId` |

### 4.2 ReworkEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.6 消费策略逐条迁入）。

```yaml
ReworkEventConsumeAppService:
  订阅主题与处理:
    # 过点执行上下文（主题前缀 mes.*）
    mes.unit.routed-to-rework (UnitRoutedToRework):
      -> ReworkTaskService.onUnitRoutedToRework
      # 幂等：source_event_id 去重表（BIZ-02）
    mes.reentry.rejected (ReentryRejected, reason=InvalidReentryPoint):
      -> ReentryPointService.onReentryRejected
      # 幂等：task_id + rework_task_id 去重（INV-CX-01）
```

> **不直接消费工艺管理上下文事件**：返修规则与再入点配置通过 REST 查询（非事件订阅），不在本上下文消费范围。

> **上下文外事件只消费不重发**（INV-CX-02）：本上下文将订阅事件包装为 `ReworkTaskCreated` / `ReentryPointReevaluated` 等本上下文语义事件后发布，下游可凭主题前缀区分来源。

> **主题命名约定**：本域**对外发布**使用 `rework.*` 前缀。本域**订阅**使用各发布域实际前缀（`mes.*`），不重写。`rework.*` 与 `repair.*`（设备维修）**严格区分，严禁混用**（INV-CX-06）。

### 4.3 ReworkQueryAppService（查询应用服务）

**职责**：提供读模型查询，支撑返修看板、在制品追踪、数据应用上下文。

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 返修上下文](../事件风暴/返修上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 ReworkTask（返修任务）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-05 | `COMPLETED` / `SCRAPPED` 为终态，之后任何事件均拒收 | `ReworkTaskState` 状态机；终态拒收任何命令 |
| INV-08 | 单件报废需审批通过才能 `SCRAPPED` | `ScrapDecisionService.onScrapApproved`，审批结果去重（task_id） |
| INV-09 | 报废驳回/撤回后任务退回 `DIAGNOSED` 重新评估 | `ScrapDecisionService.onScrapRejectedOrWithdrawn` -> `task.rejectScrapRediagnosis()` |
| INV-10 | 状态单向流转，仅 `ReevaluateReentryPoint` / `ResumeRepair` / `RejectScrapRediagnosis` 允许回退 | `ReworkTaskState` 状态机；可逆边仅再入点被拒回退重判 / 验证失败回退修理 / 报废驳回回退诊断 |
| INV-14 | 返修任务在 `CREATED` 时锁定 `routeVersion`（参考过点执行上下文 INV-CX-02 模式），再入点判定基于锁定版本 | `ReworkTask.accept` 时快照 `routeVersion`；若过点执行因版本变更拒绝再入点，重判时读取最新版本规则 |

#### 6.1.2 FaultDiagnosis（故障诊断）

> 无 FaultDiagnosis 特有聚合不变式；相关约束见 §6.2 业务不变式。

#### 6.1.3 RepairAction（返修动作）

> 无 RepairAction 特有聚合不变式；相关约束见 §6.2 业务不变式。

#### 6.1.4 ReworkVerification（返修验证）

> 无 ReworkVerification 特有聚合不变式；相关约束见 §6.2 业务不变式。

#### 6.1.5 ReentryPoint（再入点判定）

> 无 ReentryPoint 特有聚合不变式；相关约束见 §6.2 / §6.3。

### 6.2 业务不变式（Business Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| BIZ-01 | ReworkTask | 一个 SN 同时只能有一个未终态的 ReworkTask（同一 SN 不并行返修） | 跨实例唯一性，由 `ReworkTaskService` 创建时校验同 SN 是否存在未终态任务 + 数据库唯一索引 `(sn, status NOT IN (COMPLETED, SCRAPPED))` 辅助保证（**禁止挂聚合根**） |
| BIZ-02 | ReworkTask | 同一 `UnitRoutedToRework` 不重复创建返修任务 | 跨实例，由 `source_event_id` 事件去重表 + `ReworkTaskService` 保证（**禁止挂聚合根**） |
| BIZ-03 | FaultDiagnosis, ReworkTask | 一个 `ReworkTask` 可多次诊断（首次诊断后报废驳回可再诊断）；每次诊断必须记录 `repair_feasibility` | 跨聚合（FaultDiagnosis + ReworkTask），由 `DiagnosisService` 编排保证（**禁止挂聚合根**） |
| BIZ-04 | RepairAction, ReworkTask | `RepairAction` 必须关联一个 `IN_REPAIR` 状态的 `ReworkTask`；产品级修理，不消耗备件库存 | 跨聚合（RepairAction + ReworkTask），首条动作由 `ReworkExecutionService` 同事务推进任务 `IN_REPAIR` 后创建；后续动作校验任务状态；`parts_replaced[]` 仅记录追溯（**禁止挂聚合根**） |
| BIZ-05 | ReworkVerification, ReworkTask | `ReworkVerification` 必须关联一个有 `RepairAction` 记录的 `ReworkTask`；`FAILED` 验证必须有原因说明 | 跨聚合（ReworkVerification + ReworkTask），由 `ReworkVerification.submit` 前置校验 + `VerificationService` 编排保证（**禁止挂聚合根**） |
| BIZ-06 | ReworkVerification, ReworkTask | 返修验证失败重试上限=3 次，超过则升级返修主管评估是否转报废（`repair_feasibility` 重判为 NOT_REPAIRABLE） | 跨聚合（ReworkVerification + ReworkTask），由 `VerificationService` 重试计数 + 超限升级保证（**禁止挂聚合根**） |

### 6.3 跨上下文不变式（Cross-Context Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| INV-CX-01 | ReentryPoint, ReworkTask（本），工艺管理上下文 | 再入点必须来自工艺管理上下文的返修规则配置（或默认回退）；`ReentryRejected` 后重新判定再入点 | 跨上下文，由 `ReentryPointService` REST 查询工艺管理上下文 + `onReentryRejected` 消费策略保证；幂等：task_id + rework_task_id 去重 |
| INV-CX-02 | ReworkTask（本），过点执行上下文等 | 上下文外事件只消费不重发——本上下文将订阅事件包装为本上下文语义事件后发布，下游凭主题前缀区分来源 | 跨上下文，由 `ReworkEventConsumeAppService` 包装发布保证；主题前缀 `rework.*` vs `mes.*` |
| INV-CX-03 | ReworkTask（本），设备管理服务维修上下文 | 单件报废与设备报废不混淆——`UnitScrappedAfterRework`（单件级，`rework.task.scrapped`）vs `ScrapRecommendation`（设备级，`repair.scrap.recommendation`），事件名、主题前缀、消费方均不同，**严禁混用** | 跨上下文，由事件名区分 + 主题前缀区分 + 消费方区分保证（过点执行/WIP vs 台账上下文） |
| INV-CX-04 | ReentryPoint（本），工艺管理上下文 | 再入点配置一致性——本上下文 REST 查询工艺管理上下文为权威源，本地不缓存规则（每次判定实时查询，避免配置漂移） | 跨上下文，由 `ReentryPointService` 每次判定实时 REST 查询保证；若性能要求需缓存，待与工艺管理上下文确认缓存失效机制 |
| INV-CX-05 | ReentryPoint, ReworkTask（本），过点执行上下文 | `ReentryRejected` 后重判再入点，`reeval_count` 阈值=3，超过则发布 `ReentryPointExhausted` 升级人工处理，不再自动重判 | 跨上下文，由 `ReentryPoint.reevaluate` 前置 `reeval_count < 3` + `ReentryPointService` 编排保证 |
| INV-CX-06 | ReworkTask（本），设备管理服务维修上下文 | `rework.*` 与 `repair.*` 事件前缀严格分离——本上下文只发布 `rework.*` 主题，**严禁**发布 `repair.*` 或 `brework.*` 主题；订阅 `mes.*` 不重写 | 跨上下文，由主题命名约定 + 代码审查校验保证；`rework.*` 为单件产品返修，`repair.*` 为设备维修，两者聚合/语义/消费方完全不同 |

## 7. 对外契约（发布主题）

下游消费方只看以下投影，不直接读本上下文聚合：

| 主题 | 事件 | 主消费方 |
|------|------|----------|
| `rework.task.created` | ReworkTaskCreated(task_id, sn, defect_reason, source_station, source_event_id) | 数据应用上下文（返修统计） |
| `rework.task.completed` | UnitReworkCompleted(sn, task_id, reentry_point, rework_result) | **过点执行上下文**（再入点校验 + RoutingProgress 推进）；在制品追踪上下文（间接，经有过点执行中转） |
| `rework.task.scrapped` | UnitScrappedAfterRework(sn, task_id, scrap_reason) | **过点执行上下文**（单件已报废，不再回主线）；**在制品追踪上下文**（WIP 标记报废）；数据应用上下文（良率统计） |
| `rework.diagnosis` | DiagnosisResultRecorded(task_id, fault_cause, repair_feasibility) | 质量上下文（缺陷分析）；数据应用上下文（返修根因分析） |
| `rework.action.performed` | RepairActionPerformed(task_id, action_type, performed_by) | 数据应用上下文（返修动作统计）；追溯上下文 |
| `rework.verification` | ReworkVerificationSubmitted(task_id, method, result) | 数据应用上下文（返修质量统计） |

**主题命名约定**：
- 本上下文**对外发布**：`rework.<aggregate>.<event-class>`（`rework` 为本上下文缩写，**与设备管理服务维修上下文的 `repair` 前缀严格区分**），表示"已经过单件返修语义解释"。
- 本上下文**订阅**：使用各发布限界上下文自己的前缀，不重写——`mes.*`（过点执行上下文）、工艺管理上下文（`process.*` 或制造资源服务约定前缀，REST 查询为主）、质量上下文（`quality.*` 或制造资源服务约定前缀，REST 查询为主）。
- **严禁混用**：`rework.*`（单件产品返修）与 `repair.*`（设备维修）是两个不同限界上下文的前缀，聚合/语义/消费方完全不同，代码与配置中必须严格区分（INV-CX-06）。

## 9. 领域服务与应用服务的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                           外部调用入口                                  │
│                                                                      │
│  REST/移动端 ──▶ ReworkCommandAppService (应用服务)                    │
│                 ├─ 单聚合操作：直接委托聚合根方法                        │
│                 ├─ 跨聚合编排：委托领域服务（诊断/返修/验证/再入/报废）    │
│                 └─ 同事务推进任务状态 + 发布集成事件                      │
│                                                                      │
│  消息消费 ───▶ ReworkEventConsumeAppService (应用服务)                 │
│                 └─ 翻译 mes.* 事件 -> 委托领域服务                        │
│                   （包装为本上下文语义事件后发布，INV-CX-02）                │
│                                                                      │
│  查询请求 ───▶ ReworkQueryAppService (应用服务，读模型)                │
│                 └─ 直接查询读模型投影                                   │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  ReworkTaskService │ DiagnosisService │ ReworkExecutionService        │
│  VerificationService │ ReentryPointService │ ScrapDecisionService    │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  ReworkTask / FaultDiagnosis / RepairAction                           │
│  ReworkVerification / ReentryPoint                                    │
│  └─ 表达业务状态、行为、不变式、领域事件；不依赖 Spring/MQ/HTTP          │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 返修->过点执行经异步事件解耦（INV-CX-02），不在过点主事务中引入分布式事务
