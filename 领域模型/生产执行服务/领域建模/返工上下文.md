# 返工上下文 — 领域建模（Batch Rework Domain Model）

> **限界上下文**：返工上下文
> **统一语言**：BatchReworkOrder（返工工单·批次/订单级）, ReworkRoute（返工工艺路线·工艺管理上下文只读引用）, ReentryPoint（批量再入点·整批回主线的工位）, ReworkTrigger（返工触发·质量异常/工程变更/人工决策）, ReworkProgress（返工进度·按 SN 维度累计）, ScrapDecision（批量报废决策·返工后整批或部分判废）
> **建模依据**：[事件风暴 — 返工上下文](../事件风暴/返工上下文.md)

---

## 0. 建模总览

本域是生产执行服务下的**批量再处理子域**，是 PCBA + 整机组装混合型车间所有"订单/批次级返工活动"的执行权威源。核心职责是管理**返工工单生成、返工工艺路线引用、批量再入点判定、返工进度跟踪、批量再入放行、返工后批量报废**——即"**一批产品怎么返工、走什么返工路线、从哪批量再入**"；**不负责**过点判定与拦截（归过点执行上下文，本上下文向其发布 `brework.order.released` 由其做再入校验+推进）、**不负责单件返修**（归返修上下文 `rework.*`，单件级离线修复，与本上下文粒度/触发/聚合完全不同）、**不负责设备维修**（归设备管理服务维修上下文 `repair.*`，修机器而非修产品）、不负责工艺路线定义与版本生命周期（归工艺管理上下文，本上下文只读引用返工工艺路线）、不负责在制品位置投影（归在制品追踪上下文，本上下文只发布再入/报废事件供其投影）。

本上下文与过点执行上下文是"批量返工"与"在线过点"的接力关系——返工完成后的批量再入由本上下文**判定**再入点（读返工路线配置），过点执行上下文**校验**再入点（持有 routeVersion 步序定义，INV-07）。这是"判定"与"校验"的职责分离，参考返修上下文同款模式。本上下文**不直接扣减** `WorkOrderProgress`（口径归过点执行 INV-08），通过事件异步解耦。

> **聚合边界说明**：事件风暴统一语言中的 `ReworkRoute` 建模为只读引用值对象 `ReworkRouteRef`（非聚合根）——返工工艺路线的定义与版本生命周期归工艺管理上下文，本上下文只在 `ROUTE_ASSIGNED` 时锁定 `rework_route_id` + `rework_route_version` 引用，后续进度跟踪与再入点判定基于锁定版本实时 REST 查询（INV-13）。`ReentryPoint` 建模为 `BatchReworkOrder` 的属性（`reentry_point`）——批量再入点是返工工单的一次性判定结果，不独立成聚合。`ReworkProgress` 建模为独立聚合根——按 SN 维度累计进度，有独立的生命周期（进度累计→pending_qty=0 触发转态），与 `BatchReworkOrder` 的状态机解耦（INV-04）。`ScrapDecision` 不独立成聚合根——报废建议与审批是 `BatchReworkOrder` 的行为（`recommendScrap`/`approveScrap`），通过 `ScrapDecisionService` 编排跨上下文审批流。这样 2 个聚合根各自守护单一一致性边界，路线引用/再入点/报废决策不另起聚合，避免聚合碎片化。

## 1. 聚合根

### 1.1 BatchReworkOrder（返工工单·批次/订单级）

**一致性边界**：单个返工工单的身份、触发来源、SN 清单、返工路线引用、再入点、状态流转、报废决策与关单。

**职责**：关联源工单与 SN 清单；承载返工工单主轴状态机（CREATED→ROUTE_ASSIGNED→IN_REWORK→PENDING_REENTRY→RELEASED→COMPLETED / SCRAPPED）；锁定返工路线版本引用；定义批量再入点；发起批量报废建议与审批；接收再入点重判命令。

```yaml
BatchReworkOrder:
  # ─── 标识 ───
  rework_order_id:      ReworkOrderId         # 返工工单唯一标识（聚合根ID）

  # ─── 来源 ───
  source_work_order_id: SourceWorkOrderId     # 源工单（原生产工单，引用工单管理上下文）
  sn_list[]:            List<SnId>            # 返工 SN 清单（一批 SN, INV-01）
  trigger_source:       ReworkTrigger         # QUALITY / ECN / MANUAL
  reason:               ReworkReason          # 返工原因（BatchDefect / ECN / ManualDecision）
  source_event_id:      SourceEventId?        # 来源事件 ID（幂等去重键，若来自事件，INV-02）

  # ─── 返工路线引用 ───
  rework_route_ref:     ReworkRouteRef?       # 返工工艺路线引用（ROUTE_ASSIGNED 时锁定，INV-09/INV-13）

  # ─── 再入点 ───
  reentry_point:        ReentryPoint?         # 批量再入点（整批回主线的工位）
  reeval_count:         Integer = 0           # 再入点重判次数（INV-06）

  # ─── 状态 ───
  state:                BatchReworkOrderState # CREATED / ROUTE_ASSIGNED / IN_REWORK / PENDING_REENTRY / RELEASED / COMPLETED / PENDING_SCRAP_DECISION / SCRAPPED

  # ─── 报废 ───
  scrap_reason:         ScrapReason?          # 报废原因（PENDING_SCRAP_DECISION 时）
  scrap_sn_list[]:      List<SnId>?           # 报废 SN 清单（部分报废时，🔴 是否拆单）

  # ─── 审计 ───
  created_at:           DateTime
  released_at:          DateTime?
  completed_at:         DateTime?
```

**行为**：
- `create(source_work_order_id, sn_list[], trigger_source, reason, source_event_id?)` → 发出 `BatchReworkOrderCreated`（前置：`sn_list` 非空 INV-01；`source_event_id` 非空时幂等去重 INV-02；→ `CREATED`）
- `assignReworkRoute(rework_route_id, rework_route_version)` → 发出 `ReworkRouteAssigned`（前置：当前 `CREATED`；返工工艺路线已从工艺管理上下文 REST 查询成功并锁定版本 INV-03/INV-09；→ `ROUTE_ASSIGNED`）
- `startBatchRework()` → 状态 `ROUTE_ASSIGNED` → `IN_REWORK`（前置：当前 `ROUTE_ASSIGNED`；返工路线已分配；**不发独立生命周期事件**，由 `ReworkRouteAssigned` 后策略驱动，经 `BatchReworkOrderService` 编排）
- `completeBatchRework()` → 状态 `IN_REWORK` → `PENDING_REENTRY`（前置：`pending_qty=0` INV-04；**不发独立生命周期事件**，由 `ReworkProgressAccrued(pending_qty=0)` 策略驱动，经 `ReworkProgressService` 编排）
- `releaseBatchRework(reentry_point)` → 发出 `BatchReworkOrderReleased`（前置：当前 `PENDING_REENTRY`；再入点已定义；→ `RELEASED`）
- `completeReworkOrder(completed_qty)` → 发出 `BatchReworkOrderCompleted`（前置：当前 `RELEASED`；过点执行上下文已回传 `BatchReworkReentered` INV-07；→ `COMPLETED`，终态 INV-05）
- `recommendScrap(reason, scrap_sn_list[], diagnosis_summary)` → 发出 `BatchScrapRecommended`（前置：当前 `IN_REWORK`；返工后判定整批或部分 SN 无法修复/不经济；→ `PENDING_SCRAP_DECISION`）
- `approveScrap()` → 发出 `BatchReworkOrderScrapped`（前置：当前 `PENDING_SCRAP_DECISION`；批量报废审批通过；→ `SCRAPPED`，终态 INV-05）
- `rejectScrapRework()` → 状态 `PENDING_SCRAP_DECISION` → `IN_REWORK`（前置：报废审批驳回/撤回 INV-10；回到 `IN_REWORK` 重新评估）
- `reevaluateReentryPoint(new_reentry_point)` → 发出 `ReentryPointReevaluated`（前置：当前 `PENDING_REENTRY` 或 `RELEASED`；消费过点执行 `ReentryRejected`；`reeval_count` + 1；→ `IN_REWORK`，INV-06）
- `exhaustReentryPoint()` → 发出 `ReentryPointExhausted`（前置：`reeval_count ≥ 阈值 3` 或仍无合法再入点；→ 升级人工处理，工单停留在 `IN_REWORK`）

> **状态机隐含驱动说明**：`ROUTE_ASSIGNED→IN_REWORK`、`IN_REWORK→PENDING_REENTRY` 两条边不发独立工单生命周期事件，分别由 `ReworkRouteAssigned` 后策略 / `ReworkProgressAccrued(pending_qty=0)` 策略隐含驱动（状态机内部推进，工单状态在读模型投影中反映）。这与事件风暴 §2.2 状态图一致——事件风暴仅对 `BatchReworkOrderCreated/ReworkRouteAssigned/BatchReworkOrderReleased/BatchReworkOrderCompleted/BatchReworkOrderScrapped` 命名了工单生命周期事件，中间态由相邻聚合的事件承载。

> **RELEASED vs COMPLETED 区分**：`RELEASED` 表示本上下文已发布 `brework.order.released` 给过点执行上下文，但过点执行尚未完成批量再入；`COMPLETED` 才表示整批已成功再入主线。保留 `RELEASED` 中间状态便于跟踪再入进度与处理再入失败回退（INV-06）。🔴 过点执行上下文是否回传 `BatchReworkReentered` 以驱动 RELEASED→COMPLETED 待确认。

> **部分报废与部分再入**：同一返工工单内，若部分 SN 判废、部分再入，`BatchReworkOrderScrapped` 的 `scrap_sn_list[]` 只含报废 SN，`BatchReworkOrderReleased` 的 `sn_list[]` 只含再入 SN，两者可并行发布。工单状态以"是否所有 SN 已终态（再入或报废）"驱动 COMPLETED。🔴 是否拆单待与 SME 确认。

### 1.2 ReworkProgress（返工进度·按 SN 维度）

**一致性边界**：单个返工工单下按 SN 维度的返工进度累计。

**职责**：跟踪每个 SN 的返工状态（PENDING/REWORKED/SCRAPPED）；累计已返工/待返工/已报废数量；`pending_qty=0` 时驱动工单 `IN_REWORK→PENDING_REENTRY`（INV-04）。

```yaml
ReworkProgress:
  # ─── 标识 ───
  progress_id:        ProgressId            # 进度唯一标识（聚合根ID）

  # ─── 关联 ───
  rework_order_id:    ReworkOrderId         # 关联返工工单

  # ─── 数量累计 ───
  total_qty:          Integer               # 返工 SN 总数
  reworked_qty:       Integer               # 已返工 SN 数
  scrapped_qty:       Integer               # 已报废 SN 数
  pending_qty:        Integer               # 待返工 SN 数（= total - reworked - scrapped）

  # ─── SN 维度状态 ───
  sn_status[]:        List<SnReworkStatus>  # 各 SN 的返工状态

  # ─── 审计 ───
  last_accrued_at:    DateTime?
```

**行为**：
- `initialize(rework_order_id, sn_list[])` → 发出 `ReworkProgressInitialized`（前置：`sn_list` 非空；所有 SN 初始 `PENDING`；`total_qty = sn_list.size`；`pending_qty = total_qty`）
- `accrueProgress(sn, new_status)` → 发出 `ReworkProgressAccrued`（前置：`sn` 在 `sn_list` 中且当前 `PENDING`；`new_status ∈ {REWORKED, SCRAPPED}`；更新 `sn_status` 与数量累计；`reworked_qty + scrapped_qty + pending_qty = total_qty`）。若 `pending_qty = 0`，经 `ReworkProgressService` 编排工单 `completeBatchRework()`（INV-04）

> **首条进度由 `BatchReworkOrderService` 编排**：工单 `startBatchRework()` 后，`BatchReworkOrderService` 同事务创建 `ReworkProgress` 并 `initialize()`。

> **返工动作归属（🔴 热点）**：批量返工的"返工动作"（如整批补焊/整批重做工序）归返修上下文或返工区执行系统，本上下文只跟踪进度（消费返修上下文的 `UnitReworkCompleted` 或返工区执行系统的进度上报）。🔴 是否消费返修 `UnitReworkCompleted` 驱动 `ReworkProgress.accrueProgress` 待确认。

## 2. 值对象

### 2.1 标识值对象

```yaml
ReworkOrderId:       { value: String }    # 返工工单唯一标识
SourceWorkOrderId:   { value: String }    # 源工单标识（引用工单管理上下文）
ProgressId:          { value: String }    # 返工进度唯一标识
SnId:                { value: String }    # 序列号标识
SourceEventId:       { value: String }    # 来源事件 ID（幂等去重键）
```

> 不可变。由系统在各自 `BatchReworkOrderCreated` / `ReworkProgressInitialized` 事件时生成。`SourceWorkOrderId` 是上下文外引用，经防腐层（ACL）从工单管理上下文翻译为本上下文语义，本上下文不持有源工单聚合。

### 2.2 BatchReworkOrderState（返工工单状态）

```yaml
BatchReworkOrderState:
  - CREATED                 # 已创建，待分配返工路线
  - ROUTE_ASSIGNED          # 返工路线已分配，待开始返工
  - IN_REWORK               # 返工中（含再入点重判回退）
  - PENDING_REENTRY         # 返工完成，待批量再入放行
  - RELEASED                # 已放行，待过点执行再入完成
  - COMPLETED               # 已完成（终态，整批回主线, INV-05）
  - PENDING_SCRAP_DECISION  # 待批量报废审批
  - SCRAPPED                # 已报废（终态，INV-05）
```

**状态机**：

```
[CREATED] ──AssignReworkRoute──▶ [ROUTE_ASSIGNED] ──StartBatchRework──▶ [IN_REWORK]
                                                                           │
                    ┌──────────────────────────────────────────────────────┤
                    │                                                      │
                    │ CompleteBatchRework                                  │ RecommendScrap
                    │ (pending_qty=0, INV-04)                               │
                    │                                                      │
                    v                                                      v
            [PENDING_REENTRY]                                  [PENDING_SCRAP_DECISION]
                    │                                              │           │
                    │ ReleaseBatchRework                  ApproveScrap │  RejectScrapRework
                    │                                              │   (驳回重返工, INV-10)
                    v                                              v           │
              [RELEASED] ──CompleteReworkOrder──▶         [SCRAPPED]          │
                    │        (BatchReworkReentered,          (终态)            │
                    │         INV-07)                          ▲              │
                    │                                           │              │
                    v                                           │              │
             [COMPLETED] ◀──────────────────────────────────────┘              │
              (终态)                                                          │
                                                                              │
   [PENDING_REENTRY] ──ReevaluateReentryPoint──▶ [IN_REWORK] ◀───────────────┘
   [RELEASED]        ──ReevaluateReentryPoint──▶ [IN_REWORK]   (再入点被拒回退, INV-06)
                                                                              │
   COMPLETED / SCRAPPED 之后任何事件均拒收（终态 INV-05）                       │
```

**不变式**：
- `CREATED → ROUTE_ASSIGNED`：`assignReworkRoute()`，前置 `CREATED`；返工路线已从工艺管理上下文 REST 查询成功并锁定版本（INV-03）
- `ROUTE_ASSIGNED → IN_REWORK`：`startBatchRework()`，前置 `ROUTE_ASSIGNED`；由 `ReworkRouteAssigned` 策略驱动
- `IN_REWORK → PENDING_REENTRY`：`completeBatchRework()`，前置 `pending_qty=0`（INV-04）；由 `ReworkProgressAccrued(pending_qty=0)` 策略驱动
- `PENDING_REENTRY → RELEASED`：`releaseBatchRework()`，前置 `PENDING_REENTRY`；再入点已定义
- `RELEASED → COMPLETED`：`completeReworkOrder()`，前置 `RELEASED`；过点执行回传 `BatchReworkReentered`（INV-07）；→ `COMPLETED`，终态 INV-05
- `IN_REWORK → PENDING_SCRAP_DECISION`：`recommendScrap()`，前置 `IN_REWORK`
- `PENDING_SCRAP_DECISION → SCRAPPED`：`approveScrap()`，审批通过；→ `SCRAPPED`，终态 INV-05
- `PENDING_SCRAP_DECISION → IN_REWORK`：`rejectScrapRework()`，报废驳回/撤回（INV-10），可逆回退
- `PENDING_REENTRY / RELEASED → IN_REWORK`：`reevaluateReentryPoint()`，再入点被拒回退重判（INV-06），可逆回退
- `COMPLETED / SCRAPPED` 之后任何事件均拒收（终态 INV-05）
- 状态单向流转，仅 `ReevaluateReentryPoint` / `RejectScrapRework` 允许回退（INV-10）

### 2.3 ReworkTrigger（返工触发来源）

```yaml
ReworkTrigger:
  - QUALITY    # 质量上下文批量异常信号（批次性/系统性缺陷）
  - ECN        # 工程变更触发已生产批次返工
  - MANUAL     # 人工决策（生产主管/质量主管/工程师终端指令）
```

> 不可变枚举。决定 SN 清单来源：`QUALITY` 时由质量上下文提供不良 SN 清单；`ECN` 时由源工单的全部在制 SN；`MANUAL` 时由人工圈定。🔴 质量上下文批量异常信号是否携带 SN 清单待确认。

### 2.4 ReworkReason（返工原因）

```yaml
ReworkReason:
  category: ReworkReasonCategory    # BatchDefect / ECN / ManualDecision
  detail:   String                  # 原因详述（如"回流焊温区3偏差导致整批焊点不良"）
  source_event_id: SourceEventId?   # 来源事件 ID（若来自质量上下文/ECN 事件）

ReworkReasonCategory:
  - BatchDefect       # 批次性缺陷（质量上下文批量异常）
  - ECN               # 工程变更
  - ManualDecision    # 人工决策
```

> 不可变。`category` 与 `ReworkTrigger` 对应（QUALITY→BatchDefect、ECN→ECN、MANUAL→ManualDecision）。`detail` 供追溯与数据应用上下文分析。

### 2.5 ReworkRouteRef（返工工艺路线只读引用）

```yaml
ReworkRouteRef:
  rework_route_id:      String    # 返工工艺路线 ID（引用工艺管理上下文）
  rework_route_version: Integer   # 返工工艺路线版本（ROUTE_ASSIGNED 时锁定, INV-09）
```

> 不可变值对象。返工工艺路线是**独立于正常工艺路线的专用路线**，从工艺管理上下文 REST 查询引用（INV-03/INV-13）。本上下文不缓存路线内容（每次引用实时查询，避免配置漂移 INV-13）。`rework_route_version` 在 `ROUTE_ASSIGNED` 时锁定（参考过点执行上下文 INV-09 模式），后续返工进度跟踪与再入点判定基于锁定版本；若返工工艺路线在返工期间变更，已生成返工工单不受影响（沿用锁定版本），新返工工单用新版本。

> 🔴 **热点：返工工艺路线在工艺管理上下文的形态**——工艺管理上下文的"返工工艺路线"尚未定义事件风暴，其数据结构与查询接口形态未确定。本上下文定义一个 `ReworkRouteQuery` 端口接口（输入 `source_route_id`/`reason`，输出 `rework_route_id` + `rework_route_version` + `steps` + `reentry_point`），具体实现由工艺管理上下文提供。待工艺管理上下文事件风暴落地后对齐。

### 2.6 ReentryPoint（批量再入点）

```yaml
ReentryPoint:
  step_no:       StepNo    # 再入步序号（引用返工工艺路线步骤）
  station_type:  String    # 再入工位类型
  description:   String?   # 再入点描述
```

> 不可变值对象。批量再入点是返工工单定义的整批回主线的工位，随 `brework.order.released` 发布给过点执行上下文。再入点必须来自工艺管理上下文的返工工艺路线配置（或默认回退，INV-06）。本上下文**只判定**再入点（读返工路线配置），过点执行上下文**校验**再入点（是否在 routeVersion 合法步序内，INV-07）。

### 2.7 SnReworkStatus（SN 返工状态）

```yaml
SnReworkStatus:
  sn:     SnId                # 序列号
  status: SnReworkState       # PENDING / REWORKED / SCRAPPED
  accrued_at: DateTime?       # 状态变更时间

SnReworkState:
  - PENDING     # 待返工
  - REWORKED    # 已返工
  - SCRAPPED    # 已报废
```

> 隶属于 `ReworkProgress.sn_status[]` 的值对象集合。`PENDING` → `REWORKED` 或 `SCRAPPED`，不可逆。`reworked_qty + scrapped_qty + pending_qty = total_qty` 恒成立。

### 2.8 ScrapReason（报废原因）

```yaml
ScrapReason:
  - NotEconomical    # 返工不经济（返工成本过高）
  - NotRepairable    # 无法修复（技术上不可行）
  - Other            # 其它（需附说明）
```

> 不可变枚举。`BatchScrapRecommended` 事件载荷中携带。本上下文只发布报废建议与执行，不负责报废物料的回收处理（归物料上下文/废料管理）。

### 2.9 BatchReworkOrderLifecycleView（返工工单生命周期视图）

```yaml
BatchReworkOrderLifecycleView:
  rework_order_id:      ReworkOrderId
  source_work_order_id: SourceWorkOrderId
  state:                BatchReworkOrderState
  trigger_source:       ReworkTrigger
  sn_count:             Integer
  rework_route_id:      String?
  reentry_point:        ReentryPoint?
  progress:             ReworkProgressSummary?
  created_at:           DateTime
  released_at:          DateTime?
```

> 读模型投影，供数据应用上下文返工统计看板与返工主管监控查询，不进聚合。由 `BatchReworkOrderLifecycleProjection` 在 `brework.order.*` 事件到达时刷新。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 BatchReworkOrderService（返工工单生成服务）

**职责**：消费多来源触发信号（质量上下文批量异常/ECN/人工决策），经幂等去重后创建 `BatchReworkOrder`；编排工单创建后的自动路线分配与进度初始化。

```yaml
BatchReworkOrderService:
  方法:
    onQualityBatchDefectDetected(source_work_order_id, sn_list[], reason_detail, source_event_id):
      # 来源：质量上下文批量异常信号（🔴 事件未定义）
      # 1. 幂等去重：source_event_id 去重表（INV-02）
      # 2. 创建 BatchReworkOrder → BatchReworkOrderCreated（CREATED）
      #    trigger_source=QUALITY, reason.category=BatchDefect
      # 3. 策略：自动分配返工路线 → 委托 ReworkRouteService.assignRoute()
      # 4. 策略：自动开始返工 + 初始化 ReworkProgress

    onEcnReworkTriggered(source_work_order_id, sn_list[], reason_detail, source_event_id):
      # 来源：工程变更 ECN 返工触发（🔴 来源未定义）
      # 1. 幂等去重：source_event_id 去重表（INV-02）
      # 2. 创建 BatchReworkOrder → BatchReworkOrderCreated（CREATED）
      #    trigger_source=ECN, reason.category=ECN
      # 3. 策略：自动分配返工路线 → 委托 ReworkRouteService.assignRoute()
      # 4. 策略：自动开始返工 + 初始化 ReworkProgress

    onManualReworkDecision(source_work_order_id, sn_list[], reason_detail, operator):
      # 来源：人工终端指令
      # 1. 幂等去重：(source_work_order_id, operator, 时间窗口) 去重
      # 2. 创建 BatchReworkOrder → BatchReworkOrderCreated（CREATED）
      #    trigger_source=MANUAL, reason.category=ManualDecision
      # 3. 策略：自动分配返工路线 → 委托 ReworkRouteService.assignRoute()
      # 4. 策略：自动开始返工 + 初始化 ReworkProgress

    startBatchRework(rework_order_id):
      # 前置：工单 ROUTE_ASSIGNED
      # 1. order.startBatchRework() → IN_REWORK
      # 2. 创建 ReworkProgress → ReworkProgressInitialized（同事务）
      # 3. sn_status[] 全部初始化为 PENDING
```

> **为什么不放在聚合根内**：返工工单生成需跨实例查询去重表（`source_event_id` / `(source_work_order_id, operator, 时间窗口)`）、识别触发来源并路由创建策略——单条 `BatchReworkOrder` 聚合无权查询其它工单实例，也无法自我驱动来源路由。幂等去重（INV-02）是跨实例不变式，由本服务 + 事件去重表保证。

> 🔴 **热点：返工触发来源的事件形态**——质量上下文的"批量质量异常信号"与工程变更的"ECN 返工触发"事件尚未定义。本上下文定义一个 `ReworkTriggerPort` 端口接口（输入 `source_work_order_id`/`sn_list`/`reason`/`trigger_source`，输出是否生成返工工单），具体触发事件由质量上下文/工程变更模块提供。待质量上下文与工程变更模块事件风暴落地后对齐触发事件契约。

> 🔴 **热点：返工工单的 SN 清单来源**——`trigger_source=QUALITY` 时由质量上下文提供不良 SN 清单；`trigger_source=ECN` 时由源工单的全部在制 SN；`trigger_source=MANUAL` 时由人工圈定。SN 清单的准确性由触发方保证，本上下文只接收并固化。待与质量上下文确认批量异常信号是否携带 SN 清单。

### 3.2 ReworkRouteService（返工工艺路线查询服务）

**职责**：从工艺管理上下文 REST 查询返工工艺路线，锁定版本并分配给返工工单。

```yaml
ReworkRouteService:
  方法:
    assignRoute(rework_order_id):
      # 前置：工单 CREATED
      # 1. REST 查询工艺管理上下文：根据 source_work_order_id 的产品/路线类型
      #    查询对应的返工工艺路线（独立于正常路线，INV-03）
      # 2. 锁定 rework_route_id + rework_route_version（INV-09/INV-13）
      # 3. order.assignReworkRoute(rework_route_id, rework_route_version)
      #    → ReworkRouteAssigned → ROUTE_ASSIGNED
      # 4. 返回锁定的 rework_route_version

    queryReentryPoint(rework_order_id):
      # 前置：工单 IN_REWORK 或 PENDING_REENTRY
      # 1. REST 查询工艺管理上下文：根据锁定的 rework_route_id + rework_route_version
      #    获取返工工艺路线的再入点配置（ReentryPoint/ReentryRules）
      # 2. 返回再入点列表（供 ReentryPointService 判定）
      # 每次实时查询，不缓存（INV-13）

    queryRouteSteps(rework_order_id):
      # 前置：工单已锁定 rework_route_version
      # 1. REST 查询工艺管理上下文：获取锁定版本的步骤序列
      # 2. 返回步骤列表（供进度跟踪与再入点判定参考）
```

> **为什么不放在聚合根内**：返工工艺路线查询需跨上下文 REST 调用工艺管理上下文——`BatchReworkOrder` 聚合无权发起 HTTP 调用或查询上下文外数据。路线版本锁定（INV-09）是跨上下文一致性不变式，由本服务 + REST 实时查询保证（INV-13）。

> 🔴 **热点：返工工艺路线的版本锁定**——返工工单在 `ROUTE_ASSIGNED` 时锁定 `rework_route_version`（参考过点执行上下文 INV-09 模式），后续返工进度跟踪与再入点判定基于锁定版本；若返工工艺路线在返工期间变更，已生成返工工单不受影响（沿用锁定版本），新返工工单用新版本。待与工艺管理上下文确认返工工艺路线版本管理机制。

### 3.3 ReworkProgressService（返工进度累计服务）

**职责**：编排返工进度累计——接收 SN 维度返工完成/报废信号，更新 `ReworkProgress`，`pending_qty=0` 时驱动工单 `IN_REWORK→PENDING_REENTRY`（INV-04）。

```yaml
ReworkProgressService:
  方法:
    accrueSnReworked(rework_order_id, sn):
      # 来源：返修上下文 UnitReworkCompleted（🔴 是否消费）或返工区执行系统进度上报
      # 1. 加载 ReworkProgress
      # 2. progress.accrueProgress(sn, REWORKED) → ReworkProgressAccrued
      # 3. 若 pending_qty = 0 → order.completeBatchRework() → PENDING_REENTRY（INV-04，同事务）

    accrueSnScrapped(rework_order_id, sn, scrap_reason):
      # 来源：返工区判废信号
      # 1. 加载 ReworkProgress
      # 2. progress.accrueProgress(sn, SCRAPPED) → ReworkProgressAccrued
      # 3. 若 pending_qty = 0 → order.completeBatchRework() → PENDING_REENTRY（INV-04，同事务）
      # 注意：此处的 SCRAPPED 是进度维度的 SN 报废，区别于工单维度的批量报废建议

    batchAccrueProgress(rework_order_id, sn_status_updates[]):
      # 批量更新多个 SN 的返工状态（性能优化，适用于大批量场景）
      # 1. 逐 SN 校验：sn 在 sn_list 中且当前 PENDING
      # 2. 批量更新 sn_status 与数量累计
      # 3. 发布单次 ReworkProgressAccrued（含批量变更摘要）
      # 4. 若 pending_qty = 0 → order.completeBatchRework()（INV-04）
```

> **为什么不放在聚合根内**：返工进度累计需跨 `ReworkProgress` + `BatchReworkOrder` 两个聚合——`pending_qty=0` 时需驱动工单状态流转（`IN_REWORK→PENDING_REENTRY`），单聚合无权推进对方状态。进度信号来源（返修上下文/返工区执行系统）是跨上下文消费，归本服务编排。

> 🔴 **热点：返工进度跟踪的粒度**——返工进度是按 SN 维度逐个跟踪，还是按数量批量累计？建议：**按 SN 维度跟踪**（`sn_status[]` 记录每个 SN 的状态），便于精确追溯哪些 SN 已返工、哪些待返工、哪些报废。但若批量大（如 1000+ SN），SN 维度跟踪可能有性能压力，待与 SME 确认典型批量规模与跟踪粒度。

> 🔴 **热点：返工动作的归属**——批量返工的"返工动作"（如整批补焊/整批重做工序）是归本上下文还是返修上下文？建议：**返工动作归返修上下文或返工区执行系统**，本上下文只跟踪进度（消费返修上下文的 `UnitReworkCompleted` 或返工区执行系统的进度上报）。本上下文不重复建模返工动作的细节。待与返修上下文确认是否消费其完成事件驱动本上下文 `ReworkProgress` 累计。

### 3.4 ReentryPointService（批量再入点判定服务）

**职责**：判定批量再入点（读返工路线配置），编排批量再入放行；消费过点执行 `ReentryRejected` 后重新判定再入点（`reeval_count` 阈值 3，INV-06）。

```yaml
ReentryPointService:
  方法:
    determineAndRelease(rework_order_id):
      # 前置：工单 PENDING_REENTRY
      # 1. 委托 ReworkRouteService.queryReentryPoint() 获取返工工艺路线的再入点配置
      # 2. 判定批量再入点（取返工路线起点或配置的默认再入点）
      # 3. order.releaseBatchRework(reentry_point) → BatchReworkOrderReleased → RELEASED
      # 4. 发布到 brework.order.released（过点执行上下文消费做再入校验 INV-07）

    reevaluateOnRejected(rework_order_id, rejection_reason):
      # 来源：过点执行上下文 mes.reentry.rejected (ReentryRejected)
      # 1. 幂等去重：rework_order_id 去重（INV-06）
      # 2. 加载 BatchReworkOrder → reeval_count + 1
      # 3. 若 reeval_count < 阈值（3）：
      #    a. 重新 REST 查询返工工艺路线的再入点配置（可能命中不同再入点或回退默认再入点）
      #    b. order.reevaluateReentryPoint(new_reentry_point) → ReentryPointReevaluated → IN_REWORK
      #    c. 重新 determineAndRelease() → BatchReworkOrderReleased(new_reentry_point)
      # 4. 若 reeval_count ≥ 阈值 或 仍无合法再入点：
      #    a. order.exhaustReentryPoint() → ReentryPointExhausted
      #    b. 升级人工处理（返工主管介入），工单停留在 IN_REWORK
```

> **为什么不放在聚合根内**：再入点判定需跨上下文 REST 查询工艺管理上下文的返工路线配置——`BatchReworkOrder` 聚合无权发起 HTTP 调用。`ReentryRejected` 的重判逻辑涉及 `reeval_count` 阈值判定与跨上下文再入点查询，不自然归属单一聚合。再入点重判（INV-06）是跨聚合 + 跨上下文编排，归本服务。"判定"与"校验"分离——本上下文判定再入点，过点执行上下文校验再入点合法性（INV-07）。

> 🔴 **热点：再入点重判的死循环防护**——`ReentryRejected` 后重判再入点，若新再入点仍被过点执行拒绝，可能形成死循环。建议：**reeval_count 阈值=3**，超过则发布 `ReentryPointExhausted` 升级人工处理，不再自动重判。阈值是否可配置待与 SME 确认。

> 🔴 **热点：ReentryRejected 的载荷扩展**——过点执行上下文拒绝批量再入点的常见原因（`reason=InvalidReentryPoint`）是什么？建议：过点执行上下文在 `ReentryRejected` 载荷中补充 `rejection_detail`（如 `RouteVersionChanged` / `StepNotFound`），便于本上下文针对性重判。待与过点执行上下文确认载荷扩展。

> 🔴 **热点：工艺版本变更对在制返工工单的影响**——批量返工期间，工艺路线版本发生变更，原再入点判定是否仍有效？建议：**返工工单在 `ROUTE_ASSIGNED` 时锁定 `rework_route_version`**（参考过点执行上下文 INV-09 模式），再入点判定基于锁定版本；若过点执行上下文因版本变更拒绝再入点，本上下文重判时读取**最新版本**的返工工艺路线。待与过点执行上下文确认再入点校验是用返工工单锁定的 routeVersion 还是最新版本。

### 3.5 ScrapDecisionService（批量报废审批服务）

**职责**：编排批量报废建议与审批——诊断不可修复/不经济时发布 `BatchScrapRecommended` 建议；消费审批结果驱动工单关单（通过）/退回返工（驳回/撤回）。

```yaml
ScrapDecisionService:
  方法:
    recommendBatchScrap(rework_order_id, reason, scrap_sn_list[], diagnosis_summary):
      # 前置：工单 IN_REWORK；返工后判定整批或部分 SN 无法修复/不经济
      # 1. order.recommendScrap(reason, scrap_sn_list, diagnosis_summary)
      #    → BatchScrapRecommended → PENDING_SCRAP_DECISION
      # 2. 发布到 brework.order.scrap_recommended（🔴 审批流归属待确认）

    onScrapApproved(rework_order_id):
      # 来源：批量报废审批通过（🔴 审批流来源待确认）
      # 1. 幂等去重：rework_order_id 去重
      # 2. order.approveScrap() → BatchReworkOrderScrapped → SCRAPPED（终态 INV-05）
      # 3. 发布到 brework.order.scrapped
      #    - 过点执行上下文订阅（批量 SN 已报废，不再回主线）
      #    - 在制品追踪上下文订阅（WIP 标记报废）

    onScrapRejected(rework_order_id):
      # 来源：批量报废审批驳回/撤回
      # 1. 幂等去重：rework_order_id 去重
      # 2. order.rejectScrapRework() → IN_REWORK（INV-10，可逆回退）
      # 3. 工单回到 IN_REWORK 重新评估
```

> **为什么不放在聚合根内**：批量报废审批需跨上下文消费审批结果事件驱动工单状态流转——`BatchReworkOrder` 聚合无权订阅外部事件。审批结果去重是跨实例不变式，由本服务 + 去重表保证。报废建议的发布（`brework.order.scrapped`）是跨上下文集成事件，归本服务编排。

> 🔴 **热点：批量报废是否需要审批流**——返工后判定批量报废是否需返工主管/质量主管审批，还是返工工程师可直接判废？建议：**需审批**——批量报废影响工单良率与物料成本（一批 SN），应有审批留痕。审批人角色与权限模型待与质量上下文/权限模型确认。审批流是否独立成上下文还是本上下文内嵌简化版，待 SME 决策。

> 🔴 **热点：部分报废与整批报废的处理**——若返工后只有部分 SN 判废，是发布 `BatchReworkOrderScrapped`（仅含报废 SN）+ `BatchReworkOrderReleased`（含再入 SN），还是拆分多张工单？建议：**同一返工工单内部分处理**——`BatchReworkOrderScrapped` 的 `scrap_sn_list[]` 只含报废 SN，`BatchReworkOrderReleased` 的 `sn_list[]` 只含再入 SN，两者可并行发布。工单状态以"是否所有 SN 已终态（再入或报废）"驱动 COMPLETED。待与 SME 确认是否支持部分报废部分再入。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与过点执行上下文的协作经**异步事件解耦**（`brework.order.released` → 过点执行再入校验），不在过点主事务中引入分布式事务。

### 4.1 ReworkCommandAppService（返工命令应用服务）

**职责**：处理返工工单生成、路线分配、开始返工、进度记录、批量返工完成、放行、完成工单、报废建议与审批的写操作命令（REST/终端入口，发命令者：返工主管/质量主管/工程师/系统）。

```yaml
ReworkCommandAppService:
  方法:
    # ─── 返工工单生成 ───
    createBatchReworkOrder(cmd):
      # 委托 BatchReworkOrderService.onManualReworkDecision → 写仓储 → Outbox
      # 幂等：commandId + (source_work_order_id, operator, 时间窗口) 去重（INV-02）

    # ─── 路线分配 ───
    assignReworkRoute(rework_order_id):
      # → ReworkRouteService.assignRoute（同事务工单 ROUTE_ASSIGNED）

    # ─── 开始返工 ───
    startBatchRework(rework_order_id):
      # → BatchReworkOrderService.startBatchRework（同事务工单 IN_REWORK + 进度初始化）

    # ─── 进度记录 ───
    recordReworkProgress(rework_order_id, sn, new_status):
      # → ReworkProgressService.accrueSnReworked / accrueSnScrapped
      #   若 pending_qty=0 → 同事务 order.completeBatchRework() → PENDING_REENTRY

    # ─── 批量返工完成 ───
    completeBatchRework(rework_order_id):
      # 前置：pending_qty=0（INV-04）
      # → order.completeBatchRework() → PENDING_REENTRY

    # ─── 放行 ───
    releaseBatchRework(rework_order_id):
      # → ReentryPointService.determineAndRelease
      #   → order.releaseBatchRework(reentry_point) → BatchReworkOrderReleased → RELEASED

    # ─── 完成工单 ───
    completeReworkOrder(rework_order_id, completed_qty):
      # 前置：RELEASED + 过点执行回传 BatchReworkReentered（INV-07）
      # → order.completeReworkOrder(completed_qty) → BatchReworkOrderCompleted → COMPLETED

    # ─── 报废建议与审批 ───
    recommendBatchScrap(rework_order_id, reason, scrap_sn_list[], diagnosis_summary):
      # → ScrapDecisionService.recommendBatchScrap
    approveBatchScrap(rework_order_id):
      # → ScrapDecisionService.onScrapApproved
    rejectScrapRework(rework_order_id):
      # → ScrapDecisionService.onScrapRejected
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 生成返工工单 | 单聚合事务 | `BatchReworkOrderService` | `BatchReworkOrderCreated` | `commandId`；`source_event_id`/(source_work_order_id, operator, 窗口) 去重（INV-02） |
| 分配返工路线 | 单聚合事务 | `ReworkRouteService` | `ReworkRouteAssigned` | `commandId`；`version` |
| 开始返工 | 工单 + 进度同事务 | `BatchReworkOrderService` | `ReworkProgressInitialized` | `commandId` |
| 记录返工进度 | 进度 + 工单同事务 | `ReworkProgressService` | `ReworkProgressAccrued`（+工单内部推进 PENDING_REENTRY） | `commandId`；`(sn, version)` |
| 完成批量返工 | 单聚合事务 | `BatchReworkOrder.completeBatchRework` | 状态内部推进 PENDING_REENTRY | `commandId` |
| 放行批量返工 | 单聚合事务 | `ReentryPointService` | `BatchReworkOrderReleased` | `commandId`；`version` |
| 完成返工工单 | 单聚合事务 | `BatchReworkOrder.completeReworkOrder` | `BatchReworkOrderCompleted` | `commandId`；终态拒收（INV-05） |
| 建议批量报废 | 单聚合事务 | `ScrapDecisionService` | `BatchScrapRecommended` | `commandId` |
| 批准/驳回批量报废 | 单聚合事务 | `ScrapDecisionService` | `BatchReworkOrderScrapped` / 状态回退 IN_REWORK | `commandId`；终态拒收 |

### 4.2 ReworkEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.6 消费策略逐条迁入）。

```yaml
ReworkEventConsumeAppService:
  订阅主题与处理:
    # 质量上下文（🔴 主题前缀待对齐）
    (批量质量异常信号):
      → BatchReworkOrderService.onQualityBatchDefectDetected
      # 幂等：source_event_id 去重表（INV-02）

    # 工程变更（🔴 来源未定义）
    (ECN 返工触发):
      → BatchReworkOrderService.onEcnReworkTriggered
      # 幂等：source_event_id 去重表（INV-02）

    # 过点执行上下文（主题前缀 mes.*）
    mes.reentry.rejected (ReentryRejected, reason=InvalidReentryPoint):
      → ReentryPointService.reevaluateOnRejected
      # 幂等：rework_order_id 去重（INV-06）

    mes.reentry.reworked (BatchReworkReentered, 🔴 是否回传统一):
      → ReworkCommandAppService.completeReworkOrder
      # 幂等：rework_order_id 去重（INV-07）

    # 返修上下文（🔴 是否消费）
    rework.task.completed (UnitReworkCompleted):
      → ReworkProgressService.accrueSnReworked
      # 幂等：(rework_order_id, sn) 去重
      # 🔴 是否消费返修完成事件驱动本上下文进度累计待确认
```

> **上下文外事件只消费不重发**（INV-11）：本上下文将订阅事件包装为 `BatchReworkOrderCreated` / `BatchReworkOrderCompleted` 等本上下文语义事件后发布，下游可凭主题前缀区分来源。

> **主题命名约定**：本域**对外发布**使用 `brework.*` 前缀（**严禁与 `rework.*` / `repair.*` 混用**）。本域**订阅**使用各发布域实际前缀（`mes.*`/`rework.*`/`quality.*`），不重写。

### 4.3 ReworkQueryAppService（查询应用服务）

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。

### 6.1 返工工单不变式

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-01 | 一张返工工单覆盖一批 SN（`sn_list` 非空） | `BatchReworkOrder.create` 前置；`sn_list` 非空不可创建 |
| INV-02 | 同一触发信号不重复创建返工工单 | `source_event_id` 事件去重表 / `(source_work_order_id, operator, 时间窗口)` 去重，由 `BatchReworkOrderService` + 事件去重表保证（非聚合根自身可校验） |
| INV-03 | 返工工艺路线必须从工艺管理上下文 REST 查询获得，本上下文不缓存路线 | `ReworkRouteService.assignRoute` 前置；每次引用实时查询，避免配置漂移（INV-13） |
| INV-05 | `COMPLETED` / `SCRAPPED` 为终态，之后任何事件均拒收 | `BatchReworkOrderState` 状态机；终态不可逆 |
| INV-09 | 返工工艺路线版本在 `ROUTE_ASSIGNED` 时锁定（`rework_route_version`），后续进度跟踪与再入点判定基于锁定版本 | `ReworkRouteRef` 值对象不可变；`ReworkRouteService.assignRoute` 锁定版本 |
| INV-10 | 状态单向流转，仅 `ReevaluateReentryPoint` / `RejectScrapRework` 允许回退 | `BatchReworkOrderState` 状态机；可逆边仅再入点被拒回退重判 / 报废驳回回退返工 |

### 6.2 返工进度不变式

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-04 | `pending_qty=0` 才能从 `IN_REWORK` 转 `PENDING_REENTRY`（所有待返工 SN 已终态：返工或报废）；`reworked_qty + scrapped_qty + pending_qty = total_qty` | `ReworkProgress` 一致性边界；`ReworkProgressService` 在 `pending_qty=0` 时编排工单 `completeBatchRework()` |

### 6.3 再入点不变式

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-06 | 再入点必须来自工艺管理上下文的返工工艺路线配置（或默认回退）；`reeval_count` 超阈值（3）则升级人工，不再自动重判 | `ReentryPointService.reevaluateOnRejected` 阈值判定；`ReentryPointExhausted` 升级人工处理 |

### 6.4 跨上下文协作与一致性不变式

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-07 | 再入点合法性校验归过点执行上下文——本上下文**只判定**再入点，过点执行上下文**校验** `reentry_point` 是否在 routeVersion 合法步序内；过点执行回传 `BatchReworkReentered` 驱动 `RELEASED→COMPLETED`（🔴 是否回传统一） | 跨上下文，"判定"与"校验"职责分离；本上下文发布 `brework.order.released` 携带 `reentry_point`，过点执行校验合法性 |
| INV-08 | 本上下文不直接扣减 `WorkOrderProgress`（口径归过点执行）——返工完成再入后，过点执行上下文按自身口径将再入放行的 SN 计入 `reworked_qty` | 跨上下文，进度口径不重叠；本上下文只跟踪返工工单维度进度，不重复过点执行的工单进度累计 |
| INV-11 | 上下文外事件只消费不重发——本上下文将订阅事件包装为本上下文语义事件后发布，下游凭主题前缀区分来源 | `ReworkEventConsumeAppService` 包装发布；主题前缀 `brework.*` vs `mes.*`/`rework.*`/`quality.*` |
| INV-12 | 批量报废与单件报废/设备报废不混淆——事件名区分（`BatchReworkOrderScrapped` vs `UnitScrappedAfterRework` vs `ScrapRecommendation`）+ 主题前缀区分（`brework.order.scrapped` vs `rework.task.scrapped` vs `repair.scrap.recommendation`）+ 消费方区分 | 跨上下文，三种报废语义完全不同，**严禁混用** |
| INV-13 | 返工工艺路线一致性——本上下文 REST 查询工艺管理上下文为权威源，本地不缓存路线（每次引用实时查询，避免配置漂移）；`rework_route_version` 在 `ROUTE_ASSIGNED` 时锁定 | 跨上下文，由 `ReworkRouteService` REST 实时查询保证；与过点执行上下文 INV-09 版本锁定模式同构 |
| INV-14 | 上下文外事件消费幂等——`consumed_event` 表 + 业务键去重（INV-02/INV-06/INV-07 的通用机制） | 各外部事件按既定去重键幂等消费，由 `consumed_event` 表保证 |

## 7. 对外契约（发布主题）

下游消费方只看以下投影，不直接读本上下文聚合：

| 主题 | 事件 | 主消费方 |
|------|------|----------|
| `brework.order.created` | BatchReworkOrderCreated(rework_order_id, source_work_order_id, sn_list[], rework_route_id, reentry_point, reason) | 在制品追踪上下文（WIP 标记离线返工）、数据应用上下文（返工统计） |
| `brework.order.released` | BatchReworkOrderReleased(rework_order_id, reentry_point, sn_list[]) | **过点执行上下文**（批量再入校验 + RoutingProgress 推进, INV-07） |
| `brework.order.completed` | BatchReworkOrderCompleted(rework_order_id, completed_qty) | 数据应用上下文（返工工单完成统计、良率分析） |
| `brework.order.scrapped` | BatchReworkOrderScrapped(rework_order_id, scrap_sn_list[], scrap_reason) | **过点执行上下文**（批量 SN 已报废，不再回主线）、**在制品追踪上下文**（WIP 标记报废）、数据应用上下文（良率统计） |
| `brework.order.progress` | ReworkProgressAccrued(rework_order_id, reworked_qty, pending_qty, scrapped_qty) | 数据应用上下文（返工进度看板） |
| `brework.order.scrap_recommended` | BatchScrapRecommended(rework_order_id, scrap_sn_list[], reason, diagnosis_summary) | 批量报废审批方（🔴 审批流归属待确认） |

**主题命名约定**：
- 本上下文**对外发布**：`brework.<aggregate>.<event-class>`（`brework` = batch rework 缩写），表示"已经过批量返工语义解释"。
- **严禁与单件返修上下文的 `rework` 前缀、设备管理服务维修上下文的 `repair` 前缀混用**——三者事件名、主题前缀、消费方均不同：
  - 批量报废：`brework.order.scrapped`，消费方是过点执行上下文 + 在制品追踪上下文
  - 单件报废：`rework.task.scrapped`，消费方是过点执行上下文 + 在制品追踪上下文
  - 设备报废建议：`repair.scrap.recommendation`，消费方是设备工装台账上下文
- 本上下文**订阅**：使用各发布限界上下文自己的前缀，不重写——`mes.*`（过点执行上下文）、工艺管理上下文（`process.*`，REST 查询为主）、质量上下文（🔴 前缀待对齐）、返修上下文（`rework.*`，🔴 是否消费）。

> 🔴 **热点：制造资源服务各上下文的主题前缀**——工艺管理上下文与质量上下文的事件风暴尚未编写，其主题前缀（建议 `process.*` / `quality.*`）待制造资源服务限界上下文事件风暴落地后对齐。本上下文对工艺管理上下文以 REST 查询为主，对质量上下文以事件订阅（批量异常信号）为主，前缀影响需对齐。

## 9. 领域服务与应用服务的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                           外部调用入口                                  │
│                                                                      │
│  REST/终端 ──▶ ReworkCommandAppService (应用服务)                     │
│                ├─ 单聚合操作：直接委托聚合根方法                        │
│                ├─ 跨聚合编排：委托领域服务（工单生成/路线/进度/再入点/报废）│
│                └─ 同事务推进工单状态 + 发布集成事件（outbox）            │
│                                                                      │
│  消息消费 ───▶ ReworkEventConsumeAppService (应用服务)                 │
│                └─ 翻译 mes.*/rework.*/quality.* 事件 → 委托领域服务     │
│                  （包装为本上下文语义事件后发布，INV-11）                │
│                                                                      │
│  查询请求 ───▶ ReworkQueryAppService (应用服务，读模型)                │
│                └─ 直接查询读模型投影                                    │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  BatchReworkOrderService │ ReworkRouteService │ ReworkProgressService │
│  ReentryPointService     │ ScrapDecisionService                       │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  BatchReworkOrder / ReworkProgress                                    │
│  └─ 表达业务状态、行为、不变式、领域事件；不依赖 Spring/MQ/HTTP          │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 返工与过点执行经异步事件解耦（`brework.order.released` → `mes.*` 校验），不在过点主事务中引入分布式事务
