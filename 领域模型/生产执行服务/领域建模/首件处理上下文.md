## 0. 建模总览

本域是生产执行服务下的**首件门禁子域**，是 PCBA + 整机组装混合型车间"换线 / ECN / 换料后首件放行批量生产"的权威源。核心职责是管理**首件触发与标识、首件检验流程编排、首件放行门禁判定**——即"**首件怎么识别、怎么检验、怎么放行批量生产**"；**不负责**过点判定本身（归在制品执行上下文，本上下文仅向其发布门禁信号）、不负责质量检验标准配置（归质量上下文）、不负责工艺路线定义与首件要求配置（归工艺管理上下文）、不负责在制品位置投影（归在制品执行上下文）、不负责单件返修任务（归返修上下文）。

本上下文与在制品执行上下文虽同属生产执行服务，但首件对过点的协作采用**异步事件解耦**：首件门禁放行/拦截经 `fai.article.released` / `fai.article.blocked` 事件发布，在制品执行上下文消费后执行 `EnableBatchProduction` / `EnforceFirstArticleGate`（在制品执行上下文 §2.7 消费表、§N.1 策略表已定义）；同时本上下文消费在制品执行上下文的 `mes.checkpoint.lifecycle` 跟踪首件单元过点进度以驱动检验流程步骤完成。首件检验数据来源采用立场 (b)：复用在制品执行上下文的 `TestResult`（首件单元在过点时采集的测试结果即首件检验数据），本上下文消费质量上下文对该 `TestResult` 的业务判定结果，避免重复采集。

## 1. 聚合根

### 1.1 FirstArticle（首件标识）

**一致性边界**：单次首件活动的身份、触发原因、关联工单×产品×产线×路线、首件单元绑定、放行门禁状态。

**职责**：标识一次首件活动；管理 REQUESTED->INSPECTING->PENDING_DECISION->RELEASED/BLOCKED 状态机；绑定首件单元；授权回退再检。

```yaml
FirstArticle:
  # ─── 标识 ───
  first_article_id:   FirstArticleId        # 首件唯一标识（聚合根ID）

  # ─── 关联 ───
  work_order_id:      WorkOrderId           # 关联工单（INV-01）
  line_id:            LineId                # 关联产线
  route_id:           RouteId               # 关联工艺路线
  product_id:         ProductId             # 关联产品

  # ─── 触发 ───
  trigger:            FirstArticleTrigger   # LineChange / ECN / MaterialChange
  trigger_event_id:   TriggerEventId        # 触发事件ID（去重键 BIZ-01）

  # ─── 首件单元 ───
  first_article_unit_id: FirstArticleUnitId?  # 首件单元SN（异步绑定，可空 INV-13）

  # ─── 状态 ───
  state:              FirstArticleState     # REQUESTED / INSPECTING / PENDING_DECISION / RELEASED / BLOCKED
  overridden:         Boolean               # 是否经人工授权放行（INV-14）
  blocking_reason:    BlockingReason?       # BLOCKED 时必填（QualityHold / QualityGateFail）
  held_steps[]:       List<StepNo>?         # BLOCKED 时挂起的检验步骤

  # ─── 审计 ───
  requested_at:       DateTime
  released_at:        DateTime?
  blocked_at:         DateTime?
  reopened_at:        DateTime?
  reopen_count:       Integer               # 回退再检次数（INV-05）
```

**行为**：
- `request(work_order_id, line_id, route_id, product_id, trigger, trigger_event_id)` -> 发出 `FirstArticleRequested`（前置：INV-01 关联完整；BIZ-01 去重通过；-> `REQUESTED`）
- `markInspecting()` -> 状态 `REQUESTED` -> `INSPECTING`（前置：检验流程已编排且首件单元已绑定 BIZ-02；**不发独立生命周期事件**，由 `InspectionFlowComposed` + `FirstArticleUnitBound` 隐含驱动）
- `markPendingDecision()` -> 状态 `INSPECTING` -> `PENDING_DECISION`（前置：检验流程所有步骤完成 INV-06；**不发独立生命周期事件**，由 `InspectionResultsAggregated` 隐含驱动）
- `release(overridden=false)` -> 发出 `FirstArticleReleased`（前置：当前 `PENDING_DECISION` 且门禁判定 PASS INV-07；-> `RELEASED`，终态 INV-03）
- `block(blocking_reason, held_steps[])` -> 发出 `FirstArticleBlocked`（前置：当前 `PENDING_DECISION` 且门禁判定 BLOCK/HOLD；`blocking_reason` 必填；-> `BLOCKED`）
- `reopen(reopen_reason, reopened_by)` -> 发出 `InspectionReopened`（前置：当前 `BLOCKED`；人工授权 INV-05；-> `INSPECTING`；保留历史事件链；`reopen_count++`）

> **状态机隐含驱动说明**：`REQUESTED->INSPECTING`、`INSPECTING->PENDING_DECISION` 两条边不发独立首件生命周期事件，分别由 `InspectionFlowComposed`+`FirstArticleUnitBound` / `InspectionResultsAggregated` 隐含驱动（状态机内部推进，首件状态在读模型投影中反映）。这与事件风暴 §2.2.1 状态图一致。

> **RELEASED 终态（INV-03）**：`RELEASED` 之后任何事件均拒收。`BLOCKED` 可经 `ReopenInspection` 回退 `INSPECTING`（INV-05），不是终态。

> **触发去重（BIZ-01）**：同一 `(work_order_id, trigger, trigger_event_id)` 三元组只产生一次 `FirstArticle`，由 `FirstArticleTriggerService` + 事件去重表 + 数据库唯一索引 `(work_order_id, trigger, trigger_event_id)` 共同保证。ECN 触发按 `(work_order_id, route_id, ecn_id)` 去重。

### 1.2 InspectionFlow（首件检验流程编排）

**一致性边界**：单次首件检验流程的步骤编排、过点进度跟踪、步骤推进与结果汇总。

**职责**：编排首件单元在指定检验工位的检验步骤序列；消费在制品执行上下文 `mes.checkpoint.lifecycle` 跟踪首件单元过点进度；推进检验步骤；汇总检验结果驱动门禁判定。

```yaml
InspectionFlow:
  # ─── 标识 ───
  flow_id:            FlowId                # 检验流程唯一标识（聚合根ID）

  # ─── 关联 ───
  first_article_id:   FirstArticleId        # 关联首件标识
  first_article_unit_id: FirstArticleUnitId? # 首件单元SN（编排时可能为空，后续绑定）

  # ─── 检验步骤（聚合内实体）───
  steps[]:            List<InspectionStep>  # 检验步骤序列（按 step_no 排序）

  # ─── 状态 ───
  state:              InspectionFlowState   # COMPOSED / IN_PROGRESS / COMPLETED
  current_step_no:    StepNo?               # 当前进行中的步骤序号

  # ─── 审计 ───
  composed_at:        DateTime
  started_at:         DateTime?
  completed_at:       DateTime?
  version:            Integer               # 重新检验时版本号递增（🔴 见热点）
```

**行为**：
- `compose(first_article_id, inspection_steps[], first_article_unit_id?)` -> 发出 `InspectionFlowComposed`（前置：关联 `FirstArticle` 存在；`inspection_steps[]` 非空；-> `COMPOSED`）
- `startInspection()` -> 状态 `COMPOSED` -> `IN_PROGRESS`（前置：首件单元首次过点进入检验工位 INV-08；**不发独立生命周期事件**，由首条 `InspectionStepAdvanced` 隐含驱动）
- `advanceStep(step_no, station_id, sn)` -> 发出 `InspectionStepAdvanced`（前置：当前 `IN_PROGRESS`；`step_no` 为当前步骤；`sn` 匹配 `first_article_unit_id`；BIZ-03 去重）
- `aggregateResults(step_results[], aggregated_verdict, source_test_result_ids[], source_quality_verdict_ids[])` -> 发出 `InspectionResultsAggregated`（前置：所有步骤完成；末步 `CheckpointReleased` 已到达 + 质量检验结果可用；-> `COMPLETED`，终态 INV-06）

> **COMPLETED 终态（INV-06）**：`COMPLETED` 之后任何事件均拒收。重新检验（`InspectionReopened`）时若原 `InspectionFlow` 已 `COMPLETED`，则新建 `InspectionFlow` 实例（`version++`），原流程保留为历史；若未 `COMPLETED`，则续用原流程。

> **幂等与去重（BIZ-03）**：消费 `mes.checkpoint.lifecycle` 时以 `(sn, station_id, source_event_id)` 去重，避免过点事件重复投递导致检验步骤重复推进。

### 1.3 GateDecision（放行/拦截决策）

**一致性边界**：单次首件门禁判定的决策事实、判定依据与授权放行记录。

**职责**：综合检验流程结果判定 PASS / BLOCK；BLOCK 必带 `blocking_reason`；HOLD 可经人工授权放行（`OverrideGate`）；发布门禁信号到在制品执行上下文。

```yaml
GateDecision:
  # ─── 标识 ───
  decision_id:        DecisionId            # 决策唯一标识（聚合根ID）

  # ─── 关联 ───
  first_article_id:   FirstArticleId        # 关联首件标识
  flow_id:            FlowId                # 关联检验流程
  work_order_id:      WorkOrderId           # 关联工单

  # ─── 判定 ───
  verdict:            GateVerdict           # PASS / BLOCK / HOLD
  blocking_reason:    BlockingReason?       # BLOCK/HOLD 时必填（QualityHold / QualityGateFail）
  gate_scope:         GateScope             # WORK_ORDER（固化）

  # ─── 授权放行（HOLD 场景）───
  overridden:         Boolean               # 是否经人工授权放行
  override_authorizer: String?              # 授权人（INV-14）
  override_reason:    String?               # 授权原因（INV-14）
  overridden_at:      DateTime?

  # ─── 审计 ───
  decided_at:         DateTime
```

**行为**：
- `decide(flow_id, first_article_id, work_order_id, aggregated_verdict, gate_scope=WORK_ORDER)` -> 发出 `GateDecisionMade`（前置：`InspectionResultsAggregated` 已到达；判定逻辑综合 `aggregated_verdict`；-> 按 verdict 分流）
- `releaseGate()` -> 发出 `FirstArticleReleased`（前置：`verdict=PASS` 或 `overridden=true`；-> `FirstArticle` 状态 `RELEASED`；同一 `work_order_id` 最终态只发一次 BIZ-04）
- `blockGate(blocking_reason, held_steps[])` -> 发出 `FirstArticleBlocked`（前置：`verdict=BLOCK/HOLD`；`blocking_reason` 必填；同一 `work_order_id` 最终态只发一次 BIZ-05）
- `overrideGate(override_authorizer, override_reason)` -> 发出 `FirstArticleOverridden`（前置：`verdict=HOLD`；`override_authorizer` + `override_reason` 必填 INV-14；-> `overridden=true`；-> 后续 `releaseGate()` 发布 `FirstArticleReleased(overridden=true)`）

> **门禁作用域（固化）**：`gate_scope=WORK_ORDER`（工单级），按 `work_order_id × product_id × line_id` 维度。产线级门禁会误伤并行工单，已固化为工单级。在制品执行上下文消费时按 `work_order_id` 维度解除/强制门禁。

> **HOLD vs BLOCK 区分**：`verdict=HOLD`（待人工裁决）与 `verdict=BLOCK`（明确不合格）统一走 `blockGate()` 发布 `FirstArticleBlocked`，但 `blocking_reason` 区分（`QualityHold` vs `QualityGateFail`）。HOLD 可经 `overrideGate()` 授权放行，BLOCK 需返修或重新检验后走 `ReopenInspection`。

> **门禁幂等（BIZ-04/BIZ-05）**：同一 `work_order_id` 的 `FirstArticleReleased` / `FirstArticleBlocked` 只发布一次最终态事件；状态回退后再放行的，在制品执行上下文以 `work_order_id` 去重（在制品执行上下文 §2.7 已定义）。

## 2. 值对象

### 2.1 标识值对象

```yaml
FirstArticleId:      { value: String }    # 首件唯一标识
FlowId:              { value: String }    # 检验流程唯一标识
DecisionId:          { value: String }    # 门禁决策唯一标识
WorkOrderId:         { value: String }    # 工单标识（引用工单/排产上下文，经 ACL 翻译）
LineId:              { value: String }    # 产线标识
RouteId:             { value: String }    # 工艺路线标识（引用工艺管理上下文，经 ACL 翻译）
ProductId:           { value: String }    # 产品标识（引用物料上下文，经 ACL 翻译）
FirstArticleUnitId:  { value: String }    # 首件单元SN（即首件在制品的序列号）
TriggerEventId:      { value: String }    # 触发事件ID（幂等去重键 BIZ-01）
StepNo:              Integer              # 检验步骤序号（InspectionFlow 内唯一，从 1 递增）
```

> 不可变。`WorkOrderId`/`RouteId`/`ProductId` 是上下文外引用，经防腐层（ACL）从对应上下文翻译为本上下文语义，本上下文不持有其聚合。

### 2.2 FirstArticleTrigger（首件触发原因）

```yaml
FirstArticleTrigger:
  - LineChange        # 换线触发（来源：工单/排产上下文 LineChangeRequested）
  - ECN               # 工程变更触发（来源：工艺管理上下文 EcnActivated）
  - MaterialChange    # 换料触发（来源：物料上下文 MaterialChanged）
```

> 不可变枚举。三类触发各有独立去重键（BIZ-01）：`LineChange` 按 `(work_order_id, trigger, trigger_event_id)`、`ECN` 按 `(work_order_id, route_id, ecn_id)`、`MaterialChange` 按 `(work_order_id, part_no, change_type, trigger_event_id)`。

### 2.3 FirstArticleRequest（首件请求）

```yaml
FirstArticleRequest:
  work_order_id:  WorkOrderId
  line_id:        LineId
  route_id:       RouteId
  product_id:     ProductId
  trigger:        FirstArticleTrigger
  trigger_event_id: TriggerEventId
```

> `FirstArticleTriggerService` 消费上下文外触发事件后构造，传递给 `FirstArticle.request()`。不可变值对象。

### 2.4 FirstArticleUnit（首件单元）

```yaml
FirstArticleUnit:
  first_article_unit_id: FirstArticleUnitId  # 首件单元SN
  work_order_id:         WorkOrderId
  route_id:              RouteId
  bound_at:              DateTime
```

> 首件单元 = 换线/ECN/换料后产线产出的第一件在制品单元。异步绑定：首件请求时 `first_article_unit_id` 可空，待在制品执行上下文发布该工单首件单元的首次 `CheckpointScanned` 后由 `FirstArticleUnitMatcher` 匹配并绑定（INV-13）。匹配键：`work_order_id + line_id + 产出序位=1`。

> 🔴 **热点：首件单元的产出序位识别**（事件风暴 §3）——建议立场 (a)：该工单该产线首次 `CheckpointScanned` 的 SN 即首件单元，本上下文维护"该工单该产线首件单元已绑定"标志。待与在制品执行上下文确认是否提供产出序位投影作为更权威的来源。

> 🔴 **热点：首件单元是否需在指定起点工位绑定**（事件风暴 §3）——建议立场：路线起点工位，避免中途绑定导致前序检验步骤缺失。待与工艺管理上下文确认路线起点工位的配置。

### 2.5 InspectionStep（检验步骤·聚合内实体）

```yaml
InspectionStep:
  step_no:       StepNo            # 步骤序号（InspectionFlow 内唯一）
  station_id:    StationId         # 检验工位（来自 FirstArticleRequirementCache）
  operation_id:  OperationId?      # 关联工序（来自工艺管理上下文）
  state:         InspectionStepState  # PENDING / IN_PROGRESS / COMPLETED
  advanced_at:   DateTime?         # 推进时间
  sn:            String?           # 过点时记录的首件单元SN
  result:        InspectionResult? # 该步骤检验结果（汇总后回填）
```

```yaml
InspectionStepState:
  - PENDING       # 待执行
  - IN_PROGRESS   # 首件单元已进入该工位（消费 CheckpointScanned）
  - COMPLETED     # 该步骤检验完成（消费 CheckpointReleased + 质量检验结果）
```

> `InspectionStep` 是 `InspectionFlow` 聚合内实体，不独立成聚合——生命周期完全依附于所属 `InspectionFlow`。`InspectionFlow` 编排时根据 `FirstArticleRequirementCache` 中的"首件检验工位清单"生成步骤序列。

### 2.6 InspectionResult（检验结果）

```yaml
InspectionResult:
  step_no:                  StepNo
  station_id:               StationId
  verdict:                  InspectionVerdict     # PASS / FAIL / HOLD
  source_test_result_ids[]: List<String>          # 引用的在制品执行上下文 TestResult ID
  source_quality_verdict_ids[]: List<String>      # 引用的质量上下文判定事件 ID
  recorded_at:              DateTime
```

```yaml
InspectionVerdict:
  - PASS    # 该步骤检验通过
  - FAIL    # 该步骤检验失败
  - HOLD    # 该步骤待人工裁决
```

> 首件检验数据来源采用立场 (b)：本上下文不重复采集检验数据，消费质量上下文对 `TestResult` 的业务判定结果。`source_test_result_ids[]` 与 `source_quality_verdict_ids[]` 记录数据溯源链。

> 🔴 **热点：首件检验数据来源**（事件风暴 §0）——立场 (b) 已固化：复用在制品执行上下文的 `TestResult` + 质量上下文的业务判定结果。本上下文专注"编排与门禁"，不重复建设检验执行链路。

### 2.7 GateVerdict / BlockingReason / GateScope（门禁判定值对象）

```yaml
GateVerdict:
  - PASS    # 综合判定放行
  - BLOCK   # 明确不合格，拦截
  - HOLD    # 待人工裁决（QualityHold）

BlockingReason:
  - QualityHold       # 质量待裁决（HOLD 场景）
  - QualityGateFail   # 质量门禁失败（BLOCK 场景）

GateScope:
  - WORK_ORDER        # 工单级门禁（固化）
```

> 不可变枚举。`GateScope` 当前仅 `WORK_ORDER`，固化（事件风暴 §2.4 热点立场已回填）。`BlockingReason` 区分 HOLD 与 BLOCK 语义：HOLD 可经 `OverrideGate` 授权放行，BLOCK 需返修或重新检验。

### 2.9 FirstArticleState（首件标识状态）

```yaml
FirstArticleState:
  - REQUESTED          # 已请求，待检验流程编排与首件单元绑定
  - INSPECTING         # 检验中，首件单元正在走检验流程
  - PENDING_DECISION   # 待判定，检验流程完成待门禁判定
  - RELEASED           # 已放行（终态 INV-03）
  - BLOCKED            # 已拦截（可回退 INSPECTING INV-05）
```

**状态机**：

```
                 [REQUESTED]
                      |
            检验流程编排完成 + 首件单元绑定
            (InspectionFlowComposed + FirstArticleUnitBound, BIZ-02)
                      |
                      v
            ┌──▶ [INSPECTING] ◀── 重新检验 ReopenInspection（BLOCKED 回退, INV-05）───┐
            │            │                                                           │
            │     检验流程全部步骤完成                                                 │
            │     (InspectionResultsAggregated, INV-06)                                │
            │            │                                                           │
            │            v                                                           │
            │   [PENDING_DECISION]                                                   │
            │            │                                                           │
            │     ┌──────┴───────┐                                                   │
            │     v              v                                                   │
            │   放行          拦截                                                    │
            │   ReleaseGate  BlockGate                                                │
            │   (INV-07)     (blocking_reason 必填)                                    │
            │     |              |                                                   │
            │     v              v                                                   │
            │ [RELEASED]    [BLOCKED] ────────── 重新检验 ReopenInspection ──────────┘
            │  (终态)          |                  (INV-05 人工授权)
            │                  v
            │            HOLD -> OverrideGate -> FirstArticleOverridden
            │                  -> releaseGate(overridden=true) -> RELEASED (INV-14)
            │
            └─[RELEASED] 之后: 终态, 任何事件均拒收（INV-03）
```

**不变式**：
- `REQUESTED -> INSPECTING`：检验流程已编排 + 首件单元已绑定（BIZ-02），由 `InspectionFlowComposed` + `FirstArticleUnitBound` 隐含驱动
- `INSPECTING -> PENDING_DECISION`：检验流程所有步骤完成（INV-06），由 `InspectionResultsAggregated` 隐含驱动
- `PENDING_DECISION -> RELEASED`：`ReleaseGate`，前置 `verdict=PASS` 或 `overridden=true`（INV-07）
- `PENDING_DECISION -> BLOCKED`：`BlockGate`，前置 `verdict=BLOCK/HOLD`，`blocking_reason` 必填
- `BLOCKED -> INSPECTING`：`ReopenInspection`，人工授权，`reopen_reason` + `reopened_by` 必填（INV-05）
- `RELEASED` 为终态，之后任何事件均拒收（INV-03）
- `BLOCKED` 非终态，可经 `ReopenInspection` 回退（INV-05）或经 `OverrideGate` 转 `RELEASED`（INV-14）

### 2.10 InspectionFlowState（检验流程状态）

```yaml
InspectionFlowState:
  - COMPOSED     # 已编排，待首件单元首次过点
  - IN_PROGRESS  # 检验进行中，各步骤随首件单元过点推进
  - COMPLETED    # 已完成（终态 INV-06）
```

**状态机**：

```
                 [COMPOSED]
                      |
            首件单元首次过点进入第一个检验工位
            (消费 mes.checkpoint.lifecycle: CheckpointScanned, INV-08)
                      |
                      v
            ┌──▶ [IN_PROGRESS] ──── 各检验步骤随首件单元过点推进 ────┐
            │            │                                            │
            │     所有检验步骤完成                                     │
            │     (消费 CheckpointReleased + 质量检验结果可用)          │
            │            │                                            │
            │            v                                            │
            │     [COMPLETED] ◀──────────────────────────────────────┘
            │      (终态, INV-06)
            │
            └─[COMPLETED] 之后: 终态, 任何事件均拒收
```

**不变式**：
- `COMPOSED -> IN_PROGRESS`：首件单元首次过点进入检验工位（INV-08），由首条 `InspectionStepAdvanced` 隐含驱动
- `IN_PROGRESS -> IN_PROGRESS`（推进）：`AdvanceInspectionStep`，当前检验工位过点放行且质量检验结果可用（BIZ-03 去重）
- `IN_PROGRESS -> COMPLETED`：所有检验步骤完成（INV-06），由 `InspectionResultsAggregated` 驱动
- `COMPLETED` 之后任何事件均拒收（终态 INV-06）

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 FirstArticleTriggerService（首件触发服务）

**职责**：消费三类上下文外触发事件（换线/ECN/换料），映射为首件请求；触发去重（BIZ-01）；创建 `FirstArticle` 聚合。

```yaml
FirstArticleTriggerService:
  方法:
    onLineChangeRequested(work_order_id, line_id, route_id, product_id, trigger_event_id):
      # 来源：工单/排产上下文 LineChangeRequested
      # 1. 幂等去重：(work_order_id, trigger=LineChange, trigger_event_id) 去重表（BIZ-01）
      # 2. 构造 FirstArticleRequest(trigger=LineChange, ...)
      # 3. 创建 FirstArticle -> FirstArticleRequested
      # 4. 策略：触发 ComposeInspectionFlow（委托应用服务）

    onEcnActivated(ecn_id, affected_work_orders[], affected_routes[], effective_at):
      # 来源：工艺管理上下文 EcnActivated
      # 1. 按 affected_work_orders × affected_routes 展开
      # 2. 每个 (work_order_id, route_id, ecn_id) 去重（BIZ-01）
      # 3. 逐个创建 FirstArticle(trigger=ECN, ...) -> FirstArticleRequested
      # 4. 策略：触发 ComposeInspectionFlow

    onMaterialChanged(work_order_id, line_id, part_no, change_type, trigger_event_id):
      # 来源：物料上下文 MaterialChanged
      # 1. 幂等去重：(work_order_id, part_no, change_type, trigger_event_id) 去重表（BIZ-01）
      # 2. 构造 FirstArticleRequest(trigger=MaterialChange, ...)
      # 3. 创建 FirstArticle -> FirstArticleRequested
      # 4. 策略：触发 ComposeInspectionFlow
```

> **为什么不放在聚合根内**：触发去重（BIZ-01）是跨实例不变式——需查询去重表判断同一 `(work_order_id, trigger, trigger_event_id)` 是否已存在 `FirstArticle`，单条 `FirstArticle` 聚合无权查询其它实例。三类触发来源路由（LineChange/ECN/MaterialChange）是跨上下文编排，归本服务。

> **ECN 触发展开**（BIZ-01）：ECN 影响多个工单/路线时，按 `(work_order_id, route_id, ecn_id)` 去重，每个工单×路线组合一个首件。

### 3.2 InspectionFlowService（检验流程编排服务）

**职责**：编排首件检验流程——根据 `FirstArticleRequirementCache` 生成检验步骤序列；消费在制品执行上下文 `mes.checkpoint.lifecycle` 跟踪首件单元过点进度；推进 `InspectionStep`；汇总检验结果驱动门禁判定。

```yaml
InspectionFlowService:
  方法:
    composeInspectionFlow(first_article_id, route_id, first_article_unit_id?):
      # 前置：FirstArticleRequested 已到达
      # 1. 查询 FirstArticleRequirementCache（route_id）-> inspection_stations[]
      # 2. 缓存未命中 -> 降级 REST 查询工艺管理上下文
      # 3. 生成 InspectionStep[]（按 inspection_stations[] 顺序）
      # 4. 创建 InspectionFlow -> InspectionFlowComposed
      # 5. 若 first_article_unit_id 已可用 -> 后续触发 BindFirstArticleUnit

    onCheckpointScanned(sn, work_order_id, station_id, source_event_id):
      # 来源：在制品执行上下文 mes.checkpoint.lifecycle
      # 1. 匹配 FirstArticleUnitProgress（sn = first_article_unit_id）
      # 2. 匹配失败或不在检验工位 -> 忽略
      # 3. 幂等去重：(sn, station_id, source_event_id) 去重（BIZ-03）
      # 4. 若 InspectionFlow.state=COMPOSED -> startInspection()（COMPOSED -> IN_PROGRESS，INV-08）
      # 5. 推进 InspectionStep -> InspectionStepAdvanced（PENDING -> IN_PROGRESS）

    onCheckpointReleased(sn, station_id, source_event_id):
      # 来源：在制品执行上下文 mes.checkpoint.lifecycle
      # 1. 匹配 FirstArticleUnitProgress（sn = first_article_unit_id）
      # 2. 幂等去重：(sn, station_id, source_event_id) 去重（BIZ-03）
      # 3. 推进 InspectionStep -> InspectionStepAdvanced（IN_PROGRESS -> COMPLETED）
      # 4. 若 station_id = 末步检验工位 -> 触发 AggregateInspectionResults

    aggregateResults(flow_id):
      # 前置：所有 InspectionStep COMPLETED + 质量检验结果可用
      # 1. 收集各步骤 InspectionResult（引用质量上下文判定事件）
      # 2. 综合判定 aggregated_verdict：全 PASS -> PASS；任一 FAIL -> BLOCK；任一 HOLD -> HOLD
      # 3. flow.aggregateResults(...) -> InspectionResultsAggregated -> COMPLETED（INV-06）
      # 4. 驱动 FirstArticle.markPendingDecision()（跨聚合，同事务）
      # 5. 策略：触发 GateDecisionService.decideGate
```

> **为什么不放在聚合根内**：检验流程编排需查询 `FirstArticleRequirementCache`（读模型）与降级查询工艺管理上下文（跨上下文）；过点进度跟踪需跨实例消费 `mes.checkpoint.lifecycle` 事件并按 `first_article_unit_id` 过滤；结果汇总需综合多步骤结果与质量上下文判定事件——跨聚合（`InspectionFlow` + `FirstArticle`）+ 跨上下文编排，单聚合无权推进对方状态或查询外部事件。

> **首件检验数据来源立场 (b) 已固化**：`aggregateResults` 引用的质量检验结果来自质量上下文对 `TestResult` 的业务判定事件，本上下文不重复采集检验数据。

> 🔴 **热点：质量检验结果的具体来源事件**（事件风暴 §2.3）——建议立场：消费质量上下文对首件单元 `TestResult` 的业务判定结果事件（事件名待质量上下文定义，建议 `quality.inspection.verdict`）。待与质量上下文确认是否提供独立首件检验判定事件。

### 3.3 GateDecisionService（门禁判定服务）

**职责**：综合检验流程结果判定放行/拦截；HOLD 场景人工授权放行；发布门禁信号到在制品执行上下文。

```yaml
GateDecisionService:
  方法:
    decideGate(flow_id, first_article_id, work_order_id, aggregated_verdict):
      # 前置：InspectionResultsAggregated 已到达
      # 1. 创建 GateDecision -> GateDecisionMade
      # 2. 分流：
      #    verdict=PASS -> decision.releaseGate() -> FirstArticleReleased（INV-07/BIZ-04）
      #      -> 发布 fai.article.released（在制品执行上下文 EnableBatchProduction）
      #    verdict=BLOCK/HOLD -> decision.blockGate(blocking_reason, held_steps[])
      #      -> FirstArticleBlocked（BIZ-05）
      #      -> 发布 fai.article.blocked（在制品执行上下文 EnforceFirstArticleGate）
      # 3. 同事务推进 FirstArticle 状态（PENDING_DECISION -> RELEASED/BLOCKED）

    overrideGate(decision_id, override_authorizer, override_reason):
      # 前置：GateDecision.verdict=HOLD；override_authorizer + override_reason 必填（INV-14）
      # 1. decision.overrideGate(override_authorizer, override_reason) -> FirstArticleOverridden
      # 2. decision.releaseGate() -> FirstArticleReleased(overridden=true)
      # 3. 发布 fai.article.overridden + fai.article.released
      # 4. 同事务推进 FirstArticle 状态（BLOCKED -> RELEASED, overridden=true）
```

> **为什么不放在聚合根内**：门禁判定需综合 `InspectionFlow` 的 `aggregated_verdict` 并驱动 `FirstArticle` 状态流转（跨聚合）；门禁信号发布到在制品执行上下文是跨上下文集成；`OverrideGate` 的授权逻辑跨 `GateDecision` + `FirstArticle` 两聚合。单聚合无权推进对方状态或发布跨上下文事件。

> 🔴 **热点：OverrideGate 的权限模型**（事件风暴 §2.5）——谁有权授权放行被拦截的首件？建议立场：质量工程师 + 工艺工程师双签或单签带原因，权限配置归质量上下文或独立的权限上下文（不在本上下文）。本上下文只记录授权事实（授权人 + 原因），不维护权限规则。待与质量上下文 / 权限设计确认。

### 3.4 FirstArticleUnitMatcher（首件单元匹配服务）

**职责**：异步匹配首件单元——消费在制品执行上下文 `CheckpointScanned`，按 `work_order_id + line_id + 产出序位=1` 匹配首件单元，绑定到 `FirstArticle`。

```yaml
FirstArticleUnitMatcher:
  方法:
    matchAndBind(sn, work_order_id, line_id, station_id, source_event_id):
      # 来源：在制品执行上下文 mes.checkpoint.lifecycle: CheckpointScanned
      # 1. 查询 FirstArticle：work_order_id 相同 AND line_id 相同 AND state=REQUESTED AND first_article_unit_id=null
      # 2. 匹配条件：产出序位=1（该工单该产线首次 CheckpointScanned）
      # 3. 匹配成功 -> BindFirstArticleUnit -> FirstArticleUnitBound（INV-13）
      # 4. 匹配成功但 first_article_unit_id ≠ null -> 忽略（已绑定，幂等 INV-13）
      # 5. 匹配失败 -> 忽略（非本首件工单的过点事件）
      # 6. 绑定后若检验流程已编排 -> 同事务推进 FirstArticle REQUESTED -> INSPECTING（BIZ-02）
```

> **为什么不放在聚合根内**：首件单元匹配需跨实例查询 `FirstArticle`（按 `work_order_id + line_id + first_article_unit_id=null` 条件查找）、消费在制品执行上下文 `CheckpointScanned` 事件（跨上下文）——单条 `FirstArticle` 聚合无权查询其它实例或订阅外部事件。

> **幂等（INV-13）**：同一 `FirstArticle` 只能绑定一个 `first_article_unit_id`，重复绑定事件被忽略。

> 🔴 **热点：首件单元的产出序位识别**（事件风暴 §3）——建议立场 (a)：该工单该产线首次 `CheckpointScanned` 的 SN 即首件单元，本上下文维护"该工单该产线首件单元已绑定"标志。待与在制品执行上下文确认。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与在制品执行上下文虽同属生产执行服务，但首件门禁经**异步事件解耦**（`fai.article.released` / `fai.article.blocked`），不在过点主事务中引入分布式事务。

### 4.1 FaiCommandAppService（首件命令应用服务）

**职责**：处理首件请求、检验流程编排、首件单元绑定、步骤推进、结果汇总、门禁放行/拦截、授权放行、重新检验的写操作命令（REST/移动端入口，发命令者：工艺工程师/质量工程师/产线主管）。

```yaml
FaiCommandAppService:
  方法:
    # ─── 首件触发与标识 ───
    requestFirstArticle(cmd):
      # -> FirstArticleTriggerService.onLineChangeRequested / onEcnActivated / onMaterialChanged
      # 幂等：commandId + (work_order_id, trigger, trigger_event_id) 去重（BIZ-01）

    # ─── 检验流程编排 ───
    composeInspectionFlow(first_article_id):
      # -> InspectionFlowService.composeInspectionFlow
      # 前置：FirstArticleRequested 已到达

    # ─── 首件单元绑定（人工触发，异步绑定由 FirstArticleUnitMatcher 自动完成）───
    bindFirstArticleUnit(first_article_id, first_article_unit_id):
      # -> FirstArticle.bindUnit + FirstArticleUnitBound
      # 前置：first_article_unit_id 当前为空；幂等（INV-13）

    # ─── 检验步骤推进（通常由事件消费自动驱动，人工触发为异常兜底）───
    advanceInspectionStep(flow_id, step_no):
      # -> InspectionFlow.advanceStep
      # 前置：flow IN_PROGRESS；幂等（BIZ-03）

    # ─── 结果汇总 ───
    aggregateInspectionResults(flow_id):
      # -> InspectionFlowService.aggregateResults
      # 前置：所有步骤完成 + 质量检验结果可用（INV-06）

    # ─── 门禁判定 ───
    decideGate(flow_id):
      # -> GateDecisionService.decideGate
      # 前置：InspectionResultsAggregated 已到达

    # ─── 授权放行 ───
    overrideGate(decision_id, override_authorizer, override_reason):
      # -> GateDecisionService.overrideGate
      # 前置：verdict=HOLD；override_authorizer + override_reason 必填（INV-14）

    # ─── 重新检验 ───
    reopenInspection(first_article_id, reopen_reason, reopened_by):
      # -> FirstArticle.reopen(reopen_reason, reopened_by) -> InspectionReopened（INV-05）
      # 前置：当前 BLOCKED；人工授权
      # 策略：原 InspectionFlow COMPLETED -> 新建 InspectionFlow；未 COMPLETED -> 续用
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 请求首件 | 单聚合事务 | `FirstArticleTriggerService` | `FirstArticleRequested` | `commandId`；`(work_order_id, trigger, trigger_event_id)` 去重（BIZ-01） |
| 编排检验流程 | 单聚合事务 | `InspectionFlowService` | `InspectionFlowComposed` | `commandId` |
| 绑定首件单元 | 单聚合事务 | `FirstArticleUnitMatcher` | `FirstArticleUnitBound` | `commandId`；`first_article_unit_id` 唯一（INV-13） |
| 推进检验步骤 | 单聚合事务 | `InspectionFlow.advanceStep` | `InspectionStepAdvanced` | `commandId`；`(sn, station_id, source_event_id)` 去重（BIZ-03） |
| 汇总检验结果 | 流程 + 首件同事务 | `InspectionFlowService.aggregateResults` | `InspectionResultsAggregated` | `commandId` |
| 门禁判定 | 决策 + 首件同事务 | `GateDecisionService.decideGate` | `FirstArticleReleased` / `FirstArticleBlocked` | `commandId`；`work_order_id` 最终态只发一次（BIZ-04/11） |
| 授权放行 | 决策 + 首件同事务 | `GateDecisionService.overrideGate` | `FirstArticleOverridden` + `FirstArticleReleased` | `commandId`；INV-14 |
| 重新检验 | 单聚合事务 | `FirstArticle.reopen` | `InspectionReopened` | `commandId`；INV-05 |

> **汇总检验结果 / 门禁判定的同事务边界**：`InspectionResultsAggregated` 需同事务推进 `FirstArticle` 状态 `INSPECTING->PENDING_DECISION`；`GateDecision` 需同事务推进 `FirstArticle` 状态 `PENDING_DECISION->RELEASED/BLOCKED`。用例的事务边界相应扩展为「流程 + 首件 + Outbox 同事务」/「决策 + 首件 + Outbox 同事务」。

### 4.2 FaiEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.6 消费策略逐条迁入）。

```yaml
FaiEventConsumeAppService:
  订阅主题与处理:
    # 工单/排产上下文（主题前缀待对齐）
    （LineChangeRequested）:
      -> FirstArticleTriggerService.onLineChangeRequested
      # 幂等：(work_order_id, trigger=LineChange, trigger_event_id) 去重（BIZ-01）

    # 工艺管理上下文（主题前缀 process.* / 制造资源服务约定前缀）
    process.* (EcnActivated):
      -> FirstArticleTriggerService.onEcnActivated
      # 幂等：(work_order_id, route_id, ecn_id) 去重（BIZ-01）
    process.* (首件检验工位清单配置变更):
      -> RefreshFirstArticleRequirementCache
      # 幂等：route_id + version 去重

    # 物料上下文（主题前缀待对齐）
    （MaterialChanged）:
      -> FirstArticleTriggerService.onMaterialChanged
      # 幂等：(work_order_id, part_no, change_type, trigger_event_id) 去重（BIZ-01）

    # 在制品执行上下文（主题前缀 mes.*）
    mes.checkpoint.lifecycle (CheckpointScanned):
      -> FirstArticleUnitMatcher.matchAndBind（首次匹配绑定）
      -> InspectionFlowService.onCheckpointScanned（检验步骤推进）
      # 幂等：(sn, station_id, source_event_id) 去重（BIZ-03/INV-13）
    mes.checkpoint.lifecycle (CheckpointReleased):
      -> InspectionFlowService.onCheckpointReleased（步骤推进/末步汇总）
      # 幂等：(sn, station_id, source_event_id) 去重（BIZ-03）
    mes.routing.progress (RoutingProgressed):
      -> 更新 FirstArticleUnitProgress 投影（不触发命令）

    # 质量上下文（主题前缀 quality.* / 制造资源服务约定前缀）
    quality.* (质量检验结果事件，事件名待对齐):
      -> 供 InspectionFlowService.aggregateResults 引用
      # 幂等：(sn, station_id, verdict_event_id) 去重

      -> RefreshInspectionStandardCache
      # 幂等：standard_id + version 去重
```

> **上下文外事件只消费不重发**（INV-CX-01）：本上下文将订阅事件包装为本上下文语义事件（`FirstArticleRequested` / `InspectionStepAdvanced` / `FirstArticleUnitBound` 等）后发布，下游凭主题前缀 `fai.*` 区分来源。

> **主题命名约定**：本域**对外发布**使用 `fai.*` 前缀（`fai` = first article inspection 缩写）。本域**订阅**使用各发布域实际前缀（`mes.*`/`process.*`/`quality.*`/工单排产上下文/物料上下文前缀），不重写。

> 🔴 **热点：换线/ECN/换料触发事件的具体事件名与主题**（事件风暴 §2.6）——工单/排产上下文、工艺管理上下文、物料上下文的事件风暴尚未编写，其触发首件的具体事件名与主题前缀待对齐。本上下文按抽象引用，前缀以各上下文最终约定为准。

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 首件处理上下文](../事件风暴/首件处理上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 FirstArticle（首件标识）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-01 | 必须关联工单 × 产品 × 产线 × 路线 | `FirstArticle.request` 前置校验 |
| INV-03 | `RELEASED` 为终态，之后任何事件均拒收 | `FirstArticleState` 状态机 |
| INV-05 | `BLOCKED` 回退需人工授权——`ReopenInspection` 必须带 `reopen_reason` + `reopened_by` | `FirstArticle.reopen` 前置校验 |
| INV-13 | 同一 `FirstArticle` 只能绑定一个 `first_article_unit_id`，重复绑定被忽略 | `FirstArticleUnitMatcher` + `FirstArticle.first_article_unit_id` 唯一 |

#### 6.1.2 InspectionFlow（首件检验流程编排）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-06 | `COMPLETED` 为终态，之后任何事件均拒收；COMPLETED 需所有检验步骤完成 | `InspectionFlowState` 状态机 + `InspectionFlow.aggregateResults` 前置 |
| INV-08 | 进入 `IN_PROGRESS` 需首件单元首次过点进入检验工位 | `InspectionFlow.startInspection` 前置：消费 `CheckpointScanned` 且 `station_id` ∈ `inspection_steps[]` |

#### 6.1.3 GateDecision（放行/拦截决策）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-07 | 放行需检验结果综合判定 PASS | `GateDecision.releaseGate` 前置：`verdict=PASS` 或 `overridden=true` |
| INV-14 | `OverrideGate` 必带 `override_authorizer` + `override_reason` | `GateDecision.overrideGate` 前置校验 |

### 6.2 业务不变式（Business Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| BIZ-01 | FirstArticle | 触发去重——同一 `(work_order_id, trigger, trigger_event_id)` 只产生一次 `FirstArticleRequested`；ECN 按 `(work_order_id, route_id, ecn_id)` 去重 | 跨实例，由 `FirstArticleTriggerService` + 事件去重表 + 数据库唯一索引 `(work_order_id, trigger, trigger_event_id)` 共同保证（**禁止挂聚合根**） |
| BIZ-02 | FirstArticle, InspectionFlow | 进入 `INSPECTING` 前检验流程必须已编排且首件单元已绑定 | 跨聚合（FirstArticle + InspectionFlow），由 `FirstArticle.markInspecting` 前置 `InspectionFlowComposed` + `FirstArticleUnitBound` 均已到达（**禁止挂聚合根**） |
| BIZ-03 | InspectionFlow | 消费过点事件以 `(sn, station_id, source_event_id)` 去重，避免检验步骤重复推进 | 由 `InspectionFlowService` + `consumed_event` 去重表保证（**禁止挂聚合根**） |
| BIZ-04 | GateDecision | `FirstArticleReleased` 同一 `work_order_id` 最终态只发一次 | 跨实例，由 `GateDecisionService` + `work_order_id` 去重保证；在制品执行上下文消费侧 `work_order_id` 去重（在制品执行上下文 §2.7）（**禁止挂聚合根**） |
| BIZ-05 | GateDecision | `FirstArticleBlocked` 同一 `work_order_id` 最终态只发一次；BLOCK 必带 `blocking_reason` | 跨实例，同上（**禁止挂聚合根**） |
| BIZ-06 | FirstArticle, InspectionFlow | 重新检验时原 `InspectionFlow` 已 `COMPLETED` 则新建、未 `COMPLETED` 则续用——保证一个 `FirstArticle` 关联多个 `InspectionFlow` 版本时历史可追溯 | 跨聚合（FirstArticle + InspectionFlow），由 `FaiCommandAppService.reopenInspection` 编排逻辑保证（**禁止挂聚合根**） |

### 6.3 跨上下文不变式（Cross-Context Invariants）

| 编号 | 涉及聚合根 | 不变式 | 说明 |
|------|-----------|--------|------|
| INV-CX-01 | FirstArticle（本），在制品执行上下文等 | 上下文外事件只消费不重发——本上下文将订阅事件包装为本上下文语义事件后发布，下游凭主题前缀 `fai.*` 区分来源 | 跨上下文，由 `FaiEventConsumeAppService` 包装发布保证；主题前缀 `fai.*` vs `mes.*`/`process.*`/`quality.*` |
| INV-CX-02 | FirstArticle, InspectionFlow, GateDecision（本），各外部上下文 | 上下文外事件消费幂等——`consumed_event` 表 + 业务键去重（BIZ-01/BIZ-03/INV-13 的通用机制） | 跨上下文，各外部事件按既定去重键幂等消费，由 `consumed_event` 表保证 |
| INV-CX-03 | GateDecision（本），在制品执行上下文 | 首件门禁作用域一致性——本上下文发布的 `gate_scope=WORK_ORDER` 与在制品执行上下文消费侧理解一致 | 跨上下文契约约定，由两上下文事件风暴文档共同维护 |

```
│                   -> 委托领域服务（包装为本上下文语义事件后发布，INV-CX-01）  │
│                                                                      │
│  查询请求 ───▶ FaiQueryAppService (应用服务，读模型)                   │
│                 └─ 直接查询读模型投影                                   │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           领域服务层                                    │
│  FirstArticleTriggerService │ InspectionFlowService                   │
│  GateDecisionService        │ FirstArticleUnitMatcher                 │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  FirstArticle / InspectionFlow / GateDecision                        │
│  └─ 表达业务状态、行为、不变式、领域事件；不依赖 Spring/MQ/HTTP          │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 首件门禁与在制品执行经异步事件解耦（`fai.article.released` / `fai.article.blocked`），不在过点主事务中引入分布式事务
