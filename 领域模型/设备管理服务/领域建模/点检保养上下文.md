## 0. 建模总览

本域是设备管理服务下的**预防性运维子域**，是 PCBA + 整机组装混合型车间所有"预防性运维活动"的调度权威源。核心职责是管理点检/保养的**规则定义、计划生成、任务调度、执行签核、超期预警、工装寿命判定**——即"**何时该做、谁来做、怎么做**"；**不负责**资产的身份数据与可用性状态（归设备工装台账上下文，下文简称「台账上下文」）、不负责故障维修执行（归维修上下文）、不负责计量检定（归计量检定上下文）。

阈值规则（点检周期 / 保养周期 / 寿命上限）**存本上下文**——它们是运维规则，归 `InspectionRule` / `MaintenanceRule`。台账上下文只存"当前累积值"，不做阈值判定。本上下文消费台账上下文发布的度量事件，与阈值比较后发出 `InspectionDue` / `MaintenanceDue` / `FixtureLifeExceeded` 调度信号。

## 1. 聚合根

### 1.1 InspectionRule（点检规则）

**一致性边界**：单条点检规则的定义、触发条件、检查项模板、执行角色、状态流转。

**职责**：规定"某类资产何时该做点检、检查哪些项、由谁做、参照哪个 SOP"。

```yaml
InspectionRule:
  # ─── 标识 ───
  rule_id:                RuleId                  # 规则唯一标识（聚合根ID）
  rule_kind:              RuleKind                # 固定 INSPECTION

  # ─── 目标资产（抽象引用，经 ACL 从台账上下文翻译）───
  target_asset_kind:      TargetAssetKind         # EQUIPMENT / FIXTURE / ANY
  target_classification:  TargetClassification    # 资产分类（如"回流焊""钢网"）

  # ─── 触发条件 ───
  trigger:                TriggerCondition        # 触发条件（周期/阈值）

  # ─── 检查项模板 ───
  item_templates:         List<ItemTemplate>      # 检查项模板（item_kind=CHECK）

  # ─── 执行指派 ───
  responsible_role:       ResponsibleRole         # 执行角色
  sop_references:         List<SOPReference>      # SOP 引用（仅引用 SOP ID）

  # ─── 调度参数 ───
  plan_horizon:           PlanHorizon             # 计划周期（如每周/每月）
  task_deadline:          TaskDeadline            # 任务执行时限（从计划生成起算）

  # ─── 状态 ───
  state:                  RuleState               # DRAFT / ACTIVE / SUSPENDED / OBSOLETE
```

**行为**：
- `define(target_asset_kind, target_classification, trigger, item_templates, responsible_role, sop_references, plan_horizon, task_deadline)` -> 发出 `InspectionRuleDefined`（前置：无，新建；状态进入 `DRAFT`）
- `update(changed_fields, effective_from)` -> 发出 `InspectionRuleUpdated`（前置：当前非 `OBSOLETE`；变更从下个周期生效，已生成计划/任务不受影响——快照语义 BIZ-06）
- `activate()` -> 发出 `InspectionRuleActivated`（前置：`item_templates` 非空 INV-02；`DRAFT`/`SUSPENDED` -> `ACTIVE`）
- `deactivate()` -> 发出 `InspectionRuleDeactivated`（前置：当前为 `ACTIVE`；-> `SUSPENDED`，暂停监听触发条件）
- `obsolete(replacement_rule_id?)` -> 发出 `InspectionRuleObsoleted`（前置：当前非 `OBSOLETE`；任意非终态 -> `OBSOLETE`，终态——之后任何事件均拒收 INV-03）
- `assessDue(metric_snapshot, now)` -> 返回 `DueAssessment`（纯查询，不发事件；由 `RuleTriggerEvaluationService` 调用，根据 `trigger` 判定是否到期）

> **规则与资产的关系**：规则按 `target_asset_kind + target_classification` 覆盖一类资产，不绑定单个资产 ID。资产的入账/停用/报废影响该资产是否纳入调度覆盖范围（由 `AssetRuleSyncService` 维护），不改变规则定义本身。

### 1.2 MaintenanceRule（保养规则）

**一致性边界**：单条保养规则的定义、触发条件、维护项模板、度量重置策略、寿命上限、状态流转。

**职责**：规定"某类资产何时该做保养、维护哪些项、是否重置累积度量、工装寿命上限"。

```yaml
MaintenanceRule:
  # ─── 标识 ───
  rule_id:                RuleId                  # 规则唯一标识（聚合根ID）
  rule_kind:              RuleKind                # 固定 MAINTENANCE

  # ─── 目标资产 ───
  target_asset_kind:      TargetAssetKind         # EQUIPMENT / FIXTURE / ANY
  target_classification:  TargetClassification    # 资产分类

  # ─── 触发条件 ───
  trigger:                TriggerCondition        # 触发条件（周期/运行时长/使用次数/寿命上限）

  # ─── 维护项模板 ───
  item_templates:         List<ItemTemplate>      # 维护项模板（item_kind=ACTION，可含 metric_reset）

  # ─── 执行指派 ───
  responsible_role:       ResponsibleRole
  sop_references:         List<SOPReference>

  # ─── 调度参数 ───
  plan_horizon:           PlanHorizon
  task_deadline:          TaskDeadline

  # ─── 保养专有 ───
  life_limit:             LifeLimit?              # 寿命上限（仅 target_asset_kind=FIXTURE 可设 INV-06）

  # ─── 状态 ───
  state:                  RuleState
```

**行为**：
- `define(target_asset_kind, target_classification, trigger, item_templates, responsible_role, sop_references, plan_horizon, task_deadline, life_limit?)` -> 发出 `MaintenanceRuleDefined`（前置：`item_templates` 中含 `metric_reset=true` 的项必须指定 `reset_metric_kind` INV-05；`life_limit` 仅 `target_asset_kind=FIXTURE` 可设 INV-06；状态进入 `DRAFT`）
- `update(changed_fields, effective_from)` -> 发出 `MaintenanceRuleUpdated`（前置：当前非 `OBSOLETE`；快照语义 BIZ-06）
- `activate()` -> 发出 `MaintenanceRuleActivated`（前置：`item_templates` 非空 INV-02；-> `ACTIVE`）
- `deactivate()` -> 发出 `MaintenanceRuleDeactivated`（前置：当前为 `ACTIVE`；-> `SUSPENDED`）
- `obsolete(replacement_rule_id?)` -> 发出 `MaintenanceRuleObsoleted`（前置：当前非 `OBSOLETE`；终态 INV-03）
- `assessDue(metric_snapshot, now)` -> 返回 `DueAssessment`（纯查询；判定 `RUN_HOUR_THRESHOLD` / `CYCLE_THRESHOLD` / `CALENDAR_PERIOD` 是否到期）
- `assessLife(metric_snapshot)` -> 返回 `FixtureLifeJudgement`（纯查询；仅 `target_asset_kind=FIXTURE` 且 `life_limit` 非空时有效，判定 `accumulated_cycles ≥ life_limit` / `≥ life_limit × 0.8`）

> **`life_limit` 归属**：寿命上限是运维规则（"这类工装用到多少次该报废"），不是资产属性，故存 `MaintenanceRule`。台账上下文只存 `accumulated_cycles`，不做阈值判定（对应台账上下文 INV-CX-05/INV-CX-06）。若同类工装因供应商不同有不同寿命上限，按 `target_classification` 细分多条规则。

### 1.3 InspectionPlan（点检计划）

**一致性边界**：单个周期点检计划的明细清单与完成进度。

**职责**：一次到期触发后，按规则快照生成单周期计划，承载该周期内每台待点检资产的明细。

```yaml
InspectionPlan:
  # ─── 标识 ───
  plan_id:                PlanId                  # 计划唯一标识（聚合根ID）
  plan_kind:              PlanKind                # 固定 INSPECTION

  # ─── 来源 ───
  source_rule_id:         RuleId                  # 来源规则（快照引用）
  plan_horizon:           PlanHorizon             # 计划周期（如 2026-W24）
  urgency:                Urgency                 # ROUTINE / POST_REPAIR

  # ─── 明细 ───
  plan_items:             List<PlanItem>          # 每条对应一台资产
  #   PlanItem:
  #     asset_id          : AssetId
  #     rule_id           : RuleId                # 关联 ACTIVE 规则 INV-07
  #     due_reason        : DueReason
  #     deadline          : TaskDeadline
  #     item_status       : PlanItemStatus        # PENDING / IN_PROGRESS / COMPLETED / SKIPPED / OVERDUE

  # ─── 状态 ───
  status:                 PlanStatus              # DRAFT / ACTIVE / PARTIALLY_COMPLETED / COMPLETED / OVERDUE

  # ─── 审计 ───
  generated_at:           DateTime
```

**行为**：
- `generate(source_rule_id, plan_horizon, plan_items, urgency, generated_at)` -> 发出 `InspectionPlanGenerated`（前置：每条 `plan_item.rule_id` 关联一条 `ACTIVE` 的 `InspectionRule` INV-07；`plan_items` 内 `asset_id` 不重复 BIZ-03；状态进入 `DRAFT`）
- `activate()` -> 状态 `DRAFT` -> `ACTIVE`（前置：已生成；由 `TaskSchedulingService` 在拆解任务后调用，不发独立对外事件）
- `recordItemTerminal(asset_id, item_status)` -> 更新对应 `plan_item.item_status`；状态 `ACTIVE` -> `PARTIALLY_COMPLETED`；若全部 `plan_item` 进入终态（`COMPLETED`/`SKIPPED`）-> 调用 `complete()`
- `recordItemOverdue(asset_id)` -> 标记对应 `plan_item` 为 `OVERDUE`；计划状态可转 `OVERDUE`（可逆，随任务补做恢复）
- `complete()` -> 发出 `InspectionPlanCompleted`（前置：所有 `plan_item` 终态；状态 -> `COMPLETED`，终态）

> **跨计划去重**（BIZ-03）：同一资产同一周期不重复生成计划，由 `PlanGenerationService` 查询读模型 + 数据库唯一索引 `(asset_id, rule_id, plan_horizon)` 共同保证，不挂在聚合根上。

### 1.4 MaintenancePlan（保养计划）

**一致性边界**：单个周期保养计划的明细清单与完成进度。

**职责**：一次到期触发后，按规则快照生成单周期保养计划，承载该周期内每台待保养资产明细。

```yaml
MaintenancePlan:
  # ─── 标识 ───
  plan_id:                PlanId
  plan_kind:              PlanKind                # 固定 MAINTENANCE

  # ─── 来源 ───
  source_rule_id:         RuleId
  plan_horizon:           PlanHorizon
  urgency:                Urgency                 # ROUTINE / POST_REPAIR

  # ─── 明细 ───
  plan_items:             List<PlanItem>

  # ─── 状态 ───
  status:                 PlanStatus

  # ─── 审计 ───
  generated_at:           DateTime
```

**行为**：
- `generate(source_rule_id, plan_horizon, plan_items, urgency, generated_at)` -> 发出 `MaintenancePlanGenerated`（前置：每条 `plan_item` 关联 `ACTIVE` 的 `MaintenanceRule` INV-09；`plan_items` 内 `asset_id` 不重复 BIZ-04）
- `activate()` -> `DRAFT` -> `ACTIVE`
- `recordItemTerminal(asset_id, item_status)` -> 更新明细；推进状态
- `recordItemOverdue(asset_id)` -> 标记 `OVERDUE`（可逆）
- `complete()` -> 发出 `MaintenancePlanCompleted`（前置：所有 `plan_item` 终态）

> **加急合并**（INV-CX-04）：维修上下文发布的 `MaintenanceSuggested` 到达时，若该资产已有未执行保养计划，`PlanGenerationService` 合并关联维修工单而非重复生成，由读模型查询 + `(asset_id, plan_kind, pending)` 去重保证。

### 1.5 InspectionTask（点检任务）

**一致性边界**：单台资产一次点检任务的逐项登记、签核、verdict 判定与状态流转。

**职责**：承载一次点检执行的全部事实——逐项结果、证据、签核、整体 verdict。

```yaml
InspectionTask:
  # ─── 标识 ───
  task_id:                TaskId                  # 任务唯一标识（聚合根ID）
  task_kind:              TaskKind                # 固定 INSPECTION

  # ─── 来源 ───
  plan_id:                PlanId                  # 来源计划
  plan_item_ref:          PlanItemRef             # 关联计划的 plan_item（INV-11）
  source_repair_order_id: String?                 # 加急任务关联的维修工单（POST_REPAIR 时）

  # ─── 目标资产 ───
  asset_id:               AssetId
  asset_kind:             TargetAssetKind         # 设备/工装

  # ─── 执行项（从规则模板实例化，快照）───
  items:                  List<TaskItem>
  #   TaskItem:
  #     item_id           : ItemId
  #     name              : String
  #     standard          : String                # 标准/目标值
  #     result            : ItemResult?           # 执行结果（待执行时为空）
  #     evidence          : Evidence?             # 证据（照片/签名 URL）
  #     required_evidence : Boolean

  # ─── 执行指派 ───
  assignee:               Assignee                # 执行人/角色
  deadline:               TaskDeadline

  # ─── 状态 ───
  state:                  TaskState               # PENDING / IN_PROGRESS / COMPLETED / SKIPPED / OVERDUE
  verdict:                TaskVerdict?            # PASS / FAIL（签核时计算）

  # ─── 审计 ───
  started_at:             DateTime?
  completed_at:           DateTime?
  completed_by:           String?
```

**行为**：
- `create(plan_id, plan_item_ref, asset_id, asset_kind, items, assignee, deadline, source_repair_order_id?)` -> 发出 `InspectionTaskCreated`（前置：关联一个 `InspectionPlan` 的 `plan_item` INV-11；状态 -> `PENDING`）
- `start(started_by)` -> 发出 `InspectionStarted`（前置：当前为 `PENDING`；未超 `deadline` INV-21；-> `IN_PROGRESS`）
- `recordItem(item_id, verdict, measured_value, evidence)` -> 发出 `InspectionItemRecorded`（前置：当前为 `IN_PROGRESS` 或 `OVERDUE`；该 item 未登记）
- `confirm(completed_by)` -> 发出 `InspectionCompleted(verdict)`（前置：当前为 `IN_PROGRESS` 或 `OVERDUE`；所有 item 已登记结果 INV-12；verdict 计算见下；-> `COMPLETED`，终态）
- `skip(reason)` -> 发出 `InspectionSkipped`（前置：当前为 `PENDING`；`reason` 为资产停用/外转等；-> `SKIPPED`，终态——之后任何事件均拒收 INV-13）
- `markOverdue()` -> 发出 `InspectionOverdue`（前置：当前为 `PENDING` 或 `IN_PROGRESS`；过 `deadline` 未完成；-> `OVERDUE`，可逆非终态 INV-19）

> **整体 verdict 计算**（INV-20）：`confirm` 时若所有 item `verdict=PASS` 则整体 `verdict=PASS`；存在任一 `FAIL` 则整体 `verdict=FAIL`，但其他 `PASS` 项结果仍保留。`verdict=FAIL` 时由应用服务策略发布 `RepairSuggested` 到 `pm.inspection.anomaly`，由维修上下文决定是否创建维修工单——本上下文不直接创建维修工单。

> **OVERDUE 可逆**（INV-19）：`OVERDUE` 为可逆中间态，补做后可通过 `recordItem` + `confirm` 转 `COMPLETED` 签核闭环；`SKIPPED` 为终态。`OVERDUE` 状态下仍允许 `recordItem` 与 `confirm`，不允许 `start`（已超起算时机）。

### 1.6 MaintenanceTask（保养任务）

**一致性边界**：单台资产一次保养任务的逐项执行、度量重置、签核与状态流转。

**职责**：承载一次保养执行的全部事实——逐项动作、证据、是否重置度量、签核。

```yaml
MaintenanceTask:
  # ─── 标识 ───
  task_id:                TaskId
  task_kind:              TaskKind                # 固定 MAINTENANCE

  # ─── 来源 ───
  plan_id:                PlanId
  plan_item_ref:          PlanItemRef             # 关联计划的 plan_item（INV-14）
  source_repair_order_id: String?

  # ─── 目标资产 ───
  asset_id:               AssetId
  asset_kind:             TargetAssetKind

  # ─── 执行项（从规则模板实例化，快照）───
  items:                  List<TaskItem>
  #   TaskItem (保养项扩展):
  #     item_id           : ItemId
  #     name              : String
  #     standard          : String
  #     result            : ItemResult?           # action_taken: DONE/SKIPPED
  #     evidence          : Evidence?
  #     required_evidence : Boolean
  #     metric_reset      : Boolean               # 是否重置度量（来自模板）
  #     reset_metric_kind : MetricKind?           # 重置的度量类型（INV-05/INV-16）

  # ─── 执行指派 ───
  assignee:               Assignee
  deadline:               TaskDeadline

  # ─── 状态 ───
  state:                  TaskState
  metric_reset_directive: MetricResetDirective?  # 签核时的度量重置指令

  # ─── 审计 ───
  started_at:             DateTime?
  completed_at:           DateTime?
  completed_by:           String?
```

**行为**：
- `create(plan_id, plan_item_ref, asset_id, asset_kind, items, assignee, deadline, source_repair_order_id?)` -> 发出 `MaintenanceTaskCreated`（前置：关联一个 `MaintenancePlan` 的 `plan_item` INV-14；状态 -> `PENDING`）
- `start(started_by)` -> 发出 `MaintenanceStarted`（前置：当前为 `PENDING`；未超 `deadline` INV-21；-> `IN_PROGRESS`）
- `performItem(item_id, action_taken, evidence)` -> 发出 `MaintenanceItemPerformed`（前置：当前为 `IN_PROGRESS` 或 `OVERDUE`；该 item 未执行；载荷携带 `action_taken` 与 `metric_reset` 标志）
- `confirm(completed_by, metric_snapshot?, skip_metric_reset?)` -> 发出 `MaintenanceCompleted(metric_reset, reset_info)`（前置：当前为 `IN_PROGRESS` 或 `OVERDUE`；所有 item 已执行 INV-15；-> `COMPLETED`，终态）
- `skip(reason)` -> 发出 `MaintenanceSkipped`（前置：当前为 `PENDING`；-> `SKIPPED`，终态 INV-13）
- `markOverdue()` -> 发出 `MaintenanceOverdue`（前置：当前为 `PENDING` 或 `IN_PROGRESS`；过 `deadline`；-> `OVERDUE`，可逆 INV-19）

> **度量重置决策**（INV-21 / INV-16）：`metric_reset` 字段来自规则模板定义（策略归工程标准），不是执行时临时决定。`confirm` 时：
> - 若任一 `metric_reset=true` 的 item 被执行（`action_taken=DONE`）且 `skip_metric_reset=false`，则 `MaintenanceCompleted` 携带 `metric_reset=true` + `reset_metric_kind` + `reset_baseline=metric_snapshot.accumulated_value`（当前累积值快照）INV-16。
> - 执行人可在签核时标注 `skip_metric_reset=true`（如发现翻修不合格），此时 `metric_reset=false`——本上下文记录执行事实，不强制重置。
> - `metric_snapshot` 由应用服务经 ACL 从台账上下文度量快照读取后传入，聚合根不直接访问台账上下文。
> - 事件发布到 `pm.maintenance.completed`，台账上下文消费后 `ResetMetricBaseline` -> 发布 `MetricBaselineReset`，本上下文 `MetricBaselineSyncService` 据此刷新缓存基准。

### 2.3 RuleState（规则状态）

```yaml
RuleState:
  - DRAFT       # 已定义，待激活
  - ACTIVE      # 已激活，监听触发条件
  - SUSPENDED   # 暂停监听
  - OBSOLETE    # 废弃（终态）
```

**状态机**：

```
              Define（设备工程师/工艺工程师，前置：无）
                |
                v
            +--------+   Activate（前置：item_templates 非空）    +--------+
            | DRAFT  |-------------------------------------------->| ACTIVE |
            +--------+                                              +--------+
                |                                                        |  ^
                |                                          Deactivate   |  | Activate
                |                                                       v  |
                |                                                  +------------+
                |                                                  | SUSPENDED  |
                |                                                  +------------+
                |
                |  Obsolete（终态——之后任何事件均拒收）
                v
            +----------+
            | OBSOLETE |
            +----------+
```

**不变式**：
- `DRAFT -> ACTIVE`：前置 `item_templates` 非空（INV-02）
- `ACTIVE ⇄ SUSPENDED`：可逆，`ActivateRule` / `DeactivateRule`
- 任意非终态 -> `OBSOLETE`：终态，之后任何事件均拒收（INV-03）

### 2.4 TaskState（任务状态）

```yaml
TaskState:
  - PENDING       # 待执行
  - IN_PROGRESS   # 执行中
  - COMPLETED     # 已完成（终态）
  - SKIPPED       # 已跳过（终态）
  - OVERDUE       # 已超期（可逆非终态）
```

**状态机**：

```
   Create（调度引擎，前置：对应 Plan 已生成）
     |
     v
 +---------+  Start（前置：未超 deadline）   +-------------+
 | PENDING |----------------------------->| IN_PROGRESS |
 +---------+                              +-------------+
     |                                          |
     | Skip（资产停用/外转）                       | Confirm（前置：所有 item 已登记）
     |                                          |
     v                                          v
 +---------+                              +------------+
 | SKIPPED |                              | COMPLETED  | 终态——之后任何事件均拒收
 +---------+                              +------------+
  终态——之后                                   ^
  任何事件均拒收                                |
                                              | Confirm（前置：所有 item 已登记，补做后签核闭环）
                                              |
 +---------+                                  |
 | OVERDUE |----------------------------------+
 +---------+
  可逆（非终态，补做后 Confirm 转 COMPLETED）

  PENDING / IN_PROGRESS 过 deadline 未完成 -> MarkOverdue（定时扫描策略）
```

**不变式**：
- `PENDING -> IN_PROGRESS`：`Start*`，前置未超 `deadline`（INV-21）
- `IN_PROGRESS / OVERDUE -> COMPLETED`：`Confirm*`，前置所有 item 已登记/执行（INV-12 / INV-15）
- `PENDING -> SKIPPED`：`SkipTask(reason)`，终态（INV-13 / INV-19）
- `PENDING / IN_PROGRESS -> OVERDUE`：`Mark*Overdue`，可逆（INV-19）
- `OVERDUE -> COMPLETED`：`Confirm*`，补做后签核闭环（INV-19）

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 RuleTriggerEvaluationService（规则触发判定服务）

**职责**：消费台账上下文度量事件与内部日历定时器，评估规则触发条件，发出 `InspectionDue` / `MaintenanceDue` / `FixtureLifeExceeded` / `FixtureLifeWarning` 调度信号。

```yaml
RuleTriggerEvaluationService:
  方法:
    onEquipmentRunHourAccrued(asset_id, accumulated_run_hours, reset_baseline):
      # 1. 加载该资产匹配的 ACTIVE MaintenanceRule（trigger=RUN_HOUR_THRESHOLD）
      # 2. 构造 MetricSnapshot，调用 rule.assessDue(snapshot, now)
      # 3. 若 is_due -> 发出 MaintenanceDue(asset_id, rule_id, due_reason)
      #    幂等：按 (asset_id, rule_id, accumulated_run_hours) 去重，重复值不重复触发（INV-CX-05）

    onFixtureCycleAccrued(fixture_id, accumulated_cycles, reset_baseline):
      # 1. 加载该工装匹配的 ACTIVE 规则（CYCLE_THRESHOLD / LIFE_UPPER_LIMIT）
      # 2. 对 CYCLE_THRESHOLD 规则 -> rule.assessDue -> MaintenanceDue
      # 3. 对 LIFE_UPPER_LIMIT 规则 -> rule.assessLife：
      #      EXCEEDED -> FixtureLifeExceeded（+ 同事务通知台账上下文 SuspendAsset）
      #      WARNING  -> FixtureLifeWarning
      #    幂等：FixtureLifeExceeded 与 MaintenanceDue(LIFE_UPPER_LIMIT) 由事件去重表
      #          (fixture_id, accumulated_cycles, life_limit) 保证不重复发布（BIZ-05）

    onCalendarTick(now):
      # 扫描 ACTIVE 规则（trigger=CALENDAR_PERIOD）+ 调度覆盖范围内的资产清单
      # 距上次执行达周期 -> InspectionDue / MaintenanceDue
      # 幂等：按 (asset_id, rule_id, plan_horizon) 去重

    assessAndEmit(rule, metric_snapshot, now):
      # 内部统一入口：调用 rule.assessDue / rule.assessLife，去重后发出事件
```

> **为什么不放在聚合根内**：触发判定需读取规则聚合 + 外部度量快照（`MetricSnapshot`，来自台账上下文）+ 调度覆盖范围内的资产清单（跨聚合 / 跨上下文）。单条规则无权持有全局度量与资产清单，也无法自我驱动日历定时器。阈值比较的纯逻辑下沉到 `TriggerCondition.assess` / `MaintenanceRule.assessLife`（值对象 / 聚合根内），领域服务只负责编排与去重。

> 🔴 **热点：双重触发**——一台设备可能同时绑定"日历周期点检"和"运行时长保养"两条规则，两者独立触发、独立生成计划。本服务对每条规则独立评估，不合并触发信号。待 SME 确认是否需要在同一资产上做触发去重（当前建议不合并，保留各自审计链）。

### 3.2 PlanGenerationService（计划生成服务）

**职责**：`*Due` 事件 -> 加载规则 + 匹配资产清单 -> 生成单周期计划。

```yaml
PlanGenerationService:
  方法:
    onInspectionDue(asset_id, rule_id, due_reason):
      # 1. 加载 ACTIVE InspectionRule（快照规则模板与调度参数）
      # 2. 解析该规则覆盖的资产清单（按 target_asset_kind + classification 查调度覆盖视图）
      # 3. 构造 plan_items（每台资产一条，deadline = generated_at + rule.task_deadline）
      # 4. 跨计划去重：查询读模型确认 (asset_id, rule_id, plan_horizon) 无未完成计划
      #    + 数据库唯一索引兜底（BIZ-03）
      # 5. 创建 InspectionPlan -> 发出 InspectionPlanGenerated

    onMaintenanceDue(asset_id, rule_id, due_reason):
      # 同上 -> MaintenancePlan（BIZ-04 去重）

    onMaintenanceSuggested(asset_id, repair_order_id, urgency=POST_REPAIR):
      # 维修上下文建议性事件：若该资产已有未执行保养计划 -> 合并关联维修工单（INV-CX-04）
      # 否则 -> GenerateMaintenancePlan(urgency=POST_REPAIR)
```

> **为什么不放在聚合根内**：计划生成需读取规则聚合 + 调度覆盖资产清单 + 跨计划去重校验（跨聚合 / 跨实例）。计划聚合根无权查询其它计划实例，去重由本服务 + 唯一索引保证。

> **快照语义**（BIZ-06）：计划生成时从规则快照 `item_templates` / `task_deadline` / `plan_horizon`，之后规则变更不影响已生成计划与任务。

### 3.3 TaskSchedulingService（任务调度服务）

**职责**：`*PlanGenerated` 事件 -> 拆解 `plan_items` 为任务 + 分配当班人员 + 加急合并。

```yaml
TaskSchedulingService:
  方法:
    onInspectionPlanGenerated(plan_id):
      # 1. 加载 InspectionPlan（状态 DRAFT）
      # 2. 每条 plan_item -> 实例化 TaskItem（从规则模板快照）-> 创建 InspectionTask
      # 3. 按 rule.responsible_role 匹配当班人员 -> assignee（支持后续手动改派）
      # 4. plan.activate() -> 状态 ACTIVE
      # 发出 InspectionTaskCreated（per plan_item）

    onMaintenancePlanGenerated(plan_id):
      # 同上 -> MaintenanceTask

    onInspectionRequested(asset_id, repair_order_id, urgency=POST_REPAIR):
      # 维修上下文建议性事件：若同资产已有未执行点检任务 -> 合并关联维修工单（INV-CX-04）
      # 否则 -> 新建加急 InspectionTask（urgency=POST_REPAIR）
```

> **为什么不放在聚合根内**：任务创建需读取计划聚合 + 规则角色 + 当班人员排班（跨聚合 / 跨上下文）；加急合并在读模型上判定同资产未执行任务，跨实例去重。

> 🔴 **热点：任务分配策略**——自动分配还是手动派工？建议：规则中指定 `responsible_role` -> 计划生成时自动匹配当班人员 -> 支持手动改派。工装点检/保养可能需先借出到指定区域，任务分配需考虑位置（读侧按 `issued_to.station_id` 过滤候选）。待 SME 确认是否引入排班服务依赖。

### 3.4 PlanProgressService（计划进度服务）

**职责**：任务终态/超期事件 -> 更新计划明细进度 -> 推进计划状态至 `PlanCompleted`。

```yaml
PlanProgressService:
  方法:
    onInspectionCompleted(task_id, plan_id, asset_id, verdict):
      # plan.recordItemTerminal(asset_id, COMPLETED) -> 若全部终态 -> plan.complete()
      # 发出 InspectionPlanCompleted

    onInspectionSkipped(task_id, plan_id, asset_id):
      # plan.recordItemTerminal(asset_id, SKIPPED) -> 推进状态

    onInspectionOverdue(task_id, plan_id, asset_id):
      # plan.recordItemOverdue(asset_id) -> 计划状态可转 OVERDUE（可逆，不终态）

    onMaintenanceCompleted / onMaintenanceSkipped / onMaintenanceOverdue(...):
      # 同上 -> MaintenancePlan
```

> **为什么不放在聚合根内**：计划进度需读取任务事件 + 计划聚合（跨聚合）。计划聚合无权观察任务状态，由本服务在任务事件到达时反向更新计划。

### 3.5 AssetRuleSyncService（资产规则同步服务）

**职责**：台账上下文资产生命周期事件 -> 同步调度覆盖范围与任务跳过/取消。

```yaml
AssetRuleSyncService:
  方法:
    onAssetCommissioned(asset_id, asset_kind, classification):
      # 将资产纳入调度覆盖范围（规则状态不变——规则按分类已 ACTIVE）
      # ActivateMatchingRules：确保该分类对应的 ACTIVE 规则开始覆盖此资产
      # 幂等：按 asset_id（INV-CX-05）

    onAssetSuspended(asset_id):
      # 该资产所有 PENDING 任务 -> skip(AssetSuspended)
      # 暂停调度该资产（IN_PROGRESS 任务由执行人决定是否继续，不强制中断）
      # 幂等：按 asset_id

    onAssetRetired(asset_id):
      # 取消该资产所有未执行任务（PENDING -> SKIPPED，reason=AssetRetired）
      # 将资产移出调度覆盖范围
      # 规则本身按分类保留（除非该分类已无在用资产，由工程标准决定是否 Obsolete）
      # 幂等：按 asset_id
```

> **为什么不放在聚合根内**：资产生命周期影响多规则覆盖范围 + 多任务实例，需跨聚合编排。规则是分类级模板，资产是实例——资产停用/报废影响该资产的调度范围与任务，不直接 Obsolete 分类规则。

> **语义澄清**：事件风暴 §4.1 的 `ActivateMatchingRules` / `DeactivateRules` 命名偏宽泛。本服务将其落地为"调度覆盖范围"的纳入/移出 + 资产任务的跳过/取消，规则定义本身（按分类）保持稳定。若未来出现"单资产专属规则"，可扩展为按 `asset_id` 绑定的规则实例。

### 3.6 MetricBaselineSyncService（度量基准同步服务）

**职责**：消费 `MetricBaselineReset` / `FixtureRefurbished` -> 更新本上下文缓存的 `reset_baseline` + 刷新寿命消耗视图。

```yaml
MetricBaselineSyncService:
  方法:
    onMetricBaselineReset(asset_id, metric_kind, new_baseline):
      # 更新缓存的 reset_baseline（取最新基准，INV-CX-01）
      # 触发 RuleTriggerEvaluationService 用新基准重算到期视图
      # 幂等：按 (asset_id, metric_kind) 取最新基准（INV-CX-05）

    onFixtureRefurbished(fixture_id, life_reset, accumulated_cycles):
      # 若 life_reset=true：按新 accumulated_cycles（=0）重算寿命消耗视图（INV-CX-03 偏移量非负）
      # 刷新 LifeConsumptionView，避免继续用旧累积值误判寿命超限（BIZ-05 不重复触发）
      # 幂等：按 fixture_id + 翻修序号去重（INV-CX-05）
```

> **为什么不放在聚合根内**：`reset_baseline` 缓存与 `LifeConsumptionView` 是跨规则 / 跨任务的共享读模型状态，不属于单个聚合。其一致性（INV-CX-01 / INV-CX-03）是 `RuleTriggerEvaluationService` 正确判定的前提，由本服务作为一等领域关注点维护。

> 🔴 **热点：`FixtureRefurbished` vs `FixtureCycleAccrued` 双通道**——台账上下文翻修时既重置 `accumulated_cycles=0` 又发布 `FixtureRefurbished(life_reset=true)`。本服务理论上靠 `FixtureCycleAccrued` 携带的新 `reset_baseline` 即可重算，`FixtureRefurbished` 作为显式信号用于寿命视图刷新。建议两者都消费、以 `FixtureCycleAccrued.reset_baseline` 为权威计算源，`FixtureRefurbished` 仅触发视图刷新。待 SME 确认是否冗余。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与台账上下文同属设备管理服务，点检异常、点检超期、保养超期、寿命超限等强防错阻塞由应用服务在**同一本地事务**内编排本上下文聚合与台账上下文 `AvailabilityProjection`（INV-CX-06），不依赖异步消息完成内部一致性。

### 4.1 RuleCommandAppService（规则命令应用服务）

**职责**：处理规则定义、变更、激活、停用、废弃的写操作命令（REST 入口，发命令者：设备工程师/工艺工程师）。

```yaml
RuleCommandAppService:
  方法:
    defineInspectionRule(cmd):       # -> InspectionRule.define -> 写仓储 -> Outbox
    defineMaintenanceRule(cmd):      # -> MaintenanceRule.define（校验 INV-05/INV-06）
    updateRule(rule_id, changed_fields, effective_from):
    activateRule(rule_id):           # 校验 INV-02
    deactivateRule(rule_id):
    obsoleteRule(rule_id, replacement_rule_id?):
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 定义规则 | 单聚合事务 | `InspectionRule` / `MaintenanceRule.define` | `*RuleDefined` | `commandId`；`(asset_kind, classification, trigger)` 唯一索引（BIZ-01/BIZ-02） |
| 变更规则 | 单聚合事务 | `*.update` | `*RuleUpdated` | `commandId`；version |
| 激活/停用 | 单聚合事务 | `*.activate` / `deactivate` | `*RuleActivated` / `Deactivated` | `commandId`；version |
| 废弃规则 | 单聚合事务 | `*.obsolete` | `*RuleObsoleted` | `commandId`；终态拒收（INV-03） |

### 4.2 TaskCommandAppService（任务命令应用服务）

**职责**：处理任务执行与签核的写操作命令（移动端 / REST 入口，发命令者：点检员/保养员/设备工程师），并编排与台账上下文可用性投影的同事务同步。

```yaml
TaskCommandAppService:
  方法:
    startInspection(task_id, started_by):
      # -> InspectionTask.start -> 写仓储 -> Outbox

    recordInspectionItem(task_id, item_id, verdict, measured_value, evidence):
      # -> InspectionTask.recordItem -> 写仓储 -> Outbox

    confirmInspection(task_id, completed_by):
      # 1. -> InspectionTask.confirm -> 得 InspectionCompleted(verdict)
      # 2. 同事务委托台账可用性端口：
      #      verdict=PASS -> clearBlocking(INSPECTION_ANOMALY) + recompute
      #      verdict=FAIL -> suspend(INSPECTION_ANOMALY) + markUnavailable
      # 3. 若 verdict=FAIL -> 策略发布 RepairSuggested(asset_id, failed_items) 到 pm.inspection.anomaly
      # 4. InspectionTask + AvailabilityProjection + Outbox 同事务提交（INV-CX-06）

    startMaintenance / performMaintenanceItem(...):
      # -> MaintenanceTask.start / performItem

    confirmMaintenance(task_id, completed_by, skip_metric_reset?):
      # 1. 经 ACL 读取台账上下文当前 MetricSnapshot（供 reset_baseline）
      # 2. -> MaintenanceTask.confirm(completed_by, metric_snapshot, skip_metric_reset)
      # 3. 同事务委托台账可用性端口：clearBlocking(MAINTENANCE_OVERDUE) + recompute
      # 4. 若 metric_reset=true -> MaintenanceCompleted 携带 reset_info -> 台账上下文消费后 ResetMetricBaseline
      # 5. MaintenanceTask + AvailabilityProjection + Outbox 同事务提交（INV-CX-06）

    skipTask(task_id, reason):
      # -> InspectionTask/MaintenanceTask.skip -> 写仓储 -> Outbox
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 开始任务 | 单聚合事务 | `*.start` | `*Started` | `commandId`；version |
| 登记/执行项 | 单聚合事务 | `*.recordItem` / `performItem` | `*ItemRecorded` / `ItemPerformed` | `commandId`；item 唯一 |
| 签核点检 | 任务 + 台账投影 + Outbox 同事务 | `InspectionTask.confirm` + 台账可用性端口 | `InspectionCompleted`，FAIL 时 `RepairSuggested`，可能 `AssetSuspended`/`AssetAvailabilityChanged` | `commandId`；任务终态拒收 |
| 签核保养 | 任务 + 台账投影 + Outbox 同事务 | `MaintenanceTask.confirm` + 台账可用性端口 + ACL 读 MetricSnapshot | `MaintenanceCompleted(metric_reset)`，可能 `MetricBaselineReset` | `commandId`；任务终态拒收 |
| 跳过任务 | 单聚合事务 | `*.skip` | `*Skipped` | `commandId`；终态拒收（INV-13） |

> **RepairSuggested 策略归属**：`RepairSuggested` 是对 `InspectionCompleted(FAIL)` 的单聚合内部反应式策略，由本应用服务在签核事务后发布到 `pm.inspection.anomaly`，由维修上下文决定是否创建 `RepairOrder`——本上下文不直接创建维修工单。verdict 判定（FAIL if 任一项 FAIL，INV-20）在聚合根内完成，应用服务只做集成路由。

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 点检保养上下文](../事件风暴/点检保养上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 InspectionRule / MaintenanceRule（规则聚合根共享）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-02 | 启用状态下至少 1 个 `item_template` | `activate()` 前置：`item_templates` 非空；由 `InspectionRule` / `MaintenanceRule` 聚合根行为保证 |
| INV-03 | `OBSOLETE` 后任何事件均拒收 | 规则废弃为终态，不可逆；由 `InspectionRule` / `MaintenanceRule` 聚合根状态机保证 |

#### 6.1.2 MaintenanceRule（保养规则）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-05 | 含 `metric_reset=true` 的 item 必须指定 `reset_metric_kind` | `MaintenanceRule.define` 前置校验；由 `MaintenanceRule` 聚合根行为保证 |
| INV-06 | `life_limit` 仅 `target_asset_kind=FIXTURE` + `MAINTENANCE` 规则可设 | `MaintenanceRule.define` 前置校验；由 `MaintenanceRule` 聚合根行为保证 |

#### 6.1.3 InspectionPlan（点检计划）

```

│                 └─ 委托 RuleTriggerEvaluationService / 任务聚合         │
│                                                                      │
│  消息消费 ───▶ PmEventConsumeAppService (应用服务)                     │

                              |
                              v

│                           领域服务层                                    │
│  RuleTriggerEvaluationService │ PlanGenerationService                  │
│  TaskSchedulingService        │ PlanProgressService                    │
│  AssetRuleSyncService         │ MetricBaselineSyncService              │
│  └─ 封装跨聚合规则，加载聚合，调用聚合行为，写仓储，返回领域事件           │
└──────────────────────────────────────────────────────────────────────┘
                              |
                              v
┌──────────────────────────────────────────────────────────────────────┐
│                           聚合根（领域层）                              │
│  InspectionRule / MaintenanceRule / InspectionPlan / MaintenancePlan  │
│  InspectionTask / MaintenanceTask                                     │

└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的业务规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- 同服务强防错阻塞由应用服务本地事务编排，跨服务通知经 Outbox 最终一致（INV-CX-06）
