## 0. 建模总览

本域是设备管理服务下的**纠正性运维子域**，是 PCBA + 整机组装混合型车间所有"故障修复活动"的执行权威源。核心职责是管理**故障报告受理、维修工单派工与 SLA、故障诊断、维修执行与备件消耗、维修验证与关单、升级与外协、报废建议**——即"**故障怎么修、备件怎么用、修不好怎么办**"；**不负责**资产的身份数据与可用性状态（归设备工装台账上下文，下文简称「台账上下文」）、不负责预防性点检/保养（归点检保养上下文）、不负责计量检定（归计量检定上下文）、不负责备件库存本身（归后续「备件管理上下文」，本上下文仅发布消耗事件）。

本上下文与台账上下文**虽同属设备管理服务**，但维修对台账的协作按**是否强防错阻塞**区分：修复后恢复资产（`RepairCompleted`->Reinstate）、维修不经济发起报废建议（`ScrapRecommendation`）采用**异步事件解耦**——`ReinstateAsset` 不是强防错阻塞（台账综合判定后可能因其它阻塞原因如检定超期而不恢复），异步解耦让台账保留可用性判定的唯一权威；报废建议同理只发布不执行。唯一例外是 CRITICAL 故障——CRITICAL 紧急工单创建时，应用服务同事务委托台账上下文可用性端口 `SuspendAsset(reason=CriticalFault)`（强防错本地事务同步，INV-CX-09），资产停用间接阻断生产；不再发布 `LineStoppageRequested`（当前服务无异常处理上下文）。

## 1. 聚合根

### 1.1 MalfunctionReport（故障报告）

**一致性边界**：单条故障报告的身份、来源、分级分类与确认状态。

**职责**：统一建模来自多来源（生产执行/台账通信故障/点检保养/人工）的故障信息；故障分级分类；DATA_COLLECTION 草稿的确认/误报驳回；幂等去重。

```yaml
MalfunctionReport:
  # ─── 标识 ───
  report_id:        ReportId              # 报告唯一标识（聚合根ID）

  # ─── 来源 ───
  source:           ReportSource          # PRODUCTION / DATA_COLLECTION / INSPECTION / MANUAL
  source_event_id:  SourceEventId?        # 来源事件ID（幂等去重键，如 RepairSuggested 的 task_id）

  # ─── 故障资产（抽象引用，经 ACL 从台账上下文翻译）───
  asset_id:         AssetId
  asset_kind:       AssetKind             # EQUIPMENT / FIXTURE / INSTRUMENT

  # ─── 故障描述 ───
  symptom:          String                # 故障现象描述
  severity:         Severity              # CRITICAL / HIGH / MEDIUM / LOW
  production_impact:ProductionImpact      # LINE_STOPPED / DEGRADED / NO_IMPACT
  attachments[]:    List<Evidence>        # 现场照片/视频

  # ─── 报告人 ───
  reported_by:      String
  reported_at:      DateTime

  # ─── 确认状态 ───
  state:            ReportState           # PENDING_CONFIRMATION / CONFIRMED / DISMISSED
  confirmed_by:     String?
  confirmed_at:     DateTime?
  dismiss_reason:   String?
```

**行为**：
- `report(source, asset_id, asset_kind, symptom, severity, production_impact, attachments, reported_by, source_event_id?)` -> 发出 `MalfunctionReported`（前置：幂等去重通过 BIZ-01/BIZ-02；`source=DATA_COLLECTION` -> `PENDING_CONFIRMATION`；其余来源 -> `CONFIRMED`）
- `confirm(confirmed_by)` -> 发出 `MalfunctionReportConfirmed`（前置：当前为 `PENDING_CONFIRMATION`；-> `CONFIRMED`；触发策略：故障分级 -> 创建 RepairOrder）
- `dismiss(reason)` -> 发出 `MalfunctionReportDismissed`（前置：当前为 `PENDING_CONFIRMATION`；-> `DISMISSED`，终态——之后任何事件均拒收 INV-21）

> **草稿确认流（INV-15）**：仅 `source=DATA_COLLECTION`（台账上下文 `AssetSuspended(reason=CommunicationLost)` 评估报修）生成草稿；PRODUCTION/INSPECTION/MANUAL 来源由发起方已确认需维修，`report()` 直接进入 `CONFIRMED` 并由策略创建 RepairOrder。草稿确认/驳回避免通信抖动产生大量误报工单（事件风暴 §1 热点）。

> **幂等去重（BIZ-01/BIZ-02）**：`source_event_id` 非空时按其去重；为空（人工报修）时按 `(asset_id, symptom, 时间窗口)` 去重。跨来源去重由 `MalfunctionReportService` + 事件去重表保证，不挂在聚合根上。

### 1.2 RepairOrder（维修工单）

**一致性边界**：单个维修工单的派工、SLA、状态流转、升级、外协、报废建议与关单。

**职责**：关联故障报告；承载 SLA 管控与超时升级；驱动诊断->维修->验证->关单的主轴状态机；发起报废建议；登记外协维修结果。

```yaml
RepairOrder:
  # ─── 标识 ───
  order_id:         OrderId               # 工单唯一标识（聚合根ID）

  # ─── 来源 ───
  report_id:        ReportId              # 关联故障报告（INV-02）
  asset_id:         AssetId
  asset_kind:       AssetKind

  # ─── 分级与派工 ───
  severity:         Severity              # 故障分级（来自报告）
  priority:         Priority              # 派工优先级（分级映射，INV-11）
  assignee:         String?               # 维修人员
  dispatched_at:    DateTime?             # 派工时间（SLA 响应计时起点）

  # ─── SLA ───
  sla:              Sla                   # 响应/修复时限（分级映射，INV-11）
  repair_started_at:DateTime?             # 首条 RepairAction 时间（SLA 修复计时起点）

  # ─── 升级（建模为属性，非状态——见 INV-12）───
  escalation:       Escalation            # 升级级别 + 原因（NONE/L1/L2/L3）

  # ─── 外协 ───
  external_repair:  ExternalRepairInfo?   # 外协派工信息（vendor/结果/费用/替换备件）

  # ─── 报废 ───
  scrap_application_id: String?           # 关联台账上下文报废申请ID（PENDING_SCRAP_DECISION 时）

  # ─── 状态 ───
  state:            RepairOrderState      # CREATED/DISPATCHED/DIAGNOSED/IN_REPAIR/VERIFIED/PENDING_SCRAP_DECISION/CLOSED
  close_reason:     CloseReason?          # Repaired / AssetScrapped / AssetRetired
```

**行为**：
- `open(report_id, asset_id, asset_kind, severity, priority, sla)` -> 发出 `RepairOrderCreated`（前置：关联 `CONFIRMED` 的 MalfunctionReport INV-02；-> `CREATED`）
- `dispatch(assignee, dispatched_at)` -> 发出 `RepairOrderDispatched`（前置：当前 `CREATED`；启动 SLA 响应计时；-> `DISPATCHED`）
- `markDiagnosed()` -> 状态 `DISPATCHED` -> `DIAGNOSED`（前置：当前 `DISPATCHED`；**不发独立生命周期事件**，由 `DiagnosisResultRecorded` 隐含驱动，经 `DiagnosisService` 编排）
- `startRepair()` -> 状态 `DIAGNOSED` -> `IN_REPAIR`（前置：当前 `DIAGNOSED` 且诊断 `feasibility=REPAIRABLE`；**不发独立生命周期事件**，由首条 `RepairActionPerformed` 隐含驱动，经 `RepairExecutionService` 编排）
- `markVerified()` -> 状态 `IN_REPAIR` -> `VERIFIED`（前置：当前 `IN_REPAIR`；**不发独立生命周期事件**，由 `RepairVerificationSubmitted(VERIFIED)` 隐含驱动，经 `VerificationService` 编排）
- `close(reason)` -> 发出 `RepairOrderClosed`（前置：当前 `VERIFIED` 且 `reason=Repaired`；或当前 `PENDING_SCRAP_DECISION` 且 `reason=AssetScrapped`；或任意非终态且 `reason ∈ {AssetRetired, FalseAlarm}`；-> `CLOSED`，终态 INV-03）。`reason=FalseAlarm` 须附误报说明，典型用于诊断前发现误报。若 `reason=Repaired` 同时发出 `RepairCompleted`（INV-14）
- `reopen(reason=VerificationFailed)` -> 发出 `RepairOrderReopened`（前置：当前 `IN_REPAIR`；验证 FAILED 且带原因 INV-06；-> `IN_REPAIR`，回退维修 INV-02）
- `reopenForRediagnosis()` -> 发出 `RepairOrderReopened`（前置：当前 `PENDING_SCRAP_DECISION`；台账报废驳回/撤回 INV-CX-02；-> `DIAGNOSED`，重新评估方案）
- `recommendScrap(payload)` -> 发出 `ScrapRecommendation`（前置：当前 `DIAGNOSED` 且诊断 `feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}`；-> `PENDING_SCRAP_DECISION`）
- `escalateResponse()` -> 发出 `RepairEscalated`（前置：当前 `DISPATCHED` 且响应 SLA 超时；`escalation.level` 递增，`reason=ResponseTimeout`）
- `escalateRepair()` -> 发出 `RepairEscalated`（前置：当前 `IN_REPAIR` 且修复 SLA 超时；`escalation.level` 递增，`reason=RepairTimeout`）
- `dispatchExternalRepair(vendor, estimated_completion)` -> 发出 `ExternalRepairDispatched`（前置：`escalation.level=L3` 或内部无法修复；设置 `external_repair`；-> `IN_REPAIR`）
- `recordExternalRepairResult(result, cost, parts_replaced[])` -> 发出 `ExternalRepairCompleted`（前置：`external_repair` 已派工；记录结果/费用/替换备件；进入验证阶段）

> **状态机隐含驱动说明**：`DISPATCHED->DIAGNOSED`、`DIAGNOSED->IN_REPAIR`、`IN_REPAIR->VERIFIED` 三条边不发独立工单生命周期事件，分别由 `DiagnosisResultRecorded` / 首条 `RepairActionPerformed` / `RepairVerificationSubmitted(VERIFIED)` 隐含驱动（状态机内部推进，工单状态在读模型投影中反映）。这与事件风暴 §2.2 状态图一致——事件风暴仅对 `RepairOrderCreated/Dispatched/Reopened/Closed` 命名了工单生命周期事件，中间态由相邻聚合的事件承载。

> **升级建模为属性（INV-12）**：事件风暴 §2.2 将 `[ESCALATED]` 画作状态节点，但升级后需"回到 DISPATCHED 或 IN_REPAIR"，回退目标取决于升级前阶段。为避免升级回退丢失原阶段，建模为 `escalation: Escalation` 属性（`level ≠ NONE` 表示升级中），主状态机保持 `DISPATCHED/IN_REPAIR` 不变。详见 §10 映射说明。

> **RepairCompleted 发布条件（INV-14）**：仅 `close(reason=Repaired)` 时发布 `RepairCompleted` 到 `repair.order.completed`（台账上下文 `ReinstateAsset`）；`reason=AssetScrapped/AssetRetired` 时资产已不在，不发布 `RepairCompleted`。

### 1.3 FaultDiagnosis（故障诊断）

**一致性边界**：单次故障诊断的根因、维修方案、可修复性判定。

**职责**：记录诊断结论与 `repair_feasibility`；驱动维修/报废分流；一个 RepairOrder 可多次诊断（首次诊断后升级再诊断，INV-04）。

```yaml
FaultDiagnosis:
  # ─── 标识 ───
  diagnosis_id:     DiagnosisId           # 诊断唯一标识（聚合根ID）

  # ─── 关联 ───
  order_id:         OrderId               # 关联维修工单

  # ─── 诊断结论 ───
  fault_cause:      FaultCause            # 故障原因（分类编码 + 自由描述）
  repair_plan:      String                # 维修方案
  estimated_parts[]:List<EstimatedPart>   # 预估所需备件（part_code, quantity）
  estimated_duration: Duration            # 预估维修时长
  repair_feasibility:RepairFeasibility    # REPAIRABLE / NOT_ECONOMICAL / NOT_REPAIRABLE

  # ─── 成本（供报废建议判定）───
  estimated_repair_cost: Decimal?         # 维修预估成本（NOT_ECONOMICAL 判定输入）

  # ─── 审计 ───
  started_at:       DateTime?
  diagnosed_by:     String?
  diagnosed_at:     DateTime?
```

**行为**：
- `start(order_id, started_by)` -> 发出 `DiagnosisStarted`（前置：工单当前 `DISPATCHED`；创建诊断记录）
- `recordResult(fault_cause, repair_plan, estimated_parts, estimated_duration, feasibility, estimated_repair_cost?, diagnosed_by)` -> 发出 `DiagnosisResultRecorded`（前置：当前已 `start`；每次必填 `feasibility` INV-04；经 `DiagnosisService` 编排工单 `markDiagnosed()`）

> **可修复性判定（INV-04 / 事件风暴 §2.3 热点）**：`repair_feasibility` 判定逻辑（"维修成本 ≥ 资产残值 × 阈值" 等）不在本上下文硬编码——本上下文只记录诊断结论与 `estimated_repair_cost`，阈值判定由策略引擎/工程标准执行，结论写入 `feasibility`。`REPAIRABLE` -> 进入维修执行；`NOT_ECONOMICAL/NOT_REPAIRABLE` -> `RecommendScrap`。

> **多次诊断**：升级后再诊断时新建 `FaultDiagnosis` 实例（INV-04），最新一条的 `feasibility` 驱动工单当前分流。历史诊断保留作为维修知识沉淀（供数据应用上下文 MTBF/故障分析）。

### 1.4 RepairAction（维修动作）

**一致性边界**：单个维修动作的类型、描述、备件消耗与执行证据。

**职责**：关联 `IN_REPAIR` 工单；记录维修动作；登记备件消耗并发布 `PartsConsumed`。

```yaml
RepairAction:
  # ─── 标识 ───
  action_id:        ActionId              # 动作唯一标识（聚合根ID）

  # ─── 关联 ───
  order_id:         OrderId               # 关联维修工单（INV-05）

  # ─── 动作 ───
  action_type:      ActionType            # REPLACE / REPAIR / ADJUST / CLEAN / LUBRICATE / OTHER
  description:      String                # 动作描述

  # ─── 备件消耗 ───
  parts_consumed[]: List<PartsConsumption> # 消耗的备件（part_code/name/quantity/from_location）

  # ─── 审计 ───
  performed_by:     String
  started_at:       DateTime
  completed_at:     DateTime
  evidence_urls[]:  List<String>          # 照片/视频证据
```

**行为**：
- `perform(order_id, action_type, description, parts_consumed, performed_by, evidence_urls)` -> 发出 `RepairActionPerformed`（前置：工单 `IN_REPAIR` INV-05；`parts_consumed` 中备件来自有效库位）。若 `parts_consumed` 非空，同时发出 `PartsConsumed`（一条动作可消耗多备件，按 `(action_id, part_code)` 幂等 INV-CX-04）

> **首条动作驱动 IN_REPAIR**：工单首条 `RepairAction` 由 `RepairExecutionService` 编排——若工单仍 `DIAGNOSED`，先 `order.startRepair()` 再创建 `RepairAction`，二者同事务。后续动作工单已在 `IN_REPAIR`，直接创建。

> **备件消耗实时性（事件风暴 §2.4 热点）**：采用"先领后用"——维修开始时从备件管理上下文领用（预留库存），维修完成确认消耗或退回。本上下文发布 `PartsConsumed` 事件供备件管理上下文扣减库存，不直接操作备件库存聚合。备件消耗幂等（INV-CX-04）防止重复扣减。

### 1.5 RepairVerification（维修验证）

**一致性边界**：单次维修验证的方式、结果与失败原因。

**职责**：关联有 `RepairAction` 的工单；`VERIFIED/FAILED` 分流；`FAILED` 必须有原因说明。

```yaml
RepairVerification:
  # ─── 标识 ───
  verification_id:  VerificationId        # 验证唯一标识（聚合根ID）

  # ─── 关联 ───
  order_id:         OrderId               # 关联维修工单

  # ─── 验证 ───
  method:           VerificationMethod    # MANUAL_TEST / AUTO_TEST / PRODUCTION_TRIAL / INSPECTION
  result:           VerificationResult    # VERIFIED / FAILED
  failed_reason:    String?               # FAILED 时必填（INV-06）

  # ─── 审计 ───
  verified_by:      String
  verified_at:      DateTime
  evidence_urls[]:  List<String>?
```

**行为**：
- `submit(order_id, method, result, failed_reason?, verified_by)` -> 发出 `RepairVerificationSubmitted`（前置：工单 `IN_REPAIR` 且至少一条 `RepairAction` INV-06；`result=FAILED` 时 `failed_reason` 必填 INV-06）。经 `VerificationService` 编排：`VERIFIED` -> `order.markVerified()` + `order.close(Repaired)`；`FAILED` -> `order.reopen(VerificationFailed)`

> **PRODUCTION_TRIAL 边界（事件风暴 §2.5 热点）**：试产验证需生产执行服务配合（投少量产品验证）。本上下文不直接指挥生产——当 `method=PRODUCTION_TRIAL` 时，`VerificationService` 发布 `RepairVerificationRequiresProductionTrial` 建议事件到生产执行服务，由其决定是否安排试产；验证结果待试产反馈后由设备工程师回填 `submit()`。

> **INSPECTION 联动点检**：当 `method=INSPECTION`（点检验证），`VerificationService` 发布 `InspectionRequested` 到点检保养上下文（`repair.suggestion`），由其决定是否创建点检任务；本上下文不直接创建点检任务。

### 2.1 ReportId / OrderId / DiagnosisId / ActionId / VerificationId（标识）

```yaml
ReportId:        { value: String }    # 故障报告唯一标识
```

```yaml
ReportSource:
```

```yaml

  - EQUIPMENT    # 设备
```

```yaml
  - NORMAL    # 普通（MEDIUM 映射）
  - LOW       # 低（LOW 映射）
```

> 不可变枚举。由 `Severity` 映射而来（INV-11），工单创建时确定。

### 2.7 Sla（服务等级协议）

```yaml
Sla:

  repair_deadline:   Duration    # 修复时限（开始到完成）
```

> 由 `Severity` 映射（INV-11）：CRITICAL->15min/2h、HIGH->30min/4h、MEDIUM->2h/24h、LOW->8h/72h。映射规则存配置（策略引擎），不在聚合根硬编码。工单持 `sla` 快照，创建后不受分级映射规则变更影响。


> 不可变枚举。由诊断工程师/策略引擎判定，写入 `FaultDiagnosis.repair_feasibility`。判定阈值（残值比）不在本上下文硬编码（事件风暴 §2.3 热点）。

### 2.9 PartsConsumption（备件消耗）

```yaml
PartsConsumption:
```

```yaml
EstimatedPart:
```

```yaml
VerificationMethod:
```

> 不可变枚举。`PRODUCTION_TRIAL` 触发 `RepairVerificationRequiresProductionTrial` 建议事件；`INSPECTION` 触发 `InspectionRequested` 建议事件。

```yaml
  - VERIFIED   # 验证通过
```

### 2.16 CloseReason（关单原因）

```yaml
CloseReason:
  - Repaired      # 修复完成（验证 VERIFIED）-> 发布 RepairCompleted
  - AssetScrapped # 资产已报废（报废审批通过）-> 不发布 RepairCompleted
  - AssetRetired  # 资产已退役（台账上下文 AssetRetired）-> 不发布 RepairCompleted

```

> 不可变枚举。决定是否发布 `RepairCompleted`（INV-14）——仅 `Repaired` 发布，其余三种不发布。

```yaml
ScrapRecommendationPayload:
  asset_id:               AssetId
  reason:                 ScrapReason
  diagnosis_summary:      String          # 诊断摘要

  asset_residual_value:   Decimal?        # 资产残值
```

> `ScrapRecommendation` 事件载荷。本上下文只发布建议，不执行报废（INV-CX-05）；审批与执行归台账上下文 `ScrapApplication` 聚合。

### 2.18 ReportState（报告状态）

```yaml
ReportState:
  - PENDING_CONFIRMATION   # 草稿待确认（仅 DATA_COLLECTION）
  - CONFIRMED              # 已确认（触发创建 RepairOrder）
  - DISMISSED              # 误报驳回（终态）
```

**状态机**：

```
                Report(source=DATA_COLLECTION)
                          |
                          v
                +----------------------+
                | PENDING_CONFIRMATION |
                +----------------------+
                    |              |
           Confirm  |              | Dismiss(reason)
                    v              v
                +----------+   +-----------+
                |CONFIRMED |   | DISMISSED |  终态——之后任何事件均拒收
                +----------+   +-----------+

   Report(source=PRODUCTION/INSPECTION/MANUAL) ──直接──▶ CONFIRMED
```

**不变式**：
- `PENDING_CONFIRMATION -> CONFIRMED`：`confirm()`，仅 `DATA_COLLECTION` 草稿（INV-15）
- `PENDING_CONFIRMATION -> DISMISSED`：`dismiss(reason)`，终态（INV-21）
- 非草稿来源 `report()` 直接 `CONFIRMED`
- `DISMISSED` 之后任何事件均拒收（INV-21）

### 2.19 RepairOrderState（维修工单状态）

```yaml
RepairOrderState:
  - CREATED                 # 已创建，待派工
  - DISPATCHED              # 已派工，待诊断
  - DIAGNOSED               # 已诊断，待维修/待报废决策
  - IN_REPAIR               # 维修中（含外协维修中）
  - VERIFIED                # 验证通过，待关单
  - PENDING_SCRAP_DECISION  # 待报废审批决策
  - CLOSED                  # 已关闭（终态）
```

**状态机**：

```
[CREATED] ──Dispatch──▶ [DISPATCHED] ──DiagnosisResultRecorded──▶ [DIAGNOSED]
                                                              │
                            ┌─────────────────────────────────┼─────────────────────────┐
                            │                                 │                         │
                  feasibility=REPAIRABLE             feasibility ∈ {NOT_ECONOMICAL,   │
                            │                         NOT_REPAIRABLE}                  │
                  首条 RepairActionPerformed                    │                         │
                            v                                 v                         │
                       [IN_REPAIR] ◀──reopen(FAILED)──┐  [PENDING_SCRAP_DECISION]      │
                            │  ▲                      │       │       │                 │
        RepairVerification  │  │                      │ 报废   │       │ 报废驳回/        │
        Submitted(VERIFIED) │  └──reopenForRediagnosis─┘ 通过   │       │ 撤回             │
                            v     (回 DIAGNOSED)               v       │ (回 DIAGNOSED)   │
                       [VERIFIED] ──close(Repaired)──▶ [CLOSED]        │                 │
                                                         (终态)         │                 │
                                                                        v                 │
                                                                   [CLOSED]                │
                                                                (reason=AssetScrapped)     │
                                                                                           │
   任意非终态 ──AssetRetired──▶ [CLOSED] (reason=AssetRetired) ◀──────────────────────────┘

   DISPATCHED/IN_REPAIR ──SLA 超时──▶ escalation.level++（属性变更，状态保持，INV-12）
```

**不变式**：
- `CREATED -> DISPATCHED`：`dispatch()`，前置 `CREATED`
- `DISPATCHED -> DIAGNOSED`：`markDiagnosed()`，由 `DiagnosisResultRecorded` 驱动
- `DIAGNOSED -> IN_REPAIR`：`startRepair()`，前置 `feasibility=REPAIRABLE`，由首条 `RepairActionPerformed` 驱动
- `IN_REPAIR -> VERIFIED`：`markVerified()`，由 `RepairVerificationSubmitted(VERIFIED)` 驱动
- `VERIFIED -> CLOSED`：`close(Repaired)`，同时发布 `RepairCompleted`（INV-14）
- `IN_REPAIR -> IN_REPAIR`：`reopen(VerificationFailed)`，可逆回退（INV-02）
- `DIAGNOSED -> PENDING_SCRAP_DECISION`：`recommendScrap()`，前置 `feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}`
- `PENDING_SCRAP_DECISION -> CLOSED`：`close(AssetScrapped)`，由报废审批通过驱动（INV-CX-01）
- `PENDING_SCRAP_DECISION -> DIAGNOSED`：`reopenForRediagnosis()`，由报废驳回/撤回驱动（INV-CX-02），可逆回退
- 任意非终态 -> `CLOSED(AssetRetired)`：由台账 `AssetRetired` 驱动（INV-CX-07）
- 任意非终态 -> `CLOSED(FalseAlarm)`：误报关单，须附误报说明，不发布 `RepairCompleted`（INV-14）；典型用于 `CREATED/DISPATCHED/DIAGNOSED` 阶段发现误报
- `CLOSED` 之后任何事件均拒收（终态 INV-03）
- 状态单向流转，仅 `ReopenRepairOrder` / `ReopenForRediagnosis` 允许回退（INV-02）

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。

### 3.1 MalfunctionReportService（故障报告受理服务）

**职责**：消费多来源（生产执行/台账通信故障/点检保养/人工）的故障信号，经幂等去重后创建 `MalfunctionReport`；DATA_COLLECTION 草稿的确认/驳回编排。

```yaml
MalfunctionReportService:
  方法:
    onProductionMalfunctionReported(asset_id, asset_kind, symptom, severity, production_impact, source_event_id):
      # 来源：生产执行服务 mes.* MalfunctionReported
      # 1. 幂等去重：source_event_id 去重表（BIZ-02）
      # 2. report(source=PRODUCTION, ...) -> MalfunctionReported（直接 CONFIRMED）
      # 3. 策略：severity -> priority -> 创建 RepairOrder（委托应用服务）

    onAssetSuspendedForCommunicationLost(asset_id):
      # 来源：台账上下文 eam.* AssetSuspended(reason=CommunicationLost)
      # 1. 评估是否生成故障报告（asset_id + 通信故障时间窗口去重，BIZ-01）
      # 2. report(source=DATA_COLLECTION, severity=MEDIUM, ...) -> MalfunctionReported（PENDING_CONFIRMATION 草稿）
      # 3. 不自动创建 RepairOrder，待值班工程师 confirm()

    onRepairSuggested(asset_id, task_id, symptom, severity):
      # 来源：点检保养上下文 pm.* RepairSuggested
      # 1. 幂等去重：source_event_id=task_id（BIZ-02）
      # 2. report(source=INSPECTION, ...) -> MalfunctionReported（直接 CONFIRMED，点检已确认需维修）
      # 3. 策略：创建 RepairOrder

    onManualReport(asset_id, asset_kind, symptom, severity, reported_by):
      # 来源：人工终端报修
      # 1. 幂等去重：(asset_id, symptom, 时间窗口)（BIZ-01）
      # 2. report(source=MANUAL, ...) -> MalfunctionReported（直接 CONFIRMED）
      # 3. 策略：创建 RepairOrder

    confirmReport(report_id, confirmed_by):
      # 值班工程师确认草稿 -> MalfunctionReportConfirmed -> 策略创建 RepairOrder

    dismissReport(report_id, reason):
      # 草稿误报驳回 -> MalfunctionReportDismissed（终态，不创建 RepairOrder）
```

> **为什么不放在聚合根内**：报告受理需跨实例查询去重表（`source_event_id` / `(asset_id, symptom, 时间窗口)`）、识别来源并路由创建工单策略——单条 `MalfunctionReport` 聚合无权查询其它报告实例，也无法自我驱动来源路由。幂等去重（BIZ-01/BIZ-02）是跨实例不变式，由本服务 + 事件去重表保证。

> 🔴 **热点：自动报修 vs 人工确认**（事件风暴 §1）——`AssetSuspended(CommunicationLost)` 自动生成草稿（`PENDING_CONFIRMATION`），由值班工程师确认后才创建 RepairOrder，避免通信抖动误报。已固化为 INV-15 + `ReportState` 状态机。

> **CRITICAL 资产停用策略**（INV-CX-09）：CRITICAL 报告确认后创建紧急 RepairOrder 时，应用服务同事务委托台账可用性端口 `SuspendAsset(reason=CriticalFault)`（强防错本地事务同步），确保关键故障资产立即可用性降为不可用；非 CRITICAL 不停用资产。通信故障（DATA_COLLECTION）资产已由台账停用，SuspendAsset 幂等。

### 3.2 DiagnosisService（故障诊断服务）

**职责**：编排诊断流程——创建诊断、记录结论、驱动工单 `DISPATCHED->DIAGNOSED`、按 `feasibility` 分流（REPAIRABLE 待维修 / NOT_ECONOMICAL·NOT_REPAIRABLE 发起报废建议）。

```yaml
DiagnosisService:
  方法:
    startDiagnosis(order_id, started_by):
      # 前置：工单 DISPATCHED
      # 1. 创建 FaultDiagnosis -> DiagnosisStarted
      # 2. （可联动维修知识库建议，暂缓）

    recordDiagnosisResult(order_id, fault_cause, repair_plan, estimated_parts, estimated_duration, feasibility, estimated_repair_cost?, diagnosed_by):
      # 1. 加载当前 FaultDiagnosis -> recordResult(...) -> DiagnosisResultRecorded
      # 2. 加载 RepairOrder -> order.markDiagnosed()（DISPATCHED -> DIAGNOSED，同事务）
      # 3. 分流：
      #    feasibility=REPAIRABLE -> 等待首条 RepairAction（RepairExecutionService）
      #    feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE} -> recommendScrap(order, payload)
```

> **为什么不放在聚合根内**：诊断结论记录在 `FaultDiagnosis` 聚合，但其结果是驱动 `RepairOrder` 状态流转（`DISPATCHED->DIAGNOSED`）与报废分流——跨 `FaultDiagnosis` + `RepairOrder` 两个聚合，单聚合无权推进对方状态。`feasibility` 分流策略跨聚合，归本服务编排。

> **可修复性阈值不在本上下文硬编码**（事件风暴 §2.3 热点）：本服务只记录 `estimated_repair_cost` 与 `feasibility` 结论，"维修成本 ≥ 残值 × 阈值"的判定由策略引擎/工程标准执行后传入。

### 3.3 RepairExecutionService（维修执行服务）

**职责**：编排维修动作执行——首条动作驱动工单 `DIAGNOSED->IN_REPAIR`、创建 `RepairAction`、发布备件消耗事件、登记外协维修结果。

```yaml
RepairExecutionService:
  方法:
    performRepairAction(order_id, action_type, description, parts_consumed, performed_by, evidence_urls):
      # 1. 加载 RepairOrder
      # 2. 若 order.state=DIAGNOSED -> order.startRepair()（DIAGNOSED -> IN_REPAIR，首条动作驱动）
      #    若 order.state=IN_REPAIR -> 直接创建动作
      #    否则 -> 拒收（INV-05）
      # 3. 创建 RepairAction -> RepairActionPerformed
      # 4. 若 parts_consumed 非空 -> PartsConsumed（按 (action_id, part_code) 幂等 INV-CX-04）
      # 5. 发布到 repair.parts.consumed（备件管理上下文扣减库存）
      # 6. （可选）维修中发现保养需求 -> 发布 MaintenanceSuggested 到 repair.suggestion

    dispatchExternalRepair(order_id, vendor, estimated_completion):
      # 前置：escalation.level=L3 或内部无法修复
      # 1. order.dispatchExternalRepair(vendor, estimated_completion) -> ExternalRepairDispatched
      # 2. 外协执行黑盒，等待结果回填

    recordExternalRepairResult(order_id, result, cost, parts_replaced[]):
      # 1. order.recordExternalRepairResult(...) -> ExternalRepairCompleted
      # 2. parts_replaced 仅记录追溯，不触发 PartsConsumed（INV-13）
      # 3. 进入验证阶段（VerificationService）
```

> **为什么不放在聚合根内**：首条 `RepairAction` 需先推进 `RepairOrder` 状态（跨聚合），且 `RepairAction` 与 `RepairOrder` 在不同聚合；备件消耗事件发布 + 备件管理上下文联动是跨上下文编排。单聚合无权推进对方状态或发布跨上下文事件。

> 🔴 **热点：备件消耗实时性**（事件风暴 §2.4）——采用"先领后用"：维修开始时从备件管理上下文领用（预留库存），维修完成确认消耗或退回。本服务发布 `PartsConsumed` 供备件管理上下文扣减，备件领用/退回的库存操作归备件管理上下文，本上下文不直接操作备件库存聚合。

### 3.4 VerificationService（维修验证服务）

**职责**：编排维修验证——提交验证结果、`VERIFIED` 驱动关单 + `RepairCompleted`、`FAILED` 驱动退回维修、按 `method` 发布跨上下文建议事件。

```yaml
VerificationService:
  方法:
    submitVerification(order_id, method, result, failed_reason?, verified_by):
      # 1. 前置校验：工单 IN_REPAIR 且至少一条 RepairAction（INV-06）；FAILED 必填 failed_reason
      # 2. 创建 RepairVerification -> RepairVerificationSubmitted
      # 3. 分流：
      #    result=VERIFIED -> order.markVerified() + order.close(Repaired)
      #       -> RepairOrderClosed + RepairCompleted（发布到 repair.order.completed）
      #    result=FAILED -> order.reopen(VerificationFailed) -> RepairOrderReopened（回 IN_REPAIR）
      # 4. 按 method 发布跨上下文建议事件：
      #    method=PRODUCTION_TRIAL -> RepairVerificationRequiresProductionTrial（到生产执行服务，待试产反馈后回填结果）
      #    method=INSPECTION -> InspectionRequested（到点检保养上下文，由其决定是否创建点检任务）
```

> **为什么不放在聚合根内**：验证结果需驱动 `RepairOrder` 关单/退回（跨聚合）、发布 `RepairCompleted` 集成事件、按 `method` 路由跨上下文建议——跨 `RepairVerification` + `RepairOrder` 两聚合 + 跨上下文编排。

> 🔴 **热点：PRODUCTION_TRIAL 边界**（事件风暴 §2.5）——试产验证需生产执行服务配合，本上下文不直接指挥生产。已固化为：`method=PRODUCTION_TRIAL` 时发布 `RepairVerificationRequiresProductionTrial` 建议事件，由生产执行服务决定是否安排试产，验证结果待试产反馈后回填。

### 3.5 ScrapRecommendationService（报废建议服务）

**职责**：诊断不可修复/不经济时发布 `ScrapRecommendation` 建议到台账上下文；消费台账报废审批结果驱动工单关单（通过）/退回诊断（驳回/撤回）。

```yaml
ScrapRecommendationService:
  方法:
    recommendScrap(order, diagnosis):
      # 前置：order DIAGNOSED，diagnosis.feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}
      # 1. 构造 ScrapRecommendationPayload（reason, diagnosis_summary, estimated_repair_cost, asset_residual_value）
      # 2. order.recommendScrap(payload) -> ScrapRecommendation -> PENDING_SCRAP_DECISION
      # 3. 发布到 repair.scrap.recommendation（台账上下文发起报废审批）
      # 本上下文只发布建议，不执行报废（INV-CX-05）

    onScrapApplicationApproved(order_id, application_id):
      # 来源：台账上下文 eam.asset.scrap ScrapApplicationApproved
      # 1. 幂等去重：application_id 去重表（INV-CX-01）
      # 2. order.close(AssetScrapped) -> RepairOrderClosed
      #    不发布 RepairCompleted（资产已报废，INV-14）

    onScrapApplicationRejectedOrWithdrawn(order_id, application_id):
      # 来源：台账上下文 eam.asset.scrap ScrapApplicationRejected / Withdrawn
      # 1. 幂等去重：application_id 去重表（INV-CX-02）
      # 2. order.reopenForRediagnosis() -> RepairOrderReopened -> DIAGNOSED（重新评估方案）
```

> **为什么不放在聚合根内**：报废建议需发布跨上下文集成事件、消费台账审批结果驱动工单状态流转（跨聚合 + 跨上下文），审批结果去重（INV-CX-01/INV-CX-02）是跨实例不变式，由本服务 + `application_id` 去重表保证。

> **报废审批与执行归台账上下文**（INV-CX-05）：本上下文只发布 `ScrapRecommendation` 建议，台账上下文 `ScrapApplication` 聚合负责审批与执行。本上下文工单在建议报废后进入 `PENDING_SCRAP_DECISION`，等待审批结果驱动关单/退回。

### 3.6 SlaEscalationService（SLA 监控与升级服务）

**职责**：定时扫描 SLA 超时工单，按响应/修复超时升级，并在内部无法修复时派工外协。

```yaml
SlaEscalationService:
  方法:
    scanResponseTimeout(now):
      # 查询 DISPATCHED 且 (dispatched_at + sla.response_deadline) < now 的工单
      # 逐个 -> order.escalateResponse() -> RepairEscalated（level++，reason=ResponseTimeout）
      # 升级矩阵：L1->L2 通知维修主管重新分配高级工程师；L2->L3 通知工程经理决定外协
      # 幂等：按 (order_id, escalation_level, 超时窗口) 去重（BIZ-03）

    scanRepairTimeout(now):
      # 查询 IN_REPAIR 且 (repair_started_at + sla.repair_deadline) < now 的工单
      # 逐个 -> order.escalateRepair() -> RepairEscalated（level++，reason=RepairTimeout）
      # 幂等：按 (order_id, escalation_level, 超时窗口) 去重（BIZ-03）

    decideExternalRepair(order_id):
      # 当 escalation.level=L3 且内部无法修复
      # -> 委托 RepairExecutionService.dispatchExternalRepair(vendor, estimated_completion)
      # -> ExternalRepairDispatched

    onCriticalResponseTimeout(order_id):
      # CRITICAL 级别 30 分钟未响应 -> 自动升级到维修主管
      # -> order.escalateResponse() -> RepairEscalated
```

> **为什么不放在聚合根内**：SLA 超时判定需定时扫描所有工单实例（跨实例查询）、按升级矩阵决定升级级别与外协——单聚合无权自我驱动定时器或查询其它工单。升级幂等（BIZ-03）是跨实例不变式，由本服务 + 去重表保证。

> 🔴 **热点：CRITICAL 停线处理**（事件风暴 §2.1）——CRITICAL 级别故障导致产线停机，SLA 极短（15min 响应/2h 修复）。CRITICAL 紧急工单创建时应用服务同事务委托台账 `SuspendAsset(reason=CriticalFault)`（强防错同步，INV-CX-09），资产停用间接阻断生产；30 分钟未响应自动升级维修主管。本上下文不直接指挥停线（停用资产归台账，生产调度归生产执行服务）。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文与台账上下文虽同属设备管理服务，但维修->台账的协作按**是否强防错阻塞**区分：恢复资产（`RepairCompleted`->Reinstate）、报废建议（`ScrapRecommendation`）走**异步事件解耦**（台账综合判定，非强防错阻塞，INV-CX-08）；CRITICAL 故障停用资产（`SuspendAsset`）走**本地事务同步**（强防错阻塞，与点检保养 INV-27 同构，INV-CX-09）。

### 4.1 RepairCommandAppService（维修命令应用服务）

**职责**：处理报修、派工、诊断、维修、验证、升级、外协、报废建议的写操作命令（REST/移动端入口，发命令者：操作员/维修工程师/设备工程师/生产主管/派工员）。

```yaml
RepairCommandAppService:
  方法:
    # ─── 报修 ───
    reportMalfunction(cmd):
      # 委托 MalfunctionReportService.onManualReport -> 写仓储 -> Outbox
      # 幂等：commandId + (asset_id, symptom, 时间窗口)（BIZ-01）
    confirmReport(report_id, confirmed_by):
      # -> MalfunctionReportService.confirmReport
    dismissReport(report_id, reason):
      # -> MalfunctionReportService.dismissReport（终态拒收 INV-21）

    # ─── 派工 ───
    dispatchOrder(order_id, assignee):
      # -> RepairOrder.dispatch -> 写仓储 -> Outbox
      # 启动 SLA 响应计时

    # ─── 诊断 ───
    startDiagnosis(order_id, started_by):
      # -> DiagnosisService.startDiagnosis
    recordDiagnosisResult(order_id, ...):
      # -> DiagnosisService.recordDiagnosisResult（同事务推进工单 DIAGNOSED + 分流）

    # ─── 维修执行 ───
    performRepairAction(order_id, ...):
      # -> RepairExecutionService.performRepairAction
      #   （首条动作同事务推进工单 IN_REPAIR + 备件消耗事件）
    dispatchExternalRepair(order_id, vendor, estimated_completion):
      # -> RepairExecutionService.dispatchExternalRepair
    recordExternalRepairResult(order_id, result, cost, parts_replaced[]):
      # -> RepairExecutionService.recordExternalRepairResult

    # ─── 验证 ───
    submitVerification(order_id, method, result, failed_reason?, verified_by):
      # -> VerificationService.submitVerification
      #   VERIFIED -> 同事务 order.close(Repaired) + 发布 RepairCompleted
      #   FAILED -> 同事务 order.reopen(VerificationFailed)

    # ─── 报废建议 ───
    recommendScrap(order_id):
      # 前置：order DIAGNOSED 且 feasibility ∈ {NOT_ECONOMICAL, NOT_REPAIRABLE}
      # -> ScrapRecommendationService.recommendScrap

    # ─── 升级（人工触发，定时触发走 §4.3）───
    escalateResponse(order_id):
      # -> RepairOrder.escalateResponse -> RepairEscalated
    escalateRepair(order_id):
      # -> RepairOrder.escalateRepair -> RepairEscalated
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 报修 | 单聚合事务 | `MalfunctionReportService` | `MalfunctionReported` | `commandId`；`source_event_id`/`(asset_id,symptom,窗口)` 去重（BIZ-01/07） |
| 确认/驳回草稿 | 单聚合事务 | `MalfunctionReport.confirm`/`dismiss` | `MalfunctionReportConfirmed`/`Dismissed` | `commandId`；终态拒收（INV-21） |
| 派工 | 单聚合事务 | `RepairOrder.dispatch` | `RepairOrderDispatched` | `commandId`；version |
| 记录诊断 | 诊断 + 工单同事务 | `DiagnosisService` | `DiagnosisResultRecorded`（+工单内部推进 DIAGNOSED） | `commandId` |
| 执行维修动作 | 动作 + 工单同事务 | `RepairExecutionService` | `RepairActionPerformed` + `PartsConsumed` | `commandId`；`(action_id,part_code)`（INV-CX-04） |
| 外协派工/登记结果 | 单聚合事务 | `RepairExecutionService` | `ExternalRepairDispatched`/`Completed` | `commandId` |
| 提交验证 | 验证 + 工单同事务 | `VerificationService` | `RepairVerificationSubmitted` + `RepairOrderClosed`/`Reopened` + `RepairCompleted`(VERIFIED) | `commandId`；工单终态拒收 |
| 建议报废 | 单聚合事务 | `ScrapRecommendationService` | `ScrapRecommendation` | `commandId` |
| 人工升级 | 单聚合事务 | `RepairOrder.escalate*` | `RepairEscalated` | `commandId`；`(order_id,level,窗口)`（BIZ-03） |

> **CRITICAL 紧急工单创建的同事务台账停用**（INV-CX-09）：报修/确认草稿后策略创建 RepairOrder 时，若 `severity=CRITICAL`，应用服务同事务委托台账可用性端口 `SuspendAsset(reason=CriticalFault)`，确保关键故障资产立即不可用。报修/确认用例的事务边界相应扩展为「报告/工单 + 台账可用性投影 + Outbox 同事务」。非 CRITICAL 不停用资产。

### 4.2 RepairEventConsumeAppService（事件消费应用服务）

**职责**：订阅上下文外事件，翻译为本上下文命令，委托领域服务处理（事件风暴 §2.6 消费策略逐条迁入）。

## 5. 领域事件

### 5.1 故障报告事件

| 事件 | 载荷 | 发出者 |
|------|------|--------|
| `MalfunctionReported` | report_id, source, asset_id, asset_kind, symptom, severity, production_impact, reported_by, reported_at, source_event_id? | MalfunctionReport（经 MalfunctionReportService 编排） |
| `MalfunctionReportConfirmed` | report_id, confirmed_by, confirmed_at | MalfunctionReport |
| `MalfunctionReportDismissed` | report_id, dismiss_reason, dismissed_at | MalfunctionReport |

> `MalfunctionReportConfirmed` / `MalfunctionReportDismissed` 为实现事件风暴 §1 热点（DATA_COLLECTION 草稿确认流）而显式命名，已同步回事件风暴 §事件命名速查表。

### 5.2 维修工单生命周期事件

| 事件 | 载荷 | 发出者 |
|------|------|--------|
| `RepairOrderCreated` | order_id, report_id, asset_id, asset_kind, priority, sla_deadline | RepairOrder |
| `RepairOrderDispatched` | order_id, assignee, dispatched_at | RepairOrder |
| `RepairOrderReopened` | order_id, reason(VerificationFailed / ScrapRejected), target_phase | RepairOrder（经 VerificationService / ScrapRecommendationService 编排） |
| `RepairOrderClosed` | order_id, close_reason(Repaired/AssetScrapped/AssetRetired), closed_at | RepairOrder |
| `RepairCompleted` | order_id, asset_id, repair_summary, completed_at | RepairOrder（仅 `close(Repaired)` 时，INV-14） |

> `DISPATCHED->DIAGNOSED`、`DIAGNOSED->IN_REPAIR`、`IN_REPAIR->VERIFIED` 三条边不发独立工单生命周期事件，分别由 `DiagnosisResultRecorded` / 首条 `RepairActionPerformed` / `RepairVerificationSubmitted(VERIFIED)` 隐含驱动（工单状态在读模型投影反映）。

### 5.3 诊断事件

| 事件 | 载荷 | 发出者 |
|------|------|--------|
| `DiagnosisStarted` | diagnosis_id, order_id, started_at, started_by | FaultDiagnosis |
| `DiagnosisResultRecorded` | diagnosis_id, order_id, fault_cause, repair_plan, estimated_parts[], estimated_duration, repair_feasibility, estimated_repair_cost? | FaultDiagnosis（经 DiagnosisService 编排） |

### 5.4 维修执行事件

| 事件 | 载荷 | 发出者 |

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 维修上下文](../事件风暴/维修上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

#### 6.1.1 MalfunctionReport（故障报告）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-15 | DATA_COLLECTION 通信故障报告以草稿(`PENDING_CONFIRMATION`)生成，确认(`CONFIRMED`)后才创建 RepairOrder；PRODUCTION/INSPECTION/MANUAL 直接 `CONFIRMED` | 由 `MalfunctionReport` 聚合根 `ReportState` 状态机 + `MalfunctionReportService` 编排保证（事件风暴 §1 热点） |
| INV-21 | `DISMISSED` 后任何事件均拒收 | 报告误报驳回为终态，不可逆；由 `MalfunctionReport` 聚合根状态机保证 |

#### 6.1.2 RepairOrder（维修工单）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-02 | `RepairOrder` 必须关联一条 `MalfunctionReport`；状态单向流转，仅 `ReopenRepairOrder` / `ReopenForRediagnosis` 允许回退 | 由 `RepairOrder.open` 前置 + 状态机保证；可逆边仅验证失败回退维修 / 报废驳回回退诊断 |
| INV-03 | `RepairOrderClosed` 后任何事件均拒收 | `CLOSED` 为终态，不可逆；由 `RepairOrder` 聚合根状态机保证 |
| INV-11 | 故障分级 -> 派工优先级 + SLA 映射：CRITICAL->URGENT(15min/2h)、HIGH->HIGH(30min/4h)、MEDIUM->NORMAL(2h/24h)、LOW->LOW(8h/72h) | 映射规则存配置（策略引擎），工单创建时快照 `priority`+`sla`；CRITICAL 30min 未响应自动升级；由 `RepairOrder.open` 行为保证 |
| INV-12 | 升级建模为 `escalation` 属性（`level≠NONE` 表示升级中），主状态机保持 `DISPATCHED/IN_REPAIR`，升级回退不丢失原阶段 | 事件风暴 `[ESCALATED]` 状态节点 -> 建模为属性（§2.11），避免回退目标歧义；由 `RepairOrder` 聚合根保证 |

| INV-14 | `RepairCompleted` 仅在 `close(reason=Repaired)` 时发布；`reason ∈ {AssetScrapped, AssetRetired, FalseAlarm}` 不发布 | `RepairOrder.close` 行为内判定；资产已不在或非真实故障不触发恢复；由 `RepairOrder` 聚合根保证 |

#### 6.1.3 FaultDiagnosis（故障诊断）

| 编号 | 不变式 | 说明 |
|------|--------|------|
| INV-04 | 一个 `RepairOrder` 可多次诊断（首次诊断后升级再诊断）；每次诊断必须记录 `repair_feasibility` | `FaultDiagnosis` 独立聚合，每次 `recordResult` 必填 `feasibility`；由 `FaultDiagnosis` 聚合根行为保证 |

## 暂缓模块说明

按当前阶段要求，下列内容**本次不展开**，待对应模块设计时再合并：

- 备件库存管理、备件 BOM、安全库存、采购补货 -> 后续「备件管理上下文」（本上下文仅发布 `PartsConsumed` 事件）
- 维修知识库（故障-方案关联、智能推荐）-> 数据应用上下文（`RepairKnowledgeEntry` 暂缓，本上下文发布 `repair.diagnosis` 供其分析）
- MTBF / MTTR / 维修成本分析 -> 数据应用上下文（消费 `repair.diagnosis` / `repair.verification` / `repair.external`）
- 移动端维修操作界面与离线执行 -> 应用层
- 与 ERP/EAM 的工单/成本同步 -> 本上下文的 ERP/EAM 工单成本适配层（ACL，消费 `repair.external`）
- 维修工单的智能派工（基于技能矩阵、负载均衡）-> 后续优化（当前 `responsible_role`->当班人员->手动改派）

这些将通过本上下文已经定义的事件契约（`repair.*` 主题）衔接，避免回头返工。
