# 设备数据接入上下文 — 领域建模（Equipment Data Ingestion Domain Model）

> **限界上下文**：设备数据接入上下文
> **统一语言**：Equipment（设备·采集侧记录）, EdgeGateway（边缘网关）, CollectionChannel（采集通道）, ProtocolAdapter（协议适配器）, ProtocolProfile（协议画像）, DataPoint（数据点）, DataPacket（数据报文）, RawSignal（原始信号）, BackfillCursor（补传游标）, DataQualityFlag（数据质量标记）, EquipmentRunHourAggregation（运行时长聚合）, DeadLetterEnvelope（死信信封）, EquipmentAlarm（设备报警·归一化）, AlarmSeverityMapping（报警分级映射）, AssetEndpointReference（资产端点引用）
> **建模依据**：[事件风暴 — 设备数据接入上下文](../事件风暴/设备数据接入上下文.md)

---

## 0. 建模总览

本域是设备管理服务下的**支撑域**，仅对"数据如何从设备汇集到平台"负责——**搬运而不解释**。核心职责是管理**设备接入会话、协议解析、报文封装与质量打标、边缘缓存与断点续传、平台去重与乱序矫正、运行时长轻量聚合、设备报警归一化**；**不负责**设备资产身份与建档（归设备工装台账上下文，下文简称「台账上下文」）、不负责业务判定（归质量上下文）、不负责过站推进（归过点执行上下文）。

本上下文的 `Equipment` 是"采集侧设备记录"（在线状态、通道绑定、协议画像），**不是资产主数据**——`equipment_id` 由台账上下文 `AssetIdentifierAssigned` 颁发，本上下文不另行分配（INV-CX-07）。本上下文与台账上下文共享 `equipment_id` 但视角不同：台账是"资产管理视角"，本上下文是"通信视角"，`EquipmentOnline ≠ AssetCommissioned`（INV-CX-08）。

## 1. 聚合根

### 1.1 Equipment（设备·采集侧记录）

**一致性边界**：单台设备的采集侧在线状态、网关绑定、协议适配器引用与通道引用。

**职责**：维护"通信视角"的设备在线状态机（UNBOUND->OPENING->ONLINE⇄SUSPECT->OFFLINE->CLOSED），绑定网关与协议适配器，引用当前活跃采集通道。**不持有**资产主数据（型号/厂商/分类经 ACL 引用台账，见 `AssetEndpointReference`）。

```yaml
Equipment:
  # ─── 标识 ───
  equipment_id:          EquipmentId              # 采集侧设备记录ID（聚合根ID，由台账上下文颁发 INV-CX-07）
  asset_endpoint:        AssetEndpointReference   # 资产端点引用（model/vendor/classification，经 ACL 从台账翻译）

  # ─── 网关与协议绑定 ───
  gateway_id:            GatewayId?               # 绑定的边缘网关（UNBOUND 时为空）
  protocol_adapter_id:   ProtocolAdapterId?       # 绑定的协议适配器（UNBOUND 时为空）
  active_channel_id:     ChannelId?               # 当前活跃采集通道（BIZ-01：同时仅一个）

  # ─── 在线状态 ───
  online_state:          EquipmentOnlineState     # 在线状态机
  terminated:            Boolean                  # 是否因资产退役进入终态（INV-03）

  # ─── 会话观测 ───
  firmware_ver:          String?                  # 握手时上报的固件版本
  program_ver:           String?                  # 握手时上报的程序版本
  last_seen_at:          DateTime?                # 最近心跳/报文时间戳
  last_heartbeat_seq:    Long?                    # 最近心跳序号

  # ─── 降级与重连 ───
  suspect_since:         DateTime?                # 进入 SUSPECT 的时刻
  reconnect_attempts:    Integer                  # 当前重连尝试次数
  escalated_level:       EscalationLevel?         # 已升级的告警级别（产线/车间/工厂）
```

**行为**：
- `bindGateway(gateway_id, protocol_profile)` -> 发出 `GatewayBound`（前置：当前为 `UNBOUND` 或非终态 `CLOSED`；创建/绑定 `ProtocolAdapter`；状态 -> `OPENING`）
- `openCollectionChannel(firmware_ver, program_ver)` -> 发出 `EquipmentOnline`（前置：当前为 `OPENING` 且握手成功且首帧可解析；状态 -> `ONLINE`；绑定 `active_channel_id`）
- `rejectChannel(reason)` -> 发出 `CollectionChannelRejected`（前置：当前为 `OPENING` 且握手失败；状态 -> `CLOSED`，`terminated=false` 可重绑）
- `recordHeartbeat(rtt, seq_no)` -> 发出 `HeartbeatReceived`（前置：当前为 `ONLINE` 或 `SUSPECT`；滚动更新 `last_seen_at` / `last_heartbeat_seq`；若处于 `SUSPECT` 则联动 `clearSuspect`）
- `markSuspect(grace_window)` -> 发出 `HeartbeatTimedOut`（前置：当前为 `ONLINE`；状态 -> `SUSPECT`；记录 `suspect_since`）
- `clearSuspect()` -> 状态 `SUSPECT` -> `ONLINE`（前置：心跳恢复 或 重连成功且补传完成；发出 `EquipmentRecovered`）
- `markOffline()` -> 发出 `EquipmentOffline`（前置：当前为 `SUSPECT` 且重连失败达 N 次；状态 -> `OFFLINE`；载荷携带 `entered_buffer_mode=true`）
- `recoverEquipment(gap_window, backfilled_msg_count)` -> 发出 `EquipmentRecovered`（前置：当前为 `OFFLINE` 且重连成功且补传完成；状态 -> `ONLINE`；重置 `reconnect_attempts`）
- `escalateChannel(level)` -> 发出 `ChannelEscalated`（前置：`SUSPECT->OFFLINE` 转移时；记录 `escalated_level`；发布到 `dc.equipment.lifecycle` 供台账 `SuspendAsset(CommunicationLost)`）
- `reloadProtocolProfile(protocol_profile)` -> 发出 `ProtocolProfileReloaded`（前置：当前非终态；仅协议相关字段重载，不中断通道）
- `closeChannel(reason=AssetRetired)` -> 发出 `EquipmentClosed`（前置：已消费台账 `AssetRetired`；任意非终态 -> `CLOSED`，`terminated=true`；**终态——之后任何采集事件均拒收** INV-03）

> **CLOSED 的两种语义**（承接事件风暴 §2.2.1 歧义）：`CLOSED` 由两条路径进入——①`rejectChannel`（握手失败，`terminated=false`，可经 `bindGateway` 重绑重试）；②`closeChannel` 因台账 `AssetRetired`（`terminated=true`，终态，INV-03 拒收一切）。`terminated` 标志区分二者，避免为终态单设状态而偏离事件风暴命名。

> **SUSPECT 语义**：表示"可能断连但未确认"，保守计为在线——运行时长聚合仍计入该时段（§2.4 / §1.6）。`ChannelEscalated` 在 `SUSPECT->OFFLINE` 转移时发布，台账上下文消费后执行 `SuspendAsset(reason=CommunicationLost)`，本上下文不停用资产。

### 1.2 CollectionChannel（采集通道）

**一致性边界**：网关到设备的一次连接——从握手建立到关闭的连接状态与缓冲游标引用。

**职责**：维护连接状态机（CLOSED->OPENING->ESTABLISHED⇄DEGRADED->CLOSED），与 `Equipment` 状态联动但独立维护。一个 `equipment_id` 同时只有一个活跃 `CollectionChannel`（BIZ-01）。

```yaml
CollectionChannel:
  # ─── 标识 ───
  channel_id:            ChannelId                # 通道唯一标识（聚合根ID）
  gateway_id:            GatewayId                # 所属网关
  equipment_id:          EquipmentId              # 所属设备（INV-02：channel_id ↔ (gateway_id, equipment_id) 一一对应）
  protocol_adapter_id:   ProtocolAdapterId        # 解码所用协议适配器

  # ─── 连接状态 ───
  connection_state:      ChannelConnectionState   # 连接状态机
  terminated:            Boolean                  # 是否因资产退役进入终态（INV-03）

  # ─── 握手与会话 ───
  cipher_suite:          String?                  # 握手协商的加密套件
  established_at:        DateTime?                # 建立时刻
  degraded_since:        DateTime?                # 进入 DEGRADED 的时刻

  # ─── 缓冲与补传 ───
  backfill_cursor_id:    BackfillCursorId?        # 关联的补传游标（INV-02：缓冲区单调递增游标）
  entered_buffer_mode:   Boolean                  # 是否已切换到边缘缓存模式
```

**行为**：
- `open(gateway_id, equipment_id, protocol_adapter_id)` -> 发出 `CollectionChannelOpened`（前置：已消费 `GatewayBound`；状态 `CLOSED` -> `OPENING`）
- `establishChannel(cipher_suite)` -> 状态 `OPENING` -> `ESTABLISHED`（前置：握手成功；记录 `established_at`）
- `rejectChannel(reason)` -> 状态 `OPENING` -> `CLOSED`（前置：握手失败；`terminated=false` 可重开）
- `degradeChannel(grace_window)` -> 状态 `ESTABLISHED` -> `DEGRADED`（前置：心跳超时；记录 `degraded_since`）
- `restoreChannel()` -> 状态 `DEGRADED` -> `ESTABLISHED`（前置：心跳恢复 或 重连成功）
- `enterBufferMode()` -> 标记 `entered_buffer_mode=true`（前置：进入 `DEGRADED` 或设备 `OFFLINE`；后续报文走断连缓冲）
- `close(reason=AssetRetired)` -> 发出 `CollectionChannelClosed`（前置：已消费台账 `AssetRetired`；任意非终态 -> `CLOSED`，`terminated=true`；终态 INV-03）

> **与 Equipment 的联动**：`CollectionChannel` 与 `Equipment` 状态机同步演进但各自独立维护——通道 `DEGRADED` 对应设备 `SUSPECT`，通道 `ESTABLISHED` 对应设备 `ONLINE`。两者不互相持有引用，由 `HeartbeatMonitorService` / `ReconnectService` 在同事务内协调推进（BIZ-01 由 `GatewayBindingService` + (equipment_id, status=ACTIVE) 唯一索引保证）。

### 1.3 ProtocolAdapter（协议适配器）

**一致性边界**：单台设备绑定的一份协议画像与解码策略——协议参数、节点映射、解码逻辑入口。

**职责**：持有可热重载的 `ProtocolProfile`，对原始帧执行解码（`decodeFrame`），产出通用 `DataPointDecoded` 或设备特定采集事件；解码失败产出 `FrameDecodeFailed`。**不解释业务语义**——只把协议字段结构化为数据点，PASS/FAIL 判定留给质量上下文（INV-CX-01 / INV-CX-03）。

```yaml
ProtocolAdapter:
  # ─── 标识 ───
  adapter_id:            ProtocolAdapterId        # 适配器唯一标识（聚合根ID）
  equipment_id:          EquipmentId              # 所属设备（1:1 绑定）

  # ─── 协议画像 ───
  protocol_profile:      ProtocolProfile          # 协议画像（协议类型/节点映射/参数/加密套件）
  decoding_strategy:     DecodingStrategyRef      # 设备特定解码策略引用（ISP：按设备类型选择）

  # ─── 状态 ───
  reloaded_at:           DateTime                 # 最近一次画像重载时刻
  decode_fail_streak:    Integer                  # 连续解码失败次数（驱动协议异常升级）
```

**行为**：
- `load(equipment_id, protocol_profile, decoding_strategy)` -> 发出 `ProtocolAdapterLoaded`（前置：`Equipment.bindGateway` 时创建）
- `reloadProtocolProfile(protocol_profile)` -> 发出 `ProtocolProfileReloaded`（前置：消费台账 `AssetSpecificationProfileUpdated` 且画像含协议相关字段；仅重载协议相关字段，不中断通道）
- `decodeFrame(raw_frame)` -> 纯方法，返回解码结果：
  - 成功 -> 发出 `DataPointDecoded`（通用数据点）+ 按设备类型经 `DecodingStrategy` 发出设备特定采集事件（如 `PrinterCycleObserved` / `SerialNumberMarked`）
  - 失败 -> 发出 `FrameDecodeFailed`（递增 `decode_fail_streak`；连续失败达阈值由 `DeadLetterService` 升级为 `ProtocolAnomalyRaised`）
- `resetFailStreak()` -> 解码成功时清零 `decode_fail_streak`

> **为什么不把解码放在领域服务**：解码依赖该设备绑定的 `ProtocolProfile`（节点映射、地址表）——这是聚合的私有状态，由聚合统一持有与热重载（SRP：画像变更只此一处）。解码的纯计算逻辑下沉到 `DecodingStrategy` 策略对象（ISP：适配器不实现各设备解码细节，按设备类型委托），聚合只负责"用谁的画像、委托给哪个策略、产出什么事件"。这与点检上下文 `TriggerCondition.assess` / `MaintenanceRule.assessLife` 的纯方法下沉同构。

> **设备特定事件归属**：§3 各设备的采集事件（`PrinterCycleObserved` / `AOIInspectionStarted` / `SerialNumberMarked` / `FastenerTightened` 等）均由 `ProtocolAdapter` 经对应 `DecodingStrategy` 在 `decodeFrame` 时发出——它们是协议级结构化事实（"过板了一次""拧紧了一枪"），不是业务判定（"印刷不良""拧紧合格"）。业务语义一律留给下游上下文（INV-CX-01 / INV-CX-03）。

### 1.4 DataPacket（数据报文）

**一致性边界**：一帧封装好的上行报文——从打质量标到上行投递/缓冲的完整搬运事实。

**职责**：承载一帧报文的标识、时间戳三元组、质量标记与载荷引用；保证 `msg_id` 全局唯一、`source_ts ≤ ingest_ts`、质量必须打标（INV-04）。

```yaml
DataPacket:
  # ─── 标识 ───
  msg_id:                MsgId                    # 报文全局唯一标识（聚合根ID，BIZ-02）
  equipment_id:          EquipmentId              # 来源设备
  channel_id:            ChannelId                # 来源通道

  # ─── 时间戳三元组 ───
  timestamps:            TimestampTriple          # source_ts / ingest_ts / clock_skew（INV-04 / INV-11）

  # ─── 质量与载荷 ───
  quality:               DataQualityFlag          # GOOD/SUSPECT/BAD/LATE（INV-04：必须打标）
  payload_ref:           PayloadReference         # 载荷引用（结构化数据点 / 对象存储 URI）
  topic_target:          TopicReference           # 拟发布的下游主题

  # ─── 投递状态 ───
  delivery_state:        PacketDeliveryState      # EDGE_BUFFERED / DISPATCHED / BACKFILL_ENQUEUED / PERSISTED / PUBLISHED
  cursor:                BackfillCursorValue?     # 边缘缓存位点（断连缓冲时携带）
```

**行为**：
- `stampQuality(quality)` -> 发出 `QualityStamped`（前置：已 `DataPointDecoded`；写入 `quality`，INV-04）
- `seal(payload_ref, topic_target)` -> 发出 `DataPacketSealed`（前置：已打质量标；固化 `msg_id` / `timestamps` / 载荷引用）
- `edgeBuffer(cursor)` -> 发出 `EdgeBuffered`（前置：已封装；写入边缘缓存，记录 `cursor`）
- `dispatch()` -> 发出 `PacketDispatched`（前置：连接正常；状态 -> `DISPATCHED`）
- `enqueueBackfill(cursor)` -> 发出 `BackfillEnqueued`（前置：连接异常 / `entered_buffer_mode`；状态 -> `BACKFILL_ENQUEUE`；进入断连缓冲）
- `markPersisted(partition)` -> 发出 `PacketPersisted`（前置：平台层去重/乱序矫正通过；状态 -> `PERSISTED`）
- `markPublished(topic)` -> 发出 `PacketPublished`（前置：已持久化；状态 -> `PUBLISHED`；供上下文外消费）

> **时间戳基准**（INV-11）：以设备 `source_ts` 为事件时间基准；当设备时钟漂移超阈值（建议 3s）时按 `ingest_ts` 修正并记录 `clock_skew`。`source_ts ≤ ingest_ts` 始终成立（INV-04）。

> **大文件/曲线不进主流**（INV-15）：烧录日志、扭矩曲线、AOI 图像等大体积载荷走对象存储，主流 `DataPacket` 只承载 URI + 校验和（`sha256`）。这是吞吐与成本的核心折衷。

### 1.5 BackfillCursor（补传游标）

**一致性边界**：单条通道的补传位点——单调递增，恢复后必须先补齐再放新。

**职责**：跟踪断连缓冲区的水位，保证补传顺序与"先补后新"（INV-05）。

```yaml
BackfillCursor:
  # ─── 标识 ───
  cursor_id:             BackfillCursorId         # 游标唯一标识（聚合根ID）
  channel_id:            ChannelId                # 所属通道

  # ─── 位点 ───
  buffered_cursor:       BackfillCursorValue      # 已写入断连缓冲的最大位点（单调递增 INV-05）
  backfilled_cursor:     BackfillCursorValue      # 已补传完成的最大位点（单调递增）
  resuming:              Boolean                  # 是否处于补传进行中
```

**行为**：
- `enqueue(msg_id, cursor)` -> 追加到断连缓冲，推进 `buffered_cursor`（前置：通道 `entered_buffer_mode`；单调递增 INV-05）
- `beginResume()` -> 发出 `BackfillResuming`（前置：通道恢复且 `backfilled_cursor < buffered_cursor`；`resuming=true`）
- `advance(msg_id, cursor)` -> 推进 `backfilled_cursor`（前置：`resuming=true`；按位点顺序补传）
- `complete()` -> 发出 `BackfillCompleted`（前置：`backfilled_cursor == buffered_cursor`；`resuming=false`；载荷携带 `backfilled_count`）

> **"先补齐再放新"**（INV-05）：恢复后 `resuming=true` 期间，新报文必须排在补传队列之后——由 `buffered_cursor` / `backfilled_cursor` 的单调性与 `BackfillService` 的顺序保证。补传数据的时间戳已在原始区间内，运行时长聚合去重处理（§1.6）。

### 1.6 EquipmentRunHourAggregation（运行时长聚合）

**一致性边界**：单台设备一个班次内的运行时长聚合——基于自身观测的 Online/Offline 区间。

**职责**：按设备分组、按班次周期累加 Online->Offline 区间时长，周期性发布 `EquipmentRunHourAggregated`，供台账上下文累计为 `EquipmentRunHourAccrued`。**不依赖台账资产状态**——以本上下文自身观测的 Online/Offline 为准（INV-CX-08 / INV-15）。

```yaml
EquipmentRunHourAggregation:
  # ─── 标识 ───
  aggregation_id:        AggregationId            # 聚合唯一标识（聚合根ID）
  equipment_id:          EquipmentId              # 所属设备
  period:                RunHourPeriod            # 聚合周期（班次窗口）

  # ─── 在线区间 ───
  online_segments:       List<OnlineSegment>      # 本周期内的在线区间（去重、不可重叠 BIZ-03）
  #   OnlineSegment: { started_at, ended_at, source: ONLINE|RECOVERED }

  # ─── 聚合结果 ───
  run_hours_in_period:   RunHours                 # 本周期运行时长（1 位小数）
  total_online_segments: Integer                  # 在线区间数
  source:                String                   # 聚合来源（自身观测）
  published:             Boolean                  # 是否已周期性发布
```

**行为**：
- `openSegment(started_at)` -> 开启一条在线区间（前置：`EquipmentOnline` 或 `EquipmentRecovered`；若与已有区间重叠则去重合并 BIZ-03）
- `closeSegment(ended_at)` -> 关闭当前在线区间（前置：`EquipmentOffline`）
- `publish(period_end)` -> 发出 `EquipmentRunHourAggregated`（前置：班次结束；状态 `published=true`；载荷 `equipment_id / period_start / period_end / run_hours_in_period / total_online_segments / source`）

> **聚合规则**（承接事件风暴 §2.4）：聚合周期对齐车间排班（每班 8h）；在线判定 = `EquipmentOnline` ~ `EquipmentOffline`；`SUSPECT` 时段仍计为在线（保守计在线）；`EquipmentRecovered` 回填时段不重复计算（补传数据时间戳已在原始区间内，去重处理 BIZ-03）。精度保留 1 位小数（如 7.5h），与台账 `run_hours` 一致。

> **工装使用次数不在此聚合**（INV-CX-02）：`FixtureCycleAccrued` 不在本上下文聚合。本上下文只上报原始采集事件（`StencilUsageIncremented` / `TestFixtureCycleCounted`），台账上下文订阅后自行累加。累积度量维护权归台账上下文。

### 1.7 DeadLetterEnvelope（死信信封）

**一致性边界**：一帧解码失败的原始字节及其失败原因与保留窗口。

**职责**：落地死信，保留原始字节 + 失败原因 + `retain_until`（INV-07），供事后回放与协议异常分析；保留窗口结束后清理。

```yaml
DeadLetterEnvelope:
  # ─── 标识 ───
  dead_letter_id:        DeadLetterId             # 死信唯一标识（聚合根ID）
  equipment_id:          EquipmentId              # 来源设备
  channel_id:            ChannelId                # 来源通道

  # ─── 失败信息 ───
  raw_bytes_ref:         RawBytesReference        # 原始字节引用（对象存储 URI INV-07）
  reason:                DeadLetterReason         # 失败原因枚举
  failed_at:             DateTime                 # 失败时刻

  # ─── 保留 ───
  retain_until:          DateTime                 # 保留截止（建议 7 天滚动窗口）
  state:                 DeadLetterState          # RETAINED / PURGED
```

**行为**：
- `store(raw_bytes_ref, reason, retain_until)` -> 发出 `DeadLetterStored`（前置：`FrameDecodeFailed`；状态 -> `RETAINED`；INV-07）
- `purge()` -> 状态 `RETAINED` -> `PURGED`（前置：`now > retain_until`；终态；清理原始字节）

> **死信回放**（承接事件风暴 §2.3 热点）：解码失败的原始字节保留 7 天滚动窗口以便事后回放；存储成本需与运维确认。`ProtocolAnomalyRaised` 由 `DeadLetterService` 在连续解码失败达阈值时发出（基于 `ProtocolAdapter.decode_fail_streak`），与单条死信落地独立。

### 1.8 EquipmentAlarm（设备报警·归一化）

**一致性边界**：单台设备单个报警码的归一化记录——从 Raised 到 Cleared 的两态生命周期。

**职责**：将各设备协议（SECS/GEM alarm code / PLC bit 位等）的报警帧归一化为统一的 `EquipmentAlarmRaised` / `EquipmentAlarmCleared`，经 `AlarmSeverityMapping` 解析 severity，发布到 `dc.equipment.alarm.raw`。**不做资产停用判定**——CRITICAL 停用由台账上下文 `SuspendAsset` 执行（INV-CX-02）。

```yaml
EquipmentAlarm:
  # ─── 标识 ───
  alarm_id:              AlarmId                  # 报警实例唯一标识（聚合根ID）
  equipment_id:          EquipmentId              # 来源设备
  alarm_code:            AlarmCode                # 设备原始报警码

  # ─── 归一化结果 ───
  severity:              AlarmSeverity            # CRITICAL/WARNING/INFO（经 AlarmSeverityMapping 解析 INV-09）
  source_protocol:       SourceProtocol           # 来源协议（SECS_GEM/OPC_UA/PLC/MQTT...）

  # ─── 生命周期 ───
  state:                 AlarmState               # ACTIVE / CLEARED
  raised_at:             DateTime
  cleared_at:            DateTime?
```

**行为**：
- `raise(raw_frame, severity_mapping)` -> 发出 `EquipmentAlarmRaised`（前置：当前无活跃实例 或 已 `CLEARED`；解析 severity；状态 -> `ACTIVE`；**幂等**：同一 equipment+alarm_code 活跃期间不重复 Raised INV-10）
- `clear(raw_frame)` -> 发出 `EquipmentAlarmCleared`（前置：当前为 `ACTIVE`；状态 -> `CLEARED`；**幂等**：已 CLEARED 不重复 Cleared INV-10）

> **severity 映射配置驱动**（INV-09）：severity 由"设备型号 × alarm_code -> severity"映射表（`AlarmSeverityMapping`，配置驱动）解析，映射规则归工程标准，**不在事件载荷硬编码**。不同协议的报警分级统一映射到 CRITICAL/WARNING/INFO。

> **归一化只搬运不判定**（INV-CX-02）：本上下文只负责归一化并发布原始报警（含 severity 分级）。`severity=CRITICAL` 的资产停用判定与执行在台账上下文（`SuspendAsset(reason=CriticalAlarm)`），本上下文不停用资产。

### 2.3 EquipmentOnlineState（设备在线状态）

```yaml
EquipmentOnlineState:
  - UNBOUND     # 已建采集侧记录，未绑定网关
  - OPENING     # 已绑定网关，握手进行中
  - ONLINE      # 在线（握手通过且首帧可解析）
  - SUSPECT     # 疑似断连（心跳超时宽限内，保守计在线）
  - OFFLINE     # 离线（重连失败达 N 次，切边缘缓存）
  - CLOSED      # 关闭（终态：资产退役；或非终态：握手失败可重绑）
```

**状态机**：

```
                         [UNBOUND]
                            |
              消费 AssetRegistered -> BindGateway
                            |
                            v
                         [OPENING]
                            |
              ┌───── 握手成功(首帧可解析) ─────┐
              │                                │
              v                                v
        ┌──▶ [ONLINE] ◀── 心跳恢复/重连+补传 ──┐
        │        │                              │
        │   心跳超时宽限                         │
        │        v                              │
        │   [SUSPECT] ─── 重连失败 N 次 ──▶ [OFFLINE]
        │        │                              │
        │   心跳恢复/重连+补传                   │
        └────────┘                              │
                                                 │
        消费 AssetRetired -> CloseChannel         │
              │                                  │
              v                                  │
           [CLOSED 终态] ◀─── 重连成功+补传 ─────┘
        (terminated=true，之后任何采集事件均拒收 INV-03)

        握手失败(不可恢复) -> RejectChannel -> [CLOSED 非终态] -> 人工介入后 BindGateway -> [OPENING]
```

**不变式**：
- `UNBOUND -> OPENING`：前置已消费 `AssetRegistered(asset_kind=Equipment)`（INV-CX-07）
- `OPENING -> ONLINE`：前置握手成功且首帧可解析
- `OPENING -> CLOSED(非终态)`：`rejectChannel`，`terminated=false`，可经 `bindGateway` 重绑
- `ONLINE ⇄ SUSPECT`：心跳超时 / 恢复
- `SUSPECT -> OFFLINE`：重连失败达 N 次，同步发布 `ChannelEscalated`
- `OFFLINE -> ONLINE`：重连成功且补传完成
- 任意非终态 -> `CLOSED(终态)`：消费 `AssetRetired`，`terminated=true`，之后拒收一切（INV-03）

### 2.4 ChannelConnectionState（通道连接状态）

```yaml
ChannelConnectionState:
  - CLOSED      # 关闭（终态：资产退役；或非终态：握手失败可重开）
  - OPENING     # 握手进行中
  - ESTABLISHED # 已建立
  - DEGRADED    # 降级（心跳超时）
```

**状态机**：

```
[CLOSED] --OpenCollectionChannel--> [OPENING] --握手成功--> [ESTABLISHED]
                                       |                       |
                                 握手失败                心跳超时
                                       v                       v
                                   [CLOSED]               [DEGRADED]
                                  (非终态)                       |
                                                          心跳恢复/重连成功
                                                                v
                                                          [ESTABLISHED]

任意非终态 --CloseChannel(AssetRetired)--> [CLOSED 终态]（terminated=true，拒收一切 INV-03）
```

> 与 `EquipmentOnlineState` 联动但独立维护：`ESTABLISHED↔ONLINE`、`DEGRADED↔SUSPECT`、`CLOSED(终态)↔CLOSED(终态)`。`CLOSED` 的终态/非终态语义同 §2.3，由 `terminated` 标志区分。

## 3. 领域服务

领域服务封装**跨聚合**的业务逻辑或**不自然归属**单一聚合根的操作。本上下文是支撑域，领域服务以"编排采集链路、守护可靠性不变式"为主，**不含业务判定逻辑**（INV-CX-01）。

### 3.1 GatewayBindingService（网关绑定服务）

**职责**：消费台账上下文资产生命周期事件，编排采集侧记录的建立、网关绑定、通道开启、协议重载与关闭；保证 BIZ-01（同设备单活跃通道）、INV-CX-07（equipment_id 来自台账）、INV-CX-09（只消费不重发）。

```yaml
GatewayBindingService:
  方法:
    onAssetRegistered(asset_endpoint, protocol_profile):
      # 1. 校验 INV-CX-07：equipment_id 来自台账，不另行分配
      # 2. 幂等：按 equipment_id 去重，已存在则不重复绑定（BIZ-01）
      # 3. 创建 Equipment(采集侧) -> bindGateway(gateway_id, protocol_profile) -> GatewayBound
      # 4. 创建 ProtocolAdapter -> load(protocol_profile, decoding_strategy)
      # 5. 创建 CollectionChannel -> open() -> CollectionChannelOpened（发起握手）
      # 6. 握手成功 -> Equipment.openCollectionChannel + CollectionChannel.establishChannel -> EquipmentOnline
      #    握手失败 -> Equipment.rejectChannel + CollectionChannel.rejectChannel -> CollectionChannelRejected
      # 记录 source_event_id 用于跨上下文追溯与幂等（INV-CX-09 / BIZ-04）

    onAssetSpecificationProfileUpdated(equipment_id, spec_keys, spec_values):
      # 仅当画像含协议相关字段 -> ProtocolAdapter.reloadProtocolProfile（INV 承接 §2.5）
      # 其余字段（工艺规格）仅记录，不触发重载
      # 不中断通道

    onAssetRetired(equipment_id):
      # 幂等：已 terminated 则忽略（INV-03）
      # Equipment.closeChannel(AssetRetired) + CollectionChannel.close(AssetRetired)
      # -> CLOSED 终态，之后拒收任何采集事件
```

> **为什么不放在聚合根内**：绑定涉及创建多个聚合（Equipment + ProtocolAdapter + CollectionChannel）+ 跨上下文事件消费 + BIZ-01 单活跃通道校验（跨实例，需查读模型 + 唯一索引）。聚合根无权查询其他实例，由本服务 + (equipment_id, status=ACTIVE) 唯一索引共同保证。本服务**只消费不重发**台账事件——订阅后包装为本上下文语义事件（`GatewayBound` / `CloseChannel`），不把 `AssetRegistered` 原样再发（INV-CX-09）。

> **`AssetRegistered` 的资产类型过滤**（承接事件风暴 §2.1）——台账 `AssetRegistered` 的 `asset_kind` 含 Equipment / Fixture / MeasuringInstrument。本服务只对 `asset_kind=Equipment` 响应；工装 / 计量器具的采集（测试工装、扭矩扳手）走“工位事件”通道（§3.6 / §3.7），不绑定长连接通道。`asset_kind` **不覆盖**“工装采集设备”，工装采集统一走工位事件通道。

---

### 3.2 FrameIngestionService（数据帧采集服务）

**职责**：编排通用数据帧采集主链（edge 侧）——从原始信号到上行投递/断连缓冲的全链路；跨 ProtocolAdapter + DataPacket + BackfillCursor 三个聚合。

```yaml
FrameIngestionService:
  方法:
    onRawSignal(raw_frame):
      # 1. 发出 RawSignalEmitted（网关侧观测）
      # 2. 委托 ProtocolAdapter.decodeFrame(raw_frame)：
      #    成功 -> DataPointDecoded + 设备特定采集事件（经 DecodingStrategy）
      #          -> DataPacket.stampQuality -> seal -> edgeBuffer(cursor)
      #          -> 连接正常：dispatch() -> PacketDispatched
      #            连接异常：enqueueBackfill(cursor) -> BackfillEnqueued（委托 BackfillService）
      #    失败 -> FrameDecodeFailed（委托 DeadLetterService 落死信 + 协议异常升级）
      # 3. 时间戳处理：source_ts 为基准，时钟漂移超阈值按 ingest_ts 修正（INV-11）
```

> **为什么不放在聚合根内**：采集主链横跨三个聚合（ProtocolAdapter 解码、DataPacket 封装投递、BackfillCursor 缓冲），且需根据连接状态分流（正常投递 vs 断连缓冲）。单聚合无权协调另两个聚合的状态，由本服务编排。解码的纯逻辑下沉到 `ProtocolAdapter.decodeFrame`（聚合内），本服务只负责链路编排与分流。

---

### 3.3 BackfillService（断点续传服务）

**职责**：管理 `BackfillCursor` 的推进与补传完成判定；保证 INV-05（单调递增、先补齐再放新）。

```yaml
BackfillService:
  方法:
    onBackfillEnqueued(channel_id, msg_id, cursor):
      # BackfillCursor.enqueue -> 推进 buffered_cursor（单调递增 INV-05）

    onChannelRestored(channel_id):
      # 通道恢复 -> BackfillCursor.beginResume -> BackfillResuming
      # 按 cursor 顺序逐条补传 -> advance()
      # backfilled_cursor == buffered_cursor -> complete() -> BackfillCompleted

    onBackfillCompleted(channel_id, backfilled_count):
      # 通知 ReconnectService 解除降级（ClearSuspect / RestoreChannel）
      # 补传数据时间戳已在原始区间内，运行时长聚合去重（BIZ-03）
```

> **为什么不放在聚合根内**：补传涉及读取通道恢复事件 + 游标聚合 + 顺序补传多报文 + 完成后联动解除降级（跨 BackfillCursor + Equipment + CollectionChannel）。游标的单调性纯逻辑在 `BackfillCursor` 聚合内，本服务负责编排与"先补后新"顺序保证。

---

### 3.4 HeartbeatMonitorService（心跳监控服务）

**职责**：监控心跳到达与超时，驱动 `Equipment` 与 `CollectionChannel` 的降级转移。

```yaml
HeartbeatMonitorService:
  方法:
    onHeartbeatReceived(equipment_id, rtt, seq_no):
      # Equipment.recordHeartbeat -> HeartbeatReceived
      # 若处于 SUSPECT -> 联动 clearSuspect（心跳恢复）
      # 滚动更新 last_seen_at / last_heartbeat_seq

    onHeartbeatTimeout(equipment_id, grace_window):
      # 定时器驱动：超过宽限窗口未收到心跳
      # Equipment.markSuspect -> HeartbeatTimedOut（状态 ONLINE -> SUSPECT）
      # CollectionChannel.degradeChannel -> 状态 ESTABLISHED -> DEGRADED
      # 触发 ReconnectService.startReconnect
```

> **为什么不放在聚合根内**：心跳超时检测需要定时器驱动 + 同时推进 Equipment（SUSPECT）与 CollectionChannel（DEGRADED）两个聚合。单聚合无权观察时间流逝与联动另一聚合，由本服务在超时事件到达时同事务协调推进。

### 3.5 ReconnectService（重连服务）

**职责**：编排重连尝试与恢复/离线判定，触发补传；驱动 `ChannelEscalated` 升级。

```yaml
ReconnectService:
  方法:
    startReconnect(equipment_id):
      # SUSPECT 状态下启动重连尝试，递增 reconnect_attempts

    onReconnectSucceeded(equipment_id, gap_window, backfilled_msg_count):
      # 重连成功 -> 触发 BackfillService.onChannelRestored（先补传）
      # 补传完成 -> Equipment.recoverEquipment -> EquipmentRecovered（OFFLINE -> ONLINE）
      #            或 Equipment.clearSuspect（SUSPECT -> ONLINE）
      #            + CollectionChannel.restoreChannel（DEGRADED -> ESTABLISHED）

    onReconnectFailed(equipment_id, attempts):
      # 重连失败达 N 次 -> Equipment.markOffline -> EquipmentOffline（SUSPECT -> OFFLINE）
      #                 + CollectionChannel.enterBufferMode
      #                 + Equipment.escalateChannel(level) -> ChannelEscalated（发布到 dc.equipment.lifecycle）
      # 台账上下文消费 ChannelEscalated -> SuspendAsset(reason=CommunicationLost)（本上下文不停用 INV-CX-02）
```

> **为什么不放在聚合根内**：重连涉及重连尝试计数 + 触发补传（跨 BackfillService）+ 联动 Equipment / CollectionChannel 两个聚合 + 发布 `ChannelEscalated` 供台账停用。跨聚合编排与"先补传再恢复"顺序由本服务保证。

---

### 3.6 PlatformIngestionService（平台接入服务）

**职责**：编排平台层数据接入——去重、乱序矫正、落库、分发；保证 INV-04（msg_id 全局唯一）。

```yaml
PlatformIngestionService:
  方法:
    onPacketReceived(msg_id, source_ts, ingest_ts):
      # 1. 发出 PacketReceived（报文已被 Broker 接收）
      # 2. 去重 Deduplicate：按 msg_id 查去重表
      #    命中 -> DuplicateDiscarded（BIZ-02）
      #    未命中 -> PacketAccepted
      # 3. 乱序窗口缓冲 BufferReorder：按 source_ts 排序
      #    乱序到达 -> LateArrivalReordered（迟到矫正，打 LATE 质量标）
      # 4. 落库 + 分发 PersistAndPublish：
      #    DataPacket.markPersisted -> PacketPersisted
      #    DataPacket.markPublished -> PacketPublished（发布到下游 dc.* 主题）
```

> **为什么不放在聚合根内**：去重需查全局去重表（跨实例，msg_id 唯一索引（BIZ-02））；乱序矫正需维护时间窗口缓冲（跨多报文）；落库与分发涉及存储与消息总线。这些是跨报文实例的集成关注点，由本服务 + msg_id 去重表保证。`DataPacket` 聚合只承载单报文状态，本服务协调多报文的关系。

### 3.7 DeadLetterService（死信与协议异常服务）

**职责**：处理解码失败——落死信 + 连续失败升级协议异常告警；保证 INV-07。

```yaml
DeadLetterService:
  方法:
    onFrameDecodeFailed(equipment_id, channel_id, raw_bytes_ref, reason):
      # 1. 创建 DeadLetterEnvelope.store -> DeadLetterStored（INV-07：原始字节 + 原因 + retain_until）
      # 2. 检查 ProtocolAdapter.decode_fail_streak：
      #    连续失败达阈值 -> 发出 ProtocolAnomalyRaised（通知平台运维）
      # 3. 死信保留窗口结束 -> DeadLetterEnvelope.purge（定时驱动）

    onDecodeSucceeded(equipment_id):
      # ProtocolAdapter.resetFailStreak（清零连续失败计数）
```

> **为什么不放在聚合根内**：协议异常升级需要跨多帧统计连续失败次数（`ProtocolAdapter.decode_fail_streak`）+ 创建 DeadLetterEnvelope 聚合 + 发布 `ProtocolAnomalyRaised`。死信落地本身是 `DeadLetterEnvelope.store` 聚合行为，本服务负责"连续失败升级"策略编排。

### 3.8 RunHourAggregationService（运行时长聚合服务）

**职责**：基于自身观测的 `EquipmentOnline` / `EquipmentOffline` 区间，周期性聚合运行时长并发布；保证 BIZ-03。

```yaml
RunHourAggregationService:
  方法:
    onEquipmentOnline(equipment_id, at):
      # 加载/创建当班 EquipmentRunHourAggregation -> openSegment(at, ONLINE)

    onEquipmentRecovered(equipment_id, at):
      # openSegment(at, RECOVERED)（回填时段去重 BIZ-03）

    onEquipmentOffline(equipment_id, at):
      # closeSegment(at)

    onShiftEnd(equipment_id, period_end):
      # 班次结束定时驱动 -> EquipmentRunHourAggregation.publish(period_end)
      # -> EquipmentRunHourAggregated 发布到 dc.equipment.runtime
      # 台账上下文订阅后 AccrueRunHour 累计为 EquipmentRunHourAccrued（本上下文不代劳 INV-CX-02）
```

> **为什么不放在聚合根内**：聚合需要消费 Equipment 生命周期事件（跨聚合）+ 班次结束定时器驱动 + 同 `equipment_id + period` 去重（跨实例，BIZ-03）。`EquipmentRunHourAggregation` 聚合承载单设备单班次区间，本服务负责跨班次/跨实例的编排与去重。**在线判定以本上下文自身观测为准，不依赖台账资产状态**（INV-CX-08 / INV-15）。

> **聚合精度**（承接事件风暴 §2.4）——秒级 Online/Offline 区间累加到 1 位小数小时精度足够。保留 1 位小数（如 7.5h），与台账 `run_hours` 精度一致。

### 3.9 AlarmNormalizationService（报警归一化服务）

**职责**：将各设备协议的报警帧归一化为统一的 `EquipmentAlarmRaised` / `EquipmentAlarmCleared`，经 `AlarmSeverityMapping` 解析 severity；保证 INV-09 / INV-10。

```yaml
AlarmNormalizationService:
  方法:
    onAlarmFrameReceived(equipment_id, alarm_code, source_protocol, model, frame_kind):
      # frame_kind = ALARM_RAISED / ALARM_CLEARED
      # 1. 查 AlarmSeverityMapping：按 model + alarm_code 解析 severity（配置驱动 INV-09）
      # 2. 加载/创建 EquipmentAlarm 聚合：
      #    ALARM_RAISED -> EquipmentAlarm.raise(frame, severity_mapping) -> EquipmentAlarmRaised
      #      幂等：活跃期间不重复 Raised（INV-10）
      #    ALARM_CLEARED -> EquipmentAlarm.clear(frame) -> EquipmentAlarmCleared
      #      幂等：已 Cleared 不重复 Cleared（INV-10）
      # 3. 发布到 dc.equipment.alarm.raw（不翻译，含 severity 分级）
      # 台账上下文按 severity=CRITICAL 消费 -> SuspendAsset(reason=CriticalAlarm)（本上下文不停用 INV-CX-02）
```

> **为什么不放在聚合根内**：归一化需要查 `AlarmSeverityMapping`（配置值对象，跨设备共享）+ 加载/创建 `EquipmentAlarm` 聚合（跨实例幂等 INV-10）+ 按帧类型分流 Raised/Cleared。severity 解析的纯查表逻辑在 `AlarmSeverityMapping`，Raised/Cleared 的状态机与幂等在 `EquipmentAlarm` 聚合，本服务负责编排。

> **severity 映射规则**（承接事件风暴 §3.10）——口径：**severity=CRITICAL 仅用于必须立即停用资产的报警**（安全联锁、关键部件失效、通信丢失等），台账消费后执行 `SuspendAsset(reason=CriticalAlarm)`；WARNING / INFO 走通知服务人工告警。分级由 `AlarmSeverityMapping` 配置驱动，映射规则归工程标准（人工告警由通知服务订阅 `dc.equipment.alarm.raw`，非独立限界上下文）。

## 4. 应用服务

应用服务是**外部调用入口**，负责：接收请求 / 事务边界 / 调用领域服务编排 / 发布集成事件。本上下文是支撑域，应用服务以"高吞吐采集入口 + 定时驱动 + 跨上下文事件消费 + 实时查询"为主。

### 4.1 IngestionAppService（采集入口应用服务）

**职责**：网关上行原始帧 / 设备特定事件的高吞吐采集入口，委托采集主链各领域服务。

```yaml
IngestionAppService:
  方法:
    ingestRawFrame(equipment_id, raw_frame):
      # 委托 FrameIngestionService.onRawSignal
      # 事务边界：单帧采集主链（解码->打标->封装->缓冲/投递）
      # 高吞吐：批量/异步落库，Outbox 保证不丢

    ingestDeviceEvent(equipment_id, device_event):
      # 设备特定事件（经 DecodingStrategy 已结构化）-> DataPacket 封装 -> 上行
      # 委托 FrameIngestionService（设备特定事件分支）

    ingestAlarmFrame(equipment_id, alarm_code, source_protocol, frame_kind):
      # 委托 AlarmNormalizationService.onAlarmFrameReceived
```

| 用例 | 事务边界 | 调用领域对象 | 产出事件 | 幂等策略 |
|------|----------|--------------|----------|----------|
| 采集原始帧 | 单帧事务 | `FrameIngestionService` + `ProtocolAdapter` / `DataPacket` / `BackfillCursor` | `RawSignalEmitted` / `DataPointDecoded` / `DataPacketSealed` / `EdgeBuffered` / `PacketDispatched` / `BackfillEnqueued` | `msg_id`（BIZ-02） |
| 采集设备事件 | 单帧事务 | `FrameIngestionService`（设备特定分支） | §3 各设备特定事件 | `msg_id` |
| 采集报警帧 | 单帧事务 | `AlarmNormalizationService` + `EquipmentAlarm` | `EquipmentAlarmRaised` / `EquipmentAlarmCleared` | `(equipment_id, alarm_code, 活跃期间)`（INV-10） |

### 4.2 ChannelCommandAppService（通道命令应用服务）

**职责**：通道/设备命令入口（REST，发命令者：平台运维/设备工程师）——手动重连、手动关闭、协议重载等。

```yaml
ChannelCommandAppService:

    getRealtimeDataPoints(equipment_id, logical_names):
      # 委托 DataQueryAppService（过点实时数据查询入口 INV-CX-04）
```

### 4.3 LedgerEventConsumerAppService（台账事件消费应用服务）

**职责**：订阅台账上下文资产生命周期事件，翻译为本上下文命令，委托 `GatewayBindingService`。

```yaml
LedgerEventConsumerAppService:
  订阅主题与处理:
    # 台账上下文（主题前缀 eam.*）
```

## 6. 不变规则（Invariants）

不变规则是领域模型中**必须始终为真**的业务约束，无论经过何种操作序列。按**一致性边界**分为三段，**分别编号、不可混列**（编号在此首次诞生；事件风暴侧以无编号"已识别约束"清单对应，见 [事件风暴 - 设备数据接入上下文](../事件风暴/设备数据接入上下文.md#已识别约束)）：

- **聚合不变式（`INV-XX`）**：落在单一聚合的一致性边界内，事务内强一致、始终为真，由聚合根前置条件 / 状态机 / 规约守护，**按所属聚合根分子节归位**。
- **业务不变式（`BIZ-XX`）**：本上下文内跨聚合 / 跨实例，一致性边界与任意单事务无法重合，最终一致，由领域服务 + 唯一索引 / 事件去重表 / Saga 守护，**禁止挂在聚合根上**。
- **跨上下文不变式（`INV-CX`）**：跨限界上下文，最终一致，由事件订阅 + ACL + 跨服务协调守护（同服务部署时可走本地事务强一致，见各条说明）。

### 6.1 聚合不变式（Aggregate Invariants）

按所属聚合根分子节归位。

**原则**：
- 应用服务不包含业务逻辑，只做编排和事务边界（CLAUDE.md 分层）
- 领域服务封装跨聚合的采集链路规则，每个领域服务必答"为什么不放在聚合根内"
- 聚合根内的业务逻辑由聚合根自身保证，行为是业务动词方法（非 `update/save` 流水账）
- 不变式由聚合根 + 领域服务 + 唯一索引/事件去重表共同守护
- **采集只搬运不解释**是贯穿性硬约束（INV-CX-01），所有领域服务与应用服务不得越界做业务判定
